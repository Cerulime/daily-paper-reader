# Beyond Predefined Sinks: Security-Aware Dependency Analysis for LLM Agents 

HANG CUI 

Large language model (LLM)-based agents increasingly connect model-generated decisions to security-sensitive software capabilities, including command execution, filesystem access, network communication, browser control, and external tools. Existing analyses often use predefined sensitive operations to anchor their analysis, but operation identity alone is insufficient to determine the security implications of an agent behavior. We present AgentSecGraph, a security-aware static analysis framework that constructs a candidate-centered Security-Aware Agent Dependency Graph (Security-ADG) for each security-sensitive operation. The representation augments operation identity with agent relevance, source and dependency evidence, trust-boundary context, guard evidence, and external-effect semantics. We further introduce AgentSecBench, a reproducible corpus of 67 real-world LLM-agent repositories spanning 11 agent ecosystems and 37,542 source files. Applying the current analyzer to all frozen repositories yields 23,866 static security-sensitive operation candidates across 65 repositories, for which AgentSecGraph emits 23,866 candidate-centered Security-ADG artifacts without reported construction failures. Corpus-wide analysis recovers source-to-operation dependency evidence for 9,821 candidates (41.15%) and potential guard evidence for 3,075 (12.88%). The complete analysis finishes in 50.8 minutes. Using a separate reproduction-backed evaluation layer, we establish a conservative reference set of 22 security-sensitive behaviors across 13 repositories: one confirmed vulnerability, one pending disclosure candidate, and 20 guarded behaviors that do not meet the vulnerability criteria. In a held-out representation study, Security-ADG preserves 91.1% of the reference context and all five observed guards, compared with 20.0% for a sink-only view and 40.0% for a simplified ADG. These results show that security-aware dependency and contextual evidence enable distinctions that cannot be recovered from sensitive-operation identity alone. 1 Introduction 

Large language model (LLM)-based agents are rapidly evolving from text-generating assistants into software systems capable of planning, invoking tools, maintaining state, and interacting with external environments. Early paradigms such as ReAct [36] and Toolformer [27] demonstrated how language models can interleave reasoning with external actions. Modern frameworks, including LangChain [5], LangGraph [18], AutoGen [33], and CrewAI [7], provide reusable abstractions for tool invocation, memory, workflow orchestration, and multi-agent coordination. The Model Context Protocol (MCP) [2] extends this ecosystem by standardizing access to external tools and resources. This transition fundamentally changes the security boundary of LLM applications. In a conven-tional chatbot, an unsafe model output may remain textual; in an agent system, the same output can influence command execution, filesystem operations, browser actions, database access, or remote services. Agent behavior may additionally depend on user instructions, retrieved docu-ments, memory contents, model-generated plans, tool outputs, and messages from other agents. Untrusted information can therefore cross multiple software and trust boundaries before affecting an externally visible operation. Prior work has demonstrated these risks through indirect prompt

Static program analysis provides a natural foundation for reasoning about these behaviors. 2 Motivation and Problem Formulation 

LLM-agent software differs from conventional language-model applications: model-mediated deci-sions can directly trigger executable capabilities. Modern agents combine tools, memory, retrieval, workflows, and multi-agent communication [5, 7, 18, 27, 33, 36], while protocols such as MCP [2] standardize access to external tools and resources. These capabilities introduce security-relevant relationships that are often hidden behind frame-work abstractions such as tool decorators, workflow nodes, dynamically registered functions, plugins, and inter-agent handoffs. Consequently, security analysis must reason not only about host-language operations, but also about how agent-facing inputs can access and influence those operations. 

2.1 Agent-Specific Security Semantics 

Untrusted information in an agent application may originate from user instructions, retrieved documents, web content, memory, model outputs, or external tools. Such values may subsequently influence command execution, filesystem access, network communication, browser actions, database operations, or other externally visible effects. Static source–sink and taint analysis provides a natural foundation for recovering these relation-ships. Classical program representations such as Program Dependence Graphs (PDGs) [12] capture data and control dependencies, while systems such as FlowDroid [3] and YASA [30] demonstrate precise and scalable source–sink reasoning. Recent work extends these ideas to LLM-integrated software: TaintP2X [14] traces LLM-generated values toward sensitive operations, Agent Au-dit [39] incorporates agent-specific configuration and privilege information, and AgentFuzz [22] dynamically searches for inputs that trigger sensitive behavior. However, LLM-agent software introduces an additional semantic layer. A parameter exposed through an agent tool interface has different security implications from an unrelated internal parameter, even if both eventually reach the same low-level API. Framework-induced relationships must therefore be interpreted alongside ordinary program dependencies. 

2.2 Why Sink Identity Is Insufficient 

Figure 1 illustrates the central limitation of operation-only analysis. All three examples contain the same command-execution operation, but their security semantics differ: one preserves a direct dependency from an agent-facing input, one removes that dependency through a constant overwrite, and one retains the dependency while introducing an allowlist guard. This observation motivates a distinction among three levels of evidence. A security-sensitive operation candidate is a source-code operation that may produce or prepare a security-relevant external effect. A security-critical behavior combines such an operation with agent-specific depen-dency and contextual evidence. A vulnerability is a stronger conclusion that additionally depends on factors such as controllability, protection mechanisms, deployment exposure, authorization, privilege, impact, and exploitability. Accordingly, Sensitive Operation ≠ Security-Critical Behavior ≠ Vulnerability . (2) Predefined operation specifications are therefore useful for locating code that deserves further analysis, but operation identity should be treated as an analysis anchor , not as a vulnerability verdict. 3 AgentSecGraph 3.1 Overview 

AgentSecGraph is a static analysis framework for recovering auditable security-relevant evidence associated with sensitive operations in LLM-agent software. Rather than interpreting a matched operation as a security violation, AgentSecGraph treats it as an analysis anchor and builds a candidate-centered Security-ADG for it. Given a candidate operation 𝑜 ∈ O , AgentSecGraph determines how the operation is exposed to agents, recovers relevant source-to-operation dependencies, extracts trust-boundary and guard evidence, and summarizes the resulting security context using 𝐶 (𝑜 ) from Equation 4. Figure 2 summarizes the end-to-end workflow. The framework deliberately separates static evidence recovery from vulnerability assessment. Its output records only what can be established from the frozen source snapshot and retains uncertainty when the conclusion depends on runtime, deployment, or threat-model evidence. 

3.2 Candidate Anchoring and Framework Normalization 

The analysis begins with security-sensitive operation candidates 𝑜 ∈ O . Each candidate is associated with its frozen repository snapshot, source location, operation category, detector provenance, and local code context. Candidate generation is intentionally permissive. A match establishes that a potentially security-relevant capability exists, but not that the capability is agent-controlled, reachable from an untrusted source, insufficiently guarded, or exploitable. 6 Hang Cui

The current implementation supports representative constructs from MCP/FastMCP, LangChain, CrewAI, AutoGen, OpenAI Agents SDK, Semantic Kernel, and LlamaIndex. The supplementary material documents the normalization contract, supported construct families, and matching rules.

3.4 Dependency, Trust-Boundary, and Guard Analysis 

Starting from values consumed by a candidate operation, AgentSecGraph performs backward dependency recovery to identify whether a recognized source may influence the candidate. Con-ceptually, the analysis seeks a local chain 

𝑠 ⇝ 𝑣 1 ⇝ · · · ⇝ 𝑣 𝑜 → 𝑜, (8) where 𝑠 is an agent-relevant or externally influenced source and 𝑣 𝑜 is consumed by operation 𝑜 .For Python, dependency recovery is AST-based and follows local parameters, assignments, definitions, and reassignments. For example, if an agent-facing parameter is overwritten by a constant before reaching the candidate, the corresponding dependency is terminated. For TypeScript and JavaScript, the current implementation performs syntax-aware lexical back-ward tracing over local parameters, definitions, assignments, and supported registration patterns. This analysis is more conservative than the Python engine and does not provide complete alias, type, or control-flow reasoning. Dependency evidence alone does not imply that a behavior is unsafe. AgentSecGraph therefore also records evidence of safeguards and trust boundaries. Representative guard evidence includes allowlists, fixed-argument or argument-vector command construction, schema or syntax validation, authentication checks, path restrictions, sandboxing, and resource limits. A may_guard edge indicates only that defensive evidence is visible; it does not prove that the guard is complete or effective. Similarly, may_cross records available evidence that an external, agent-facing, or otherwise less-trusted value may influence a local or more privileged capability, while deployment-dependent trust and privilege may remain unknown. The current implementation represents privilege context only when explicit evidence is recov-erable from supported source-level constructs. It does not infer deployment identities, ambient permissions, or runtime authorization state. Likewise, every candidate is deterministically mapped to an abstract external-effect category. The resulting effect node encodes modeled semantics rather than a runtime-confirmed effect and is therefore a schema property, not an empirical recovery result. The recovered evidence is summarized using the security-context tuple 𝐶 (𝑜 ) defined in Equa-tion 4, whereas the graph itself preserves source-level provenance and relationships for inspection. In particular, 𝐷 (𝑜 ) = true means that dependency evidence was recovered; it does not imply Vulnerability (𝑜 ) = true. 

3.5 Implementation and Analysis Contract 

AgentSecGraph is implemented as a modular source-analysis pipeline with language-specific analyzers, framework adapters, and deterministic graph generation. The Python engine uses the language AST to recover enclosing scopes, parameters, local defi-nitions, assignments, decorators, and backward def–use relationships. The TypeScript/JavaScript engine performs syntax-aware lexical tracing and explicitly records the weaker guarantees provided by this approach. Framework adapters map framework-specific tool declarations and capability-registration mech-anisms into the normalized representation from Equation 6. The adapter layer is independent of the graph schema, allowing new frameworks to be supported without redesigning Security-ADG. For each candidate, the implementation emits a candidate-centered Security-ADG together with source-level provenance and analysis metadata. We report graph construction as successful when the deterministic pipeline emits exactly one graph artifact linked to the original candidate identifier and source provenance. This measures one-to-one generation and linkage, not the semantic correctness Beyond Predefined Sinks 9

or completeness of recovered relationships. It also derives three deterministic representation views from the same candidate: (1) sink-only , retaining only the sensitive operation; (2) simplified ADG , retaining structural operation and external-effect information; and (3) full Security-ADG, retaining source/dependency, trust-boundary, guard, and external-effect evidence. These projections allow representation-level comparisons without changing the underlying candidate population. All analyses operate on repositories frozen at recorded Git commits. Candidate-generation rules, framework adapters, dependency logic, and graph construction are independent of human annota-tions, model-generated security judgments, reproduction outcomes, and vulnerability dispositions. The current analysis is intentionally local. Python analysis is not a complete whole-program interprocedural, alias, points-to, or symbolic analysis, and TypeScript/JavaScript tracing does not provide sound, complete alias or control-flow analysis. Reflection, dynamic registration, metapro-gramming, and deployment-dependent exposure or privilege may therefore produce incomplete evidence. Accordingly, Security-ADG should be interpreted as an auditable static evidence representa-tion for a candidate operation, not as a proof of reachability, exploitability, guard sufficiency, or vulnerability. 

4 Evaluation 

We evaluate AgentSecGraph on frozen snapshots of real-world LLM-agent repositories. Our four questions concern corpus-wide coverage and scalability, conservative behavior-level ground truth, distinctions beyond sink identity, and the security context preserved by Security-ADG. Throughout the evaluation, we distinguish three levels of evidence: static candidates , reproduction-confirmed behaviors , and vulnerability dispositions . Static candidates are analysis inputs rather than vulnerability labels. 

4.1 Evaluation Populations and Experimental Setup 

Corpus construction. AgentSecBench is a corpus of publicly available LLM-agent repositories drawn from diverse ecosystems, including MCP-based systems, coding agents, framework-based applications, autonomous agents, and multi-agent platforms. We retain repositories containing substantive agent logic and analyzable source code while excluding duplicates, mirrors, trivial examples, and repositories unsuitable for reproducible source-level analysis. Repository inclusion is independent of AgentSecGraph output. Each retained repository is frozen at a recorded Git commit so that candidate extraction, graph construction, reproduction, and evaluation refer to the same source snapshot. The supplementary material documents the collection criteria and aggregate corpus composition. The public artifact repository provides the complete row-level repository inventory and immutable commit identifiers. 4.2 Reproduction-Confirmed Ground Truth 

Static candidates do not constitute behavior or vulnerability ground truth. We therefore establish a conservative reference set through targeted reproduction. Validation progresses from source inspection to controlled behavioral confirmation using, where appropriate, isolated execution, stubbing or monkeypatching of external effects, or paired attack–defense tests. A case enters the reference set only if the relevant behavior can be tied to the frozen source snapshot. Model assistance may support diagnostics or test scaffolding, but model judgments are never treated as ground-truth labels. The resulting set contains 22 reproduction-confirmed behaviors across 13 repositories. Each case retains its frozen source location, Security-ADG instance, and recovered dependency path. We conservatively assign each case one of three dispositions: 

• Vulnerability ground truth : reproduction and security evidence support a vulnerability conclusion under the evaluated threat model; 

• Pending disclosure candidate : the behavior warrants further coordination or validation but is not treated as confirmed vulnerability ground truth; and 

• Guarded non-vulnerability : the behavior is reproducible, but observed protections or usage constraints do not support a vulnerability conclusion under the tested conditions. Table 2 summarizes the reference set alongside the corpus-wide analysis population. The supplementary material documents the auxiliary 344-operation inventory and matching protocol. Incomplete independent adjudication precludes aggregate recovery metrics and exhaustive repository-wide ground-truth claims.

Only one case currently satisfies our criteria for vulnerability ground truth; one additional case remains pending disclosure, while 20 are guarded behaviors that do not meet the vulnerability criteria under the evaluated conditions. This distribution shows that reproducing a sensitive behavior does not by itself establish a vulnerability. Even when an agent-facing value reaches a powerful capability, deployment exposure, authorization, privilege, guards, and impact remain relevant to the vulnerability determination. 

Finding. Reproduction-backed validation provides auditable behavior-level evidence while pre-serving the distinction between security-sensitive behavior and vulnerability. Neither static candi-dates nor model-generated judgments are used as ground truth. 

4.5 RQ3: Beyond Sink Identity 

Question. What security-relevant distinctions does Security-ADG expose beyond sensitive-operation identity alone? Results. Across the reproduction-confirmed cases, superficially similar sensitive operations ex-hibit materially different security contexts. Recurring patterns include direct versus removed source dependencies, guarded versus unguarded execution, validation paths versus effectful execution paths, and identical low-level operations exposed under different agent or trust contexts. For example, an agent-facing parameter may directly influence command execution in one case but be overwritten by a constant in another. Similarly, an otherwise equivalent dependency path may be accompanied by an allowlist, authentication check, fixed argument construction, path restriction, or sandboxing mechanism. A sink-only representation cannot express these distinctions because it records only operation identity. Security-ADG instead retains source provenance, dependency, trust-boundary, guard, and effect evidence associated with the same candidate. 

Finding. Sensitive-operation identity is useful for candidate discovery but insufficient for security interpretation. The additional dependency and security-context evidence preserved by Security-ADG distinguishes behaviors that appear equivalent under an operation-only view.

5 Discussion and Threats to Validity 5.1 Interpreting “Beyond Predefined Sinks” 

Our results do not imply that predefined security-sensitive operations should be discarded. Such specifications remain a practical and scalable mechanism for locating code that warrants further Beyond Predefined Sinks 15 

analysis. The limitation is that operation identity alone does not determine whether an operation is agent-influenced, whether it crosses a trust boundary, or what protection mechanisms constrain its use. Accordingly, “beyond predefined sinks” refers to augmenting sink identity rather than replacing sink specifications. AgentSecGraph uses predefined operations as candidate anchors and then recovers agent semantics, source provenance, dependency, trust-boundary, guard, and external-effect evidence for each one. This distinction is reflected in the representation study: retaining only operation identity pre-serves substantially less independently supported security context than the full Security-ADG. The benefit of Security-ADG therefore lies not in eliminating sink specifications, but in providing the evidence needed to interpret superficially similar operations differently. 

5.2 From Security Evidence to Vulnerability 

A reproduced security-sensitive behavior is not necessarily a vulnerability. The reproduction study demonstrates this distinction directly: behaviors can be tied to frozen source snapshots and exercised under controlled conditions while still being constrained by validation, authorization, sandboxing, fixed argument construction, deployment assumptions, or intended usage. Static evidence should therefore be interpreted according to its strength. A recovered dependency indicates that the available source-level evidence supports a possible influence from an agent-relevant value to a sensitive operation. A recovered guard indicates that potentially relevant defensive evidence is visible. Neither observation alone proves exploitability, vulnerability, or safety. We therefore view Security-ADG as an evidence representation rather than a binary vulnerabil-ity classifier. Candidate-centered graphs support a staged workflow: inexpensive static analysis identifies and contextualizes behaviors, and costlier reproduction and security review examine cases that warrant it. This separation also supports security auditing, candidate prioritization, regression analysis, and responsible-disclosure triage, provided that these uses preserve the distinction between evidence and vulnerability conclusions. 

5.3 Limitations and Threats to Validity 

Construct and internal validity. Our evaluation relies on distinctions among sensitive operations, security-critical behaviors, and vulnerabilities, as well as on the context dimensions in Security-ADG. These abstractions omit some deployment-dependent factors. Context completeness measures represented evidence, not proven reachability or exploitability; guard visibility does not establish sufficiency. Errors in candidate rules, adapters, dependency recovery, or reproduction could affect the results. We mitigate this risk by freezing snapshots and analysis configurations before evaluation, separating graph construction from labels, and retaining source locations, graphs, and dependency evidence. The analysis is intentionally incomplete. Python recovery is local and AST-based, not a sound whole-program, alias, points-to, or symbolic analysis. TypeScript and JavaScript rely on weaker, syntax-aware lexical tracing. Reflection, dynamic registration, metaprogramming, or deployment-specific exposure and privilege may therefore yield missing or imprecise evidence. Privilege context is represented only when explicit evidence is recoverable from supported source-level constructs; the current full-corpus extraction recovers none. In addition, the available corpus-wide aggregates report identical source, dependency, and trust-crossing counts. We therefore do not interpret them as three independent recovery measurements or claim an independently validated trust-boundary recovery rate. 16 Hang Cui 

External validity. AgentSecBench contains 67 frozen repositories from 11 agent ecosystems but is not statistically representative of the entire ecosystem. Availability, selection criteria, and open-source access shape its composition. Python dominates the sample, and AgentSecGraph analyzes Python dependencies more strongly than TypeScript/JavaScript dependencies; aggregate results are therefore not language-independent performance estimates. 

Conclusion validity. The current full-corpus candidate population is generated by a later scanner version than the frozen five-repository pilot manifest. The 23,866-candidate full-corpus population and historical 531-candidate cohort are therefore not directly comparable as a corpus-size scaling experiment. Re-running the current scanner on the same five snapshots yields 508 candidates because language scoping and AST filtering changed; we preserve the historical manifest rather than merging the populations. Corpus-wide evidence frequencies are descriptive properties of the current analyzer and bench-mark. They neither estimate vulnerability prevalence nor establish recall with respect to all security-relevant behaviors in the repositories. The reported timing comes from one completed run rather than a repeated-run distribution, and the archived aggregate does not include peak memory usage; scalability conclusions are correspondingly limited to the observed run. The five-model panel was used only to prioritize candidate inspection and did not determine reference-set eligibility. Because this triage may nevertheless influence which cases receive earlier manual attention, we do not treat the reproduction set as an unbiased estimate of corpus-wide behavior prevalence. The reference set contains 22 behaviors across 13 repositories; the representation study contains nine held-out cases, including five with guard evidence. These samples support the reported case-and representation-level findings, but not exhaustive recall or general vulnerability-detection claims. We therefore do not use precision, recall, or F1 as primary metrics for the reference set. Incomplete adjudication likewise precludes matched counts or aggregate recovery metrics for the 344-operation inventory. Likewise, 91.1% context completeness and 5/5 guard visibility describe the evaluated cases rather than universal performance. 

6 Related Work 6.1 Security Evaluation of LLM Agents 

The growing autonomy of LLM agents has motivated extensive work on their attack surfaces. Prior studies demonstrate indirect prompt injection [13, 24, 37], evaluate attacks and defenses in realistic agent environments [9], and study unsafe agent–tool interactions [26]. Broader benchmarks exam-ine security failures across prompts, tools, and memory [38], harmful multi-step agent misuse [1], and real-world software-security tasks [19]. Recent work broadens the threat model beyond prompt injection to poisoned agent memory [6], web-agent compromise [11], resource abuse [25], and MCP-specific risks [16, 31, 32, 40]. A recent systematization organizes the design, attack, and defense landscape of agentic systems [17]. Large-scale ecosystem evidence also shows that third-party agent skills can carry deliberately malicious instructions and helper code [23]. These studies primarily focus on attack generation, adversarial evaluation, or vulnerability bench-marking. AgentSecGraph addresses a complementary problem: recovering auditable dependency and security-context evidence through static analysis of sensitive behavior in real-world agent source code. Beyond Predefined Sinks 17 

6.2 Program Analysis for Agent Security 

Traditional program analysis provides several foundations for security-oriented dependency rea-soning. Program Dependence Graphs (PDGs) capture control and data dependencies [12], while Code Property Graphs integrate syntax, control flow, and dependence information into a unified representation for vulnerability discovery [35]. Declarative systems such as QL further demon-strate that expressive program queries can scale to large codebases [4]. Dynamic information-flow tracking in TaintDroid [10] and static source–sink analyses such as FlowDroid [3] and YASA [30] provide complementary taint-oriented reasoning. Recent work adapts these techniques to LLM-integrated software. AgentFuzz [22] dynamically searches for inputs that drive agents toward sensitive operations. TaintP2X [14] statically traces LLM-generated values toward sensitive sinks, while Agent Audit [39] combines agent-aware data flow with credential, configuration, and privilege analysis. AgentSecGraph differs in its analytical objective. Rather than treating a predefined source–sink relation as sufficient to characterize security risk, it uses sensitive operations as candidate anchors and augments them with agent semantics, source provenance, dependency, trust-boundary, guard, and external-effect evidence. 

6.3 Security Enforcement for LLM Agents 

A complementary line of work aims to prevent unsafe agent behavior through isolation, information-flow control, and least-privilege enforcement. IsolateGPT [34] isolates LLM-integrated applications from system resources, CaMeL [8] separates trusted control flow from untrusted data, Progent [28] introduces programmable least-privilege policies over tool calls, and ACE [21] separates planning from execution while enforcing information-flow and capability boundaries. AttriGuard instead performs runtime causal attribution of tool invocations to identify actions driven by untrusted observations [15]. These systems primarily enforce security policies at runtime. AgentSecGraph is complementary: it does not enforce a policy, but statically records evidence about trust boundaries, guards, statically available privilege context, and external effects so that existing agent software can be audited.

7 Conclusion 

LLM-agent software connects model-generated decisions to security-sensitive capabilities, making operation identity alone insufficient for interpreting security-relevant behavior. We presented AgentSecGraph, a static analysis framework that treats sensitive operations as candidate anchors and constructs candidate-centered Security-ADG representations. By preserving agent relevance, provenance, dependencies, trust boundaries, candidate guards, available privilege information, and external effects, AgentSecGraph separates operation detection from security interpretation. We also introduced AgentSecBench, a reproducible corpus of 67 frozen repositories spanning 11 ecosystems and 37,542 source files. Applying the current analyzer to the full corpus yields 23,866 static security-sensitive operation candidates across 65 repositories, for which AgentSecGraph emits 23,866 candidate-centered Security-ADG artifacts without reported construction failures. Corpus-wide analysis recovers source-to-operation dependency evidence for 41.15% of candidates and potential guard evidence for 12.88%, completing in 50.8 minutes. A separate reproduction-backed evaluation establishes a conservative reference set of 22 behav-iors: one confirmed vulnerability, one pending disclosure candidate, and 20 guarded behaviors that did not meet the vulnerability criteria. In the held-out study, Security-ADG preserves 91.1% of the reference context and all five observed guards, compared with 20.0% for a sink-only view and 40.0% for a simplified ADG; neither reduced view exposes the guards. These results support the central conclusion of this work: predefined sensitive operations remain useful analysis anchors, but security-critical behavior in LLM-agent software is interpreted more faithfully when operation identity is augmented with dependency and security-context evidence.

A AgentSecBench Repository Inventory and Collection Criteria 

AgentSecBench contains 67 publicly available LLM-agent repositories spanning 11 agent ecosys-tems. Corpus construction was performed independently of AgentSecGraph output. We retained repositories with substantive agent logic and analyzable source code, including MCP-based systems, coding agents, framework-based applications, autonomous agents, and multi-agent platforms. We excluded duplicates, mirrors, trivial examples, and repositories unsuitable for reproducible source-level analysis. Each retained repository is identified by its repository coordinate and an immutable Git commit. Candidate extraction, graph construction, reproduction, and evaluation use that same frozen snapshot. The machine-readable frozen corpus manifest in the public artifact repository provides the complete row-level repository inventory and commit identifiers; the PDF reports the aggregate composition in Table 7 rather than duplicating the long manifest. The nine repositories in the remaining-language group primarily use C#, Rust, Go, PHP, or Shell. Repository inclusion is not conditioned on candidate counts, graph construction outcomes, reproduction outcomes, vulnerability dispositions, or model-generated judgments. The frozen manifest is therefore an input to the evaluation rather than an output selected by the analyzer.

E.4 Population and Reproducibility Notes 

The full-corpus measurements above must not be compared directly with the historical 531-candidate frozen pilot cohort as though repository count were the only changing variable. The pilot manifest was generated by an earlier scanner configuration. Applying the current scanner to the same five frozen repository snapshots yields 508 candidates because subsequent language scoping and AST filtering changed candidate extraction. We therefore preserve the three populations separately: 

• Frozen pilot cohort: 531 candidates from five repositories, retained for compatibility with historical pilot and annotation studies; 

• Current five-repository scan: 508 candidates on the same repository snapshots, used only to document scanner-version drift; and 

• Current full-corpus run: 23,866 candidates from all 67 frozen repositories, used for the corpus-wide characterization and scalability results reported above. None of these candidate populations constitutes a vulnerability count, and this descriptive corpus-wide experiment does not establish repository-wide recall. 

F Inventory-Bounded Evaluation 

The main evaluation uses corpus-wide descriptive measurements, reproduction-confirmed behavior evidence, and a held-out representation-preservation study. We additionally retain an auxiliary source-level operation inventory to provide bounded evidence about operation recovery on code that was separated from development-time method tuning. This evaluation is deliberately described as inventory-bounded . The finite inventory does not establish that every relevant operation in either repository has been enumerated and therefore cannot support claims of repository-wide exhaustive recall. 

F.1 Held-Out Operation Inventory 

The frozen inventory contains 344 source-level operation records from two repositories: 

• dddabtc/winremote-mcp : 148 operation records; and 

• nexu-io/html-anything : 196 operation records. The two repositories were held separate from development-time method tuning when this inventory was constructed. The inventory covers eight security-sensitive operation categories. 28 Hang Cui 

The category distribution is not intended to estimate the prevalence of security-sensitive opera-tions in the broader LLM-agent ecosystem. It describes only the frozen auxiliary inventory used for this bounded evaluation. 

F.2 Reference Evidence 

Inventory entries are tied to frozen source locations and are reviewed using inspectable source-level evidence. Where stronger validation is available for a corresponding behavior, the evaluation distinguishes among the following evidence levels: 

• Source-level evidence , establishing that a relevant program construction or dependency exists in the frozen source snapshot; 

• Stub or monkeypatch evidence , establishing which call or argument is produced under a controlled input; 

• Isolated execution evidence , establishing that the corresponding external effect occurs in a controlled environment; and 

• Attack–defense paired evidence , evaluating whether a candidate protection mechanism constrains the corresponding behavior. These evidence levels are not interchangeable. In particular, the 344-operation inventory primarily serves as a source-level operation inventory and is not itself a set of confirmed vulnerabilities. Model-generated judgments are not treated as reference labels. 

F.3 Prediction-to-Reference Matching 

Method outputs are matched to inventory entries using the frozen matching rule match = repository + commit + file + operation category + line overlap . (11) No label-dependent line tolerance or manual per-item matching is introduced after evaluation. A reference inventory record is considered recovered only when a method output satisfies the frozen matching rule. Let 𝐼 denote the 344-operation reference inventory and let 𝑀 denote the set of method outputs matched to records in 𝐼 . We define inventory-bounded recall as 

𝑅 inv = |𝑀 ||𝐼 | . (12) Because 𝐼 is a finite reviewed inventory rather than an exhaustive enumeration of all possible security-relevant operations in the two repositories, 𝑅 inv must not be interpreted as repository-wide recall. 

F.4 Evaluation Status and Claim Boundary 

The frozen inventory defines the finite population and the coordinate-level matching protocol used by the evaluator. At the time of this study, however, the independently adjudicated label file does not cover all 344 inventory items. The evaluator therefore refuses to emit aggregate or category-level recovery metrics, and we do not report matched counts, recall, precision, or F1 for this population. Results from the smaller reviewed sample are not substituted for full-inventory measurements. The inventory is retained here to document the evaluation population and protocol; completing the independent adjudication remains future work. Beyond Predefined Sinks 29 

F.5 Interpretation and Limitations 

This auxiliary evaluation serves a narrower purpose than the corpus-wide characterization in Section E. The latter measures how the current analyzer behaves over all 67 frozen repositories, whereas the 344-operation inventory provides a finite source-level denominator on two held-out repositories. The inventory therefore supports statements about recovery relative to its reviewed records, but not claims of exhaustive repository-wide recall. Likewise, an operation matched in this evaluation is not necessarily agent-controlled, exploitable, or vulnerable. Behavior-level and vulnerability conclusions remain governed by the separate reproduction-backed evidence layer described in the main paper.
