## 摘要
可信执行环境（TEE）通过远程认证向远端对等方证明代码和数据的完整性：TEE 使用硬件绑定密钥对其配置信息进行签名，从而签发认证报告，配置信息包括其内部加载代码的度量值（密码学摘要）。验证者通过将这些度量值与参考值进行匹配来评估该报告。然而，当被度量的工件为专有工件时，验证者无法自行推导参考值：它只能确认 TEE 内运行着具有给定度量值的某个东西——而无法确认程序的行为符合预期——从而被迫完全信任参考值提供方。我们提出一种无需披露工件即可弥合这一差距的架构，它组合了两个 TEE 工作负载：可证明构建（Hugenroth et al., 2025），其将源代码摘要绑定到构建工件的度量值；以及可证明审计（本文提出），其将同一源代码摘要绑定到在 TEE 内执行的自动化审计——模糊测试、静态分析、AI 代码审计、形式化方法——的判定结果。二者都是机密计算证明（Confidential Computing Proofs）的实例：将 TEE 认证视为一种硬件支持的零知识证明。将这两个证书链接起来，可使验证者得出结论：正在运行的工件是由满足所审计属性的源代码构建而来，且无需披露源代码或构建工件。在 Intel SGX 上使用 Gramine 库操作系统、对 Python 代码运行 Bandit 安全分析器的概念验证实现，证明了该方法的实用性。

## Abstract
Trusted Execution Environments (TEEs) prove the integrity of code and data to a remote peer through remote attestation: the TEE issues an attestation report by signing, with a hardware-bound key, its configuration information, including measurements (cryptographic digests) of the code loaded inside it. A verifier appraises the report by matching these measurements against reference values. When the measured artifact is proprietary, however, the verifier cannot derive the reference values itself: it can only confirm that something with a given measurement is running inside the TEE---not that the program behaves as expected---forcing full trust in the reference value provider. We propose an architecture that closes this gap without disclosing the artifact, composing two TEE workloads: attestable build (Hugenroth et al., 2025), which binds a source code digest to a build artifact measurement, and attestable audit (proposed in this paper), which binds the same source code digest to the verdicts of automated audits---fuzzing, static analysis, AI code auditing, formal methods---executed inside a TEE. Both are instances of Confidential Computing Proofs: TEE attestation viewed as a hardware-backed zero-knowledge proof. Chaining the two certificates lets the verifier conclude that the running artifact was built from source code satisfying the audited properties, without disclosing either the source code or the build artifact. A proof-of-concept implementation on Intel SGX with the Gramine Library OS, running the Bandit security analyzer on Python code, demonstrates the practicality of the approach.

# 论文结构化总结：Attestable Audit

## 1. 核心问题与整体含义

- **研究背景**：TEE（如 Intel SGX、AMD SEV-SNP、Intel TDX、AWS Nitro Enclaves）通过远程认证（Remote Attestation）向远端验证者证明内部代码与数据的完整性。其核心机制是"度量-比对"（measurement-and-comparison）：TEE 用硬件绑定密钥对包含代码度量值（如 SGX 的 `MRENCLAVE`、CVM 的 `MEASUREMENT`/`MRTD`、IMA 的文件哈希、CoCo 的 `MR_CONFIG_ID`）的配置信息签名，验证者将其与参考值比对。
- **核心痛点**：当被度量工件为**专有软件**时，验证者无法自行推导参考值（既无源码、也无公开可复现构建），只能依赖参考值提供方（通常是软件厂商）下发参考值。结果验证者只能确认"某个具有此摘要的东西在 TEE 内运行"，而**无法知道程序实际行为，也无法验证其是否具备任何属性**（如无后门）。
- **理论根源**：作者引用 Sadeghi 与 Stüble（2004）的观点——二进制摘要只是标识符，而非语义保证。验证者被迫对参考值提供方产生完全信任。
- **整体含义**：论文目标是在**不披露源码与构建工件**的前提下，把"仅凭摘要的信任"升级为"对代码语义属性的可验证信任"，从而移除对参考值提供方的信任依赖，实现专有工作负载的**基于属性的认证（Property-Based Attestation）**。

## 2. 方法论

### 2.1 核心思想
组合两个 TEE 工作负载，形成从"运行中工件度量"到"源码属性"的证书链：

- **可证明构建（Attestable Build，Hugenroth et al., 2025）**：在 TEE 内构建源码，将**源码摘要**绑定到**构建工件度量**。
- **可证明审计（Attestable Audit，本文提出）**：在 TEE 内对源码执行自动化审计（模糊测试、Valgrind、污点分析、静态分析、AI 代码审计、形式化方法等），将**同一源码摘要**绑定到**审计判定结果**。
- 二者统一为 **Confidential Computing Proofs（CCP）**——把 TEE 认证视为一种硬件支持的零知识证明：报告数据字段承诺了形如 ∃w. φ(x, w) 的量化命题。

### 2.2 关键符号与绑定关系
- `h_X = H(X)`：数据 X 的哈希摘要。
- `m_X := meas(X)`：认证报告绑定的工件度量（与普通哈希区分，例如 SGX 需经 `sgx_sign` 生成 `MRENCLAVE`）。
- `AR_X(d)`：工件 X 的认证报告，其 `REPORT_DATA` 字段绑定数据 d。
- **构建证书数据**：`d_Bld = (h_S, h_ConfBld, m_B)`，报告 `R_Bld = AR_Bld(H(d_Bld))`。
- **审计证书数据**：`d_Aud = (h_S, h_ConfBld, h_Aux, Conf_Aud, Verdict)`，报告 `R_Aud = AR_Aud(H(d_Aud))`。
- 其中 S 为专有工件（源码/权重/配置等，内容无关），Conf_Bld 为私有构建配置，Conf_Aud 为公开审计配置，Aux 为私有辅助输入（如形式化证明）。

### 2.3 端到端协议（7 步流程）
1. **认证（Certification）**：开发者用可证明构建器构建，得到 (d_Bld, R_Bld)；用可证明审计器审计源码 S，得到 (d_Aud, R_Aud)。
2. **部署**：将构建产物 B 部署到 attester 环境。
3. **证书投递**：把两份证书发给验证者。
4. **度量认证**：attester 与验证者完成常规远程认证，证明自身度量 m。
5. **构建认证**：验证者从公开发布物复现构建器度量 m_Bld，验证 R_Bld 的根信任、`REPORT_DATA = H(d_Bld)` 及度量字段。
6. **审计认证**：同理复现审计器度量 m_Aud，验证 R_Aud。
7. **证据链接（Chaining）**：校验 d_Bld 与 d_Aud 共享同一 `h_S` 与 `h_ConfBld`，且 d_Bld 中的 `m_B` 等于步骤 4 观测到的 m。由此证明：**运行中的工件由满足所审计属性的源码构建而来**。

### 2.4 安全论证与要点
- **绑定性（P1）**：伪造报告需攻破 TEE 根信任；篡改工作负载会改变 m_Bld/m_Aud，而验证者独立复现这些度量；混搭攻击（不同源码/配置/辅助输入）被第 7 步交叉校验拒绝；替换二进制会因度量不符而在第 4 步暴露。
- **非披露性（P2）**：除公开的 Conf_Aud 与 Verdict 外，传输内容均为摘要，不泄露 S、Conf_Bld、Aux、B（依赖哈希原像抗性）。
- **可证明构建器与审计器自身必须可公开审查**（开源且可复现构建，或公开二进制），否则信任只是转移而非消除。
- **选择性披露风险**：开发者可只披露有利的审计结果，故依赖方策略应规定所需的审计配置，而非被动接受任意结论。
- **CCP 关系（附录 B）**：给出 φ_Bld 与 φ_Aud 的具体形式，并指出两点优化——在 TEE 内直接计算 B 与 Verdict 避免重复计算；构建器同时输出 B 以便直接部署。

## 3. 实验设计

- **场景**：概念验证（PoC）实现，无传统意义上的数据集或 benchmark。

## 6. 主要结论与发现

- 指出了专有软件远程认证中的**根本性信任缺口**：度量比对只能给出标识性保证，无法给出语义属性保证。
- 提出将**可证明构建与可证明审计组合**的架构，用 CCP 把源码摘要分别链接到构建产物度量与审计结论，从而让验证者在**不披露源码与构建产物**的情况下，得出"运行工件由满足所审计属性的源码构建"的结论。
- 理论上将可证明构建与可证明审计统一为 Russinovich 等人的 **CCP 框架**（硬件支持的 ZKP 替代方案）。
- PoC 表明：借助 Intel SGX + Gramine，用现成的 Bandit 工具即可生成绑定审计结论的 CCP，架构**在工程上可行**。
- 补充结论：该架构与 attester/工件类型无关（可适配 SGX 应用、IMA 度量主机上的脚本、CVM 中的专有 LLM 权重）；与 CTS 互补（CTS 可发布与时间戳化这些声明），与 PCC 互补（PCC 证明可作为私有 Aux 在审计器内校验）。

## 7. 优点

- **问题定位精准**：清晰刻画了专有软件场景下"参考值提供方即信任瓶颈"这一被长期忽视的结构性问题。
- **架构解耦优雅**：证书的**签发**（在 TEE 信任模型下一次性完成）与**应用**（可在任意度量发射平台上使用，甚至非 TEE 平台）分离，具备良好的通用性与可复用性。
- **非披露性设计**：全程仅传输摘要，配合哈希承诺，避免源码与二进制泄露，直接服务于厂商代码保密诉求。
- **理论统一性强**：将两个独立机制归入 CCP 形式化框架，并给出显式的关系式与量化命题表述。
- **对比分析透彻**：与 PBA、PCC、ZK/ZKVM 的差异化分析维度清晰（保护对象、签发 vs. 应用、运行时绑定方式、属性表达范围），并指出 PCC 证明可作为 Aux 与本文方案互补。
- **工程务实**：借助 Gramine LibOS 复用现有构建与审计流水线，不改算法，只承担隔离机制的常数级开销，避免了将审计流程重写为 ZK 电路的巨大成本。
- **讨论诚实**：主动披露选择性披露、TCB 恢复、依赖覆盖、物理攻击（TEE.fail）等残余风险，并提出中立第三方托管等应对建议。

## 8. 不足与局限

- **实验极其单薄**：仅一个 PoC，无性能数据、无消融、无多场景验证；PoC 只实现 CCP 生成侧，未验证完整验证者协议（步骤 5–7）与端到端安全属性。
- **缺乏实证对比**：与 ZKP/ZKVM 的成本对比仅为定性论述，未给出任何实测开销（证明生成时间、验证时间、证明大小）。
- **信任模型仍依赖硬件**：安全性建立在 TEE 根信任、芯片厂商 PKI、TEE 配置与测量软件 TCB 之上；作者也承认恶意但被度量的工具链（信任信任攻击）会直接击穿绑定性保证。
- **物理攻击风险**：TEE.fail 等工作表明低成本的 DDR5 内存总线插接可提取认证签名密钥并伪造报告，这使"自托管且有利可图的开发者"场景在现实中存在风险；论文将此列为"超出协议分析范围"的局限。
- **选择性披露未解**：开发者可只披露有利审计结论，协议本身无法强制全面审计；只能依赖依赖方策略规定审计配置。
- **依赖覆盖不完整**：动态链接库等运行期依赖的变更不改变工件度量，需由平台侧认证单独绑定，构成"仅审计应用工件"的固有限制。
- **证书生命周期与 TCB 恢复成本**：TCB 恢复后证书失效需重签，构建证书重签在非可复现构建情形下还要求重新部署，带来运维代价。
- **审计质量不保证**：框架不定义 Verdict 的语义，审计工具本身的效力由依赖方策略判断，论文明确将此排除在贡献之外。
