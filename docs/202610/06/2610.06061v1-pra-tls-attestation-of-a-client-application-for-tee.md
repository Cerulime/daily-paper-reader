## 摘要
可信执行环境（TEE）是保护敏感信息以及对机密数据执行计算的安全基础。在富执行环境（REE）中，不可信应用会调用隔离执行环境（enclave）中的处理。随后，enclave将执行结果返回给不可信应用。即使enclave已经通过证明，enclave与不可信应用之间的边界仍会带来风险，例如篡改输入参数或返回值，以及操纵应用调用函数的顺序。因此，不仅需要建立enclave本身的真实性与完整性，还需要建立应用及其执行环境的真实性与完整性。在本研究中，我们提出一种证明协议——可移植远程证明TLS（PRA-TLS），用于调用enclave的客户端应用。我们引入一个充当证明者的守护进程。PRA-TLS使用可信的Attester Daemon在运行时度量宿主环境和应用代码的状态，并将这些度量结果作为证明证据，供远程Verifier验证。该机制仅在软件环境处于预期状态且应用代码被验证为合法时，才允许enclave继续执行。我们为所提出的协议定义了攻击模型和安全需求，并使用Tamarin Prover对其安全性进行了形式化评估。此外，我们使用Intel SGX实现了PRA-TLS原型，并评估了其性能。

## Abstract
Trusted Execution Environments (TEEs) are secure foundations for protecting sensitive information and executing computations over confidential data. Processing in an isolated execution environment (enclave) is invoked by an untrusted application in the Rich Execution Environment (REE). Then the enclave returns the execution results to the untrusted application. Even if the enclave has been attested, the boundary between the enclave and the untrusted application poses risks, such as tampering with input arguments or return values and manipulating the order in which the application invokes functions. Therefore, it is necessary to establish the authenticity and integrity of not only the enclave itself but also the application and its execution environment. In this study, we propose an attestation protocol, Portable Remote Attestation TLS (PRA-TLS), for a client application that invokes an enclave. We introduce a daemon that acts as an attester. PRA-TLS uses a trusted Attester Daemon to measure the state of the host environment and application code at runtime, providing these measurements as attestation evidence for verification by a remote Verifier. This mechanism allows the enclave to proceed only when the software environment is in the expected state and the application code is verified as legitimate. We define attack models and security requirements for the proposed protocol and formally evaluate its security using the Tamarin Prover. Furthermore, we implement a prototype of PRA-TLS using Intel SGX and evaluate its performance.

## 1. 核心问题与整体含义

- **研究背景**：TEE（如 Intel SGX、Arm TrustZone、RISC-V Keystone）通过隔离执行环境（enclave）保护敏感数据与代码，使其免受富执行环境（REE）中 OS、特权软件及恶意软件的影响。现有远程证明机制（如 Intel SGX 的 Quote、RA-TLS）主要证明 **enclave 自身**的代码与初始状态。
- **核心问题**：enclave 由 REE 中的**不可信客户端应用**调用，二者通过 ECALL/OCALL 边界交互。即使 enclave 已通过证明，该边界仍可能被攻击者利用：
  - 篡改 ECALL 参数或 OCALL 返回值；
  - 操纵 ECALL 调用顺序；
  - 恶意客户端应用调用合法 enclave 二进制，但 enclave 的证明结果仍可能被视为有效。
- **为什么仅验证应用签名不够**：enclave 可能以共享对象（.so）形式提供，可被任意应用调用；客户端应用运行时还会加载共享库，难以预先识别并验证所有实际执行代码；也难以将已验证代码安全绑定到真正调用 enclave 的进程。
- **整体含义**：需要将证明范围从 enclave 扩展到**调用 enclave 的客户端应用及其执行环境**，并保证其真实性与完整性不仅在启动时成立，也在运行时成立。本文提出 **PRA-TLS（Portable Remote Attestation TLS）**，通过引入受信 Attester Daemon，为客户端应用生成证明证据，并由远程 Verifier 校验后决定是否允许 enclave 继续执行。

## 2. 方法论：核心思想与关键技术

- **核心思想**：扩展 Intel SGX 的 RA-TLS 协议，在 TLS 握手中同时完成：
  - enclave 证明；
  - 客户端应用代码及其执行环境的证明；
  - 证明证据与当前 TLS 会话 nonce 的绑定。
- **系统组成**：Verifier、软件栈（CPU—Linux 内核）、Client Application、TEE Application、Attester Daemon、Daemon-side TEE、TPM 2.0。
- **信任链与 TCB**：
  - 信任根：Intel SGX CPU 与 TPM；
  - 启动时：UEFI Secure Boot 验证 bootloader、Linux 内核等启动链组件；
  - 运行时：Linux IMA 度量关键软件组件，包括 Attester Daemon 及其依赖库、SELinux 策略；
  - SELinux 强制访问控制限制只有 Attester Daemon 能访问 PRA-TLS 所需的 TPM 功能（AK、Quote 生成等）；
  - 假定 Linux 内核、SELinux 策略、Attester Daemon 在启动后保持完整；利用内核漏洞攻破 Attestation TCB 不在范围内。
- **PCR 使用**：
  - `PCR_TCB = {PCR 0–10} ∪ {PCR 11}`；
  - PCR 0–7：固件、bootloader 等 pre-OS 启动度量；
  - PCR 8：内核命令行；
  - PCR 9：内核镜像与 initrd；
  - PCR 10：Linux IMA 度量；
  - PCR 11：Attester Daemon 及其依赖库的 IMA 度量；
  - 假设内核静态链接所有模块，不动态加载内核模块，以降低 PCR 顺序不确定性。
- **两类证据**：
  - **Boot Attestation Evidence**：Attester Daemon 调用 TPM，用 AK 对 `PCR_TCB` 与 Verifier nonce 生成 TPM Quote，证明客户端应用运行在预期软件栈上；
  - **Runtime Attestation Evidence**：Attester Daemon 在运行时度量客户端应用代码，计算 `SHA-256(nonce || app-hash)`，作为 `qualifyingData` 交给 TPM，由 TPM 放入 `extraData` 并签名，证明应用代码完整性。
- **执行环境绑定（防中继）**：
  - Daemon-side TEE 与 TEE Application 在同一机器、相同签名条件下派生相同的 TEE sealing key；
  - Daemon-side TEE 用该密钥加密 nonce；
  - TEE Application 用自身 sealing key 加密从 Verifier 收到的 nonce，并与收到值比较；
  - 若一致，说明证据来自同一台机器上的 Attester Daemon；若中继到另一台合法机器，密钥不同，nonce 解密/比对失败。
- **协议流程**：
  1. TEE Application 经 TLS 握手从 Verifier 获得 ServerHello 中的 nonce；
  2. 经 Client Application 和 Unix domain socket 向 Attester Daemon 发送证据生成请求；
  3. Attester Daemon 生成 TPM Quote、运行时证据，并让 Daemon-side TEE 加密 nonce，返回证据；
  4. TEE Application 验证执行环境绑定，将 Boot/Runtime 证据、nonce 等嵌入 RA-TLS 的 X.509 证书扩展，发送给 Verifier；
  5. Verifier 验证 TPM 签名、`PCR_TCB` 与参考值、运行时证据与参考应用哈希，从而确认客户端应用及执行环境的真实性与完整性。
- **证书扩展**：在 Intel RA-TLS 证书基础上增加 `tpm2-evidences` 和 `nonce` 字段，其中 `tpm2-evidences` 包含 `tpm2-quote`、`sign`、`app-hash`。
