## Abstract 

Trusted Execution Environments (TEEs) prove the integrity of code and data to a remote peer through remote attestation: the TEE issues an attestation report by signing, with a hardware-bound key, its configuration information, including measurements (cryptographic digests) of the code loaded inside it. A verifier appraises the report by matching these measurements against reference values. When the measured artifact is proprietary, however, the verifier cannot derive the reference values itself: it can only confirm that something 

with a given measurement is running inside the TEE—not that the program behaves as expected—forcing full trust in the reference value provider. We propose an architecture that closes this gap with-out disclosing the artifact, composing two TEE workloads: attestable build (Hugenroth et al. , 2025), which binds a source code digest to a build artifact measurement, and attestable audit (proposed in this paper), which binds the same source code digest to the verdicts of automated audits—fuzzing, static analysis, AI code auditing, formal methods—executed inside a TEE. Both are instances of Confidential Computing Proofs: TEE attestation viewed as a hardware-backed zero-knowledge proof. Chaining the two certificates lets the veri-fier conclude that the running artifact was built from source code satisfying the audited properties, without disclosing either the source code or the build artifact . A proof-of-concept implementation on Intel SGX with the Gramine Library OS, running the Bandit secu-rity analyzer on Python code, demonstrates the practicality of the approach.

## 1 Introduction 1.1 Background 

Remote attestation (RA) for Trusted Execution Environments (TEEs) is a protocol by which a TEE proves the integrity of its code and data to a remote peer. Throughout this paper we follow the terminology of the RATS architecture [3], which defines the following roles. The attester is the platform under attestation; it issues evidence 

containing claims about its own state. The verifier appraises the evidence and sends the attestation results to the relying party , the party that decides, based on those results, whether to interact with the attester. In this appraisal, the verifier validates the authenticity of the evidence using endorsements (such as certificate chains and certificate revocation lists) issued by an endorser (typically the hardware vendor), and matches the measurements contained in the evidence against reference values supplied by a reference value provider (typically the software vendor). The basic flow of RA is as follows. The attester measures crypto-graphic hash values of the code loaded into its isolated execution context, and issues as evidence an attestation report : the system’s configuration information, including these measurements , signed with an attestation key bound to the TEE platform. The verifier validates the authenticity of the attestation report using the en-dorsements, and then matches the measurements in the report against the reference values, thereby confirming that the expected code is running inside the TEE. This ‘measurement-and-comparison’ pattern of RA appears con-sistently throughout the TEE ecosystem in several specific forms. The most basic form of this pattern is the RA for the initial TEE state. In Intel SGX, the digest of the loaded enclave image 

MRENCLAVE is measured at load time and bound into the attestation report (SGX quote) [9]. In Confidential VMs (CVMs) such as AMD SEV-SNP and Intel TDX, the digest of the VM’s initial memory state (MEASUREMENT and MRTD , respectively) is measured at VM launch and bound into the attestation report (SNP report and TD quote, respectively). The verifier checks these load-time measurements against reference values to confirm that the expected enclave or VM image is running. Another, more complex pattern can be observed in CVM’s run-time attestation. While the above measurements cover only the initial state of the TEE, runtime integrity in CVMs is typically han-dled by Kernel’s runtime integrity protection system, such as the Linux Integrity Measurement Architecture (IMA) [24]. IMA is a Linux kernel subsystem that measures and logs hash digests of files accessed inside the VM according to a loaded IMA policy. To make the measurement log itself attestable, IMA extends each entry into an append-only register that is isolated from both the guest OS and the hypervisor: a Platform Configuration Register (PCR) of a vTPM arXiv:2610.04480v1 [cs.CR] 3 Oct 2026 HASP ’26, October 31-November 01, 2026, Athens, Greece Takuma Imamura 

residing inside the guest VM (e.g. VMPL 0 for SEV-SNP [17]), or a Runtime Measurement Register (RTMR) provided by Intel TDX [14]. After verifying the authenticity of the IMA log against this register, the verifier appraises each entry—consisting of a file path and a file hash—according to some policy. For example, the policy may allow or deny specific combinations of file paths (or patterns) and hashes (or hash lists, such as the set of hashes corresponding to an acceptable version range of a binary). Denial policies are particularly useful for excluding library versions known to contain severe vulnerabilities or for blocking known malware. Yet another form of the pattern appears in the RA for Confi-dential Containers (CoCo). CoCo [8] is a container running in-side a CVM. The host configures the hash digest of a container policy—which itself contains the digest of the permitted container images—in a configurable register (e.g. HOST_DATA for SEV-SNP or 

MR_CONFIG_ID for TDX) at guest VM launch, and passes the corre-sponding policy to a policy engine inside the guest VM. The policy engine verifies the authenticity of the received policy by comparing its hash against the policy measurement field (e.g. HOST_DATA or 

MR_CONFIG_ID ) in the attestation report, and only then launches the container according to the policy. The verifier validates the entire chain by (1) comparing the launch measurement (e.g. MEASUREMENT or 

MRTD ) in the attestation report against its reference value to confirm that the expected container runtime and policy engine are running, (2) comparing the policy measurement field (e.g. HOST_DATA or 

MR_CONFIG_ID ) in the attestation report against the hash of the expected container policy to confirm that the expected policy is loaded inside the CVM, and (3) comparing the container image digest embedded in the pol-icy against the reference value to confirm that the expected container is running. In each of these cases, the attester provides the verifier with evidence that includes digests of its own program artifacts—VM initial images; kernel modules, libraries, and executables inside the guest OS; container images; among others—and the verifier validates this evidence by comparing the digests against reference values. When the program in question is open source (and, strictly speak-ing, its build is reproducible [15]), the verifier can prepare these reference values itself by building from source and computing the resulting digests. Even when the source is not open, the verifier can still derive reference values independently as long as the executable or container image itself is publicly available. The situation differs fundamentally, however, when the program is closed and proprietary. In this case, the verifier cannot derive reference values on its own. Instead, a reference value provider distributes only the reference values to the verifier. The verifier can then confirm that “something with this digest is running inside the TEE,” but nothing more: it cannot determine what program is actually running, nor whether the program has any particular property of interest (e.g. the absence of a backdoor). This is essen-tially the same problem pointed out by Sadeghi and Stüble in 2004 [23]: a binary’s digest is just an identifier, not a semantic guarantee. In this case, the relying party is forced to place full trust in the reference value provider in everything beyond the bare hash digest (see Figure 1). 

## 1.2 Our contribution 

In this paper, we propose an architecture that closes this gap in remote attestation without disclosing the pre-hashed data. Our approach builds on two mechanisms. 

Attestable build , introduced by Hugenroth et al. [13], builds source code inside an attestable isolated environment, such as a TEE 1, to cryptographically bind the source code digest to the build artifact digest. 

Attestable audit , proposed in this paper, performs automated audits on source code inside a TEE to cryptographically bind the source code digest to properties of the code. Here, automated audit covers fuzzing, Valgrind [20], taint analysis, AI code auditing, and formal verification, among others. These two mechanisms yield a chain from the build artifact digest—which is what a remote verifier observes in the attestation evidence of a running TEE—to verifiable properties of the source code, without disclosing either the source code or the build artifacts. Conceptually, our approach is grounded in the observation that remote attestation can be considered as a hardware-backed zero-knowledge proof (ZKP); see [22] for further discussion. To demonstrate the feasibility of attestable audit, we provide a proof-of-concept implementation on Intel SGX using the Gramine LibOS [26, 27]. The PoC takes a Python script as input and runs Bandit [21], a static security analyzer, inside the SGX enclave; the resulting audit report is bound to the source code digest via the enclave’s attestation report. 

## 2 System model and trust assumptions 

Parties. We follow the standard RATS role model [3] (see Figure 1): the relying party trusts the verifier and the endorser. The attester may be any RATS-compliant platform—SGX enclaves, CVMs, TPM-backed systems, AWS Nitro Enclaves, etc.—and its trust assumptions are inherited from the underlying technology. The developer of the attester’s proprietary code acts as the reference value provider, and we use the two terms interchangeably. 

Adversary model. Our key departure from the standard model is that the relying party does not trust the reference value provider: the adversary is a malicious developer who may present arbitrary— forged, stale, or mix-and-matched—reference values, certificates, and code, in order to make the relying party accept an attester that lacks the claimed properties. Conversely, the developer regards the verifier as honest-but-curious: it follows the protocol but at-tempts to learn the proprietary artifact. As usual in the TEE setting, the hardware root of trust and the chip vendor’s PKI are trusted, whereas the host OS, the hypervisor, and all software outside a TEE are untrusted. 

Security goals. The architecture must provide (P1) binding : if the verifier accepts, the attester runs a build artifact whose source code actually produced the claimed audit verdicts under the disclosed au-dit configuration; and (P2) non-disclosure : the verifier learns nothing

We also take the semantic quality of the audit tools as given: what an audit verdict is worth is decided by the relying party’s policy, not by our construction.

## 3.5 Attestable build and audit as CCPs 

The attestable build and the attestable audit can be unified under a single generalised concept: the Confidential Computing Proof (CCP) of Russinovich et al. [22]. A CCP is essentially TEE attestation viewed as a hardware-backed zero-knowledge proof (ZKP)—for a decidable (Turing computable) relation 𝜑 (𝑥, 𝑤 ), an open-source TEE workload Π𝜑 decides 𝜑 on public input 𝑥 and private witness 

𝑤 , and then emits an attestation report whose report-data field commits to the quantified statement ∃𝑤 .𝜑 (𝑥, 𝑤 ); the report-plus-measurement is the proof object for the statement ∃𝑤 .𝜑 (𝑥, 𝑤 ). We refer the reader to [22] for the full formalism. Concretely, the attestable build is a CCP for the relation “ 𝑆 hashes to ℎ𝑆 and, under the build configuration Conf Bld , builds to an arti-fact with measurement 𝑚 𝐵 ,” and the attestable audit is a CCP for the relation “ 𝑆 , audited under Conf Aud with auxiliary input Aux ,yields verdicts Verdict .” The full logical relations, together with a remark on how our workloads depart from a literal CCP decider, are given in Appendix B. 

## 3.6 Security considerations 

We briefly argue that the protocol of Section 3.4 achieves the goals of Section 2, and make its residual assumptions explicit. 

Binding (P1). A malicious developer cannot forge 𝑅 Bld or 𝑅 Aud 

without breaking the TEE root of trust, and cannot obtain them from tampered workloads without changing the measurements 

𝑚 Bld and 𝑚 Aud , which the verifier reproduces independently from the public releases (Steps 5–6). Mix-and-match attacks—presenting an audit certificate issued for different source code, a different build configuration, or a different auxiliary input—are rejected by the cross-checks of Step 7, and presenting a binary other than the certified one yields an attested measurement 𝑚 ≠ 𝑚 𝐵 in Step 4. 

Non-disclosure (P2). Beyond the public Conf Aud and Verdict , ev-ery entry of 𝑑 Bld and 𝑑 Aud that the verifier receives is a digest, so nothing about 𝑆 , Conf Bld , Aux , or 𝐵 is revealed beyond what Verdict 

itself discloses—assuming, as usual for hash commitments, that the artifacts carry enough entropy to resist brute-force preimage guess-ing. 

Selective disclosure. The developer chooses which certificates to present: it may run many audits and disclose only favourable ones. A verdict therefore means “this audit, under this configuration, produced these results,” not “no audit ever failed.” Relying-party policies should hence prescribe the audit configurations they re-quire, rather than merely accept whatever verdicts are presented. 

Trusted computing base. The soundness of the certificates rests on the measured workloads: the build toolchain inside the attestable builder and the audit tools inside the attestable auditor are part of the TCB, so a malicious-but-measured toolchain (in the spirit of trusting-trust attacks) defeats P1. Detecting such a toolchain is exactly what the public inspectability requirement of Section 2 enables. 

## 4 Examples 

The architecture of Section 3 is attester/artifact-agnostic: the veri-fier merely cross-checks digests, so the CCPs are issued once un-der the issuer’s TEE trust model and then applied to deployments whose own attestation technology may be entirely different. We sketch three instantiations, one for each attester form surveyed in Section 1. 

## 4.1 Proprietary SGX application 

The attester is a proprietary SGX enclave; the CCPs certify enclave-level properties such as statelessness, correct use of an RA-TLS handshake [28], or the absence of tainted flows from confidential inputs to untrusted outputs. Building an SGX enclave image in-volves a heavyweight toolchain, so the attestable builder is best hosted in a CVM. Note that for SGX the measurement 𝑚 𝐵 is the 

MRENCLAVE ; the builder therefore derives the expected MRENCLAVE 

from the build output via the sgx_sign tool of SGX-SDK. This is why meas (·) is kept distinct from 𝐻 (·) . The audit platform is chosen per audit type: AI code auditing requires a CVM with a TEE-capable GPU (e.g. NVIDIA Confidential Computing), whereas lightweight static analysis may run inside SGX, as in our PoC (Sec-tion 5). At verification time, the attester presents an SGX quote proving the MRENCLAVE of the running enclave, and the vendor— the party that would conventionally act as the reference value provider—ships the pre-generated CCPs instead of a bare refer-ence MRENCLAVE . The verifier runs the protocol of Section 3 and concludes that the running enclave satisfies the audited properties. 

## 4.2 Proprietary script on an IMA-measured host 

The attester is a server-side script running on a Linux host with a TPM-backed IMA; the CCP certifies properties of the script. Because the script is deployed as-is, the attestable builder is omitted and the measurement of 𝑆 is simply the file hash recorded by IMA. The attester presents the IMA measurement log containing the script’s entry, the PCRs to which the log is extended (typically PCR 10), and a TPM quote over those PCRs; together these prove the digest of the running script, and the vendor ships the audit CCP in place of a reference digest. This example illustrates the decoupling most starkly: the audit CCP is issued under a TEE trust model even though the deployment platform of the attester is not necessarily a TEE. When the Linux OS itself is running within a CVM and the vTPM is located at a guest privilege level isolated from both the guest OS and the hypervisor [17], the deployment-side trust model aligns with the issuer’s. 

## 4.3 Proprietary LLM behind an open-source server 

The attester is an inference server running inside a CVM; the server is fully open source, but the loaded model weights are proprietary. Here 𝑆 is the weight file and the CCP certifies model-level prop-erties, e.g. quantitative scores on a prompt-injection-resistance benchmark; Verdict can carry such scores, since its format is ar-bitrary. Benchmarking requires GPU inference, so the attestable auditor runs in a CVM with a TEE-capable GPU (e.g. NVIDIA’s Hopper, Blackwell and Rubin); no attestable builder is involved, as the audit certifies properties of the weights as given. The verifier thus trusts the reported weight digest because it trusts the verified server code, and the vendor’s CCP lifts that digest to the benchmarked property.

## 6 Related work 

In this section, we position our framework against three lines of related work, each of which relates to ours in a different way. Code Transparency Services offer a complementary substrate on which our build and audit claims could be published; cryptographic ZKPs are an alternative proof mechanism that does not scale to the work-loads we target; and Property-Based Attestation and Proof-Carrying Code share our goal of attesting properties rather than binary iden-tity, while relying on different trust models and suffering from their own limitations in the proprietary setting, e.g. code disclosure and reproducible builds. 

## 6.1 Code transparency service 

The closest conceptual neighbour is the work of Delignat-Lavaud 

et al. [10]. They propose a Code Transparency Service (CTS) for confidential computing, which records signed claims about source releases, builds, policies, reviews, and deployed artifacts in a public append-only verifiable ledger and returns receipts for registered claims. CTS is claim-agnostic by design and can, in principle, record claims produced by code-scanning or code-verification services, including claims generated by auxiliary TEEs. In this sense, the output of an attestable audit could be registered in CTS.

Our work addresses a different layer of the problem. CTS pro-vides a transparency and accountability substrate for storing and checking claims, but it does not define how a privacy-preserving au-dit claim about undisclosed source code should be generated, what such a claim means, or how it should be cryptographically linked to the artifact digest observed in remote attestation. Attestable audit fills this gap by running the audit inside a TEE and binding the resulting audit-derived properties to a source code digest. When composed with attestable build, this yields an end-to-end verifica-tion chain from the currently attested artifact digest to properties of the corresponding, undisclosed source code. Thus, CTS could be used to publish, timestamp, and make accountable the build and audit claims produced by our mechanism, whereas our contribution is the concrete TEE-backed evidence-generation and verification mechanism for such claims. 

## 6.2 Zero-knowledge proof for code properties 

Zero-knowledge proofs (ZKPs), including zk-SNARKs, zk-STARKs, and general-purpose zkVMs such as RISC Zero [4], could, in prin-ciple , serve our purpose by replacing CCPs directly. In practice, however, current general-purpose ZKP systems do not scale to the workloads we target. Across these schemes, the cost of proof gener-ation and/or verification—and the size of the resulting proof—grows with the complexity of the verification logic for the statement being proved [16]. For statements as heavy as a software build, a fuzzing campaign, or a GPU-accelerated AI code audit, this dependence makes ZKPs impractical. Vanilla zk-SNARK and zk-STARK systems require that the verification logic be converted into arithmetic con-straints, which are typically written in domain-specific languages such as Circom [2], resulting in significant implementation costs. Furthermore, efficient zk-SNARK systems (such as Groth16 [11]) require a multi-party trusted setup, which complicates the trust model. Although zkVMs remove the need to hand-write a verifica-tion circuit, the underlying complexity problem remains. Therefore, while ZKPs offer strong cryptographic guarantees, they are not efficient enough for our purpose. Our framework employs the Confidential Computing Proof (CCP) [22]. A CCP does not cryptographically encode the entire evalua-tion trace. Instead, it provides hardware-rooted attestation evidence that proves the identity of applications running within the TEE and the claims generated by those applications. Soundness therefore relies on the hardware root of trust, the TEE isolation mechanism, and the correctness of the measured applications, which must be implemented so that they emit the claims only after the intended build or audit has completed successfully. The advantage is the cost profile: because existing applications run essentially unmodified inside the TEE—reusing existing build systems and audit pipelines— the asymptotic complexity of the computation is unaffected; the additional cost consists only of a constant-factor overhead imposed by the isolation mechanisms (e.g. memory encryption) plus the cost of attestation itself. This is dramatically smaller than the cost of existing ZKP systems, which grows with the complexity of the computation being proved, as discussed above. This trade-off changes the engineering problem. Instead of rewrit-ing the audit pipeline as a ZK-friendly circuit or zkVM program, the main requirement is to run it in a TEE and to bind its outputs to the Attestable Audit: Property-Based Attestation for Proprietary Workloads without Artifact Disclosure HASP ’26, October 31-November 01, 2026, Athens, Greece 

attestation report. Process-based TEEs such as Intel SGX require SDK-specific re-implementation of existing applications but no al-gorithmic changes; Library OSes such as Gramine [26] and Occlum [25] keep code modifications to a minimum. Confidential VMs such as AMD SEV-SNP and Intel TDX further improve compatibility by supporting largely unmodified VM workloads, and confidential GPU platforms extend this model to selected GPU-accelerated work-loads. The cost of this practicality is a different trust model: unlike ZKPs, attestable audit depends on trusted hardware, vendor attesta-tion infrastructure, TEE configuration, and the software TCB inside the measured environment. Our goal is therefore not to replace ZKPs, but to provide a practical remote-attestation-native mech-anism for proving audit properties of complex, non-ZK-friendly software workloads. 

## 6.3 Property-based attestation and proof-carrying code 

The question of attesting properties of code rather than mere binary identity is not new. Haldar et al. [12] proposed Semantic Remote Attestation, in which a trusted virtual machine attests to high-level properties of the code it executes; Sadeghi and Stüble [23] spelled out the general principle of Property-Based Attestation (PBA), ar-guing that relying parties care about properties, not the specific binary that realises them. Subsequent work developed concrete PBA protocols with [5] and without [6] a Trusted Third Party (TTP). In a related line, Proof-Carrying Code (PCC) [18, 19] and its foundational variant [1] attach machine-checkable proofs of prop-erties directly to a binary, allowing the code consumer to verify the property locally before execution. Our work shares the same end goal—conveying semantic guarantees about a program rather than a bare hash digest. 

Protected asset. PBA hides which of a set of known admissible configurations the attester runs, but the configurations themselves are inspected by the certifier [5] or published as an agreed list [6]; even the TTP-free protocol [6] removes the trusted party only at the protocol layer, since establishing that each listed configuration possesses the property still presupposes that someone can inspect the code—which is not an option for proprietary code. Likewise, a PCC proof is delivered together with the binary and effectively discloses the code. Attestable audit instead protects the vendor’s code confidentiality: no certificate, admissible list, or proof derived from the code’s content is ever published, and the verifier sees only a digest, the audit configuration, and the verdicts. 

Issuance versus application. The attestable auditor acts as a certifi-cate issuer for code properties: a CCP is issued once per  𝑆, Conf Aud 



and can then be consumed in the attestation of arbitrarily many deployments of the same code. The deployed workload need not itself be a TEE—the verifier merely cross-checks digests, so any measurement-emitting attester (a CVM, a confidential container, or an IMA-measured workload with a TPM) qualifies—while the unforgeability of the certificate rests on the TEE trust model of the issuer, independently of the deployment platform. Moreover, the is-suance act itself is attested: the CCP proves that the measured audit pipeline actually ran on the code, whereas a PBA credential proves only that the TTP signed, not that any inspection took place [5]; attestable audit is thus structurally a PBA whose TTP is replaced by a transparent, machine-checkable issuer, and whose TPM-bound presentation protocol is replaced by a plain digest cross-check. PCC sits at the opposite end of the spectrum: its proofs are self-certifying and need no issuer trust at all, but they can be consumed only by a party holding the code, and hence cannot serve as a certificate in remote attestation without disclosure, and its property class is confined to what the proof logic can express (e.g. memory and type safety), whereas an attestable audit can certify any computable property. 

Runtime binding. A PBA credential certifies reference measure-ments, so binding a source-level property to the binary loaded at runtime requires either trusting the certifier’s claim about the source-to-binary link or letting the verifier re-derive the link in-dependently, which in practice demands a reproducible build [15] and disclosure of the source code. PCC needs no such link because the proof is constructed over the machine code itself, but only because the consumer holds the code, which conflicts with non-disclosure. Our attestable build provides the link as a CCP attesting

Complementarity. These approaches are complementary rather than competing: a PCC-style machine-checkable proof can be sup-plied as the private auxiliary witness Aux and checked inside the attestable auditor, conveying proof-grade assurance to the verifier without disclosing either the code or the proof. 

## 7 Discussion 7.1 Hosting the attestable services 

Our architecture is agnostic to who operates the TEE platform on which the attestable builder and auditor run. Under the standard TEE threat model of Section 2, all software and operators outside the TEE are untrusted, so the guarantees formally hold regardless of the host. In practice, however, this model is strained by low-cost physical attacks. TEE.fail [7] demonstrates that attestation signing keys of current TEE platforms can be extracted via DDR5 memory-bus interposition with equipment costing under a thousand dollars, enabling the forgery of attestation reports. Given such attacks, a situation in which a party that has an incentive to cheat also has physical access to the hosting machine is undesirable, even though it is nominally covered by the threat model. Therefore, the TEE platform serving the attestable builder and auditor should be provided by a neutral third party without incentive to attack either side—neither to forge certificates as a self-hosting developer could, nor to harvest the developer’s proprietary inputs as a malicious host could. Cloud service providers are natural candidates: if a CSP qualifies as such a party, using its TEE platform is a particularly desirable choice, because CSP platforms are isolated inside tightly controlled data centres—whose physical locations are often even undisclosed— making physical access by any interested party difficult. 

## 7.2 Certificate lifecycle and TCB recovery 

The certificates (attestation reports) issued by the attestable builder and auditor bind the digest of 𝑆 to the result of a completed compu-tation. The build report certifies the resulting artifact measurement, whereas the audit report certifies the resulting verdicts. As specified HASP ’26, October 31-November 01, 2026, Athens, Greece Takuma Imamura 

in Section 3.4, these certificates are generated before deployment and reused when verifying deployments of the certified artifact. Their role is therefore not to establish the freshness of a particular verification session. Consequently, they require no session binding and need not include a nonce. This reuse assumes that the TCB under which a certificate was is-sued remains trusted. If a vulnerability or compromise triggers TCB recovery, the platform updates its components (such as microcode and firmware), and the endorser revokes the affected TCB version through updated endorsements. A certificate issued under the re-voked TCB then fails verification and must be reissued by rerunning the corresponding computation on the recovered platform. For the attestable builder, reissuance requires rebuilding 𝑆 . If the rebuilt artifact has a measurement different from that of the running attester, the check in Step 7 fails and the artifact must be redeployed. A reproducible build avoids this cost by reproducing the same artifact measurement, allowing only the build certificate to be reissued. 

## 7.3 Dependency coverage in auditing 

The dependencies covered by an audit depend on its analysis. An audit confined to source 𝑆 need not resolve dependencies, whereas a dependency-aware audit may inspect direct and transitive depen-dencies. In the latter case, their resolution must match that used to build artifacts 𝐵 . Pinning the dependencies and using a reproducible build can make this correspondence deterministic. Reproducibility of 𝐵 , however, does not fix dependencies supplied at run time. A dynamically linked library installed in the execution environment may change without changing 𝐵 . This is a limitation of auditing only the application artifact. To address this issue, code outside that artifact must be bound separately by platform-side attestation. For example, CCPs for a confidential container may cover its container image, while CVM attestation must separately establish the expected container runtime and policy engine. 

## 8 Conclusion 

We identified a fundamental gap in remote attestation for propri-etary software: matching a measurement against a reference value tells a verifier only that “something with this digest is running,” forcing full trust in the reference value provider. We proposed an architecture that closes this gap by composing an attestable build and an attestable audit, both cast as Confidential Computing Proofs: open-source TEE workloads that bind a source code digest to a build artifact digest and to an audit verdict without disclosing ei-ther the source code or the build artifact to the verifier. This enables property-based attestation for proprietary applications without code disclosure. A PoC on Intel SGX with the Gramine Library OS, auditing Python code with Bandit, demonstrates that CCP genera-tion is practical with off-the-shelf tools.
