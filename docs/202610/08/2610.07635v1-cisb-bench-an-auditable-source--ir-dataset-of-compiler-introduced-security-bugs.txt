# CISB-Bench: An Auditable Source–IR Dataset of Compiler-Introduced Security Bugs 

Saatvik Pradhan, Anuroop Saini, Pranav Attrey, and Suman Saha 

The Pennsylvania State University University Park, PA, USA 

{szp6118, abs7800, pka5235, szs339 }@psu.edu 

Abstract —Compiler-introduced security bugs (CISBs) arise when an optimization, lowering, or instrumentation decision changes a security-relevant property of the generated program. They are difficult to study because their evidence is distributed across issue reports, reduced tests, historical configurations, and compiler artifacts; a security-related report also does not imply that every associated reduction establishes a security-bearing compiler failure. We present CISB-Bench, an auditable dataset of 429 exact C-program rows mined from GCC and LLVM. Each row contains its C reduction, a standardized LLVM IR analysis bundle at -O0 through -O3 , public provenance, a final binary label, and a primary mechanism or boundary annotation. Two reviewers independently labeled the fixed corpus, agreeing on 369 rows (86.0%, Cohen’s κ = 0 .662 ); the 60 disagreements were adjudicated. The final dataset comprises 280 CISBs and 149 hard non-CISB cases. The prediction task is to recover this reviewed exact-row label from the supplied artifacts; it is not a claim that standardized IR alone reproduces every historical compiler failure. We characterize the security mechanisms and evidence boundaries represented by the corpus, and demonstrate how its paired artifacts support source-only, IR-aware, and joint analyses. CISB-Bench provides a reusable, inspectable target for compiler-security mining and detection research. 

Index Terms —compiler security, mining software repositories, benchmark dataset, GCC, LLVM 

I. I NTRODUCTION 

Compilers are part of the security boundary between a source program and the executable that ultimately runs. Op-timizations, target lowering, and security instrumentation are expected to preserve relevant behavior, yet each can alter a property on which a security mechanism relies. The resulting correctness–security gap arises when a transformation meets a conventional correctness criterion but defeats a security property [1]. Examples include optimizations that eliminate secret-erasure stores [2], sanitizer-eliding transformations [3], and compiler-created double fetches that weaken control-flow integrity [4]. Other work documents the security con-sequences of compiler side effects and secret-dependent com-piled code [5]–[7]. We call such failures compiler-introduced security bugs (CISBs). CISBs are challenging to mine and evaluate at scale. Their evidence is rarely contained in a single artifact: an issue report may describe the affected target, an old compiler version, a patch, and multiple reduced programs. A reduction can be a complete witness, but it can also be a helper, a control, or a fragment that no longer instantiates the reported mechanism. Compiler-testing methods discover semantic miscompila-tions [8], [9], empirical studies characterize GCC and LLVM reports [10], [11], and prior security work establishes that CISBs matter [12]. What remains missing is an inspectable exact-row decision boundary with paired source/IR evidence and difficult negatives. We present CISB-Bench, 429 exact C reductions from GCC and LLVM, each with public provenance and standardized LLVM IR at -O0 –-O3 . A fixed-corpus, three-gate review produced 280 CISBs, 149 hard non-CISBs, and mechanism or boundary annotations. The benchmark targets the reviewed exact-row label from released C and IR; its standardized IR supports uniform analysis rather than replaying every historical toolchain. The distinguishing unit is an exact C reduction paired with standardized IR and a reviewed compiler-to-security decision, rather than a report, generated test, or source-level CVE instance (Table I). II. CISB D EFINITION AND DATASET DESIGN 

A. Exact-row definition 

We define a CISB as an exact program row for which three conditions hold. First, compiler causation (G1): an optimization, lowering decision, ABI handling rule, or in-strumentation action causes or materially enables the failure. arXiv:2610.07635v1 [cs.CR] 6 Oct 2026 Second, semantic or protection change (G2): that action changes executable behavior or a requested runtime protection. The relevant change can be a value, address, store, branch, layout, calling convention, or generated check. Third, security relevance (G3): the changed behavior affects a supported security-bearing operation, including memory or concurrency safety, integrity, confidentiality, availability, or a protection mechanism. All three gates are required. Thus, a compiler crash does not create a vulnerable executable; a missed warning is not a lost runtime protection; and a changed numerical result is not a CISB without a supported security-bearing consumer. We also distinguish source-authored unsafe or undefined behavior from a separate compiler-created security mechanism. A policy-dependent class retains cases in which compilation amplifies disclosed source undefined behavior into a broader security-relevant manifestation; users applying a strict defined-source policy can identify that class separately. This boundary is motivated by prior work on optimization-unstable code and the security consequences of undefined behavior [16]–[18]. 

B. Why exact rows and hard negatives 

The unit of analysis is a source reduction and its associated IR artifacts, rather than a report title or issue family. This prevents a report’s security context from being inherited by every related test. It is especially important because min-imization can omit a dereference, target configuration, or consumer that was essential to the original failure; reduction can also change definedness assumptions [19], [20]. Upstream reports are retained as provenance and historical context, not as automatically trusted labels. It also avoids treating issue-level duplicates or closely related reductions as independent security witnesses [21]–[23]. The non-CISB class is consequently a designed boundary set, not random background code. It contains diagnostic-only cases, compiler-process failures, incomplete reductions, source-authored unsafe behavior, semantically benign trans-formations, and ordinary wrong-code cases with no sup-ported security consequence. A method that merely recognizes words such as “overflow,” “sanitizer,” or “optimization” should therefore produce false positives; the benchmark evaluates prediction of the reviewed exact-row label, not independent proof of the complete G1–G3 chain. Establishing the historical mechanism may additionally require issue evidence and the affected compiler configuration. A non-CISB label means only that the retained evidence does not establish all three gates for that exact row under this policy. It is not a general assurance that the source program, the historical issue, or an execution in another configuration is secure. III. M INING AND ARTIFACT CONSTRUCTION

Reports without a retained C reduction or a complete artifact bundle were not eligible. This criterion excludes many real reports, but it is necessary for a dataset whose instances can be inspected and reused without a proprietary environment. This choice follows a broader reproducibility tradition in mined software datasets, where an available issue report alone is insufficient to make a case evaluable [24]–[26]. Candidate selection used two independent triage signals to prioritize review. First, a weighted keyword score over report text and tracker metadata used security, memory-safety, optimization, control-flow, integer, undefined-behavior, and compiler-component terms; a score cutoff of 10 retained 1,075 cases. Second, a fixed structured language-model screen using the OpenAI model identifier gpt-4.1-mini read each report’s summary, compiler origin, component, severity, and tracker keywords; the dated backend snapshot was not retained. The screen returned a candidate flag, confidence, proposed impact, and vulnerability type. Retention depended only on a true candidate flag, with no confidence cutoff, yielding 1,241 cases. Neither screen consumed the released C/IR bundle or supplied a benchmark label. We reviewed only their 429-case intersection. Requiring both a lexical signal and an independent semantic screen concentrated finite manual review on cases with two kinds of preliminary support, while preserving the entire resulting candidate set for review rather than silently discarding later false positives. Thus, the intersection is neither a prevalence sample nor a recall-oriented census of compiler-security re-ports. Terms such as “overflow” and “crash” remain ambigu-ous; the later review determines the binary target. The archived artifact contains the exact query groups, weights, structured-screen prompt, and construction scripts.

M ANUAL VERIFICATION AND FINAL LABELS 

Mining produces candidate evidence, not ground truth. We therefore fixed the 429-row corpus before manual review and asked two undergraduate researchers who had completed compiler coursework to independently classify every row. Reviewers applied the three gates in Section II, inspecting the C reduction, its standardized source–IR analysis artifacts, and public issue evidence when it was needed to establish a historical target, patch, or manifestation. They received a shared written codebook with worked anchor cases, but did not conduct a formal calibration or training exercise before independent labeling. Reviewers agreed on 369 of 429 rows (86.0%) and disagreed on 60 (14.0%). The corresponding Cohen’s κ is 0.662. Of the disagreements, 52 had one reviewer label the row CISB and the other non-CISB in one direction, and eight in the reverse direction. The statistic is intentionally reported before adjudication: the resolved labels are the benchmark target, not a measure of independent reviewer agreement. Each disagreement received a final evidence-based adjudica-tion. The adjudicator considered the competing classifications against G1–G3, the row’s C reduction, standardized IR bundle, and relevant issue context, then recorded a final label and evidence-based rationale. The adjudicator was a doctoral re-searcher in Computer Science. Adjudication is therefore not an automatic majority vote. The resulting frozen target contains 280 CISBs (65.3%) and 149 non-CISB cases (34.7%). The final data do not present post-adjudication identity as inter-rater reliability; they provide one frozen evaluation target for downstream methods. This distinction matters because label noise and misclas-sification can distort conclusions drawn from mined soft-ware data [27], [28]. Retaining a fixed candidate set, pre-adjudication agreement, and a separate final target makes the review protocol inspectable without implying that the adjudicated labels are mechanically certain. The disagreements reveal why a compiler-security bench-mark cannot use issue language alone. A row may omit the claimed trigger, show only a build-time failure, inherit unsafe behavior from source, or have no security-bearing use for an observed wrong value. Conversely, a compact reduction may preserve a lost sanitizer check, invalid atomic behavior, or target-lowering error that a generic wrong-code label does not capture. Final labels thus represent a documented decision about the exact program, not a broad assertion about every report in the issue family. The corpus contains 277 GCC-origin rows (166 CISB, 111 non-CISB) and 152 LLVM-origin rows (114 CISB, 38 non-CISB); these are descriptive corpus counts, not estimates of compiler-defect prevalence. V. A. Primary taxonomy 

The binary target establishes whether a row is a CISB, but it does not explain how a compiler action becomes security-relevant. We therefore assign every CISB one dom-inant compiler-created mechanism and every non-CISB one primary evidence boundary. A class captures the principal compiler-to-security chain, not every possible downstream consequence. For example, a wrong stack-slot access is clas-sified as ABI/target lowering even when it could also affect confidentiality or memory safety. The taxonomy is derived after binary-label adjudication and is descriptive of this corpus, rather than an independently validated labeling instrument. Reviewers selected the same primary class on 252 of 429 rows (58.7%; Cohen’s κ = 0 .535 )after normalizing label wording and combining spatial and temporal memory safety. The remaining 177 primary classes were resolved through taxonomy adjudication using the row-level source, IR, and final-label evidence. This distinction lets users treat the binary labels as the primary benchmark target while using the taxonomy for error analysis and controlled subset selection. 

B. What the corpus represents 

The most common CISB mechanisms are spatial/temporal memory safety (44 rows), data-state integrity (41), and alias/provenance (40). This distribution shows that CISBs are not confined to familiar dead-store-elimination examples. They also arise when compilation changes object identity, lifetime state, a live value flowing to a check, an ABI state, or a generated protection. The negative set is equally informative. Equivalent or benign behavior is the largest non-CISB boundary (86 rows), fol-lowed by source-authored unsafe behavior (18), no supported security consequence (16), and incomplete or non-instantiating reductions (16). These cases make a superficial classifier look plausible while testing whether it matches the reviewed exact-row labels. For instance, a removed operation is not necessarily a CISB if it is dead or unobservable; a visible wrong value is not necessarily security-relevant if it is printed and discarded; and a sanitizer report is not evidence that the current reduction executes the required violation. Compiler-origin counts characterize the released resource, not population defect rates. VI. R ESEARCH USE AND REPRODUCIBILITY

B. Recommended evaluation and release use 

Construct an undirected graph connecting rows that share an issue identifier or an identical source hash, and assign each connected component wholly to one partition. Thus, related rows, including those connected transitively through either relation, must not cross partitions. This matters because the 429 rows have 283 issue IDs and 366 hashes; 88 issue IDs recur across 234 rows and 62 hashes recur across 125 rows. Taxonomy and adjudication rationale are reserved for post-hoc analysis and must not be detector inputs. Report-text retrieval should be declared separately from a method that inspects only released C and IR. Because the corpus has 280 CISBs and 149 deliberately difficult non-CISBs, aggregate accuracy is insufficient. We recommend CISB precision, recall, F1, a confusion matrix, and post-hoc errors by mechanism and boundary class. An-alyzer studies should also state compiler version, target, and optimization level: contemporary non-reproduction of a his-torically supported case is not, by itself, a label error. The public archive provides the canonical CSV, per-sample C/IR bundles, README, and construction materials at https: //doi.org/10.6084/m9.figshare.31797592. It excludes private review material, credentials, and local paths. The dataset is not a census: it is restricted to retainable C reductions from GCC and LLVM reports and may underrepresent other ecosystems, historical environments, and failures without compact repro-ducers. VII. R ELATED WORK AND CONCLUSION 

Compiler fuzzing, differential testing, and translation vali-dation aim to find or rule out semantic compiler errors [8], [9], [29], [30]. Empirical compiler-bug studies characterize the reports and optimization defects in GCC and LLVM [10], [11]. These efforts motivate our data sources, but their targets are broader than the security consequence of an exact C reduction paired with standardized IR. Secure-compilation research and work on the correctness–security gap show why semantic preservation alone does not guarantee a selected security property [1], [31], [32]. Xu et al. [12] provide the closest empirical CISB study; CISB-Bench complements it with an auditable benchmark target, hard negatives, and paired optimization-level artifacts. Formal compiler correctness and constant-time-preservation work provide complementary guar-antees for selected compiler or security properties [33], [34], while binary security analysis can check properties such as constant time and secret erasure at a different layer [35]. Application-vulnerability datasets such as Big-Vul and MegaVul support learning from CVE-linked source changes [36], [37]; related resources include CVEfixes [38]. They do not, however, provide compiler-generated IR artifacts or label the compiler’s causal role. Recent MSR data papers similarly emphasize reproducible security instances, quality-controlled labels, or manually validated task data [13]–[15]. CISB-Bench fills this resource gap with 429 inspected C reductions and standardized IR bundles, 280 final CISBs, 149 hard non-CISB cases, and descriptive mechanism/boundary annotations. The task evaluates prediction of the reviewed exact-row label from released C and IR.
