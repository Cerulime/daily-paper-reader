## 摘要
现代移动和边缘平台在加载时提供硬件支持的应用与平台完整性证明。然而，一旦应用程序开始执行，它们几乎不提供支持。我们提出 ARA，一种面向 ARM 的应用运行时锚点，将这种加载时信任链扩展到执行阶段。ARA 通过可度量的加载链从底层 ARM 平台信任根 (RoT) 引导，并利用最近引入的 ARM 权限覆盖扩展 (POE) 在应用程序地址空间内建立经过证明的受保护运行时。由此产生的运行时域可以承载用于度量和存储的可编程 RoT (RTM/RTS)，从而支持应用程序运行时完整性验证、证明证据生成以及对秘密的受保护使用，同时保持对应用程序运行时状态的高效访问。作为示例性用途，我们实例化 ARA 用于受保护媒体解密和应用程序控制流度量。我们的原型和评估表明，ARA 能以接近进程内开销的成本支持频繁的、由运行时 RoT 支持的操作，其开销比进程外等效方案分别低约 10 倍和 50 倍。这为在 ARM 上从分层证明过渡到应用程序运行时可信计算提供了一座实用桥梁。

## Abstract
Modern mobile and edge platforms provide hardware-backed attestation of application and platform integrity at load-time. However, they offer little support once application execution begins. We present ARA, an Application-Runtime Anchor for ARM that extends this load-time chain of trust into execution. ARA bootstraps from the underlying ARM platform Root of Trust (RoT) through a measured loading chain and establishes an attested protected run-time within the application address space using recently introduced ARM Permission Overlay Extensions (POE). The resulting run-time domain can host programmable RoTs for Measurement and Storage (RTM/RTS), enabling application run-time integrity verification, attestation evidence generation, and protected use of secrets while retaining efficient access to application run-time state. As exemplary uses, we instantiate ARA for protected media decryption and application control flow measurement. Our prototype and evaluation show that ARA supports frequent run-time RoT-backed operations at near in-process cost, with roughly 10x and 50x lower overhead than out-of-process equivalents. This offers a practical bridge from layered attestation to application run-time trusted computing on ARM.

# 论文总结：Extending Layered Attestation into ARM Application Run-Times (ARA)

## 一、核心问题与整体含义

- **背景**：现代移动/边缘平台（Android、iOS）已通过硬件背书的分层证明（layered attestation）在**加载时**验证应用与平台完整性，代表性服务包括 Google Play Integrity API 与 Apple App Attest，底层依赖 ARM TrustZone 等硬件信任根（RoT）。
- **核心问题**：一旦应用进入**运行阶段**，平台几乎不再提供任何可信支撑——无法可信地度量运行时行为，也无法在应用自身内部保护密钥等安全关键状态。
- **根因分析**：建立"以应用为中心的 RoT"存在关键矛盾——既要**隔离**出一个应用内的可信运行时基座，又要把它与底层硬件背书的 RoT 保证**连接**起来。传统方案（独立进程、内核特权软件、TEE）虽能提供隔离，但每次运行时可信计算操作都要跨越保护边界（上下文切换、IPC、特权级/TEE 切换），开销对细粒度运行时服务（如持续完整性监控）而言不可接受；纯软件方案（插桩、SFI）虽避免边界跨越，却带来巨大的应用运行时开销。
- **整体含义**：作者观察到 ARMv8.9 新引入的 **POE（Permission Overlay Extension）**首次使"硬件背书的分层证明"与"应用级隔离"共存于同一架构。ARA 利用这一契机，在**应用自身地址空间（用户态）内**构建硬件隔离、可被证明的运行时锚点，承载可编程的度量 RoT（RTM）与存储 RoT（RTS），把信任链从加载时延伸到执行期。

## 二、方法论

### 核心思想
- 在同一个用户态进程内，用 POE 把地址空间划分为三个互不信任的域，使可信运行时基座（ARA）与不可信应用（App）**共享虚拟地址空间但硬件强制隔离**，从而让 RoT 操作的开销接近普通进程内函数调用，同时通过分层证明系统实现远程可验证性。

### 关键技术细节

- **POE 机制基础**：
  - POE 在常规 MMU 页表权限之上叠加一层访问控制，粒度到虚拟内存页，权限编码在页表项（PTE）中。
  - 处理器维护 `POR_EL0` 寄存器（64 位，含 16 组 4 位 R/W/X 权限）；标准 64 位 PTE 中域 ID 仅 3 位，故实际同时可用 8 个域（Perm0–Perm7）。
  - 有效权限 = 常规 MMU 权限 ∩ 该页域 ID 所选中的 POE 权限，全部由硬件并行检查，开销极小。
  - **快速域切换**：用户态一条 `msr POR_EL0, Xn` 即可重配权限，无需内核介入；因此可在加载时静态扫描并 NOP 掉不可信代码中的 `msr POR_EL0` 指令。Linux 6.12 起 arm64 通过 `pkey_*` 系统调用族与 `pkey_mprotect()` 暴露该能力。

- **三域隔离与访问控制矩阵（Table 1）**：
  - **DOM0**：ARA 可信代码与数据（libara.so、RoT 服务、密钥、度量状态）。
  - **DOM1**：ARA 受控调用入口（App 唯一可执行进入的域）。
  - **DOM2**：不可信应用代码。
  - 运行在 DOM2 时 `POR_EL0` 配置为 DOM2 行：禁止直接访问 DOM0，但允许执行 DOM1；DOM1 内部再分"entry/exit"两种配置，entry 配置无 DOM0 权限，exit 配置提升为 DOM0 权限完成上下文切换。

- **引导与度量链（扩展分层证明）**：
  - ARA 用户态 loader 是进程中第一个执行的代码，由平台完整性机制（Play Integrity / App Attest）在加载时度量。
  - loader 预置 DOM0 代码的已知良好哈希，加载 `libara.so` 前先校验哈希；可信构造函数随后校验 App 与 ARA 入口点哈希。
  - 由此形成信任链：**Platform RTM → ARA loader → App**，每一级在加载时验证下一级。
  - 设计要点：POE 配置、App 二进制静态检查、seccomp-BPF 安装都被写成 ARA 域代码的静态部分，因此对 ARA 域的加载时度量即可证明"图 3 所示进程配置确实被执行"。

- **加载时二进制分析与 JIT 中介**：
  - ARA 逐 4 字节对齐遍历 App 所有可执行区域，匹配 `msr POR_EL0, Xn` 的固定 opcode 与系统寄存器编码（掩码掉源寄存器字段），替换为 NOP（AArch64 定长对齐指令使该过滤比 x86 简单）。
  - 所有创建/修改可执行内存的请求（如 JIT 把 RW 页提升为 RX）被 ARA 截获，先以只读映射、扫描并修补非法指令，再重新标记为 DOM2 可执行，从而维持不变量 IV1。

- **系统调用过滤与中介**：
  - 安装 seccomp-BPF 过滤器，拦截来自 ARA 代码区之外的敏感系统调用（可修改地址空间/保护状态、影响 POE 域分配、让内核代 App 访问 DOM0/DOM1 内存等），重定向到 ARA 校验参数后放行或拒绝。
  - 信号投递与返回同样被中介，防止 App 以非 DOM2 配置恢复执行。
  - 为降低高频系统调用的 seccomp 陷入开销，ARA 额外通过受控调用接口暴露"系统调用服务"快速路径，由 DOM0 代为发起，但**不削弱**校验策略。

- **受控调用流程（Listing 1）**：
  - 接口：`secure_call(FUNCTION_ID fid, void *arg)`。
  - DOM1 入口保存 App 上下文 → `mov x9, DOM0_CONFIG` → `msr POR_EL0, x9` → `isb` 使权限生效 → 跳转到可信 DOM0 调度器 `ara_secure_call`（切换至 DOM0 栈、校验服务 ID 与参数、调用对应函数）。
  - 返回时清除执行状态、恢复 DOM2 配置与 App 上下文；`POR_EL0` 权限切换点被刻意放在 DOM0–DOM2 页边界，保证移除 DOM0 执行权限后下一条指令取自 DOM2 可执行页。

- **平台完整性服务集成与秘密下发**：
  - **Google Play Integrity**：ARA 生成端点密钥对 (pk_D0, sk_D0)，把 pk_D0 放入 `requestHash`；服务器验证 requestHash 匹配、`appRecognitionVerdict = PLAY_RECOGNIZED`、签名证书摘要匹配及平台完整性判决后，用 pk_D0 加密下发秘密。
  - **Apple App Attest**：通过 `DCAppAttestService.generateKey` 与 `attestKey` 获取密钥与证明对象；服务器校验 Apple 信任链与 App ID 绑定后取出 pk_D0 并加密下发。
  - 秘密只进入 DOM0，App 只能通过 ARA 调用间接使用（如用主密钥派生会话密钥、解密应用数据）。

- **RTS/RTM 实例化方式**：
  - RTS：保证下发秘密始终留在 DOM0，返回给 App 的仅是策略允许的输出。
  - RTM：对 App 插桩以收集运行时状态并经 ARA 调用转发；ARA 侧度量/扩展该状态，用下发签名密钥对报告签名后发往远端服务器。

- **安全论证**：定义 7 条不变量（IV1 无 POE 误配置、IV2 返回 App 必为 DOM2 权限、IV3 无 App→DOM0 直接控制转移、IV4 危险系统调用被中介、IV5 异步控制流被中介、IV6 可信服务实现正确、IV7 加载时绑定），并逐一论证其足以满足 4 个安全目标（G1 运行时信任保持、G2 运行时度量完整性、G3 ARA 数据机密性与完整性、G4 ARA 执行完整性）。

## 三、实验设计

- **原型平台（两套互补实现）**：
  1. **QEMU**：在修改后的 ARM Cortex-A76 处理器模型上实现**完整 POE 支持**。
  2. **物理 ARM Cortex-A76**：因商用设备尚无 POE，将每条写 `POR_EL0` 的 `msr` 替换为写 `NZCV` 的 `msr` 并保留内存屏障，以保留程序行为同时计入寄存器更新代价（近似代理）。

- **案例一：RTS——隔离媒体解密**
  - 场景：受 Digital Rights Management 启发的解密流水线（参照 Google Widevine L3），使用 **gpac/libgpac** 框架，媒体以 AES 认证加密保护，密钥在加载时证明成功后由服务器一次性下发。
  - 数据集：3 个 MP4 负载（均为 600 秒、60 FPS）：
    - 1080p / 1920×1080 / 2.00 GB / 26.71 Mbps
    - 4K / 3840×2160 / 4.00 GB / 53.37 Mbps
    - 4K / 3840×2160 / 8.01 GB / 106.74 Mbps
  - 数据以 64 KiB 逻辑块投递；共享内存配置使用 4 MiB 环形缓冲；所有配置绑定到单个 Cortex-A76 核。
  - 对比方法：**Baseline（无隔离）**、**进程隔离**（Shared Memory、Unix domain Socket、named Pipe/FIFO 三种 IPC 变体）、**ARA 隔离**。进程隔离同时被视为使用 Cortex-A TEE（TrustZone）开销的下界。
  - 重复 50 次，报告 95% 置信区间。
