# Names Are Not Objects: Object-Bound Confinement for Compromised AI Coding Agents 

# Daniel Commey 

# Abstract 

Coding agents read repositories and web pages that anyone can write, and then act with their user’s authority. Prompt-injection defenses make it less likely that the model is steered but do not prevent it, so the system around the model must contain an agent that is already compromised. Many exploits against deployed coding agents share one cause: a check approves a name , such as a path, an argument vector, or a directory, and a later step maps that name to a different object :the file behind a symlink, the behavior an option selects, or a repository that git discovers on its own. We present Zero-Trust Agent Cells (ZTAC). A cell runs the agent in a kernel sandbox whose only route to files, programs, and the network is a socket to a broker. The broker resolves each request to the object it will act on, decides on that object, and checks at use that it is acting on the object it authorized. Programs that the broker starts run in a sandbox compiled from the same policy, and approvals are bound to the resolved object and can be used once. Our macOS prototype has 3.2k lines of trusted Rust code, excluding dependencies. We evaluate it against 74 attacks with ground-truth oracles, including replays of 10 publicly disclosed incidents. A tool allowlist loses 66 of them, and an allowlist combined with the kind of command sandbox that deployed agents use loses 56. ZTAC loses 2, both of which encode a secret into traffic to an allowed endpoint, and holds 14 for review. It completes 43 of 46 benign operations, with 8 approval prompts, and 4 of 7 workflows. A no-op brokered request has a median latency of 4.0 ms, and the spawned programs we measured take 8.5 ms to 18.4 ms longer than without ZTAC. 

# 1 Introduction 

Coding agents such as SWE-agent [66] and the agents shipped with commercial assistants read issues, documentation, and repositories that anyone can write, and then call tools that act on the developer’s machine. A prompt injection in any of that content can direct the agent to read credentials, mod-ify files that later run with more privilege, or send data away [17, 28, 69]. Model-level defenses such as structured queries [8], instruction hierarchies [57], and input mark-ing [30] reduce attack success, but adaptive attackers continue to bypass them [38, 68]. A system that runs an agent must therefore limit what the agent can do after it has been com-promised. This is the setting of classic confinement [1, 47], applied to a principal that may follow instructions from any text it reads. Deployed agents confine tools with command allowlists, permission prompts, and operating-system sandboxes for the commands they run [21, 40]. The exploits disclosed against them in 2025 and 2026 show where these mechanisms fail. A read-only command allowlist admitted options that run code or write files [46]; in one case an allowlisted git show wrote a crafted format string over .git/config with --output ,and the next routine git diff ran the external diff driver it defined [22]. Agents ran git inside a nested directory that 

git accepted as a bare repository, whose configuration then executed attacker commands [10, 26, 53]. Six assistants wrote through a project file that was a symlink to a file in the user’s home directory, and their approval dialogs showed the name of the link [20]. Most escapes in a series of seven did not break the sandbox at all: they planted a file in the workspace that a tool outside the sandbox later executed, such as an editor task, a hook, or the interpreter of a virtual environment [13]. In each case a check inspected a name : a command string, a path, a directory’s name. The effect depended on an object 

that a different parser selected later: the behavior that the full argument vector requested, the configuration file that git 

discovered, the file a symlink pointed to, or the program that an editor found by looking inside a directory. File-system security has known this gap for decades as the time-of-check to time-of-use and name-resolution problem [5, 7, 56]. Agents bring it back at every layer of the tool stack, and they can be steered into constructing the aliases themselves. Zero-Trust Agent Cells (ZTAC) is a confinement architec-ture for coding agents built on one rule: authorize the object that will be used, and use only the object that was authorized. ZTAC has three parts. 1arXiv:2610.14488v1 [cs.CR] 10 Oct 2026 • A cell runs the agent in a kernel sandbox that lets it load its runtime, read its key, and connect to one Unix socket. It cannot read workspace contents, open network con-nections, or create processes; it can read file metadata. • A broker receives signed requests on that socket and handles each in six stages: authenticate, resolve, decide, gate, execute, and record. Resolution maps the request to a concrete object (a file identified by its workspace path and inode, a program and argument vector, an endpoint), and the later stages act only on that object. • One policy, two enforcement points. The path rules that the broker evaluates are compiled, in the same order, into the Seatbelt profile under which every spawned program runs. Where the profile differs from the broker, it is stricter by design. Requests that need a human are held in an approval queue. An approval is bound to the cell, the parameters, and the resolved object, expires, and can be used once. Authorization and outcome records form a hash chain signed by the broker. We implemented ZTAC on macOS in Rust and evaluated it against 74 attacks in 7 categories. Each attack has an ora-cle that checks the attacker’s goal against ground truth (file contents, service logs, repository history, or the effect of a tool run after the session) instead of the broker’s reply. The adversary controls everything inside the cell, including the agent runtime and any code it runs, and may plant files in the workspace. Our contributions are: 1. An analysis of agent exploits as name/object gaps at five layers: paths, argument vectors, repository configuration, files handed to other tools, and approvals. For each layer we give a design that resolves the name before deciding. 2. A broker and cell implementation with 3,164 lines of trusted Rust code, excluding tests and dependencies, in which one policy drives both the broker and the sandbox of every spawned program. 3. An evaluation with ground-truth oracles against five con-figurations, among them a command sandbox of the kind deployed agents use, and 14 ablations. ZTAC lets 2 of 74 attacks succeed, contains all 10 replayed incidents, and completes 43 of 46 operations and 4 of 7 workflows. 4. Eight flaws that we found in our own implementation while building the attack suite and reviewing the code, seven of them name/object gaps inside ZTAC, and the change that closed each. 

# 2 Background: Names and Objects 

A coding agent exposes a small set of tools: read and write files, run a program, and make an HTTP request [2, 66, 67]. A policy for these tools is written in terms of names, because names are what the model emits and what a human can read: “do not read .env ”, “allow git status ”, “allow requests to 

api.example.com ”. The operating system and the tools act on objects, and the two diverge in the five ways of Table 1. 

Paths. Path-based checks are the textbook case. A rule that protects .env must also catch config.txt when it is a sym-link to .env , CHANGELOG.txt when it is a hard link to it, and 

.ENV on the case-insensitive file system that macOS uses by default. Canonicalizing the path once is not enough, because anything that can modify the directory tree between the check and the open can swap a directory for a symlink [5]. An agent is in a good position to do this: it can ask the broker to run a program that leaves such a modification behind. Lilienthal and Hong report check-to-use races in agent tool chains more generally [34]. 

Argument vectors. An allowlist matches a command string, but the program interprets the whole vector, including git 

options such as -c , --output , and --no-index . A general in-terpreter accepts any program as an argument, so no argument check can make it safe. 

Repository configuration. Repositories contain configura-tion that git executes, and repository discovery adds an alias: 

git run in a directory that looks like a bare repository uses that directory’s configuration [53]. A poisoned workspace may already contain such files. 

Files handed to other tools. The agent’s writes outlive its session. Editors run tasks from .vscode/tasks.json 

when a folder opens, agent harnesses run hooks from project settings, editors execute the interpreter of every virtual envi-ronment they discover, and git obeys the configuration of any directory it accepts as a repository. These consumers run outside whatever sandbox confined the agent [13], and their notion of the object is not the path that a rule names. A repository need not be called .git [11]; git needs only a HEAD file, an objects directory, and a refs directory. A virtual environment is recognized by its contents, whatever its directory is called [36]. On a case-insensitive volume, 

.VSCODE/tasks.json is the editor’s task file. 

Approvals. A human approval is a check like any other. If it is recorded as “the cell may run this request”, the cell can present it twice, with different arguments, or after it has changed what the request’s names refer to: a symlink’s target, or the content staged for a commit. # 3 Threat Model and Goals 

Adversary. The adversary controls everything inside a cell: the model, the agent runtime, and any code the agent writes or runs, as if a prompt injection had succeeded completely. The adversary may also place arbitrary files, including sym-links, hard links, and .git contents, in the cell’s workspace before the session starts (a poisoned repository). The adver-sary knows the policy and the public keys of all cells. The adversary does not hold other cells’ private keys and cannot reach the reviewer except through the summaries and free-text intents that the broker displays. 

Trusted components. We trust the kernel and its sandbox, the broker and its configuration, the operator who writes the policy, and the reviewer who answers approval requests. Pro-grams that the broker spawns are not trusted; they run under the exec sandbox. 

Assets and goals. We consider five attacker goals, each checked by an oracle in the evaluation: disclosure of files outside the workspace, of another cell’s workspace, or of sen-sitive workspace files without approval; integrity violations of files outside the workspace, of repository metadata, or of sensitive workspace files without approval; execution of code outside the policy, such as a shell, a repository-configured command, or a file that a tool outside the cell runs after the session; exfiltration of data to an endpoint the policy does not allow; and authority : acting as another cell, replaying a request, or using an approval for something the reviewer did not approve. 

Security properties. ZTAC aims for the following prop-erties. P1, complete mediation: the cell has no effect on files, programs, or the network except through the broker. P2, object-level authorization: the broker decides on the object the operation will use, and at use the adapter checks that it reached that object or fails, provided nothing outside ZTAC changes the workspace during a request. P3, consistent con-finement: code that a permitted request starts is subject to the compiled path rules or to stricter ones. P4, bound approvals: 

an approval authorizes exactly one execution of the reviewed request on the reviewed object by the requesting cell, within the recorded object-state scope. P5, accountability: every well-formed request leaves a signed record, written before any effect it causes; altering a record is detectable, and so is deleting one, given a retained later head hash or receipt. 

Out of scope. Kernel and sandbox escapes; side and covert channels; exfiltration of data that the policy lets the cell read, encoded into traffic to an endpoint the policy allows; a re-viewer who approves a harmful request because its descrip-tion persuades them; denial of service against the broker; and pre-existing files that developer tools execute independently of any agent action. 34 Design 

A deployment runs one broker and one cell per agent session (Figure 1). Each cell has a key pair, a workspace directory, and a set of tools granted by the operator. 

# 4.1 Cells 

A cell is a process tree that the launcher starts under a deny-by-default kernel sandbox profile. The profile allows reading the system libraries and frameworks needed to load code, reading the cell’s private key, executing the agent’s own binary, and connecting to the broker’s Unix socket. It allows no other file access, no network sockets, no signals to other processes, and no execution of other programs. The cell therefore cannot read its own workspace directly: it sees files only through the bro-ker, which makes every read and write a mediated, recorded event (P1). Giving the cell read access to its workspace would be faster, but reads of sensitive files are exactly the events the policy must see. The agent reaches its model through the broker’s HTTP tool, with the model provider’s API as an endpoint in the policy. Read-only directories that the agent runtime needs, such as its installed packages, can be added to the cell profile at launch. 

# 4.2 Authentication 

A request names a tool, carries JSON parameters, a free-text intent, a timestamp, a 128-bit nonce, and optionally an ap-proval identifier, and is signed with the cell’s Ed25519 key. The cell identifier is derived from the hash of the public key, so a cell cannot claim an identifier without the matching pri-vate key. The broker verifies the signature, checks that the key is enrolled, rejects timestamps outside a window (30 s by default) and nonces or request identifiers seen within it, and checks that the tool is granted to the cell. Each accepted nonce and request identifier is appended to a replay log and synced to disk before authentication succeeds, so a request cannot be replayed after the broker restarts, even within the 1 s tolerance for timestamps ahead of the broker’s clock. Requests signed before the broker started are refused. The intent is shown to reviewers and logged but never used for authorization. Au-thentication matters even on a single machine: every process of the same user can connect to the socket, and cells must not be able to act as each other. 

# 4.3 Resolve before deciding 

The resolver turns parameters into the operation the broker would perform. The policy is evaluated on this resolved form, and the adapters execute exactly this form. 

Files. A path is joined to the cell’s workspace and resolved the way the kernel would open it: symlinks in the existing prefix are followed, and components that do not exist yet (for a write) are appended literally and may not refer to a parent di-rectory. The result must lie inside the workspace. On macOS, 

realpath returns the stored case of each existing component, so .ENV resolves to .env . Rules are matched against the re-solved workspace-relative path, not the requested string, and without regard to case, because a component that does not ex-ist yet keeps the requested spelling and other tools will open it under any case. Two properties of the target are recorded with it. If the target is a regular file with more than one hard link, its other names are unknown, so name-based rules cannot be trusted and the read requires approval. The device and inode number identify the object that was classified. 

Race-free use. Resolution and use are separate system calls, so a process that modifies the workspace concurrently could swap a directory for a symlink after the check. The file adapters therefore never open a path string. They open the workspace directory and walk the resolved relative path one component at a time with openat(O_NOFOLLOW) , so a symlink anywhere on the path makes the open fail. A read then compares the inode it reached with the classified one and fails on a mismatch. A write creates a temporary file in the directory it reached and renames it over the target with 

renameat , which replaces a symlink at the destination instead of following it. As a second, independent measure, spawned programs cannot create processes, so no code started by the cell is running while the broker handles a later request. 

Provenance. A file that the cell wrote through the broker is readable by that cell even if a rule would otherwise hold it, as long as its content is unchanged. The broker keeps the SHA-256 of the last content it wrote for each cell and path. Reading back one’s own output discloses nothing, and without this exception a cell that writes a test certificate would need approval to read it back. 

Programs. A program name maps to an absolute binary chosen at broker start-up, with a kind: plain programs that load no code (such as echo ), git , and interpreters . The work-ing directory is resolved like a path. Arguments must be strings within count and length limits. 

Endpoints. A URL is parsed once; the host, port, and scheme of the parsed URL decide, and the adapter sends the request to that parsed URL.

Programs. Plain programs are allowed. Interpreters are al-lowed only when the exec sandbox is active. For git , the first argument must be a subcommand from one of two tiers: read-only and staging subcommands ( status , diff , log ,

show , rev-parse , ls-files , add ) are allowed, and subcom-mands that change history or the working tree ( commit , push ,

checkout , switch , reset , merge , rebase , and others) re-quire approval. Requiring the subcommand first rules out global options such as -c and -C . Options that write files, run programs, or select another repository ( --output , --exec ,

--upload-pack , --git-dir , and ten others) are refused. Be-cause git accepts any unambiguous prefix of a long option, an argument is refused when its name is a prefix of a refused option. A commit must use the existing index: -a , --include ,

--only , and pathspec forms are refused because they incorpo-rate working tree content after review. 

Endpoints are host and port pairs, each marked automatic or approval-required. Only GET and POST are supported. Before a request leaves, the broker scans the body, the decoded URL, and all headers against secret patterns (PEM private-key headers and the token formats of several cloud, source-hosting, and API services) and refuses a match. 

# 4.5 One policy, two enforcement points 

Argument filtering cannot confine an interpreter, and it cannot anticipate every behavior of a program as large as git . ZTAC therefore runs every spawned program inside a Seatbelt profile that the broker generates for that program from the policy. The profile starts from (deny default) and allows reading system libraries, the program’s toolchain directory, and the workspace; writing the workspace and a per-cell temporary directory; and executing only binaries inside the toolchain. It allows no network access, no connections to the broker socket, and no process creation, which also rules out background processes that outlive the request. The path rules become allow and deny clauses emitted in reverse order, so that Seatbelt’s last matching clause gives the broker’s first matching rule; an exception such as 

.env.example therefore holds in both places. One transla-tion turns each glob into a regular expression anchored at the workspace, with ASCII case folding. The broker’s matcher lets . match a newline, as Seatbelt’s does, and direct requests refuse control characters in paths. The profile is stricter than the broker in three ways. A rule that restricts reads also denies writes, because link(2) and 

rename(2) are checked as writes on the source, so a pro-gram cannot give a protected file a new name. A program cannot create, rename, or remove a directory that a restricting 5rule names, such as .github in **/.github/** , because re-naming a directory moves everything below it; these clauses come last. And a spawned program has no approval path, so whatever the broker would hold for review, the profile denies. Writes to .git are denied to every program except git . Seat-belt matches resolved paths, so symlinks do not evade these clauses, but a hard link is a second name that no path rule recognizes. Before it starts a program, the broker therefore refuses the command if any regular file in the workspace has more than one link. This also refuses benign hard links, such as the object files of a repository cloned from a local path, and the scan grows with the number of files. Files whose content the cell wrote (by provenance) are readable by the program, as they are for direct reads. We test agreement on 52 path and access cases, with each deliberate difference specified in advance. 

git receives additional treatment. It runs with GIT_DIR 

and GIT_WORK_TREE fixed to the workspace, so repository discovery cannot pick up a look-alike bare repository. Sys-tem and global configuration are disabled, and command-line configuration, which takes precedence over the repository’s own, pins 14 settings: no hooks, no file-system monitor, no pager, editor, credential helper, or SSH command, and no pro-tocols other than local files. git therefore cannot fetch or push over the network; network access goes through the bro-ker’s HTTP tool. For diff , show , and log , the broker adds 

--no-ext-diff and --no-textconv . These settings close the configuration hooks that have fixed names. They cannot close the ones whose names the repository chooses, such as filter drivers. The exec sandbox stops those, because the kernel refuses any command that git tries to run outside its toolchain. 

# 4.6 Egress 

Only the broker opens network connections. A redirect sends the request to a destination the policy did not see, so the broker follows a redirect only if the new URL is itself an endpoint the cell could reach without approval, and re-checks every hop. A system proxy is ignored, so the parsed URL is the destination. Allowlist entries bind host and port: an allowlisted host does not expose its other services. 

# 4.7 Approvals 

When the policy requires approval, the broker stores a pend-ing record and returns its identifier. The record shows the reviewer the resolved operation (for example read .env for a request that named config.txt ), the policy’s reason, and the agent’s intent. The record also stores the full canonical request parameters. ztacctl approvals show displays all fields; execution summaries include every argument and the working directory, and write summaries include the content hash. The cell cannot write the approval store, because it lies outside everything the cell sandbox allows. 

# 4.8 Audit 

Before an allowed operation runs, the broker appends an au-thorization record; after it runs, the broker appends a final record with its result status. Refused and pending requests receive a decision record. Each record has a sequence number, the request identifier and cell, the decision and reason, the resolved summary, a hash of the parameters, whether the oper-ation ran, and stage timings. Each record includes the hash of its predecessor and is signed by the broker [49], and the broker returns the record’s hash and signature to the cell as a receipt. Editing, reordering, or deleting a record breaks verification of every later record; truncating the tail is detected against a retained head hash or a receipt. A failed authorization append prevents execution. A failed final append is reported as an audit failure, but cannot undo an effect that already happened. 6The broker verifies the existing chain at startup and refuses to extend a damaged log. Per-record syncing is optional and dis-abled in our measurements; the replay log is always synced. The chain provides tamper evidence, not crash-proof final outcomes (P5). 

# 5 Implementation 

ZTAC is written in Rust and consists of a shared core (pro-tocol, canonical JSON, signing, and profile generation; 327 lines), the broker (2,753 lines), and the cell launcher (84 lines), for 3,164 non-blank, non-comment lines of authored trusted code, excluding tests and library dependencies. The broker uses the ed25519-dalek , sha2 , regex , and reqwest 

libraries. Cells and the broker communicate with newline-delimited JSON over a Unix socket with mode 0600 . Signa-tures cover a canonical encoding with sorted keys, so both sides hash the same bytes. The broker serves each connection on a thread but pro-cesses requests under one lock, which makes approval con-sumption and workspace changes atomic with respect to each other. Sandboxes use Seatbelt through sandbox-exec . Apple marks this interface as deprecated, but it remains the mecha-nism that deployed agent sandboxes use on macOS [21, 40], and its profile language has been studied in depth [6, 19]. The glob compiler turns every letter into a class of both cases, so the broker matcher and profile compiler apply the same ASCII case folding. On macOS, /usr/bin/git and 

/usr/bin/python3 are shims that consult xcrun ; the broker resolves the real binaries once at start-up and admits only their toolchain directory. Spawned programs get a cleared en-vironment, HOME set to the workspace, and a private temporary directory. On Linux, the cell maps onto Landlock [54], seccomp, and a network namespace. The exec sandbox is harder to port. Landlock grants access to directory hierarchies and cannot exclude matching files inside an allowed one, so the deny clauses would need another mechanism, such as a view of the workspace that omits protected files, or a supervisor for decisions that depend on run-time state, like the one in Sand-lock [58]. We have not built that port. 

# 6 Evaluation 

RQ1: Does ZTAC contain a compromised agent, and how do simpler designs, including a configuration modeled on deployed command sandboxes, compare? RQ2: Which mech-anisms are responsible? RQ3: Can an agent still do its work? 

RQ4: What does mediation cost? 

# 6.1 Setup 

Experiments ran on a Mac18,5 with an Apple M6 and 24 GiB of memory running macOS 27.0.1 (26A434), with git 2.54.0 (Apple Git-157) and Python 3.9.6. Each configuration starts its own broker with two enrolled cells, A (the attacker) and B (a victim). Cell A’s workspace is a small Python project under version control with a .env file that holds a database pass-word and an access key. Cell B’s workspace holds a private file and a commit that names it. Outside both workspaces, a home directory holds an SSH private key and a shell start-up file. Every value an attacker might steal is a unique canary string. Local HTTP services stand in for an allowlisted sink, an endpoint that requires approval, an endpoint that redirects, and an internal administration service that is not allowlisted; a UDP listener and a Unix socket standing in for a privileged local daemon complete the set. All services record every re-quest verbatim. The harness sends cell A’s broker requests signed with A’s key. Direct attacks run a probe program inside A’s cell sandbox, or as an ordinary process in configurations without one. 

Configurations. B0 executes every request as given, like an agent with direct tool access. B1 is a tool allowlist of the kind deployed agents use in their default permission modes: paths must be relative and free of .. , git subcommands must come from the union of ZTAC’s two tiers, hosts must be allowlisted, and there is no approval tier, no resolution, and no sandbox. 

B2 adds to B1 a command sandbox modeled on the sand-boxes that deployed agents place around the commands they run [21, 40]: every spawned program, including interpreters, runs under a Seatbelt profile that lets it read and execute any-thing and create processes, but write only the workspace and a temporary directory, with no network. The agent process itself is not confined, and the sandbox knows nothing of the path rules. Zbroker is the full ZTAC broker without the cell sandbox, which isolates the contribution of P1. ZTAC is the full system. Each of 14 ablations removes one defense from ZTAC, or two overlapping ones together. A prompt-only de-fense is not a separate configuration: under our threat model the prompt is controlled by the adversary, so it behaves as B0. 

Attacks and oracles. The suite contains 74 attacks: 15 on the file system, 21 through program execution, 8 that hand a file to a tool outside the cell, 9 on the network, 5 on the request protocol, 6 on approvals, and 10 in which the cell process acts directly instead of through the broker. Before each attack, the workspaces, canaries, and service logs are reset. # 6.3 RQ2: Which mechanisms matter 

Removing a defense lets the attacks in Table 4 succeed. Where two defenses overlap, a paired removal shows what either one prevents. Authentication stops impersonation, un-enrolled clients, and tampering; freshness stops replay. For direct file requests, resolved classification stops the symlink and hard-link aliases of .env , the symlinked editor directory, and approval retargeting: without it, the broker classifies the requested name, so a symlink called cert.txt needs no ap-proval at all. The case alias .ENV needs no resolution, because rules match without regard to case. Strict egress stops the attacks that reach another port on an allowlisted host, follow a redirect to the internal service, or reach the approval-required endpoint through the automatic entry for the same host. Full-request scanning stops keys placed in the URL or a header. The approval tier is the largest single contributor (18 attacks): without it, every request that the policy considers sensitive runs. The VCS guard and the exec sandbox overlap but do not coincide. Without the exec sandbox, a repository-defined clean filter runs (the pinned configuration cannot name it) and 

git diff --no-index reads outside the workspace. With-out the VCS guard, the GitPwned replay succeeds: the sand-box must let git write its own metadata, so only the option filter stops --output=.git/config . Removing both lets 5 attacks through, and without the exec sandbox ZTAC must also refuse interpreters (RQ3). The object-binding ablation removes resolved-object and repository-state binding while retaining exact request fields, a comparator motivated by Approval Laundering [61]. It lets 2 additional attacks succeed, including approval retargeting and stale staged state. Removing policy rules from the exec sandbox admits 7 additional attacks: workspace confinement alone does not protect sensitive files within it. Descriptor walking and the fork ban overlap; their paired ablation and the repeated trials below isolate the directory-swap vector. We also execute broker requests and Seatbelt file opens on 52 specified path/access cases: default exceptions, nested paths, case aliases, overlapping allow/deny rules, access-specific rules, and newline paths. All match their indepen-dently specified outcomes; of these, 3 differ between broker and sandbox by design, through read-to-write strengthening or control-character rejection. A separate test confirms the guard on renaming a protected directory. 

# 6.4 Flaws found in our own implementation 

Building the suite and reviewing the code exposed eight flaws in ZTAC that the existing attacks did not detect. The evaluated system fixes all eight, and each has a regression test in the attack suite or, for the broken diff, in the benign workload. 

(1) Approval retargeting. Approvals were bound to the re-quest parameters only. A cell requested to read cert.txt ,a symlink to a test certificate; the reviewer approved read certs/dev.pem ; the cell then had a Python script repoint the symlink to .env and presented the approval, which still matched. Binding approvals to the resolved object closed it. 

(2) Stale repository state. A cell staged a typo fix and re-quested a commit. After the reviewer approved it, the cell staged a backdoor file with the allowed git add and pre-sented the approval, and the commit included the backdoor. Binding git approvals to HEAD and the index closed it. 

(3) Directory swap. The read adapter opened the canonical path string with O_NOFOLLOW on the last component only, so a process left behind by a script could swap a workspace directory for a symlink between check and use. In 10 trials per configuration, the swap succeeds in 10 when both the descriptor walk and the fork ban are removed, and in 0, 0, and 0 when only the walk, only the fork ban, or neither is removed. 

(4) Directory rename. A script could write a workflow under 

ci/ and then rename ci to .github , because the sandbox clause for **/.github/** matched paths below .github 

but not the directory itself. The profile therefore also guards every directory that a restricting rule names. 

(5) Case at creation. Resolution returns the stored case of components that exist, but appends new components as the request spells them, and rules were matched with case. A write to .VSCODE/tasks.json matched no rule, and the edi-tor later opens that file as .vscode/tasks.json . Rules are matched without regard to case in the broker and the gener-ated profiles. On our volume, Seatbelt already compared paths without regard to case, so only direct writes were affected. 

(6) A broken diff. Pinning diff.external to the empty string, meant to disable external diff drivers, made git try to execute an empty command for every textual diff. The workload used only git diff --stat and missed it. ZTAC passes --no-ext-diff instead, and the workload includes a plain git diff .

(7) Sandbox-profile injection. # 7 Discussion and Limitations 

Exfiltration through allowed channels. ZTAC controls where data can go, not what it encodes. A cell that may read a secret and may post to an endpoint can send the secret in any encoding, as the two remaining successful attacks do. Pattern scanning catches careless or verbatim leaks only. Closing this channel requires information-flow tracking that follows data from sensitive reads to outgoing requests [14, 16, 52], or a policy in which no cell holds both sensitive data and an exit, avoiding the combination that Willison calls the lethal trifecta [64]. ZTAC supports the second option through per-cell tool grants and broker-wide endpoint rules. Distinct endpoint rules per cell are not implemented; separate broker configurations could provide that separation. 

Handoff rules are an enumeration. The rules for files that other tools run name the consumers we know: editor tasks, agent hooks, git ’s HEAD , and virtual-environment interpreters. A tool that executes some other file, recognized by its own signature, is not covered until a rule names that file. Writing the rule for the file that makes a directory executable, rather than for the directory’s conventional name, is what keeps a renamed directory from evading it, but the list has to be maintained like the list of credential files. Some handoffs are out of reach of any rule: a Makefile or a test that the agent edits runs when the developer next builds, and only review of the change can judge it. 

What object binding relies on. File reads walk from the workspace with openat and compare the inode they reach with the authorized one, so the check and the use concern the same descriptor. Writes compare the directory entry with 

fstatat and then replace it with renameat ; these are two system calls. They are equivalent to one atomic step only because the broker handles one request at a time and no pro-gram started by a cell runs between requests (the fork ban). A process outside ZTAC that changes the workspace con-currently, such as the developer’s editor, is covered neither by this argument nor by the hard-link check. Programs and working directories are bound by path, not by descriptor. The race trials cover the directory-swap vector only. 

Approval-state scope. The Git binding hashes the current 

HEAD , current branch, packed refs, and index. Together with refusing unstaged commit forms, this supports the staged-commit tests. Other loose branch references and all working-tree state are not included; approvals for merge , reset ,

checkout , or rebase therefore do not establish the same reviewed-revision guarantee. Binding resolved revision tar-gets is required before claiming it for these commands. 

The reviewer. Escalation moves the decision to a human, who can be persuaded by the agent’s intent text or tired by frequent prompts. ZTAC shows the resolved operation rather than the request and binds the approval to it, which removes the most direct forms of deception, but it cannot judge whether a commit is harmful. We count 8 prompts in 46 operations and did not study reviewer fatigue or accuracy; a deployment would tune the rules, for example to allow commits on a scratch branch. 

Platform and sandbox. Our profiles allow reading file metadata everywhere, which reveals whether a path outside the workspace exists and how large it is. We did not test Seat-belt itself for escapes. Denying process creation is blunt, since build tools spawn children; allowing it needs a guarantee that all descendants end with the request, which a process group does not give (a child can call setsid ) and a Linux cgroup does. 

Agent integration. We evaluated ZTAC with a client library and scripted requests, not with an off-the-shelf agent runtime. Porting an agent means replacing its tools with broker calls and launching it in a cell; its model traffic becomes an allowed exit. A deployment should let the broker attach the model API key to those requests, so the key never enters the cell. 

Scope of the evaluation. Endpoints are matched by host name, so a name that resolves to an internal address would be reached. Requests from different cells serialize behind one lock, so a long-running program blocks other cells. Prove-nance is held in memory and lost on restart. The evaluation uses one small Python project, and B2 approximates deployed sandboxes rather than running them. The suite covers the gap classes of Table 1 but cannot be complete; extending it kept finding new aliases. 12 8 Related Work 

Confinement and reference monitors. ZTAC applies com-plete mediation, fail-safe defaults, and privilege separation [1, 42, 47]. Janus interposed system calls [27]; interposition fails when the kernel re-reads names after the monitor checks them [23]. Ostia instead delegated sensitive calls to a trusted agent [24], as the ZTAC broker does. Capabilities remove am-bient authority [18, 63]; scoped resolution prevents the broker becoming a confused deputy [29]. Trusted-directory walks, no-follow opens, and identity checks are established reme-dies for pathname attacks [5, 7, 56]. ZTAC applies them to an agent that constructs aliases on demand, authenticates every request [44, 62], and uses signed hash chaining [49]. Our trun-cation check still needs a retained head; richer tamper-evident structures are another option [15]. 

Model-level defenses. Training, structured prompts, and input marking [8,30,57], plus classifiers [31], reduce injection but remain subject to adaptive attacks [38,68]. ZTAC assumes compromise and complements these defenses. 

System-level defenses for agents. CaMeL separates plan-ning from untrusted data and checks capabilities before tool calls [16]; FIDES tracks information-flow labels [14]. Progent, AgentSpec, and Conseca constrain tool calls with policy [51, 55, 59]. IsolateGPT isolates applications [65]; ACE separates planning and execution [33]. SEAgent sup-plies mandatory access control [32], AC4A resource permis-sions [50], AuthGraph provenance-aware authorization [60], and GAAP information-flow enforcement [52]. Agent libOS controls typed capabilities [70]; PORTICO revokes capabili-ties when subgoals close [48]. Agent-security design patterns and foundations frame these approaches [4,9]. ZTAC supplies a concrete enforcement boundary beneath tool-call policy: res-olution, descriptor-based file use, and confined spawned pro-grams. Its rule language is simpler than these policy models; combining it with one of them is future work. 

Approvals and file systems. Approval Laundering binds invocation fields; its token stops delegation mismatches and a seeded temporal construction [61]. Our comparator tests the separate gap when those fields stay fixed but a symlink target or staged state changes. YoloFS stages changes for review, inspection, and undo and evaluates hidden side effects [71]; we evaluate adversarial aliases and approval-state changes. Rashidi reports fragmented isolation and TOCTOU compar-isons [43]; our suite evaluates these mechanisms together. 

Agent sandboxes in practice. Commercial agents combine command sandboxes with prompts [3, 21, 40]. Sandlock con-fines agent code on Linux with Landlock and seccomp and moves decisions that depend on run-time state, including in-spection of execve arguments without check-to-use races, to a supervisor [58]. The agent runtime that embeds Sandlock is trusted; ZTAC treats the runtime itself as compromised and confines it. Public escapes show how workspace files can later execute outside the command sandbox [13, 20]. ZTAC also confines the agent process, compiles ordered path rules, checks resolved aliases, and binds approvals to recorded ob-ject state. Risk taxonomies and emulated-tool studies motivate this boundary [41, 45]. 

# 9 Conclusion 

A compromised coding agent is a local adversary that creates files, links, and repository configuration, asks a privileged component to act on names it chose, and leaves files for the developer’s own tools to run. ZTAC removes its ambient au-thority, resolves every request to an object before deciding, checks that object at use, and compiles the same policy into the sandbox of every program it starts. On our suite it con-tained all but two of 74 attacks and all 10 replayed incidents. The price is 4.0 ms per brokered request and 3 of 7 workflows, those that need process creation, a virtual environment, or git commit -a .

# B Open Science 

The artifacts are available at https://github.com/dco mmey/ztac . The artifacts are the Rust source of the broker, cell launcher, and evaluation harness; the attack suite with its oracles and predicted outcomes; the benign workload; the script that runs all experiments and records the environment; the raw results of the runs reported here; and the analysis script that generates every table, figure data file, and number in this paper from those results. Running experiments/run.sh 

on a Mac with the Xcode command-line tools reproduces the evaluation, including the repeated race trials; its running time depends on the benchmark scale and the number of trials. The attack scenarios target only local test files and local services. 

# C Ethical Considerations 

This work involves no human subjects and no user data. All attacks ran against our own system and local test services, with canary values in place of real secrets. The incidents we cite were publicly disclosed by their discoverers; some were unpatched by their vendors at the time of disclosure. Our replays reproduce their mechanisms only against our own system, we did not run them against the affected products, and we describe them at the level of detail of the public disclosures. We report no new vulnerability in a third-party product.
