Abstract 

Confidential Virtual Machines (CVMs), such as AMD SEV-SNP, and process enclaves, such as Intel SGX, provide work-load protection against cloud threats. However, they strongly differ in TCB, deployment cost and speed, peer workload protection, resource sharing, fine-grained isolation and at-testation, and programming capabilities. Nesting process enclaves within CVMs offers an optimal solution and an op-portunity to address long-standing SGX limitations: lack of intra-enclave protection, expensive transitions and exception paths, slow enclave cloning, and a restricted programming model that limits Library Operating Systems (LibOS). This paper introduces TEEVisor, a CVM-resident architec-ture consisting of a security monitor and a kernel driver that leverages AMD SEV-SNP Virtual Machine Privilege Levels (VMPLs) to build hardware-protected, process-level enclaves inside a guest CVM with two modes: (1) an SGX binary compatibility mode to run unmodified SGX applications; and (2) a novel extended SGX (eSGX) mode optimizing slow execution paths and offering richer enclave programming capabilities. On commercial AMD EPYC hardware, against native CVM execution, TEEVisor incurs under 5% overhead on compute- and memory-bound workloads, around 12% on I/O-heavy applications, and accelerates enclave cloning to a rate of 93 𝜇 s/MB of enclave size, demonstrating that eSGX semantics inside a CVM are practical for production use. 

1 Introduction 

Confidential computing has become a cornerstone primitive for running sensitive cloud workloads on shared infrastruc-ture. Two common Trusted Execution Environment (TEE) ab-stractions are: process-based enclaves such as Intel SGX [13], isolating userspace components in behind a small Trusted Computing Base (TCB), and confidential virtual machines 

(CVMs) such as AMD SEV-SNP [19] and Intel TDX [6], which protect a VM from a malicious hypervisor. SGX is prevalent in server CPUs and at the core of Intel TDX attestation. Critically, neither enclaves nor CVMs alone meet the de-mands of modern cloud services: enclaves retain a small, auditable TCB but impose rigid memory layouts, expensive transitions, and a poor programming model; CVMs offer bi-nary compatibility and rich OS services but expose a large attack surface [14, 22]. This tension has concrete operational consequences. Work-load isolation, resource sharing, deployment cost, and TCB

MicroCVM isolation (e.g., unikernels) reduce TCB but has same scaling issues. Some domains have strict re-quirements (e.g., healthcare [15]) for confidential isolation of workloads, and demand either enclaves or exclusive CVM per workload that is costlier or has higher orchestration com-plexity. Thus, we are motivated to explore solutions at the intersection of CVMs and process-based enclaves. Architectural bottlenecks in SGX have hindered its broader adoption: enclave exceptions force costly transitions and host interaction, degrading memory management and latency in exception-heavy applications (JVM [44]); host-mediated signaling and transitions for preemption; and emulating 

fork /clone using sealing and state copying has significant overheads despite SGXv2 improvements and runtimes like Haven [9], SCONE [7], Graphene-SGX [37] and Occlum [35]. Lack of in-enclave privilege layers prevents efficient en-forcement of trust and isolation. As such, LibOS secrets can-not be robustly isolated and protected from buggy or com-promised enclave applications, especially in multi-party en-claves. Software-based isolation mechanisms —MPK-based [28, 38], nested enclaves [31], and compiler-based compartmen-talization [35]—mitigate some risks but still demand host cooperation, restrict the programming model, may impose performance overheads, or leave enforcement gaps. Address-ing this issue allows new capabilities: faster handling of syscalls and exceptions inside enclaves without software recompilation or enclave transitions; adding timers; easy preemptive scheduling and switching of threads; leading to efficient and richer enclave computing. Comparatively, CVMs avoid these problems by reusing conventional OS stacks, but attempts to shrink the CVM TCB (unikernels [14], micro-VMs [22, 42], and hardened minimal images [12]) trade one set of compatibility challenges for an-other without restoring the small, auditable TCB of enclaves. Recent CVM extensions, AMD SEV-SNP’s Virtual Machine Privilege Levels (VMPLs) [2] and Intel TDX partitioning [4], expose primitives that allow a security monitor (SM) to cre-ate process-level isolation, protected from the guest OS, in a CVM. Prior related efforts—NestedSGX [39], vSGX [43], Veil [5], and Gramine-TDX [22]—demonstrate important di-rections but leave the SGX–CVM gap open: they either re-quire modifications of applications or runtimes, incur large cross-VM transitions, or need hypervisor changes. arXiv:2610.12695v1 [cs.CR] 8 Oct 2026 Our insight is that a single CVM-resident SM can expose the full, unmodified SGX ISA to legacy enclaves and offer new enclave extensions that fix SGX’s long-standing limitations— all without hypervisor, hardware, or host-kernel changes. The core idea combines VMPL isolation, a new in-enclave 

horizontal privilege separation , and a kernel driver outside the enclave TCB for resource management. We present TEEVisor, a CVM firmware built on Coconut SVSM [3] and AMD SEV-SNP. It provides two enclave modes: (1) bit-for-bit SGX compatibility for unmodified binaries, and (2) a novel extended SGX mode with; horizontal privilege levels, copy-on-write cloning, in-enclave exception handling, direct memory management, soft timers, short syscall loops, new context-switch instructions, and SGX-style attestation while keeping resource management under guest OS. We implement TEEVisor as a Rust SM and Linux kernel driver, evaluated on AMD EPYC 7313. An EENTER /ERESUME

TEEVisor adds under 5% overhead on Redis (SCONE), improves Nginx throughput by 25% (Gramine EX-ITLESS [18]), and incurs ∼12% on MariaDB (SCONE). COW-Cloning scales linearly (93 𝜇 s/MB), allowing elimination of costly page re-encryption steps in fork [8, 18]. This paper makes the following contributions: 1. Zero-modification SGX on CVMs. TEEVisor ex-ecutes unmodified SGX binaries, and runtimes (e.g., Gramine, SCONE) in a CVM, enabling drop-in adop-tion of the SGX ecosystem. 2. Extended SGX (eSGX) novelties. eSGX introduces horizontal privilege levels, architectural enclave cloning, in-enclave exception handling and direct memory management, soft timers, and short syscall paths to address core SGX overheads and gaps. 3. Minimal-TCB SM. TEEVisor excludes the guest OS from the enclave TCB, keeps resource management under the untrusted host, and composes with exist-ing CVM attestation without requiring hypervisor or hardware changes. 4. Implementation and evaluation. We implement TEEVisor on Coconut SVSM and SEV-SNP and demon-strate low overheads on compute- and memory-bound workloads, modest overhead on I/O-bound applica-tions, and significant speedups for workloads previ-ously dominated by exits, demonstrating practicality for production use. 

2 Background 

2.1 Intel SGX 

Intel Software Guard Extensions (SGX) isolates regions of virtual address space, enclaves , from the OS and other un-trusted code. Enclave memory resides in encrypted Processor Reserved Memory (PRM): the OS maps enclave virtual ad-dresses into the Enclave Page Cache (EPC), and integrity is enforced through Enclave Page Cache Metadata (EPCM). Enclaves are managed via ENCLS (ring 0) and executed via 

ENCLU (ring 3). Thread Control Structures (TCS) define per-thread execution contexts. At initialization, SGX measures enclave code and data into MRENCLAVE and can emit reports bound to this measurement for local or remote attestation; Quoting Enclaves (QEs) sign reports with secure keys [13]. 

Exception model. Any exception or interrupt during enclave execution triggers an asynchronous exit (AEX): the CPU saves enclave state into the current state save area (CSSA) frame, clears sensitive state, and leaves enclave mode. The OS may handle the event or deliver a signal to a user-space AEX handler. ERESUME restores the saved state. SGX enclave dynamic memory management (EDMM) relies on AEX for resource management with the OS. 

2.2 AMD SEV-SNP 

AMD SEV-SNP, is the latest AMD’s CVM extension that builds on SEV/SEV-ES memory and register protections by adding integrity protection, secure interrupt handling, and flexible attestation using an isolated Secure Processor (SP) running firmware independent of normal CPU cores. 

Reverse Map Table (RMP). The SP-managed RMP in-jectively maps every System Physical Address (SPA) to a Guest Physical Address (GPA) while recording ownership and permissions. A page is owned by the hypervisor (HV), a guest VM, or the SP firmware. Writes are allowed only by the owner; HV reads return encrypted data. The RMPUPDATE 

instruction and the SEV-SNP API modify RMP entries. To pre-vent remap attacks, every page must be explicitly accepted via PVALIDATE inside the CVM; use of an unvalidated page raises a VMM Communication Exception ( #VC ). 

Virtual Machine Privilege Levels (VMPLs). This fea-ture provides hierarchical privilege domains in a CVM. It has 4 levels (VMPL0-VMPL3) each with a Virtual Machine Save Area (VMSA). Per-page permissions (read, write, user- and supervisor-executable) are recorded per VMPL in RMP ta-ble. VMPL0 is the most privileged level; the CVM boots into VMPL0 with full permissions granted on all memory pages. VMPL0 creates higher VMPLs via RMPADJUST and PVALIDATE 

on private pages, and initializes VMSAs before updating the RMP. Permissions checks enforce RMP permissions. 

Interrupts. SEV-SNP has two interrupt interfaces. Re-stricted injection with a doorbell exception ( #HV ) polling a par-avirtualized queue. Alternate injection uses guest-controlled queuing and injection, and a VMSA to emulate APIC/x2APIC. 

VMPL switching. VMRUN binds a vCPU to a specific VMPL via a VMSA pointer in the Virtual Machine Control Block (VMCB); only one VMPL is active per vCPU at any time. I/O and CPUID instructions force a non-automatic exit to VMPL0 for handling when REFLECT #VC attribute is configured.

The guest may also request the HV for a VMPL switch via the Guest-Host Communication Block (GHCB). 

Attestation and sealing. At VMLAUNCH , the SP measures all guest data and metadata pages into a Launch Digest; an optional signed Identity Block (IDB) can bind expected di-gests. After launch, the guest obtains attestation reports from the SP over a secure channel, signed by the Versioned Chip Endorsement Key (VCEK) or Versioned Loaded Encryption Key (VLEK) registered with the AMD Key Distribution Ser-vice. Sealing keys can be derived from VCEK, VLEK, or a migration-agent-supplied VM Root Key (VMRK). 

2.3 Secure VM Service Module (SVSM) 

SVSM defines an execution environment for hosting privi-leged VMPL0 service modules, and protocols to discover and interact with them. The SVSM binary, VM secrets, and meta-data are measured at launch; additional firmware or binaries can be loaded at other VMPLs under the same measurement model. COCONUT-SVSM [3] is an open-source, Rust-based SVSM reference implementation of the protocol. 

2.4 Library OSes for SGX 

Running unmodified applications in SGX usually requires a LibOS that services syscalls inside the enclave. Represen-tative systems range from libc shims to full in-enclave ker-nels: Panoply [36], SCONE [7], Gramine (formerly Graphene-SGX) [37], SGX-LKL [32], and Occlum [35]. SGXv2 [25] added EDMM and richer exception information, easing Li-bOS integration, but the architectural constraints that mo-tivate TEEVisor’s design; host-mediated exceptions; lack of intra-enclave privilege and isolation between an enclave application and LibOS, page-table control, and architectural enclave cloning support; and coarse AEX-based preemption, are unaddressed in SGXv2 and are revisited in §4.2. 

3 Overview 

TEEVisor is designed to execute unmodified SGX binaries transparently inside AMD SEV-SNP CVMs, while introduc-ing new primitives that strengthen SGX’s security properties and address its architectural limitations. This section states the design goals, threat model, and overall architecture. 

3.1 Design Goals 

TEEVisor pursues five goals:  

> 1

Userspace binary and ISA compatibility. Unmodified SGX binaries, SDKs, and LibOSes run on TEEVisor without recompilation. TEEVisor implements the Intel SGX ISA and matches its execution semantics.  

> 2

Memory flexibility. TEEVisor lets any guest memory back an enclave, enabling dynamic mapping of guest OS memory as private enclave memory unlike SGX’s fixed EPC.  

> 3

Rich LibOS abstractions. TEEVisor brings new ISA extensions and features for greater LibOS capabilities while retaining SGX security and resource control model.  

> 4

Strengthened isolation. A dedicated VMPL hosts en-claves, hardening the boundary between enclave, SM, and untrusted guest OS.  

> 5

Attestation support. TEEVisor exposes SGX-compatible attestation workflows so applications can verify they run on genuine, attested hardware and CVM. 

3.2 Threat Model 

TEEVisor minimizes the trusted surface while accounting for adversaries both inside and outside the CVM. TEEVi-sor adopts SGX and AMD SEV-SNP threat models except hardware attacks outside their scope, and DoS attacks. The TCB includes only the SM and the enclave; the guest OS and its drivers are explicitly outside this boundary. TEEVisor defends against four adversary classes: 

Malicious hypervisor. TEEVisor relies on SEV-SNP hard-ware primitives to protect enclave memory and page tables from host observation or tampering. 

Compromised guest OS. Even a fully compromised guest kernel cannot access enclave data: the SM enforces isolation through VMPL permissions independently of the guest OS. 

Untrusted peer applications. VMPL hardware isolation protects enclaves from guest OS and other applications. 

Trust enforcement of enclave code. Third-party code run-ning inside an enclave may be malicious, incorrect or buggy. TEEVisor partitions the enclave into a trusted runtime range and an enclave-application user range, enforced by separate page tables so user code cannot corrupt, access or randomly execute in runtime. 3.4 Comparison with Existing Approaches 

Table 1 compares TEEVisor with three SEV-SNP-based de-signs. vSGX [43] preserves binary compatibility by splitting the application across a normal VM and a CVM; trap han-dlers in both VMs decode enclave instructions and drive SGX emulation. The cross-VM path introduces large round-trip overheads and requires hypervisor adaptation. Veil [5] uses VMPLs to create enclaves inside a single CVM with a dedi-cated VMPL0 monitor, but defines its own SGX-like ABI and relies on hypervisor changes, so it cannot accept unmodified SGX binaries. NestedSGX [39] extends COCONUT-SVSM to host enclaves in SVSM-reserved memory and emulates SGX via ioctls and syscalls, but it does not fully support the SGX model due to missing binary compatibility and incomplete shared-memory synchronization. TEEVisor also builds on COCONUT-SVSM and dedicates a VMPL to enclaves, but is unique in that it runs unmodified SGX binaries at low VMPL-transition overhead and adds features beyond SGX, including in-enclave exception and syscall handling, and architectural COW cloning with page sharing across enclaves.

4 Design 

We first describe the enclave life cycle (§4.1) and how TEEVi-sor achieves userspace binary compatibility 1 and extended SGX (eSGX) features 3 (§4.2). We then present the memory-management design that delivers memory flexibility 2 and strengthened isolation 4 (§4.3), and close with TEEVisor’s attestation chain 5 (§4.4). 

4.1 Enclave Life Cycle 

We describe the control-flow transfers among TEEVisor’s parts during enclave creation, execution, and destruction. 

4.1.1 Enclave Creation. All ENCLS instructions are han-dled by the SM in VMPL0. Untrusted Runtime interacts with the driver via ioctls as in SGX. The driver emulates ENCLS leaf instructions via dedicated SVSM calls. ECREATE creates an enclave in VMPL1 by initializing an SGX Enclave Control Structure (SECS) page, enclave’s root identity. SECS spec-ifies the enclave’s attributes and enables the Runtime and Clone extensions. EADD adds regular pages with customized permissions or TCS pages to the enclave identified by its SECS. EEXTEND measures each newly added page into the en-clave’s digest. After all pages are added and measured, EINIT 

submits a signature structure (SIGSTRUCT) to verify that measurements and attributes match expectations, finalizes the measurement, and makes the enclave executable. 

4.1.2 Enclave Execution. Enclave execution comprises launch, exit, and destruction. 

Enclave Launch. Figure 3 shows how TEEVisor pre-serves binary compatibility during launch. When user-space code executes EENTER , the TEEVisor driver’s die-notifier hook, invoked on the #UD exception path, parses the fault-ing instruction. If it is an ENCLU , the handler enqueues the emulation task on the current task’s work list and marks the exception as handled. Before returning to user space, the kernel executes the emulation, which switches to VMPL1 via the SVSM protocol; the VMPL1 ENCLU handler then loads the enclave context and enters the enclave.

4.1.3 Enclave Destruction. The TEEVisor driver initi-ates destruction when the guest OS terminates the host process. ECCLEARCACHE , ESYNC , and EREMOVE reclaim cache blocks, shared pages, and other resources from the SM; all remaining state is released once the SECS page is removed. 

4.2 Binary Compatibility and eSGX 

To meet 1 , TEEVisor preserves the SGX binary interface and emulates SGX semantics precisely: ENCLU instructions in untrusted code are trapped by the TEEVisor driver at VMPL2, while those inside enclaves are trapped by the SM at VMPL1. This uniform trapping mechanism also lets TEE-Visor correctly emulate instructions that hardware cannot execute directly. Beyond binary compatibility, TEEVisor de-livers eSGX through five features (F1–F5). It is enabled by two new SECS flags; Runtime and Clone . Jointly, F1–F5 ad-dress the SGX limitations summarized in §2.4 and advance goals 1 – 4 :

F1: Horizontal privilege layers. The enclave address space is split into Enclave Runtime (ER) and Enclave Userspace (EU) .ER can read and modify EU memory, but not vice versa, and holds the privilege to execute enclave-management in-structions and handle exceptions that enable running an unmodified application in EU with low overhead. 

F2: In-enclave memory management. ER manages en-clave memory attributes inside, reducing exits and speeding applications with frequent attribute modifications. 

F3: Flexible exception handling. Exceptions raised in-side the enclave are handled by Runtime handlers when configured; unresolved events can be re-raised to the host. Unconfigured exception handlers trigger a normal AEX. 

F4: Controlled runtime/user transitions. TEEVisor pro-vides syscall- and iret -like instructions enabling: (1) tran-sitions between ER and EU; (2) triggering correct Runtime handler, and (3) enabling a mode or context switch. 

F5: Enclave cloning. TEEVisor supports page-granularity COW cloning of a running enclave, preserving integrity and preventing misuse by untrusted parties. 

4.2.1 Enclave Runtime. ER enforces isolation at mem-ory and instruction-privilege levels. Code in ER can access the whole enclave; EU code sees user range only, with the runtime range placed at higher (non-overlapping) addresses. Metadata pages (SSA, TCS, handler pages) and the enclave en-try point must reside in the runtime range; execution begins in runtime mode. Shared memory with guest OS is accessible only from the ER. A dedicated User SSA (USSA) saves EU context alongside the existing SSA range and is repointable via ESETUSSA . In EU, ENCLU is illegal ( #UD ) while syscall is legal and triggers a mode switch. Since TEEVisor owns the enclave page table, EMODPE and EMODPR are replaced with 

EMODP for permission control without guest OS interaction. 

Syscall and exception fast paths. Fig. 5 shows in-enclave syscall and exception handling. The trap handler redirects an EU syscall to a syscall entry in the handler page, switching modes; sysret switches back to EU. SGX-supported excep-tions (with vectors in SSA) redirect to their corresponding entries, incrementing CSSA and saving context in the SSA. Other interrupts and guest OS shared-memory #PFs follow AEX flow. To request guest OS support (e.g., handling #PF via 

ESYNC /EAUG ), ERAISE re-raises SGX-supported exceptions to trigger an AEX. ESWITCH restores EU context in USSA.

4.2.2 Enclave Clone (F5). Clone extends the Runtime feature to accelerate child-enclave creation via COW; ini-tially duplicating only metadata pages. It offers consistency and reliability by enforcing a single active TCS at clone, before the SM freezes enclave state. ECLONE freezes an en-clave, exits synchronously with context saved and writes 

ECloneMetadata to guest OS buffer. An ioctl binds the child using this metadata, and the TEE-Visor driver drives the child’s ECCREATE /ECLONEINFO /ECADD /

ECINIT sequence during a fork , unfreezing the parent on success or calling ECABORT on failure. Post-clone, ERESUME 

continues execution on the cloned TCS. Regular pages are shared until a write or EPCM change triggers a COW, which is serviced from an in-enclave block cache ( ECADDCACHE ), synchronizing mapping states via a polled slotted page. Sec-tion C details the full cloning sequence (Fig. 14).

Because TEEVisor disallows memory swapping in favor of flexible memory conversion (§4.3), the swap-related ENCLS instructions are not supported. AEXNOTIFY, and its associated EDECCSSA , is likewise unnecessary for Runtime-enabled enclaves, which observe exceptions directly. Two new common instructions, 

ESYNC and EADDB (§4.2.4), fill emulation gaps. Some legacy in-structions are disabled under the Runtime feature to harden the enclave against a malicious guest OS, since the SM man-ages page attributes without exiting to the host. 

4.2.4 Common New Instructions. TEEVisor introduces two new ENCLS instructions common to all enclave modes: 

ESYNC and EADDB . ESYNC manages shared pages inside the en-clave and is callable only by the driver, to preserve userspace compatibility and SGX memory guarantees. EADDB accel-erates batch page initialization by using an SVSM buffer to describe contiguous page runs instead of registers (as in 

EADD ). It processes pages sequentially, updating a count, and returns the total pages added to an enclave.

4.3 Memory Management 

TEEVisor separates memory into guest-managed normal memory and SM managed secure memory. VMPL permis-sions isolate the two regions, while the SM can dynamically convert normal pages into enclave memory on demand. TEE-Visor extends EPCM metadata to track page state, sharing, and ownership throughout the enclave lifecycle. During en-clave construction, pages are converted and mapped with enclave permissions; during destruction, their mappings and references are released, and pages with no remaining users are cleared and returned to the guest OS. See Section H. 

4.4 Attestation 

TEEVisor uses two attestations: (1) Platform attestation to verify CVM setup and identity, provision it, and guard against 

rollback attacks ; and (2) SGX-style attestation for application enclaves. SM includes embedded metadata to match identity and measurements of a Platform Initialization Enclave (PIE) and a Quoting Enclave (QE). At boot, the SM generates an ephemeral attestation key pair (SMpub/SMpriv) to anchor local and remote attestations. After registering SMpub with a Key Broker Service (KBS) via SEV-SNP report, SMpriv signs enclave quotes and derives 

local attestation and ephemeral sealing (per boot) keys. KBS’s public key (KBSpub), embedded in the boot image, validates the CVM. Currently, TEEVisor does not support migration .

4.4.1 Platform Attestation. A platform attestation and initialization service (PAIS) runs on the guest OS to attest the platform via PIE. The SM gives PIE extended privileged ac-cess. PIE fetches a public key and nonce from KBS, requests a VMPL0 report containing hash(SMpub, nonce, MRENCLAVE) as REPORT_DATA, and submits them back. On verification, SMpub is registered and KBS returns secrets encrypted with it which the PIE provisions the SM with ESMPROV instruction. The SM validates signatures using KBSpub, confirms cor-rect KBS ownership, and accepts the secrets. All subsequent reports signed by SMpriv are accepted by KBS. Figure 15 illustrates this flow. 

4.4.2 Local and Remote Attestation. TEEVisor preserves SGX report structure with compatible local and remote at-testation anchored, which use QE, in SEV-SNP hardware and registered keys (SMpub/SMpriv). Section D provides the chain-of-trust and key-derivation details. 

5 Implementation 

We implement TEEVisor on top of the COCONUT-SVSM software stack [3]. In addition to a new Linux kernel driver (TEEVisor Driver, 3000 LOC) and an extension of the secu-rity monitor (TEEVisor Security Monitor, 11,500 LOC), TEE-Visor reuses several VMPL-enlightened components from COCONUT-SVSM to realize its functionality; Linux Kernel, QEMU and Open Virtual Machine Firmware (OVMF). 

5.1 Security Monitor 

The SM runs in VMPL0 and services requests from lower VMPLs. It extends the COCONUT-SVSM SM (Rust with sup-porting assembly). As noted in §2.3, SVSM passes parameters through registers plus a registered buffer (CAA page); we add a new request category for extended enclave operations alongside the existing Core, Attestation, and vTPM cate-gories. This subsection covers the implementation details and non-trivial challenges in the SM. 

5.1.1 Security Monitor Initialization Across VMPLs. 

The SVSM SM runs exclusively in VMPL0 with full VMPL permissions; in TEEVisor it emulates ENCLU in VMPL1 while handling other requests in VMPL0, which demands careful permission setup across both levels (Fig. 6). Initialisation pro-ceeds in two stages. During BSP bring-up, TEEVisor parses the IGVM launch info, grants VMPL1 permissions over the SM range, and installs a VMPL1-specific IDT; each AP then follows the same flow and boots into VMPL1 before return-ing to VMPL0. Each vCPU keeps VMPL-exclusive per-CPU state that points at a shared CAA page. Once every vCPU is up, the monitor constructs the EPCM from the guest memory layout; its size scales with guest memory, so a sufficiently large heap is reserved (optionally capped).

The driver passes physical addresses when emulating across VMPLs because the guest OS lacks enclave page map-pings. However, for an ENCLU originating inside the enclave, binary compatibility demands virtual addresses, which the SM resolves by walking its own enclave page tables. The SM returns an SGX error code or an x86 exception vector (encoded) in RAX on return to the guest OS. 

5.1.3 Exception Model. Logically a single vCPU switches between VMPLs, but the HV views the vCPU’s VMPLs as multiple vCPUs with separate contexts that share one APIC ID. Our baseline SVSM lacks Alternate Injection, so TEEVi-sor uses Restricted Injection: KVM emulates the APIC and injects interrupts into the target VMPL via #HV vector. I/O interrupts always go to the active lowest-privilege VMPL (VMPL2 in the normal path), IPIs are routed to the target vCPU in the same VMPL, and timer interrupts are injected into the originating vCPU. Because guest-OS-armed timers cannot cross VMPL boundaries, TEEVisor arms a VMPL1 periodic timer at 100 Hz to preempt enclave execution into SM, then do an AEX; a one-shot timer would be more faithful but costs ∼10,000 cycles per x2APIC MSR access. 

5.1.4 Page Ownership with Clone Feature. Under Clone, an EPCM entry can be shared across enclaves, and SGX’s assumption that every enclave page is removed before its SECS no longer holds. This breaks SECS-based ownership: reusing a destroyed parent’s SECS page for a new enclave creates an ABA-style confusion in which shared pages ap-pear to belong to the wrong enclave. TEEVisor resolves this 

> 7

by tracking each enclave via a unique identifier and an ac-tive descendant counter in an enclave-node list, which safely validates ownership on every EPCM modification (detailed in Section B). 

5.1.5 Page Table Optimization. For eSGX enclaves, the SM keeps two page tables to enforce memory isolation. Be-cause the user range appears in both tables with identical attributes, TEEVisor shares the corresponding page-table entries across the two tables after aligning each level. A re-served bit marks entries that also belong to the runtime table so they are correctly reclaimed when the enclave is removed. 

5.2 TEEVisor Driver 

The driver runs in the Linux kernel at VMPL2 and is invoked by userspace programs to manage enclave life cycles. We preserve binary compatibility and minimize porting effort by retaining the device node /dev/sgx_enclave and its ioctls, and adding new ones for the Clone feature. To run on stock kernels, TEEVisor driver re-implements unexported kernel helpers. Driver implementation details are covered hereafter. 

5.2.1 ENCLU Emulation. ENCLU instruction raises #UD ex-ception, which the kernel dispatches through its exception chain. The driver registers a die notifier that hooks every 

#UD and, on matching an ENCLU , starts instruction emulation and marks the exception handled. Per Linux conventions the notifier stays short and lock-free, so TEEVisor defers the actual work by enqueueing an emulation task at the head of the current task’s work list to run in a safe context. The emulator stores the user context and timer state into the CAA page, switches to VMPL1, and on return reloads the user context and dispatches on the exit reason filled in by the SM: Interrupt (emulator handles the vector before returning to user space so signals are delivered correctly), EEXIT and 

Timer (returns to user space directly as in §5.1.3), Clone 

(ECLONE triggers a synchronous exit and the driver marks the enclave as in-clone), Cache (COW ran out of cache pages, driver calls ECADDCACHE ), and NO_FREE_SLOT (no free slot on the synchronisation page, driver drains and resumes). 

5.2.2 Shared Memory Synchronization. ESYNC lazily synchronises shared memory (§4.2.4): the driver tracks shared-memory mappings like enclave pages and unmaps them be-fore destruction. On a shared-memory page fault, the ENCLU 

emulator’s post-AEX page-fault path calls handle_mm_fault 

to populate the mapping and syncs it into the enclave via 

ESYNC . TEEVisor installs an mmu_notifier on the enclave’s address space; its invalidate_range_start hook removes affected shared mappings via ESYNC before the kernel mu-tates them, and they are re-mapped lazily on next access. 

5.2.3 Clone/Fork Support. During enclave cloning (as shown in Fig. 14), the TEEVisor driver multiplexes enclaves on a single fd using an address-space-keyed xarray so par-ent and child processes can resolve their instances after 

fork . The workflow is triggered within fork by the VMA’s 

vma_open callback; if CLONE_BIND metadata is present, it runs the creation sequence ( ECCREATE , ECLONEINFO , ECADD ,

ECINIT ). Failures trigger ECABORT , with the status retrieved via CLONE_RESULT since vma_open cannot propagate errors. COW-Clone copies only private metadata pages. Shared pages are marked read-only with incremented reference counts; subsequent page faults check EPCM permissions to enter the COW path. Shared pages use refcounted structures, cache blocks are freed when relevant pages are released, and a kernel thread synchronizes new COW pages to the guest OS. Section C details the xarray, ioctls, and state machines. 

5.2.4 Timer. ESETTIMER avails and runs a per-TCS timer (100 𝜇 s resolution) that pauses on OS yields, AEX , or EEXIT ,and raises a Timer exception upon expiry. 

6 Evaluation 

We evaluated TEEVisor on an AMD EPYC 7313 server (16 phys-ical cores, 2 threads per core, 128 GB DDR4 RAM), with the CVM configured at 16 vCPUs pinned to 3 GHz and 8 GB of RAM. Host and guest ran Ubuntu 22.04 with Linux 6.11.0 (SVSM branch, commit 3b04c21 ); the TEEVisor SM was built in Rust release mode. We used Intel SGX SDK v2.27, Gramine v1.9 and SCONE v6.0.4 for workload evaluation. We report micro-benchmarks (§6.1) and real-world applications under Gramine (§6.2) and SCONE (§6.3).

We evaluated TEEVisor with Gramine on representative applications: Nginx for high-concurrency HTTP serving and OpenSSL for TLS-heavy cryptography; Redis and Mem-cached for low-latency, memory-bound key-value stores; and MariaDB for I/O-heavy relational workloads. and Nginx . OpenSSL s_server /s_time workload collapses in both SYNC and EXITLESS due to Gramine’s futex-based file-system synchronisation and the absence of an fd cache, a LibOS-level limitation. 6.3 Application Benchmarks with SCONE 

We also evaluated TEEVisor under SCONE on Redis, Mem-cached, and MariaDB to quantify the additional latency in-troduced by TEEVisor and to compare how different LibOS frameworks shape the overall overhead. We ran the same Redis benchmark and memtier_benchmark with default pa-rameters, raising SCONE_SSPINS to 10,000 to lengthen the enclave-thread spin window and reduce context switches. As Fig. 11 shows, TEEVisor adds under 5% overhead on Redis, essentially matches the baseline on Memcached (HW mode is slightly faster, likely from reduced scheduling overhead), and adds about 12% on MariaDB. 

6.4 Discussion 

VMPL transitions are the dominant source of TEEVisor over-head. This is largely invisible for compute-intensive work-loads, where the boundary cost is a small fraction of total ex-ecution time, but becomes significant for I/O-intensive work-loads with frequent syscalls. A well implemented shared-syscall-buffer LibOS (as in SCONE, or EXITLESS in Gramine) can substantially mask this cost.

Frequent access to unmapped shared memory and permis-sion changes on already-synchronized shared pages intro-duce latency by triggering an extra page-table synchroniza-tion operation in TEEVisor. Applications designed for SGX, and for TEEVisor, should avoid these patterns. eSGX exception mechanism reduces minimal overhead to 3.4 μs compared to AEX enclave exit-and-resume cycle in SGX of at least 36.5 μs. The exception table further enables safer and more efficient exception identification. EMODP ac-celerates page permission changes entirely in-enclave, while ESETUSSA multiplexes enclave application threads over a single TCS through a simple pointer update. 

7 Related Work 

Minimizing the CVM TCB. Gramine-TDX [22] offloads network and filesystem operations to the host via paravirtual-ized interfaces but still carries a LibOS. Unikernel- and micro-VM-based confidential runtimes, IncognitOS [14], KylinX-style dynamic library OSes [42], and hardened minimal im-ages [12], shrink the guest at the cost of compatibility. Intra-CVM privilege separation via VMPLs is complementary: Veil [5], Cabin [27], and Wallet [10] carve CVMs into small trustlets that treat the guest OS as untrusted. TEEVisor sits in this family, guest OS is outside the enclave TCB, VMPL-based enclave isolation and page-table based horizontal priv-ilege separation, host-managed resources. 

VMPL-based SGX on CVMs. NestedSGX [39] emulates SGX leaf functions at the highest VMPL but requires modi-fying every SGX application’s untrusted code and exposes no extended semantics. vSGX [43] preserves binary compat-ibility by splitting the application across a normal VM and a CVM, incurring millisecond cross-VM transitions. Veil [5] defines its own SGX-style ABI at VMPL0 but cannot run unmodified SGX binaries and requires hypervisor changes. TEEVisor is the first VMPL-based monitor to execute unmod-ified SGX binaries, SDKs, and shielding runtimes (Gramine, SCONE) inside a CVM, and adds extended semantics (eSGX) absent from prior VMPL designs. 

Userspace SGX binary compatibility. Haven [9], Oc-clum [35], SCONE [7], Panoply [36], Gramine [37], and SGX-LKL [32] interpose on in-enclave syscalls via LibOSes or shims, improving compatibility at the cost of in-enclave TCB and often bespoke toolchains. TEEVisor preserves this path unchanged: unmodified binaries under SCONE and Gramine execute on TEEVisor without recompilation. 

Extended enclave primitives. MPK-based in-process isolation and privilege hierarchies for SGX are explored in En-claveDom [28], SGXLock [11], and LightEnclave [17]; Nested Enclave [31] proposes multi-layered privilege as a hardware extension; RISC-V proposals such as Timber-V [40] explore fine-grained isolation with shared memory. Software-only enclave cloning is explored in MigSGX [29] and in sealing-based work [16], neither has hardware memory sharing. TEEVisor differs by combining horizontal privilege levels, in-enclave exception and syscall handling, direct memory management, and architectural COW cloning, all in a CVM, without HV changes and keeping SGX-binary compatibility. 

> 11

8 Conclusion 

TEEVisor uses AMD SEV-SNP VMPLs to build hardware-protected, process-level enclaves inside a guest CVM, closing the gap between SGX-style isolation and CVM flexibility: the guest OS is outside the TCB, enclaves can be backed by ar-bitrary guest memory, and strict privilege and exception boundaries are preserved while keeping full userspace bi-nary compatibility with existing SGX stacks. Compute- and memory-bound workloads incur under 5% overhead (nbench averages 4.8%); I/O-heavy workloads depend on the libOS, Memcached under Gramine SYNC loses over 80% throughput, EXITLESS ∼40%, and under SCONE both Redis and Mem-cached stay within 5%. COW Clone enables fast, memory efficient and practical fork for LibOS multiprocessing.

A Complete SGX Instruction Catalogue 

This appendix lists the full set of SGX structures and instruc-tions adapted or introduced by TEEVisor, and the complete instruction-feature matrix summarised in §4.2. 

A.1 Modified and New Structures and Instructions 

The following SGX structures and instructions are adapted to support the Runtime feature: 

SECS. The existing base/size fields now define the user range; new runtime base and runtime size fields define the runtime range. A new attribute bit enables the Runtime feature. 

TCS. A new OUSSA field records the USSA offset from the enclave base, analogous to OSSA .

GPRSGX. A new SwitchFlag field restores the correct exe-cution mode on ERESUME after an AEX. 

EADD . Extended with sanity checks that force metadata pages into the runtime range. A new handler-page type is added via EADD ; it holds the predefined entry points for exception and syscall handlers, all of which must be non-empty. 

EENTER /ERESUME . Launch-time checks verify that the han-dler page is present and that the entire SSA range, including the USSA, is valid, since the runtime exception path can advance CSSA without exiting. New instructions introduced for the Runtime feature: 

syscall . In user mode, syscall switches to runtime mode and dispatches to the corresponding handler-page entry; no context is saved in the USSA. 

sysret . In runtime mode, sysret returns to user mode, jumping to RCX with sanitized flags in R11; no context is restored from the USSA. 

ERAISE and EraiseInfo . ERAISE raises an SGX-supported exception described in EraiseInfo to the guest OS via the AEX flow. EraiseInfo combines the existing ExitInfo (vec-tor, exit type, validity) and EXINFO (extended info, e.g., page-fault details). 

ESETTIMER . Sets the TCS timer count in 100 𝜇 s units with the highest bit requesting a periodic mode. It is cleared by setting the counter to 0. 

ESETUSSA . Resets the USSA to the address in RBX, updating 

OUSSA in the current TCS after sanity checks. 

ESWITCH and SwitchFlag . ESWITCH consumes a SwitchFlag 

in RBX to load context from the specified SSA/USSA, switch mode, and decrement CSSA as needed. SwitchFlag contains a USER bit (mode), an SSE_IGNORE bit (whether to load SSE state), and a 4-bit target SSA index. USER may only be set with target index 0 (the USSA). ESWITCH additionally checks that the USER and SSE_IGNORE bits in the target GPRSGX match the input flag. 

EMODP . Unifies EMODPR and EMODPE under a single ABI for complete in-enclave permission control over regular pages. Additional adaptations and instructions support the Clone feature: 

SECS. A new attribute bit enables the Clone feature. 

EREMOVE /EMODT . Because pages can now be shared across enclaves, the caller must pass the target enclave’s SECS to disambiguate ownership. 

ESMPROV . The provisioning interface used by PIE to transfer the KBS-provided provisioning blob into the SM. 

ENCLS in clone state. All ENCLS except ESYNC are disabled while an enclave is mid-clone. 

ECLONE and ECloneMetadata . ECLONE initiates cloning by exiting to a target address and populating ECloneMetadata 

at a shared address. The metadata carries the clone hash, total page count, and metadata-page count, enough to uniquely identify the clone and coordinate with the driver. 

ECCREATE and ECCreateInfo . ECCREATE creates the child enclave by copying the parent SECS and binds parent and child via ECCreateInfo . The child is created only when ev-ery non-SECS field in ECCreateInfo matches the parent’s metadata. 

ECLONEINFO and request page. ECLONEINFO queries un-mapped virtual addresses for a specific metadata-page type (TCS or SSA). ECLONEINFORequest begins the request page, followed by per-mapping entries; the security monitor fills in the virtual addresses and the valid-entry count. 

ECADD and request page. ECADD installs the queried meta-data mappings. ECLONEINFORequest is transformed into the request page by filling in physical addresses and bumping the next-entry index. 

ECINIT . Verifies that all metadata pages have been added, initializes the child enclave, and unfreezes the parent. The input is ECCreateInfo , used to validate binding and memory requirements.

ECABORT . Aborts cloning on a parent enclave identified by its SECS, reverting security-monitor state and unfreezing the parent. 

ECADDCACHE . Adds a cache block (base, size) to the target enclave; pages are validated and will be allocated during COW. Each enclave has at most one cache block, removed by the monitor once consumed. 

ECCLEARCACHE . Removes all unallocated pages from the cur-rent cache block.

B Page Ownership and ABA Avoidance 

Each EPCM entry records the owner of a physical page (§H.1). Under Clone, an entry can be shared across enclaves, so the security monitor must ensure that ENCLS /ENCLU requests target pages that actually belong to the intended enclave. Re-quests originate either from the guest OS via ENCLS (outside the enclave) or from enclave code via ENCLU (inside). 

ENCLU operations need no ownership check: the running enclave’s identity is known and the security monitor main-tains its page table, so any mapping inside the enclave’s virtual range belongs to that enclave. 

ENCLS operations that cross VMPL boundaries do need validation. Since the EPCM entry alone does not uniquely identify the owner under sharing, the caller must pass the target enclave’s SECS, and the monitor verifies that the page belongs to that enclave or one of its descendants. Because page ownership now changes only on page add or COW with refcount 1, SGX’s original assumption, that all enclave pages are removed before the SECS, no longer holds. As a result, the SECS page can no longer safely serve as the enclave identity for cross-enclave ownership tracking. Figure 12 illustrates the failure: an enclave creates a child, the child never writes the shared pages (so COW never runs), and the parent is destroyed. The EPCM still lists the parent as owner. If a new enclave reuses the same physical page for its SECS, the EPCM misleadingly associates the shared pages with a different enclave, an ABA-style ownership confusion that breaks the SGX identity model under sharing. To resolve this, TEEVisor explicitly tracks cross-enclave relationships. As Fig. 13 shows, the security monitor main-tains an enclave-node list and allocates a free slot per enclave. Each slot stores the parent’s index and a counter of active enclaves in its subtree (itself plus all descendants). On child creation, the monitor increments the counter for the parent and all ancestors; on destruction, it decrements them. The monitor can therefore always tell whether an enclave has active descendants, which suffices for safe own-ership validation on EPCM modification and eliminates the ABA confusion above.

D.2 Local Attestation 

Local attestation uses the report key, derived by EGETKEY 

from ephemeral root keys and additional user input; ver-ification recomputes the MAC over the signed portion of the report and compares it to the MAC field in the report. Because local attestation only verifies locality rather than identity, TEEVisor uses ephemeral root keys generated ran-domly at bootstrap, every enclave running under the same TEEVisor instance can derive the matching report key. 

D.3 Remote Attestation 

Because a verifiable hardware-embedded key is not directly accessible inside a CVM, TEEVisor bootstraps a monitor-held signing key from the SEV-SNP attestation mechanism in Section D. At bootstrap, the monitor generates an attestation key pair (SMpub/SMpriv); after attestation and registration of SMpub a Key Broker Service (KBS). Then, the SMpriv signed report can be verified and accepted by the target KBS.

H.1 EPCM and Memory State 

TEEVisor extends each EPCM entry with four fields to sup-port memory conversion and sharing: a shared bit (since any normal page can back an enclave, a simple valid bit no longer suffices), a Pvalidate bit (tracking SEV-SNP acceptance state so the monitor refuses access to unvalidated pages), an 8-bit 

reference counter (for cross-enclave sharing and COW ac-counting), and a unique ownership identifier that replaces the raw SECS reference to avoid ABA confusion after a COW clone. TEEVisor allocates one EPCM entry per normal-memory page at initialisation, a memory trade-off for flexibility, and grants VMPL1 access to secure memory and VMPL2 to nor-mal memory before yielding to the guest OS. The SVSM page-state-change path is piggybacked to keep EPCM accep-tance state in sync with the RMP. During enclave construc-tion , the monitor revokes VMPL2 access and grants VMPL1 access, maps each page into the enclave’s page table with permissions matching its EPCM entry, builds a second run-time page table when Runtime is enabled, and requires an 

ECSYNC -registered synchronisation page under Clone. At ex-ecution , shared-memory mappings are installed lazily via 

ESYNC during page faults; mode transitions under Runtime switch the active page table; Clone increments shared-page counters on successful child creation and services COW faults from pre-registered cache blocks, with a sole-owner optimisation analogous to Linux COW. At destruction , the monitor unmaps and decrements counters; when a page has no remaining users, its contents are cleared, its EPCM reset, VMPL2 access restored, and VMPL1 access revoked.
