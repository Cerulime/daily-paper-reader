## 摘要
机密虚拟机（CVM），如 AMD SEV-SNP，以及进程飞地，如 Intel SGX，可针对云威胁提供工作负载保护。然而，它们在 TCB、部署成本与速度、对等工作负载保护、资源共享、细粒度隔离与证明以及编程能力方面存在显著差异。将进程飞地嵌套在 CVM 中提供了一种最优解决方案，并为解决 SGX 长期存在的局限提供了机会：缺乏飞地内保护、昂贵的切换与异常路径、缓慢的飞地克隆，以及限制库操作系统（LibOS）的受限编程模型。本文介绍 TEEVisor，一种驻留于 CVM 的架构，由安全监控器和内核驱动组成，利用 AMD SEV-SNP 虚拟机特权级（VMPL）在客户机 CVM 内构建受硬件保护的进程级飞地，具备两种模式：（1）SGX 二进制兼容模式，用于运行未经修改的 SGX 应用程序；（2）一种新颖的扩展 SGX（eSGX）模式，优化慢速执行路径并提供更丰富的飞地编程能力。在商用 AMD EPYC 硬件上，相对于原生 CVM 执行，TEEVisor 在计算密集型和内存密集型工作负载上产生低于 5% 的开销，在 I/O 密集型应用上约为 12%，并将飞地克隆加速至每 MB 飞地大小 93 μs 的速率，表明 CVM 内的 eSGX 语义在生产使用中是切实可行的。

## Abstract
Confidential Virtual Machines (CVMs), such as AMD SEV-SNP, and process enclaves, such as Intel SGX, provide workload protection against cloud threats. However, they strongly differ in TCB, deployment cost and speed, peer workload protection, resource sharing, fine-grained isolation and attestation, and programming capabilities. Nesting process enclaves within CVMs offers an optimal solution and an opportunity to address long-standing SGX limitations: lack of intra-enclave protection, expensive transitions and exception paths, slow enclave cloning, and a restricted programming model that limits Library Operating Systems (LibOS).   This paper introduces TEEVisor, a CVM-resident architecture consisting of a security monitor and a kernel driver that leverages AMD SEV-SNP Virtual Machine Privilege Levels (VMPLs) to build hardware-protected, process-level enclaves inside a guest CVM with two modes: (1) an SGX binary compatibility mode to run unmodified SGX applications; and (2) a novel extended SGX~(eSGX) mode optimizing slow execution paths and offering richer enclave programming capabilities. On commercial AMD EPYC hardware, against native CVM execution, TEEVisor incurs under 5% overhead on compute- and memory-bound workloads, around 12% on I/O-heavy applications, and accelerates enclave cloning to a rate of 93~$μ$s/MB of enclave size, demonstrating that eSGX semantics inside a CVM are practical for production use.

## 1. 核心问题与整体含义（研究动机与背景）

- **两类 TEE 抽象的互补与冲突**：
  - 进程级飞地（Intel SGX）：TCB 小、可审计，但内存布局僵化、ECALL/OCALL 切换昂贵、异常路径（AEX）代价高、编程模型受限。
  - 机密虚拟机（AMD SEV-SNP、Intel TDX）：二进制兼容、OS 服务丰富，但攻击面大（guest OS 在 TCB 内）。
- **运维层面的现实痛点**：单负载独占 CVM 成本高、供给慢、难以扩展且削弱按负载的证明能力；容器级 CVM 对受损 guest OS 保护不足；unikernel/micro-VM 虽缩小 TCB，却牺牲兼容性且未恢复飞地式的可审计小 TCB。
- **SGX 长期架构瓶颈**：
  - 异常/中断触发 AEX，强制昂贵的状态保存与宿主交互，拖慢异常密集应用（如 JVM）；
  - 缺乏飞地内特权分层，LibOS 秘密无法与有缺陷/被攻破的应用隔离（多方可信场景尤甚）；
  - `fork`/`clone` 依赖 sealing + 状态拷贝，克隆代价高；
  - 宿主中介的抢占与信号机制效率低。
- **研究空白**：已有的 NestedSGX、vSGX、Veil、Gramine-TDX 分别存在需改应用/运行时、跨 VM 切换开销大、需改 hypervisor 或缺乏完整二进制兼容等问题。
- **整体含义**：论文主张将进程飞地"嵌套"进 CVM 是最优折中，并首次在同一 CVM 内同时实现**未修改 SGX 二进制兼容**与**扩展 SGX（eSGX）语义**，无需改硬件、hypervisor 或宿主内核。

## 2. 方法论

### 2.1 核心思想

- 单个驻留 CVM 的安全监视器（SM）暴露完整、未修改的 SGX ISA，并叠加新扩展。
- 三大支柱：**VMPL 隔离** + **飞地内水平特权分离** + **飞地 TCB 之外的内核驱动**（资源管理仍归 guest OS）。

### 2.2 架构与 VMPL 划分

- **VMPL0**：SM 内核态，处理 ENCLS 请求，管理飞地与 VMPL 权限授予/撤销。
- **VMPL1**：SM 内核态处理 ENCLU，用户态运行飞地代码；飞地内 ENCLU（如 EACCEPT）由异常处理器模拟。
- **VMPL2**：guest Linux 内核中的 TEEVisor 驱动，捕获用户态 ENCLU，并暴露与现有 SGX 驱动兼容的 ENCLS 接口。
- 基于 Coconut SVSM 与 AMD SEV-SNP，复用 OVMF、QEMU、Linux 等 VMPL 适配组件。

### 2.3 飞地生命周期

- **创建**：驱动经 ioctl 模拟 ENCLS（ECREATE 建立 SECS、EADD 加页、EEXTEND 度量、EINIT 校验 SIGSTRUCT 并激活）。
- **进入**：用户态 EENTER 触发 #UD → die-notifier 挂钩解析指令 → 入队仿真任务 → 通过 SVSM 协议切到 VMPL1 → 加载飞地上下文。
- **退出**：EEXIT/ECLONE 同步退出或异常/ERAISE 触发 AEX，均由 VMPL1 SM 异常处理器处理，再返回 VMPL2；驱动解码异常向量，能内部解决的就不交给原生 Linux 处理器。
- **销毁**：ECCLEARCACHE、ESYNC、EREMOVE 回收缓存块与共享页。

### 2.4 eSGX 五大特性（F1–F5）

- **F1 水平特权层**：地址空间分为 Enclave Runtime（ER，可信）与 Enclave Userspace（EU，不可信）；ER 可读写 EU，反之不可；EU 中 ENCLU 非法（#UD），`syscall` 合法并触发模式切换。元数据页（SSA、TCS、handler page）与入口点必须位于 runtime 区。
- **F2 飞地内内存管理**：EMODP 统一 EMODPR/EMODPE，飞地内直接改页权限，无需退出到宿主。
- **F3 灵活异常处理**：飞地内异常先交给 Runtime 处理器；未配置则走正常 AEX；可经 ERAISE 重新抛给宿主。
- **F4 受控运行/用户态切换**：新增 syscall/sysret 快速模式切换、ESETUSSA 重定向 USSA、ESETTIMER 软定时器、ESWITCH 按 SwitchFlag 恢复模式与上下文。
- **F5 飞地克隆**：页粒度 COW 克隆运行中的飞地；ECLONE 冻结父飞地并输出 ECloneMetadata，驱动在 `fork` 中执行 ECCREATE/ECLONEINFO/ECADD/ECINIT 序列；普通页写时复制，由飞地内 block cache（ECADDCACHE）服务。

### 2.5 内存管理与 ABA 规避

- 将内存分为 guest 管理的普通内存与 SM 管理的安全内存，VMPL 权限隔离，支持按需把普通页动态转换为飞地页（区别于 SGX 固定 EPC）。
- EPCM 条目扩展四个字段：shared 位、pvalidate 位（与 SEV-SNP 接受状态同步）、8 位引用计数、唯一所有权标识。
- **ABA 问题**：Clone 下 EPCM 条目可跨飞地共享，"SECS 页作为身份标识"不再成立（父飞地被销毁后 SECS 页被复用会造成所有权混淆）。解决方案是维护**飞地节点列表**，每槽记录父索引与子树活跃计数，创建时对祖先加一、销毁时减一，从而安全校验所有权。
- 页表优化：EU 区在两套页表中属性相同，共享页表项并用保留位标记以便回收。

### 2.6 证明链

- **平台证明**：SM 启动时生成临时密钥对 SMpub/SMpriv；PAIS/PIE 经 KBS 获取 nonce，请求 VMPL0 报告（REPORT_DATA = hash(SMpub, nonce, MRENCLAVE)），注册 SMpub 后由 KBS 下发加密秘密，SM 用 ESMPROV 装载，防回滚。
- **本地/远程证明**：保持 SGX report 结构，由 QE 与 SMpriv 签名，锚定到 SEV-SNP 硬件与注册密钥；当前**不支持迁移**。

### 2.7 实现规模

- TEEVisor Driver：约 3000 LOC（Linux 内核模块，保留 `/dev/sgx_enclave` 与既有 ioctl）。
- TEEVisor Security Monitor：约 11,500 LOC（Rust + 少量汇编）。

## 6. 主要结论与发现

- **开销**：相对原生 CVM，计算/内存密集负载平均开销 < 5%（nbench 4.8%）；LMbench bw_mem、WolfSSL、SGXGauge hash-join 几乎无可测开销；SCONE 下 Redis 开销 < 5%，Memcached 基本持平，MariaDB 约 12%。
- **I/O 与应用差异**：Gramine 下 Nginx EXITLESS 提升 25%（fd 缓存 + sendfile 避免上下文切换），SYNC 相对仿真模式损失 50%；Redis EXITLESS 损失约 10%，Memcached 约 40%，MariaDB 最高损失 50%；SCONE 下 Redis/Memcached 均控制在 5% 内。
- **切换成本**：EENTER/ERESUME 9.7 μs，其中 VMPL 切换占 4.5–5.5 μs，是跨边界开销的主导项。
- **eSGX 快路径**：Runtime 指令仅 1.1–4.4 μs（syscall 2.3 μs、sysret 1.1 μs、异常 2.5 μs、EMODP 4.4 μs）；异常机制最小开销 3.4 μs，而 SGX 的 AEX 退出-恢复循环至少 36.5 μs。
- **克隆**：线性扩展，93 μs/MB（比飞地创建快约 20×）；clone+COW 比新建飞地快约 1.4–1.7×，另有内存节省。
- **总体判断**：VMPL 转换是主要开销源，对计算密集负载可忽略，对频繁系统调用的 I/O 负载显著；由 SCONE 或 Gramine EXITLESS 这类共享系统调用缓冲的 LibOS 可有效掩盖该成本。

---

## 7. 优点

- **兼容性与扩展性兼得**：首次在 VMPL 方案中实现**未修改 SGX 二进制/SDK/LibOS（Gramine、SCONE）**的直接运行，同时提供 eSGX 新语义，不要求 hypervisor、硬件或宿主内核改动。
- **TCB 设计清晰**：guest OS 与驱动明确置于飞地 TCB 之外，SM 借助 VMPL 硬件权限而非软件检查强制隔离；驱动仅做资源管理。
- **水平特权分离有实用价值**：ER/EU 划分解决了 SGX 长期缺失的"飞地内隔离"，使 LibOS 秘密能抵御有缺陷或被攻破的应用，适配多方可信场景。
- **架构级 COW 克隆**：把 `fork` 的代价从"随飞地内容增长"变为"随飞地大小线性增长"，对 LibOS 多进程模型是实质性改善。
- **工程细节扎实**：识别并解决了 Clone 引入的 SECS 所有权 ABA 混淆（飞地节点列表 + 子树活跃计数）、跨 VMPL 地址（物理 vs 虚拟）语义、CAA 页权限维护、共享内存惰性同步与 mmu_notifier 失效处理等难题。
- **页表优化**：EU 区在两套页表间共享页表项，减少内存与维护开销。
- **评估层次完整**：指令级 → 微基准 → 双 LibOS 真实应用 → 克隆/COW 规模扫描，并配有细粒度正确性测试。

---

## 8. 不足与局限

- **性能限制**：
  - VMPL 切换（4.5–5.5 μs）是根本瓶颈，I/O 与系统调用密集负载受影响明显（MariaDB 约 12%，Gramine SYNC 下 Memcached 损失超 80%）。
  - 未实现内存交换，因此 SGX 的 EWB/ELDB/ELDU/ETRACK 等换页类指令不受支持，限制了超大飞地场景。
  - 定时器用 100 Hz 周期中断近似，非一次性精确定时（因 x2APIC MSR 访问约 10,000 cycles 过贵），抢占精度有限。
- **功能缺失**：**不支持飞地迁移**；AEXNOTIFY/EDECCSSA 在 Runtime 模式下被判定为不必要；部分旧指令在 Runtime 特性下被禁用以强化安全性。
- **对比公平性存疑**：与 NestedSGX 的指令延迟对比取自其论文数据，非同一硬件复现；NestedSGX 修改用户态代码以减少驱动仿真开销，口径不一致。表 1 的五维对比为定性描述，缺少定量支撑。
- **依赖与可移植性**：实现绑定 AMD SEV-SNP + Coconut SVSM；Intel TDX 分区特性仅作为背景提及，未做验证；需依赖 VMPL-enlightened 的 OVMF/QEMU/内核分支（Linux 6.11 SVSM 分支特定 commit），离"开箱即用"尚有距离。
- **评估覆盖**：
  - 仅单机、单配置（16 vCPU / 8 GB），未做多核扩展性、内存压力或 NUMA 场景测试。
  - 应用集合偏服务端常见负载（Redis/Memcached/MariaDB/Nginx），未涉及异常密集的 JVM 类应用——而这正是论文批判 SGX 时的核心动机之一，eSGX 异常快路径
