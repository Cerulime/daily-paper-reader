# Security Is More Than a Library Call: How Security Features Live in Code 

KEVIN HERMANN, Ruhr University Bochum, Germany 

SVEN PELDSZUS, Chalmers | University of Gothenburg, Sweden 

THORSTEN BERGER, Ruhr University Bochum and Chalmers | University of Gothenburg, Germany and Sweden Implementing security features—functionalities that protect sensitive data or prevent malicious actions by attackers—is important for ensuring the security and integrity of software systems. Correctly implementing access control, cryptography, or other security features is challenging as they require substantial domain expertise, careful design, and custom implementation to integrate them within the software system. Previous work has thoroughly studied security awareness, perception, practices, and expertise via surveys, interviews, and experiments. While they have shown that the implementation of security features are often supported by security libraries and frameworks, they have also shown that developers rarely are security experts, and make mistakes that introduce vulnerabilities into software when using them. Despite this extensive knowledge of security practices and developer behavior, we still lack a comprehensive understanding of how security features actually manifest at the code level across full software systems. We close this gap by conducting a mining study of security features in 9 popular and large open-source Java systems such as Hadoop, Signal Server, and Tomcat. We manually inspected 2,127,761 lines of code across 19,121 files, identifying and annotating 183,395 lines implementing 561 security features corresponding to 54 security features in our taxonomy. We analyzed the characteristics of the identified security features, such as their size, scattering, tangling, common implementation patterns, and the use of internal and external functionalities. Our findings show that security features are far more than mere calls to external libraries. Security features, such as access control, can grow large in size, scatter across the whole codebase, and frequently tangle with each other. External security libraries are commonly used, but they require substantial amounts of code for integration. Once integrated, developers reuse their own functionality extensively throughout the codebase. We publish our annotated dataset for future research on security features in software systems. 

1 Introduction 

Modern software systems implement a wide range of security-specific functionality, commonly re-ferred to as security features [1]. Applications authenticate users and services, enforce authorization decisions, protect data at rest and in transit, manage credentials and cryptographic keys, validate system state, and record security-relevant events. Yet, implementing such functionality correctly remains difficult. Empirical studies have repeatedly shown that developers struggle to implement security-sensitive functionality correctly, including cryptographic API usage and password storage [2–4]. Even when developers actively seek implementation guidance, the resources they consult can substantially affect the security of the resulting code [5]. At scale, incorrect integration of otherwise well-established security mechanisms can lead to exploitable vulnerabilities, as demonstrated, for example, for TLS in Android applications [6]. One response to these difficulties is to encapsulate security functionality in libraries and frame-works. Such abstractions provide reusable implementations of cryptographic primitives, authen-tication mechanisms, access-control infrastructure, secure communication, and other security functionality, reducing the need for application developers to implement sensitive mechanisms from scratch. However, using a security library does not eliminate the application-specific code required to integrate a security mechanism. Studies of security APIs show that developers often

Security libraries and frameworks therefore provide useful entry points for locating security functionality, but they do not necessarily capture all code involved in realizing a security feature [1]. Prior empirical work has also examined the usability and misuse of security APIs [2, 3, 7], showing that developers frequently struggle with security-sensitive APIs and their correct integration. At the same time, feature-location [8, 9] research has shown that scattering and tangling complicate program comprehension and maintenance. For security features, however, it remains unclear how much code they comprise, how widely they are scattered, how strongly they are tangled with other security features, and what part of them comprises custom code instead of library uses. Despite extensive research on vulnerabilities, security APIs, secure development practices, and security-relevant code [10–16], we lack a systematic understanding of how functional security features are realized across complete software systems. In particular, it remains unclear how much code they comprise, how widely they are distributed throughout a codebase, which parts are implemented within a project rather than provided by external functionality, and how different security features interact. Understanding these characteristics is important for techniques that aim to locate, analyze, maintain, or reason about security functionality. To address these open questions, we investigate four research questions: 

RQ1: What is the code-level footprint of security features? 

RQ2: What are implementation and usage patterns of security features? 

RQ3 : What parts of security features are implemented within a software project? 

RQ4: How do security features interact? We conduct an empirical study of functional security features in nine mature Java systems from seven categories drawn from GitHub, comprising 2,127,761 lines of code across 19,121 files. We manually identify and annotate security-feature code at both line and block granularity and map the identified functionality to a taxonomy of functional security features derived by Hermann et al. [1]. The resulting dataset contains 561 security features across the 183,395 annotated lines of code in 19,712 locations and records their source-code footprint, including size, distribution, interactions with other security features, and use of internal and external functionality. We contribute: 

• a curated dataset of 561 functional security features from 9 mature Java software systems; 

• a characterization of the size, scattering, and tangling of security features; and 

• an analysis of custom implemented and externally provided security functionality. Our analysis shows that security features are more than just small wrappers around external security libraries. Across the studied systems, most security-relevant functionality is implemented internally, although custom implementations frequently use external functionality. The balance differs considerably among security feature categories. Standardized functionality, such as crypto-graphic primitives, is more likely to be externalized. In contrast, application-specific functionality, such as session management and access-control logic, requires substantially more project-specific integration and implementation. Security features also differ considerably in their footprint and distribution throughout the codebase. Access-control functionality, in particular, spans large por-tions of some systems. Analyses that identify security functionality solely through recognizable security-library calls therefore miss parts of its implementation. 

2 Background 

We give an overview of security features, their characteristics, and our annotation approach. 

Functional Security Features. Security features are functionalities of a software system that enforce security properties, such as protecting the integrity of a system against malicious actions or preserving the confidentiality of sensitive data [1, 17–21]. Examples include authentication, Security Is More Than a Library Call: How Security Features Live in Code 3authorization, encryption, secure storage, and security monitoring. Such functionality must be selected, implemented, and maintained as part of the broader software system [19–21]. This can be challenging because developers are often not security experts and must correctly integrate security mechanisms provided by libraries and frameworks into application-specific code [2–5]. To systematically characterize security functionality, we build on the taxonomy of Hermann et al. [1]. The taxonomy comprises 68 implementation-level functional security features organized into five top-level categories and provides guidance for locating their realizations in code: 

Access Control. Authentication and authorization functionality for identifying users or services and controlling access to system resources. 

Cryptography. Functionality for protecting data using encryption, hashing, key management, and related cryptographic mechanisms. 

Security Monitoring. Functionality for recording and observing security-relevant events, includ-ing logging, auditing, and intrusion detection. 

Secure Data Handling. Functionality for securely storing and processing sensitive or untrusted data, including input validation and protection against injection attacks. 

System State Protection. Functionality for preserving the integrity and availability of system state, including session management, synchronization, and resource management. Hermann et al. [1] show that these features can be exposed through framework APIs, annotations, and configuration mechanisms. We use their taxonomy as the conceptual basis for identifying and categorizing security-feature implementations in complete software systems. 

Feature Annotations. To record feature locations in source code, we use the embedded fea-ture annotation notation [22]. The notation marks either contiguous blocks of code or individual lines with a feature name, which is defined in a feature model. A code block is delimited by 

//&begin[FeatureName] and //&end[FeatureName] , while individual lines are annotated using 

//&line[FeatureName] . The notation represents feature locations directly in the source code and allows annotations of multiple features to overlap. For example, the code excerpt at the bottom of Fig. 1 shows the use of these annotations to annotate lines 236–280 as belonging to the security feature Password , and the line 232 as also belonging to the security feature Salting .

Feature Scattering and Tangling. Software features are not necessarily localized in a single module or component. A feature is scattered when its implementation is distributed across multiple program elements, while code is tangled when the same program element contributes to multiple features or concerns [9, 23]. Scattering is commonly measured using concern-diffusion metrics, such as Concern Diffusion over Components (CDC) and Concern Diffusion over Operations (CDO), which count the number of components or operations contributing to a concern [23, 24]. In our study, we analogously measure scattering by the number and relative share of files and methods containing a security feature. We measure tangling through overlapping feature annotations, quantifying how much code associated with one security feature is also associated with another. Scattering and tangling can complicate program comprehension and maintenance, as developers need to identify and reason about multiple code locations to understand or modify a feature. For security features, these properties are particularly relevant because security functionality can be distributed throughout the system and overlap with other security functionality. We therefore characterize how widely security features are distributed across the codebase and their overlap.

3.1 Repository Filtering 

Our study requires repositories that represent complete, mature software systems in which security functionality is embedded in a broader application context. We are interested in how security features are implemented as part of a system, how widely their code is distributed, how they interact with each other, and to what extent they rely on custom implementation. We are interested in complete general-purpose software systems that integrate security features as part of their overall functionality, rather than libraries that provide them. To identify suitable subject systems for our analysis, we therefore apply the following selection criteria: (1) System Type: The system is a complete software system. Complete systems provide the application context in which security features interact with other system functionality. (2) Security Focus: Security is not the primary purpose of the system. This avoids selecting sys-tems in which security functionality is inherently dominant and, therefore, not representative of how security features occur in general-purpose software systems. (3) Maintenance Status: The repository is actively maintained. This limits the study to systems that are still developed and avoids analyzing obsolete or abandoned implementations. (4) Repository Independence: The repository is not a fork of another project. This avoids treating substantially duplicated codebases as independent subject systems. (5) Documentation Language: The repository’s README is written in English. We rely on project documentation during repository selection to determine its purpose. (6) Implementation Language: Java is the dominant programming language of the repository. Restricting to one language improves comparability between systems and avoids language-specific implementation differences in our analysis. Java also provides a sufficiently large set of mature server-side and infrastructure systems from different application domains. (7) Codebase Size: The repository contains a sufficiently large Java codebase to study the distri-bution and implementation structure of security features. Small Java components embedded in otherwise non-Java systems are therefore excluded. Security Is More Than a Library Call: How Security Features Live in Code 5(8) Repository Popularity: The repository has substantial community adoption. We use popu-larity as an initial proxy for selecting established projects to avoid rarely used repositories. We operationalized these criteria in three filtering steps. First, we queried the GitHub Search API for repositories containing Java code (6) that have at least 5,000 stars (8). We excluded repositories labeled as “Android,” as these follow a platform-specific security architecture [26] that differs substantially from general-purpose systems. This resulted in 467 repositories. Second, we queried the GitHub Languages API and retained those containing at least 1 MB of Java code (7) for which Java accounts for at least 80% of the repository’s source code (6). This reduced the set to 198 repositories. Finally, the first author manually inspected each remaining repository and applied the application-oriented (1), security-focus (2), maintenance (3), fork (4), and documentation language (5) criteria. After this step, 41 repositories remained as candidates for analysis. 

3.2 Repository Selection 

Our analysis requires detailed examination of security features within each subject system. We therefore selected a subset of repositories to enable in-depth analysis while preserving the diversity of system types in the candidate pool. To characterize this diversity, we examined the purpose and functionality of each repository. We iteratively grouped repositories according to these charac-teristics. After four rounds of discussion, we identified 7 system categories. Repositories could be assigned to multiple categories when their functionality spanned more than one system type: 

• Application Servers (1 system) 

• Big Data (12 systems) 

• Cloud (7 systems)

• Enterprise Services (6 systems) 

• IoT Management Systems (2 systems) 

• Streaming and Event Systems (11 systems) We selected 9 repositories for detailed analysis, covering at least one repository of each system type. For system types with more than 10 systems, we included two repositories to better represent the diversity of our candidate pool. We further selected systems of different sizes to capture variation between smaller and larger codebases. Table 1 shows the final set of selected repositories. 

3.3 Security Feature Identification and Annotation 

We systematically identified and annotated security features in the selected repositories. 

3.3.1 Scope. Since we are interested in security features written and used by developers, we analyzed all Java production files of the repositories. Therefore, we excluded tests, benchmarks, other embedded applications, dependencies, examples, documentation, resources, and websites contained in the repository, as they do not provide logic for the application’s operation. However, we used these artifacts to gain a better understanding of the system and its security features. We recorded security features by annotating singular lines or blocks of code if they contributed to the implementation or usage of a security feature. This could include, e.g., a method, a class, or a set of lines of code within a method that related to a security feature. The annotation process used a standardized notation [22] and HAnS as a corresponding annotation editor [27]. 

3.3.2 Annotation Process. The first author, a PhD student with four years of experience in software security, manually investigated the codebase of the repositories and annotated all lines of code that implement or use a security feature. We used the taxonomy of Hermann et al. [1] for our analysis, since they provide a structured collection of security features and guidance on how they can be located. We mapped all identified security features to this taxonomy. To better understand how security features are realized in practice, we recorded identified features at a finer level of 6 Hermann et al. granularity than provided by the taxonomy. For example, we recorded authentication tokens or external service credentials, which are mapped to the security feature credentials in the taxonomy. The first author was highly inclusive in the annotation of all repositories to improve recall, i.e., annotating all potential security feature code, even when not certain about its classification. The first and second authors subsequently reviewed the dataset by examining the annotated code, and discussed the taxonomy mapping. They resolved any disagreements through discussion until a consensus was reached. We chose the timing and frequency of reviews based on the repository size and the number of its modules. However, in the early stages of the annotation process, we held more frequent discussions to ensure a shared understanding. This process was repeated until all repositories were fully annotated to ensure the validity and the reliability of our dataset. The whole process took approximately 6 months to complete. As a final validation step, we used our findings of our study to identify potential gaps or inconsistencies in our annotations and the mapping to the taxonomy. For example, we used internal and external APIs we categorized as contributing to security features (RQ3) to cross-check whether the annotations in the code were consistent and complete. The precision of our annotations around API usage was already high (92.8%), with only a few minor inconsistencies that we corrected. 

3.3.3 Taxonomy Refinement. In total, we identified 561 security features across all analyzed reposi-tories. While we already sorted them according to the existing taxonomy, the first and second author refined the initial categorization in two separate meetings to ensure that our taxonomy accurately reflects the security features as we observed them in the projects. While we were able to categorize all security features according to the original taxonomy, some security features required discussions on their proper placement within the taxonomy, as they could fit into multiple categories. We carefully reviewed and discussed these cases until a consensus was reached. This resulted in 12 features being moved to different categories, and 14 features moved within the same category. 

3.4 Data Analysis 

We analyzed the annotated security features at the level of the predefined taxonomy with respect to the four research questions. For RQ1, we characterized the implementation structure of security features by measuring their size, and scattering across the codebase. For RQ2, we classified how se-curity features are implemented, distinguishing custom implementation from functionality obtained through reusable security libraries. For RQ3, we analyzed whether security-related functionality is provided internally by the project or through external APIs. For RQ4, we examined how security features interact with each other by analyzing their shared lines of code.

8 Related Work 

Prior research on software security has predominantly focused on identifying vulnerabilities rather than characterizing the implementation of security functionality in software systems. For example, Henriques et al. [37] mine vulnerability databases and source-code repositories to continuously update vulnerability datasets, while Shihab and Alanezi [38] survey datasets and techniques used for software vulnerability analysis. Çetin et al. [39] investigate the use of large language models for detecting vulnerabilities in source code. These works concern the presence and detection of security defects. In contrast, we study the code that realizes functional security features , code that mitigates security risks, rather than posing them. More closely related to our objective, prior work has investigated the identification and interpre-tation of security-relevant code. Ryoo et al. [40] study the use of architectural security tactics in open source software projects. Mirakhorli et al. [41] use machine learning to identify security tactics. Similarly, SWAN [14] uses machine learning to detect security-relevant methods for sanitization Security Is More Than a Library Call: How Security Features Live in Code 17 and authentication, while Dev-Assist [15] builds on it to automatically generate specifications for static analysis. Krishnamurthy et al. [16] use large language models to explain security-critical code with the goal of helping developers avoid introducing vulnerabilities. These approaches aim to locate or reason about selected security-relevant architecture decisions in code, whereas we characterize how functional security features are realized across complete software systems. Overall, existing work provides substantial evidence on vulnerabilities and security code analysis, but offers little empirical evidence on how security features are realized. Our work addresses this question by studying security features in nine Java systems and characterizing their size, scattering, tangling, implementation patterns, and reliance on internal and external functionality. 

9 Discussion 

Our findings show that security features extend beyond individual security API calls. Their im-plementation crosses library, location, and feature boundaries, with substantial variation across projects. These characteristics have implications for security feature location, security analysis, and security-aware development tools. 

Security Is More Than a Library Call. Security libraries are important building blocks of security features, but are only a part of them. While their APIs can provide useful entry points for locating security features [1], our results show that these entry points often lead to project-specific abstractions that are used throughout the codebase. Security feature location techniques should treat APIs as seeds and follow them into custom implementations and their usages. Locating such functionality is generally challenging [21], and general-purpose feature-location techniques struggle with scalability and false positives [8, 42]. An alternative to repeatedly recover-ing feature locations is to maintain feature-to-code knowledge during evolution [43]. Our findings suggest that such knowledge should capture external functionality, project-specific implementa-tions, and their usage sites. For practitioners, existing project-specific security abstractions can provide starting points for understanding and modifying security features. Our dataset captures these relationships, providing a basis for security-specific feature-location techniques. 

Security Features Are Scattered and Tangled. Our findings connect to a long line of feature-interaction research showing that features cannot always be understood independently [44–46]. Prior work has also identified structural interactions at the source-code level [47]. We observe related interactions for security features in general-purpose software systems: access-control checks occur within secure-data operations, credentials require cryptographic protection, and security monitoring is embedded within access-control and cryptographic functionality. Scattering distributes security functionality across the codebase, requiring reasoning across multiple implementation locations [48, 49], while tangling additionally requires reasoning across feature boundaries. Existing feature-interaction techniques provide a starting point for identifying and reasoning about such dependencies [44, 45, 50]. Our dataset enables investigating how these techniques can be adapted to functional security features in conventional software systems. These characteristics are also relevant to vulnerability analysis. Static security analyzers struggle with false positives and practical adoption [10, 51, 52]. TraceSec [53] shows that providing project-specific security context can improve the prioritization of analyzer findings. Security-feature locations and interactions provide complementary code-level context that could help analyses account for related functionality beyond individual APIs or locations. Future work could investigate whether this context improves vulnerability detection and prioritization. 

Security Features Depend on Project Context. Security-feature footprint and interaction vary substantially across projects and appear to depend more on the underlying security model 18 Hermann et al. than on project size. Researchers and tools should therefore account for project-specific security responsibilities and abstractions rather than assuming a universal implementation structure. This variation means that the relevant context for implementing a security feature is inherently project-specific, which is particularly important for AI-assisted development. Developers already struggle with security APIs [2–5, 12, 54], and AI-generated code can contain vulnerabilities [55–59], while coding agents may operate on a limited scope of the codebase [60]. Our findings suggest that security-aware agents should consider existing security abstractions, their usage sites, and interact-ing features when modifying or generating security-sensitive code. Our dataset provides annotated examples for investigating whether such context improves AI-assisted security development. 

10 Threats to Validity 

We now discuss the potential threats to the validity of our study. 

Internal Validity. Author bias may have influenced the sampling of subject systems. The systems were selected based on the knowledge and familiarity with the subject domain of two authors, resulting in 9 systems from 7 different categories. Author bias may also have influenced the identification of security features. While the first author conducted the identification, the first and second author frequently discussed and reviewed the dataset to mitigate potential biases. The categorization of security features according to the taxonomy may also be subject to author bias, which we mitigated through discussion between two authors until consensus was reached. 

External Validity. The generalizability of our findings may be limited due to how we selected the subject systems. Our study focused on software systems written in Java, which may not generalize to systems written in other programming languages. The subject systems were selected based on their popularity on Github, which are often mature and security-conscious. Finally, our subject systems were drawn from 7 different categories, which may limit the generalizability of our findings to other types of software systems. 

Conclusion Validity. The correlations reported in our study may be prone to outliers in our dataset. During sampling, we aimed to select projects that are representative of different categories, and span varying sizes, organizations, and security focus. 

Construct Validity. We used a predefined taxonomy of security features for the annotation and categorization process, which may constrain the scope of security features considered. The authors discussed all security features that we could not immediately categorize until consensus was reached. We were able to categorize all security features according to the predefined taxonomy. 

11 Conclusion 

We presented a mining study of how functional security features are realized in nine open-source Java software systems. We manually annotated their security-feature code and analyzed its footprint, implementation and usage patterns, origin, and interactions. Our results show that security features are more than just a simple library call. While individual code locations are often small, they collectively form a substantial and scattered footprint across the codebase. Security-feature code is dominated by the use of internally implemented functionality that frequently integrates external security functionality into project-specific abstractions. Security features also interact with each other, and their implementations often overlap. Our annotated dataset provides a basis for developing and evaluating techniques for security feature location, security analysis, and security-aware development. While external security APIs provide useful entry points for locating security features, analyses should also account for project-specific implementations, their usages, and interacting features. Security functionality therefore needs to be considered across libraries, locations, and feature interactions. Security Is More Than a Library Call: How Security Features Live in Code 19
