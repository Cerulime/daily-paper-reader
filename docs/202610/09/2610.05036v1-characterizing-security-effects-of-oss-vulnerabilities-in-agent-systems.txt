DEQING ZOU, Cyberspace Security University of China, China Software agents increasingly depend on open source components when executing tools and interacting with external systems. Security flaws in these dependencies may therefore influence more than the software process in which they occur: their consequences can be carried through tool outputs, agent state, and information subsequently exposed to the model. Determining whether such a consequence is actually realized in a particular execution, and where its influence stops within the agent system, remains challenging. We investigate how known OSS vulnerabilities behave when exercised as part of agent workflows. Our study reveals recurring patterns in the way security-relevant consequences emerge and propagate across runtime layers. Building on these observations, we use vulnerability-aware semantic information, differential executions of vulnerable and corrected software, and runtime provenance spanning multiple layers to determine whether a vulnerability produces an observable security effect and to identify the furthest layer at which that effect remains manifested. Our evaluation shows that this approach can accurately distinguish realized vulnerability effects and determine their manifestation boundaries across a diverse collection of vulnerability scenarios. We additionally apply the analysis to documented workflows in a real-world agent framework and uncover multiple security effects originating from known vulnerabilities in its OSS dependencies. These results highlight the importance of reasoning about vulnerable dependencies in terms of their execution-level consequences rather than vulnerability presence alone. 1 Introduction 

How Do OSS Vulnerabilities Manifest in Agents? As agents become increasingly capable, completing complex tasks increasingly relies on open source software (OSS) to interact with external environments, including network services, files, databases, and executable code. Agent Hosts, Tools, MCP Servers, and their underlying protocol libraries, parsers, HTTP clients, and data-storage components together form the software stack that executes agent actions [18]. These components may themselves contain publicly disclosed software vulnerabilities [14]. In agent systems, the effects of OSS vulnerabilities may extend beyond the conventional software runtime. They can pass through Tool returns and Host processing, reach model-visible Observations, and become inputs to subsequent agent decisions [6, 21, 58]. For example, a vulnerability may cause an unauthorized file read, unintended credential use, or improper resource modification at runtime. The resulting data or state may then be returned by a Tool, transformed by the Host, and exposed

to the model. Across this process, the concrete operation, state, or value carrying the vulnerability effect may change, while the security-relevant consequence may remain represented. This raises a fundamental question for analyzing known OSS vulnerabilities in agents. What security-relevant effect does a target vulnerability actually cause in a concrete agent execution, and how far through the agent stack does that effect remain manifest as its representation changes? 

What Is Missing from Existing Analysis? The core difficulty is connecting a vulnerability-induced runtime change to its downstream manifestation in the agent execution. This connection cannot always be established by tracking the original runtime value. A vulnerability may alter a re-source state, authorization behavior, or external response. The resulting Tool output or Observation may no longer contain the original value, yet may still reflect the same security consequence. Existing analyses address different parts of this problem. OSS vulnerability analysis can identify vulnerable dependencies [8, 32], determine whether vulnerability-related code is reachable [19, 31], and determine whether vulnerable constructs are actually exercised at runtime [31, 32]. These techniques establish whether a vulnerability is present, reachable, or exercised in the underlying software. Data-flow and taint analysis can further track information dependencies [15, 17]. However, once a vulnerability changes a resource state, authorization decision, external response, or other runtime outcome, later Agent representations may no longer preserve a direct correspondence to the original operation, state, or value. Existing OSS-centric analyses therefore do not directly determine whether the same vulnerability-attributable effect remains manifest after such transformations. Agent security analysis starts from the other end of the execution. Existing work examines security-relevant content in Tool outputs and model-visible Observations [13, 17, 35, 43], as well as subsequent agent behavior [2, 37, 60]. However, it typically does not trace these Agent-level phenomena back to the realized runtime effect of a specific known OSS vulnerability. This leaves a missing link between vulnerability-specific runtime effects and their downstream manifestations in the Agent execution. 

What Must Be Identified? We therefore decompose the problem into two analyses. Vulnerability attribution identifies the security-relevant runtime change caused by the target vulnerability in a given execution. Effect manifestation determines the furthest execution boundary at which that attributed effect remains manifest. We accordingly ask the following research question. Given an agent execution, what security-relevant effect is actually caused by a target OSS vulnerability, and what is the furthest execution boundary at which that effect remains manifest? 

Preliminary Study. We first conduct a preliminary study of 52 vulnerability cases. Across these cases, we observe a recurring effect structure. A vulnerability-attributable root runtime change acts on specific objects or states and may further produce security-relevant consequences. We also observe different manifestation depths. Some effects remain within the underlying runtime, while others enter the Tool-return path or reach the model-visible Observation. Based on these observations, we define a realized vulnerability effect as the security-relevant runtime change caused by the target vulnerability, together with its affected objects or states and any resulting security-relevant consequences. We define the furthest execution boundary at which the effect remains manifest as its maximum manifestation boundary. 

Oscar. Based on this abstraction, we present Oscar ( Open-Source CVE Analysis for Agent 

Runtime), a framework for identifying realized vulnerability effects and localizing their maximum manifestation boundaries. Given a target vulnerability, an agent task, and its input, Oscar extracts trigger semantics and patch semantics from public vulnerability information and the corresponding patch. It then executes the vulnerable and fixed versions under equivalent conditions. Oscar combines paired execution differences with vulnerability-specific semantics to identify the root runtime change attributable to the target vulnerability. It then uses runtime provenance across the Characterizing Security Effects of OSS Vulnerabilities in Agent Systems 3

Program, Resource, MCP, Host, and Agent layers to recover the affected objects or states, resulting security-relevant consequences, and the maximum manifestation boundary. 

Evaluation. We evaluate Oscar on an independently constructed vulnerability test set and real-world agent frameworks. Oscar achieves 96.4% F1 and 96.0% accuracy in realized vulnerability effect identification and correctly localizes 24 of 28 maximum manifestation boundaries. We further deploy five Agent Hosts in the real-world open-source autonomous research framework ARIS. Across these heterogeneous agent runtimes, Oscar identifies vulnerability effects that either remain within the underlying runtime or reach model-visible Observations. Ablation experiments show that both vulnerability-specific semantics and vulnerable/fixed paired execution are important for accurate vulnerability attribution and effect reconstruction. 

Contributions. In summary, this paper makes the following contributions. 

• Problem characterization. We formulate the cross-layer effect manifestation problem for known OSS vulnerabilities in agent runtimes. The problem is to determine how an effect caused by a specific vulnerability in the underlying software execution manifests across subsequent agent execution when its original code- or value-level correspondence may no longer be preserved. 

• Effect abstraction and analysis. Through a preliminary study of 52 vulnerability cases, we char-acterize the recurring structure of realized vulnerability effects and introduce the maximum mani-festation boundary. Based on these observations, we design Oscar, which combines vulnerability-specific semantics, paired execution, and cross-layer runtime provenance to identify realized effects and localize their manifestation boundaries. 

• Evaluation. We evaluate Oscar on an independent vulnerability test set and a real-world multi-Host agent environment. The results show that Oscar accurately identifies OSS vulnerability effects realized in concrete executions and localizes their furthest manifestation boundaries. 

2 Preliminary Study 

Having motivated the need to connect vulnerability-attributable runtime effects with their down-stream manifestations, we first conduct a preliminary study to understand how such effects appear in concrete Agent executions. Specifically, we examine the runtime structure of realized vulnerabil-ity effects and how far these effects remain manifest as execution proceeds from the underlying software runtime to model-visible Observations. 

2.1 Problem Definition and Scope 

We study known OSS vulnerabilities in concrete Agent executions initiated by user tasks and inputs. We assume that the target vulnerability and its affected component have already been identified. Our goal is to determine whether the vulnerability produces a security-relevant effect in the given execution and, if so, how far that effect manifests through the Agent execution stack. Our analysis is execution-specific. We do not identify vulnerabilities in the Agent stack, generate inputs to trigger them, estimate their triggering likelihood under natural workloads, or consider unknown vulnerabilities. Instead, we focus on the runtime consequences of a known vulnerability under a given Agent execution. Accordingly, we investigate two research questions: 

• RQ1: What security-relevant effects do known OSS vulnerabilities produce in concrete Agent executions? 

• RQ2: How far do these effects manifest through the Agent execution stack?

2.4 Cross-Layer Manifestation Boundaries 

We next examine how far each realized effect manifests through the Agent execution stack. Follow-ing the typical execution structure of tool-augmented agents [37, 38, 55], we inspect the underlying runtime execution, Tool Result, Host processing, and model-visible Observation. We refer to the execution initiated by one Tool invocation and the processing that produces its corresponding Observation as an execution round .Across the 51 realized effects, we observe three recurring maximum manifestation boundaries: Runtime, Tool, and Observation. As shown in Figure 2(a), 32 effects (62.7%) reach the Observation boundary, where the effect remains identifiable in the model-visible Observation. Another 15 effects (29.4%) reach the Tool boundary, where a representation enters the Tool-return path but does not reach the Observation after Host processing. The remaining four effects (7.8%) remain at the Runtime boundary, where the effect is realized in program execution, external resources, or environmental state, but no representation enters the Tool Result. These boundaries summarize the furthest scope reached by each effect, with Host processing treated as an intermediate transformation rather than a separate boundary. For the 19 effects with a Runtime or Tool maximum manifestation boundary, Figure 2(b) summa-rizes the mechanisms that prevent further manifestation. Host text/field redaction occurs in nine cases (47.4%), where Host processing removes or replaces security-relevant content associated with the effect. Host native-carrier down-projection occurs in six cases (31.6%), where an image, Blob, or embedded resource no longer preserves the effect after Host-side representation conversion. Tool Result omission occurs in four cases (21.1%), where an effect realized in the underlying runtime is not represented in the Tool Result.

3 Oscar 

Motivated by the recurring effect structure and manifestation boundaries identified in Section 2, we propose Oscar ( Open-Source CVE Analysis for Agent Runtime) to identify the realized effect of a known OSS vulnerability under a given Agent task and input and localize its maximum manifestation boundary. 

3.1 System Overview 

Figure 3 presents the three-stage workflow of Oscar. ❶ Vulnerability Semantic Analysis. Oscar extracts vulnerability trigger semantics and patch semantics from public vulnerability information and the corresponding patch to constrain subsequent runtime analysis. ❷ Cross-Layer Execution Graph Construction. Oscar executes the vulnerable and fixed versions under the same conditions and constructs paired execution graphs spanning the Program, Resource, MCP, Host, and Agent layers to preserve cross-layer runtime provenance. ❸ Runtime Effect Analysis and Localization. 

Oscar compares the paired graphs to identify the vulnerability-induced root runtime change, reconstruct the realized effect, and determine its maximum manifestation boundary. Figure 3 also illustrates a running example involving a path-traversal vulnerability in an MCP file-reading Tool. The vulnerable version accesses a file outside the intended directory, whereas the fixed version rejects the same request before file access. 

3.2 Vulnerability Semantic Analysis 

To attribute runtime behavior to the target vulnerability, Oscar extracts vulnerability trigger semantics 𝐴 𝑉 and patch semantics 𝑃 fix .

3.2.1 Vulnerability Trigger Semantics. 𝐴 𝑉 captures the input characteristics and runtime conditions required to reach a vulnerability-relevant execution path. Oscar derives 𝐴 𝑉 from CVE descriptions, security advisories, PoCs, and related documentation, including the relevant interface, parameters, and trigger conditions. It is used to construct vulnerability-relevant executions and to constrain subsequent attribution of runtime differences. Satisfying 𝐴 𝑉 indicates that the vulnerability-relevant path is reached, but does not by itself establish a realized effect. In the running example, 𝐴 𝑉 captures the path parameter and its directory-traversal characteristic, such as ../private/canary.txt .Characterizing Security Effects of OSS Vulnerabilities in Agent Systems 7

3.2.2 Patch Semantics. 𝑃 fix captures the vulnerable behavior eliminated or constrained by the fix. Oscar derives 𝑃 fix using a vulnerability-fix semantic extraction technique [10], together with vulnerability descriptions, security advisories, and patch-related text. It is used to determine whether an observed runtime difference corresponds to the behavior addressed by the patch. In the running example, 𝑃 fix specifies that access to files outside ROOT must be blocked before file access occurs. 

3.3 Cross-Layer Execution Graph Construction 

A realized vulnerability effect may originate in program execution, affect external resources, and further propagate through Tool returns and Host processing into the Agent context. To capture this runtime provenance, Oscar constructs a cross-layer execution graph spanning the Program, Resource, MCP, Host, and Agent layers.

3.3.2 Paired Execution Graph Generation. Oscar uses the fixed version as an execution-level reference to distinguish vulnerability-induced behavior from normal task behavior. It executes the vulnerable and fixed versions under the same Tool input, Host configuration, and external runtime environment, producing paired execution graphs 𝐺 𝑣 and 𝐺 𝑓 .For each execution, Oscar records the concrete Tool parameters, executed program operations, resource/state interactions, runtime values, Tool returns, Host processing, Agent Observations, and subsequent Agent Actions. Only events that actually occur are instantiated in the graph. Thus, the paired executions differ only in the target OSS version at setup, while 𝐺 𝑣 and 𝐺 𝑓 preserve the runtime divergences induced by that version change. In the running example, the vulnerable version receives ../private/canary.txt , accesses 

/workspace/private/canary.txt , and obtains VULN_WITNESS_7F3A . Thus, 𝐺 𝑣 contains the out-of-scope file access and its subsequent value propagation. The fixed version rejects the same input before file access, so these events are absent from 𝐺 𝑓 .

3.4 Runtime Effect Analysis and Localization 

With the paired execution graphs constructed, Oscar next identifies the realized vulnerability effect and localizes its manifestation. The analysis proceeds from the root runtime change, to effect reconstruction, and finally to maximum manifestation boundary localization. 

3.4.1 Root Runtime Change Identification. Paired executions may exhibit many runtime differences, including both vulnerability-induced behavior and downstream changes caused by execution divergence. To identify where the realized effect first emerges, Oscar aligns runtime entities in 

𝐺 𝑣 and 𝐺 𝑓 with corresponding execution semantics, and compares the aligned graphs to identify differences in runtime events, relations, states, and values. Because graph differences alone do not establish vulnerability causality, Oscar further attributes each candidate difference using 𝐴 𝑉 and 

𝑃 fix : 𝐴 𝑉 confirms that the execution satisfies the trigger conditions, while 𝑃 fix determines whether the difference corresponds to behavior eliminated or constrained by the patch. We distinguish three forms of candidate differences during graph comparison. An event or relation may occur only in one execution; aligned runtime entities may carry different values or states; or the same operation may interact with a different resource or produce a different outcome. These candidates are identified before vulnerability attribution. 𝐴 𝑉 and 𝑃 fix are then used to retain only differences that are consistent with both the trigger conditions and the behavior addressed by the patch. Among the attributed differences, Oscar defines the earliest security-relevant runtime change as the root runtime change 𝑟 𝑉 , which serves as the provenance root of the realized effect. If no such change exists, Oscar reports 𝐸 𝑉 = ∅ and stops the analysis. In the running example, 

../private/canary.txt satisfies 𝐴 𝑉 , while 𝑃 fix requires accesses outside ROOT to be blocked. Since only the vulnerable execution performs the out-of-scope file access, Oscar identifies the out-of-scope file read as 𝑟 𝑉 .

3.4.2 Realized Effect Reconstruction. After identifying where the effect begins, Oscar reconstructs the affected objects or states and additional security-relevant consequences. Following Finding 1, it represents the realized effect as 

𝐸 𝑉 = (𝑟 𝑉 , 𝑂 𝑉 , 𝑆 𝑉 ),

where 𝑂 𝑉 denotes the objects or states affected by 𝑟 𝑉 , and 𝑆 𝑉 denotes additional security-relevant values, states, or external outcomes. Starting from 𝑟 𝑉 , Oscar follows Resource and Data relations Characterizing Security Effects of OSS Vulnerabilities in Agent Systems 9

to identify runtime entities representing the affected objects or states 𝑂 𝑉 , and then follows Data, Resource, and Control relations to recover downstream security-relevant consequences 𝑆 𝑉 . If 𝑟 𝑉 

acting on 𝑂 𝑉 already constitutes the complete effect, then 𝑆 𝑉 = ∅.In the running example, the out-of-scope read acts on /workspace/private/canary.txt and obtains VULN_WITNESS_7F3A . Accordingly, 𝑂 𝑉 = {/workspace/private/canary.txt } and 𝑆 𝑉 =

{VULN_WITNESS_7F3A }.

3.4.3 Effect Manifestation Localization. The final step determines how far the realized effect manifests in the Agent system. Starting from the entities constituting 𝐸 𝑉 , Oscar follows their cross-layer provenance in 𝐺 𝑣 . We regard an entity at a later layer as an effect representation when it remains connected through runtime provenance to 𝑟 𝑉 , 𝑂 𝑉 , or 𝑆 𝑉 and preserves the corresponding security-relevant behavior, state, value, or outcome. This criterion does not require byte-level equality with the original runtime value: Host-side filtering, formatting, or projection may alter the concrete representation while preserving the same effect semantics. Conversely, merely carrying vulnerability-related diagnostic information is insufficient if the realized effect itself is no longer represented. Following Finding 2, Oscar defines the maximum manifestation boundary as 

𝐵 (𝐸 𝑉 ) ∈ { 𝐵 Runtime , 𝐵 Tool , 𝐵 Observation }.

Here, the Runtime boundary covers the Program and Resource layers, the Tool boundary covers the MCP and Host layers, and the Observation boundary corresponds to the model-visible Agent Observation. Accordingly, 𝐵 (𝐸 𝑉 ) = 𝐵 Runtime if no effect representation enters the Tool Result, 

𝐵 (𝐸 𝑉 ) = 𝐵 Tool if it enters the Tool-return path but not the Agent Observation, and 𝐵 (𝐸 𝑉 ) =

𝐵 Observation if it remains identifiable in the Observation. Host processing is treated as an intermediate stage rather than a separate maximum boundary. In the running example, the value obtained by the out-of-scope file read enters the Tool Result, passes through MCP and Host processing, and remains identifiable in the Agent Observation. Oscar therefore assigns 𝐵 (𝐸 𝑉 ) = 𝐵 Observation .

4 Evaluation 

We evaluate Oscar from three aspects: its effectiveness in identifying realized vulnerability effects, its accuracy in localizing their maximum manifestation boundaries, and the contribution of its major design components. Our experiments focus on the following Research Questions (RQs): 

• RQ1: How accurately can Oscar determine whether a known OSS vulnerability forms a realized effect under a given Agent task and input? 

• RQ2: How accurately can Oscar localize the maximum manifestation boundary of a realized vulnerability effect? 

• RQ3: How do vulnerability-attribution evidence and graph representation contribute to Oscar’s analysis? 

4.1 Evaluation Setup 

Implementation. We implemented Oscar in Python 3.12 following the three-stage workflow described in Section 3. For each case, Oscar extracts vulnerability trigger semantics 𝐴 𝑉 and patch semantics 𝑃 fix , executes the vulnerable and fixed versions, constructs their execution graphs, reconstructs 𝐸 𝑉 = (𝑟 𝑉 , 𝑂 𝑉 , 𝑆 𝑉 ), and determines 𝐵 (𝐸 𝑉 ). The collected runtime trace covers program and resource events, Tool Results, Host-side representations, and model-visible Observations. 

Environment. All experiments were conducted on a server running Ubuntu 24.04.2 LTS, equipped with two 64-core AMD EPYC 7B13 processors, 188 GiB of memory, one 40 GiB NVIDIA A100 GPU, and one 80 GiB NVIDIA A100 GPU. Docker 28.5.1 was used to isolate individual cases. For paired 10 Yu Ji, Yang Wei, Yutao Hu, Haojun Zhao, Yueming Wu, and Deqing Zou 

executions, the Agent task, input, Host configuration, Tool set, container configuration, network settings, and external services were kept unchanged. Only the target OSS version differed between the vulnerable and fixed executions. 

Baselines. We compare Oscar against three representative baselines: Code Reachability, AgentFuzz, and MCP-BiFlow. Code Reachability [49] checks whether the vulnerability-related code region is reachable from the current Tool entry. AgentFuzz [28] dynamically detects vulnerabilities in LLM agents by executing Agent tasks and observing vulnerability-triggering behavior. MCP-BiFlow [17] detects unsafe data flows in MCP servers by recovering request-side and return-side propagation paths. For case-level comparison, we normalize their outputs to Effect Yes, Effect No, or Unassessed according to each method’s detection result. 

Dataset. We first collected popular MCP servers and Agent tools from public repositories and tool ecosystems, and used OSV to identify known vulnerabilities in these projects and their dependencies. For each candidate, we manually examined the vulnerability advisory, affected versions, source code, and patch to confirm that the affected component lies on the Tool execution path. We then constructed the corresponding Agent task and execution context using DeepSeek Harness [7], and manually annotated the effect label and, for positive cases, the realized effect and its maximum manifestation boundary based on the vulnerability semantics and execution context. The preliminary study and evaluation cases are separated by project. Development and test cases are further grouped by project-vulnerability family to avoid overlap between the two sets. As shown in Table 3, the final independent test set contains 50 cases, including 28 Effect Yes and 22 Effect No. Among the 28 positive cases, 10 have a Runtime boundary, eight have a Tool boundary, and 10 have an Observation boundary.

5 Real-World Applicability 

We evaluate Oscar on ARIS (Auto-Research-In-Sleep) [53], an open-source autonomous research harness that coordinates multiple agents for tasks such as literature review, experiment execution, and paper writing. 

5.1 Real-World Evaluation Setup 

ARIS is well suited for this evaluation because it supports multiple Agent Hosts within a unified workflow. As of October 2, 2026, its GitHub repository has 16,901 stars and 1,428 forks [51]. To ensure reproducibility, we pin ARIS to commit 2132036 [52] and deploy five Agent Hosts: DeepSeek Harness, Qwen-Agent [34], PraisonAI [33], Goose [1], and OpenCode [3]. These Hosts differ in Tool invocation, MCP integration, session representation, and model-request construction, allowing us to evaluate Oscar across heterogeneous Agent runtime implementations. We first use OSV-Scanner 2.6.0 [11] to scan the resolved dependency environments of the five Hosts. In total, we analyze 5,941 dependency entries and identify 117 vulnerable package-version entries, corresponding to 303 unique CVE identifiers. We then analyze code reachability and retain 25 reachable vulnerability instances whose vulnerable functionality can be exercised through normal Agent functionality. For each instance, we construct an Agent task following the normal usage described in the corresponding Host README and execute it using the Host’s native Tool interface, runtime environment, and configuration. Under the same Agent task, Tool input, Host configuration, and external environment, we run both the vulnerable and fixed versions of the target OSS component, repeating each version three times. Oscar then identifies realized vulnerability effects and localizes their maximum manifestation boundaries. In parallel, we record complete runtime traces for manual validation, including vulnerability-relevant program operations, resource/state changes, Tool Results, host-processed representations, and actual model requests.

6 Discussion 

Scope of Analysis. Oscar analyzes the realized effect of a known OSS vulnerability under a given Agent task, input, and execution context. A negative result therefore means that no attribut-able security-relevant effect is established for the analyzed execution. It does not imply that the vulnerability is generally harmless or unreachable under other inputs. 

Vulnerability Attribution. Attributing runtime changes to a target CVE is difficult because vulner-able and fixed versions may contain unrelated differences. Oscar therefore combines vulnerability trigger semantics 𝐴 𝑉 , patch semantics 𝑃 𝑓 𝑖𝑥 , and paired vulnerable/fixed executions. Ablation results support this design: removing 𝑃 𝑓 𝑖𝑥 or the fixed execution reduces realized effect identification F1 from 96.4% to 84.7% and 88.1%, respectively. Attribution may still be affected by incomplete vulnerability descriptions or unrelated changes in fixing commits. 

Runtime Evidence Completeness. Vulnerability effects may appear in program state, external resources, or persistent environments without explicit return values. Oscar captures program operations, resource interactions, runtime values, and external-state changes in a cross-layer execution graph, enabling detection of Runtime-boundary effects that return-side analysis may miss. Effect confirmation nevertheless requires an observable witness linked to the relevant execution. In our evaluation, the only false negative arises from an external-state change whose provenance cannot be reliably associated with the corresponding Tool invocation. 

Cross-Layer Effect Correspondence. A realized effect may change representation as it propa-gates through Tool Results, Host processing, and Agent Observations. Oscar preserves runtime provenance from the root change to downstream representations using an effect-aware cross-layer execution graph, rather than relying only on value similarity or co-occurrence. This improves boundary localization over Raw Trace and Generic Provenance representations. Complex Host-side transformations can still obscure whether downstream representations preserve the same security-relevant effect, accounting for the remaining RQ2 localization errors. 

Generalizability and Realism. Oscar’s cross-layer execution graph is extensible to evolving Agent runtimes by adding or refining node and relation types without changing the effect recon-struction and localization procedure. Evaluation across five heterogeneous Agent Hosts provides initial evidence for this portability. Since naturally occurring Agent workloads and user inputs are unavailable, we construct vulnerability-relevant tasks to evaluate Oscar’s analysis capability. Our real-world study further follows documented usage and native execution environments while exercising vulnerability-relevant conditions. The results therefore support portability across Agent runtimes, rather than vulnerability triggering frequency in natural workloads. 

7 Related Work 7.1 Vulnerability Analysis of Open Source Software Components 

OSS Component and Vulnerable Code Analysis. OSSPolice identifies reused components and versions [8], CENTRIS detects modified and nested reuse [45], and OSSFP uses function fingerprints [47]. VulSCA adds code-level vulnerability confirmation [19], while code-centric analysis examines vulnerable code in downstream applications [31]. Graph-based methods model program dependencies with heterogeneous code graphs [59] or use code-property-graph-guided 18 Yu Ji, Yang Wei, Yutao Hu, Haojun Zhao, Yueming Wu, and Deqing Zou 

slicing [24]. These studies cover component identification, vulnerable-code detection, and related analysis [27], but do not capture the concrete runtime effects of vulnerabilities. 

Vulnerability Trigger and Patch Analysis. PatchFinder traces vulnerabilities to fixing com-mits [26], E-SPI identifies security patches from commit structure [46], and GraphSPD represents patch changes with code property graphs [42]. PS 3 derives semantic signatures for patch-presence testing [57], while Robin distinguishes vulnerable and patched behavior [54]. P 3 jointly analyzes pre- and post-patch versions [39]. These studies recover vulnerability triggers and fix actions [10], but do not reconstruct the resulting runtime effect or trace it beyond the vulnerable program. 

7.2 Vulnerability Analysis in Agent and MCP Systems 

Program Analysis for LLM-Integrated Systems. LLMSmith combines call-chain analysis with execution validation [29], and TaintP2X tracks model-generated data to sensitive operations [15]. AgentFlow models Agent components and control/data dependencies [41]. Agent-BOM combines system structure with runtime semantic states [25], while Agentproof checks workflow-level safety properties [50]. These methods extend program analysis to model–program interactions, but do not trace the effect of a specific OSS vulnerability across Agent-system layers. 

Runtime Testing of Agent Systems. ToolEmu evaluates Agent risks in an emulated environ-ment [37]. AgentFuzz uses directed fuzzing [28], AGENTVIGIL tests indirect prompt injection [43], MELON compares original and masked re-executions [60], and ChainFuzzer fuzzes multi-tool execution chains [48]. These approaches validate concrete Agent security behaviors, but do not attribute them to known OSS vulnerabilities or reconstruct their effects. 

Runtime Provenance and Effect Tracing. KAIROS builds whole-system provenance graphs [5], R-CAID performs provenance-based root-cause analysis [12], and ORTHRUS reconstructs depen-dency paths [23]. MAGIC [22] and FLASH [36] learn provenance-graph representations. SHADE-WATCHER models audit interactions [56], while DEPIMPACT propagates dependency impact [9]. Provenance-based auditing reasons over execution dependencies [20], but mainly focuses on system-level events rather than vulnerability-specific effects [16]. 

Security Analysis of MCP Systems. MCP Safety Audit evaluates MCP-connected workflows [35], while large-scale server analysis studies MCP security [14]. MCP-BiFlow performs bidirectional data-flow analysis [17]. DCIChecker checks description–implementation inconsistencies [40], MCPZoo supports runtime validation [4], and MindGuard analyzes tool poisoning with decision-dependence graphs [44]. These methods focus on the Agent-Tool boundary, but do not establish the end-to-end connection between known OSS vulnerabilities and their runtime effects in Agent systems. 

8 Conclusion 

This paper studies how known OSS vulnerabilities manifest in agent executions. We present Oscar, a runtime analysis framework that identifies the security-relevant effect actually caused by a target vulnerability and determines its maximum manifestation boundary. Oscar combines vulnerability-specific semantics with vulnerable/fixed paired execution to attribute runtime changes to the target vulnerability, and uses cross-layer runtime provenance to recover their manifestations across the Agent stack. Our evaluation shows that Oscar achieves 96.4% F1 and 96.0% accuracy in realized vulnerability effect identification and correctly localizes 24 of 28 maximum manifestation boundaries. Evaluation on five Agent Hosts in the real-world ARIS framework further demonstrates that Oscar can analyze vulnerability effects that either remain within the underlying runtime or reach model-visible Observations across heterogeneous agent runtimes.
