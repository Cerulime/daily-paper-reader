## Abstract 

Database systems are predominantly developed in unsafe languages (e.g., C/C++) to meet the performance requirements through low-level memory management, yet this reliance renders them prone to systemic memory-safety issues that compromise reliability, consis-tency, security, and durability. Through an extensive bug analysis of prominent database systems, we show that these memory-safety issues persist in production environments despite advancements in database testing tools. While emerging hardware-assisted exten-sions, such as Arm’s Memory Tagging Extension (MTE) and CHERI, offer a promising mitigation path for memory safety, their practi-cal applicability and performance overhead within the specialized constraints of database systems remain largely unexplored. In this paper, we evaluate these modern hardware extensions through the lens of what we define as the database trilemma : the fundamental trade-off between safety , performance , and portability ,to determine their viability for production-grade database systems. We provide the first side-by-side comparison of MTE and CHERI across a database workload suite. Our bottom-up study spans mi-croarchitecture, the compiler/runtime/OS stack, core data structures (ART, B+Tree, hash table, skip list, linked list, and queue), and full database systems (Redis, LevelDB, SQLite, MySQL, DuckDB, and LadyBugDB) to characterize their performance, safety guarantees, and ease of adoption. We find that while hardware extensions can offer near-determinis-tic protection, they introduce non-uniform performance taxes: MTE provides high portability with modest overheads ( ≈10%), while CHERI delivers superior safety guarantees with higher performance penalties (20–60%) and significant porting effort. Our study equips database systems architects with an actionable guide towards build-ing the next generation of reliable, secure databases using hardware-assisted safety mechanisms. 1

## 1 Introduction 

Database systems are predominantly implemented in memory-unsafe languages (e.g., C/C++), to meet the performance require-ments of data-intensive applications. Such languages provide de-velopers with fine-grained control over memory management, en-abling practitioners to design high-performance buffer managers, indexing structures, and query execution engines. However, this power comes at a significant cost: the lack of inherent memory safety .

Memory safety denotes the guarantee that memory accesses are well-defined and restricted to their intended regions; violations of this property [126, 133] are categorized as spatial or temporal .

Spatial errors (e.g., overflows, out-of-bounds access) occur when a program accesses memory outside its intended boundaries, while 

temporal errors (e.g., use-after-free, double-free) refer to when a program accesses memory after its deallocation. In database sys-tems, such violations constitute fundamental reliability, consistency, durability, and security issues. The software industry has long grappled with memory safety [7, arXiv:2610.11525v1 [cs.DB] 8 Oct 2026 Proc. ACM Manag. Data 4, 6 (SIGMOD), Article 378, December 2026 Meignan--Masson et al.

Database systems are no exception; our study across major open-source database systems (§2.1) reveals that memory-safety bugs remain a substantial share of all reported issues, and that even recently developed systems [31, 42] are not immune, confirming that memory safety remains a serious concern. One option to address these issues is to rewrite existing systems in memory-safe languages (e.g., Rust), which offer performance while providing built-in safety guarantees. While such rewrites have proven successful, both for new projects [35] and for rewriting core components of production systems [65], they remain a substantial undertaking for systems comprising millions of highly optimized lines of code, where the engineering cost is often prohibitive. As an alternative, database practitioners commonly resort to 

exhaustive testing and software-based runtime checks . While formal verification can prove safety, it fails to scale to the complexity of modern database systems. Meanwhile, software-based runtime approaches [54, 73, 85, 120, 121] are prohibitively expensive (up to 79% for lookups in LevelDB), as shown in Figure 1, and are, in general, not practical for production database systems. To this end, hardware vendors have proposed new hardware extensions to provide memory safety with lower performance over-heads. In particular, several propositions such as ARM’s Memory Tagging Extension (MTE) [12], Capability Hardware Enhanced RISC Instructions (CHERI) [141], x86’s upcoming ChkTag [33], In-tel’s deprecated Memory Protection Extensions (MPX) [13], and Oracle’s SPARC Silicon Secured Memory [6] offer new primitives for memory safety. As shown in Figure 1, such extensions reduce overhead considerably compared to software-based approaches— yet they still impose non-trivial costs, and adopting them requires non-trivial code modifications, raising portability concerns. Together, these constraints expose a “Database Systems Trilemma” :a fundamental conflict between safety , performance , and portabil-ity . In essence, developers must sacrifice performance for safety, or portability for a modern safe language, or, as is most common, sacrifice safety for the performance and control of unsafe languages. While these technologies are increasingly adopted in mobile ecosystems [25, 51], they have been slow to reach database systems, mainly due to the lack of a systematic analysis and experimentation with these hardware extensions in this context. To this end, we aim to answer the central question: Should your database system use hardware-assisted memory-safety extensions in production? 

To provide an answer, we conduct the first side-by-side, cross-layer comparison (Figure 2) of memory-safety hardware extensions tailored for database systems, spanning from microarchitecture through data-structures to full systems. Our study begins with a 

microarchitectural analysis of the underlying hardware primitives (§ 3). Next, we evaluate how these primitives affect the "building blocks" of database systems by porting and benchmarking a set of critical data structures (§ 4). We scale our analysis to production-grade database systems, detailing the engineering effort and per-formance trade-offs of retrofitting them with hardware safety (§5). Finally, we analyze the role of the operating system and compiler toolchains for hardware-assisted memory safety (§6). To ground our analysis in practice, we distill our findings into actionable takeaways for database practitioners. At the microar-chitectural level, we show that while hardware extensions effec-tively mask the cost of runtime checks, the overhead of managing metadata—such as CHERI’s 128-bit capability loads or MTE’s tag-on-store requirements—can become a bottleneck for write-heavy workloads. At the data structure layer, the “performance tax” is not uniform; cache-friendly structures (e.g., B+ trees) absorb the over-head of memory safety checks better than pointer-chasing struc-tures (e.g., linked lists). For full systems, there is an “engineering-performance” trade-off: MTE offers high portability and modest overheads ( <10%) but provides only probabilistic safety, whereas CHERI offers deterministic, fine-grained protection at the cost of higher porting complexity and performance penalties (20%–60%). To summarize, our study serves as a bridge between architec-tural research and industrial database engineering. By quantify-ing the performance-safety trade-offs of modern hardware, we provide a concrete roadmap for building the next generation of “reliable/secure-by-default” data infrastructure. Our work demon-strates that hardware-assisted safety is finally approaching the ma-turity required for production database systems, offering a viable path to resolving the long-standing database trilemma. Overall, this paper makes the following contributions: 

• Empirical bug study: We quantify the prevalence of memory-safety-related Common Vulnerabilities and Exposures (CVEs) and bugs in open-source database systems, showing they remain a substantial share of reported issues. 

• Hardware-assisted memory safety extensions: We port six data structures and six database systems. We detail the best prac-tices and pitfalls of using the MTE and CHERI extensions. 

• Cross-layer experimental analysis: We evaluate the perfor-mance across four layers: (i) microarchitecture , (ii) data structures ,

(iii) database systems , and (iv) compilers, runtime, and OS .

• The database trilemma synthesis: We formalize and evaluate the trade-offs between safety, performance, and portability. 

• Open-source evaluation framework: To facilitate further re-search into secure and reliable data infrastructure, we make our entire evaluation pipeline, including the “MTE-tagged” and “CHERI-fied” database systems source code, publicly available.

## 2.1 Memory Safety in Database Systems 

Despite the performance benefits of manual memory management, database systems written in unsafe languages (e.g., C/C++) are in-herently exposed to spatial memory safety violations (e.g., buffer overflows, out-of-bounds accesses) and temporal violations (e.g., use-after-free, double-free) [93, 126, 134], whose consequences go well beyond simple crashes. A single erroneous memory access can cause silent data corruption by overwriting adjacent records before they are flushed to storage, produce incorrect query results by corrupting in-memory index structures, exhaust system resources , in-troduce concurrency hazards by corrupting shared metadata, expose sensitive user records to unauthorized parties, or allow unauthorized transactions—ultimately threatening the correctness and durability guarantees that database systems are designed to provide. To quantify the prevalence of memory safety bugs in real-world database systems, we conduct a systematic study of publicly re-ported CVEs and bug reports in the last decade (2015–2025) across seven open-source database systems—ClickHouse, DuckDB, Lev-elDB, MariaDB, MySQL, Redis, and RocksDB—spanning different deployment models and storage engines. The volume of bugs and CVEs (Table 1), and the non-expert nature of bug report writers ren-der manual classification impractical and simple keyword matching unreliable. Instead, we propose using a Large Language Model (LLM) to clas-sify bug reports and CVEs. We employ a locally hosted GPT-OSS 120B model on an NVIDIA H100 GPU to classify each report into 

bug , programmer error , or other , as some bug trackers include addi-tional reports (e.g., user errors, feature requests, and more). Given the higher selectivity, we consider all CVEs to be bugs. Further, the LLM determines whether a bug is memory-safety-related and, if so, identifies its primary operational implication, given a set of options. Each classification is repeated three times independently. We treat a bug as a confirmed memory safety issue only when all 

three repetitions agree. Further details on the methodology are provided in §B. 

Limitations. We do not aim to establish a new state-of-the-art vulnerability classifier, but to provide a system-specific overview complementing related work [20, 81, 127, 130] using more robust pipelines and frontier models. Our pipeline has several limitations, and we report its results as motivating estimates , not exact counts. First, we run a quantized model without ground-truth validation. Second, requiring agreement across all three runs excludes incon-sistently flagged borderline bugs. However, as the model tends to repeat errors [28], agreement provides less confidence than three independent judgments. Third, we classify only issue-tracker re-ports and CVEs, excluding fixes landed without corresponding issues; our claims therefore concern memory-safety reports , not all memory-safety bugs. Finally, MySQL redacts security-sensitive tracker issues, which may affect its memory-safety share. The per-year timeline is also affected by project age, the model’s familiarity with recent terminology, and gaps in CVE enrichment; we therefore interpret it as evidence of sustained presence, not a precise trend. Our analysis yields three key findings: (i) Memory safety bugs affect all database systems. Even recent systems (e.g., DuckDB, ClickHouse) are not immune, highlighting that memory-safety violations remain prevalent despite good practices and modern software engineering techniques. (ii) Memory-safety issues remain a substantial source of bugs in these systems today: through the pe-riod, they consistently account for a non-trivial share of all reported bugs and CVEs every year (Figure 3), despite significant advances in testing, fuzzing, and bug-finding tools [36, 48, 52, 66, 68, 117– 119, 123, 152, 153]. By contrast, large vendors such as Microsoft and Android identified memory safety as the source of ≈ 70% of security issues [8, 9, 112] and report a declining share after deploying mitiga-tions, e.g., Android from 76% to 24% between 2019–2024 [135]. We observe no comparable decline in our dataset. (iii) Memory safety violations can cause diverse harm, as shown in Table 1. The most common implication is a system crash ( ≈87%), followed by resource exhaustion, and incorrect query results. 

## 2.2 Scope: The Database System Trilemma 

Memory safety solutions are governed by three competing dimen-sions: performance overhead , protection coverage , and portability .High-performance systems typically reject solutions that intro-duce non-trivial latency. Consequently, developers often employ best-effort safety models that prioritize execution speed over ex-haustive protection. However, the primary determinant for adop-tion is often the engineering effort required for integration. For large-scale systems, the cost of manual refactoring often outweighs the benefits of improved memory safety. Several software-based approaches have been proposed to prevent memory safety viola-tions [17, 21, 27, 39–41, 54, 55, 60, 62, 67, 73–75, 85, 86, 102, 104, 105, 120–122, 124, 128, 139, 146, 150], with all facing the challenge of rec-onciling the tensions within this trilemma. Their runtime overheads remain the most significant hindrance to production deployment. The alternative of memory-safe languages shows promising results Proc. ACM Manag. ## 3 Architectural Analysis 

After establishing hardware-assisted memory safety as a promising direction, we describe and evaluate the microarchitectural foun-dations of two modern memory safety extensions implemented in research and production hardware (CHERI (§3.1) and MTE (§3.2)) to realize the costs and constraints that any high-level system will inherit. These two extensions differ in maturity: MTE ships in pro-duction silicon today, whereas CHERI is available only on research hardware. We also analyze Intel MPK in §A.1. 

Experimental setup. We conduct our experiments on the Morello Evaluation Platform [57], a prototype implementing CHERI, and an Ampere 1a server, a commercially available server. We run all experiments with synchronous MTE (§3.2), as this is the only mode the Ampere 1a supports [69]. For CHERI, we use Morello LLVM [15]; when compiling in purecap mode (§3.1), we link against a capability-aware port of the Musl C standard library [16]. For MTE, we use upstream LLVM and glibc with MTE enabled. The detailed testbed is described in our supplementary material (Appendix A). We evaluate instructions by executing them 1 .6 × 10 9 times in an unrolled loop of 16 instructions. We measure (i) Latency with data dependencies between instructions and (i) Throughput without dependencies. 

## 3.1 CHERI 

Mechanism. CHERI [142] replaces 64-bit pointers with 128+1-bit hardware-enforced capabilities that encode a memory address, the accessible boundaries, its permissions and object type, and a validity bit (Figure 4). Capabilities are unforgeable and monotonic :overwriting a capability with arbitrary data clears its validity bit. New capabilities can only be derived by narrowing existing ones. Morello implements CHERI for Armv8.2-A, storing the validity bit alongside data in memory. CHERI protects against spatial violations and enables control-flow integrity, while temporal safety can be achieved through capability revocation [45, 140, 143]. Code can be compiled in two modes: purecap , where every pointer is a capability, or hybrid , where only explicitly annotated pointers are.

## 4 Analysis of Data Structures 

Building upon our analysis, we now investigate how MTE and CHERI overheads propagate to the core data structures of modern database systems, chosen within a representative taxonomy. 

## 4.1 Data Structures Taxonomy 

To this end, we propose a use-case-driven taxonomy to ensure coverage of the distinct memory access patterns found in practice. 

Primary access to data. Primary index data structures express relationships across large parts of the data and are used to improve the performance of typical operations. For Key-Value Store work-loads, systems typically use Log-Structured Merge (LSM) trees or 

hash tables . 𝐵 ∗-trees and tries are common for transaction-oriented systems, whereas analytics-oriented systems usually opt for block range indexes. Finally, graphs are typically represented in adjacency lists using the Compressed Sparse Row (CSR) format. 

Temporary buffering. Database systems use additional structures to hold temporary data. Temporary data can be buffered before writing to storage, especially in write-heavy workloads, or when executing long-running, complex queries. Key-Value Store systems commonly use Skip lists to buffer writes in memory, while trans-actional systems usually perform writes directly in the primary data structure. Analytical workloads require complex selections and joins, which are typically performed using hash tables .

Internal organization. Database systems employ auxiliary data structures internally to organize transient data and manage state and operations (e.g., queues ). For our analysis, we choose established representatives of the above categories, listed in Table 6, along with their operations and memory access types. For primary indexes, we select the B+ tree from the Leanstore [78] implementation that uses optimistic lock coupling, and the Adaptive Radix Tree (ART) [79]. For temporary data buffering, we consider the cache-line-aligned hash table (CLHT) [34] and LevelDB’s Skip list [64]. Finally, we examine Boost’s implementations of a queue and a linked list. 

## 4.2 Porting to Memory Safe Hardware 

CHERI. For the CHERI purecap target, the compiler handles most of the portable C/C++ code. The compiler natively inserts capability-aware atomic operations, used in lock-free data structures. Three classes of issues require manual intervention. First, CHERI enforces 16-byte capability alignment, disrupting cache-aware de-signs designed to prevent false sharing or pack pointers densely. Second, traditional bit-wise pointer manipulation for custom align-ment discards capability metadata, triggering runtime violations. Third, pre-allocating a large region and subdividing it at runtime holds only a capability covering the entire range by default, pro-viding no sub-region safety. We resolve these issues by replacing alignment-dependent code (e.g., in Boost’s queue) with CHERI-native alignment functions, and narrowing the returned capability to each allocated block at the point of subdivision. 

MTE. Porting to MTE requires no changes beyond the memory al-locator. For data structures that rely on the system allocator, we use an MTE-enabled allocator (e.g., glibc’s Ptmalloc); the data structure code itself remains intact. Turning on tagging mandates glibc to support memory tagging (>2.33) and to set the GLIBC_TUNABLES 

environment variable to glibc.mem.tagging=3 .However, high-performance data structures often define their own allocators. We port these by modifying alloc/free functions to align pointers to 16-byte granule boundaries, assign a random tag to the pointer (using irg ), and, for larger allocations, iterate over the allocated memory range and set the allocation tag (with stg ). Another non-trivial case arises in data structures that encode links between elements as custom indices rather than pointers— our B-tree, for instance, stores parent-to-child links as Page IDs (PIDs) and reconstructs the pointer on every traversal. To minimize changes to the data structure design, we first reconstruct the pointer and then fetch the allocation tag using the ldg instruction. 

Takeaway: Retrofitting data structures for hardware safety extensions requires careful porting due to the pointer length and alignment assumptions. Porting to MTE is simpler, as most mod-ifications are in the allocators, whereas CHERI requires invasive refactoring to maintain capability provenance and alignment.

After seeing the overhead at the data structure level, we analyze the impact of CHERI and MTE across a representative set of database systems to examine whether these costs remain acceptable when MTE and CHERI are applied to full-fledged database systems under realistic workloads and how much engineering effort porting each system requires. Experimental parameters. We sweep both the working-set size and the thread count. ## 5.1 In-Memory Key-Value Store (Redis) 

Redis is a popular in-memory key-value store that caches clients’ data in an ordered fashion. Redis uses a hash table with separate chaining for collision handling and relies on jemalloc for superior performance and memory utilization in database workloads [43]. 

Porting. To port Redis to CHERI, we use the purecap port of Musl libc, with static linking to avoid mixed-ABI symbols. The main code changes involve replacing pointer casts to 64-bit integer types (e.g., 

unsigned long ) with (u)intptr_t to preserve capability metadata, and ensuring 16-byte capability alignment. One non-trivial issue arises when Redis exploits the contiguity of argv[0] through argv[argc] to write to a shared buffer via argv[0] . This trick is forbidden by the capabilities model, as each pointer is bound to its own allocation. We fix this by restricting the access to argv[0] alone. For MTE, we port the jemalloc allocator used by Redis. When allocating, jemalloc generates a new tag using irg and assigns it to the region, ensuring adjacent regions receive different tags. It reserves tag 0 for freed regions, and tags 1–15 for used memory.

## 5.4 Embedded Database System (SQLite) 

SQLite is an embedded relational (OLTP) database system. It pro-vides a SQL engine that interacts directly with disk files.and uses a B+Tree for table storage, with a default block size of 4 KiB. 

Porting. For CHERI, we follow the same process as in Redis. A no-table challenge lies in SQLite’s allocator, which adds 64 bits of meta-datato each allocation and returns a pointer to the region.Under CHERI, this pointer retains capabilities over the entire region , with the metadata, allowing buggy code to corrupt the allocator’s state. Restricting the capability to the user region prevents this, but requires the allocator to maintain a separate capability for meta-data access. To minimize code changes, we retain the unrestricted pointer returned by the allocator, which allows metadata access. For MTE, since SQLite relies on the system allocator, we use MTE-enabled glibc and avoid code modifications. However, MTE initialization via prctl must occur exactly once per process. Stan-dalone database systems can perform this initialization at startup; for embedded libraries such as SQLite, initialization must be han-dled either by the host application or by the library itself, in which case it should first check the active MTE state to avoid conflicts. 

Results. We execute a synthetic transaction workload on SQLite using tpcc-python [111], with 1–50 warehouses and measure trans-action throughput after 60 seconds. The throughput differences of both the MTE and CHERI ports remain within the measurements’ confidence intervals at all sizes, as depicted in Figure 12c.

## 5.6 Graph Database System (LadyBugDB) 

LadyBugDB is a graph database system, based on KuzuDB. It uses Compressed Sparse Row (CSR) indexing to store the graph topology, and uses analytical columnar format for node and edge properties. To avoid memory explosions and spills during graph traversals and joins, LadyBugDB leverages a factorized representation of interme-diate results, keeping data compressed in memory. 

Porting. For CHERI, we use the same CMake toolchain file that streamlines build system modifications and manually disable Scal-able Vector Extension (SVE) support, since the Morello board does not implement it, but the build system fails to detect it automati-cally. Beyond these configuration changes, LadyBugDB runs with-out code modifications under the CHERI purecap architecture. For MTE, we instrument LadyBugDB’s buffer manager’s existing get-Frame() function—which maps a frame or a page ID to a memory location—to tag the returned pointer before passing it to the rest of the system, making MTE fully transparent to the codebase. 

Results. We evaluate LadyBugDB using queries from the official LDBC Social Network Benchmark (SNB), sweeping scale factors 10– 100 and the thread count, which includes standard SNB queries and graph-specific operations (e.g., shortest-path search). As shown in Figure 12f, MTE introduces a geo-mean overhead of 9–14%, growing mildly with the thread count. In comparison, the mean overhead of CHERI is negligible across all configurations. The outliers can be explained by the value types. Queries over variable-length string attributes, which are dictionary-encoded and must be materialized in heap-allocated memory, cost 10% overhead, against 4% for queries over fixed-width numeric attributes of the same table. 55% of the additional cycles are spent in the dictionary scan and a further 29% in the allocator, whose cost doubles because every allocation must have its region tagged and re-tagged on free. 

Comparison with data structure analysis. Across all six systems, overheads are lower than for their underlying data structures (§4). The reason is that end-to-end execution also encompasses other tasks, including query parsing and planning, logging, etc. , which are typically less memory-intensive and amortize safety-check costs. System workloads exercise the whole database system, whereas our microbenchmarks isolate a single data structure operation. 

Takeaway: Porting full database systems exposes the difference between MTE and CHERI in terms of portability and performance. MTE offers a highly portable integration path with minimal mod-ifications to the allocator and maintains a low performance over-head of 5-10%. Conversely, CHERI demands deeper refactoring to correct memory alignments and capability provenance, which can hinder adoption if external dependencies are incompatible. Performance-wise, CHERI imposes a higher penalty, 20-60%, par-ticularly on write-heavy key-value stores.

## 6.1 Compiler Analysis 

For C and C++, clang [15] and gcc [11] forks exist for CHERI and Morello; MTE is also supported by both upstream compilers. Ongo-ing work extends CHERI support to other languages (i.e., Rust [59]). 

Programming model. CHERI compilers support both purecap 

mode, where all pointers are capabilities, and hybrid mode, where only explicitly annotated pointers are. To manipulate capabilities, the compiler exposes intrinsics for operations such as setting or clearing the validity bit, adjusting bounds or permissions, and seal-ing/unsealing. In contrast, MTE requires no pointer annotation, preserving the type system and ABI. The compiler exposes intrin-sics to manipulate logical tags and load or store allocation tags. 

IR representation and optimizations. CHERI’s LLVM fork rep-resents capabilities using a separate address space, allowing them to coexist with normal pointers in hybrid code while preserving most optimization passes. Certain passes that assume 64-bit point-ers must be disabled when compiling for capabilities. Further, at the time of writing, LLVM may miscompile capability comparisons by checking only addresses. Correct behavior requires treating ca-pabilities with potentially differing bounds, permissions, or validity as distinct. Otherwise, optimizations may be missed or produce miscompilations (Figure 14). In this example, foo is called with two capabilities with the same address but differing tags. Since q == p only checks addresses, the compiler concludes that q and p are interchangeable and may dereference the untagged q in place of p.Another constraint appears when storing capabilities in untyped byte arrays. For small copies, the compiler may replace memcpy 

with a load-store sequence if 16-byte alignment can be proven stati-cally. Code that stores capabilities in untyped byte buffers loses this guarantee, forcing a fallback to memcpy to preserve correctness. 

Compiler-driven safety. Typically, compilers insert instructions to automatically provide safety when compiling to memory-safe hardware. For CHERI, the compiler transparently creates capabil-ities with appropriate bounds for stack allocations; the dynamic linker handles references to globals, whose addresses are unavail-able at compile time. Subobject bounds narrowing (i.e., restricting a reference to a struct field or array element to its own bounds) is disabled by default for compatibility but is supported and can be enabled. This affects common database code patterns in which nodes store keys, payloads, and child pointers as subobjects. Our microbenchmarks, which create references to objects within an ar-ray, show no measurable performance difference between the two configurations; thus, enabling it globally is safe for most database code. Users can still opt out of subobject bounds narrowing for structs or fields where this leads to compatibility problems. For MTE, LLVM provides a stack and globals sanitizer, while GCC support is under development. Rather than tagging each stack variable individually, which would require padding every object to the 16-byte tag granularity, the entire stack frame receives a single tag, preventing stack overflows. Correct stack and global tagging require support in the entire toolchain. The compiler must insert tagging and untagging code on function entries, returns, and when unwinding stack frames after non-local control flow (e.g., exceptions, setjmp/longjmp instructions), while the dynamic linker must be MTE-aware to enable MTE for stack and global regions. Currently, only the Android toolchain supports this end-to-end. Figure 13 and Table 10 quantify the resulting code-generation changes across the evaluated systems. For CHERI, we see changes to instructions (e.g., ldr ) which now operate on capabilities, as well as new instructions (e.g., scbdns ) that manipulate capabili-ties. The large share of modified instructions means that the en-tire tooling stack, including debuggers and disassemblers, must be CHERI-aware to correctly interpret binaries. For MTE, in con-trast, the binaries contain few explicit instructions; in several sys-tems, most MTE-specific instructions reside in glibc rather than in the application. This highlights a key difference between the two mechanisms: CHERI changes pointer-carrying code throughout the binary, whereas MTE is limited to allocator and runtime support. 

Takeaway: Toolchain maturity is a major factor in the porting complexity. MTE is highly portable by retaining existing ABIs and relies mostly on libraries. CHERI alters the entire binary, requiring specialized toolchains and increasing the porting effort. 

## 6.2 Runtime Libraries 

Hardware memory safety is only effective if the software that man-ages memory cooperates with it. Two components are central: the Application Binary Interface (ABI), the binary contract that fixes pointer size and layout across compiled modules, and the memory allocator , which hands out pointers (or capabilities). We discuss the constraints each mechanism places on these components. 

ABI and binary compatibility. CHERI purecap binaries are ABI-incompatible with standard binaries. The generated ELF marks the ABI in a flag, and all linked libraries must be recompiled using the purecap ABI. As a partial solution, a hybrid ABI eases migration by allowing developers to introduce capabilities into unchanged code via pointer annotations. In contrast, MTE leaves the ABI unchanged, enabling adoption without recompiling dependencies. 

Exception handling. Stack unwinding recognizes signal frames by reading instructions at the return address and matching them against the kernel’s rt_sigreturn trampoline. Purecap forbids this be-cause the program counter carries execute but not load permission, so inspecting code as data faults. Unwinders must instead obtain the bytes indirectly, e.g. , through a system call, which requires significant changes to the library implementation. As a result, we could not get exception handling working in our purecap builds. The database systems are unaffected, as they compile with -fno-exceptions .

Temporal memory safety. CHERI can enforce temporal safety via capability revocation [45, 140, 143]. Freed regions are quaran-tined until a privileged capability revocation pass invalidates their capabilities, preventing use-after-reallocation . In contrast, MTE can retag freed memory, probabilistically invalidating existing pointers. As tags are finite, a reallocated region may receive the same tag as a dangling pointer, leaving stale accesses undetected. Allocators can reduce, but not eliminate, by delaying reuse through quarantine. 

Takeaway: Hardware-assisted memory safety extensions place a significant performance and complexity burden on the mem-ory allocator. CHERI inflates the memory footprint of pointer-heavy database systems by up to 66%. Similarly, MTE changes the complexity of memory allocations to O( 𝑛 ), which can impact allocation-heavy database systems.

## 6.4 Coverage of Memory-Safety Bug Classes 

Finally, we evaluate how MTE and CHERI protect against the classes of bugs that we identified in our bug study §2.1. We reproduce each class that our classifier considers memory-safety-related (§B), i.e. 

including buffer overflows, out-of-bounds accesses, use-after-free, null pointer dereferences, as small test cases. We run each case 200 times without protection, with MTE, and with CHERI, and report in Table 11 whether each class is detected at the faulting access. 

Spatial safety. CHERI deterministically detects heap, stack, and global overflows and out-of-bounds accesses. In comparison, MTE Should Your Database Systems Use Hardware-Assisted Memory Safety Extensions in Production? Proc. ACM Manag. Data 4, 6 (SIGMOD), Article 378, December 2026 

protects only the heap, at the 16-byte granularity of its tags, and detects an access landing in another object only if both objects carry different tags. This behavior leads to probabilistic safety, where MTE catches 89% of the out-of-bounds accesses in our test scenario, due to tag collisions. 

Temporal safety. MTE retags freed memory, so a use-after-free faults deterministically until the memory is reallocated and prob-abilistically afterwards. CHERI requires capability revocation to detect use-after-free, which CheriBSD supports but Morello Linux does not (§6.3). Both mechanisms catch double frees. 

Null pointers and uninitialized memory. Without protection and with MTE, which only checks tags within tagged mappings, a null pointer dereference is stopped only because the OS leaves the first page unmapped. CHERI turns it into a capability fault at the faulting access: a null pointer carries no valid capability, so even accesses at large offsets from NULL , which may land in mapped memory without protection, are rejected. Uninitialized memory ac-cesses are not detected by any mechanism, as neither tracks whether memory was written: a new allocation still exposes the previous owner’s data. Allocators can close this gap by zeroing memory on allocation, for example by using special MTE instructions that tag and zero memory in a single operation, i.e. stzg (§3.2). 

Takeaway: Without protection, the reproduced bugs silently corrupt or leak data, or are caught late by allocator checks, consis-tent with the crashes, incorrect results, and corruption of our bug study. MTE and CHERI instead stop most of these bug classes at the faulting access, before corrupted data propagates. CHERI deterministically enforces spatial safety but needs OS support for temporal safety, whereas MTE covers spatial and temporal heap bugs, but probabilistically and without protecting stack and global memory. Neither detects uninitialized memory accesses. 

## 7 Related Work 

Software-based approaches. Significant work has been done to retrofit memory safety into existing codebases written in unsafe languages. Trip-wire-based approaches pad allocations with inac-cessible guard regions to catch out-of-bounds accesses [54, 120, 121]. Object-based approaches associate metadata, stored in disjoint ta-bles or shadow memory, with an object, enforcing spatial safety via bounds checks on pointer manipulation and temporal safety by invalidating stale metadata [21, 27, 55, 60, 62, 85, 86, 105]. Pointer-based approaches embed metadata inline (e.g., fat pointers) or in separate memory regions, tracking all pointers to enforce temporal safety, and checking bounds on every access [40, 41, 73, 74, 102, 124, 146]; some approaches also combine per-pointer and per-object metadata [128, 139]. Orthogonal techniques include static analy-sis [39], parallelization of checks [150], and protection against mem-ory error exploits via safe control-flow [17, 75] and software-based fault isolation [26, 58, 136, 147, 148]. Additionally, safe languages or dialects enforce memory safety at the type system [3, 67, 104]. Software approaches incur performance overheads that are prohibi-tive in production database deployments, a gap our work quantifies and motivates through hardware-assisted alternatives.

## 8 The Database Systems Trilemma 

This paper presents the first side-by-side, cross-layer comparison of MTE and CHERI on a database workload suite, spanning from microarchitecture through an indexed-data-structure layer to full systems. We investigate the answers that MTE and CHERI offer to the memory safety trilemma (§2.2) across micro-architectural analysis, data structures, and full-fledged database systems. We summarize our findings in Table 12 and compare against software-based approaches and memory-safe languages in Figure 16. The two extensions take different approaches. CHERI provides strong, deterministic guarantees by enforcing pointer bounds, per-missions, and unforgeability. It detects spatial violations, including out-of-bounds accesses and buffer overflows, provides temporal safety through capability revocation, and catches intra-object over-flows when the compiler narrows sub-object bounds. By contrast, MTE detects the same bug classes probabilistically and cannot de-tect intra-object overflows. Neither mechanism catches type confu-sion, valid-but-incorrect pointer use, or other logic bugs. This divergence inversely correlates with performance: CHERI imposes significant overheads (20–60%) across database system workloads, whereas MTE’s average overhead is moderate (5–10%). Finally, the invasiveness of the two solutions dictates their practical portability. MTE requires minimal changes to the build and deploy-ment pipeline because it is fully supported by current toolchains. On the other hand, the CHERI toolchain introduces considerable com-plexity due to the fundamental change in pointer size. Its purecap ABI also requires compatible builds of all dependent libraries, which demands significant engineering effort for use in large, dependency-heavy applications like database systems. Overall, MTE and CHERI show that the Pareto frontier has moved beyond what software-based approaches can offer, making hardware enforcement a viable path to production-grade memory safety in database systems.

## A Additional Architectural Analysis A.1 MPK 

Experimental Setup. We evaluate Memory Protection Keys (MPK) on a dual-socket Intel Xeon Gold 6438Y+ CPU with 32 cores per socket and 2 threads per core, featuring 2 TiB of memory, running NixOS 25.05 and Linux 6.0.0. Each core features 32 KiB of L1i cache, 48 KiB of L1d cache, 2 MiB of L2 cache, while each core additionally features 60 MiB of L3 cache. 

Mechanism. MPK introduces a per-thread isolation mechanism on a page-level granularity. Four unused bits in the Page Table Entry (PTE) specify one of 16 distinct protection keys. Each thread then specifies its access rights in the thread-local PKRU register, which holds two bits for each key, specifying read and write permis-sions. This allows for very fast switching of access rights, compared to mprotect system calls. Code using MPK allocates a new protection key by calling pkey_alloc . pkey_mprotect associates a protection key with a memory region, while pkey_free marks the key as free again. To mirror mprotect ’s model, user-space code must synchro-nize the PKRU register between threads [110]. MPK complements mprotect ’s permissions: With mprotect , users can select between five permissions: inaccessible, read-only, read-execute, read-write, and read-write-execute. Execute-only is not possible. Conversely, MPK allows to enable read or write permissions. The effective per-mission is that of the intersection of the page table entry and the PKRU register. Using MPK allows to set a page to execute-only, by disallowing reading through MPK. However, MPK imposes some drawbacks: As the number of keys is limited to 16, allocating new keys may fail. Freeing keys does not invalidate existing keys, allowing for key use-after-free scenarios where pages using the freed are accessible using the reallocated key. We evaluate the overheads of MPK, in particular the cost of reading, writing, and updating the PKRU register, as well as the cost of the newly introduced system calls in Table 14. As accessing the PKRU register is thread-local and done in user space, it performs very well. Updating the permissions com-pletes in under 19 cycles. The system calls are much more expensive, taking around 270 cycles to allocate or free a protection key and around 450 cycles to change the protection key of a memory page.

## B.5 Result Analysis 

Our analysis scripts produce a set of complementary statistics that we collect to gain confidence in the results presented in §2.1. The full outputs are retained for validation and manual inspection. More precisely, our analysis produces two types of output: 

Aggregate statistics. For each database and each repetition, we extract: the total number of entries processed; the count classified as bug , programmer error , or other ; and the subset flagged as a memory safety bug. The keyword set size is gathered in parallel as an independent baseline. Tracking these numbers across all three repetitions allows us to assess the stability of the classifier and identify any significant variation between runs. 

Intersection analysis & result validation. We compute all non-empty intersections across the four signal sets (Keywords, LLM repetition 1, LLM repetition 2, LLM repetition 3), to observe the 

exclusive contribution of each subset combination (i.e., entries that appear in exactly that combination and no other). This reveals the degree of agreement between the keyword heuristic and the LLM classifier, and quantifies how consistently each entry is flagged across repeated classifications. Note that the keyword set serves here as a comparative signal only; the confirmed memory safety count is derived exclusively from the three-way LLM intersection, as this produced more accurate results. Finally, to further validate the automated classification, we conducted a manual inspection of a sample of flagged entries, cross-checking titles, descriptions, and LLM outputs against the expected classification. 

Limitations. This pipeline is a motivating analysis, not a validated vulnerability classifier, and its numbers should be read as estimates. We use a quantized (Q4_K_M) gpt-oss-120b model rather than a full-precision frontier model, and we do not report precision, recall, or inter-annotator agreement against a manually labeled ground-truth set; dedicated works such as DUALLM [81] provide such validated baselines. Our three-way agreement rule—counting a report as a memory-safety bug only when all three runs concur—has two dis-tinct effects. The first concerns coverage : requiring agreement filters out reports that only one or two runs flagged, i.e., the cases the model classifies inconsistently. These borderline cases are dropped Proc. ACM Manag. Data 4, 6 (SIGMOD), Article 378, December 2026 Meignan--Masson et al. 

from the counted set, so the rule trades away some coverage in exchange for a set of entries that is more likely to be correct. The second concerns confidence : one might hope that three runs act like three independent judgments, so that a mistake in one run is caught by the others. This does not hold here, because we sample the same model three times. When such a model is uncertain about a case, it tends to make the same error on every run rather than a different one each time, so the runs are correlated rather than inde-pendent [28]. Agreement across runs therefore reflects the model’s consistency, and provides less assurance than three genuinely inde-pendent judgments would. We also classify issue-tracker reports and CVEs only, and exclude fixes that land as pull requests without an associated issue (§B.2); issue-text-only classification is known to be weaker than classification that also ingests commit messages and diffs [81]. Consequently, our claims concern memory-safety 

reports rather than all memory-safety bugs. Finally, MySQL’s bug tracker redacts security-sensitive issues, so memory-safety bugs for MySQL are systematically under-reported in the source we scrape, which partly explains its low memory-safety share in §2.1.
