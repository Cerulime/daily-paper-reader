## Abstract 

Commercial on-device network operating systems (NOSes) run complex control planes in production routers and switches, where configuration update tasks are executed by multiple loosely coupled components through asynchronous message passing. Such executions are prone to race conditions: the same ordered input commands may produce different out-comes when messages are delivered in different orders. The race conditions are difficult to expose because they often manifest only as subtle, delayed malfunctions. Existing static analysis techniques lack scalability and precision for large-scale industrial NOSes, while dynamic ones incur substantial system-execution cost when attempting to cover the space of asynchronous message interleavings. To address the challenges above, we present NosRacer, a dynamic analysis framework for race condition detection in industrial-grade on-device NOSes. NosRacer uses a two-phase design. The concentration phase reduces analysis scope by leveraging the locality of configuration update tasks. Race condition detection is then limited to a small subset of involved components and crucial state variables, thereby reducing the detection cost. The perturbation phase proactively perturbs message asynchrony to increase the like-lihood of executions with race-condition-exposing message interleavings. It keeps perturbation practical by grouping compatible perturbations for parallel execution and adap-tively strengthening perturbations. We implement NosRacer in a commercial, actively devel-oped NOS. NosRacer is integrated into the existing testing factory and used to detect race conditions in 5 key control-plane components. NosRacer achieves 66% precision and detects 21 race conditions confirmed by developers as severe bugs, while keeping the detection overhead below 10%.

## 1 Introduction 

Commercial on-device Network Operating Systems (NOSes), such as Cisco IOS XR, Juniper JunOS, Huawei VRP, and SONiC, are complex software stacks deployed on produc-tion routers and switches [6, 18, 21, 52]. In a typical NOS control plane, protocol and management functions are imple-mented by tens to hundreds of loosely coupled components, which coordinate with one another through asynchronous messages [19, 20, 51]. Configuration updates are routine operations in produc-tion NOSes, e.g., due to topology changes, traffic dynamics, and policy revisions [24, 47, 62]. As shown in Figure 1, one configuration update task typically consists of an ordered sequence of configuration commands. These commands are processed by multiple control-plane components, which in-teract through asynchronous messages, in order to validate, propagate, and realize the requested state changes. Correct execution of the configuration update task is of vi-tal importance to the NOS control plane [22, 54, 55]. However, ensuring correct execution of the task is greatly hampered by the race condition problem [40]. That is, in different ex-ecutions of the same update task, asynchronous message passing may result in different ways of coordination among components, thus producing different update results. Race conditions typically do not manifest immediately as user-visible system anomalies. Instead, they manifest themselves in silent and subtle malfunctions, e.g., a subscription quietly lost, a state left stale, or a downstream notification missed [34, 35, 55]. By the time severe network failures occur, it is

Race conditions are notoriously difficult to detect and fix in various concurrent and distributed systems [5, 23, 32, 39]. In NOSes, though each component under-goes extensive unit, integration, and stress testing, these tests mainly validate component-wise functional correctness [50, 53, 60]. Race-condition checking is still insufficient. We analyzed the anomalies observed in a large-scale production NOS deployment (2021~2024). Among all the 53 issues clas-sified as “message timing related", 27 issues were caused by race conditions, as confirmed by the testing engineers. The race condition problem has been extensively stud-ied in concurrent programming [9, 10, 45] and event-driven programming [15, 31, 38, 44]. Both static [1, 14] and dy-namic [45, 63] analysis techniques have been developed. In this work, we study how to cope with race conditions in a production NOS with 200+ control-plane components, each typically containing 5k+ variables and 10k+ functions. At this scale, existing static analysis techniques face severe scal-ability challenges, and their precision is also limited [14, 29]. Although dynamic analysis techniques can improve accuracy by using concrete execution information, the enormous num-ber of possible asynchronous executions makes the system-execution cost unacceptable [28, 39, 42]. To unearth race conditions in a production NOS, we pro-pose the dynamic analysis framework NosRacer. The core innovation of NosRacer lies in its two-phase design. The 

concentration phase substantially reduces the detection cost, while the perturbation phase improves its effectiveness in exposing race conditions, as detailed below.

Concentration. In the concentration phase, the key issue is to cope with the complexity of an industry-grade NOS. NosRacer first leverages the existing testing factory of the target NOS to run a small subset of closely related test cases and concentrate on a small subset of components in the NOS. This is motivated by the observation that configuration update tasks exhibit locality, i.e., each task typically involves only a limited number of components. Among the 27 race-condition-induced bugs we studied, every task involves no more than 8 of the 200+ components, and 80% involve at most 5. After identifying the components involved in a configura-tion update task, NosRacer then leverages static analysis to concentrate on a small subset of crucial variables in compo-nent implementations. This is based on the observation that, in essence, the configuration update is the update of the cru-cial state information of the involved components. Such state is typically stored in a small set of crucial variables in the component implementations. Tracking reads and updates on the variable values can help us efficiently detect race condi-tions. That is, if the crucial state information variables are accessed by concurrent operations in asynchronous message handlers, potential race conditions can occur. 

Perturbation. The major obstacle to effective race condi-tion detection in NosRacer is the enormous space of possible system executions induced by asynchronous message inter-leavings. As a dynamic analysis tool, NosRacer must care-fully plan system executions to keep the overheads under control. To address this obstacle, NosRacer proactively per-turbs the asynchrony of message passing, thereby increasing the likelihood of test executions with the specific message in-terleavings needed to expose race conditions. In a statistical sense, the perturbation is expected to consistently reproduce the race condition until it is fixed. If the update tasks can

NosRacer consolidates perturbations within the same test execution whenever possible, thereby conserving the limited testing budget. However, two factors fundamentally affect the efficiency of perturbation. In industrial-grade NOSes, NosRacer lacks fine-grained control over message-passing perturbations. As a result, dif-ferent perturbations may conflict with one another. Nos-Racer groups compatible perturbations within the same test execution and dispatches multiple groups of perturbations to the testing factory for parallel execution. A perturbation may also fail to produce a perturbed execu-tion with the message ordering required for race condition detection. Based on failed perturbed executions, NosRacer adaptively strengthens the perturbation to improve the like-lihood of successful race condition detection. Due to the side effects introduced by imprecise perturbation, increasing the perturbation strength is not always beneficial. Excessive perturbation may drive the system execution away from the original execution, rendering it ineffective for race con-dition detection. NosRacer estimates an upper bound on perturbation strengthening by statically analyzing how time-out mechanisms are implemented in the system. NosRacer further uses a small number of perturbed executions to em-pirically estimate this upper bound. 

Key results. We evaluate NosRacer on 5 control-plane components of a commercial on-device NOS (200+ compo-nents, 100M+ LOC, 200,000+ test cases). It detects 15 new race conditions and reproduces 6 known ones, with a pre-cision of 66%. All 21 bugs have been fixed. The deployment and usage cost of NosRacer is no more than 20 person-days, and the increase in testing cost is less than 10%. 

Summary. This work makes three main contributions. 

• We propose NosRacer, a dynamic analysis framework for race condition detection in configuration-update scenarios in industrial-grade NOSes. 

• We implement NosRacer in a commercial NOS under ac-tive development and integrate it into the existing testing factory. 

• We apply NosRacer to detect race conditions in 5 com-ponents of the NOS under test, and present detailed eval-uations showcasing the effectiveness and efficiency of NosRacer. 

## 2 NosRacer Happen-Before Model 

At the core of race condition detection lies the problem of rea-soning about the temporal ordering relations among shared-resource accesses [26]. This section defines the happen-before model behind NosRacer. It first defines the configuration update task, and then the happen-before relation between operations in the task. The definition of a race condition naturally follows from that of the happen-before relation. 

2.1 Configuration Update Task 

Configuration updates are routine in production NOSes. A 

configuration update task consists of a sequence of configu-ration update commands issued by upstream components in the NOS control plane. A task is carried out by multiple com-ponents that coordinate through asynchronous messages. In each run, NosRacer selects one task and designates one component involved in the task as the target component .NosRacer analyzes race conditions on a per-component ba-sis because components constitute the natural ownership and concurrency boundaries in the NOS control plane. This design improves effectiveness by localizing potential race conditions to the state variables and message-handling logic of individual components. The detection of race conditions utilizes the asynchronous interaction between the target component and the interacting components . Instead of rea-soning about all possible shared-resource accesses and mes-sage interleavings at the system level, NosRacer restricts the analysis to a small subset of components, thereby reducing the search space. Since components interact via message passing, compo-nent execution follows an event-driven model. Upon the delivery of one message, the component will initiate the corresponding message handler to process the message. The message handler consists of two types of operations. One is local operations, which mainly read and update local in-formation of the component. The other is message-sending operations, which result in message handler execution in another component. The key to race condition detection is the reasoning about the temporal happen-before relations among operations in message handlers, as defined in detail below.

2.3 Race Condition 

In a configuration update task, a race condition [40] is char-acterized by the fact that the same task may lead to different outcomes under different message orderings. 

Crucial variable. For a configuration update task, the core logic of a component is to update the various states it holds throughout the configuration update process. The intermedi-ate state of a component is maintained through variables that encode the state information. We call such variables crucial variables . Once we concentrate on crucial variables, the race condition detection problem reduces to determining whether a crucial variable may be concurrently updated. Concurrent update operations on a crucial variable can potentially be

Severity of a race condition. When race conditions are detected, test engineers are primarily concerned with the severity of the race condition, i.e., how the effects of a race condition propagate and are amplified through subsequent component executions. In this work, the severity assessment (§3.3) primarily focuses on whether a race condition affects the subsequent sequences of message-sending operations and message handler function calls. 

## 3 NosRacer Framework 

NosRacer is a dynamic analysis framework for race condi-tion detection. The practical deployability of NosRacer in industrial-grade NOSes stems from two key technical innova-tions, as shown in Figure 3. In the concentration phase, Nos-Racer tackles the scalability limitations of existing static and dynamic analysis techniques. In the perturbation phase, by amplifying the asynchrony of inter-component message in-teractions, NosRacer proactively constructs execution con-ditions that expose race conditions. 

3.1 Concentration 

The concentration phase serves two primary purposes: reduc-ing hundreds of components to a small subset, and thousands of component-state variables to tens or hundreds of crucial ones, as shown in Figure 1. 

3.1.1 Identification of interacting components. Our inspection of existing test executions provides the intuition that a configuration update task typically involves only a small subset of components. We conducted a comprehensive empirical study of the latest bugs related to configuration updates. The study confirms our intuition. Among 27 real-world bugs we analyzed, all involve no more than 8 interact-ing components, and 22 involve no more than 5. According to our study, NosRacer efficiently identifies the interact-ing components of the pre-specified target component, by running test cases of configuration update tasks. Note that, static analysis alone cannot precisely identify all interacting components for a given target component, because component interactions are largely determined by runtime message routing, system state, and asynchronous ex-ecution order. Although static analysis can over-approximate potential interactions, such an approximation often includes an excessive number of irrelevant components and thus pro-vides limited scalability benefits in the concentration phase. In the testing factory, each test case is annotated with rich functional labels. NosRacer uses the functional labels to se-lect test cases pertaining to the target component. Moreover, the test case profiles provide coverage statistics for the target component. The selected test cases are prioritized accord-ing to the coverage statistics. 3.1.2 Identification of crucial variables. A target com-ponent may contain a great number of configuration update-related variables (typically more than 1,000 in the NOS stud-ied in this work). However, most of such variables are ir-relevant to the inter-component message interactions. Nos-Racer identifies a variable as crucial, when it is accessed by multiple message handlers and at least one updates the variable value. Analysis of crucial variables starts from the message handler executions recorded in the test executions in the previous step (§3.1.1). NosRacer uses the Abstract Syn-tax Tree (AST) to provide a structured representation of the message handling logic, allowing NosRacer to identify vari-able declarations, read/update accesses, and message passing operations. By analyzing these syntactic structures together with component-level execution contexts, NosRacer can statically identify variables which are potentially shared across asynchronous executions and may therefore give rise to race conditions. For each identified variable, NosRacer records the access sites together with their enclosing func-tions. Our choice of an AST-based approach is motivated by the following subtle tradeoffs. Compared with Intermediate Representation (IR)-based techniques, AST-based analysis preserves source-level program structures and can be applied with lower engineering and computational cost, making it more scalable for industrial-grade NOS codebases. It allows NosRacer to efficiently identify access sites of critical vari-ables and relevant message-handling logic. However, AST-based analysis provides limited semantic information and is less precise in reasoning about aliasing, inter-procedural data flow and synchronization. In contrast, IR-based analysis enables more precise semantic reasoning, but often incurs a higher deployment and analysis cost in large production systems. 

3.1.3 Preparatory test executions. Given the crucial variables, NosRacer needs concrete test executions to deter-mine whether the crucial variables are updated by concurrent message handlers. NosRacer leverages coverage informa-tion in test case profiles to select test cases that cover func-tions containing crucial-variable access sites (as recorded in the previous step in §3.1.2). NosRacer greedily selects the test case that covers the maximum number of uncovered crucial-variable access sites, until all the sites are covered. Given the test executions, NosRacer constructs the graph of operations in the test execution traces. NosRacer pairs sends and receives using message hashes recorded at the send/receive APIs. The operations are modeled as graph nodes, and an edge is added between two operations if these two operations are ordered by the happen-before relation defined in §2.2. Based on the operation graph, NosRacer can decide the concurrency between message handlers, and thus can detect concurrent accesses on crucial variables. This graph lets NosRacer determine concurrency without adding logical timestamps to messages. NosRacer uses the concur-rent accesses to construct subsequent perturbed test execu-tions.

As the delay increases, NosRacer soon fails to observe the original concurrent accesses in the resulting test executions. 3.3 Detection and Validation 

NosRacer first performs preparatory test executions to iden-tify suspected race conditions, i.e., concurrent accesses. Nos-Racer then constructs perturbed executions as evidence to confirm these suspects. 

Precision analysis. In the ideal case, NosRacer is complete, in the sense that every race condition it confirms is a real one, assuming that its model of the NOS under test is accurate and complete. In real-system deployments, NosRacer does not provide strict soundness or completeness guarantees. Nevertheless, by confirming race condition suspects through perturbed executions, it produces high-precision race condition reports in practice, as shown in the experimental evaluation (§5). 

Severity assessment. Detected race conditions are submit-ted to NosRacer users, i.e., testing engineers and developers, for severity assessment. Severity assessment is primarily based on comparing the behaviors of the original and per-turbed test executions. The severity of each reported race condition is measured by how quickly and to what extent it leads to user-visible abnormal program behavior. Specifically, we consider three measures of severity: 

• First point of divergence . NosRacer identifies the earliest subsequent behavior at which the original and perturbed executions deviate. For NosRacer users, the first point of divergence provides a concrete starting point for under-standing the impact of a detected race condition. It helps developers localize the propagation of the race condition, and prioritize severe cases. 

• Divergence in outgoing-message sequences . Analyzing di-vergence in sequences of outgoing messages helps Nos-Racer users understand whether and how the effect of a race condition propagates beyond the component where it occurs. Since NOS components interact primarily through asynchronous messages, such divergence shows how the race condition has altered the interaction among compo-nents. 

• Divergence in message-handler sequences . Comparing mes-sage handler sequences across executions helps NosRacer users understand how a race condition affects the subse-quent control-plane execution. Since NOS components are message-driven, the message handler sequences provide a high-level view of how components process messages during a configuration update task. Divergence in these sequences indicates how the race condition has affected the execution path within a component. 

3.4 Discussions 

The current design of NosRacer incorporates several simpli-fications motivated by practical considerations. Specifically, with respect to the monitored objects, NosRacer currently focuses on simple crucial variables. Beyond simple crucial variables, NosRacer also needs to investigate how to handle complex data structures and database entries. With respect to the properties being monitored, NosRacer currently fo-cuses on crucial variables and behavior differences observed within test executions. Extending its observation model to include cross-component invariants, configuration consis-tency properties, and richer state correlations may expose a broader class of race conditions. Moreover, richer perturba-tion mechanisms, such as controlled message reordering or runtime support from messaging middleware, can improve the success rate of constructing race-exposing executions. However, enhancing the perturbation mechanism requires a broader assessment of its system-wide impact. The current design and implementation of NosRacer rep-resent the first step in a longer-term effort. Going forward, we will leverage empirical data collected from practical de-ployment (§4) and evaluation (§5) to guide our efforts in addressing the above limitations and developing the next generation of NosRacer. 

## 4 Implementation and Integration 

We first describe the NosRacer implementation of dynamic tracing and analysis, followed by the integration into an industrial-grade NOS. 

Implementation. NosRacer is implemented as a dynamic analysis tool for NOS control planes, centered on runtime tracing and offline analysis. Runtime tracing relies on Clang-based source instrumentation [33]. The generated hooks in selected NOS components record crucial-variable accesses, message exchanges, and the execution context. Message sender-side hooks also inject message delays during per-turbation executions. Offline analysis enables perturbation planning and race condition detection. It identifies concurrent accesses on cru-cial variables, derives delay rules for perturbation executions, and compares original and perturbed executions for race condition detection. Within each execution, offline analysis distinguishes runtime instances using the source-level vari-able identifier and object address. Since object addresses may change across executions, it matches original and perturbed accesses using the variable identifier and recorded execution context, including message context and access call stacks. The NosRacer implementation consists of over 9,000 lines of C/C++ code and 25,000 lines of Python code. Appendix C provides the implementation details. 

Integration. NosRacer is integrated into the testing fac-tory of the target NOS. Its deployment has been active in the production Continuous Integration (CI) pipeline for over 3 

> 8

months, and covers 5 control-plane components. The test-ing factory executes system-level test plans on virtualized network topologies, persistently stores test artifacts, and publishes test results for further analysis, as detailed in Ap-pendix A. To integrate NosRacer into the testing factory, an orches-trator manages each NosRacer run as a dependency graph of test executions and offline-analysis steps. The orchestrator submits test plans to the factory, retrieves test artifacts for analysis, and submits follow-up plans generated from anal-ysis results. Appendix B presents the detailed orchestrator workflow of NosRacer. Applying NosRacer to a new target component only re-quires the component name, functional labels for relevant configuration-update tests, and optional hints about related components or tasks. Preparing this configuration typically takes less than 30 minutes per component. 

## 5 Evaluation 

In this section, we evaluate the performance of NosRacer with respect to the following questions: 1) How effective is NosRacer in detecting race conditions and finding bugs? (§5.1); 2) How efficient is NosRacer? (§5.2). We evaluate NosRacer on 5 target components in a pro-duction on-device NOS. ARP [43], DHCP [8], and VRRP [30] are protocol-derived labels for components that provide pro-tocol/application services. MGR-A and MGR-B are anonymized labels for components that provide device-state orchestra-tion services. Each component contains more than 500k lines of code, and the testing factory provides more than 5,000 related configuration-update test cases per component on average. For each target component, NosRacer runs 200 prepara-tory executions. Each preparatory execution gives rise to 3–5 perturbation groups on average, due to conflicts between per-turbations. These groups are submitted as parallel perturbed executions. For unsuccessful perturbations, NosRacer per-forms up to 3 rounds of perturbation strengthening. The experiments mainly evaluate the effectiveness and efficiency of NosRacer. The effectiveness evaluation focuses on three aspects: NosRacer’s ability to detect race condi-tions, the severity of the detected race conditions, and the rate at which they are confirmed as real system bugs. The effectiveness evaluation further examines how perturbation strengthening affects the ability of NosRacer to detect race conditions. The efficiency evaluation focuses on the over-head incurred by NosRacer in detecting race conditions, and specifically evaluates the contribution of the concentration phase to overhead reduction. 

5.1 Effectiveness 

Across the 5 target components, NosRacer generates 32 race condition reports, each accompanied by severity assessment results to support developer review. Developers confirmed 66% (21 out of 32) of the reported race conditions as severe bugs. NosRacer exposed all 21 confirmed bugs using existing tests, even though the same tests had repeatedly passed in the testing factory. Among the 21 developer-confirmed bugs, 15 were previously unknown, and 6 were known bugs which were recently reported and were still open at the time. The severity assessment results provide effective guidance for developers to understand the downstream impact of the race conditions and locate the relevant buggy code fragments. All 21 confirmed bugs have now been fixed. Given the effectiveness of NosRacer as evidenced by this round of testing-factory deployment and integration, the development team is applying NosRacer to more control-plane compo-nents in our target NOS, as well as to other production NOSes having similar architecture.

5.1.2 From concurrent accesses to race conditions. 

The results show a substantial reduction from observed con-current accesses to the race conditions reported by Nos-Racer. Across the 5 components, NosRacer observes over 800 concurrent accesses, with at least 120 in every compo-nent. 5.3 Discussion 

Our evaluation highlights the strengths and limitations of NosRacer, and offers guidance for improving its design and practical effectiveness. 

5.3.1 Benign race conditions. In the evaluation, devel-opers classified 6 reported race conditions as benign. We inspected their feedback to understand why these reported race conditions are not classified as bugs. The first reason is that differences in crucial variable values may not vio-late the correctness invariant of the current configuration update task. For example, in a VRRP switchover task [30], several physical routers are configured for the same virtual router with one virtual IP address. The correctness invari-ant is that exactly one of them should be the active router for that virtual router. A different handler order may make NosRacer observe a different role value on one router for the same switchover task. If the group still has exactly one active router, developers classify the report as benign. 

> 11

The second reason is that some components use periodic synchronization or retry to maintain consistency with up-stream components or configuration databases. In several reports, developers explained that the value difference may cause a transient intermediate abnormal state, but later syn-chronization or retry rewrites the affected variable and re-stores the normal state. Developers therefore did not treat the report as requiring a fix. To cope with benign race conditions, a possible improve-ment is to provide, during offline analysis, an interface through which developers can specify system-specific correctness in-variants over crucial variables. These invariants can then be used to filter out benign race conditions. 

5.3.2 Perturbation Effectiveness. NosRacer obtained corresponding perturbed accesses for only 19% of the concur-rent accesses (157 out of 824). To understand this reduction, we inspected the concurrent accesses not paired with per-turbed accesses. For each of these concurrent accesses, we measured the time span between the configuration update commands. The time spans between commands were usually large: less than 10% had a 1~5 second span, about 25% had a 5~10 second span, and over 60% had a span above 10 seconds. A long time interval between commands limits the effects of message delay injection. In our perturbation strengthen-ing experiments, delays above about 5 seconds often drove executions into timeout or retry paths. NosRacer then of-ten failed to observe the same concurrent access occurrence. This observation suggests that improving perturbation effec-tiveness requires test cases that place related configuration commands closer together. A practical approach is to derive such test cases from existing ones. For example, a test case can apply, withdraw, and then re-apply the same configura-tion command, so that state changes occur within a shorter interval. This gives NosRacer a better chance to obtain the corresponding perturbed access, while the side effects of delay injection remain under control. 

## 6 Related Work 

Existing testing techniques have limited effectiveness in race condition detection for concurrent and distributed sys-tems. In particular, system-level stress testing relies on non-deterministic scheduling and therefore cannot systematically explore rare message interleavings [3, 28, 39]. Formal meth-ods establish rigorous correctness guarantees through theo-rem proving or model checking under a formal specification [13, 27, 41, 49, 57, 59]. However, in industrial NOSes, for-mal verification is often impractical, due to its high learning curve and substantial adoption cost [2, 12, 17]. To address these limitations, prior work has explored both static and dynamic approaches for detecting race conditions in concurrent and distributed systems. Static analysis tech-niques are widely used to detect race conditions in concur-rent programs, often based on lockset analysis or happens-before inference [1, 9, 58]. Such techniques are further ex-tended for race condition detection in asynchronous event-driven programs [16, 31]. However, production NOS con-trol planes consist of loosely coupled components that com-municate through asynchronous messages. Existing static analysis techniques must conservatively over-approximate possible message interleavings and execution paths, lead-ing to combinatorial path explosion [4, 31]. This severely limits their scalability on production NOSes with million-line-scale codebases. Static analysis techniques also suffer from limited precision. Recent studies show that static de-tectors on large system codebases still produce substantial false positives that require manual validation [14, 23, 29]. Production NOSes widely employ customized optimizations, such as priority message queues and batched state commits, which further hinder existing static analysis techniques from precisely detecting race conditions. NosRacer uses static analysis primarily to identify crucial variables and message-interaction perturbation points. Race condition suspects are identified mainly from dynamic execution information and confirmed through perturbed executions. Dynamic analysis techniques improve the precision of race condition detection by observing concrete runtime be-haviors and execution states [10, 25, 44–46, 48, 63]. However, applying dynamic analysis to production NOSes remains challenging due to the high cost of executing complex dis-tributed control-plane workloads and the enormous space of possible message interleavings. Deterministic simulation and systematic exploration techniques have been proposed to improve interleaving coverage in concurrent and distributed systems [7, 11, 28, 42, 56, 61]. However, exhaustive deter-ministic control incurs substantial runtime and engineer-ing overhead, making such approaches difficult to deploy in industry-scale NOSes. In contrast, NosRacer employs probabilistic delay injection at carefully selected execution points to efficiently expose race condition-prone asynchro-nous interleavings while maintaining low execution over-head. Existing distributed concurrency-bug detectors iden-tify suspicious accesses or message orderings from recorded executions, and validate them through runtime triggering [32, 36, 37]. Recent work further uses static analysis to guide test generation for such bugs in RPC-based distributed sys-tems [5]. In both cases, bug validation largely depends on visible failure symptoms. In NOS configuration update tasks, however, race-condition-induced bugs often corrupt control-plane state silently [34, 35, 55]. NosRacer therefore makes this silent corruption observable to developers by reporting crucial-variable value differences and subsequent behavioral differences. 

> 12

## 7 Conclusion 

In this work, we present NosRacer, a dynamic analysis framework for race condition detection in on-device NOSes. NosRacer tackles the problem with a two-phase design. The concentration phase reduces the analysis cost by exploiting the locality of configuration update tasks, while the perturba-tion phase proactively perturbs the message asynchrony to confirm race condition suspects. Integrated into the existing testing factory of a production NOS, NosRacer demonstrates that dynamic race condition detection can be made practical for large-scale actively developed NOSes. Several directions remain for future work. One direction is to support incremental analysis as the NOS codebase evolves. Future work could reuse traces and analysis results across code revisions to update race-condition candidates incre-mentally, reducing the cost of deploying NosRacer in CI pipelines. Another direction is to enrich severity analysis. NosRacer currently analyzes how race conditions affect subsequent message-sending and function-call sequences. Future work could further incorporate configuration consis-tency checks, cross-component state invariants, and user-visible service-level symptoms, to help developers prioritize detected race conditions. Finally, it would be valuable to study whether NosRacer’s two-phase design generalizes to other asynchronous multi-component systems. Production distributed control systems and cloud management platforms share similar challenges: asynchronous message interactions, large execution spaces, and limited testing budgets.

## A Testing Factory of the Target NOS 

The testing factory of the studied NOS is a large-scale Contin-uous Integration (CI) platform that runs workloads for NOS development and release testing. The factory runs system-level tests on virtualized multi-device topologies. These tests configure devices through Command Line Interface (CLI) commands and inject test traffic to validate NOS functional-ity, performance, and stability. Configuration-update tests constitute a large portion of these system-level tests. They apply configuration commands and validate the resulting NOS behavior. NosRacer uses these existing tests, together with their profiles and the factory execution environment. 

A.1 Test Execution Environment 

System-level tests are submitted to the factory as test plans .They may come from CI jobs, release-test campaigns, or developer debugging sessions. The factory schedules these plans across a pool of virtualized testbeds, tracks the state of each execution, and stores the artifacts produced by com-pleted executions. At the scale of the studied testing factory, the testbed pool contains over 10,000 virtualized testbeds, and the factory keeps over 5,000 test executions running con-currently. The factory sustains a daily throughput of over 200,000 system-level test executions. Each test plan follows a factory-defined schema that speci-fies the topology to instantiate, the workload to execute, and the checks used to determine the test outcome. The topology specification defines the nodes and links in the test: De-vice Under Test (DUT) nodes represent the network devices hosting the NOSes under test; peer nodes provide neigh-boring devices along the packet forwarding paths; traffic endpoints inject or observe test traffic; and virtual links con-nect the nodes. The workload specifies the CLI commands to issue, the test traffic to inject or observe, and the device-state queries to run. The checks validate device-local outcomes and cross-device behaviors, such as reachability, forward-ing behavior, convergence, and state consistency. Beyond topology, workload, and checks, a test plan can also include auxiliary files and execution-specific parameters. The factory manager schedules test plans across the testbed pool. It maintains queues of pending plans, tracks which testbeds are available or occupied, and chooses a compat-ible testbed for each plan based on the plan’s topology re-quirements. The manager keeps multiple plans executing in parallel by assigning queued plans to testbeds as they be-come available. When multiple plans use the same or similar topology, the manager can place them on suitable testbeds to reduce redundant topology setup. The testbed pool supplies the virtualized environments used by the test plans. A testbed manager controls each testbed. Once the factory manager assigns a plan to a testbed, the testbed manager sets up the requested topology and runs the test. During the setup of a test execution, the testbed manager prepares the requested topology. KVM-based vir-tual machines run NOS device instances for DUT nodes and for peer nodes that require a full NOS image. Docker con-tainers run traffic endpoints and auxiliary test services. The testbed manager connects these devices and services with virtual links, producing the multi-device NOS environment specified by the test plan. After the test execution environment is ready, the testbed manager starts the workload using the auxiliary files and pa-rameters specified in the test plan. For configuration-update tests, it first applies the initial configuration and checks whether the DUTs have reached the required initial state. It then applies configuration changes, queries device state, observes traffic behavior during or after the update, and checks whether the observed behavior matches the expected outcomes of configuration updates. At the end of a test execution, the testbed manager writes command outputs, device logs, traffic observations, state snapshots, and test results to the artifact store of the testing factory, which is a storage service backed by file systems and databases. The artifact store indexes these artifacts by test execution information and records each artifact’s type and storage location, allowing downstream tools to retrieve the artifacts for a given test execution. The factory also includes a unified reporting system. It presents the factory’s standard test outcomes together with analysis reports generated by external tools, and links each report to its test plan, execu-tion instance, and artifacts. This enables test engineers to inspect both execution outcomes and analysis results within the same testing workflow. The testbed is then released back to the pool for later test executions. Selected tests from Nos-Racer enter this pipeline through the orchestrator described in §4. 

A.2 Configuration-Update Test Cases 

The factory maintains more than 200,000 configuration-update tests. These tests exercise ordered sequences of configura-tion commands issued to one or more DUTs in the test topol-ogy. The covered update scenarios arise from operational changes, including topology changes, traffic dynamics, and policy revisions. These update scenarios can affect connec-tivity, protocol behavior, forwarding state, or access policy. Each test captures the lifecycle of a configuration update. It first establishes the pre-update device state and then applies one or more ordered configuration changes. The test checks intermediate and post-update outcomes during and after the update. Together, these tests span hundreds of NOS compo-nents and thousands of configuration features. Thousands of configuration-update tests are added or updated as the NOS evolves through each monthly release cycle. The factory maintains a profile for each configuration-update test to organize and select tests at scale. Each profile contains functional labels and coverage information. The

## B NosRacer Workflow Orchestration 

NosRacer builds its end-to-end workflow on the testing factory. The orchestrator coordinates this workflow as a dependency graph of testbed executions and offline-analysis steps. It tracks the state of each step, submits test plans when their inputs are ready, retrieves execution artifacts, and uses analysis results to submit follow-up plans. Given the target component and its functional labels, the orchestrator first invokes the build pipeline to insert message-passing hooks across NOS components. It then selects related configuration-update tests from the testing factory and sub-mits test plans that execute the instrumented NOS image to collect message traces for concentration. After concentra-tion produces the interacting components, crucial variables, and selected tests, the orchestrator invokes the build pipeline again to instrument the target-related components with both message-passing hooks and variable-access hooks. It then submits the selected tests as preparatory runs, which pro-duce the traces needed by offline analysis. Offline analysis processes preparatory traces and orga-nizes the resulting perturbations into groups. For each group, the orchestrator creates a perturbation test plan, attaches the message-delay rules generated for that group, and submits the plan to the factory. After the factory completes the per-turbed tests, the orchestrator retrieves the traces for offline analysis. When a perturbation execution needs strengthen-ing, the orchestrator submits a follow-up perturbation plan with increased message delays. Finally, offline analysis pro-duces race-condition reports, and the orchestrator publishes these reports through the testing factory’s reporting system. The orchestrator records which preparatory run each per-turbation group belongs to and which perturbed executions were launched for that group. These records let offline anal-ysis tools match perturbation traces with the corresponding preparatory traces, and let final reports link each detected race condition to concrete artifacts produced in the corre-sponding factory executions. 

## C NosRacer Implementation 

The implementation details below address two issues central to NosRacer. Runtime tracing must capture enough context around crucial-variable accesses and message exchanges for ordering and value analysis, while also supporting message-delay perturbation. Offline analysis must match original and perturbed access occurrences across executions even when variable instances and recorded traces differ across runs. 

C.1 Runtime Tracing 

NosRacer uses Clang-based AST analysis to perform source-level instrumentation [33]. Concentration provides the inter-acting components and crucial variables to be instrumented. The instrumentation inserts message-passing hooks in the 

> 17

target component and its interacting components, and in-serts variable-access hooks at crucial-variable access sites in the target component. The generated hook code is compiled into the corresponding NOS components. During system exe-cution, the hook code invokes the runtime library to generate execution traces. Variable-access hooks are placed at read/update access sites of crucial variables in the target component. These accesses may appear inside conditional expressions, loop conditions, function arguments, or compound update expres-sions. The insertion point therefore determines when the hook is triggered and which value is recorded. NosRacer uses Clang AST to locate these access sites, classify each ac-cess as a read or update, and choose an insertion point based on the surrounding statement. Specifically, hooks for condi-tional and loop expressions are placed after the expression is evaluated on the executed path, while hooks for update ex-pressions record the updated value. When a variable-access hook is triggered, the runtime library records the source-level variable identifier, object address, access type, access value, and runtime call stack. The NOS communication layer provides a small set of com-mon APIs for exchanging messages between components. NosRacer wraps these send/receive API calls with message-passing hooks. When a message-passing hook is triggered, the runtime library records the sender, receiver, message type, and runtime call stack. For send/receive pairing within an execution, it also records hashes of the complete mes-sages. The runtime library records a message operation only when both the sender and the receiver are either the tar-get component or one of its interacting components. When a message-receiving hook is triggered, the runtime library checks whether the received message should be recorded. If the message is recorded, the runtime library also records traces from the message handler that processes the message and associates them with the recorded incoming message. Offline analysis uses this association to link each variable-access operation to the message handler that contains it. For perturbation executions, the same runtime library reads the delay rules. Before invoking the original send API, the send-API wrapper checks each outgoing message and injects the delay specified in the delay rules. 

C.2 Offline Analysis 

Offline analysis first handles runtime variable instances within each execution. A source-level crucial variable may corre-spond to multiple runtime objects in the same execution. Offline analysis uses the source-level variable identifier and object address to distinguish these instances. Offline analysis then checks whether each concurrent ac-cess occurrence has a matching perturbed access occurrence across executions. This matching does not use object ad-dresses, which may change across executions. A perturbed access occurrence is matched only when it has the same recorded crucial-variable identifier as the original occur-rence and the two corresponding handler executions appear in the reversed order. Offline analysis matches handler ex-ecutions using the recorded incoming message processed by the handler and the runtime call stack of the access. The same variable and execution-context information is used to identify duplicate occurrences with the same handler order, avoiding duplicate race condition reports. Race condition detection compares the observed values in an original occurrence and its matched perturbed occurrence. Before this comparison, offline analysis checks the recorded access sequences on both sides. For each side, the check scans the recorded access sequence of the same runtime variable instance within the configuration update task. Each observed value change must have a corresponding recorded update access. The runtime library records traces only for handlers whose incoming messages are recorded. Updates performed while processing other messages may be absent from the trace. Such missing updates prevent offline analysis from reliably attributing an observed value difference to the reversal of handler order. For each access in the original and perturbed occurrences, offline analysis identifies the message handler that contains the access. It then follows recorded send/receive relations backward from that handler to identify the configuration update task to which the handler belongs. Within that task, offline analysis extracts the recorded access sequence for the same runtime variable instance. If a recorded access has a value different from the previous recorded access but is not an update access that records the new value, the update that produced the change is missing from the trace. If either occurrence contains such a missing update, NosRacer ex-cludes the matched pair from race condition detection. Other concurrent or perturbed occurrences are still analyzed.
