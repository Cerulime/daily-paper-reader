## 摘要
我们提出了一种构建于 CHERI 内存安全之上的高效、基于链接的进程内隔离模型，该模型能够对整个 UNIX 用户空间进行细粒度隔离，在桌面系统上可扩展到 10K+ 个隔离域。该模型的“一键式”隔离可沿现有库边界进行，对于 Chromium 等大型应用，每个进程通常可承载 500+ 个隔离域，远超其他机制所支持的并发可用保护域数量（例如，Intel MPK 最多支持 16 个）。自定义策略可以进一步细分库。在测试的数千个 C/C++ 程序中，只有 V8 JavaScript 引擎需要源码级适配（涉及垃圾回收和 JIT 编译的改动代码少于 300 行）。我们通过在编译器工具链和操作系统中的支持，为 Armv8-A 和 RISC-V 的 CHERI 扩展版本实现了该模型。案例研究展示了隔离域之间内存的平滑委派、隔离域感知的调试与可视化，以及对复杂托管语言运行时的可扩展性，证明了我们单地址空间模型的优势。我们使用多种处理器进行评估，包括 Arm 的超标量 Morello，尤其是首个商用 CHERI 支持的 RISC-V 应用核心——Codasip 的顺序双发射 X730。

## Abstract
We present an efficient linkage-based model for in-process compartmentalization built on CHERI memory safety, which enables fine-grained compartmentalization of the entire UNIX user-space, scaling to 10K+ compartments on desktop systems. The model's "push-button" compartmentalization along existing library boundaries regularly hosts 500+ compartments per process for large applications such as Chromium, far exceeding the number of concurrently available protection domains supported by other mechanisms (e.g., up to 16 for Intel MPK). Custom policies can further subdivide libraries. Of the thousands of C/C++ programs tested, only the V8 JavaScript engine required source-level adaptation (<300 lines of changed code concerning garbage collection and JIT compilation).   We implement the model for CHERI-extended versions of Armv8-A and RISC-V through support in the compiler toolchain and operating system. Case studies illustrate the smooth delegation of memory between compartments, compartment-aware debugging and visualization, as well as extensibility to a complex managed language runtime, demonstrating the benefits of our single-address-space model. We evaluate using multiple processors, including Arm's superscalar Morello and, notably, the first commercial CHERI-enabled RISC-V application core---Codasip's in-order dual-issue X730.

# 论文总结：Efficient Linkage-Based Compartmentalization on CHERI

## 1. 核心问题与整体含义
- **研究动机**：进程内隔离长期受限于可用架构原语。Intel MPK 等机制保护域数量少（如 16 个），且常需静态分配或高成本动态重配，难以支持数据依赖的共享；例如 tcpdump 按包内容在 100+ 个 dissector 间路由，理论访问控制配置可达 ≫2^100。
- **背景**：CHERI 通过 capability 扩展指针，在硬件层提供细粒度边界、权限、不可伪造性与内存安全；CheriBSD 的 CheriABI、堆时间安全、Arm Morello 与 CHERI-RISC-V 生态已较成熟。
- **整体含义**：论文提出一种基于链接关系的进程内隔离模型，沿现有动态库边界实现“一键式”隔离，目标是在 UNIX 用户态以单地址空间支持 10K+ 隔离域，并尽量少改源码、兼容现有构建与调试工作流。

## 2. 方法论
- **核心思想**：把动态链接本身作为隔离边界。默认情况下，可执行文件与每个共享库形成独立隔离域；开发者可通过策略进一步细分库、控制符号引用权限。
- **构建时流程**：
  - 编译器生成可重定位对象；静态链接器读取隔离策略。
  - **放置规则**：把同一共享库内的符号/函数划分到多个 sub-library，例如将 crypto 与 io 函数分到不同子库。
  - **ACL**：定义 subject（子库）、object（符号 glob）、permissions（Read/Write/Execute），静态链接器拒绝非法引用，并对允许的 capability 施加权限约束。
  - 启用 `-ffunction-sections` 等支持任意放置；静态链接器生成每子库的代码、数据、GOT/PLT 等，并插入 padding 使 capability 边界不重叠。
- **运行时流程**：
  - 动态链接器按策略加载与重定位，将代码指针 bounds 限制到所属 sub-library，而非整个共享库。
  - 跨隔离域函数指针由 **trampoline** 包装；trampoline 分为调用腿与返回腿，负责切换执行栈、更新 **Trusted Stack** 与 **Stack Lookup Table**，并保存/恢复 callee-saved 寄存器、清理非参数/非返回值寄存器。
  - 支持快速路径：同一隔离域内的“自转换”可直接尾调用，避免不必要开销；尾调用可折叠可信帧，防止 Trusted Stack 膨胀。
- **系统集成**：
  - 系统调用只允许通过 C runtime wrapper 发出，wrapper 函数指针带不可伪造权限位，内核检查 PCC 权限位。
  - 信号先进入集中式 handler，完成 TCB 临界区后再分发。
  - `setjmp/longjmp`、C++ 异常通过特权 API 展开 Trusted Stack；V8 垃圾回收也复用这些 API 遍历跨隔离域栈。
- **安全保证**：包括栈安全、寄存器完整性与机密性、良好括号化控制流、策略执行、转换中介、系统调用中介等；与 CheriABI 的空间/时间内存安全、CFI 形成叠加保护。

## 3. 实验设计
- **平台**：Arm Morello（Armv8-A，超标量乱序 ASIC）、Cambridge Toooba（RISC-V 乱序 FPGA）、Codasip X730（RISC-V 双发射 9 级 FPGA，商用核）、CapLtd CVA6-CHERI（RISC-V 双发射 6 级 FPGA）。系统为 CheriBSD，非调试构建，默认启用全局堆时间安全；gRPC 除外。
- **案例与 benchmark**：
  - **tcpdump**：从 11 个隔离域扩展到 180 个；用 100K 包抓包文件测转换次数与 CPU 周期。
  - **Chromium/V8**：47M LoC Chromium 原型，V8 约 2M LoC，改动 <300 行；无策略时得到 536 个运行时隔离域；V8 约 115K 测试。
  - **微基准**：跨库立即返回函数调用，比较启用/禁用隔离的指令与周期开销。
  - **FFmpeg/libdav1d**：解码 10 秒 AV1 视频，3 种分辨率，各 5 次。
  - **SPDK**：fio + SPDK 插件对 RAM disk 随机读，比较 coalescing 与不 coalescing。
  - **gRPC**：QPS benchmark，不同 payload 大小，比较禁用、3 域 coalescing、82 域分离。
- **对比方法/配置**：主要是禁用隔离 baseline、启用隔离但无策略/有策略、coalescing 与不 coalescing；并非与传统 MPK/SFI 系统做同机端到端对比，而是与自身 baseline 对比并讨论相关机制限制。

## 6. 主要结论与发现
- 基于链接的 CHERI 隔离可扩展到 **10K+ 隔离域**；桌面 Morello 登录 KDE 后已有 2000+ 域，启动更多应用后超过 10K。
- Chromium 等大型应用每进程常见 **500+ 隔离域**，远超 Intel MPK 的 16 个保护域。
- 数千 C/C++ 程序中仅 V8 需少量源码适配（<300 行），说明兼容性与增量采用能力较强。
- 性能开销高度依赖工作负载：tcpdump CPU 周期 +33.3%；FFmpeg 开销通常 <1%；SPDK 4KB 请求吞吐下降 1.9%–13%；gRPC 64B 小包下降 25%–33%，大 payload 低于 5.6%。
- 快速路径与 coalescing 能显著降低开销；gRPC 中快速路径减少 99.2% 自转换。
- 单地址空间模型在调试、追踪、可视化、托管语言运行时支持方面可行。

## 7. 优点
- **兼容性强**：无策略也可运行，有策略也可在无隔离环境运行；复用现有构建系统，几乎无需编译器额外标志。
- **增量细化**：默认按库隔离，再通过放置规则和 ACL 细分，适合逐步部署。
- **硬件级安全基础**：利用 CHERI capability、sentry、monotonicity、堆时间安全，实现细粒度、可动态委派的内存共享。
- **系统集成完整**：覆盖动态链接、trampoline、栈切换、寄存器 ABI 卫生、系统调用、信号、异常、GC/JIT。
- **工具链与调试支持**：扩展 GDB、提出 CheriTree 可视化 capability 可达性，利于安全审计。
- **多平台实证**：在 Morello 与多种 CHERI-RISC-V 核上评估，含首个商用 CHERI-RISC-V 应用核。

## 8. 不足与局限
- **TCB 仍较大**：内核、动态链接器、C/C++ runtime、线程库及部分 libc 功能仍受信任。
- **系统接口的 ambient authority**：`setjmp`、信号处理器、文件描述符、`dlopen`、`ptrace`、`dl_iterate_phdr` 等仍可能绕过或削弱隔离边界。
- **未完全解决的风险**：
  - 线程局部存储尚未隔离。
  - 汇编生成的“wild”函数指针可能不触发转换，调用方也未检查。
  - 函数签名在 UB 场景下可能不准确。
  - 栈时间安全未解决；跨域栈引用可能被 hoard。
  - 侧信道与瞬态执行攻击不在范围内，仅作为未来工作。
- **性能局限**：小消息、细粒度 I/O、频繁跨域调用场景开销明显；gRPC 中堆时间安全与隔离同时启用的性能问题需进一步工程优化。
- **策略与审计**：自动化策略生成、分布式策略审计仍开放；手工策略质量依赖开发者。
