## 摘要
基于微控制器（MCU）的设备日益普及，使得高效、可扩展的固件安全分析至关重要。近期的固件重托管工作使自动化漏洞评估成为可能，但仍存在两个缺口。首先，现有工具在有限且高度重叠的数据集上进行评估，削弱了所报告结果的泛化性。其次，先前研究沿着孤立的维度推进了最新技术水平，例如仿真、模糊测试或缺陷诊断，但缺乏对这些组件在动态分析工作流中如何交互与互补的整体理解。基于OTACAP和FirmLine最近发布的大规模MCU固件数据集，我们对发表在顶级会议和期刊上的24种基于仿真的固件分析工具开展了实证研究。我们将这些工具置于统一的自动化分析流水线中：仿真配置侦察、仿真、缺陷发现和诊断。在每个阶段，我们使用去重并验证的4,571个基于ARM的固件样本子集，评估工具的输出是否提供足够信息以支撑后续阶段。仅有1,580个样本（34.5%）能够被成功模糊测试，即使只要至少一种现有工具能够对其模糊测试就计该样本为成功。在这些样本中，模糊测试结果普遍较差，平均代码覆盖率仅为10%，且存在大量误报的崩溃/挂起。通过对失败的模糊测试尝试和假阳性案例进行系统分析，我们揭示了当前方法中的根本性挑战和方法学局限。这些发现凸显了当前最新技术中的关键缺口，并为未来基于仿真的固件分析研究提供了可操作的见解。

## Abstract
Microcontroller (MCU)-based devices are increasingly pervasive, making efficient, scalable firmware security analysis critical. Recent firmware re-hosting work enables automated vulnerability assessment, yet two gaps remain. First, existing tools are evaluated on limited, heavily overlapping datasets, undermining the generalizability of reported results. Second, prior research advances the state of the art along isolated dimensions, such as emulation, fuzzing, or bug diagnosis, without a holistic understanding of how these components interact and complement one another in dynamic analysis workflows.   Building on recently released large-scale MCU firmware datasets from OTACAP and FirmLine, we present an empirical study of 24 emulation-based firmware analysis tools published in top conferences and journals. We position these tools within a unified automated analysis pipeline: emulation configuration reconnaissance, emulation, bug finding, and diagnosis. At each stage, we evaluate whether a tool's output provides sufficient information to enable the subsequent stage, using a deduplicated and validated subset of 4,571 ARM-based firmware samples. Only 1,580 samples (34.5%) can be successfully fuzzed, even counting a sample successful if at least one existing tool can fuzz it. Among these, fuzzing results are generally poor, with average code coverage of only 10% and many false crashes/hangs. Through a systematic analysis of failed fuzzing attempts and false-positive cases, we expose fundamental challenges and methodological limitations in current approaches. These findings highlight critical gaps in the state of the art and provide actionable insights to guide future research in emulation-based firmware analysis.

## 2. 方法论：统一四阶段流水线与工具系统化

### 2.1 统一分析流水线（核心思想）

假设给定固件镜像，端到端流程分为四阶段，逐阶段验证"上一阶段输出是否足以支撑下一阶段"：

1. **阶段 1：仿真配置侦察**——从黑盒剥离固件中恢复 ISA、基地址（Base）、入口点（EP），部分工具还依赖 MCU 规格、硬件 I/O 日志、HAL 源码等。
2. **阶段 2：仿真**——全系统重托管，含 ISA 翻译与三类外设交互建模：MMIO、IRQ、DMA。按目标组件分为四类：
   - **EC（CPU 仿真）**：QEMU、Unicorn、ICICLE（基于 Ghidra SLEIGH）；
   - **EP（外设仿真）**：启发式建模（P2IM 的访问模式、μEmu/Fuzzware 的路径约束、Ember-IO 的覆盖复用、AIM/AidFuzzer 的等待态感知中断触发、DICE/GDMA 的 DMA 学习）与高保真建模（Pretender/Conware 的硬件日志、SEmu 的 NLP 规格提取、Perry 的 HAL 符号执行、FlexEmu 的 LLM 建模）；
   - **EPH（HAL 替换）**：HALucinator、SAFIREFUZZ 等，绕开外设建模但依赖库匹配精度；
   - **ET（移植执行）**：如 SAFIREFUZZ 在 Cortex-A 服务器上动态二进制改写执行。
3. **阶段 3：安全测试（模糊测试）**——以 AFL/AFL++/LibAFL/libFuzzer 为前端，仿真环境为后端；增强维度包括输入生成/变异（Hoedur、MultiFuzz 的多外设流、I2S 替换、PEmu 的协议感知）与执行反馈（Ember-IO 的 FERMCov、ICICLE/MultiFuzz 的 P-code 细粒度分支反馈）。
4. **阶段 4：缺陷诊断**——仅 FirmRCA 支持，基于反向污点分析定位根因指令，并在崩溃重放时抓取内存快照。

### 2.2 关键机制与判定规则（文字化"算法"）

- **崩溃/挂起分类归一化**：把各工具异常统一为四类——非映射访问（UR/UW/UF）、权限违规（RV/WV/EV）、不支持指令（UI）、挂起（在时间或基本块阈值内未消费输入，如 Hoedur/MultiFuzz 的 300 万基本块）。
- **通用内存布局假设**（表 III）：Text 用户自定义、RAM 0x2000_0000、Peripheral 0x4000_0000、System Peripheral 0xE000_0000、IRQ RET 0xFFFF_F000——用于判定"合法访问被误报"。
- **阶段 1 筛选算法**：用 Ghidra Emulator 执行固件，若前 10,000 条指令中出现 >10 条唯一指令且未终止，则判定基地址/入口点候选有效。
- **问题归因启发式（附录 M）**：例如 P4 通过 UI 异常识别；P5 通过"工具未映射但属合法 ARM 区域"的地址识别；P7 通过"中断上下文 + 未初始化指针 RV"识别；P8/P9 通过故障地址落在外设区、系统外设区或 0x20100000–0x3FFFFFFF 识别。作者明确声明这只是"高度可疑特征"，非精确因果分类器。

### 2.3 文献筛选标准

覆盖 S&P、USENIX Security、CCS、NDSS 等 15 年（2010–2025）文献，入选需满足：**单体固件**（排除 Linux 类 Type-I）、**全生命周期仿真**（排除 HITL 与仅启动仿真如 Jetset）、**通用性**（排除基带/车载/工控/卫星/USB/TrustZone 专用工具）、**ARM Cortex-M**（排除 MSP430、x86）、**支持动态分析**。最终阶段 2/3 入选 **21 项工作**，加上阶段 1（FirmXRay、FirmLine、OTACap）与阶段 4（FirmRCA），共系统化 **24 个工具**。

## 6. 主要结论与发现

- **总体漏斗式衰减**：4,571 个固件中，仅 **1,580 个（34.5%）** 能被至少一个现有工具成功模糊测试；平均代码覆盖率仅 **9%–11.7%**（Fuzzware 9.19%、MultiFuzz 10.23%、Hoedur 11.73%），仅 426/578/603 个样本覆盖率超过 10%。
- **阶段 1**：FirmXRay 通过筛选 2,468 例、FirmLine 391 例、rbasefind 1,227 例，大量样本因信息源不足而失败。
- **阶段 2**：P2IM/AIM/DICE 在全部 2,468 例上失败（2,127 例立即中止，341 例陷入死循环）；μEmu 仅为 295 例生成外设模型；Fuzzware/GDMA/MultiFuzz 分别失败 997/1,006/969 例；AidFuzzer 失败 2,460 例（仅 8 例成功）。
- **阶段 3**：超过 1/3 样本报告崩溃（Fuzzware 521/1,471、MultiFuzz 681/1,499、Hoedur 619/1,485），但**绝大多数为假阳性**；Hoedur 报 27,987 次挂起（1,065 例样本），MultiFuzz 报 2,987 次（1,301 例样本）。
