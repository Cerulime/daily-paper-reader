## 摘要
大语言模型（LLM）的进展推动了人们对可扩展方法的探索，以评估生成的软件及安全敏感软件的安全性。静态分析作为一种可扩展、可复现且低成本的安全门禁被广泛采用，但无法直接观察运行时利用行为。依赖于对抗性输入、执行上下文或漏洞利用链的漏洞可能绕过静态检查，但在实践中仍可利用，然而通过静态分析常被视为安全行为的证据。本文引入静态通过-动态失败（SPDF）现象，以及一个三阶段智能体流水线，结合静态扫描、LLM驱动的通用弱点枚举（CWE）推理和在隔离Docker容器中的自主漏洞利用验证。我们评估了来自SecurityEval、RedCode和CyberNative数据集的1,355个Python样本。在复合Bandit-Semgrep门禁下未产生任何发现的654个样本中，LLM检测阶段在235个文件中识别出394个候选漏洞。动态验证在95个文件中确认或部分确认了可利用性，得到包含式流水线比率为14.53%（约为每7个静态干净样本中的1个）。该比率表示在Bandit-Semgrep干净样本中，流水线识别出候选漏洞并获得支持可利用性的运行时证据的比例。结果因数据集而异：在候选文件--CWE对中，RedCode的确认可利用性为33.7%，CyberNative为28.6%，SecurityEval为5.4%。若干频繁被确认的类别，包括CWE-338和CWE-916，既未被Bandit也未被Semgrep标记。这些发现表明，静态分析成功与运行时安全是软件保障的不同层级，而非可互换的度量，并有可能重塑AI生成代码和安全敏感代码的评估方式。

## Abstract
Advances in large language models (LLMs) fuel the quest for scalable methods to assess the security of generated and security-sensitive software. Static analysis is widely adopted as a scalable, reproducible, and inexpensive security gate, but cannot directly observe runtime exploit behaviour. Vulnerabilities dependent on adversarial inputs, execution context, or exploit chaining may evade static checks while remaining exploitable in practice, yet passing static analysis is often treated as evidence of secure behaviour. This paper introduces the Static-Pass Dynamic-Fail (SPDF) phenomenon and a three-stage agentic pipeline combining static scanning, LLM-driven Common Weakness Enumeration (CWE) reasoning, and autonomous exploit verification in isolated Docker containers. We evaluate 1,355 Python samples from SecurityEval, RedCode, and CyberNative datasets. Of the 654 samples producing no findings under the composite Bandit-Semgrep gate, the LLM detection stage identified 394 candidate vulnerabilities across 235 files. Dynamic verification confirmed or partially confirmed exploitability in 95 files, yielding an inclusive pipeline rate of 14.53% (roughly 1 in 7 statically clean samples). This rate represents the proportion of Bandit-Semgrep-clean samples for which the pipeline identified a candidate vulnerability and obtained runtime evidence supporting exploitability. Outcomes varied by dataset: among candidate file--CWE pairs, confirmed exploitability was 33.7% for RedCode, 28.6% for CyberNative, and 5.4% for SecurityEval. Several frequently confirmed classes, including CWE-338 and CWE-916, were flagged by neither Bandit nor Semgrep. These findings indicate that static-analysis success and runtime security are hierarchical layers of software assurance rather than interchangeable measures, and have the potential to reshape how AI-generated and security-sensitive code is evaluated.

# 论文总结：Beyond Static Guarantees — 静态通过-动态失败（SPDF）差距的量化研究

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：LLM 编程助手日益普及，安全评估流水线（如 SecurityEval、RedCode、AutoSafeCoder、VulnRepairEval）却高度依赖 Bandit、CodeQL、Semgrep 等静态分析工具。
- **核心矛盾**：静态分析可扩展、可复现、成本低，但不执行代码，无法直接观察运行时利用行为。依赖对抗性输入、执行上下文或利用链的漏洞可能完全绕过静态检查，而"通过静态分析"却常被当作安全的证据。
- **论文提出的问题**：定义并量化 **Static-Pass Dynamic-Fail（SPDF）现象**——在复合 Bandit–Semgrep 门禁下无任何告警、但在运行时被证实可利用的漏洞。
- **整体含义**：软件安全应被理解为**证据的层级结构**（静态分析 → 漏洞推理 → 动态验证），成功于某一层级并不保证下一层级成功；静态通过 ≠ 运行时安全。

## 2. 方法论：三阶段 Agentic 安全流水线

### 核心思想
用"静态过滤 → LLM 推理检测 → 动态利用验证"逐级加强证据强度；只有同时满足"静态干净 + LLM 判定候选 CWE + 运行时证据支持"的样本才算 SPDF 实例。

### 阶段一：静态分析门禁
- 工具：**Bandit v1.8.4.dev21**（Python 专用安全检查）+ **Semgrep v1.155.0**（auto 规则集）。
- 未施加额外的置信度/严重度阈值；两工具结果在**文件级**合并。
- 任一工具报告任一 finding 即视为"被标记"并剔除；只有两者都无发现的文件才进入下一阶段。

### 阶段二：CWE 漏洞检测 Agent
- 模型：`gpt-5.4-nano`，`temperature=0`（确定性解码）。
- 范式：ReAct 风格推理 + 检索增强（RAG），要求将疑似漏洞与 MITRE CWE 官方定义对照验证后才能上报。
- 三个工具：`search_web`、`fetch_cwe_detail`、`report_findings`；系统提示明确禁止未检索 CWE 定义就报告。
- 约束：每次最多 10 轮推理/工具调用；**每样本独立运行 5 次**，在 file–CWE 级别按**多数投票（≥3/5）** 聚合。
- 产出：结构化漏洞报告（CWE 编号、名称、严重度、理由），即"候选漏洞"（尚未动态验证）。

### 阶段三：动态利用验证 Agent
- 模型：`gpt-5.4-nano`，`temperature=0.3`（鼓励探索多样利用策略），最多 30 轮推理/工具调用。
- 六个工具：`fetch_cwe_info`（MITRE）、`fetch_nvd_cve_examples`（NVD 真实 CVE）、`write_harness`、`read_file`、`run_in_docker`、`report_verdict`；强制先检索 CWE 定义与 NVD 示例再生成利用 harness。
- 自适应测试：不执行固定测试集，按 CWE 类型定制利用（如命令注入多载荷变体、路径穿越多策略、反序列化恶意序列化输入）。
- 沙箱：隔离 Docker 容器，**禁用网络**、**256 MB 内存上限**、可配置执行超时。
- 判定四类：**CONFIRMED / PARTIAL / NOT TRIGGERED / INCONCLUSIVE**；仅当有与目标 CWE 和 NVD 证据一致的运行时可观察行为才算确认（单纯的运行时异常不算成功利用）。
- 每个 file–CWE 对独立评估 5 次，**≥3/5 返回 CONFIRMED** 才判定为动态验证通过。

### SPDF 度量公式
```
SPDFR = |{static-pass} ∩ {dynamic-fail}| / |{static-pass}|
```
- 分母为通过 Bandit–Semgrep 门禁的唯一文件数；分子为其中被动态验证确认可利用的唯一文件数。
- 两种口径：**保守式**（仅 CONFIRMED）与**包含式**（CONFIRMED + PARTIAL）。
- 重要限定：由于动态验证只针对 LLM 检测出的候选，SPDFR 应理解为**完整检测-验证流水线的产出率**，而非全体静态通过样本中可利用漏洞的真实流行率。

### 统计方法
- 数据集间差异：Pearson 卡方独立性检验（α = 0.05）。
- CWE 类别间差异：**基于置换的卡方检验**（因部分类别样本量小，违反渐近检验假设）。

## 6. 主要结论与发现

### RQ1：静态干净代码的运行时可利用程度
- 654 个静态通过文件中，LLM 检测出 235 个文件含候选漏洞（394 个 file–CWE 对）。
- 动态验证结果：**CONFIRMED 120（30.5%）、PARTIAL 20（5.1%）、NOT TRIGGERED 208（52.8%）、INCONCLUSIVE 46（11.7%）**。
- **保守式 SPDFR = 83/654 = 12.69%**；**包含式 SPDFR = 95/654 = 14.53%**（约每 7 个静态干净样本中有 1 个）。
- 即超过八分之一的静态通过样本被证实存在可通过执行触发的漏洞；但不足一半的推理型怀疑转化为实际可利用证据。
- 这些数值应理解为**模型依赖下的可利用性下界**，而非全体静态通过样本的真实流行率。

### RQ2：哪些 CWE 类别最易"静态度过、动态失败"
- **数据集差异显著**：RedCode 33.7%（106/315）、CyberNative 28.6%（12/42）、SecurityEval 5.4%（2/37）；χ²(2)=12.55，p=0.0019。人工策展的生成任务型基准确认率最低，对抗性/预置漏洞语料最高。
- **CWE 类别差异显著**：χ²(22)=138.06，置换 p < 0.0001。
- 高频确认类别：**CWE-400（27 例，非受控资源消耗）**、CWE-338（弱伪随机数生成器）、CWE-330（随机值不足）、CWE-916（密码哈希计算强度不足）、CWE-22（路径穿越）。
- **CWE-338 与 CWE-330 达到 100% 确认率**（每个候选都被 CONFIRMED）。
- 反例：CWE-94（代码注入）、CWE-434（不受限文件上传）、CWE-20（输入校验不当）有大量候选却**零确认**——存在候选弱点不等于实际可利用。
- **整类漏洞被静态工具完全遗漏**：CWE-338（15 例确认）、CWE-916（9）、CWE-73（6）、CWE-770（6）、CWE-862（6）在整个集合中均无 Bandit 或 Semgrep 告警。而 CWE-400、CWE-330、CWE-22 虽在别处被 Bandit 覆盖，仍有个体实例逃逸。
- 结论：SPDF 不只是"已覆盖类别内的孤立假阴性"，还包括**规则式工具覆盖范围之外的整个语义性弱点类别**（随机性质量、密码强度、授权逻辑、资源消耗）。

### RQ3：Agentic 动态验证的成本
- 总成本约 **96.3M tokens、28.7 小时**，动态验证阶段占大头（71.7M tokens、18.2 小时）。
- 结论：动态利用验证比静态分析昂贵得多，**适合作为选择性深度验证层，而非穷举式筛查手段**。

### 总体论断
- 软件安全是**证据层级**而非二元属性；静态分析通过应被解读为"风险降低"，而非"安全证明"。
- 静态分析仍是高效的一线过滤器（以近乎零成本剔除了 701 个文件），但最强评估必须结合执行验证。
- 可利用性应被当作**一等安全产出指标**，而非检测的隐含副产品。

## 7. 优点

- **成本透明**：不仅报告 token、延迟、轮次，还给出 Docker 执行次数与单次验证的长尾分布（均值 > 中位数），使读者能判断该方法在真实工程中的可行性边界。
- **对结论的自我限定**：作者明确指出 SPDFR 是"完整检测-验证流水线的产出率"而非真实流行率，并将其表述为"模型依赖下的可利用性下界"，没有把数字过度泛化为普遍安全结论。
- **提供了静态工具的覆盖盲区清单**：识别出 CWE-338、CWE-916、CWE-73、CWE-770、CWE-862 等整类被 Bandit/Semgrep 完全遗漏的类别，对 SAST 规则建设有直接的实践参考价值。

## 8. 局限与不足

- **因果归因不清**：SPDFR 混合了三种可能来源——静态工具的真假阴性、LLM 检测器的召回上限、动态验证器自身的失败率。当前设计无法区分"静态漏报"与"验证器没能造出可用 harness"，因此 12.69% 这一数字的语义是复合的。
- **缺少消融与对照**：未测试单一 Bandit、单一 Semgrep、不同门禁组合下的 SPDFR 变化；未对比不同 LLM（或不同 temperature、不同轮次预算）对检测与验证结果的影响；也没有与人工审计或既有漏洞数据集标签的对照。
- **单模型依赖**：检测与验证均由 `gpt-5.4-nano` 完成，模型的能力边界、安全对齐策略与拒答倾向会直接塑造结果。例如模型可能对某些 CWE 类别（如 CWE-94 代码注入）倾向于保守判定，从而产生"零确认"的假象。
- **多数投票的潜在偏差**：5 次运行虽降低随机性，但同一模型同一提示下的 5 次采样相关性高，投票更接近"一致性检查"而非独立重复；对 temperature=0 的检测阶段，5 次运行近乎确定性复制，多数投票的统计增益有限。
- **数据集不平衡与代表性**：RedCode 占候选对的 79.9%、确认结果的 88.3%，聚合比率被单一基准主导；三个数据集的来源（人工策展、对抗场景、DPO 生成）都偏"含漏洞语料"，不能代表真实开源代码中静态通过样本的漏洞分布。
- **仅有 Python**：Bandit 是 Python 专用工具，Semgrep 也仅用 auto 规则集，结论无法外推到 C/C++、Java、JavaScript 等语言或 CodeQL 这类跨语言工具。
- **无人工复核**：120 例 CONFIRMED 与 208 例 NOT TRIGGERED 全部由自动化 agent 判定，缺少专家分层抽样审计，无法评估验证器的精确率/召回率，也无法排除"LLM 自造 harness 自证漏洞"的循环论证风险。
- **PARTIAL 语义模糊**：包含式 SPDFR 把 PARTIAL 计入分子，但论文未给出 PARTIAL 的严格操作化定义与人工可复核的判定边界，导致 12.69% 与 14.53% 之间的差异难以解释。
- **成本与可扩展性**：28.7 小时、96.3M tokens 仅覆盖 1,355 个样本，若按真实代码库规模外推，成本不可接受；论文虽建议"选择性深度验证"，但未给出如何选择（如优先级排序策略）的具体方案。
- **时间敏感的外部依赖**：依赖 NVD 实时检索与 MITRE CWE 页面，结果随时间漂移，可复现性受外部服务状态影响。
- **无安全/伦理讨论**：论文未讨论让 LLM 自动生成并执行利用代码所带来的滥用风险、沙箱逃逸风险与合规问题。

## 9. 可改进方向与后续工作

- **消融矩阵**：分别测量（a）纯静态、（b）静态+检测、（c）静态+检测+验证 的产出差异，并单独评估检测器召回与验证器精度，把 SPDFR 分解为可归因的乘积项（如 P(静态漏报) × P(检测命中) × P(验证成功)）。
- **多模型与多提示对照**：用不同厂商/规模的模型重复全流程，检验 SPDFR 对模型选择的敏感性，给出结果的置信区间而非单点估计。
- **引入人工金标准**：对 CONFIRMED、PARTIAL、NOT TRIGGERED 各分层抽样，由安全专家盲审，校准自动判定的一致性（如报告 Cohen's κ）。
- **扩充静态工具对照组**：加入 CodeQL、PyLint、mypy 安全插件或商业 SAST，观察门禁换用后 SPDFR 如何变化，从而把结论从"Bandit–Semgrep 组合的失效"推广到"静态分析范式的边界"。
- **平衡数据集**：引入真实开源项目的静态通过样本（如从 PyPI 抽样），避免聚合指标被 RedCode 类对抗语料主导。
- **优先级排序机制**：基于本研究的 CWE 类别确认率（如 CWE-338/330 达 100%，CWE-400 高频），设计"高风险 CWE 优先验证"的调度策略，以降低选择性验证的总成本。
- **验证器可信度评估**：为动态验证引入"harness 质量检查"与"负对照"（对已知安全代码运行同一 harness，确认不会误报 CONFIRMED），缓解自证循环。
- **跨语言扩展**：在 Java/JavaScript 上用 Semgrep 自定义规则 + 对应运行时沙箱复现实验，检验 SPDF 是否为语言无关现象。
- **开放工件**：发布 harness 模板、Docker 镜像、提示词与判定日志，提升可复现性并支持社区审计。

## 10. 个人综合评价与启发

- **最大贡献在于视角转换**：把"静态通过"从一个二元结论降格为一条证据链中的中间状态，并用 SPDFR 这一可测量指标将其量化。这一概念即使实验细节有争议，仍然对安全评估实践具有直接影响——任何声称"经 SAST 扫描无问题"的报告都应被追问其动态证据。
- **工程方法学上有借鉴价值**：三阶段设计体现了"用便宜手段做剪枝、用昂贵手段做确认"的成本分层思想，与模糊测试中的 seed 筛选、漏洞挖掘中的静态引导动态（concolic）思路一脉相承。动态验证器基于 CWE 定义 + NVD 实例自适应生成 harness 的做法，比固定测试集更贴近真实利用行为。
- **结论需谨慎引用**：12.69% 这一数字不宜被当作"静态分析漏报率"或"静态通过代码的漏洞流行率"直接引用。它是在特定模型、特定工具组合、特定（偏含漏洞）语料下、由自动判定产生的复合流水线产出率，且缺少人工校准与消融分解。
- **最值得警惕的发现**：CWE-338（弱随机数）、CWE-916（密码哈希强度）、CWE-862（授权缺失）、CWE-770（资源无限制分配）等**整类语义性弱点被规则式 SAST 完全遗漏**。这说明静态工具的能力边界不只是"漏报个例"，而是对需要跨语句语义、数据流与业务上下文推理的弱点类型系统性失明。这一观察对 SAST 规则设计与 LLM 辅助审计的定位都有指导意义。
- **反向启示**：并非所有候选弱点都可利用——CWE-94、CWE-434、CWE-20 有大量候选却零确认，说明"LLM 认为可疑"与"运行时真的能被攻击"之间存在显著鸿沟。这提示 LLM 安全审计应避免只输出告警列表，而应把可利用性验证作为报告的一部分。
- **总体定位**：本文更接近一篇**问题定义与方法学探索性研究**，而非严格意义上的 benchmark 论文。它的价值在于提出了一个好问题、给出了可操作的测量流程与一组有启发性的观察；其结论的强度受限于单模型、无消融、无人工复核，未来工作若能补齐这些环节，SPDFR 有望成为安全评估报告中的常规指标。
