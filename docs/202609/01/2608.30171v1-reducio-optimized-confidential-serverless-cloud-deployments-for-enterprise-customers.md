## 摘要
最近，基于机密虚拟机（CVM）的无服务器平台被提出，以解决无服务器函数的隐私问题，同时实现低延迟。不幸的是，我们的研究表明，为了实现这些特性，现有方案在基础设施变更和平台内存方面提出了不小的要求。Reducio 是一种替代性无服务器平台设计，不需要基础设施变更，并显著降低平台内存需求。该平台使用两个关键组件设计：(1) 基于内核降权特性的 CVM 内部函数隔离框架，最小化基础设施需求；(2) 分层缓存方法和算法，有效利用小型内存函数缓存。我们的评估表明，Reducio 可以显著减少部署的平台要求和函数内存消耗。

## Abstract
Serverless platforms based on Confidential Virtual Machines (CVMs) have been recently proposed to address the privacy problems with serverless functions, while achieving low latency. Unfortunately, our study indicates that to achieve these properties, existing proposals impose non-trivial requirements in terms of infrastructure changes and platform memory. Reducio is an alternate serverless platform design that does not require infrastructure changes and significantly reduces platform memory requirements. The platform is designed using two key components: (1) a function isolation framework inside a CVM based on kernel deprivileging features that minimize infrastructure requirements, and (2) a layer-wise caching methodology and algorithm that effectively uses a small in-memory function cache. Our evaluation indicates that Reducio can significantly reduce both platform requirements for deployment and function memory consumption.

## 1. 核心问题与整体含义

**研究动机与背景：**
- 无服务器计算（Serverless Computing）虽然简化了云应用的部署，但带来了严重的隐私风险——开发者将代码和数据交给云提供商后，对敏感信息（如医院的患者数据、金融数据）的控制权完全丧失。
- 为了在无服务器场景下恢复数据隐私，学术界提出了机密无服务器平台（Confidential Serverless Platforms），利用硬件辅助的可信执行环境（TEE）将函数实例与云主机基础设施隔离。
- 当前主流方法是基于机密虚拟机（CVM，如Intel TDX、AMD SEV-SNP、ARM CCA），将整个客户软件栈保护在硬件加密和完整性隔离中。

**现有方案的三点关键缺陷（论文的切入点）：**
1. **部署要求苛刻（L1）**：现有方案要么依赖微内核（如CoFunc）需要将I/O栈委托给宿主机，要么依赖AMD VMPL特权级划分（如Wallet）需要修改宿主机hypervisor和paravisor，均需要大规模基础设施改造，部署和迁移困难。
2. **冷启动延迟高（L2）**：基于内核内监控器（intra-kernel monitor）的Erebor方案虽然部署友好（单方部署），但缺乏安全的Copy-on-Write（CoW）fork支持，导致函数冷启动延迟达4.6秒级别，比现有最优方案慢了数个数量级。
3. **内存开销巨大（L3）**：为实现快速启动，现有方案依赖将函数Zygote（预初始化快照）常驻内存。仅21个SeBS基准函数的Zygote就需约5.15 GiB内存，而真实部署需要维护数万个不同的Zygote，内存成本不可扩展。简单的LRU等缓存替换策略在高内存压力下的性能也很差。

**整体含义：** Reducio旨在设计一个**部署友好**（无需基础设施修改）与**内存-延迟协同优化**（低内存开销 + 低启动延迟）的机密无服务器平台，面向企业客户（如医院、金融机构、政府承包商）的私有化服务器部署场景，使其既有隐私保护又能经济高效地运营。

## 2. 方法论

### 核心思想
REDUCIO提出一种全新设计，不再试图“一劳永逸”地将完整函数Zygote保留在内存中，而是结合两种关键创新：

### 关键技术细节

**（1）基于内核降权（Intra-Kernel Deprivileging）的函数隔离框架**

- 采用Nested Kernel设计理念，在CVM内部嵌入一个**安全监控器（Security Monitor）**，处于比OS内核更高的特权级。
- 内核被降权（deprivileged），无法直接访问受保护的内存页；监控器通过特权指令陷阱和内存保护（Intel PKS）控制MMU层的关键操作。
- 无需VMPL、无需修改宿主机hypervisor、无需委托I/O栈——**自包含部署在CVM内部**。

**（2）安全CoW Fork扩展（6个新安全监控调用 SMC）**

监控器需要**验证**（而非重新实现）内核的fork流程，新增以下SMC：

| SMC | 用途 |
|---|---|
| `initialize_fork` | 声明fork意图，建立父子关系 |
| `declare_page` | 声明新页表或受保护进程页 |
| `update_mapping` | 更新页表项映射 |
| `protected_copy` | 在受保护页之间复制内容 |
| `declare_cow_page` | 标记CoW物理页 |
| `finalize_fork` | 结束fork并验证完整性 |

设计维护六个安全不变量（Inv1–Inv6）：
- **Inv1**：受保护物理页只能在同一家族进程间共享。
- **Inv2**：共享页必须映射到相同虚拟地址。
- **Inv3**：CoW共享必须显式声明。
- **Inv4**：fork结束时父子进程受保护物理页数量必须相同。
- **Inv5**：受保护页内容只能复制到其他受保护页。
- **Inv6**：复制后的新页只能映射到原页的虚拟地址。

内核在fork系统调用和缺页异常路径中被插桩（instrumentation），每次页表更新和执行受保护拷贝时都调用监控器验证。最终通过有限状态机（FSM）决策逻辑拒绝任何违反上述不变量的操作。

**（3）分层预测式函数进程缓存**

借鉴RainbowCake的分层思想但扩展为**内存内函数缓存**（非文件系统）：
- **Bare层**：只加载LibOS和标准C库，体积最小（约2MB），可运行任意用户函数。
- **Runtime层**：加载语言运行时（如Python解释器）及其依赖，按语言/版本区分，可运行该语言的所有函数。
- **Warm层**：加载特定函数的全部依赖，即传统Zygote，启动延迟最低。

**预测算法（Predictive Time-Series Algorithm）：**
- 将每个函数的到达过程建模为**泊松分布**。
- 根据预测的**平均到达间隔（Inter-Arrival Time, IAT）** 和平台配置的**成本函数（权衡启动延迟与内存占用）** 计算存活时间TTL。
- 优先从Warm→Runtime→Bare逐级fork以最小化延迟，同时在新层预热完成后继续向前推进一步fork，维护多层缓存状态。
- 利用**Azure函数调用轨迹**计算变异系数（CoV），据此生成逼真的突发/平滑的调用模式用于预热和驱逐决策。

## 6. 主要结论与发现

1. **启动延迟与最优方案相当**：REDUCIO的安全CoW fork约10ms/次，与Wallet、CoFunc的Zygote fork机制性能相当。
2. **内存占用大幅降低**：相比按需加载（Baseline-OD）和缓存全量（Baseline-FC），REDUCIO内存使用分别减少**58%和64%**（RSS累计GB×s度量）。
3. **性能保持合理水平**：端到端几何平均延迟384ms，仅落后Baseline-OD（320ms）约19.9%、落后Baseline-FC（322ms）约19.3%；函数层面几何均值性能与Baseline-FC的差距也保持在19.3%的量级。
4. **p99延迟有代价**：REDUCIO的p99延迟（8385ms）明显高于Baseline-OD（3307ms）和Baseline-FC（2687ms），原因是预测不准确时不得不进行更深的冷启动。
5. **成本显著下降**：在AWS Lambda价格模型下，REDUCIO对应的内存成本（0.06美元/阶段）比Baseline-OD（0.16美元）和Baseline-FC（0.18美元）低**2.4倍和2.8倍**。
6. **突发性工作负载友好**：对于高CoV（突发性）函数受益最大（如graph-mst），而对平滑、低调理速率函数（如graph-bfs）效果较差。
7. **监控器开销可控**：LMBench显示fork+execve为3.48×、缺页处理为5.84×的开销，但SMC开销平均仅约1.2k周期，在实际函数启动场景下影响可忽略。

## 7. 优点

1. **部署友好**：设计严格遵循Nested Kernel/fork验证哲学，无需修改宿主机、无需VMPL、无需更改hypervisor，仅需软件层面的CVM内部部署，可直接在现有云CVM环境使用。
2. **安全性严谨**：6个明确的安全不变量 + 有限状态机验证的CoW fork机制在逻辑上严密；监控器始终保持“验证而非代劳”的职责边界，降低了监控器本身的TCB复杂性。
3. **内存-延迟协同优化思路新颖**：将分层缓存思想从文件系统扩展到内存内函数进程，通过多级预热/逐级降级策略，让少内存也能达到相当优异的性能。
4. **系统实现完整**：约8400行代码实现了从监控器到LibOS到调度器的全栈原型，并明确将开源研究工件，可复现性强。
5. **评估维度全面**：从微基准（LMBench）、函数级基准（SeBS）到真实云轨迹（Azure）再到货币成本分析，扎实且权威。
6. **定位清晰**：目标明确针对企业客户私有化部署场景，并且给出了3个真实企业案例（Zürich保险、Booz Allen、Portbase），使动机具有说服力。

## 8. 不足与局限

1. **p99延迟偏高**：预测不精准时，冷启动深（冷→Warm需要重新加载所有依赖），p99达到8.4秒，很难用于要求低尾延迟的生产系统。
2. **缺乏消融/参数敏感性实验**：未报告预测算法中α、IAT分位数、滑动窗口等参数的影响，也未分离“分层缓存”和“预测策略”的独立贡献；TTL计算方法的细节略显模糊。
3. **安全评估未经验证**：安全分析停留在证明式论述（Inv1–Inv6的逻辑推演），缺少实证攻击测试、模糊测试、页表对象（pte）重放攻击、fork滥用攻击等安全实验的验证。
4. **硬件依赖限制**：依赖Intel TDX + PKS特性，未在AMD SEV-SNP或ARM CCA上验证可移植性；监控器依赖现代内核的PKS功能，内核版本受限（6.8.0）。
5. **场景单一**：只支持CPU-only函数，未涉及GPU、FPGA等异构加速场景；只支持Linux环境。
6. **多语言支持未验证**：虽然Gramine支持多种语言，但实验只覆盖Python；多语言运行时的缓存共享行为、内存节省效果和性能差异没有被测量。
7. **实验时间尺度短**：仅1小时轨迹测试，无法体现长时间运行时的记忆保留、缓存漂移、监控器漏洞累积和内存碎片等问题。
8. **比较偏差风险**：与Wallet/CoFunc的比较是基于论文中的引用数据而非同机复现；CoWV/版本选择、调度参数（如α=0.996）也可能使对比的公平性存在一定隐性偏差。
