## 摘要
我们提出 CHERI-D Reincarnate（Reinc），这是对 CHERI 的一种架构扩展，用于可扩展且高效的时序内存安全。先前工作 CHERI-D 在固定位置存储有限宽度的代 ID，当对象的 ID 耗尽时，需要将该对象隔离。Reinc 通过分配转生进一步提供 use-after-free 缓解，同时允许对象立即重用已释放的内存：当分配槽的当前 ID 耗尽时，Reinc 不会隔离该分配槽，而是动态地为该槽分配一个新 ID。耗尽的 ID 会被隔离，并在之后回收，而底层内存仍可供立即重用。通过隔离 ID 而非内存，Reinc 在常见情况下能够持续重用内存，从而大幅降低内存清扫频率和隔离内存开销。Reinc 进一步引入一致性 ID 缓存，同时保留完全去中心化的 ID 组织。时序元数据仍与其所保护的内存共置，从而保持局部性并避免中心化元数据结构。为支持多核执行，Reinc 使用轻量级反向映射和基于过滤器的机制，将物理一致性事件连接到按虚拟地址访问的 ObjID 缓冲区。我们将 Reinc 实现为软硬件协同设计，涵盖 CHERI-Toooba（超标量 FPGA 软核）、QEMU、LLVM/Clang 和 CheriBSD。在我们评估的工作负载中，Reinc 大幅降低了内存清扫频率和内存隔离，同时仅带来较低的性能与硬件开销。

## Abstract
We propose CHERI-D Reincarnate (Reinc), an architectural extension to CHERI for scalable and efficient temporal memory safety. Prior work CHERI-D has a finite-width generation ID stored at a fixed location, requiring an object to be quarantined when its ID is exhausted. Reinc further provides use-after-free mitigation while permitting immediate freed memory reuse for objects through allocation reincarnation: rather than quarantining an allocation slot upon ID exhaustion, Reinc dynamically assigns a new ID to that slot when its current ID is exhausted. Exhausted IDs are quarantined and later reclaimed, while the underlying memory remains available for immediate reuse. By quarantining IDs rather than memory, Reinc enables continuous reuse of memory in the common case, substantially reducing both memory-sweep frequency and quarantine memory overhead.   Reinc further introduces coherent ID caching while retaining a fully decentralized ID organization. Temporal metadata remains colocated with the memory it protects, preserving locality while avoiding centralized metadata structures. To support multicore execution, Reinc connects physical coherence events to the virtually addressed ObjID buffer using lightweight reverse-map and filter-based mechanisms.   We implement Reinc as a hardware-software co-design spanning CHERI-Toooba (superscalar FPGA softcore), QEMU, LLVM/Clang and CheriBSD. Across our evaluated workloads, Reinc substantially reduces memory-sweep frequency and memory quarantine while incurring low performance and hardware overhead.

# CHERI-D Reincarnate 论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：CHERI 通过硬件能力（capability）提供细粒度空间内存安全，但**时序内存安全**（temporal safety）仍具挑战——能力可被复制，在其引用对象释放后仍可能被解引用（悬垂能力）。
- **现有方案及其局限**：
  - **Cornucopia Reloaded**：软件隔离+清扫撤销，延迟内存复用，隔离带来性能/内存/缓存效率开销，且只提供 use-after-reallocation（UAR）而非严格 use-after-free（UAF）保护。
  - **Picasso**：集中式有效性位表 + 大对象 ID 字段，提供即时 UAF 保护，但中心化 ID 分配、ID 耗尽、表碎片导致开销。
  - **CHERI-D**：将 8-bit 代 ID 内联在分配中，去中心化、比位向量更省元数据；但**ID 静态绑定分配槽**，ID 耗尽时必须隔离整个对象；**仅支持 < 4 KiB 对象**；且 Picasso 与 CHERI-D 均只在**单核**下评估。
- **整体含义**：论文提出 **CHERI-D Reincarnate（Reinc）**，核心洞察是"**耗尽身份（ID）不必耗尽它所保护的内存**"，目标是面向应用级/服务器级多核 CHERI 系统、长时间高强度分配负载，实现可扩展、低开销的时序安全。

## 2. 方法论

### 核心思想
- **分配转生（allocation reincarnation）**：当某分配槽当前 ID 耗尽时，不隔离该槽，而是动态为同一槽关联一个新的 ID 位置（IDLOC），使底层内存**立即可复用**。
- **ID 隔离与回收（ID quarantine & reclamation）**：仅隔离耗尽的 ID，待内存清扫使携带该 ID 的悬垂能力失效后，重置并回收该 ID。若回收在所有 ID 位置耗尽前完成，**内存永不进入隔离**。
- 效果：以"隔离 ID"替代"隔离内存"，形成**无限的时间代际空间**而无需更宽的 ID 字段。

### 关键技术与算法细节
- **能力格式扩展**：新增 8-bit 能力 ID 字段、3-bit IDMODE、6-bit IDLOC；ID 0 保留给"不朽"未检查能力，只有 ID 0 能力可修改 ID 字段。
- **IDMODE 0–7 对象大小分级**（表 1）：
  - Mode 0：< 63 B，64 B cache line 内相对放置；
  - Mode 1：63 B–4 KiB，页内相对（沿用 CHERI-D）；
  - Mode 2–7：4 KiB–1 GiB，**top-relative 放置**，粒度分别为 1 KiB、8 KiB、64 KiB、512 KiB、4 MiB、32 MiB。
- **ID 地址重构算法**（Algorithm 1）：
  - Mode 0：`AlignDown(A,64B) + 16B×IDLOC[4:0] − 1 − IDLOC[5]`；
  - Mode 1：`AlignDown(A,4KiB) + 4032B + IDLOC`；
  - Mode ≥2：`AlignDown(T,G) + IDLOC[4:0]×G − 1 − IDLOC[5]`。
  - IDLOC[5] 独立选择两个相邻 ID 之一，用于转生选择。
- **跨边界收窄的 ID 位置保持**：CHERI 能力派生收窄上界会使 top 变化，Reinc 按跨越的粒度边界数增加 IDLOC[4:0]，保持 ID 位置不变；IDLOC[5] 不受影响。
- **超 1 GiB 对象**：不分配 ID，释放时直接 `pages_unmap()` 解除映射，靠缺页触发陷阱（受益于 2 MiB/1 GiB 巨页粒度，效率高）。
- **多核一致性机制**（不改动底层一致性协议）：
  - 需在 L1 数据缓存与 ObjID 缓冲之间维持**包含（inclusive）策略**；由于 ObjID 缓冲是**虚拟地址索引**、而一致性事件基于物理地址，需桥接二者。
  - **方案一（反向映射 reverse map）**：维护物理元数据行→虚拟 ObjID 位置的小型映射，命中后按偏移 {0,16,32,48} 精确失效 4 个 16 B 条目；检测到别名则保守清空整个缓冲。
  - **方案二（过滤器 filter）**：静态布局过滤（1 KiB 粒度取行内 `lineAddr[3:0]=F`，4 KiB 及以上取 `lineAddr[5:0]=3F`）+ 小型 Bloom 风格物理地址过滤器，命中则保守清空 ObjID 缓冲，误报仅导致多余清空。
  - 两者复用已有 **L1 一致性失效事件与本地 L1 替换事件**，不新增一致性消息或协议状态，不改变时序关键的虚拟地址 ID 查找路径。
- **软件栈改动**：扩展 CheriBSD 的 **MRS（Malloc Revocation Shim）**：`free` 时若当前 ID 达到终止值 254，则置 255 标记耗尽并放入 ID 隔离（记录 IDLOC），分配槽立即归还分配器；隔离 ID 按关联分配大小计入"虚拟隔离大小"以触发清扫阈值；清扫时"revoker"检查携带 ID=255 的能力并失效；清扫后重置隔离 ID 为 0。若某槽所有 ID 均耗尽，则退化为隔离内存。
- **分配器对齐**：通过 aligned allocation 接口请求对齐，所需对齐小于各 size class 的分配器对齐，使 ID 可置于内部碎片中。

## 6. 主要结论与发现

- **性能开销低**：平均运行时开销 SPEC CPU2006 INT 1.7%、SQLite 0.7%、PARSEC 0.3%；开启一致性后，反向映射为 3.2%、过滤器为 2.5%（SPEC）；SQLite 最大开销从 Cornucopia 的 22.6% 降至 2.1%。
- **清扫与隔离大幅减少**：SQLite 下 Reinc 仅需 1 次（关闭 ID 回收时为 0 次）内存清扫，Cornucopia 需 267 次；多数 SPEC/PARSEC 工作负载零清扫、零内存隔离事件（表 3）。
- **DRAM 流量**：Reinc 仅 6%，Cornucopia Reloaded 为 48.2%。
- **安全性**：全部 CWE-416 bad case 被检测并陷入，全部 CWE-415 通过；双核 ID 一致性微基准证明远程 ID 更新后陈旧能力被正确拒绝（严格 UAF 缓解，超越 Cornucopia 的 UAR 语义）。
- **硬件开销有限**：LUT +5.27%（无一致性）/ +6.84%（反向映射）/ +6.15%（过滤器）；寄存器 +9.02%~+13.26%；LUT Memory +8.98%~+23.06%（反向映射最高）；两种设计均不增加时序关键 ID 查找路径的逻辑。
- **能力编码效率**：Reinc 仅需 17 个能力位即可实现完全可扩展的去中心化元数据存储（对比 Picasso 的 21-bit color）。

## 7. 优点

- **核心洞察新颖且简洁**："隔离 ID 而非内存"将 ID 耗尽与内存隔离解耦，用有限 8-bit ID 获得有效无限的时间代际空间。
- **坚持 CHERI 去中心化哲学**：元数据与数据共置，保持空间局部性、避免中心化表、避免额外地址翻译与 TLB/缓存压力，天然适配多核并发与 NUMA。
- **多核一致性方案轻量**：复用现有一致性失效与 L1 替换事件，无需新一致性消息/协议状态，且不侵入时序关键的虚拟地址 ID 查找路径；给出反向映射与 Bloom 过滤器两种成本/精度权衡。
- **工程完整度高**：横跨 CHERI-Toooba、QEMU、LLVM/Clang、CheriBSD、MRS、jemalloc 的完整软硬件协同实现，而非纯仿真。
- **实验数据翔实**：同时报告清扫次数、隔离事件数、峰值与时间加权平均隔离占用、DRAM 流量，量化了"内存隔离减少"这一核心卖点。
- **对象大小扩展**：从 4 KiB 扩展到 1 GiB，并用超页/巨页 unmap 优雅处理超大对象，避免浪费能力编码空间。

## 8. 不足与局限

- **多核评估不足**：FPGA 限制下最多 2 核、每核单硬件线程，无法验证 many-core 可扩展性；作者也承认该结论部分基于推测。
- **平台性能代表性问题**：25 MHz FPGA 软核，绝对性能不具代表性；SPEC 主要用 train 输入，reference 覆盖有限。
- **一致性机制保守**：本地 L1 替换即失效对应 ObjID 条目（即使未被修改），会引入额外缓冲缺失与 ID 访问；过滤器方案误报会清空整个 ObjID 缓冲，作者指出未来需与一致性协议更紧密集成。
- **软件层开销未消除**：ID 管理实现在 MRS 包装层而非分配器内部，需恢复底层分配与元数据，带来额外开销；作者列为未来工作。
- **保护范围有限**：仅覆盖用户态堆，未涉及内核、栈及多层嵌套分配器（对比 PoisonCap 的分层保护）；超 1 GiB 对象退化为 VM 层保护，不提供细粒度 ID 语义。
- **对比缺失**：未与 PoisonCap、CHERIoT、MTE+Reloaded 做端到端量化对比；未给出缓存/TLB 命中率等微架构细粒度数据。
