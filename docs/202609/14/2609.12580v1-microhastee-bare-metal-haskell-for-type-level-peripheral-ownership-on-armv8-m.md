## 摘要
Armv8-M 的 Arm TrustZone 隔离了安全与非安全软件，但开发者仍须在分别构建的固件镜像之间协调外设归属、中断路由、初始化以及网关接口。这些镜像之间不一致的假设可以成功编译，并且只在目标设备上以故障形式显现。我们提出 MicroHasTEE，一个多方编程框架，将两个固件应用表达为同一个带类型 Haskell 程序中的参与者。MicroHasTEE 使用类型级能力账本表示外设权限，并使用索引化设置计算来跟踪资源获取、配置、转移和最终化。领域特定效应类型将外设操作和中断回调限制在持有相应权限的参与者内，而带类型的可调用句柄描述非安全代码可用的安全服务。MicroHs 将共享程序编译两次，以生成独立的裸机安全与非安全固件镜像。我们在 STM32U5 Nucleo 开发板上实现了 MicroHasTEE，包括 TrustZone 配置、外设驱动以及用于跨域 Haskell 调用的序列化网关。对于通过其接口表达的程序，MicroHasTEE 会拒绝不一致的资源使用、配置后的归属变更、错误域中的回调，以及对未注册安全服务的调用。一个门锁案例研究证明了可行性，其固件镜像分别占用 232.7 KiB 和 228.4 KiB 的闪存，每个域约占用 220 KiB 的 SRAM。

## Abstract
Arm TrustZone for Armv8-M isolates Secure and Non-secure software, but developers must still coordinate peripheral attribution, interrupt routing, initialization, and gateway interfaces across separately built firmware images. Inconsistent assumptions between these images can compile successfully and emerge only as faults on the target device.   We present MicroHasTEE, a multiparty programming framework that expresses both firmware applications as participants in one typed Haskell program. MicroHasTEE represents peripheral authority with type-level capability ledgers and uses indexed setup computations to track resource acquisition, configuration, transfer, and finalization. Domain-specific effect types restrict peripheral operations and interrupt callbacks to the participant that holds the corresponding authority, while typed callable handles describe the Secure services available to Non-secure code. MicroHs compiles the shared program twice to produce separate bare-metal Secure and Non-secure firmware images.   We implement MicroHasTEE for an STM32U5 Nucleo board, including TrustZone configuration, peripheral drivers, and a serialized gateway for cross-domain Haskell calls. For programs expressed through its interface, MicroHasTEE rejects inconsistent resource use, attribution changes after configuration, callbacks in the wrong domain, and calls to unregistered Secure services. A door-lock case study demonstrates feasibility, with firmware images occupying 232.7 KiB and 228.4 KiB of flash and approximately 220 KiB of SRAM per domain.

# MicroHasTEE 论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：Armv8-M 的 TrustZone-M 在硬件上把微控制器划分为 Secure 与 Non-secure 两个隔离状态，并只允许通过显式暴露的 Secure 入口点切换。但 TrustZone-M 本身**不决定**外设、GPIO 引脚、SRAM 区域归哪个状态所有，这些归属由厂商设备专用安全硬件实现。
- **具体平台**：本文针对 STM32U5 Nucleo。内存映射的安全寄存器（ST 的 GTZC 中的 TZSC）编码外设与 SRAM 的安全归属；GPIO 端口有逐引脚的安属性位；EXTI 线归属与 NVIC 的 ITNS 中断目标需分别配置；只有 Secure 软件能修改这些属性。
- **核心痛点**：传统 STM32 开发中，Secure 与 Non-secure 固件是**分别构建的两个镜像**。两个镜像可以各自通过类型检查，却对资源归属持有相互冲突的假设（例如 Secure 代码在把 UART 交给 Non-secure 后仍继续使用它，或 Non-secure 假设自己能访问某个从未释放的 GPIO）。硬件只在运行时强制执行配置边界，无法判断两个应用是否对该边界达成一致，因此许多配置不一致只在设备上执行时才以故障形式暴露。
- **现有方案的空缺**：Trusted Firmware-M（TF-M）是 PSA SPE 的参考实现，提供安全启动、隔离 Secure 分区、标准化服务与 manifest 声明；但其 manifest **只描述 Secure 分区**，对 Non-secure 应用一无所知，无法把 manifest 的声明与 Non-secure 构建的假设绑定起来，不一致仍然只在硬件上显现。
- **整体含义**：MicroHasTEE 处理的是一个**源语言层面的互补问题**——不再用分离的 manifest 和程序描述 Secure 分区及其资源，而是从**一个类型化程序**派生两个固件镜像，并针对一份共享的资源权限与转移账目检查外设操作，把跨域不一致从运行期故障变成编译期错误。作者称这是首个在两个 TrustZone-M 状态中执行 Haskell、并用单一类型化 Haskell 程序协调其资源分配与跨状态交互的框架。

## 2. 方法论：核心思想与关键技术

### 2.1 多方编程模型

- 把 Secure 与 Non-secure 应用建模为**同一个 Haskell 程序中的两个参与者**。程序描述各参与者的计算、各自可用资源、资源转移以及允许的跨边界调用；构建系统将该程序编译两次，每个 TrustZone 域一次。
- 两次构建**类型检查同一段 setup 序列**，但只给目标域的计算赋予运行时行为，另一域的计算被替换为占位符（placeholder/dummy）。

### 2.2 类型级能力账本与索引 Setup monad

- 资源所有权由**一对类型级能力账本**表示（Non-secure 与 Secure 各一），`Setup` 是一个索引 monad：

  ```
  data Setup nsPre sPre nsPost sPost a
  ```

  前两个参数是计算前的 Non-secure/Secure 账本，中间两个是计算后的账本，`a` 是返回值。
- 每个公共归属操作**同时**更新硬件配置并在账本对之间做转移；后续操作需提供其资源出现在执行方账本中的证据，否则编译器拒绝。
- 配置阶段以 Secure 账本中的 `Unlocked` 条目表示"仍可配置"：
  - `get_console`：`s = [UART, Unlocked]`（资源需同时不在两个账本中才能获取）；
  - `tzsc_release_periph uart`：`ns = [UART], s = [Unlocked]`；
  - `lock_configuration`：把 `Unlocked` 单向替换为 `Locked`，之后禁止任何改变归属的操作。其类型使用 `Member Unlocked s` 与 `Delete Unlocked s s'` 约束。
- **被拒绝的典型程序**：在 `tzsc_release_periph` 之后调用 `uart_init`（UART 已不在 Secure 账本）；重复 `get_console`（UART 已在 Non-secure 账本）；在 `lock_configuration` 之后 `get_gpio`（配置已终结）。

### 2.3 领域特定效应类型与回调放置

- 用两个效应 monad 表示参与者计算：`data Secure effects a`、`data Nonsecure effects a`。
- 外设操作在这些 monad 上重载，例如 `gpio_toggle` 是 `GPIOActions` 类的方法，其约束 `Member (GPIO pin port) effects` 要求引脚出现在所选 monad 的能力账本中。因此同一操作两个参与者都可用，但**只有持有权限的一方**才能通过类型检查（文中 `goodNonsecure` 通过、`badSecure` 被拒）。
- 回调安装：`exti_on_nonsecure` 要求 Secure 账本含 `Locked`（配置已终结）、EXTI 属于 Non-secure，且回调本身是 `Nonsecure` monad 中、其效应列表与 Non-secure 账本统一的计算。**先锁定配置再统一账本**，可避免后续配置改变账本而使既有统一失效。

### 2.4 可调用句柄与跨域调用

- Secure 函数经 `callable` 注册：

  ```
  callable :: (Member Locked s, NonSecureCallable s f) => f -> Setup ns s ns s (Callable f)
  (<.>) :: NFData a => Callable (a -> b) -> a -> Callable b
  sg    :: Callable (Secure s a) -> Nonsecure ns a
  ```

  `NonSecureCallable` 把服务的效应账本与最终 Secure 账本统一，因此注册服务只能使用 Secure 参与者保留的资源；返回的 `Callable` 是不透明句柄。
- `<.>` 逐个施加参数并保持剩余函数类型，`sg` 在句柄完全应用后调用，是**公共 Haskell 接口中唯一在参与者之间显式传递参数与结果值的操作**。
- `nonsecure :: Member Locked s => Nonsecure ns () -> Setup ns s ns s ()` 在配置锁定后启动 Non-secure 应用。

### 2.5 编译与运行机制

- **双编译**：`SECURE` 构建标志决定公共接口重导出 `Effectful/Internal/Secure.hs` 还是 `NonSecure.hs`；前者中 `Secure = Secure (IO a)`、`Nonsecure = Nonsecure`（占位），后者相反。两者互斥，永不共存。MicroHs 每次编译生成一个 C 源文件。
- **注册同步**：`SetupState` 保存 `nonSecureCallable` 分发表、`counter` 与 `extiCallbacks`。两次构建按相同顺序执行同一 Setup 序列，各自用当前 counter 作为服务 ID 再自增，因此 Secure 侧分发表与 Non-secure 侧句柄 ID 对应。这依赖两镜像同源、同序执行并一同部署。
- **参数序列化**：`<.>` 把 writer 动作追加到句柄，动作先对参数 `deepseq` 强制求值再 `primHSerialize` 写入内存 BFILE（强制求值是因为 MicroHs 的序列化格式是组合子图，可能很大）。请求格式为 `serialize(id) || serialize(arg1) || ... || serialize(argN)`，响应为 `serialize(result)`。
- **网关**：`sg` 在 Non-secure 侧构造序列化包后经 FFI 调用 `c_sg`——这是原型**唯一的 NSC 入口点**。Secure 侧用 `cmse_check_address_range` 校验请求元数据/字节可读、结果缓冲与长度字段可写，再调用 `handle_nsc_call`：反序列化函数 ID、从 vtable 查处理器、执行、把结果拷回输出缓冲（容量不足则写 -1）。
- **分发表统一类型**：每个处理器类型均为 `Ptr BFILE -> IO (Ptr BFILE)`；`mkNSC` 按函数类型递归构造——对 `a -> b` 反序列化一个 `a`、应用函数、继续处理 `b`，直到到达 `Secure effects r` 计算并执行、序列化其结果。
- **驱动库双编译**：外设驱动库编译两次、API 相同，但特权操作（TZSC、GPIO 安全寄存器、EXTI、NVIC 归属写）在 Non-secure 构建中编译为 no-op（保留符号以维持统一 API）。构建顺序为：先构建 Secure 镜像并产出 CMSE import library，再构建 Non-secure 镜像。
