## 摘要
历史 Linux 内核补丁中蕴含的缺陷知识，其适用范围超出了最初的修复位置。近期研究表明，大语言模型（LLMs）可以从历史补丁中生成静态分析检查器，并利用它们发现新的内核缺陷。然而，生成完整检查器要求模型既要恢复补丁所表达的缺陷语义，又要实现复杂的程序分析机制，包括对象跟踪、别名分析、路径状态维护和过程间传播。将这些职责耦合在一个端到端的代码生成任务中，会使一条简单的缺陷规则转变为一个不稳定且代价高昂的分析器实现问题。为解决这一问题，我们提出 TyPatch，它将补丁特定的缺陷语义与分析器实现解耦。LLM 将每个补丁转换为一条类型状态规则，规定其被跟踪对象、动作、守卫条件、状态转移和违规。随后，一个共享后端执行这些规则，将其动作绑定到程序事件，跨别名跟踪对象标识，沿程序路径传播类型状态，并为所有规则生成报告。在 Linux v6.16 上，TyPatch 发现了 559 个不同的缺陷，其中 121 个已得到内核开发者确认。在与最先进的完整检查器构建流程进行的匹配 38 补丁对比中，TyPatch 使用的生成 token 数减少了 88.3–90.1%，而其初始报告池的精确率达到了该流程所产生报告池的 3.42–14.95 倍。

## Abstract
Historical Linux kernel patches capture defect knowledge that applies beyond their original repair sites. Recent work has shown that large language models (LLMs) can generate static-analysis checkers from historical patches and use them to uncover new kernel bugs. However, complete-checker generation requires the model both to recover the defect semantics expressed by a patch and to implement sophisticated program-analysis machinery, including object tracking, alias analysis, path-state maintenance, and interprocedural propagation. Coupling these responsibilities in a single end-to-end code-generation task can turn a simple defect rule into an unstable and expensive analyzer-implementation problem.   To address this problem, we present TyPatch, which decouples patch-specific defect semantics from analyzer implementation. An LLM translates each patch into a typestate rule specifying its tracked object, actions, guards, transitions, and violations. A shared backend then executes these rules, binding their actions to program events, tracking object identity across aliases, propagating typestate along program paths, and producing reports for all rules. On Linux v6.16, TyPatch finds 559 distinct bugs, 121 of which have been confirmed by kernel developers. In a matched 38-patch comparison with the state-of-the-art complete-checker construction workflow, TyPatch uses 88.3-90.1% fewer generation tokens, while its initial report pools achieve 3.42-14.95$\times$ the precision of those produced by that workflow.

# TyPatch 论文中文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：Linux 内核存在大量子系统特有的对象生命周期规则（创建、检查、使用、释放），违反会导致崩溃、资源泄漏和内存安全缺陷。内核规模大、配置多，普通测试负载只能覆盖少量路径，Smatch、Coccinelle、Clang Static Analyzer 等静态工具的检测能力受限于专家已实现的规则，长尾缺陷模式难以覆盖。
- **知识来源**：历史修复补丁记录了根因说明、具体修复动作以及修复前后行为差异，其中的缺陷关系往往不局限于被修改的行，可迁移到内核其他位置。
- **现有方法及其瓶颈**：KNighter 是当前最先进的“补丁→检查器”自动生成工作。它用 LLM 理解补丁、生成检测计划并实现完整的 Clang Static Analyzer（CSA）检查器。但该设计把两件事耦合在一起：
  - 恢复补丁表达的缺陷语义；
  - 实现复杂程序分析机制（回调、对象标识、别名处理、路径状态、过程间传播、报告逻辑）。
- **后果**：KNighter 自身失败分析显示，22 个未产出有效检查器的补丁中 13 个（59%）归因于实现不准确（仅 2 个归因于缺陷模式分析、7 个归因于计划）。本文匹配 38 补丁实验中，KNighter 在 GPT-5.5 下仅 167 个候选产出 27 个有效检查器，在 DeepSeek-v4-pro 下 198 个候选产出 23 个，两轮消耗 728 万与 988 万生成 token。论文用一个 cgbc hwmon 驱动案例说明：20 个生成计划全部识别出缺失的 NULL 检查，20 个检查器全部编译通过，但 18/20 无法区分修复前后的种子代码——原因是 checker 内部用 Loc 派生的 region 存储状态、却用 Val 派生的 region 查询，导致别名表更新被跳过。
- **整体含义**：把“补丁理解”与“分析器实现”解耦，可以让一条简单的缺陷规则不再退化为不稳定且昂贵的分析器实现任务，从而使历史修复知识可规模化地转化为持久检测能力。

## 2. 方法论

### 2.1 核心思想

- LLM 只负责生成补丁特有的**缺陷语义**（结构化 typestate 规则）；所有补丁**共用的程序分析机制**由一次性实现的共享后端承担。即“生成规则、复用分析器”。

### 2.2 规则表示

- 完整规则定义为 **R = ⟨O, E, Q, q₀, δ, q_b, K⟩**：
  - **(E, Q, q₀, δ, q_b)** 构成类型状态机：E 为动作字母表，Q 为有限抽象状态域，q₀ 为初始状态，δ: Q×E→Q 为状态转移函数，q_b 为违规状态。
  - **O**：指定起始动作如何选取代表被跟踪对象的程序值（函数返回值、参数/出参、字段值、受管分配等）。
  - **K = (ē, Φ)**：证据契约，ē = ⟨e₁,…,e_m⟩ 为有序关键动作序列，Φ 为报告约束（路径一致性、动作位置互异等）。仅当后端能证明约束不可能满足时才丢弃候选（fail-open）。
- **绑定形式**使状态机可执行：call 动作命名被调函数并选取参数/字段（如 `Call[of_node_put,arg0]`）；return 选取调用结果；branch 选取出边；memory 选取 load/store/解引用；exit 选取函数返回。仅承载对象、不改变状态的未绑定操作（load、store、字段地址计算、cast、实参→形参传递）由共享分析处理，不写入规则。
- **状态合并**：域 Q 带确定性 join 算子 J_Q，规则可声明合并用例，规范化时以共享回退策略补全；显式用例优先，违规状态吸收。例如标量未初始化使用规则中“初始 ⊔ 非初始 = 初始”，生命周期规则中同一对保留非初始义务；其余未匹配对按 CFG 前驱顺序确定性处理。
- **示例（cgbc）**：O = `Ret(devm_kzalloc)`；E = {AllocRet: source, BrNonNull: guard, Ref: sink}；Q = {Untracked, MaybeNull, NonNull, NPD}；转移为 Untracked--AllocRet-->MaybeNull、MaybeNull--BrNonNull-->NonNull、MaybeNull--Ref-->NPD、NonNull--AllocRet-->MaybeNull，其余为恒等自环；K 要求分配与解引用在同一可行路径上指向同一对象。

### 2.3 从补丁构造规则

- **证据构造**：联合三类证据——commit message（缺陷与修复意图）、code diff（改变行为的操作）、修复前上下文源码（对象流与条件）；对宏、wrapper、`DEFINE_FREE` 清理声明做源码展开解析，每段摘录保留 file:line 溯源信息。
- **生成**：LLM 在给定类型化 schema 下一次生成一条完整候选规则；若修复依赖规则接口之外语义（如数值边界），可返回 `NoRule`。
- **两阶段验证（以规范化分隔）**：
  1. 规范化前：schema 校验（字段类型、必需动作字段、状态/动作引用）＋ source grounding（校验 call/return 动作命名的函数确有证据支持）；
  2. 规范化（补全未列出的状态–动作对为恒等转移）；
  3. 规范化后：状态机校验（q_b 可达、从 q₀ 重放 ē 能到达 q_b）＋ 后端校验（存在标识被跟踪对象的 source 动作、拒绝不支持的动作组合、确认可翻译为后端表示）；参数位置、字段路径、branch/exit 类型均做结构检查。
- **修复循环**：失败以字段级诊断返回（如未 grounding 的被调函数、不可达违规状态、关键动作序列不构成转移路径），模型最多修订两次，每次修订重走完整验证；仍失败则返回 NoRule。通过后序列化为声明式 `.ts` 格式供后端消费。
- 实现细节：构造上下文最多 3 个被改函数体、每个 ≤200 行、总计 ≤500 行；few-shot 最多 2 个同族示例。

### 2.4 共享类型状态分析

后端需完成三件事：动作绑定到具体事件与选中值；跨别名与控制流保持对象状态、丢弃被证明不可行的历史；在不混淆状态与证据的前提下执行异构规则。

- **动作绑定**：loader 按绑定形式索引动作，将每个匹配解析为指令或 CFG 边、选中值、可选字段路径；return 选调用结果，call 选参数或出参槽，memory 选 load/store/解引用，guard 绑出边，exit 投影到活跃被跟踪对象。
- **对象标识**：别名图 A = ⟨N, F, ρ⟩，N 为抽象对象，F 为带标签的 pointee/field 边，ρ 将 LLVM 值映射到对象；store 替换 ref 边，load 跟随 ref 边，getelementptr 创建/跟随 field 边，cast 保持节点，φ/select 仅在所有入值归一到同一节点时归一；调用点实参与形参共享节点，使出参写入在返回后仍可见；识别 driver-data setter/getter 对做摘要。CFG 汇合处统一相同 LLVM 值的节点并递归统一同一字段标签可达的目标，再重映射规则槽位后合并状态——状态无需在每个规则中编码字段、局部别名与过程间传递。
- **路径敏感传播**：移除循环与返回回边，按拓扑序遍历无环过程间图；每条分析边携带 Γ = ⟨A, T, H, B⟩（别名图、按规则索引的对象状态、支撑历史、分支事实），一个对象可为多条规则携带独立状态槽。匹配动作时 `Advance` 解析对象、把出现追加到历史并应用 δ_r；起始动作在 q₀ 初始化槽位，投影 exit 推进所有活跃对象，到达 q_b 即加入候选池 W。精确转移优先于规范化恒等自环。节点动作在传播前更新状态，guard 只作用于其绑定的出边；开启条件状态跟踪时，可在后续 guard 选择或 join 之前对互补的 null/non-null 分支保持独立状态。
- **证据筛选**：因合并事实可能来自不同路径，Φ_r 要求筛选时后端在相关 CFG 切片上按单路径重放关键动作序列 ē_r（每条路径维护自己的别名图、类型状态与分支事实），检查所需动作能否在同一路径上按序作用于同一对象；只有证明不存在满足 K_r 的路径才拒绝，未知情况保留。
- **分组执行**：同一 link unit 中兼容规则共享一个 AliasGraph，对象携带独立的按规则索引状态与历史，动作索引把每个事件派发给所有匹配规则，对象传递代价只付一次——新增规则无需新的检查器实现或扫描期模型调用。
- 算法流程（Algorithm 1）：构建分析 CFG（去回边）→ 拓扑序遍历节点 → join 前驱别名图与规则事实 → 传递对象标识 → 应用节点/出边动作并 `Advance` → 复制状态到后继并应用边动作 → 对候选池执行 `RefutePath` 筛选 → 输出有序源码级报告。

## 3. 实验设计

- **目标内核**：全部扫描针对 Linux v6.16，commit `98a11dadac64`。
- **数据集**：
  - **RQ1/RQ3**：100 个历史 Linux 修复，覆盖 8 个 bug 族（Null-Pointer Dereference 20、Double Action 20、Missing Release 17、Refcount Imbalance 16、Uninitialized Use 10、Use After Release 10、Acquire–Release Order 4、Publish Before Initialization 3）；规则由 GPT-5.5、DeepSeek-v4-pro、Claude Opus 4.8 独立生成。
  - **RQ2**：KNighter 公开 benchmark 中的 38 个补丁（六类顺序对象状态族：6 个 null-dereference、5 个 leak、7 个 use-after-release、8 个 double-free、5 个 uninitialized-data、7 个 misuse），使用 GPT-5.5 与 DeepSeek-v4-pro，同一模型族、同一目标内核版本。
- **对比方法**：与 KNighter（当前最先进的完整检查器构建流程，commit `f4e834b30741`，官方默认配置）对比。论文指出 SEAL 因其公开版本依赖私有商业工具且与所用内核版本不兼容而无法纳入定量评估（KNighter 也报告过同样限制）。
- **评测协议**：
  - 每个 translation unit 限时 2 小时；RQ1 按源码位置与下游 sink 合并报告，排除种子位置与内核测试代码中的报告；为保证人工审查可行，RQ1 排除整内核扫描产生超过 2000 条原始报告的规则（GPT 2/91、DeepSeek 1/74、Opus 3/84），RQ2 无此门槛。
  - RQ2 在每个规则/检查器内部按 sink 文件、函数、行去重，不同生成工件产生的报告保持独立；对比的是**初始报告池**（不含任何报告级后处理/LLM 分诊）。
  - 所有报告均由人工对照同一 v6.16 源码审查；只有当有序动作在同一可行路径上作用于同一抽象对象时才计为真阳性。
  - 规则先被赋予 kernel scope 或 module scope，scope 只能保持或放宽、不能收窄。
- **RQ3 协议**：对全部 249 条生成规则，与种子 commit message、diff、相关源码上下文比对，判断是否保留被跟踪对象及 source/discharge/sink 角色；谓词或 API 绑定的泛化仍算对齐。

## 5. 实验结果与主要发现

### 5.1 RQ1：规则合成质量与缺陷族覆盖

- **规则生成成功率**：三套独立规则池（GPT-5.5 / DeepSeek-v4-pro / Claude Opus 4.8）分别产出 91、74、84 条有效规则（共 249 条），少量返回 `NoRule`，主要由修复依赖数值边界等规则接口之外语义所致。这说明多数历史修复可被忠实压缩为结构化 typestate 规则，且成功率对模型选择不敏感——因为生成负担已从“写检查器”降为“写规则”。
- **规则对齐性（RQ3）**：对 249 条规则与种子 commit message、diff、上下文源码逐一比对，绝大多数保留了被跟踪对象与 source / discharge / sink 三类角色；少数出现 API 或谓词的泛化（如把具体 wrapper 泛化到同族接口），仍判定为语义对齐。错配主要来自宏展开歧义与多缺陷混叠的补丁。
- **规则规模与稳定性**：一条规则通常仅含少量状态与动作（如 cgbc 例子为 4 状态、3 动作），远小于一份完整 CSA 检查器，因此合成结果在多次生成间更稳定，失败诊断也更可定位（字段级），便于修复循环收敛。

### 5.2 RQ1：检测有效性（真阳性与人工审查）

- **跨族检测**：共享后端在 8 个 bug 族上均能产出被人工确认为真阳性的报告，涵盖空指针解引用、重复动作、缺失释放、引用计数失衡、未初始化使用、释放后使用、获取–释放顺序、发布前初始化等。检测不依赖每个补丁单独实现分析器，证明“规则–分析器解耦”并未牺牲跨族表达力。
- **报告噪声与去重**：按源码位置与下游 sink 合并、排除种子位置与测试代码后，各规则的原始报告量显著下降；仅少数规则（GPT 2/91、DeepSeek 1/74、Opus 3/84）因全内核扫描报告超过 2000 条而被排除，说明大多数规则具备可人工审查的报告规模。
- **正确性判据**：仅当有序关键动作在同一可行路径上作用于同一抽象对象时才计真阳性，因此报告需同时满足“路径可行”与“对象同一”，有效抑制了仅凭模式匹配产生的假阳性。证据筛选（`RefutePath`）在无法证明路径不存在时保留候选（fail-open），保证召回优先。

### 5.3 RQ2：与 KNighter 的对比

- **检测数量与质量**：在 38 个 KNighter 公开 benchmark 补丁上，TyPatch 使用同一模型族与同一目标内核版本，产出的有效检查器/规则数量与真阳性覆盖均优于 KNighter；KNighter 在 GPT-5.5 下 167 个候选仅 27 个有效，在 DeepSeek-v4-pro 下 198 个候选仅 23 个有效。
- **成本对比**：TyPatch 生成 token 为 85.08 万（GPT-5.5）/ 97.90 万（DeepSeek），KNighter 为 728.4 万 / 988.17 万；模型调用次数 TyPatch 为 88 / 90，KNighter 为 596 / 826。即 TyPatch 以约 1/8–1/10 的 token 与约 1/7–1/9 的调用次数完成对比。
- **失败模式对比**：KNighter 的失败集中于“实现不准确”（其自身失败分析中 13/22 归因于此），而 TyPatch 把该风险转移给一次性实现、经反复验证的共享后端，使单条规则的成败主要取决于语义是否被正确表达，而非分析器是否被正确编码。cgbc 案例中 18/20 检查器无法区分修复前后代码，正是实现层面别名表不一致所致，TyPatch 通过统一别名图与规则槽位规避了这一类问题。

### 5.4 消融与关键设计验证

- **证据构造的贡献**：联合 commit message、diff 与修复前上下文，使 LLM 能恢复“对象流 + 条件”而不仅是“改了哪一行”；移除上下文源码会削弱对对象来源与守卫条件的判断。
- **两阶段验证的贡献**：规范化前 schema + source grounding 拦截未落地的被调函数；规范化后状态机校验（q_b 可达、关键动作序列可重放至 q_b）拦截不可执行的规则，二者共同把错误挡在分析之前。
- **分组执行与别名共享的贡献**：同一 link unit 内兼容规则共享别名图、对象按规则独立索引状态与历史，使新增规则不引入新的扫描期模型调用，也不重复对象传递代价，是规模化扩展的关键。

## 6. 结论、贡献与局限

### 6.1 主要贡献

1. **问题重构**：指出“补丁→检查器”范式的真正瓶颈是把缺陷语义恢复与程序分析器实现耦合，并将两者解耦为“LLM 生成规则、共享后端分析”。
2. **规则形式化**：提出 R = ⟨O, E, Q, q₀, δ, q_b, K⟩ 的声明式类型状态规则表示，含对象选择、动作字母表、状态转移、违规状态与证据契约，且支持确定性状态合并。
3. **共享类型状态分析后端**：实现动作绑定、别名图对象标识、路径敏感传播、证据筛选与分组执行，使异构规则可在同一 IR 分析中并发执行。
4. **两阶段验证与修复循环**：以规范化分隔的 schema/grounding 与状态机/后端校验，配合字段级诊断的有限次修订，将不可执行规则挡在扫描前。
5. **实证评估**：在 Linux v6.16 上以 100 个历史修复、8 个 bug 族、三套独立规则池验证有效性，并在 38 补丁 benchmark 上以更低成本优于 KNighter。

### 6.2 结论

- 历史修复知识可被规模化、低成本地转化为持久、可复用的检测能力；一条缺陷规则的成败不再取决于每次重新实现复杂分析机制的稳定性。
- 解耦设计同时改善了正确性、稳定性与经济性：生成成本数量级下降，规则更易审查与维护，新增规则边际成本低。

### 6.3 局限与未来方向

- **语义表达边界**：规则接口难以表达数值边界、复杂算术或跨对象不变式等修复，此类补丁返回 `NoRule`，可能遗漏相应缺陷族。
- **规则正确性依赖验证强度**：后端仅能在“证明不可能满足证据契约”时拒绝候选（fail-open），未知情形保留可能引入假阳性，需人工审查。
- **评估范围**：定量对比仅覆盖 KNighter（SEAL 因私有依赖与内核版本不兼容未纳入），且 benchmark 为 38 个补丁、bug 族以顺序对象状态为主；对并发、锁序、时间/权限等更广缺陷族的适用性有待验证。
- **报告后处理**：对比的是初始报告池，未纳入 LLM 分诊等报告级后处理，真实部署中的可用性还取决于后续筛选流程。
- **未来方向**：扩展规则表达（数值/关系约束）、增强证据契约的可证明性以减少 fail-open 保留、把规则池与后端移植到内核之外的 C/C++ 代码库，以及探索规则自动去重与冲突检测。

## 7. 一句话评价

TyPatch 的核心洞察是“让 LLM 只做它擅长且低风险的语义恢复，把易错昂贵的程序分析交给一次性验证过的共享后端”，从而把历史修复转化为可扩展、可复现、成本可控的内核缺陷检测规则。
