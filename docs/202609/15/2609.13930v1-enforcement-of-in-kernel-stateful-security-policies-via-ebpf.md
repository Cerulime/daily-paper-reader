## 摘要
针对在多租户系统上运行的工作负载的许多攻击都是多步骤且依赖历史的：它们由一系列看似无害的操作组成，其恶意性质只有在整个执行轨迹上才会显现。防御此类攻击需要具备状态性、在内核中强制执行且具有精确语义的安全策略。当前部署的方案至少在其中一方面有所欠缺：内核内置的系统调用过滤和经典 MAC 框架是无状态的，而当前基于 eBPF 的工具通过临时性的 YAML 规则来表达其策略，这些规则无法刻画事件之间的时序关系，且其语义仅由实现定义。我们提出 BPFence，一个满足上述性质的内核内运行时验证框架。BPFence 提供一种具有形式化语义的策略语言，能够表达事件之间的时序关系。它还提供一种类型系统，能够在静态上区分内核可控制的事件与只能观察的事件。每个类型良好的策略都会被编译为一个有限状态监控器，并证明其相对于其语义是正确的，然后再编译为在内核中运行的 eBPF 程序。我们在取自真实世界攻击模式的七个案例研究以及一组微基准和宏基准上评估 BPFence，以表明其执行开销仍与生产部署兼容。

## Abstract
Many attacks against workloads running on multi-tenant systems are multi-step and history-dependent: sequences of innocuous operations whose malicious nature emerges only over an execution trace. Defending against them requires security policies that are stateful, are enforced within the kernel, and have a precise semantics. Currently deployed proposals fail on at least one count: kernel's built-in syscall filtering and classical MAC frameworks are stateless, while current eBPF-based tools express their policies through ad hoc YAML rules that cannot capture temporal relations among events, and whose semantics is defined only by the implementation.   We present BPFence, an in-kernel runtime-verification framework that satisfies the properties above. BPFence provides a policy language with a formal semantics that can express temporal relations among events. It also provides a type system that statically distinguishes events the kernel can control from those it can only observe. Every well-typed policy is compiled into a finite-state monitor proved correct with respect to its semantics, and then into eBPF programs that run inside the kernel. We evaluate BPFence on seven case studies drawn from real-world attack patterns, and on a set of micro- and macro-benchmarks to show that the enforcement overhead remains compatible with production deployment.

## 2. 方法论：核心思想与关键技术细节

### 2.1 事件模型与轨迹语义
- 事件类型集合 `Σ = Σ_C ⊎ Σ_O`，分为**可控事件**（LSM hook，可在操作完成前拒绝或终止）与**可观测事件**（tracepoint/kprobe，只能事后告警）。
- 事件为三元组 `⟨E, fields, t⟩`，执行轨迹是时间有序的事件序列 `σ = e₁e₂…eₙ`。

### 2.2 数据感知时序逻辑
- **事件谓词**：`P ::= α | ¬P | P∧P | P∨P`，原子 `α=(E,g)`，guard 支持字面量比较、变量绑定 `field = ?X`（捕获新变量）与约束 `field = X`（匹配已绑定变量），用强 Kleene 三值语义 `K₃ = {true, false, na}`，`na` 表示事件类型不相关，避免误报。
- **时序公式**：`φ ::= P | ¬φ | φ∧φ | <φ（once）| Gφ（always）| P₁ F≤Δ P₂（有界响应）`。
- **语义域** `B₃ = {ok, pending, violated}`：`pending` 表示存在未决义务（有界响应截止期未到），`violated` 不可撤销。
- **有界响应**语义通过活跃实例集 `I(σₖ,ρ)` 定义，每个实例记录触发位置、环境和绝对截止期 `dᵢ=eᵢ.t+Δ`；截止期已过且未满足则 `violated`，未到则 `pending`。

### 2.3 DSL 与语义翻译
- 策略语法：`Π ::= ⟨d* p, A⟩`，动作 `A ∈ {Alert, Deny, Kill}`；声明 `let H := happened(P) [when H']`；策略体 `forbid P [when H]`、`when P₁ then within Δ P₂`、`p₁∧p₂`。
- 翻译函数 `⟦p⟧_DSL`：
  - `forbid P` → `G(¬P)`
  - `forbid P when H` → `G(¬(D(H)∧P))`
  - `when P₁ then within Δ P₂` → `G(P₁ F≤Δ P₂)`
  - 合取 → 两个 `G` 公式的合取
- **定理 5.5（违反持久性）**：一旦 `violated`，任何轨迹扩展都无法撤销。
- **命题 5.6**：每个违反轨迹存在唯一首个违反前缀。

### 2.4 类型系统
- **违反类型** `τ ∈ T = {C, O, T}`，构成有限格 `C ⊑ O ⊑ T`（可控事件是可控/可观测的特例；基于具体事件的违反比超时违反更可执行）。
- 关键规则：
  - `PEvent`：`Γ ⊢ (E,g) : Γ(E)`
  - `Forbid`：类型为谓词类型
  - `ForbidWhen`：`τ ⊔ τ_H`
  - `Response`：恒定赋予类型 `T`（超时可能违反）
  - `Prog`：`Allowed(τ,A)` 检查动作兼容性——`Deny/Kill` 仅允许 `τ=C`，`Alert` 恒允许。
- **定理 5.8（类型可靠性）**：类型 `τ` 是运行时触发违反事件可控性类的可靠上界。

### 2.5 监控器合成
- **正规形式 NF(Π)**：利用 `G` 对 `∧` 的分配律，把所有子句收拢到单个 `G` 下：`G(⋀ᵢ ¬ψᵢ ∧ ⋀ⱼ (P¹ⱼ F≤Δⱼ P²ⱼ))`。
- 为每个安全合取项合成**安全自动机** `Aˢᵢ`（状态 `{ok, violated}`，规则 S-Viol/S-Ok/S-Absorb），为每个有界响应合取项合成**有界响应自动机** `Aʳⱼ`（规则 R-Ok/R-Viol/R-Absorb），通过**并行组合**构成全局监控器。
- 内存 `m=(H,J)`：历史内存 H 记录每个过去公式是否已满足（单调）；J 为每个有界响应子句维护活跃实例集 `Iⱼ` 和违反标志 `fⱼ`。
- **定理 6.2（可靠性）**：监控器进入 bad 配置 ⇒ 语义违反（无误报）。
- **定理 6.3（完备性）**：语义违反 ⇒ 监控器在某前缀检测到（需事件无丢失、截止期后有事件到达）。
- **命题 B.7/B.8**：监控器确定，规模与公式和历史声明数呈线性。

### 2.6 编译到 eBPF
- 每个 hook 生成一个 eBPF 程序，跨 hook 共享 BPF map 状态。
- 用执行键 `κ`（pid/tgid/cgroup/namespace）分区监控内存，每个被监控实体独立副本；pid 作用域在进程退出时失效历史内存以防 PID 回收。
- 生成代码为无循环直线序列（编译期展开），保证通过 eBPF 验证器的终止性检查；安全合取项编译为 if–goto 检查，有界响应子句实现 `U` 函数的三阶段逻辑（检测过期、删除已满足、激活新实例）。
- 运行时守护进程：三阶段初始化（加载→填充目标 map→挂载 hook）避免策略瞬时全主机生效；轮询 ring buffer 分发违反事件；超时扫描器定期检查过期截止期。

## 6. 主要结论与发现

- **开销可接受**：微基准中每 hook 系统调用开销 4.6%~32.8%（B-3/B-5 最低 61 ns，含路径提取时约 240~432 ns）；nginx 宏基准吞吐从 155,798 req/s 降至 147,223 req/s，**仅下降 5.5%**，处于同类 LSM 监控器（BPFContain、BPFBox、Tetragon、Falco）报告范围的较低端。
- **成本结构**：路径解析（`bpf_d_path`）占单次调用成本约 70%（约 169 ns）；每个历史谓词约 19 ns 哈希查找；每个 forbid 子句约 3 ns；目标查找与 K 无关恒定 61 ns。
- **攻击面削减有效**：全部 7 个主案例中攻击触发器被正确阻止或告警，良性触发器不受干扰，**零假阴性、零假阳性**。
- **表达力优于现有工具**：BPFence 策略通常更短；Falco 规则天生只能告警且单 hook，移植到 BPFence 后仅需换 LSM hook 即可同步预防；Tetragon 支持同步执行但构造上单 hook，无法表达"模块加载后再加载 BPF 程序""shell exec 后再 connect"等跨事件关联，而 BPFence 的历史谓词与 `when` 可直接表达。

## 7. 优点

- **形式化与工程落地结合**：策略语言有明确的指称轨迹语义，监控器合成有可靠性/完备性定理，类型系统有类型可靠性定理，同时真正编译为可通过 eBPF 验证器的内核程序。
- **可控/可观测事件的静态区分**：类型系统 `C⊑O⊑T` 在编译期拒绝内核无法执行的策略（如对 tracepoint 事件要求 Deny），避免"语义上有效但不可执行"的策略被静默接受。
- **eBPF 约束下的设计权衡**：语言刻意设计为可在线监控、可运行时执行、适配 eBPF 验证器（有界内存、无无界循环、固定指令预算），生成代码无循环。
- **跨 hook 关联与状态共享**：通过共享 BPF map 和 `κ` 分区，实现跨 hook 变量关联和按实体隔离，并处理 PID 回收问题。
- **针对规避的初步对策**：fork 时历史传播与回收、文件别名（符号链接/硬链接/bind mount/rename）按文件身份而非路径匹配。
- **工程完整性**：提供标准库（4 个 schema 模块覆盖 14 个事件、4 个策略模板）、参数化模板、策略继承、运行时热更新，并有开源 artifact。

## 8. 不足与局限

- **内核控制能力受限**：仅 LSM hook 中介的事件可同步执行；仅能通过 tracepoint/kprobe 观测的事件只能检测不能阻止。
- **eBPF 执行模型限制**：禁止动态分配，监控状态存于固定大小 map，容量在加载时设定；活跃实例集在 map 满时用 LRU 丢弃，形式上假设无界 `Iⱼ`，实现与此存在偏差（虽作者称只要活跃实例装得下就忠实）。
- **仅支持轨迹属性**：无法表达超属性（如非干涉），论文明确将超属性监控列为未来工作。
- **威胁模型假设较强**：假设攻击者不主动规避已部署策略、不攻击监控器本身、不破坏 TCB；fork 逃逸和文件别名对策只是"迈向强化威胁模型的第一步"，且未评估其有效性。
- **表达力缺口**：对比中发现 Tetragon 有两个 BPFence 不支持的匹配原语——测试系统调用标志位是否置位、按调用进程权限过滤，留作未来工作。
- **实验覆盖与偏差风险**：
  - 所有实验在单台笔记本、单一内核版本上完成，未做跨硬件、跨内核版本的泛化验证。
  - 攻击/良性触发器由作者自行设计，非独立第三方基准，存在自评偏差。
  - 与 Falco/Tetragon 的开销对比被作者自认为"仅具指示性"，因

- **微基准覆盖面有限**：性能实验只挂载了单一 LSM hook（`security_file_open`），未测量多 hook 同时挂载时的组合开销、map 争用与缓存效应；宏基准也仅覆盖 open 密集型的静态文件服务负载，缺少 write/exec/网络密集等事件类型下的表现。

- **案例研究偏"能否表达/能否拦截"**：未量化被监控工作负载在真实业务下的性能影响，也未与 SELinux/AppArmor 等主流 MAC 框架在等价策略下做对照。
- **时间语义的精度未评估**：有界响应的截止期检查依赖超时扫描器轮询与事件到达，论文未报告扫描周期与 Δ 的配置关系、超时判定误差，以及高事件速率下 `pending`→`violated` 的延迟。
- **策略组合与热更新细节不足**：多策略叠加时的冲突消解、继承语义、运行时热更新的原子性与一致性（更新期间是否出现策略空窗）未展开。
- **监控器自身安全性**：依赖"攻击者不攻击 TCB"的强假设，未讨论 map 篡改、hook 卸载/替换、策略文件完整性等自保护问题。

## 9. 总体评价与启示

- **定位价值**：BPFence 是把运行时验证（RV）的形式化方法——三值语义、有界响应、自动机合成、类型可靠性——与 eBPF 内核可编程性真正打通的范例，回答了"学术 RV 理论如何落到可部署内核监控器"这一工程化难题。
- **方法论启示**：其核心设计原则是**以"可执行性"为第一约束**——用 `C ⊑ O ⊑ T` 类型格在编译期拒绝内核无法执行的策略（如对 tracepoint 要求 Deny），用无循环直线代码适配验证器。这种"类型驱动的可部署性"思路可迁移到其他内核内策略语言设计。
- **理论启示**：强 Kleene 三值语义（`na` 抑制误报）与 `{ok, pending, violated}` 状态域（处理未决义务）的组合，对任何需要表达"有界响应"属性的监控器都有参考意义；违反持久性（定理 5.5）与唯一首个违反前缀（命题 5.6）为在线检测提供了清晰的形式基础。
- **工程启示**：编译期展开、固定大小 map、执行键 `κ` 分区、三阶段挂载（加载→填 map→挂 hook）等，是适配 eBPF 约束的通用模式；fork 历史传播与按文件身份而非路径匹配，是应对规避的务实起点。
- **主要遗留问题**：超属性（如非干涉）、跨实体全局属性、强化威胁模型（规避、fork 逃逸、文件别名）、以及 Tetragon 暴露的两个匹配原语缺口（系统调用标志位测试、按进程权限过滤），构成明确的后续研究方向。
- **可复现性**：提供开源 artifact、约 7K LoC OCaml 编译器 + 2K LoC C 运行时、明确实验环境与配置，复现门槛较低；主要可复现性短板在于攻击/良性触发器为作者自研而非第三方独立基准。

## 10. 一句话总结

BPFence 用一个具备形式语义、可静态类型检查、可证明正确并真正编译到 eBPF 内核程序的策略语言，首次在 eBPF 验证器约束下同时实现"有状态 + 精确语义 + 内核内执行"，在 nginx 宏基准上以约 5.5% 吞吐损失、零假阴/假阳地拦下了涵盖后渗透、数据外泄、容器逃逸等 7 类真实攻击模式，代价是仅支持轨迹属性、强 TCB 假设与单机单内核的有限实验覆盖。
