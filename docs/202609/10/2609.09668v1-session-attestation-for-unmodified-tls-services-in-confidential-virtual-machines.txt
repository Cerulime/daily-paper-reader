# Abstract 

Confidential virtual machines simplify the migration of exist-ing services into trusted execution environments, yet attest-ing their network connections often requires changing ap-plications, TLS implementations, or certificates. We present SessionLatch, which provides session attestation while pre-serving all three. The key insight is that a trusted obser-vation of the server’s locally generated ephemeral public key, combined with standard TLS key confirmation, estab-lishes the TEE endpoint guarantee without accessing TLS secrets. This moves attestation integration to the operating system: a temporary latch holds client encrypted records while evidence exchange overlaps the application TLS hand-shake, then removes itself after verification. The resulting connection retains enterprise service authentication and the native TLS data path, with no additional payload encryption. Mutual attestation uses the same construction and overlaps evidence generation at both endpoints. We implement Linux and Windows integration and evaluate real Hygon CSV attes-tation. SessionLatch reduces short-upload mean latency by 63.1%/23.0% relative to TNG in interleaved Linux/Windows experiments. These results show that session attestation can strengthen existing confidential services without making a permanent proxy part of their data path. 

# 1 Introduction 

Confidential computing is increasingly moving toward confidential virtual machines (CVMs), driven by the ability to migrate entire software stacks with limited application changes [6, 18]. Across major architectures, Arm CCA intro-duces Realm-based isolation alongside TrustZone, Intel TDX complements SGX’s application enclaves with VM-level protection, and AMD SEV-SNP and Hygon CSV protect complete virtual machines [1, 6, 7, 15]. CVMs include the guest operating system, applications, and databases within the protected boundary while excluding the host administra-tor [3]. This deployment advantage does not automatically extend to remote access. A client must still establish that its connection reaches an approved CVM, while retaining the service’s existing application, TLS implementation, domain name, and enterprise certificate. This requirement combines two distinct forms of authen-tication. TLS authenticates a service identity and protects transport using session keys; remote attestation provides evidence about the execution environment [2, 16]. Checking both independently is insufficient. As Id-Crisis shows, an en-vironment that satisfies an attestation policy may belong to a different service or administrative domain [18]. Conversely, preserving the enterprise certificate does not establish that the current connection terminates inside a TEE. Certificate private keys may also reside in backup or deployment sys-tems. An insider who obtains such a key can terminate TLS outside the CVM and relay an attestation request to a legiti-mate instance [23]. The certificate and evidence both verify, yet application data is decrypted by the insider. Attested TLS must therefore bind service identity, execu-tion evidence, and the current key exchange to the same end-point. Existing designs place this binding before, within, or after the TLS handshake [17, 18]. Evidence created before the handshake cannot directly commit to its yet-to-be-generated ephemeral keys. Integration within the handshake can estab-lish an early binding, but commonly requires TLS extensions or internal interfaces. Integration after the handshake can use channel-derived material, but requires the application or an intermediary to withhold sensitive data until attestation completes, and can add a serial exchange. A practical gap remains: how can existing TLS services obtain a session-specific TEE endpoint guarantee without modifying their software or retaining an attestation proxy on the data path? SessionLatch builds on a simple observation: the public handshake already exposes enough material to establish this guarantee. A trusted observer inside the CVM identifies an ephemeral server public key generated by the local TLS end-point. Attestation authenticates this origin, and standard TLS Finished verification confirms participation in the cor-responding key exchange. Together, these checks establish the relevant endpoint property without directly attesting to the ECDHE shared secret. Because the public key appears in ServerHello, the binding is available early and can be observed outside the TLS library. The remaining challenge is enforcement. SessionLatch installs a temporary OS-level latch on the connection. Hello messages and the server’s handshake flight proceed nor-mally; evidence travels over a separate control connection while the application TLS stack continues processing the handshake. The latch holds the client’s subsequent encrypted records, including Finished and application data. When evi-dence verification succeeds, it releases the held records and removes itself from that flow. Subsequent traffic follows the

For communication between CVMs, the client can start generating its own evidence as soon as ClientHello is available, allowing the two attestation direc-tions to overlap. This paper makes four contributions: 1. We prove that, for server-endpoint assurance, binding the TEE attestation report to the observable ephemeral ECDHE public key and combining it with standard TLS Finished verification provides security guaran-tees comparable to directly binding the report to the ECDHE shared secret. # 2 Background and Related Work 

2.1 Confidential VMs and Remote Attestation 

A TEE protects code and data within a hardware-enforced execution boundary. Process enclaves protect selected ap-plication components; CVMs include the guest kernel and its workloads. A broader boundary simplifies migration but enlarges the trusted computing base (TCB), requiring the verifier to accept the kernel, runtime, and service configura-tion [3]. CVM memory and execution protection excludes the host and hypervisor from that boundary, but those com-ponents can still control network forwarding [1, 6, 7]. Pro-tecting a VM therefore does not establish that a remote TLS connection terminates in it. Remote attestation supplies verifiable evidence about an execution environment [2]. A typical verifier checks a signed report and its endorsement chain, compares measurements and platform security claims against an admission policy, and checks freshness material. In a CVM, reports generally describe initial VM state and platform claims; trust in the running application and observer also depends on measured images, trusted boot, and deployment configuration. 2.2 TLS 1.3 and Endpoint Binding 

In a certificate-authenticated ECDHE handshake, the client and server send ephemeral public keys 𝑋 and 𝑌 in Clien-tHello and ServerHello (Figure 1) [16]. Each retains its private key and derives a shared secret 𝑍 . The Hello messages are observable on the network, but observing them does not re-veal 𝑍 . Subsequent handshake messages are encrypted under handshake traffic keys. Certificate-chain and name checks establish service identity; CertificateVerify authenticates the transcript; Finished verifies transcript integrity and posses-sion of the corresponding handshake key. Application traffic uses separately derived keys. The distinction between long-term authentication and ephemeral key exchange matters here. Possessing a certifi-cate private key enables impersonation in a new connection, but does not reveal the shared secret of an honest ECDHE exchange. Attestation can exploit this distinction if it identi-fies the endpoint holding the ephemeral private key used in the current connection. Classical RA-TLS places a digest of a TEE-generated TLS authentication public key in an attestation report and deliv-ers the evidence with the certificate [9, 22]. The handshake demonstrates possession of the associated private key. If that key remains exclusively inside the TEE, copying the certifi-cate and evidence does not enable an external endpoint to authenticate. However, the report does not by itself establish that this key is authorized to represent the intended enter-prise service. Policies often admit an image or configuration across multiple instances to support scaling and migration;

Id-Crisis identifies the resulting diversion attack: a net-work attacker redirects a client to another attested endpoint without independently authenticating the intended service name [18]. Figure 2(a) illustrates a stronger failure case in which a leaked, unrevoked attestation key from an unre-lated device enables forged environment evidence. Evidence bound only to the long-term key or a relayable challenge does not identify the current TLS endpoint (Figure 2(b)). The composition needs both service authorization and evidence tied to the actual key exchange. 

2.3 Where to Integrate Attestation 

The point at which evidence is signed determines which session material is available and which component must prevent premature data release [17]. 

Before the handshake. RA-TLS binds evidence to an au-thentication key that exists before the current ephemeral key exchange. RATS-TLS provides modular attester, verifier, and TLS interfaces for multiple TEE platforms [5]. TNG packages this approach into transparent network guards [4]. In its plaintext-input deployment, a client guard encrypts appli-cation traffic into an RA-TLS tunnel and the server guard decrypts and forwards it. This avoids application attestation code but keeps both guards on the data path. Tunneling an existing TLS connection instead preserves its inner authenti-cation while adding encryption and potentially serial hand-shake work. Our evaluation uses TNG’s single-encryption, plaintext-input configuration. 

Within the handshake. TLS-a uses TLS extensions for evidence exchange, and Trusted Sockets Layer uses TLS callbacks to establish attested channels and mutual attesta-tion [14, 21]. Later evidence improves freshness but does not automatically repair identity and composition: the TLS-a design analyzed by Id-Crisis still lacks the required service-identity guarantee [18]. TLS+RA directly addresses the com-position by retaining enterprise authentication and binding evidence to the transcript and ECDHE shared secret [23]. An independently terminated connection has a different se-cret and cannot reuse the report. Its implementation extends OpenSSL and accesses internal key-exchange material. Ses-sionLatch targets the same endpoint property while moving integration to the OS network path. 

After the handshake. HTTPA creates an attested en-crypted channel within HTTPS, retaining outer service au-thentication but adding communication phases and encryp-tion [8, 23]. The Exported Authenticator construction dis-cussed by Id-Crisis completes ordinary TLS first and then ex-changes evidence through channel-bound authenticators [18, 19]. It need not add application encryption, but the applica-tion or an intermediary must gate sensitive data until veri-fication completes. Resumption also requires coordinating attestation and TLS state. Table 1 summarizes these deployment tradeoffs. A retained enterprise certificate is weaker than protection against an attacker who already holds its private key. Likewise, a proxy can avoid application changes without preserving the origi-nal connection’s endpoints. SessionLatch combines a public session binding with temporary OS enforcement so that at-testation does not require either TLS secrets or continuing application-data forwarding. 

# 3 System and Threat Model 

3.1 System Model 

The client connects directly to a TLS service inside a CVM using the existing domain, certificate, and service port. Ad-ditional attestation components exchange evidence over a separate control connection (Figure 3). The common deploy-ment is an ordinary client verifying a confidential server. Mutual attestation adds a client CVM and reverses the at-tester/verifier roles for the second direction. At the server, a trusted session observer 𝑂 𝑆 records pub-lic Hello fields and identifies active local TLS sessions. An attestation agent 𝐴 𝑆 generates platform reports from those records. It can attest only to a key produced by an actual local session, not to an arbitrary public key supplied by a remote requester. At the client, the original TLS stack 𝐶 performs certificate, name, and Finished checks. An OS latch 𝐺 𝐶 ob-serves the handshake and holds subsequent client encrypted records. A verifier 𝑉 𝐶 checks the report and session binding before removing the latch. The application TLS connection carries ordinary TLS and application data. The control connection carries requests and signed evidence; its path need not be trusted because accep-tance depends on report authenticity, the session binding, and protected local state. The server exposes an additional attestation port. A CVM cluster may share a control entry point if it routes requests to the instance that holds the cor-responding application TLS session.

4.2 Attesting Within the Handshake Window 

Discover and latch the flow. When an application opens a connection, the OS identifies the target flow and installs per-flow control before the initial SYN leaves. Hello mes-sages and the server handshake flight are allowed to proceed. Once ClientHello appears, the latch extracts 𝐿 and immedi-ately sends a control request. Request propagation therefore overlaps the application TLS handshake, subject to control-connection availability. 

Attest to an observed local session. The server observer associates the incoming ClientHello and the outgoing Server-Hello with one local connection. Either the request or Server-Hello may arrive first. The agent generates evidence only after the local observation is complete. Capture direction and local socket ownership distinguish local output from external input with a forged local source address. Neither an arbitrary key in a control request nor an address spoof alone can create an attestation-eligible session record. 

Verify and release. While evidence is pending, the latch holds client encrypted records after ClientHello. It need not decrypt them or identify Finished inside the encrypted pay-load: client Finished and subsequent application records fall within the held traffic. The server’s handshake flight still reaches the original TLS stack, which verifies its certificate, name, CertificateVerify, and Finished. On a valid report, matching policy, and matching 𝐵 𝑆 , the verifier authorizes release. The latch removes the per-flow filter and returns held records to the original TCP connection. Subsequent records no longer pass through the user-space attestation component. Verification failure, a session mis-match, or timeout rejects the connection. Report verification and TLS verification may complete in either order, but suc-cessful application delivery requires both: the latch must permit transmission and the TLS stack must establish an authenticated channel. The latch release decision itself is therefore an evidence decision, not an assertion that the TLS handshake has already succeeded. This separation is what permits integration with-out a new TLS callback while retaining both checks in the final acceptance condition.

# 6 Implementation 

SessionLatch runs as separate session-attestation compo-nents. The server identifies local handshakes on its protected network path, and the client temporarily holds unverified traffic; application sockets and TLS implementations remain unchanged. OS integration must prevent premature trans-mission during attestation and stop processing application traffic after success. Table 3 maps this lifecycle to Linux and Windows. 

6.1 Server: Evidence from a Local Handshake 

The Linux server uses libpcap to select Hello messages from application TLS connections, without TLS callbacks [20]. Separate capture paths distinguish ingress ClientHello from locally outgoing ServerHello. Forwarding rules exclude tar-get application traffic traversing the forwarding path, so source-address fields alone cannot make an external packet appear to be local TLS output. The observer uses SOCK_DIAG to query active TCP sockets and associates observations using full addresses and a socket cookie. It rechecks socket ownership and the handshake deadline when registering the session, generating evidence, and returning the report. The cookie distinguishes socket lifetimes that reuse the same addresses, preventing an old observation from authorizing a new connection. This uses the existing user-space Netlink interface rather than TLS secrets or a custom kernel program. A request names 𝐿 to find this local session; it cannot directly choose the server public key to be attested. A worker queue calls the Hygon CSV attestation interface. The request and local ServerHello converge on the same session record regardless of arrival order. Server-only evidence commits to 𝐵 𝑆 , and mutual evidence commits to 𝐵 𝑀 . Independent verifier logic checks report signatures, platform claims, and policy. 

6.2 Client: Default Denial, Per-Session Authorization 

The client’s initial flow state is unauthorized. It permits the public Hello exchange and the server handshake flight, while holding later client encrypted records. It does not decrypt or inspect application content. Linux and Windows differ in how they retain the barrier and bind authorization to the verified connection. 

Linux. Dynamic nftables sets track pending connections, and NFQUEUE implements the temporary user-space inter-ception window [12, 13]. An unauthorized target flow enters the queue even if its tracking-set entry is absent. Queue by-pass in the absence of a listener is disabled, so process exit does not automatically permit unverified transmission. The set is bookkeeping, not the sole deny barrier. After verification, the agent checks that the session is still valid, removes the tracking element through a persistent Netlink channel, and commits authorization with the verdict on an originally held packet. Subsequent kernel rules record the authorization mark on that packet’s conntrack connec-tion. That connection then follows the kernel path directly. Authorization expires with its connection; later four-tuple reuse does not inherit it. FIN, RST, or state reclamation does not grant permission. Verification failure retains denial and installs an independent quarantine rule for the target IP and service port until explicit recovery. 

Windows. The Windows prototype uses WinDivert on the Windows Filtering Platform packet path while applica-tion TLS continues through unmodified Schannel, the Win-dows built-in TLS implementation exposed through the Secu-rity Support Provider Interface (SSPI) [10, 11, 24]. A discov-ery handle intercepts the outbound SYN. The worker opens an exact bidirectional per-flow handle and arranges for the parent guardian to retain a duplicate reference before rein-jecting SYN. Thus, the barrier precedes the handshake, and worker termination alone does not close the last interception reference. On successful verification, the worker drains held records and both processes release their per-flow references, restor-ing the native path. On failure or worker exit, a surviving process first installs system-firewall quarantine for the target IP and TCP port, then deletes relevant TCP control blocks through IP Helper, and only then permits handle cleanup. Quarantine is persistent across restart. This ordering avoids a gap between losing interception and installing denial, but requires at least one handle holder to survive until isola-tion takes effect. The current bounded-batch prototype also rejects four-tuple reuse detected through a changed SYN sequence number within a batch. Both implementations restrict user-space packet handling to the attestation window, thereby minimizing its impact on normal traffic processing. More importantly, they achieve this without requiring either a custom eBPF program or a

6.3 Mutual Attestation 

Both evidence-producing endpoints in our testbed are Linux CSV VMs. Mutual attestation is therefore implemented on Linux; Windows is evaluated as a client verifying a Linux server. The mutual implementation reuses local observation, origin checks, and the client latch, adding client report gen-eration and server-side evidence verification. ClientHello triggers the control request and local report generation. Once the server observes its local ServerHello, it prepares combined evidence concurrently and returns it only after client evidence verifies. The client uses the same authorization path, and ordinary TLS subsequently verifies client Finished. The prototype covers authentication in both directions and client transmission gating. Symmetric gating for server-initiated sensitive data is not part of the evaluated implementation. 

# 7 Evaluation 

Our evaluation tests the three performance consequences of the design: early public-key binding keeps short connections fast, overlapping evidence generation reduces the cost of mutual attestation, and removing the latch after verification preserves the efficiency of the native data path. 

7.1 Experimental Setup 

The Linux client and server are Hygon CSV CVMs running openEuler 22.03 SP4 and OpenSSL. The client has 4 vCPUs and 4GB of memory; the server has 16 vCPUs and 32GB. The Windows client runs Windows 11 with 8 CPUs and 16GB. Every attested connection generates and verifies a real CSV report. We compare native TLS 1.3 (Native), intra-handshake TLS+RA, TNG, and SessionLatch. TNG uses plaintext input and one RA-TLS encryption layer. Server-only workloads upload 1 KiB to 64 MiB and re-ceive an acknowledgment after the server has read the com-plete payload. Mutual workloads exchange 1 KiB/1 KiB or 64 MiB/64 MiB. End-to-end latency includes connection es-tablishment, attestation, and data transfer; we report mean and p95. Effective throughput divides application payload bytes by total completion time, so it includes initial hand-shake and attestation costs. A separate experiment injects one-way delay at client egress to examine the critical path of mutual attestation. Current measurements interleave schemes and exclude warm-up from latency statistics. Windows uses seven rounds; sample counts appear in Figure 5. Linux TLS+RA/TNG re-sults are historical measurements on the same hardware and workloads, marked with hatching. Performance tests disable certificate validation and therefore exclude its cost. Resource measurements cover the user-space attestation and latch processes or TNG guards, with concurrency and units in Table 4. Linux memory uses SessionLatch RSS snap-shots and periodically sampled TNG peaks; Windows TNG resource values are historical. # 8 Conclusion 

SessionLatch enables session-level remote attestation for confidential VM services while preserving existing applica-tions, TLS implementations, and enterprise certificates. It binds evidence to a locally generated ephemeral public key already exposed by the TLS handshake, and combines this binding with standard TLS key confirmation to establish the TEE endpoint guarantee without extracting TLS secrets. A temporary OS latch enforces verification before client trans-mission and restores the native data path after success. The same construction supports mutual attestation with overlap-ping evidence generation. Linux and Windows experiments demonstrate lower latency and modest component resource costs, making transient OS enforcement a practical integra-tion point for attested TLS.
