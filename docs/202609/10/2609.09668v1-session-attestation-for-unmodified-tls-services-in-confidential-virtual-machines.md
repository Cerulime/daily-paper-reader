## 摘要
机密虚拟机简化了将现有服务迁移到可信执行环境的过程，但证明其网络连接通常需要更改应用程序、TLS 实现或证书。我们提出 SessionLatch，它在保留这三者的同时提供会话证明。关键洞见在于，对服务器本地生成的临时公钥进行可信观测，并结合标准 TLS 密钥确认，即可建立 TEE 端点保证，而无需访问 TLS 密钥。这将证明集成转移到操作系统：一个临时闩锁暂存客户端加密记录，同时证据交换与应用 TLS 握手重叠进行，随后在验证完成后自行移除。所得连接保留企业服务认证和原生 TLS 数据路径，且无需额外的载荷加密。双向证明使用相同的构造，并在两端重叠进行证据生成。我们实现了 Linux 和 Windows 集成，并评估了真实的 Hygon CSV 证明。在交错的 Linux/Windows 实验中，SessionLatch 相对于 TNG 将短上传平均延迟降低了 63.1%/23.0%。这些结果表明，会话证明可以增强现有的机密服务，而无需让永久代理成为其数据路径的一部分。

## Abstract
Confidential virtual machines simplify the migration of existing services into trusted execution environments, yet attesting their network connections often requires changing applications, TLS implementations, or certificates. We present SessionLatch, which provides session attestation while preserving all three. The key insight is that a trusted observation of the server's locally generated ephemeral public key, combined with standard TLS key confirmation, establishes the TEE endpoint guarantee without accessing TLS secrets. This moves attestation integration to the operating system: a temporary latch holds client encrypted records while evidence exchange overlaps the application TLS handshake, then removes itself after verification. The resulting connection retains enterprise service authentication and the native TLS data path, with no additional payload encryption. Mutual attestation uses the same construction and overlaps evidence generation at both endpoints. We implement Linux andWindowsintegrationandevaluaterealHygonCSVattestation. SessionLatch reduces short-upload mean latency by 63.1%/23.0% relative to TNG in interleaved Linux/Windows experiments. These results show that session attestation can strengthen existing confidential services without making a permanent proxy part of their data path.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：机密计算正从进程级 enclave 走向机密虚拟机（CVM），Arm CCA、Intel TDX、AMD SEV-SNP、Hygon CSV 等把整个 Guest OS、应用与数据库纳入保护边界，显著降低了现有服务的迁移成本。
- **矛盾点**：迁移便利并不自动延伸到远程访问。客户端仍需确认"连接确实终止于一个被批准的 CVM"，同时又必须保留服务原有的应用、TLS 实现、域名和企业证书。
- **两类认证必须同时满足**：TLS 认证服务身份并保护传输；远程证明提供执行环境证据。单独验证任一者都不够：
  - Id-Crisis 指出的 **Diversion（转移）攻击**：满足证明策略的环境可能属于另一个服务/管理域；若某设备证明密钥泄露且未吊销，还可伪造环境证据。
  - TLS+RA 指出的 **Stolen-key Relay（私钥泄露中继）攻击**：企业证书私钥可能存在于备份/部署系统中，内部人可在 CVM 外终止 TLS 并把证明挑战中继给合法实例，导致"证书通过、证据也通过，但应用数据被外部解密"。
- **根本需求**：把 **服务身份 + 执行证据 + 当前密钥交换** 绑定到同一个端点（attested TLS）。
- **现有集成位置的局限**：
  - 握手前（RA-TLS / RATS-TLS / TNG）：证据无法直接承诺尚未生成的临时密钥；TNG 的 guard 需常驻数据路径并额外加密。
  - 握手内（TLS-a、Trusted Sockets Layer、TLS+RA）：绑定强，但需 TLS 扩展或访问 TLS 内部密钥材料（如 OpenSSL 内部接口）。
  - 握手后（HTTPA、Exported Authenticator）：可无额外加密，但需应用或中间代理扣留敏感数据直到证明完成，且可能引入串行交互。
- **论文要填补的空白**：如何让**未修改的现有 TLS 服务**获得会话级 TEE 端点保证，既不修改软件，也不在数据路径上长期保留证明代理。

## 2. 方法论

### 2.1 核心洞见

- 不直接对 ECDHE 共享密钥 Z 做证明，而是**对服务器本地生成的临时公钥 Y 做可信观测**，再借助标准 TLS Finished 的密钥确认，即可建立端点保证——**全程不访问 TLS 秘密**（不读进程内存、不解密记录）。
- 绑定材料在 **ServerHello 中即为公开可见**，因此可在 TLS 库之外、由操作系统提前获得并启动证明，证据交换与 TLS 握手并行。
- 安全直觉：仅有企业证书私钥的攻击者能做认证签名，但无法得到 y 与 Z；Finished 绑定整个握手 transcript，无法从无关握手移植。

### 2.2 关键公式

- 定位客户端握手：`L = H(δ_L ‖ ks_C)`（ks_C 为 ClientHello 的 key_share 字段）
- 服务器绑定：`B_S = H(δ_S ‖ ks_S)`（ks_S 含选定群与服务器公钥 Y）
- 服务器证据：`E_S = Quote_AK_S(M_S, P_S, B_S)`
- 双向模式客户端绑定：`B_C = H(δ_C ‖ L ‖ N_C)`（N_C 为控制事务标识）
- 双向合并绑定：`B_M = H(δ_M ‖ B_S ‖ B_C)`
- δ 为角色分隔常量，H 为哈希；仅接受受支持的 TLS 1.3 协商，其余握手参数由 TLS transcript 认证。

### 2.3 运行流程（服务器证明）

1. **发现并闩锁**：连接建立（SYN 出站前）即安装按流控制；Hello 与服务器握手 flight 正常放行。
2. **ClientHello 出现后**：闩锁提取 L，立即通过独立控制连接发送证明请求（请求传播与 TLS 握手重叠）。
3. **服务器观测**：Observer O_S 用 libpcap 区分入口 ClientHello 与本地出站 ServerHello，用 SOCK_DIAG 查询活跃 TCP socket 并以 socket cookie 关联会话；请求与 ServerHello 到达顺序无关，只有本地观测完整后才生成证据；**控制请求只能按 L 查找，不能指定要签名的服务器公钥**。
4. **暂存**：闩锁扣留 ClientHello 之后的客户端加密记录（含 Finished 与应用数据），不解密、不识别 Finished。
5. **验证与释放**：报告签名、平台声明、策略 Pol_s 与 B_S 均匹配则授权释放，闩锁移出该流，后续流量走原生内核/TLS 路径；失败、会话不匹配或超时则拒绝连接。
- **验收分离**：报告验证与 TLS 验证顺序任意，但应用数据成功交付要求两者同时成立（闩锁放行 ≠ 断言握手已成功）。

### 2.4 双向证明

- 客户端在 ClientHello 出现时即生成 E_C（不等服务器消息），服务器从本地会话获得 L 与 B_S、重算 B_C、构造 B_M 并在**客户端证据验证通过后**才返回合并报告；客户端独立重算 B_M 并验证后释放闩锁；服务器随后验证 client Finished 确认参与该密钥交换。
- 服务器主动推送敏感数据的场景需要**额外的服务器侧屏障**（等客户端证据验证 + client Finished），论文明确说明该对称屏障未纳入原型评估。

### 2.5 实现要点

- **Linux 服务器**：libpcap + SOCK_DIAG，用户态 Netlink，无需自定义内核程序；worker 队列调用 Hygon CSV 证明接口。
- **Linux 客户端**：动态 nftables set 记录待定连接 + NFQUEUE 实现临时用户态拦截窗口；未授权流即使无 set 条目也进入队列；**禁用"无监听者即 bypass"**，进程退出不会自动放行；验证通过后用原始被扣包的 verdict 提交授权并标记 conntrack；失败则保留拒绝并安装独立隔离规则。
- **Windows 客户端**：WinDivert/WFP 拦截出站 SYN，父 guardian 持有重复引用后再重注入；应用侧使用未修改的 Schannel/SSPI；验证成功后 drain 并释放引用，失败或 worker 退出时先安装系统防火墙隔离、删除 TCP 控制块，再清理句柄；**要求至少一个持有拦截引用的进程存活到隔离生效**。
- 不依赖自定义 eBPF 程序，也不需要未签名的 WFP callout 驱动。

### 2.6 安全分析

- 假设：密码学与执行完整性、**本地受限证明**（Observer 能区分网络输入与本地 TLS 输出；服务器只能证明本地生成的 Y；双向服务器仅在客户端证据通过后返回合并证据）、**逐会话门控**（加密记录不能绕过闩锁）。
- **Lemma 1**：验证 Y 的本地来源证据 + 完成同一 Y 的 TLS 验证 ⇒ 存在匹配的、位于被批准 TEE 的服务器会话（除可忽略概率）；仅持长期证书私钥的外部攻击者无法独立获得记录层密钥。
- **Theorem 1（服务器端点保证）**：即使长期 TLS 私钥泄露，`Pr[Accept_C ∧ ¬∃π_S: Match] ≤ negl(λ)`。
- **Theorem 2（双向端点对应）**：双向模式下，客户端接受 ⇒ 存在已核验当前客户端绑定的匹配服务器会话；服务器接受 ⇒ 同一握手中由被批准客户端会话完成密钥确认。
- **绑定方向的重要性**：若服务器对收到的客户端公钥 X 出具证据，攻击者可自选 a 并返回 Y_A = g^a，凭窃取的证书私钥独立终止 TLS；因此必须证明服务器**本地生成**的 Y。
- 身份与数据交付：未修改 TLS 栈保留证书、名称与 CertificateVerify 检查；`Deliver_C(π) ⇒ Accept_C(π, s)`。
