## 摘要
Linux容器通过共享宿主内核实现高密度和快速生命周期操作，但这种设计也让受损的主机能够检查或修改容器状态。现有的机密计算系统保护一个安全飞地地址空间或整个客户操作系统，而近期的容器粒度系统仍然添加了独立的保护上下文。这些抽象并未将动态的宿主管辖Linux进程组作为架构保护单元。本文提出NACRE，一种用于原生机密容器的RISC-V软硬件协同设计。其关键见解是将宿主管理资源的权限与其访问或提交受保护状态的权限分离。硬件识别的容器身份将受保护的陷阱导向隔离的S模式代理，而M模式监视器提交安全敏感的身份、映射和页转换。代理在不更改satp的情况下将服务委托给宿主Linux；既不访问私有字节也不修改受保护状态的服务也避免使用M模式。我们通过扩展QEMU、OpenSBI、Linux、可信代理和runc来原型实现NACRE。该原型实现了单容器私有内存子层，并覆盖了启动、故障、fork/写时复制、用户访问和拆除路径。在五个lmbench系统调用和管道指标上，三次运行的平均值保持在runc原始基线的3.5%以内。在八个nginx对象大小平均值等权的情况下，总吞吐量降低1.9%。

## Abstract
Linux containers achieve high density and fast lifecycle operations by sharing the host kernel, but this design also lets a compromised host inspect or modify container state. Existing   confidential-computing systems protect an enclave address space or an entire guest operating system, while recent container-granularity systems still add a separate protection context.   These abstractions do not make a dynamic group of host-managed Linux processes the architectural protection unit.   This paper presents NACRE, a RISC-V hardware-software co-design for native confidential containers. Its key insight is to separate the host's authority to manage resources from its   authority to access or commit protected state. Hardware-recognized container identities direct protected traps to an isolated S-mode agent, while an M-mode monitor commits security-   sensitive identity, mapping, and page transitions. The agent delegates services to host Linux without changing satp; services that neither access private bytes nor modify protected   state also avoid M-mode. We prototype NACRE by extending QEMU, OpenSBI, Linux, a trusted agent, and runc. The prototype implements the single-container private-memory substrate and   covered launch, fault, fork/COW, user-access, and teardown paths. Across five lmbench syscall and pipe metrics, the three-run means remain within 3.5% of the runc-origin baseline. With   the eight nginx object-size means weighted equally, aggregate throughput is 1.9% lower.

# NACRE 论文详细总结

## 1. 核心问题与研究动机

- **背景问题**：Linux 容器通过共享宿主内核实现高密度部署和快速生命周期操作，但这一设计把大量安全责任交给宿主内核。一旦宿主内核或特权管理员被攻破，攻击者可以读取容器内存、篡改页表和执行状态、伪造容器元数据，使传统容器无法在**不完全可信的基础设施**上保护工作负载。
- **现有方案不足**：
  - **Enclave 方案**（如 SGX、Keystone、Penglai）：以"地址空间"为保护单元，不支持动态进程组语义，多进程容器应用需要在库 OS 或运行时中重建 Linux 进程抽象，兼容性差。
  - **机密虚拟机（CVM）方案**（如 SEV、TDX、CCA、Kata Containers）：以整机为客户保护单元，增加了客户内核、额外虚拟机监控层，牺牲了原生容器的密度和响应性，且 VM 成为资源管理单元，资源管理分散。
  - **容器粒度方案**（如 BlackBox、ConMonitor、RContainer、Fasco 等）：仍引入新的保护上下文或虚拟化层，频繁容器操作需穿越嵌套页表或保护上下文，破坏宿主 Linux 与容器进程间的直接执行路径。
- **关键困境**：传统硬件将宿主 OS 的两种角色混为一体——**资源管理权**和**安全权威（访问/提交受保护状态的权限）**。原生容器要求宿主保留前者以获得效率，但不可信的宿主不能持有后者。
- **核心主张**：定义"**原生机密容器**"为硬件保护下动态管理的一组 Linux 进程，可继续使用宿主的调度和资源管理，但宿主不能访问受保护容器状态或篡改容器成员关系。现有抽象未能让"动态的宿主管辖 Linux 进程组"成为架构保护单元。

## 2. 方法论

### 核心思想
NACRE 的核心理念是**分离宿主的"资源管理权"与"访问/提交受保护状态的权限"**，使宿主 Linux 继续执行调度、内存分配等管理职能，但不持有安全权威。

### 架构与关键技术

**（1）硬件可识别的容器身份（Container Identity, cid）**
- 容器身份作为架构安全状态，将执行上下文和受保护资源与某个 cid 关联。
- 硬件基于 cid（而非宿主维护的进程元数据）执行访问控制和事件路由。
- 可信机制控制身份的产生、继承和撤销，防宿主通过页重映射伪造成员关系或获取受保护页。

**（2）三层架构**
- **U 模式**：普通应用程序与机密容器均作为 Linux 进程运行。
- **S 模式**：引入与宿主 Linux 同特权级（peer-privilege）但处于不同硬件保护域的**可信容器代理（agent）**。容器陷阱先进入代理，代理保存受保护上下文后再委托宿主 Linux 执行服务。宿主事件仍走普通 Linux 路径。
- **M 模式**：**安全监视器（secure monitor）** 仅处理关键安全操作（身份管理、受保护映射提交、页状态转换等），是安全状态的"提交边界"。

**（3）内存保护子层**
- 预留内存包含代理代码/数据、监视器元数据和受保护的非根页表页。
- 每个物理页带角色标记（NORM/ROOT/PRIV/PEND）。
  - NORM：普通 Linux 页；
  - ROOT：satp 指向的根页表页；
  - PRIV：机密用户数据页，宿主 Linux 不能直接访问；
  - PEND：监视器事务中的临时禁用状态，仅供 M 模式访问。
- 根页表页由 Linux 分配但标记为 ROOT；非根页表页由监视器从受保护区分配，硬件翻译时可读但只有 M 模式可写。
- 采用 PMP、agent 基址-边界寄存器、QEMU 中的 PFN 角色检查来实现强制访问控制；翻译结果将执行状态纳入上下文，跨模式切换不会误用 TLB。

**（4）快速路径与慢路径分离**
- **acall/aret 轻量级切换机制**：代理和宿主 Linux 共享同一进程页表，不改变 satp、不切换页表、不需 TLB 刷新。系统调用或异常从容器进入代理后，通过 acall 把控制转给所选 Linux 处理器；Linux 返回时经 aret 回到代理。只要服务不访问私有字节、不修改受保护状态，就完全不需要进入 M 模式。
- **M 模式介入场景**：当需要提交受保护页表项、访问 PRIV 页面数据（在 M 模式中复制）、执行 fork/COW 等安全敏感事务时，才通过 SBI ecall 进入 OpenSBI。

**（5）安全监视器提交受保护 PTE 更新**
- Linux 可以做 VMA 策略判断、分配物理页、构造候选 PTE，但所有这些只是"候选提议"，须经监视器验证目标 PTE 槽、PFN 角色、执行上下文后才能写入。
- 以 monitor 事务形式执行 **fork 复制安装（FORk_COPY_INSTALL）** 和 **COW 替换（COW_REPLACE）**：先把目标页面置为 PEND，在 M 模式下复制机密字节，再原子地发布 PTE 并提升为 PRIV，保证中间状态不暴露给 Linux。

**（6）容器生命周期集成**
- 注册、exec、调度窗口、fork/clone/exit、页错误、munmap、vDSO 等路径都保留了 Linux 原生机制，但在安全敏感边界（保护页表更新、私有数据访问、fork/COW）进入 OpenSBI。
- Linux 需增加 VM_NACC_APP VMA 标记和 _PAGE_NACC 软件 PTE 位来识别"候选私有区域"，用于 routing；但该标记不构成安全授权（Linux 不能自己把页面"声明"为公开）。

**（7）容器内共享与跨容器隔离**（目标设计）
- 同容器共享对象由代理做策略控制面，OpenSBI 记录对象/cid/权限/活动映射；detach 需撤销映射和残留 TLB。
- 跨容器访问要求有监视器可见的授权 grant，绑定 owner 与 generation 元数据，防止把别的容器的 PRIV PFN 映射进来。

## 6. 主要结论与发现

1. **可行性成立**：NACRE 的"宿主 Linux 承担资源管理、硬件/监视器承担安全权威"的原生路径在 QEMU 原型上可以有效运行。
2. **性能开销低**：lmbench 的 5 个指标中，NACRE 三次均值与 runc 基线偏差 **≤3.5%**；nginx 8 对象均值等权总吞吐量比基线低 **1.87%**（比率为 0.9813）。
3. **功能路径覆盖**：启动、私有内存、fork/COW、用户访问、teardown 路径均"能工作"。
4. **经验教训**：区分"快速路径"与"需 M 模式介入的慢路径"是避免频繁进入高特权层的关键；代理与 Linux 持有相同页表，通过 acall/aret 切换比地址空间切换更轻量。
5. **安全声明边界**：当前证据只支持"已覆盖的单容器正路径"的可行性，**不构成针对恶意宿主的完整保密性/完整性证明**。

## 7. 优点

- **问题定义清晰**：精准指出"硬件将资源管理权和安全权威混为一谈"这一根因。
- **保护粒度与容器语义匹配**：保护单元是动态进程组本身，非隔离地址空间或整机，兼容 fork/clone/exec/共享内存等原生语义。
- **创新轻量切换机制（acall/aret）**：实现同页表同特权级的受控转移，规避 satp 切换、TLB 刷新和 M 模式介入，是一个优雅的架构设计点。
- **职责分离架构**：M 模式只做安全提交，S 模式代理做高频中介，路径分离有效限制 TCB 规模。
- **透明的"提议-提交"模型**：Linux 构造候选状态、Monitor 验证提交，清晰表达不可信 OS 下"非授权"原则。
- **透明兼容性**：应用无需修改源码或更换编程模型，runc 仅增加一次注册调用。
- **工程实现完整度高**：跨 QEMU、OpenSBI、Linux、agent、runc 的纵向原型实现覆盖主要正路径，评估诚实且边界清楚。

## 8. 不足与局限

- **安全论证缺口明显**：
  - 注册路径依赖协作式 pid/cid 传递（不具备防伪造/过期成员关系的核心安全属性）。
  - 调度器 hook 是合作式的；恶意 Linux 可跳过，缺少不可绕过的调度绑定和新鲜度机制。
  - 缺少 owner/generation 元数据与精确槽位（exact-slot）授权，通用 PTE 接口"目的绑定"不完整。
  - teardown 缺少"撤销-冲刷-清除-再 NORM"的恶意宿主安全事务及失败回滚。
  - 无跨容器隔离、无可信共享对象模型、无多核安全代理入口、无认证启动/DMA 防护/远程证明实现。
- **原型的 QEMU 模拟特性**：所有性能数据来自软件模拟，不能代表真实 RISC-V 硬件时序行为，vDSO 的处理方式是侵入式的，可能影响真实系统上的兼容性。
- **可扩展性证据薄弱**：hackbench 显示创建/注册路径有显著额外开销（内部计时 1.50×、端到端 4.59×），且 CONTAINER_FULL 容量问题出现，但仅单次观察。
- **实验统计力度不足**：3 轮重复不足以区分小差异；缺少对管道延迟等混合样本的深入分析；nginx 矩阵未给出置信区间。
- **Iago 攻击边界**：代理不验证宿主服务语义，宿主可返回错误结果、延迟服务或拒绝服务，存在 Iago 攻击面。
- **移植性未验证**：Arm/x86 实现需重新设计；可能重新引入地址空间切换与额外的可信软件层，安全性/性能未讨论。
