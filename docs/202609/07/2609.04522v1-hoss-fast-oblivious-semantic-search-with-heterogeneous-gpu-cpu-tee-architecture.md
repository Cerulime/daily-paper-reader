## 摘要
语义搜索已广泛部署于现代AI系统，但保护数据内容和访问模式仍具挑战性。现有最先进系统 Compass 通过在 HNSW 图上构建优化的 ORAM 来实现 oblivious 语义搜索，但即使经过激进优化，其开销仍然很大。弥补这一性能差距在根本上是困难的：Compass 已消除了大部分密码学开销，使 ORAM 访问成为主要成本，而这受限于众所周知的 Omega(log N) 带宽下界。我们的关键洞察在于，传统 ORAM 的开销源于对私有内存有限的假设，而现代 GPU TEE 提供了大型私有内存（Pmem），可隐藏内部访问模式（Hunt et al., NSDI '23）。这一转变开辟了新的设计空间。因此，我们提出 Hoss，这是一种首创的 oblivious 语义搜索系统，采用异构 CPU-GPU TEE 架构，以低拥有成本实现快速、可扩展的搜索。在 Hoss 中，GPU TEE 的大型 Pmem 承载热路径 HNSW 遍历，而图的较低层若超出 GPU 容量，则卸载至 CPU TEE。系统仅在访问这些较低层时调用 oblivious 原语。大型 Pmem 的可用性还带来了新的优化机会，例如 Hoss 采用了主机访问 ORAM 机制，超越了传统性能限制，并整合了此前设计无法实现的若干数据依赖优化。我们实现了 Hoss 原型，并与 Compass 进行基准对比。结果表明，Hoss 在保持高召回率的同时实现了高达 67 倍的加速，且在规模扩大时收益更大。

## Abstract
Semantic search is widely deployed in modern AI systems, but protecting both data contents and access patterns remains challenging. The current state-of-the-art system, Compass, achieves oblivious semantic search by building an optimized ORAM over HNSW graphs. However, even with aggressive optimizations, it still incurs large overheads. Closing this performance gap is fundamentally difficult: Compass has already removed most cryptographic overheads, leaving ORAM accesses as the dominant cost, which are constrained by well-known Omega(log N) bandwidth lower bounds. Our key insight is that traditional ORAM overhead stems from the assumption of limited private memory, whereas modern GPU TEEs provide large private memory (Pmem) that blinds internal access patterns (Hunt et al., NSDI '23). This shift opens a new design space. We therefore propose Hoss, a first-of-its-kind oblivious semantic search system with a heterogeneous CPU-GPU TEE architecture that supports fast, scalable search with low cost of ownership. In Hoss, the GPU TEE's large Pmem hosts the hot-path HNSW traversal, while the lower layers of the graph, if they exceed GPU capacity, are offloaded to CPU TEEs. The system invokes oblivious primitives only when accessing these lower layers. The availability of large Pmem also enables new optimization opportunities. For example, Hoss features a host-access ORAM mechanism that goes beyond traditional performance constraints and incorporates several data-dependent optimizations that are not possible in prior designs. We implement a prototype of Hoss and benchmark it against Compass. Our results show that Hoss achieves up to 67x speedup while maintaining high recall, with larger gains at scale.

## 2. 方法论：核心思想与关键技术

### 2.1 总体架构（Heterogeneous TEE）
- **核心思想**：采用异构 CPU-GPU TEE 架构，**按 HNSW 的层结构进行划分**：
  - 上层图（热路径）驻留于 GPU TEE 的大 Pmem 中，支持快速的数据依赖遍历；
  - 当数据规模超出 GPU HBM 容量时，将**较低层图（以第 0 层为主）卸载至主机 CPU TEE**（拥有 TB 级安全内存）；
  - 仅当访问主机驻留低层时调用 oblivious 原语，且以此避免多 GPU 扩展带来的高 TCO，仅凭单一 GPU 即可扩展至 TB 级数据。
- **安全模型**：假设云软件栈、管理员及物理访问者不可信，可嗅探 PCIe、主机 DRAM、DMA 缓冲等外部信道；亦采用标准 TEE 保护（内存加密等）；不防范芯片去封装、功耗分析等侵入式攻击及共驻 GPU 攻击。

### 2.2 存储布局：排序线性表
- 常见图表示（邻接矩阵、邻接表）在 GPU 上碎片化严重、依赖指针追逐，且与 ORAM 紧凑地址空间语义不匹配。为此提出**排序线性表表示**：
  - 将每层图扁平化为按节点 ID 排序的紧凑线性表；
  - 为每个节点在跨层使用相同的临时 ID，ID 按从顶层到底层的顺序分配；
  - 利用 HNSW 邻居数上界 M 分配定长邻居槽，从而可通过"基址 + ID × 节点大小"实现 O(1) 直接寻址，完全消除指针。
- **物理映射的差异化设计**：
  - GPU 驻留层采用**分解布局**：图结构与嵌入分开连续存储，按 ID 直接索引，避免嵌入跨层冗余；
  - 主机驻留层采用**自包含记录**：邻居表与嵌入合并存储在同一记录中，使一次 ORAM 访问即可获取展开节点所需的全部数据，从而最小化跨 TEE I/O。

### 2.3 执行模型：自托管（Self-Hosted）+ CPU Bypass
- 传统 GPU 依赖 CPU 频繁启动短内核，会暴露细粒度数据依赖执行状态。Hoss 反其道而行之：将 **CPU bypass** 从 HPC 性能优化手段**重构为安全机制**。
- GPU 端运行一个**长驻留内核**，在设备端**自托管完整查询状态**，自主推进 HNSW 遍历、发起并管理所有 ORAM 调用：
  - **init_query**：warp 拉取查询、解码并初始化设备端上下文；
  - **upper_search**：在 GPU 驻留层执行贪心搜索，warp 内并行评估邻居与距离计算；
  - **layer0_search**：抵达主机层时切换到设备端 CORAM 访问，以有界候选/结果数组配合 warp 归约实现波束搜索（替代 CPU 式动态优先队列）；
  - **result_materialize**：设备端 top-k 选择并统一写回结果。
- CPU 仅负责持续投放查询至设备可见缓冲区，不介入逐步控制路径。

### 2.4 核心原语：GPU-Assisted Coalesced ORAM（CORAM）
- 直接采用经典 CPU ORAM 或照搬 BOLT 皆不可行（前者受 Ω(log N) 限制，后者面向通用 OMAP、条件分支繁重）。Hoss 从两条原则出发重新设计：（1）利用 HNSW 的独特语义；（2）使算法适配 GPU 的 SIMD 执行。
- **结构**：主机存储划分为 M 个定长块；GPU 内部维护稠密位置映射 MAP[1..M]、每块暂存队列（stash）S[1..M] 和条目缓存 EC。
- **工作流程（每次邻居展开）**：
  1. **Coalesce read（合并读）**：对邻居集 V 中每个节点查询 MAP 得到所在主机块，去重后形成块集合 B，以**批量、页对齐**方式向 CPU TEE 发出读请求（一次读取涉及的所有不同页）；
  2. **GPU 本地计算**：从读取页（或 stash，因部分记录可能已重映射但尚未写回）中抽取目标记录，在 GPU 内完成距离计算、候选过滤与前沿选择；
  3. **Batch random remap（批量随机重映射）**：每条访问记录以均匀随机方式重映射到新块，更新 MAP，并将记录暂存至目标块 stash 队列；
  4. **Eviction（逐出）**：仅对本轮读取过的块 B 执行：合并当前页内容与该块 stash 中的暂存记录，一次性写回。
- **安全设计要点**：
  - 若记录从 stash 命中，仍须发出对应的块读请求（dummy），避免泄露逐出状态；
  - HNSW 邻居列表中节点天然无重复，合并同轮访问不会改变访问分布的不可区分性——这是单纯通用检索负载做不到的、依赖于图搜索语义的优化。
- **Stash 优化**：拆分为负载（payload）与元数据两层；负载存于定长槽数组，元数据利用空闲池与反向索引（按块分行的 (node_id, slot_idx) 对）维护。重映射仅移动元数据关联；逐出只扫描当前块对应行。lane 0 处理关键控制更新，warp 其余 lane 协同执行查行、拷贝、填充等并行操作。

### 2.5 理论分析
- **安全性（Theorem 5.1）**：满足定义 3.1 的 HNSW 搜索 obliviousness——在相同遍历长度的两查询下，CORAM 主机访问的可观测块序列分布计算上不可区分（非合并与合并变体均安全）。
- **带宽（Theorem 5.2）**：非合并变体单次邻居展开带宽为 O(M · log N / log log N)（高概率），优于传统 ORAM 的 Ω(log N) 下界。
- **合并收益（Theorem 5.3）**：合并变体期望页读取数由 M 降至 M − Θ(M²/K)，即节省 Θ(M²/K) 次页读取（M = o(K)）。
- **Stash 上界（Theorem 5.4）**：均匀访问与随机重映射假设下，stash 大小以极高概率有界（含负漂移与集中不等式分析），不会无限增长。

## 6. 主要结论与发现

- **端到端性能**：Hoss 在全部数据集与召回档位上大幅超越 Compass，recall≈0.9 时获得至少 60×、最高 **99×**（正文宣称值）的加速；即使 Hoss 在 recall=0.98 的高精度档下运行，相比 Compass 在 recall=0.9 时仍可领先最高 45×。加速比随数据集规模增大而扩大。
- **oblivious 开销极小**：归一化结果显示 Compass 相对其明文基线的减速常超 100×（最高 357×），而 Hoss 大多低于 6×。
- **内存高效**：GPU 内存占用仅约总存储的 5.3%–5.6%（位置映射 + 最大 stash）；在所有压力测试中 stash 保持有界（<12% 数据条目）。据此推算，在 GH200-NVL（288 GB HBM）等平台上 Hoss 可扩展至 TB 级语义数据。
- **CORAM 相对 BOLT**：微基准中最高取得 101×（变数据条数）与 44×（变值大小）的加速；合并机制相对无合并批处理带来最高 1.8×、相对顺序模式最高 2.8× 的额外收益。
- **卸载更多层仅带来轻微性能退化**：全部层卸载相对仅卸载 L0 仅增约 6% 延迟（recall=0.9），高召回率下增量更小。
- **总体判断**：异构 CPU-GPU TEE 架构可有效突破经典 ORAM 的性能瓶颈，在保持高安全保证的同时实现与明文系统可比拟的高性能、低成本扩展。

## 7. 优点与亮点

- **视角创新**：敏锐识别 GPU TEE 大 HBM 满足经典 ORAM 对 Pmem 的定义要求，将"硬件架构变化"转化为"突破理论下界"的系统设计机会，为 oblivious 计算开辟新方向。
- **架构设计务实**：按 HNSW 层界做 CPU/GPU TEE 划分，兼顾安全性、单 GPU 的低 TCO 与 TB 级可扩展性，避免多 GPU 扩展的算力浪费。
- **存储与执行协同设计**：排序线性表表示同时满足 GPU 直接寻址执行与 ORAM 紧凑地址空间语义；CPU bypass 被重新诠释为防泄漏机制，GPU 自托管全程查询状态，减少主机干扰。
- **算法设计适配硬件**：CORAM 充分利用 HNSW 邻居天然无重复的特点实现安全合并读；用均匀随机重映射替代 BOLT 的 power-of-two 选择，以略微增加的渐进带宽换取 GPU 友好的无分支热路径，实际性能收益显著。
