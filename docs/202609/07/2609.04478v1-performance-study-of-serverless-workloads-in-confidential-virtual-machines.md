## 摘要
机密无服务器计算正迅速成为需要强机密性保证的应用领域（如医疗、金融和机器学习）的关键范式。为了在不信任的云环境中实现这一范式，机密虚拟机（CVM）通过加密整个客户机内存来提供隔离，从而保护无服务器工作负载免受主机级访问和干扰。然而，CVM对无服务器系统的影响仍未被充分理解。本文对CVM中的无服务器工作负载进行了实证研究，系统性地涵盖了在热启动和冷启动情况下的内存效率和运行时开销。我们的结果表明，CVM会产生显著的内存开销，因为加密内存禁用了跨虚拟机页面去重并降低了内存可回收性，从而在固定内存预算下限制了热容器容量。热启动中的运行时开销取决于工作负载。频繁发生VMEXIT（尤其是空闲转换）的工作负载会遭受显著的性能下降。这些性能下降还因常见的无服务器部署实践（即将vCPU分配与内存大小耦合）而进一步放大，因为更高的内存配置会暴露比某些函数能有效利用的更多的vCPU。对于冷启动，研究重点关注容器创建，这是启动延迟中一个常见且主要的贡献因素。基于内存效率结果，我们考虑了将同一函数的多个容器整合到同一个CVM中以提升效率的部署方式，并表明在这种设置下选择性放宽某些隔离机制可以大幅减少启动开销。这些结果阐明了机密无服务器计算的主要性能权衡，并提出了提高效率和降低延迟的实用方法。

## Abstract
Confidential serverless computing is rapidly emerg- ing as a critical paradigm for application domains requiring strong confidentiality guarantees, such as healthcare, finance, and machine learning. To enable this paradigm in untrusted cloud environments, Confidential Virtual Machines (CVMs) provide isolation by encrypting the entire guest memory, and thus securing serverless workloads against host-level access and inter- ference. However, the implications of CVMs for serverless systems remain insufficiently understood. This paper presents an empirical study of serverless work- loads in CVMs, systematically covering memory efficiency and runtime overhead on both warm-starts and cold-starts. Our results show that CVMs incur substantial memory overhead because encrypted memory disables cross-VM page deduplication and reduces memory reclaimability, thereby limiting warm- container capacity under a fixed memory budget. Runtime overhead in warm-starts is workload dependent. Workloads with frequent VMEXITs, particularly idle transitions, suffer substantial slowdowns. These slowdowns are further amplified by common serverless deployment practice that couples vCPU allocation to memory size, as higher-memory configurations expose more vCPUs than some functions can use effectively. For cold starts, the study focuses on container creation, a common and major contributor to startup latency. Motivated by the memory-efficiency results, we consider the deployments in which multiple containers of the same function are consolidated within the same CVM to improve efficiency, and show that selectively relaxing certain isolation mechanisms in this setting can substan- tially reduce startup overhead. These results clarify the main performance tradeoffs of confidential serverless computing and suggest practical ways to improve efficiency and latency.

## 2. 方法论：核心思想、技术细节与流程

论文方法论的核心是 **“按生命周期分阶段隔离测量 + 比较实验 + 受控消融 + 根因分析”**：

- **生命周期拆解**：将无服务器函数执行拆成四个阶段：VM/TD 启动、远程证明、环境初始化（冷启动主体）、函数执行（热启动）。作者沿用已有文献结果处理前两阶段，而将自有测量集中于“初始化”与“执行”阶段，因为这两者直接影响热/冷启动的用户感知延迟。
- **三配置对比法（隔离开销来源）**：在每个场景下比较三组配置：
  - 普通 VM + 开启 KSM（Kernel Same-page Merging）——作为“理想内存去重”基线；
  - 普通 VM + 关闭 KSM——用来单独量化“失去跨 VM 页去重”造成的开销；
  - CVM（TDX/SEV-SNP）——由于内存加密天然不能做跨 VM 去重，且可回收性受限，可通过与“KSM 关闭”组对比估计“可回收性进一步下降”带来的额外开销。
- **规模维度设计**：在内存效率上考察两类横向扩张：同一函数多个 VM（1 函数/VM × N 个 VM）和不同函数多 VM（3 个不同函数各 1 VM），并额外对比“4 VM 各 1 实例”和“1 VM 内 4 实例”的整合效应，以判断能否在单 CVM 内部用页共享弥补跨 VM 去重损失。
- **运行开销测量**：使用统一 OpenFaaS/Kubernetes 单节点部署，预置容器镜像和本机数据，规避网络抖动和镜像拉取干扰；测量各函数在热启动下每调用延迟，并统计 VMEXIT 的种类和频次，将延迟差异与 VMEXIT 类型关联。
- **受控消融/根因分析**：
  - 调节 PyTorch 使用的线程数（与 CVM vCPU 数对应）观察并行度带来的 HLT/VMEXIT 放大；
  - 切换客户机空闲策略从 HLT（halt）为 POLL（pause 自旋），以量化空闲转换引起的 VMEXIT 贡献；
  - 在本地测试台固定/分离 NUMA、注入 LLC 争用，解释矩阵乘法表现异常（并非 CVM 自身优势）；
  - 使用普通 VM 开启/禁用 PLE 来模拟 CVM 缺少 Pause-Loop Exit 机制的影响。
- **冷启动剖析**：直接测量 runc 容器创建时间，并结合 KernelShark 跟踪定位锁竞争和 cgroup 写路径瓶颈，最后在受限信任模型下测试三类“选择性隔离放松”的收益。

## 6. 主要结论与发现

- **内存效率（结论 1）**：CVM 内存开销主要是“失去跨 VM 页去重”带来的，与关闭 KSM 的普通 VM 接近；不可回收性会再增加少量开销。随着 VM 数量从 1 增至 4，CVM 相比 KSM 开启的普通 VM 的内存开销增量最高可达 120%~147%（大模型负载）。
- **对热容器容量的影响**：固定内存预算下，CVM 能缓存的热容器数量明显下降，从而推高冷启动率。将同一函数的多个容器整合进一个 CVM（如 1 VM-4 实例）能恢复大量共享页收益，是缓解该问题的有效方向。
- **热启动延迟（结论 2）**：CVM 热启动慢不普遍存在，而是负载相关。纯 CPU 或常规 I/O 负载基本无影响；高 VMEXIT 频率且 HLT 占比较高的负载明显变慢。以图像识别（Image Recognition，IR）为例，PyTorch 多线程造成的空闲转换放大使 CVM 延迟可达到普通 VM 的近 2 倍甚至更高；HLT 切为 POLL 后 IR 延迟从 347.8 ms 降到 31.8 ms，与普通 VM（30.8 ms）几乎无差。
- **部署模式的耦合放大**：无服务器平台把 vCPU 数随内存大小线性增加，会让“内存大但不需那么多并行”的负载产生更多同步和 HLT 退出，进一步恶化 CVM 表现。
- **系统级缓解的局限**：主机侧 halt polling 对短生命周期、相位变化快的 serverless 负载效果有限；而 CVM 缺少与 PLE（Pause-Loop Exit）等价的高效硬件支持，使 guest 自旋更难以控制，强制线程整合又会显著增加延迟。
- **冷启动（结论 3）**：容器初始化在短函数中占总执行时间约 65%；CVM 自身并不额外延长容器创建时间，但冷启动本身是机密 serverless 的主要延迟源。瓶颈来自：多 vCPU 的同步开销、CPU 配额不足、cgroup 写路径中 `WRITE|PERCPU` 引起的 `percpu_rwsem` 竞争。
- **优化验证**：在“同一函数各容器互相信任、不同函数/租户仍用 CVM 隔离”的受限威胁模型下，跳过 cgroup 分配可让 runc 启动时间降低 27%，绕过 seccomp 过滤约省 30 ms，复用已有容器网络命名空间约省 50 ms。

## 7. 优点

- **问题选择务实且重要**：抓住了 CVM 与 Serverless 结合时最容易被忽略的“内存密度—冷启动—执行延迟”耦合链，而不是仅照搬通用工作负载的 CVM 性能结论。
- **测量方法论严谨**：用“KSM 开/关 vs CVM”三配置拆分内存开销，用“HLT vs POLL”和“不同线程数”做消融，用“禁用 PLE”模拟 CVM 机制缺失，形成完整的因果链条。
- **跨平台验证**：同一关键负载在 Intel TDX 与 AMD SEV-SNP 上复验，证明了结论并非某一家厂商实现的特例。
- **敢于纠偏**：针对“CVM 上矩阵乘法反而更快”的意外现象，通过 NUMA/LLC 受控实验排除“CVM 本身更优”的错误解释，体现实验客观性。
- **攻击面分析清晰**：对容器隔离放松的讨论设置了明确的威胁模型与安全边界，没有把优化建议推广到互不信任容器的普遍场景。
- **结果可直接落地**：总结部分将冷启动优化分为“配置级、内核级、信任模型相关”三层，便于实践者按权限和风险选用。

## 8. 不足与局限

- **缺少真实多租户/大规模生产场景**：实验在单节点 OpenFaaS/自建 Kubernetes 和少量 VM 上进行，没有体现真实云上成百上千函数实例并发、动态扩缩容和 QoS 调度的综合效应。因此热容器容量和冷启动率的数值结论更多是“趋势性”而非“生产绝对值”。
- **CVM 机制覆盖不全**：Intel TDX 和 AMD SEV-SNP 覆盖较好，但未涉及 ARM CCA；也仅使用 KVM/QEMU 类虚拟化，未比较 Kata Containers、Firecracker 等轻量虚拟化与 CVM 的组合。
- **服务器less 平台单一**：只用了 OpenFaaS/单节点 Kubernetes，未考察 AWS Lambda、Azure Functions 等商业平台的内部差异；容器运行时也仅测了 runc。
