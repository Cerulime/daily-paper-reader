## 摘要
静态应用安全测试（SAST）工具可帮助开发人员在部署前发现漏洞，但误报会造成大量的分类工作。我们研究了Java安全分析中的CodeQL误报是否形成可重复出现、可解释的模式，并可通过改进分析来减少。我们在来自110个项目的167个CVE实例上运行CodeQL的Java安全查询套件，重点关注误报率最高的十个查询。我们手动审查了500个抽样的误报路径和位置，并构建了一个源级分类法。五个类别是：遗漏路径约束或净化（36.6%）、良性执行上下文（29.4%）、缺失信任边界建模（27.6%）、不精确的并发建模（5%）和不精确的汇点建模（1.4%）。在这些发现的指导下，我们实现了CodeQL改进，可在查询级别检测和过滤重复出现的误报模式。这些改进消除了81.8%的已审查误报。在整个选定查询数据集中，它们消除了15.8%的已报告路径和位置，同时保留了8个真阳性中的7个。这表明，尽管固定的改进通常依赖于项目特定上下文，但许多误报可以在分析中减少。为解决这一泛化差距，我们评估了代理式编码工具是否能将改进模式适配到新项目。在我们的模式作为模板的情况下，两个工具在56%和62%的任务上成功，查询编译通过率超过90%。没有这种指导，两者仅在28%的任务上成功，而编译率降至30%到36%。这些结果支持一种面向改进的SAST工作流程，其中重复出现的误报在CodeQL查询中被建模，并自动适配到不同项目上下文，从而减少重复分类工作。

## Abstract
Static application security testing (SAST) tools help developers find vulnerabilities before deployment, but false positives create substantial triage effort. We study whether CodeQL false positives in Java security analysis form recurring, explainable patterns that can be reduced by refining the analysis. We run CodeQL's Java security query suite on 167 CVE instances from 110 projects, focusing on the ten queries with the highest false positive rates. We manually review 500 sampled false positive paths and locations and construct a source-level taxonomy. The five categories are Missed Path Constraint or Sanitization (36.6%), Benign Execution Context (29.4%), Missing Trust Boundary Modeling (27.6%), Imprecise Concurrency Modeling (5%), and Imprecise Sink Modeling (1.4%).   Guided by these findings, we implement CodeQL refinements that detect and filter recurring false positive patterns at the query level. The refinements remove 81.8% of reviewed false positives. Across the full selected-query dataset, they remove 15.8% of reported paths and locations while retaining 7 of 8 true positives. This shows that many false positives can be reduced in the analysis, although fixed refinements often depend on project-specific context. To address this generalization gap, we evaluate whether agentic coding tools can adapt refinement patterns to new projects. Given our patterns as templates, the two tools succeed on 56% and 62% of tasks, with query compile-pass rates above 90%. Without this guidance, both succeed on only 28%, while compile rates fall to 30-36%. These results support a refinement-oriented SAST workflow in which recurring false positives are modeled in CodeQL queries and automatically adapted to different project contexts, reducing repeated triage.

### 核心思想

- 基于 CWE-Bench-Java 基准，先在真实 Java 漏洞项目（CVE 实例）上运行 CodeQL 的 Java 安全扩展查询套件，从误报路径/位置中人工归纳出源级分类法。

### 关键细节与流程

1. **运行与采样**：使用 CodeQL v2.25.4 与 Java 安全扩展套件（codeql/java-queries v1.11.2），对 CWE-Bench-Java 中 167 个可直接构建的易受攻击版本（110 个独立项目）进行扫描。按告警数量统计后，选取产生误报数量最多的 10 个查询；对每个查询随机抽取 50 条误报路径/位置，共 500 条进行人工审查（超过 95% 置信度、±5% 误差所需的最低样本量 382）。

3. **查询精化设计**：将分类法映射为 CodeQL 谓词。每种精化包括四个组成部分：来自 RQ1 的模式、适用规则（rule scope）、识别模式所需的程序证据（如路径、调用者、控制流、类型等）、以及抑制点。精化保守设计：只有存在明确的证据时才抑制，且对可能掩盖真实漏洞的情况会收紧条件的限制（例如，不被抑制敏感名称的值）。
4. **精化实现风格**：分三类——结构/语法证据式、局部语义证据式、项目上下文式；相关示例包括：受同一 receiver 和覆盖 finally 释放的锁不平报；增加授权上下文谓词等。

## 6. 论文的主要结论与发现

- **RQ1 结论**：人工审查 500 条误报，得到五层级分类：
  1. **遗漏路径约束或净化**（36.6%）：代码有实际约束或者显式/隐式保护（如路径检查、数值范围检查）而 CodeQL 未建模；
  2. **良性执行上下文**（29.4%）：告警发生在测试、示例、工具代码、部署引导、生命周期等，不暴露给不可信的攻击者；
  3. **缺失信任边界建模**（27.6%）：没有考虑该操作仅可由授权/特权角色/可信服务执行，或输出被限制在敏感记录中；
  4. **不精确的并发建模**（5.0%）：锁/生命周期获取-释放没有准确被建模；
  5. **不精确的汇点建模**（1.4%）：虽然到达了 sink，但实际 API 并不构成查询假定的风险（如内部流/传输，非渲染）。
  - 不同查询的误报主导原因显著不同（如 user-controlled-bypass 中以“控制流依赖”占 96%，path-injection 中以“显式验证或净化”为主，unreleased-lock 中以“平衡清理”为主 50%）。这说明误报模式是查询相关的，需要针对性的精化，而非一刀切过滤。
- **RQ2 结论**：设计出的精化谓词在 500 条已审查误报中去除了 **409/500（81.8%）**；在全选数据集上去除了 **3,158/20,000（15.8%）** 的已报路径/位置；真阳性保留率为 **49/56（87.5%）**（移除了 7 条真阳性，有些源自非生产类代码、信任值来源和显式验证谓词叠加的条件过于激进）。强类别去除率达 67.9%–100%，显示大量误报可在查询逻辑层面被编码、压制，但覆盖的许多模式依赖于项目特定上下文。
- **RQ3 结论**：从头编写 CodeQL 精化困难的设置（无引导）：Codex 与 Claude Code 各自仅在 14/50 任务上成功（28%）；编译通过率分别只有 30% 和 36%。在引导模式（让 agent 基于 RQ2 模板进行适配）下：Codex 编译率 90%（45/50）、成功 56%（28/50），Claude 编译率 92%（46/50）、成功 62%（31/50）。这说明把跨项目误报因果模式做成可复用模板可以让 agent 编码模型更有可能生成可运行的查询级精化。
- **整体结论**：误报不是随机噪声，而是可以通过源级证据归纳出来并模型化的模式；把模式编码为 CodeQL 查询精化，再用 agentic 工具自动项目化，就能在很大程度上减少重复的人工分诊工作。

## 7. 优点

- **系统性和可追溯性**：从“真实的 CodeQL 告警+人工审查证据”出发得出分类办法，并在每一条审查中保留主/辅助标签，形成可复现、可审计的分析链条，避免单纯告警级别的后处理。
- **面向查询级改进而非仅过滤**：结果是修正后的 CodeQL 查询，而不是针对特定文件/行的屏蔽，因而可在后续 CI 运行中复用、检查。
- **具有经济学意义**：文中提到的 RQ3 引导与无引导对比很直观地量化了“误报模式的实证是模板的核心价值”——无模板时 LLM agent 成功率只有 28%、编译率仅有 33%，有模板时达到 56%/62% 成功率、91% 编译率，对照组设计清晰，显式证明了实验证据在指导自动修复中的关键作用。
- **统计控制**：使用标准有限总体抽样公式计算样本量，确保手动审查样本在 95% 置信度内可代表总体。
- **共享细节**：提供复现包且包含所有提示与精化查询，有利于其他团队复现结果。
- **类别建模明确**：分类法细粒度（细到可建模为谓词的类别），并对易被掩盖真实漏洞的情况设置保守条件。

## 8. 不足与局限

- **覆盖范围有限**：只分析 Java、CodeQL、单一查询套件（security-extended），十个最高误报的规则；结论不一定适用于 Java 之外的生态、其他 SAST（如 SpotBugs、Semgrep）、非 Java 查询套件或低尾误报的查询。
- **人工审查的主观性**：误报分类基于评审者的项目威胁模型理解，存在主观偏差。
- **抽样不平衡**：每查询 50 条，虽然抽样足够反映单个查询的分布，但不同查询的总体规模和代表度差异并没有加权；在聚合整体分类时可能高估代表性差的查询的贡献。
- **精化会移除真正的告警**：RQ2 中真阳性保留率不是 100%（最多删掉 7 条真阳性），部分类别（如非生产代码、信任值来源等）条件相对不够精确，可能存在掩盖真实漏洞的风险。
- **固定精化的泛化不足**：一些依赖项目上下文（如授权检查、框架启动）的精化在另一些项目上无法生效，造成 15.8% 的全量误报清除率远小于 81.8% 的样本清除率。
- **RQ3 agent 有相当部分的失败原因仍是 CodeQL 语法与项目语义的建模难点**：即使有引导，仍有约 38–44% 的任务未成功（尤其是在 log-injection 和 path-injection 的规则上）；样本只有 50 个任务，分到 query 层后单条规则甚至只有几例，统计效力弱于全局水平，无法细粒度判断哪种模式更容易自动化映射。
- **资源与成本信息缺失**：论文并未披露 LLM agent 的 API 调用量、token 使用总量或评估成本；没有 GPU/算力细节和高负荷训练（此类主要是推理调用）。这些如果在复现时缺失会造成后续可能的不可比风险。
- **没有引入非 CodeQL 或非 benchmark 的额外验证**：实证评估基于 CWE-Bench-Java 的 CVE，项目不完全代表现实企业代码形态，已有报告与正/负样本划分是以某个漏洞为准，无法覆盖“该项目中其他真实漏洞”的情况，所以存在着假阳性/假阴性评估的局限。
