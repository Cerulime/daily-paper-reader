## 摘要
度量启动通过将执行软件和系统状态的加密度量记录到可信平台模块（TPM）中，扩展了对启动系统的信任，从而能够通过远程证明进行后续验证。尽管该机制在现代操作系统中日益普及，其实际安全性取决于实现是否在预期条件下度量了预期组件，但这一点并未得到系统性的检查。我们提出了一种平台无关的方法，用于在虚拟化的系统与TPM交互层面分析低级TPM使用情况。它能够独立重建和验证TPM事件日志，而无需依赖引用机制本身。由于不依赖于实现细节，它适用于开放和封闭系统。我们在Linux和Windows上演示了该方法，并对systemd版本245-258（2020-2025）的Linux系统进行了系统的纵向分析，考察了度量启动使用的演变，并观察到广泛的差异。在系统之间没有出现单一的使用模式，因此需要定制化的分析。该分析识别了未记录的行为变化，揭示了对用户空间systemd服务的不一致度量，这妨碍了此类系统上的可靠远程证明和LUKS磁盘解密。

## Abstract
Measured Boot extends trust in a booted system by recording cryptographic measurements of executed software and system state into a Trusted Platform Module (TPM), enabling subsequent verification through remote attestation. Although this mechanism is increasingly deployed in contemporary operating systems, its practical security depends on whether implementations measure the expected components under the expected conditions, yet this is not checked systematically.   We propose a platform-agnostic method for analysing low-level TPM usage at the level of virtualized system--TPM interactions. It enables independent reconstruction and validation of the TPM Event Log without relying on the quoting mechanism itself. Because it does not depend on implementation details, it is applicable to both open and closed systems. We demonstrate the method on both Linux and Windows and conduct a systematic longitudinal analysis of Linux systems with systemd versions 245--258 (2020--2025), examining how Measured Boot usage evolved and observing wide divergence. No single usage pattern emerged amongst systems, warranting customized analysis.   The analysis identifies undocumented behavioural changes, reveals inconsistent measurements of user-space systemd services, which prevent reliable remote attestation and LUKS disk decryption on such systems.

## 1. 论文的核心问题与整体含义

- **研究背景**：度量启动（Measured Boot）通过 TPM 记录引导过程中各组件的度量值，使远程证明能够验证平台运行状态。该机制在现代操作系统中日益普及，但其安全性取决于实现是否在预期条件下度量了预期组件。
- **核心问题**：现有方案无法系统验证"实现是否真正按文档要求进行了度量"，即 TPM 事件日志的完整性缺乏独立验证手段；已有研究主要依赖 TPM 引证（Quote）机制本身，无法提供独立证据。
- **整体含义**：论文提出一种平台无关、低侵入的观测方法，在**虚拟化的系统与 TPM 交互层面**捕获全部 TPM 命令流，从而在不依赖系统自身实现细节的前提下，独立重建和验证 TPM 事件日志。该方法适用于开放系统（Linux）和封闭系统（Windows），可检测 TPM 事件日志中的缺失、添加、重排或修改，为度量启动的安全保障建立了可重复的系统性审计基础。

## 2. 论文提出的方法论

- **核心思想**：将测系统运行于 QEMU 虚拟机中，使用软件 TPM（swtpm）替代真实 TPM。由于虚拟机与 TPM 的所有通信都必须经过虚拟化层，故在两者之间插入一个**拦截器（interposer）**即可观测全部 TPM 交互，进而独立重建 PCR 扩展序列。
- **关键技术实现（TPMSpy 工具）**：
  1. swTPM 通过 UNIX socket 与控制通道暴露通信接口，控制通道还负责动态协商独立的数据通道；
  2. TPMSpy 伪造 swtpm 的入口，在 QEMU 启动时被调用，随后启动真正的 swtpm 守护进程与自身中继模块，让 QEMU 连接到的实际是 TPMSpy 的 socket；
  3. 拦截器在 QEMU 与 swtpm 之间做消息中继，使双方通信透明，同时记录下所有 TPM 命令（如 PCR Extend）与响应；
  4. 数据流带有时间戳、通道标识及关联通道的元信息；模块化插件机制允许扩展观测或主动修改测量值以测试远端验证工具。
- **验证流程**：将捕获的 TPM 命令流与系统中存储的 TPM 事件日志进行对比，逐步核对两者在 PCR 扩展序列上的对应关系；该方法不依赖系统中实现的日志记录功能，也无需信任系统本身的报告。
- **与其它方法的对比**：论文列举了 TPM 事件日志分析、形式化验证、硬件探针、软件探针、虚拟化五种方法，认为虚拟化在独立性、非侵入性、完整覆盖和可部署性方面综合最优，但需要补上对 TPM 交互过程的可视化拦截，这正是 TPMSpy 的贡献。

## 6. 论文的主要结论与发现

- **针对 RQ1（日志可独立重建与验证）**：TPMSpy 能在多个系统平台上完整捕获和重建 PCR 扩展事件，独立于系统 TPM 事件日志和引证机制，因此可以验证日志的完整性。
- **针对 RQ2（系统各版本行为演变）**：systemd v245–v258 度量启动行为演化剧烈，存在多种模式并存，没有单一的模式。不同版本使用不同的 PCR（8、9、11、12、14、15 等）且扩展时机与粒度差异很大。
- **针对 RQ3（文档一致性）**：多数行为与 systemd 文档一致，但发现如下偏差：
  1. 在 v245 中观测到 PCR 8 扩展，但文档首次记载 TPM 测量是 v248；经查系统提交历史，该行为自 v230 即已存在但一直未文档化。
  2. systemd 用户空间工具（如 systemd-cryptsetup、systemd-pcrmachine 等）对 PCR 15 的测量以及内核 IMA 对 PCR 10 的测量，**没有写入 TPM 事件日志**，而是记录在 `/run/log/systemd/tpm2-measure.log` 或内核虚拟文件等其他日志文件里。
  3. 在 UKI 方案中如果仅靠 TPM 事件日志做远程校验，将无法验证实际度量 PCR 11、15 的用户空间组件状态；LUKS 卷密钥测量不会出现在常规 TPM 事件日志，导致依赖 TPM 引证 + 事件日志的远程解锁方案可能失效。
  4. 某些版本中 systemd-boot 从 PCR 8 切换到 PCR 12（v251 左右），改变了引证策略的预期；GRUB 与 shim 的 PCR 8 与 14 使用则与文档一致。
- **性能开销**：TPMSpy 带来的开销可忽略，适合部署于 CI/开发场景。

## 7. 优点

- **独立性**：观测在系统外部完成，不依赖系统自述的事件日志或对组件的信任，使恶意组件难以通过隐藏自身痕迹规避检测。
- **平台无关性**：适用于 Linux、Windows 等开放或封闭系统，无需源码、修改或签名驱动。
- **完整覆盖**：可捕获整个开机流程中 QEMU–TPM 交互的每次访问，避免了早期固件阶段软件跟踪盲点。
- **非侵入与可扩展性**：不需改动被观测系统内部软件或硬件；模块化设计方便对接数据分析和测量修改工具。
- **中继设计巧妙**：不修改 QEMU/swtpm 源码，而是在外部伪装 swtpm 调用接口完成透明中继，减小了版本更新导致的兼容性问题。
- **工程可复现性好**：自动化脚本、可配置实验环境、差异分析流程与数据均已开源，能够在持续集成环境中运行。
- **发现真实问题**：不仅验证文档，还识别出了未记录的度量行为、日志归属不一致等真实安全与可用性问题。

## 8. 不足与局限

- **无法检测"未发生的测量"**：TPMSpy 只能看到实际发出的 TPM 命令，对于应当被度量但完全没有被度量的组件不会产生事件，因此无法发现"未测组件"类缺陷；作者也承认这一限制，建议与静态分析或代码审查结合。
- **上下文不足**：跟踪包只有时间戳及通道元数据，不能直接指出哪个进程/组件发起了 TPM 命令；准确归属需要额外增加虚拟机内状态查询工具。
- **固件层分析深度有限**：对 PCR 0–7 只能做跨运行对比，没有可参考的文档化语义，难以判断特定固件行为是否正确或是否有恶意改动。
- **Windows/封闭系统的验证缺少深度**：论文只证明了可捕获模式，但没有对其度量行为（如特定 PCR 语义）做出严谨结论，远程引证管理员很难具有可操作性。
- **威胁模型的边界**：该方法假定主机、虚拟化层与软件 TPM 可信；如果系统恶意控制虚拟化层，保护将失效。
- **未覆盖全部生态**：重点讨论了 systemd 生态，未涉及其他引导器或发行版以及安全启动的完整对抗实例验证；LUKS 与 systemd 的度量方案在其他版本配置下可能还需额外适配。
