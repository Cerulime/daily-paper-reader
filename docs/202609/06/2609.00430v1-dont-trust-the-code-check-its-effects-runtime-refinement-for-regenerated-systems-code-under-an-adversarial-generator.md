## 摘要
近期的工作使用大型语言模型从规范生成系统代码，将规范视为持久工件，而将实现视为可丢弃的。重新生成实现使其专门针对每个工作负载和设备。然而，该工作处于一个宽容的环境中：组件的外部可见效果（其写入和设备命令）是可恢复的，并且生成器是诚实的，因此通过重新执行来解除信任。我们针对的是不宽容的环境：其效果不可逆的系统代码，由可能具有对抗性的生成器产生。在这种情况下，重新执行无法事后检查效果，而当假设不成立时，证明会悄然失败。我们采取的立场是，此处唯一安全的操作方式是拒绝生成的代码采取行动的权限。生成的代码仅进行规划，而固定的受信任中介拥有所有效果，并且仅在规范本会产生该效果时才执行一次。由于保证存在于中介中，而非代码中，因此它在重新生成后依然有效。我们将其实例化为针对再生设备驱动程序的参考监视器，并刻画了可中介性包络，即效果词汇表上的六个条件：可读性、规范输入可观测性、可关联性、完备性、结果可枚举性和显式持久性。它们决定了此类中介何时是可能的。

## Abstract
Recent work uses large language models to generate systems code from specifications, treating the specification as the durable artifact and the implementation as disposable. Regenerating the implementation specializes it to each workload and device. However, that work lives in a forgiving setting: a component's externally visible effects, its writes and device commands, are recoverable, and the generator is honest, so trust is discharged by re-execution. We target the unforgiving setting: systems code whose effects are irreversible, produced by a generator that may be adversarial. There, re-execution cannot check an effect after the fact, and a proof fails silently when its assumptions do. We take the position that the only safe way to operate here is to deny the generated code the authority to act. The generated code only plans, while a fixed trusted mediator owns every effect and performs one only when the specification would have produced it. Because the guarantee lives in the mediator, not the code, it survives regeneration. We instantiate this as a reference monitor for regenerated device drivers, and characterize the mediability envelope, six conditions on the effect vocabulary: legibility, spec-input observability, correlatability, completeness, outcome enumerability, and explicit durability. They decide when such mediation is possible.

  - 生成器是诚实的（honest），不会恶意偏离规范；
  - 组件的外部可见效果是可逆/可恢复的；
  - 信任通过**重执行**（re-execution）来解除：验证失败后重新生成即可。
- **本论文转向的"非宽容环境"**（unforgiving setting）：
  - 系统代码的效果**不可逆**（如磁盘写入、设备 DMA 命令、发往外部的包，一旦抵达即无法召回）；
  - 生成器可能是**对抗的**（被攻陷的供应商、中毒训练数据或提示注入均可导致出格实现）；
  - 重执行无法在事后检查不可逆效果；形式验证的若干前提（可检查证明、完备主机模型、可信编译链、已验证代码与实际运行二进制绑定）在对抗生成器场景下会静默失效。
- **核心洞察/基本立场**：面对不可逆效果与对抗生成器，验证代码本身不足够——**唯一安全方式是拒绝生成代码本身具备执行权限**。代码只能“提议”（plan/propose）效果，由固定的可信中介（mediator）判断该效果是否与规范一致，再决定是否执行。由于安全保证位于可信中介而非生成代码中，该保证**在每次重新生成后依然成立**。

## 2. 方法论：核心思想与关键技术细节

### 2.1 总体架构：提议—提交分离（Proposal-Commit Separation）

- 以设备驱动为运行实例，构建信任边界：生成的设备驱动处于**不可信、受限**环境中，只能调用 `Observe` 和 `Propose` 两类接口；一个**固定、手写的可信中介**独占所有效果原语（MMIO、DMA），只有在效果被判定为规范所允许时才会执行。
- 协议消息流程：
  1. **Dispatch**：内核块请求先进入中介，由中介分发给受限的生成驱动；
  2. **Observe**：驱动向中介请求查看规范抽象状态（空闲队列槽、DMA 授权），中介返回状态快照与一份**密封令牌**（sealed token，绑定请求、状态版本号、有效期，驱动不可伪造）。后续观察会使先前令牌失效；
  3. **Propose**：驱动只能提交一个设备命令（含所持令牌）作为尝试性效果，不可附任何解释性说明；所有字段均视为不可信证据；
  4. **Validate**：中介在提交锁下重新校验令牌（防重放、过期、失效）、将自己持有的挂起请求与提议逐字段比对（请求字段由中介从内核请求重推导，不采信驱动的说法）、并检查自由选择字段是否落入规范允许集合；Validate 无论通过与否都会消费令牌，防止同一请求通过重放令牌产生第二个效果；
  5. **Commit/Reject**：只有 Validate 通过后中介才调用可信效果原语；读取实际结果后，依据规范（而非驱动）确定抽象状态转移并记入只增提交日志。Validate 失败则在不可逆效果执行之前拒绝，外部不可见。

### 2.2 规范结构（以 WRITE 子句为例）

- 中介持有的规范是**接口级别**的转换关系（与具体实现无关），只描述挂起请求、队列空闲槽、DMA 授权与结果之间的映射，而非设备内部机制。
- `permit` 区分两类字段：
  - 由规范固定、中介从请求本身重推导的字段（如 LBA、长度、DMA 源）；
  - 留给驱动自由选择的唯一字段（如队列槽号，且受观察得到的空闲集合约束）。
- `outcome` 将效果原语可能的返回值封闭为有限集合（如 WRITE 仅 `ok`、`EIO`、`short(n)`），每个结果对应固定的抽象状态转移（如 `req.done`、`req.failed`、`req.partial(n)`），使中介无需驱动回报即可判定后续状态。

### 2.3 正确性结论（Guarantee）

- 声称应达到的保证是**已提交轨迹安全性**（committed-trace safety）：所有已提交的外部可见效果序列都是规范在声明效果词汇上允许的某个轨迹的前缀。
- 保证成立依赖一系列条件：规范与解释器正确、中介无旁路且完全中介（complete mediation）、效果原语可信、提交严格串行化、结果可枚举、以及明确的崩溃模型。
- 明确**不包括**：活性/可用性（对抗驱动的沉默或最差合法提议）、时间侧信道、规范本身缺陷。

### 2.4 可中介性包络（Mediability Envelope）

论文将"规范所处于的接口抽象层级"称为规范的**高度**（altitude），并提出**六个条件**判定一个效果词汇表是否能被可靠中介：

| 类别 | 条件 | 含义 | 满足的例子（设备命令） | 失败的例子（文件系统块写） |
|---|---|---|---|---|
| 词汇须提供（由高度决定） | **可读性 Legibility** | 从单一效果本身即可识别所属操作 | 设备命令自带编码区分 READ/WRITE | 同一块写既可能是 mkdir、rmdir、rename 或损坏的结果，无法还原意图 |
| | **规范输入可观测性 Spec-input Observability** | 中介能观察到转换读取的每个输入（如授权、凭证） | 可观测 DMA 授权缓冲区 | 块层剥离了调用者的权限凭证，无法在更低层级做基于权限的判定 |
| | **可关联性 Correlatability** | 效果能按操作归组并在并发下获得可恢复顺序 | 命令自定界，一次提议一个事务 | 并发操作的交错无标记写无法归组，物理写序与提交序可能偏离 |
| 部署须提供（由工程决定） | **完备性 Completeness** | 每条外部状态变化都经由可信中介；无第三方路径 | 通过 IOMMU 与授权缓冲区将 DMA 纳入中介 | 组件已有的可写共享映射构成旁路 |
| | **结果可枚举性 Outcome Enumerability** | 原语输出结果构成封闭可枚举集合，可在返回瞬间分类 | WRITE 输出封闭为 3 类 | 不可枚举的输出空间使中介提交时被迫猜测 |
| | **显式持久性 Explicit Durability** | 持久性须作为头等效果（如 flush/barrier）被显式提议 | 显式提交 flush 并由设备确认 | 隐式持久性需中介重建屏障纪律，崩溃截断难以审计 |

- 核心规则：**在规范自身的接口层级（高度）上做中介，绝不降到其下**；低于该层级，中介等于在替组件重实现读路径、并发控制和恢复机制，超出可中介包络。在包络之内还须将完备性、串行化、结果封闭与持久性作为独立工程问题处理。

## 6. 论文的主要结论与发现

- **结论 1（信任重置）**：对可再生的系统代码，信任应当从"代码工件"转移到"效果权威"：生成代码仅做规划，固定可信中介独占并裁判每个外部效果。
- **结论 2（保证跨再生存续）**：由于安全性驻留于不随实现变化的中介与规范，每次重新生成不再需要重新证明/重新验证，代码再生成不会获得任何新权限。
- **结论 3（架构可行性）**：将该模式实例化为设备驱动的参考监视器，在体系结构上自洽（令牌、观察-提议-验证-提交协议、串行提交锁、追加日志、IOMMU 授权完整覆盖了请求生命周期）。
- **结论 4（包络限制）**：技术路线并非普遍适用；**六个条件**（可读性、规范输入可观测性、可关联性、完备性、结果可枚举性、显式持久性）清晰刻画了"何时能中介"，并指出唯一安全的分界线是"规范自身的接口高度"，之下即超出包络、需要重实现组件本身。
