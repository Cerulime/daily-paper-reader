## 摘要
我们提出了 ZIMPAF（运行时解释器插桩）和 RedPhuzz（模糊测试器），以解决当前最先进的模糊测试器的关键局限性：低效的插桩、缺乏对执行环境的了解以及有限的 Web 领域知识。ZIMPAF 实现了一种新颖的多粒度运行时解释器插桩，可提供分支覆盖率、稳健的错误和异常日志记录、函数和语言结构监控，以及识别分支指令中使用的用户提供输入。该插桩能够识别参数被污染的可能存在漏洞的函数，将其标记为高价值模糊测试目标，而无需执行污点分析。它还采用了一种新颖的后向常量探测来推断参数源自常量的可能漏洞函数，表明其无漏洞性并允许跳过它们。RedPhuzz 利用这些信息执行高度针对性的函数和输入级模糊测试，超越了简单的基于错误的模糊测试，还通过多阶段漏洞检测来发现隐蔽漏洞。我们还引入了三种新颖的变异策略以实现高度针对性和有效的模糊测试：净化感知变异、分支中输入感知变异和数据类型感知变异。我们使用六个基准 Web 应用程序中的 86 个测试用例，将 RedPhuzz 的性能与其前身（Phuzz）进行了评估。RedPhuzz 检测到了所有漏洞，而 Phuzz 未能检测到 16 个。尽管执行了更多任务，RedPhuzz 比 Phuzz 快 73%。ZIMPAF 比 Phuzz 的插桩（PCOV 和 UOPZ）更快，同时写入的数据量显著更多。在五个抽样的基准测试中，ZIMPAF 的吞吐量比 PCOV 和 UOPZ 高 2.1 到 41.22 倍，而在一个基准测试中为 0.87 倍。

## Abstract
We present ZIMPAF, runtime interpreter instrumentation, and RedPhuzz, a fuzzer, to address key limitations of state-of-the-art fuzzers: inefficient instrumentation, the lack of knowledge of the execution environment, and limited web domain knowledge. ZIMPAF implements a novel multi-granular runtime interpreter instrumentation that provides branch coverage, robust error and exception logging, function and language construct monitoring, and identification of user-supplied inputs used in branch instructions. The instrumentation is capable of identifying potentially vulnerable functions whose parameters are tainted, marking them as high-valued fuzzing targets, without performing taint analysis. It also employs a novel backward constant probe to infer potentially vulnerable functions whose parameters originate from constants, indicating their invulnerability and allowing them to be skipped. This information is utilized by RedPhuzz to perform highly-targeted function-and input-level fuzzing that goes beyond simple error-based fuzzing, but also detects silent vulnerabilities via multi-stage vulnerability detection. We also introduce three novel mutation strategies to achieve highly targeted and effective fuzzing: sanitization-aware, input-in-branch-aware, and data type-aware mutation. We evaluate RedPhuzz's performance with its predecessor (Phuzz) with 86 test cases across six benchmark web applications. RedPhuzz detects all vulnerabilities, while Phuzz fails to detect 16. RedPhuzz is 73% faster than Phuzz despite performing more tasks. ZIMPAF is faster than Phuzz's instrumentation (PCOV and UOPZ), while writing significantly more data. ZIMPAF achieves 2.1 to 41.22 times higher throughput than PCOV and UOPZ across five sampled benchmarks, and 0.87 times for one.

## 1. 论文核心问题与整体含义  
- Web 应用模糊测试长期存在三大瓶颈：  
  - **插桩效率低下**：现有工具（如 PCOV、UOPX）或通过全局 hook 导致开销大，或通过修改解释器源码（如 Witcher、Atropos）丧失可移植性和可维护性。  
  - **缺乏执行环境知识**：模糊器仅依赖 HTTP 响应或简单错误码，无法感知内部函数调用、参数来源和 sanitization 链条，导致漏报或无效变异。  
  - **Web 领域知识欠缺**：未利用数据库元数据、数据类型、参数引号信息及 sanitization 函数等，使变异盲目、路径穿越困难。  
- 论文旨在设计一套高保真（high-fidelity）的灰盒 Web 模糊测试框架，兼顾高效插桩与深入语义理解，以全面检测隐蔽漏洞并提升测试速度。

## 2. 方法论  
### 2.1 总体架构  
- 由后端运行时插桩 **ZIMPAF**（PHP 扩展）和前端模糊器 **RedPhuzz**（Python）组成，二者通过 Web 服务器与数据库协同工作。  

### 2.2 ZIMPAF：多粒度运行时解释器插桩  
- **分支覆盖采集**：绕过全局解释器主循环，仅在 16 个条件跳转/比较类 Zend 操作码处挂钩，记录 `(文件路径, 用户代码行号, 布尔结果)` 三元组作为路径指纹。这种细粒度挂钩一次安装，所有请求共享，大幅降低开销。  
- **分支参数识别**：在分支操作码处理中直接比对操作数的指针或值与 PHP 超全局数组（`$_GET`、`$_POST` 等），找出由用户输入控制的分支条件，存入日志供模糊器驱动路径探索。  
- **错误与异常日志**：三层捕获机制——拦截 `zend_error_cb`、注册错误观察者链、挂钩 `ZEND_THROW` 操作码，确保即使解释器 bailout 或用户代码压制错误也能完整记录。  
- **函数/语言结构追踪与后向常量探针**：  
  - 对 74 个潜在漏洞函数和 36 个 sanitization 函数挂钩其内部 C 实现，直接获取参数和返回值。  
  - 同时挂钩 `include/require`、`eval` 等语言结构操作码。  
  - 每个被挂钩点立即启动**后向常量探针**：沿调用者帧的操作码数组反向遍历，利用 `SendVar`、常量赋值、字符串拼接等操作码，判定 sink 参数是否完全由编译期字面量构造。若来自常量，则标记该调用为不可利用，随后被 RedPhuzz 跳过。  
- 所有日志（覆盖率、分支参数、函数追踪、异常）均按请求缓冲，在 `RSHUTDOWN` 批量写入文件系统。

### 2.3 RedPhuzz：领域感知的高保真模糊器  
- **覆盖率分析器**：先计算当前路径哈希，若哈希已存在则快速跳过；若为新路径，提取唯一三元组并聚合，创建新输入种子。  
- **追踪分析器与元数据获取器**：  
  - 解析函数/语言结构日志，识别潜在漏洞函数、sanitization 调用链以及 `die/exit` 提前终止点。  
  - 标记被常量探针判定为安全的函数为“不可利用”，并从目标列表移除。  
  - 利用参数值字符串匹配，定位哪些用户输入进入 sink（污点推断）。  
  - 对于 SQL 注入相关函数，调用 `SQLGlot` 解析查询，再通过数据库驱动获取列类型、是否引号包裹等元数据。  
- **分支参数分析器**：统计所有由用户输入控制的分支及其操作符、当前值，用于后续变异。  
- **函数与输入级模糊测试协调器**：  
  - **输入级模糊**：无漏洞函数时执行，利用“带净化函数的输入变异”、“分支参数翻转”和通用随机变异探索新路径。  
  - **函数级模糊**：当发现潜在漏洞函数后，按污点 sink 数量排序，针对性执行三种检测：  
    1. **基于错误的检查**：直接分析 ZIMPAF 提供的错误日志，并通过 SQL 错误码区分语法错误（漏洞）和语义错误（bug）。  
    2. **基于函数的检查**：提交语义正确但恶意的 payload（如符合 SQL 语法但引入 `OR 1=1`），检查返回值是否成功且恶意串存在于 sink，判断函数是否真正可利用，避免仅依赖错误码导致的漏报。  
    3. **安全序列检查**：用硬编码的安全模式（如 `prepare → bind_param → execute`）验证当前调用链是否有效防护，若满足则停止对该函数的进一步模糊。  
- **参数变异器**：  
  - **字典变异**：按漏洞类别维护恶意 payload 字典，区分引号/数值型 SQL payload。  
  - **净化感知变异**：逆序还原 sanitization 函数（如对 `base64_decode` 输入先进行 `base64_encode`），从而突破过滤屏障。  
  - **分支内参数变异**：根据分支操作符翻转条件（如 `>` 改为 `<=`）或保持当前路径不变以深入目标函数。  
  - **数据类型感知变异**：利用数据库元数据生成符合列类型的值（如 DATE、INT），或故意违反约束以暴露 bug。

## 6. 主要结论与发现  
- RedPhuzz 检出全部 86 个漏洞/缺陷，Phuzz 漏掉 16 个（包含 8 个其原始论文中提及但未正确分类的漏洞，以及 7 个语言构造相关漏洞）。  
- 在两者同时检出的缺陷上，RedPhuzz 整体速度快 73%（例如 `joomsport` 插件中耗时 176 vs Phuzz 未检测；Phuzz 仅测试 11 分钟后无果）。  
- ZIMPAF 插桩吞吐量远优于 PCOV+UOPZ：五个基准下吞吐量提高 2.1 至 41.22 倍，仅一个基准略低（0.87 倍），且 ZIMPAF 额外输出了函数追踪、分支参数等更多高维信息。  
- 后向常量探针可提前过滤约 41% 的“伪漏洞”函数，大幅减少无意义变异。  
- 净化感知和分支参数感知变异是突破复杂前置条件、触及深层漏洞的关键。

## 7. 优点  
- **系统性的插桩创新**：在解释器层面实施细粒度分支挂钩、语言结构挂钩、多级错误捕获，同时避免全局 hook 和源码补丁，兼顾效率、可移植性和完整性。  
- **零污染分析的高价值目标识别**：通过后向常量探针和参数字符串匹配，无需静态污点分析即可准确区分可污点 sink 与不可利用调用。  
- **多阶段漏洞验证**：基于错误的检测负责快速发现，基于函数利用的检测覆盖无报错漏洞，安全序列检查降低误报，三者结合显著提升准确率和召回率。  
- **高度适应性变异策略**：将净化函数、分支条件、数据库类型三类 Web 核心知识融入变异器，使模糊器能“理解”应用逻辑，而不仅仅是随机突变。  
- **开源并提供 Docker 环境**，有利于后续研究和工业界部署。

## 8. 不足与局限  
- **输入仍需手动预置**：RedPhuzz 依赖事先提供的 JSON 输入文件，尚未实现自动端点发现和全自动输入生成，降低了端到端自动化程度。  
- **净化感知变异支持有限**：目前仅对少数净化函数（如 `base64_decode`）完成逆推逻辑，复杂正则过滤（`preg_replace`）等尚未覆盖，导致个别用例耗时偏长。  
- **SQL 解析鲁棒性**：当遇到错误 format 的 SQL 语句时，SQLGlot 可能解析失败，使数据类型推断回退，影响变异针对性。  
- **泛化性验证局限于 PHP**：框架深度集成 Zend 引擎，虽有效但限制了直接迁移到其他解释型语言（Python、Ruby 等）。  
- **实验未涉及更复杂的二阶漏洞**（如 `sqli_high`）及某些极端场景（如正则拒绝服务），缺少对吞吐量方差、系统资源占用等更详细的 profiling。  
- **安全序列检查依赖人工梳理的模式**，虽有效但覆盖度有限，未来需考虑自动挖掘安全调用序列。
