## 摘要
eBPF 允许开发者用自定义的数据包处理、跟踪和调度逻辑扩展 Linux，并且验证器在执行前证明代码不会使内核崩溃。然而，编程模型是碎片化的：单个应用程序跨越内核代码、用户空间加载器和共享映射，但这些组件之间的关系并未得到检查。例如，在两端定义不同的映射或事件类型会悄悄破坏共享状态。我们观察到这些跨边界关系重复了可以由类型系统统一的信息。我们提出 KernelScript，一种将映射、程序句柄和执行域在一个源文件中进行类型化的领域特定语言，然后通过原始工具链编译为标准 C。我们在涵盖 XDP、TC、kprobe、tracepoint 和 struct_ops 的 43 个 eBPF 工作负载上评估了 KernelScript。KernelScript 在编译时拒绝标准 C/libbpf 仍能构建和加载的跨边界错误，统一的源文件将跨边界更改的差异缩小 5 倍，并且生成的代码与现有工具链保持兼容。

## Abstract
eBPF lets developers extend Linux with custom packet processing, tracing, and scheduling logic, and a verifier proves before execution that the code will not crash the kernel. The programming model, however, is fragmented: a single application spans kernel code, a userspace loader, and shared maps, yet the relationships among these pieces go unchecked. E.g. A map or event type defined differently on each side silently corrupts shared state. We observe that these cross-boundary relationships duplicate information that a type system can unify. We present KernelScript, a DSL that types maps, program handles, and execution domains in one source, then compiles to standard C through the original toolchain. We evaluate KernelScript on 43 eBPF workloads covering XDP, TC, kprobe, tracepoint, and struct_ops. KernelScript rejects cross-boundary bugs at compile time that standard C/libbpf still builds and loads, a unified source shrinks the diffs for cross-boundary changes by 5x, and generated code remains compatible with the existing toolchain.

### 2. 论文提出的方法论

KernelScript的核心思想是设计一种 **跨边界类型化的领域特定语言（DSL）**，让开发者在 **单个源文件** 中编写eBPF入口点、用户态控制流、Maps和Ring Buffers。编译器对这些跨边界结构进行统一的类型检查，然后生成标准的C代码和Makefile，再通过现有的工具链（clang, bpftool, libbpf）生成最终二进制文件。

关键技术细节如下：

*   **统一类型化模型**:
    1.  **执行域（Execution Domains）**: 为每个函数标记执行域属性（例如`@xdp`, `@tc`, `@helper`, `@kfunc`或默认的用户空间）。编译器会检查函数签名是否符合其执行域的约束（例如`@xdp`要求特定的上下文和返回类型），并拒绝跨域的非法调用。
    2.  **类型化Maps（Typed Maps）**: Map被声明为带类型的全局变量（如`var m : hash<K,V>(N)`），而不是在C中通过`SEC(".maps")`和分散的用户态代码来定义。编译器会在所有Map访问点（内核侧和用户侧）检查键和值的类型是否匹配，在编译时捕获类型错误。
    3.  **带生命周期的程序句柄（Program Handles with Lifecycle）**: 类型系统区分 **函数引用（FunctionRef）**和 **已装载程序句柄（ProgramHandle）**。`load`函数接收一个`FunctionRef`并返回一个`ProgramHandle`，而`attach`和`detach`函数只能接受`ProgramHandle`。这在编译时就强制了“先装载后附加”的顺序，并将“装载前附加”这类逻辑错误转变为类型错误。

*   **编译时安全性增强**: KernelScript能够有效在编译时拒绝那些标准C/libbpf可以成功构建、加载，但会导致隐蔽运行时错误（如数据截断、字段错位）的跨边界Bug。

### 7. 优点

*   **方法论创新**: 将eBPF内核/用户态割裂开发的痛点提炼为“类型信息重复”问题，并通过设计跨边界类型系统优雅地解决。
*   **实用主义设计**: 没有试图取代强大的底层工具链（clang, libbpf），而是作为代码生成器架设在其之上，这大大降低了推广和部署的阻力，保证了与内核社区的兼容性。
*   **问题导向明确**: 技术方案（执行域、类型化Maps、生命周期类型）直接对应现实中存在的几类典型Bug（上下文类型错误、Map类型不匹配、错误的附加顺序）。
*   **实验验证扎实**: 涵盖了从静态错误检测到动态性能和兼容性的多维度评估，尤其在Bug捕获和代码变更成本上的实验设计很有说服力。

### 8. 不足与局限

*   **生命周期状态的约束不完整**: 类型系统仅强制了“装载”必须在“附加/分离”之前，但**未跟踪完整的路径敏感状态**。例如，它无法在编译时防止“在分离后继续使用句柄”、“重复附加”或“句柄泄漏”等错误。
*   **性能评估范围有限**: 性能测试仅覆盖了最简单的XDP程序（pass和计数器），对于更复杂的、包含大量Map操作或复杂逻辑的程序，其生成代码的性能是否依然没有损失是未知的。
*   **对快速演进接口的依赖**: 论文提到可以使用`include`和`extern`声明作为访问原始头文件的回退方案，这说明当面对极其新颖或非标准的eBPF特性时，DSL本身的抽象可能滞后，需要开发者使用“逃生舱”，这可能重新引入类型不一致的风险。
*   **缺乏大型项目的验证**: 评估工作负载数量虽然不少，但似乎都是较小规模的示例或测试程序。该方法在大型、复杂的工业级eBPF项目中的适用性和有效性有待进一步验证。
