## 摘要
硬件黑客竞赛已成为评估复杂片上系统（SoC）设计安全弱点的实用平台，同时促进了安全感知验证和工具开发。本文通过开放式硬件黑客竞赛对SoC安全验证进行了系统研究，重点关注实用的漏洞分析策略、观察到的发现以及安全感知验证的经验教训。我们提出了一种多策略漏洞分析方法，结合了基于仿真的验证、形式化验证、lint分析、大语言模型（LLM）辅助漏洞检测以及覆盖引导的混合模糊测试。通过分析具有代表性的漏洞发现，展示了不同技术如何暴露互补类别的安全缺陷，并得出了用于硅前安全验证的实用经验教训。最后，我们讨论了竞赛基准如何支持新兴硬件安全技术的可重复评估，并指导未来安全感知的EDA研究。

## Abstract
Hardware hacking competitions have emerged as practical platforms for evaluating security weaknesses in complex System-on-Chip (SoC) designs while promoting security-aware verification and tool development. This paper presents a systematic study of SoC security verification through open-box hardware hacking competitions, focusing on practical vulnerability analysis strategies, observed findings, and lessons for security-aware verification. We present a multi-strategy vulnerability analysis methodology, combining simulation-based verification, formal verification, lint analysis, Large Language Model (LLM)-assisted bug detection, and coverage-guided hybrid fuzzing. Representative vulnerability findings are analyzed to illustrate how different techniques expose complementary classes of security flaws, and we derive practical lessons for pre-silicon security verification. Finally, we discuss how competition benchmarks can support the reproducible evaluation of emerging hardware security techniques and guide future security-aware EDA research.

## 2. 论文提出的方法论

### 2.1 总体工作流程

论文提出一个四阶段分析工作流：

1. **环境构建与基线建立**：编译RTL，运行可用的测试、形式化、lint流程，建立设计基线。
2. **多策略漏洞候选生成**：各分析方法独立生成候选漏洞集。
3. **候选审查与去重**：排除工具误差、无效假设、重复发现。
4. **确认与文档化**：通过自定义测试或形式化反例复现漏洞，映射到硬件CWE，记录安全影响与缓解方案。

其中，各方法并非孤立运行，而是交叉验证（例如：仿真失败→引导形式化断言；lint警告→仿真验证；LLM属性→形式化工具校验），以提高置信度、降低误报率。

### 2.2 技术细节

**（1）基于仿真的安全验证（Simulation-Based）**

- 工具：Synopsys VCS + OpenTitan DVSim框架 + 自定义自动化脚本。
- 流程：通过HJSON配置文件自动化指定目标IP、启用的测试/回归、种子（seed），批量执行冒烟测试与回归测试；分析失败日志和波形，定位周期级行为偏差。
- 判断标准：失败不直接等于漏洞，只有违反安全需求（如未授权方可更新受保护寄存器）才判定为安全相关。

**（2）形式化属性验证与安全验证（FPV / FSV）**

- FPV工具：Synopsys VC Formal。将安全需求转化为SystemVerilog断言（SVA），穷尽检查断言是否成立；不成立的断言通过形式化反例定位RTL缺陷。典型发现包括错误依赖关系的secret-wipe控制、键寄存器暴露到读数据路径等。
- FSV（即信息流分析）：定义受保护源与未授权目的地，检测两者间的非预期传播路径——典型发现为AES密钥份额与输入数据经由寄存器读接口泄露给软件。

**（3）RTL Lint与静态结构分析**

- 工具：Synopsys VC SpyGlass Lint。
- Lint识别的不完整赋值、宽度不匹配、未初始化寄存器等被结合上下文分析；对涉及密钥寄存器、权限检查、错误逻辑、状态机的告警赋予高优先级，再通过RTL审查与仿真/形式化确认。论文指出Lint自身缺乏系统级安全语义，不能单独定案。

**（4）LLM辅助漏洞分析（LLM-Assisted）**

- 流程分为四步：① 安全感知分解（按IP层次划分，优先包含密钥、生命周期状态、调试授权等敏感资产的模块）；② CWE识别（基于模块功能从CWE库中筛选候选弱点类别）；③ CWE引导的定向RTL分析（提示LLM检查该类弱点模式是否存在于指定RTL切片）；④ 定向安全属性生成（LLM生成SVA断言，并经过语法/语义校验后交给仿真或形式化工具验证）。
- 安全性原则：LLM输出仅作为“候选假设”，必须用传统EDA工具验证。论文强调LLM生成的断言可能存在错误时钟、复位语义、信号引用等问题，不能直接采信。

**（5）覆盖引导的混合模糊测试（Hybrid Fuzzing）**

- 硬件模糊器自动生成/变异输入序列（指令流或事务序列），利用覆盖率反馈引导输入向未探索状态空间推进。
- 创新点在于“混合”：先分析覆盖率数据库找出盲区，将这些盲区作为上下文交给LLM生成定向断言/测试约束/输入约束，经工具验证后集成进模糊器，引导对难达区域的探索，进而生成可复现的漏洞触发输入。

**（6）自定义漏洞利用开发（Exploit Development）**

- 利用LLM将漏洞描述映射到具体RTL与验证组件，生成扩展或轻量级UVM序列、SVA监测机制与功能检查，复用OpenTitan的UVM验证环境执行，并以断言失败、寄存器变化、中断状态等作为复现证据。论文给出了UART `lsio_trigger_o`与HMAC `WIPE_SECRET`两个完整示例。

## 6. 论文的主要结论与发现

1. **安全意图（Security Intent）是关键前置条件**：功能失败不等于安全漏洞，必须先明确受保护资产、信任边界、权限规则与预期安全行为，才能正确解释失败测试或可疑代码。许多重要漏洞来自“正常操作下功能正确，但未授权/错误/异常条件下违反安全要求”的逻辑。
2. **互补验证方法不可替代**：仿真擅长复现可执行攻击序列；形式化适合探索难达状态与时间相关属性；静态分析提供大规模结构筛选；信息流分析直接刻画保密性与完整性违规。实际需要将多种方法形成闭环指导，而非孤立使用。
3. **现有验证基础设施需要安全感知扩展**：功能回归与断言主要覆盖“预期行为”，不覆盖恶意输入、权限违规、异常状态；lint等静态方法缺乏系统级语义，必须结合人工审查与定向测试。未来需要安全相关的覆盖率指标（如安全资产覆盖、权限转换覆盖），而非仅功能覆盖率。
4. **自动化发现的漏洞必须独立验证**：lint警告、LLM假设、断言失败与模糊测试异常均只是候选漏洞，必须追溯至RTL根因，并通过仿真轨迹、形式化反例、信息流路径或自定义exploit来复现。这对LLM辅助分析尤为关键——LLM生成断言可能语法正确但语义错误。
5. **SoC级漏洞需要跨层分析**：很多安全缺陷无法在孤立模块分析中显现，其触发依赖寄存器事务、固件操作、权限状态及门级网表实现。
6. **工具自动化与并行化覆盖提升**：大SoC下手工分析不实际，自动化测试执行、日志采集、属性验证与结果分诊能显著降低重复劳动；多方法协同的Agentic LLM工作流比单技术顺序分析覆盖更广。

## 9. 总体评价与展望

### 9.1 总体评价

本文是一篇**工程实践导向的硅前安全验证方法论研究**。其核心贡献不在于提出新的算法或工具，而在于：

1. **系统整合**：将仿真、形式化验证（FPV/FSV）、RTL Lint、LLM辅助分析、混合模糊测试、exploit开发六类技术纳入统一的四阶段工作流，并明确了各类技术之间的交叉校验关系；
2. **真实场景验证**：以OpenTitan这一工业级开源RoT设计为靶标，经三届硬件安全竞赛的实际检验，证明该工作流可以发现并闭环确认真实SoC中的隐蔽安全漏洞；
3. **经验提炼与社区建设**：提出七类硬件安全缺陷分类体系，并将竞赛活动重新定位为benchmark基准、训练平台与工具评估平台，对推动安全感知EDA工具研究具有领域建设价值。

### 9.2 适用边界

该方法最适合**已有成熟EDA流程与安全规格（security intent）的SoC团队**，用于在流片前建立补充性的安全验证闭环。对于缺乏清晰安全资产清单、缺少DV基础设施或预算有限的小型团队，LLM辅助部分可单独落地，但形式化与模糊测试部分需要较高工具与人力门槛。同时，其价值应理解为“可行性示范”而非“定量性能保证”——论文并未证明该工作流优于任一单方法（如仅靠形式化或仅靠fuzzing）的具体幅度。

### 9.3 未来研究展望

- **安全覆盖率指标的形式化定义与工具实现**：将安全资产、权限状态、信任边界纳入覆盖度量，使验证收尾标准从功能覆盖率扩展为安全覆盖率；
- **开源工具链复现**：在同一工作流下改用开源仿真/形式化工具，评估性能损失与适用性差异，降低复现门槛；
- **LLM鲁棒性系统评估**：测试不同模型、不同上下文切片策略、不同提示模板对候选漏洞质量与误报率的影响，量化“LLM误导效应”的风险；
- **跨设计泛化实验**：在多个不同架构（如非RoT类SoC、MCU、AI加速器）上重复该流程，检验方法论的普适性；
- **端到端自动化的智能体工作流**：将六类方法封装为可自主迭代的Agentic验证管线，实现“候选生成—交叉验证—根因定位—exploit生成”的更大程度自动化。

## 10. 一句话总结

本文以OpenTitan真实SoC与商业EDA工具为平台，通过三届硬件黑客竞赛的实践，系统论证了“仿真+形式化+lint+LLM+模糊测试”多方法互补的硅前安全验证工作流，并强调安全意图先行、所有自动化发现必须独立验证的核心原则；其方法论框架具有较强工程参考价值，但定量对比、资源成本与跨设计泛化证据的缺失使其结论仍有待更严格的大规模实证支撑。
