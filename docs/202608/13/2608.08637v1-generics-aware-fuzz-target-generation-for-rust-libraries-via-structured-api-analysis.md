## 摘要
对Rust库API进行模糊测试需要构造满足所有权规则、泛型参数和trait约束的类型良好、可编译的调用序列；现有工具忽略这些约束或使用浅层启发式方法，导致覆盖率较低。我们提出GRAFT，它从Rust文档中提取结构化API信息，通过递归的泛型感知类型匹配构建API依赖图，并利用拓扑引导遍历和带有编译器错误反馈的LLM综合来生成可编译的模糊测试目标。在来自crates.io的13个crate上，GRAFT实现了80.75%的宏观平均API覆盖率，编译成功率为96.19%，优于RULF和RPG分别4.76倍和2.43倍，并且在包含可触达不安全API的crate上，API平均覆盖率达到了deepSURF的1.41倍。

## Abstract
Fuzzing Rust library APIs requires constructing well-typed, compilable call sequences that satisfy ownership rules, generic parameters, and trait bounds; existing tools ignore these constraints or use shallow heuristics, yielding low coverage. We present GRAFT, which extracts structured API information from Rust documentation, builds an API dependency graph via recursive generics-aware type matching, and uses topology-guided traversal plus LLM synthesis with compiler-error feedback to produce compilable fuzz targets. On 13 crates from crates.io, GRAFT achieves 80.75% macro-average API coverage at 96.19% compilation success, outperforming RULF and RPG by 4.76x and 2.43x, and reaching 1.41x the average API coverage of deepSURF on crates with unsafe-reaching APIs.

### 1. 核心问题与整体含义

Rust 语言凭借所有权（ownership）、借用（borrowing）和生命周期（lifetime）等编译期机制，在内存安全和数据竞争防护方面有着显著优势，被广泛应用于安全关键系统。然而即便如此，Rust 库中仍可能存在经由 `unsafe` 代码引发的内存安全漏洞。**Rust 库模糊测试**是一种有效的漏洞检测手段，但其核心挑战在于：生成一个合法的 fuzz target（模糊测试目标入口函数）需要构造同时满足**所有权规则、泛型参数约束和 trait bounds** 的类型良好、可编译的 API 调用序列。同一 crate 中不同 API 之间存在相互依赖关系——一个 API 的输出往往需要作为另一个 API 的参数，且泛型参数在多次调用之间必须保持一致。现有工具（如 RULF、RPG）要么完全忽略泛型类型关系，要么依赖浅层启发式方法，导致在泛型密集的复杂 crate 上 API 覆盖率低、甚至无法生成可编译的 fuzz target。

论文提出 **GRAFT（Generics-aware Rust API Fuzz Target generator）**，通过结构化 API 分析和泛型感知的递归类型匹配来建模 API 间依赖关系，结合拓扑引导遍历和 LLM 合成，显著提升了 Rust 库 fuzz 目标的生成质量与覆盖率。

### 2. 方法论

#### 2.1 核心思想

GRAFT 的总体思想是：**把 fuzz target 生成问题转化为基于结构化 API 信息与类型兼容性分析的有向图路径搜索问题**，再用 LLM 将图路径“具体化”为可编译的 Rust 代码。整体管线分为五个阶段：

1. **Rust 文档分析**：通过 `cargo doc --output-format json` 获取编译器生成的公共 API 结构化视图（`rustdoc_types::Crate`），提取函数签名、泛型参数、trait bounds、公共常量和类型定义；同样的流程也应用于 Rust 标准库。所有类型信息以结构化的 `rustdoc_types` 形式保留，而非简化为文本签名，以支持后续精确推理。

2. **泛型感知类型匹配**：对每一对 API，判定一个 API 的输出类型能否满足另一 API 的参数类型。*类型兼容性*定义为：若类型 `from` 的值可以作为类型 `to` 的参数，则 `Match(from, to) = ⊤`；否则返回 ⊥。匹配规则总结如下（表 1）：
   - **引用 / 切片 / 数组 / 指针**：剥离外层包装后递归匹配内部类型；
   - **基本类型参数**：由外部 fuzz 输入直接满足，不产生生产者边；
   - **泛型 / `impl Trait` / `dyn Trait` 目标**：检查来源类型是否满足全部要求的 trait bounds；
   - **解析路径类型**：进行结构化相等比较；
   - **元组（单非基本类型元素）**：匹配非基本类型元素；
   - **不支持的形式**：保守地返回失败。该算法显式解析泛型参数、trait bounds 和复合类型结构，并跨 API 调用边界跟踪约束满足情况。实现覆盖内联 bounds 和简单的 `where T: Trait` 谓词，但不支持关联类型谓词、trait 别名、负/自动 trait 推理、高阶生命周期等（这类情况保守失败，可能造成漏报）。

3. **API 依赖图构建**：构建有向异构图的节点集 \( V = V_c \cup V_p \cup V_f \) 包含公共常量、函数参数和函数（方法统一视为函数；类型定义不作为图节点）；边集包含参数所有权边 \( E_{own} \) 和类型流边 \( E_{flow} \)。其中 \( v \in V_f \) 的返回类型需展开 `Result<T, E>` 和 `Option<T>` 为内部类型 `T`，元组和 `Box` 包装按复合类型处理。函数可到达性定义：每个参数要么是基本类型，要么存在来自某常量或其他函数的类型流边（排除自身以避免循环自依赖）。

4. **API 序列生成**：采用拓扑引导的遍历策略，优先选择全局使用次数少、依赖深度大的 API。深度 \( d(f) \) 的定义为：常量和全基本类型 API 深度为 0；否则取所有非基本类型参数上满足条件的最深生产者深度加一的最大值。深度通过队列传播计算。算法 1 从目标 API 开始反向构造序列：基本类型参数跳过，不可变借用参数可复用**瞬态类型池**中的值，其他参数在每序列使用上限 \( B \) 约束下选择使用次数最少的生产者；最后反转序列使生产者先于消费者。

5. **LLM 合成**：序列选择与覆盖率决策由图驱动，LLM 仅负责将序列具体化为可编译的 fuzz target 和种子文件。每个序列编码为一次性 JSON prompt（包含带泛型/bounds 的签名、文档、模块路径、安全性标注，不含函数体）。使用 `qwen3.5-plus`（temperature 0.0，8192 token 上限），失败时根据编译器错误反馈进行修复，最多重试 3 次。

#### 2.2 关键定义与公式

- **API 级覆盖率**：对于类型一致的序列集合 \( S \)，定义为 \( \text{Cov}(S) = \frac{|{f \in V_f : \exists s \in S,\ f \in s}|}{|V_f|} \)，即被至少一个序列覆盖的公共 API 函数数占总公共 API 数的比例。
- **类型兼容性判定**：\( \text{Match}(from, to) \in \{⊤, ⊥\} \)，递归处理包装类型，检查 trait bound 满足情况。

### 6. 主要结论与发现

1. **GRAFT 取得了较高的编译成功率**：13 个 crate 宏平均编译成功率为 96.19%，10/13 的 crate 超过 94%。唯一两个明显偏低的 crate 是 `csv`（81.40%）和 `byteorder`（86.54%），原因是复杂泛型 trait bounds 和类型转换超出重试预算。
2. **GRAFT 实现了较高的 API 覆盖率**：宏平均 80.75%，`ryu` 和 `bumpalo` 达 100%，`base64` 和 `regex` 超 90%，最大的 `chrono`（518 个 API）也达 77.99%。
3. **显著优于现有工具**：
   - 在 8 个 GRAFT、RULF、RPG 都产出可运行结果的 crate 上，平均 API 覆盖率 80.14%，是 RULF（16.83%）的 **4.76×**，是 RPG（32.95%）的 **2.43×**；
   - GRAFT 是唯一在全部 13 个 crate 上都生成可运行 fuzz target 的工具（RPG 在 chrono/csv/bytes 上失败，RULF 在 idna/ryu 上失败）；
   - 在含 unsafe-reaching API 的 8 个 crate 上，API 覆盖率 80.89%，是 deepSURF（57.36%）的 **1.41×**；deepSURF 在 5 个不含 unsafe-reaching API 的 crate 上完全无法生成 fuzz target。
4. **泛型感知匹配最为关键**：在泛型密集的 crate（regex、fixedbitset）上，禁用泛型感知匹配导致覆盖率下降最严重（regex 从 52.38% 降至 14.29%；fixedbitset 从 56.04% 降至 15.38%），且图边数平均减少 84.5%（regex 近 99.97%）。
5. **三个组件独立且互补地贡献**：无泛型匹配、无拓扑遍历、随机序列组装三个变体分别使平均覆盖率下降 27.15、13.59、17.76 个百分点，说明各环节都不可缺失。

### 7. 优点

1. **针对 Rust 特有挑战的系统性解决方案**：同时处理所有权、泛型参数和 trait bounds 三类约束，这是此前工具未能完整解决的。
2. **泛型感知递归类型匹配算法设计精巧**：显式区分包装类型、泛型、trait 对象、路径类型等，对不支持的形式保守失败，避免引入不可行的依赖关系；对 `Result`/`Option` 的展开处理扩展了可匹配范围。
3. **图驱动与 LLM 的职责分离**：序列选择完全由依赖图决定，LLM 仅做代码具体化，避免了 LLM 在 API 依赖推理上的不确定性和不可靠性；编译器错误反馈的迭代修复机制大大提升了编译成功率。这种“结构化推理 + LLM 生成”的混合模式值得借鉴。
4. **消融实验设计清晰**：分别移除三个核心组件，验证了各自的独立贡献；且对着重泛型感知匹配的破坏性（在泛型密集 crate 上边数减少 84.5%–99.97%）进行了量化分析。
5. **评估严谨性**：对 API 过滤进行额外验证，与 deepSURF 对比时严格控制变量，多处威胁有效性
