## 摘要
硬件设计与软件一样，容易受到缺陷的影响，这些缺陷可能引入安全漏洞，并为恶意利用创造机会。然而，与软件漏洞不同，硬件缺陷在制造后永久嵌入硅片中，使得它们难以甚至无法修补。这些弱点中的许多被归类于常见弱点枚举（CWE）框架之下，包括不当的访问控制、敏感信息泄露以及非预期的权限提升。为了提高对此类漏洞的检测能力，我们提出了一种方法，利用大语言模型（LLM）直接从Verilog硬件设计中识别潜在的硬件CWE。该方法在单模块Verilog设计数据集上进行了迭代评估，以评估其在检测硬件安全弱点方面的有效性。我们的结果展示了LLM在硬件设计过程中通过提供自动化、可扩展的辅助来增强传统硬件安全分析的潜力。

## Abstract
Hardware designs, like software, are susceptible to bugs that can introduce security vulnerabilities and create opportunities for malicious exploitation. Unlike software vulnerabilities, however, hardware flaws become permanently embedded in silicon after fabrication, making them difficult or impossible to patch. Many of these weaknesses are categorized under the Common Weakness Enumeration (CWE) framework and include improper access control, exposure of sensitive information, and unintended privilege escalation. To improve the detection of such vulnerabilities, we propose a methodology that leverages a Large Language Model (LLM) to identify potential hardware CWEs directly from hardware designs in Verilog. The proposed approach is evaluated iteratively on a dataset of single-module Verilog designs to assess its effectiveness in detecting hardware security weaknesses. Our results demonstrate the potential of LLMs to augment traditional hardware security analysis by providing automated, scalable assistance for identifying security vulnerabilities during the hardware design process.

## 一、核心问题与研究动机

- **研究背景**：硬件设计（如 Verilog RTL 代码）与软件一样容易引入安全漏洞，但二者有一个关键区别——硬件缺陷在芯片流片制造后**永久固化于硅片中**，难以甚至无法像软件那样通过补丁修复。因此，在硬件设计阶段尽早发现并修复安全漏洞至关重要。
- **问题定义**：本文聚焦于利用大语言模型（LLM）直接从 Verilog 硬件描述代码中识别**硬件常见弱点枚举（CWE）**，涵盖不当访问控制（如 CWE-1262）、敏感信息泄露（如 CWE-226）、权限提升等安全威胁。
- **现有痛点**：
  - 手动调试硬件安全漏洞日益繁琐，难以应对复杂电路的规模。
  - 已有 LLM 工具（如 MAGE、AIVRIL）虽可用于 RTL 修复，但受限于幻觉问题、硬件领域知识不足，以及"欠约束修复"（under-constrained repair）导致的多种错误修复方案。
  - 欠约束修复主要由三大因素引起：**提示词设计不当、数据稀缺、长上下文处理能力不足**。
- **研究意义**：提出一种结构化方法论，为人类设计师和 LLM 提供指引，使 RTL 漏洞定位与修复更加高效，降低未来更换故障硬件的潜在成本。

## 二、方法论：核心思想与技术流程

### 核心思想
通过**多阶段、递进式的提示工程**，将 LLM 的分析过程分为六个相互衔接的步骤，使其逐步聚焦于 CWE 相关的安全弱点，避免一次性输入过多信息导致性能退化，同时借助"回顾之前对话输出"的方式缓解长上下文信息丢失问题。

### 方法论整体流程（六阶段）

1. **模块分类（Module Classification）**
   - 向 LLM 提供 Verilog 模块以及"模块类型—功能特征—对应 CWE"的映射列表（如图 3）。
   - 让模型识别模块中包含的功能特征，从而**缩小 CWE 搜索范围**（例如，无 JTAG 接口的模块无需检查 JTAG 认证问题），降低信息过载风险。

2. **资产识别（Asset Identification）**
   - 基于模块类型和功能特征，识别重要资产，包括：密钥、特权域边界、时钟行为、复位方案、攻击者能力、安全规则、有限状态机（FSM）状态等。
   - 帮助 LLM 验证其对模块行为的理解，并为后续 CWE 审查提供定位线索。

3. **依赖图分析（Dependency Graph Analysis）**
   - 要求 LLM 生成**程序依赖图（PDG）**，节点为信号/寄存器/门，边为数据流与控制依赖关系。
   - 基于 PDG 执行三种分析：
     - **可达性分析（Reachability）**：判断节点间是否存在路径。
     - **支配性分析（Dominance）**：判断某节点是否必然先于另一节点出现。
     - **污点传播分析（Taint Propagation）**：追踪不可信来源信息在设计中的流动。
   - 通过图分析发现可能被 CWE 审查遗漏的漏洞。

4. **CWE 驱动的人工审查（CWE-Driven Manual Review）**
   - 综合前述三个阶段的结果，仅提供**与潜在 CWE 相关的定制指南**（含漏洞描述、引导性问题、常见成因、识别清单）。
   - LLM 输出发现的具体漏洞列表，标注对应 CWE 编号及问题描述。

5. **测试平台生成（Testbench Generation）**
   - 根据发现的漏洞，生成定向测试平台（testbench），同时提供一组 **CWE 安全设计规则**作为验证依据。
   - 测试用例需审查以避免误判影响后续修复。

6. **仿真与代码修复（Simulation & Code Repair）**
   - 运行生成的 testbench 进行仿真。
   - 若测试全部通过，则模块通过检查；若失败，则进入代码修复阶段。
   - 修复时，LLM 接收 RTL 设计、失败测试用例及 CWE 设计规则，生成修复后的模块；若接口变化（如增加新输入），需同步更新 testbench。
   - 修复最多迭代 **3 次**，超过则判定为失败。

### 目标 CWE 范围
- 限定在 **MITRE 2025 年"最重要硬件弱点"清单**中的 9 个 CWE，其中包括：
  - CWE-226（资源重用前敏感信息未清除）
  - CWE-1189（SoC 共享资源隔离不当）
  - CWE-1191（片上调试/测试接口访问控制不当）
  - CWE-1234（硬件内部/调试模式覆盖锁）
  - CWE-1247（对电压/时钟毛刺防护不当）
  - CWE-1256（软件接口对硬件特性的限制不当）
  - CWE-1260（受保护内存范围重叠处理不当）
  - CWE-1262（寄存器接口访问控制不当）
  - CWE-1300（物理侧信道防护不当）
- 剔除了 CWE-1421 和 CWE-1423（因涉及微架构级设计考量）。

## 六、主要结论与发现

1. **高分类准确率**：LLM 在模块分类上表现优异，32 个模块中仅出现 1 次分类错误。
2. **早期分析表现良好**：资产识别、行为理解、PDG 关系解释方面表现稳定，且在 CWE 审查之前就已能正确识别部分漏洞。
3. **最大短板是测试平台生成**：生成的 testbench 频繁出现错误使用被测设计（DUT）、测试用例不完整/无效、未在测试间正确复位 DUT 等问题，严重影响验证可靠性。
4. **代码修复结果喜忧参半**：
   - 能生成语法正确的补丁，但有时会过度修改功能——例如添加非必要的特权输入或访问控制逻辑，改变原始设计意图。
   - 根因是未给 LLM 提供模块预期行为的上下文，导致模型偏好"过度安全化"而非最小修改。
5. **总体成功率**：32 个测试中 27 个通过，**成功率 84%**。
6. **误报问题严重**：5 个无漏洞模块**全部被误报**至少一个漏洞，模型将"缺少额外的安全机制"本身视为漏洞。其中包括将必要的设计行为误判为不安全（如特定状态下不做数据擦除被标记为 CWE-226）。
7. **失败案例分析**：
   - **CWE-226 测试**：CWE 识别正确，但 testbench 持续产生未初始化输出（x），3 轮修复无法解决。
   - **CWE-1300 测试（模块 5）**：模块分类错误（未识别为 Crypto Accelerator），导致 CWE-1300 完全未被审查。
   - **CWE-1300 测试（模块 6）**：CWE 识别正确，但添加的"错误状态"未能按预期触发，修复失败。
   - **非漏洞模块 2 和 3**：误报 + 测试错误，但因确认非真实漏洞而未执行修复。
