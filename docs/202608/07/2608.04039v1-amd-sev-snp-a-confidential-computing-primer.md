## 摘要
本文是关于AMD安全加密虚拟化与安全嵌套页（SEV-SNP）的技术导论，这是一种硬件机密计算实现，为虚拟机提供可信执行环境（TEEs）。SEV-SNP将虚拟机监控程序视为敌手。它使用虚拟机监控程序从未拥有的密钥加密客户机内存和寄存器状态，在访问时检测对客户机内存的任何篡改，并允许客户机向远程验证者证明其正在运行的代码。本文从硬件层面逐一构建这些保证。论文首先介绍了驱动设计的威胁模型以及执行该模型的硬件，即AMD安全处理器和内存控制器中的加密引擎。接着，论文阐述了使机密客户机变得实用的机制。反向映射表提供了内存完整性，抵御控制页表的攻击者。特权与通信机制（虚拟机特权级别、加密的虚拟机保存区和GHCB协议）允许客户机与不信任的虚拟机监控程序合作。认证流水线将客户机初始状态的硬件签名测量绑定到AMD的证书链，因此远程验证者可以独立确认正在运行的内容。

## Abstract
This paper is a technical primer on AMD Secure Encrypted Virtualization with Secure Nested Paging (SEV-SNP), a hardware confidential computing implementation that provides Trusted Execution Environments (TEEs) for virtual machines. SEV-SNP treats the hypervisor as adversarial. It encrypts guest memory and register state with keys the hypervisor never possesses, detects any tampering with guest memory at the point of access, and lets a guest prove to a remote verifier exactly what code it is running. The paper constructs each of these guarantees from the hardware up. It opens with the threat model that drives the design and the hardware that enforces it, the AMD Secure Processor and the encryption engine in the memory controller. It then develops the mechanisms that make a confidential guest practical. The Reverse Map Table provides memory integrity against an adversary who controls the page tables. The privilege and communication machinery (VM Privilege Levels, the encrypted VM Save Area, and the GHCB protocol) lets the guest cooperate with a hypervisor it does not trust. The attestation pipeline binds a hardware-signed measurement of the guest's initial state to AMD's certificate chain, so a remote verifier can confirm independently what is running.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：在公有云场景下，虚拟机（VM）运行在由云服务商完全控制的基础设施上，传统虚拟化中 hypervisor（虚拟机监控程序）拥有对客户机内存和寄存器的完整读写权限。这意味着云运营商、被攻破的 hypervisor 或具有特权的内部人员都可以任意观察或篡改客户机的执行过程。这种“行政性”安全控制（背景调查、审计、网络隔离）并非基于密码学，无法从根本上保护租户数据。
- **整体含义**：机密计算旨在解决数据“在使用中”的保护问题（填补静态加密和传输加密之间的空白）。AMD SEV-SNP 是一种硬件级可信执行环境（TEE），它将信任边界从“运营商的策略和流程”移到“硅片强制的密码学边界”。它把 hypervisor 视为敌手，通过硬件保证客户机内存的机密性、完整性以及可远程证明的启动状态。
- **具体目标**：SEV-SNP 提供三个核心安全属性：
  - **机密性**：客户机内存用每 VM 独有的密钥加密（hypervisor 无法获得），寄存器状态在 VM 退出时也被加密。
  - **完整性**：硬件能够检测 hypervisor 对客户机内存的任何篡改（替换、重放、重映射），并触发可被客户机捕获的异常。
  - **认证（Attestation）**：客户机可以向远程验证者证明自己正在运行什么代码，通过 AMD Secure Processor 的硬件签名报告和 AMD 证书链完成独立验证。
- **背景与定位**：本文是面向技术读者的 SEV-SNP 导论，自底向上构建从威胁模型到硬件基础、内存完整性、特权与通信、以及认证的完整图景。文中指出该技术是多年来 x86 虚拟化和内存加密工作的延续，也是英特尔 TDX、Arm CCA 等 TEE 架构的重要参照。

### 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

论文本质是一篇技术综述，没有提出新的算法，但系统阐述了一套硬件架构方法论。核心思想是**以硬件为根的可信边界 + 密码学强制隔离**。主要技术细节如下：

#### 2.1 威胁模型
- 定义敌手为“完全特权 hypervisor”，拥有读写任意内存、修改嵌套页表、控制中断、暂停/迁移 VM、控制 I/O 设备等能力。
- 信任边界内部：CPU 核心、缓存、片上内存控制器、AMD 安全处理器（ASP）、以及测量过的客户机代码。
- 信任边界外部：DRAM、内存总线、PCIe 设备、hypervisor、宿主机 OS、管理面、其他租户。
- 明确排除：拒绝服务攻击、侧信道/时序泄漏、客户机软件漏洞、侵入性物理攻击（内存总线拦截、电压故障注入、芯片开盖等）以及信任锚点妥协。

#### 2.2 硬件基础
- **AMD-V 虚拟化**：VMCB（虚拟机控制块）包含控制区和保存区。控制区由 hypervisor 可读写；保存区（VMSA）在 SEV-ES/SNP 中被加密，hypervisor 无法读取或修改。
- **嵌套页表**：GVA→GPA→SPA 两级地址转换。hypervisor 控制 GPA→SPA 的映射，这是篡改攻击的潜在源。
- **AMD 安全处理器（ASP）**：独立的 ARM Cortex-A5 内核，拥有自己的固件。负责生成每 VM 加密密钥（VEK）、维护 Guest Context（GCTX）、管理 VM 生命周期、签发认证报告。VEK 永远不以明文离开 ASP。
- **内存加密**：位于内存控制器中的 AES 引擎，缓存内是明文，离开 CPU 封装时加密。使用 ASID 选择 VEK，以物理地址作为 tweak（AES-128-XEX / AES-256-XTS）。当前硬件支持 **ciphertext hiding**（隐藏密文），可防止基于密文可观测性的侧信道攻击。

#### 2.3 内存完整性机制：反向映射表（RMP）
- **RMP 结构**：系统级表格，每个 4 KB 物理页对应一个 16 字节条目，记录：ASID（所有者）、GPA（应映射到的客户机物理地址）、Validated（是否验证）、Immutable、VMSA 标志、页大小、每 VMPL 权限。
- **RMP 检查**：客户机每次内存访问在地址翻译结束时，硬件检查对应 SPA 的 RMP 条目，验证 ASID 匹配、GPA 匹配、Validated 位、VMPL 权限。失败则触发 #NPF 或 #VC 异常。
- **页面验证流程**：两步合作——hypervisor 使用 RMPUPDATE 将页分配给客户机（始终清除 Validated），然后客户机执行 PVALIDATE（仅 VMPL0 可执行）将页转换为 Guest valid 状态。RMPUPDATE 永远清除 Validated 是防重映射的关键规则。
- **双射映射属性**：RMP 保证一个 SPA 最多对应一个 GPA；改变某个 GPA 的物理后备页会清空 Validated，导致客户机检测到异常。这从机制上排除了重映射、重放、混叠、破坏四类攻击。
- **IOMMU 集成**：设备 DMA 也经过 RMP 检查，阻止设备直接访问客户机私有页。普通 DMA 只能进入共享页（C=0）；Trusted I/O（TIO）允许通过认证的设备直接访问私有内存。

#### 2.4 特权与通信机制
- **VM 特权级别（VMPL）**：硬件强制的四级特权（0 最高，3 最低），独立于传统 ring 0/3。每个 RMP 条目存储四个（读/写/执行）权限三元组。RMPADJUST 指令仅允许向下授权（低 VMPL 无法获得超出调用者自身权限的许可）。
- **SVSM（Secure VM Service Module）**：运行于 VMPL0 的可信服务模块，代表 VMPL2 的客户机 OS 执行 VMPL0 专属操作（页面验证、VMSA 创建）。其内存对低 VMPL 不可见，可承载虚拟 TPM 等隔离服务。
- **VMSA 保护**：VM 退出时寄存器状态加密写入 VMSA 页，RMP 标记 VMSA 页为不可写，hypervisor 无法读取或修改。硬件只在进入/退出时操作 VMSA。
- **GHCB 协议**：共享页（C=0）上显式通信。客户机执行被拦截指令时触发 #VC 异常（vector 29），#VC handler 决定要分享哪些信息，填入 GHCB 并执行 VMGEXIT（自愿退出）。hypervisor 只能看到 GHCB 中客所填写的内容，并通过“有效位图”最小化信息暴露。客户机必须验证 hypervisor 的响应（如 CPUID 对照测量页、MSR 对照架构范围）。
- **中断保护**：受限注入模式（只有 #HV doorbell）、替代注入模式（中断控制字段在加密 VMSA 中）、以及 Secure AVIC（硬件按客户机位图只允许授权向量）。

#### 2.5 认证流水线
- **启动测量**：ASP 通过 SNP_LAUNCH_START / SNP_LAUNCH_UPDATE / SNP_LAUNCH_FINISH 逐步构建 SHA-384 摘要。每次 UPDATE 将当前摘要、页面内容 SHA-384、GPA、页面类型、VMPL 权限折叠成新的摘要。最终测量值出现在认证报告的 MEASUREMENT 字段。
- **认证报告结构**：v5 报告包含身份（策略、家庭 ID、图像 ID、安全版本）、测量（启动摘要）、自定义数据（REPORT_DATA、HOST_DATA）、平台状态（TCB 版本、PLATFORM_INFO、缓解向量）、硬件身份（CHIP_ID、CPUID）、签名密钥摘要、以及 ECDSA P-384 签名。
- **密钥层次**：AMD 根密钥（ARK，RSA-4096）→ AMD SEV 密钥（ASK，RSA-4096）→ VCEK（版本化芯片背书密钥，ECDSA P-384）。VCEK 由芯片熔断秘密和 TCB 版本衍生，每个芯片和 TCB 唯一。
- **报告验证六步骤**：接收报告 → 解析元数据 → 从 AMD KDS 获取证书 → 验证证书链（并固定 ARK、检查 CRL）→ 验证报告签名 → 检查报告内容（MEASUREMENT、POLICY、PLATFORM_INFO、REPORTED_TCB、REPORT_DATA 等）。
- **身份块（IDB）**：允许客户机所有者在启动前预先签署期望测量值，ASP 在 SNP_LAUNCH_FINISH 时比对，若不符合则启动失败。

- **客观性**：论文整体客观描述了设计意图和已公开的安全问题（如 VCEK 提取攻击），未回避风险；但作者来自 confidential.ai（AMD 生态相关公司），可能存在对 AMD 技术的一定倾向性，虽然文中在局限性上已比较坦诚。

### 6. 论文的主要结论与发现

- SEV-SNP 提供三层核心保护：**机密性**（内存以每 VM 密钥加密，hypervisor 无法获得密钥和明文）、**完整性**（RMP 确保私有内存不会被静默篡改）、**认证**（硬件签名的启动测量，链接到 AMD 证书链）。
- **RMP 和验证纪律是完整性保障的核心**：通过“RMPUPDATE 始终清除 Validated”和“客户机不重复验证同一 GPA”两条规则，实现了 GPA↔SPA 的近似双射映射，从而消除重映射、重放、混叠和破坏攻击。
- **Hypervisor 仍可以发起拒绝服务、侧信道干扰、时序观测**，这些被认为是设计边界之外。
- **信任面大幅缩小但非零**：一个 SEV-SNP 部署把对云栈中众多组件的信任集中于对 AMD 的制造、密钥管理、ASP 固件和密码原语的信任。
- **认证的意义**：认证报告不仅证明代码，还公开平台的安全状态（SMT 状态、密文隐藏是否启用、DRAM 别名检查是否完成、缓解措施向量），使远程验证者能够做更有深度的策略判断。

### 7. 优点

- **结构清晰，自底向上**：从威胁模型→硬件基础→内存完整性→特权/通信→认证，逻辑链条完整，读者只需基础虚拟化和公钥密码知识即可逐步理解。
- **概念具体化**：通过大量图示（信任边界、RMP 条目、VMRUN 循环、＃VC 流程、VCEK 层级等）将抽象机制直观呈现。
- **攻击启发式设计**：解释了 RMP 校验设计如何针对性阻断重映射重放混叠，并明确指出“RMPUPDATE 始终清除 Validated”的关键性，突出硬件设计的安全直觉。
- **承认局限与已知攻击**：文中引用了针对 SEV/SEV-ES/SEV-SNP 的真实攻击研究（SEVered、SEVurity、CipherLeaks、WeSee、BadRAM、VCEK 提取），并坦诚说明哪些风险已由新硬件缓解，哪些仍存在，比纯宣传材料更有价值。
- **兼具广度和深度**：覆盖了从 ASP 内部职责到 VCEK 证书链验证的完整链路，既有高层设计又有具体字节偏移级别的验证细节（如签名验证的 offset 0x00 至 0x29F）。

### 8. 不足与局限

- **缺乏实证数据**：没有提供任何性能开销测量（例如 RMP 检查对内存访问延迟的影响、加密对吞吐量的影响），也没有进行真实负载下的 TEE 对比实验。
- **不适用于直接工程决策**：虽然是入门指南，但作者声明不替代 AMD 规范；对于需要精确实现（字节偏移、指令编码）的工程师来说，仍需参考 AMD 官方文档。
- **安全边界的固有风险**：
  - 侧信道攻击（缓存、时序）未完全解决，即使有 Ciphertext Hiding 和分支预测隔离等缓解，仍存在残余泄漏。
  - 物理攻击（内存总线拦截等）被排除在威胁模型外，但在实际部署中可能被高价值目标利用（文中引用 TEE.Fail、Battering RAM 等证明风险“真实存在”）。
  - 信任锚点（AMD 本身）仍是单点失败：一旦 ASP 固件或制造流程被攻破，所有保证将失效（并引用了米兰版 VCEK 提取攻击为例）。
- **覆盖范围局限**：论文主要针对 AMD 具体实现，虽然提到 TDX/CCA 等概念对应关系，却没有提供跨厂商比较分析，读者难以横向评估。
- **缺少实验对比公平性**：没有对同一攻击场景下不同防护机制做对比测试，因此无法验证论文所述“屏障显著提升”的具体程度。
