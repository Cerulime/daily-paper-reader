## 摘要
容器化工作负载通常通过CI/CD管道构建，存储在注册表中，并在包括云和边缘环境在内的异构基础设施上执行。一个被攻破的构建步骤或凭据即可将常规自动化转变为恶意工件的大规模分发，这促使了对完整性、透明性以及可执行的部署时检查的需求。在本文中，我们提出了一种可验证的容器镜像分发架构，该架构解决了密钥管理挑战，并实现了策略强制的准入时验证。透明性服务生成与已验证身份绑定的一次性签名密钥，将签名事件记录在仅追加的透明性注册表中，并返回可加密验证的包含证明。这些证明和身份属性被附加到镜像元数据中，并在准入时由策略即代码进行评估，因此只有合规的工件才会被部署。我们实现了一个与GitHub Actions和GitLab Runners集成的概念验证，并评估了由此产生的管道在现实威胁模型下如何缓解常见的供应链攻击。

## Abstract
Containerized workloads are commonly built via CI/CD pipelines, stored in registries, and executed across heterogeneous infrastructures, including cloud and edge environments. A single compromised build step or credential can turn routine automation into large-scale distribution of malicious artifacts, motivating integrity, transparency, and enforceable deployment-time checks. In this paper, we present an architecture for verifiable container image distribution that addresses key-management challenges and enables policy-enforced admission-time verification. A transparency service generates one-time signing keys bound to authenticated identities, records signing events in an append-only transparency registry, and returns cryptographically verifiable proofs of inclusion. These proofs and identity attributes are attached to image metadata and evaluated by policy-as-code at admission time, so only compliant artifacts are deployed. We implement a proof-of-concept integrated with GitHub Actions and GitLab Runners and evaluate how the resulting pipeline mitigates common supply-chain attacks under a realistic threat model.

  - 许多方案的签名能力位于 CI/CD 环境内部，一旦构建系统或 runner 凭据失陷，攻击者可生成看似合法的恶意制品签名。
- **整体含义**：本文提出一种将身份绑定的一次性签名、透明度日志（append-only 注册表）与策略即代码（policy-as-code）准入控制相结合的架构，使容器镜像分发具备可验证性、可审计性和部署时强制检查能力，从而缓解常见供应链攻击并降低 CI/CD 失陷的潜在影响。

## 2. 方法论

- **核心思想**：由“透明度服务”（Transparency Service）集中负责签名与审计事件记录；每个签名事件使用一次性密钥并绑定用户身份；签名事件被记入追加式透明度注册表，并返回可加密验证的包含证明（Proof of Inclusion, PoI）；部署端在准入前对签名、身份、PoI 和新鲜性进行联合验证。
- **系统流程**：
  1. 用户通过组织 IdP（OpenID Connect）向透明度服务认证，获取绑定组织身份的访问令牌；
  2. 令牌配置到 CI/CD runner（如 GitHub Actions、GitLab Runners）；
  3. 管道执行时，透明度服务为每个签名事件生成一次性密钥对，并由 CA（如 Fulcio，HSM 保护密钥）签发短期身份绑定证书；
  4. 服务用该证书签名镜像摘要及相关元数据（如 SBOM、SLSA provenance）；
  5. 签名与证书提交至透明度注册表（如 Rekor），注册表生成包含证明 PoI；
  6. 将签名、证书、PoI 嵌入镜像清单（manifest），与镜像一同存入容器注册表；
  7. 部署端（如 FluxCD 监控注册表）拉取镜像与清单，使用策略引擎（如 Kyverno）执行准入验证。
- **接受谓词**：部署端对每个清单执行确定性验证，需同时满足：
  - **Sig**：使用证书中的公钥验证签名与镜像摘要匹配；
  - **AuthZ**：证书链有效，且证书身份属于本地策略授权的签名者集合；
  - **Transp**：PoI 有效，且绑定到该摘要、签名与证书；
  - **Fresh**：日志时间戳位于证书有效期内（防重放）。
- **可信模型**：假设 CA 密钥受 HSM 保护、透明度服务正确生成并销毁临时密钥、注册表满足追加式 Merkle 日志性质且受独立监控、容器注册表访问安全。
- **监控机制**：部署方可配置监控器持续观察透明度日志，检测可疑签名事件（如非授权身份或异常摘要），并启动响应流程（如撤销身份、拒绝列表、回滚）。

## 7. 优点

- **方法设计巧妙**：将一次性密钥生成与身份绑定集中到可隔离、可加固的透明度服务中，显著缩小了 CI/CD 环境的攻击面。
- **透明度与可审计性**：所有签名事件记录在追加式日志中，并通过 PoI 与具体镜像摘要绑定，支持独立审计和滥用检测。
- **策略驱动的准入控制**：使用策略即代码（Kyverno）在部署时强制验证，不依赖人工检查，适合 GitOps 工作流。
- **与现有生态兼容**：直接复用 Fulcio、Rekor、FluxCD 等开源组件，并支持任意 OIDC IdP，具备良好的可集成性。
- **考虑了实际部署细节**：讨论了包含延迟（promise vs proof）、监控间隔和接受延迟（cooling-off window）之间的权衡，具有工程参考价值。

## 8. 不足与局限
