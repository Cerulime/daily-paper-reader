## 摘要
自动化测试发现漏洞的速度快于开发者调查和修复它们的速度，这留下了一个已知内存破坏仍可利用的时间间隔。端到端的大语言模型修复代理可以缩短这一间隔，但它们合成的是开放式的代码更改，并且通常仅通过重放概念验证（PoC）进行验证。这种弱验证器会接受那些通过改变无关行为来掩盖观察到的崩溃的补丁，使得意外部署具有风险。我们提出了CodeMechanic，一个用于生成空间内存破坏的受限缓解措施的缺陷属性引导系统。CodeMechanic不是要求大语言模型生成永久修复，而是从崩溃中重建被违反的内存安全属性，验证被解引用的指针及其缓冲区范围，并在危险访问之前插入一个本地故障停止保护。当边界检查失败时，该保护会终止执行。由此产生的缓解措施刻意用可用性换取安全性：它可以将潜在远程代码执行转化为受控终止，同时开发者调查根本原因并准备永久修复。CodeMechanic将二维静态和动态上下文提取器与提示内调试知识和逐步验证相结合，以限制大语言模型错误的影响。在101个真实世界ARVO漏洞上，CodeMechanic首次尝试产生的合理补丁（即通过PoC重放验证的补丁）比最佳基线多47.6%，同时使用的令牌少91%。手动审计进一步表明，CodeMechanic生成与开发者编写修复语义等效的补丁数量是后者的3.4倍至4.3倍。

## Abstract
Automated testing discovers vulnerabilities faster than developers can investigate and repair them, leaving an interval in which known memory corruptions remain exploitable. End- to-end LLM repair agents can shorten this interval, but they synthesize open-ended code changes and commonly validate them only by replaying a proof of concept (PoC). This weak oracle accepts patches that silence the observed crash by changing unrelated behavior, making unintended deployment risky.   We present CodeMechanic, a bug-property-guided system for generating constrained mit- igations for spatial memory corruption. Instead of asking an LLM to generate a permanent repair, CodeMechanic reconstructs the violated memory-safety property from the crash, validates the dereferenced pointer and its buffer range, and inserts a local fail-stop guard before the dangerous access. The guard terminates execution when the boundary check fails. The resulting mitigation deliberately trades availability for security: it can convert potential remote code execution into controlled termination while developers investigate the root cause and prepare a permanent repair. CodeMechanic combines a two-dimensional static and dynamic context extractor with in-prompt debugging knowledge and stepwise val- idation to limit the effect of LLM errors. On 101 real-world ARVO bugs, the first attempt of CodeMechanic produces 47.6% more plausible patches (i.e., patches that pass PoC- replay validation) than the best baseline while using 91% fewer tokens. Manual audit further shows that CodeMechanic produces 3.4x - 4.3x more patches semantically equivalent to developer-written repairs.

### 研究背景与动机
- 自动化测试（模糊测试、静态分析）发现的漏洞速度**远超**开发者能够手动调查和修复的速度，形成“修复积压”问题。例如 Linux 内核 syzbot 上约 1,500 个未解决的已报告 bug。
- 在这段“已知漏洞但尚未修复”的窗口期内，内存破坏漏洞（尤其是空间内存破坏）可被攻击者利用，造成严重安全后果。
- 现有的大语言模型（LLM）自动化漏洞修复（AVR）代理（如 PatchAgent、San2Patch）虽然能加快修复进程，但存在三个关键问题：
  1. **补丁效应无边界（C1）**：LLM 可以修改任意代码，验证器通常只检查 PoC 是否不再崩溃，导致“看似合理但实际错误”的补丁通过验证（例如修改 fuzz driver 而非修复库本身）。
  2. **上下文不足（C2）**：崩溃点附近的代码片段往往缺乏重建内存安全属性所需的完整信息（如指针、缓冲区基址、边界表达式），LLM 容易产生幻觉或过度拟合单次执行。
  3. **依赖专家调试知识（C3）**：有效恢复相关指针和对象边界需要熟练使用代码搜索、宏解析、GDB、Sanitizer 元数据等工具，LLM 默认不具备这种工具编排能力。

### 核心思路
- 与现有方法追求“永久修复”不同，CodeMechanic 提出**缺陷属性引导的受限缓解**：从崩溃中重建被违反的空间内存安全边界属性，并在危险解引用前插入一个**本地失败即停止（fail-stop）保护**，将潜在远程代码执行（RCE）转化为**受控终止（可控的拒绝服务）**，为开发者争取修复时间。
- 核心思想是：**用可控的可用性损失换取安全性提升**，并严格限制 LLM 的补丁空间，避免开放式修改带来的不可预测副作用。

## 2. 方法论

### 核心思想：Bug-Property-Guided Mitigation
- 针对空间内存破坏，定义统一的**边界违反条件（公式1）**：
  ```
  (ptr < buf_begin || ptr + sizeof(*ptr) > buf_end)
  ```
  其中 `buf_begin` 和 `buf_end` 为合法内存缓冲区的起始和结尾地址。
- 生成的缓解补丁形式为：在危险访问前插入 `if (!valid_pointer(p)) exit(0);` 类似的本地保护，当边界检查失败时终止执行。
- 这一约束将 LLM 的输出空间限制为“在崩溃点添加局部守护逻辑”，而不是重写任意程序逻辑。

### 三个关键组件

**① 二维上下文提取器（Two-Dimensional Context Extractor）**
- **代码视图（Code View）**：
  - 代码探索工具：检查崩溃点以外的代码。
  - 宏解析工具：解析宏展开（如将 `CUR` 展开为 `*ctxt->input->cur`）。
  - 缓冲区推断工具：基于指针表达式剥离尾部的成员访问/索引，搜索相关缓冲引用（如从 `ctxt->input->cur` 推断出 `ctxt->input->base/end`）。
- **数据视图（Data View）**：
  - 指针与缓冲区验证（带 ASan 元数据）工具：利用 ASan 报告的地址和区域描述符确定验证缓冲范围。
  - 指针与缓冲区验证（不带 ASan 元数据）工具：针对栈缓冲区溢出，用 GDB 测量指针声明跨度、扫描局部变量/参数，匹配故障地址。
  - 指针类型分析工具：提供类型信息，防止“指针在界内但解引用超界”的情况（如 `size_t *` 在缓冲区末端仍会访问 8 字节而越界）。

**② 提示内人类知识（In-Prompt Human Knowledge）**
- 通过 few-shot prompting 将人工调试经验编码到提示中：
  - **工具调用顺序**：例如全局缓冲区溢出先从 ASan 日志的缓冲区符号开始计算大小和边界；堆溢出先应用缓冲区推断再打印地址验证。
  - **工具错误容错**：例如遇到 `Symbol not found` 错误（访问宏变量）时，应调用宏解析工具而非重复尝试。

**③ 缺陷属性引导的修复流程**
- 分两个代理协作：
  1. **第一代理**：根据验证过的表达式构造边界约束条件。
  2. **第二代理**：将保护插入崩溃点，并根据编译错误信息进行针对性修正。
- **错误消息驱动的补丁修正**：通过正则提取编译错误的关联部分，引导 LLM 定向修正，而非盲目重生成。
- **按需重试**：编译失败只重试第二代理；崩溃持续才重启完整流程（仅占 11%）。
- **逐步验证**：先验证指针，再验证缓冲区上下界，全部通过后才生成守护补丁，避免在错误中间结果上继续推理。

### 实现细节
- 约 5,500 行 Python 代码；接受复现环境和 PoC 文件作为输入。
- 用自定义 Clang 包装器在编译时强制 `-O0 -g` 保留完整调试信息。
- 从源码构建 GDB 12.1 以保证跨环境的 DWARF 兼容性（支持 DWARF 3–5）。
- 通过 Docker 解耦宿主机的缓解逻辑与容器内的漏洞复现环境。

## 6. 主要结论与发现

1. **效率优势显著**：
   - 单次尝试：CodeMechanic 平均 37.2 个合理补丁，比 PatchAgent 1（约 13 个）高近 3 倍，比 San2Patch 1（25.2 个）高 47.6%。
   - 成本仅 $2.75，比 San2Patch 1（$21.3）低约 87%，比 PatchAgent 1（$2.40）略高但产出多得多。
   - 五次尝试：CodeMechanic 51 个合理补丁，比 PatchAgent 5（36 个）高 41.7%，比 San2Patch 5（45 个）高 13.3%；成本 $9.90，是 San2Patch 5（$106.39）的约 1/10。
2. **人工审计结果**：51 个合理补丁中，34 个是正确缓解（non-IP），17 个与开发者修复语义等价（6 个 SE + 11 个 SERC）；语义等价数量是 PatchAgent（5个）的 3.4 倍、San2Patch（4个）的 4.25 倍。
3. **失败分析**：
   - 指针分析失败 23 个，缓冲分析失败 33 个（主要原因是缓冲定义远离崩溃点）。
   - 一旦找到全部关键变量，82% 的情况能生成合理补丁，剩余失败主要是编译问题。
4. **按类型**：堆和全局缓冲区溢出表现最好且稳定；栈缓冲区溢出仍是最难的类型。
5. **失败模式**：
   - **过度限制边界**：生成的边界为 ASan 分配范围的子集时被接受，但可能过于严格（如 `[s, s+i)` 而非 `[s, s+s_len)`），导致合法执行也被终止（可用性损失）。
   - **硬编码变量**：LLM 偶然将运行时具体地址嵌入补丁（如 `(char*)0x61d00000d1f0`），导致补丁在其他输入上不适用，需要人工审查。
6. **正交性**：三个代理覆盖的 bug 高度互补，只有 8 个 bug 被三个代理同时解决；先 CodeMechanic 后开放式修复代理的两阶段工作流可作为实用策略。

## 7. 优点

- **创新性地重新定义问题**：从“开放式的自动修复”转向“受限的临时缓解”，规避了 LLM 开放式补丁不可控的核心风险。
- **严格的输出约束**：补丁格式、位置、行为（失败即终止）都被限制，副作用可预测。
- **二维上下文提取器设计精巧**：结合静态代码视图和运行时数据视图，并用 ASan 元数据/GDB 确定性验证，减少 LLM 幻觉空间。
- **提示内人类知识工程**：将搜索/调试工具使用经验编码到 prompt，提高工具调用效率，减少无效循环。
- **分步验证 + 按需重试**：中间结果逐步校验，编译错误与逻辑错误分类处理，节省 token。
- **成本极低**：单 bug 平均约 $0.027（单次），非常适合大规模快速部署缓解。
- **跨环境兼容性**：通过 GDB 12.1 自编译和 Docker 解耦，支持从 Ubuntu 16.04 + Clang 5.0 到 Ubuntu 22.04 + Clang 15 的广泛环境。

## 8. 不足与局限

- **适用范围有限**：仅覆盖空间内存破坏（堆/栈/全局缓冲区溢出），不处理时间内存破坏（如 use-after-free），因为缺乏可靠的对象活性验证器。
- **验证缺陷（Internal Threat）**：ASan 元数据只能确认“缓冲区是离指针最近的合法区域”，不能保证是“程序意图引用的缓冲区”，存在误分类为相邻缓冲区的可能（虽然较小溢出+2048 字节 redzone 可缓解）。
- **硬编码问题未根治**：虽明确指示 LLM 不使用绝对值，但仍出现包含运行时地址/大小的补丁，需要人工审查才能部署。
- **过度限制边界**：边界是 ASan 分配范围的子集即被接受，可能终止合法执行，将安全漏洞变成拒绝服务。
- **未做消融实验**：无法量化各组件（二维上下文、提示内知识、缺陷属性引导、分步验证）的独立贡献。
- **仅测试单一 LLM**：Gemini-2.5-flash 是唯一评估的后端模型；论文提到 Gemini-2.5-pro 和 flash-lite 因 API 内部错误未能使用，故泛化性未知。
- **评估基准局限**：ARVO 缺乏全面功能测试套件，PoC 重放验证器本质上偏弱（虽有人工审计补偿）。
- **本质是缓解而非修复**：生成的补丁只针对已知的崩溃路径，对变体攻击或同一函数中其他越界访问缺乏防护；可用性牺牲（终止执行）在有些场景可能不可接受。
