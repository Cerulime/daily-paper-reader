## 摘要
开源软件（OSS）的广泛采用带来了显著的安全风险，恶意代码投毒攻击日益针对公共软件包注册中心和开源平台。现有检测方法，包括基于启发式、学习和基于大语言模型的方法，存在语言特定设计、泛化能力有限和分析成本高的问题，使其不适合大规模多语言分析。为应对这些挑战，我们提出MalTotal，一个可扩展且经济高效的语言无关恶意代码检测框架。MalTotal利用大语言模型辅助的语义推理来识别敏感API，执行混合语义切片，并重构恶意行为上下文，同时降低分析开销。我们的评估显示，MalTotal在5种主流语言上平均F1分数达到93.1%，优于8个最先进的基线方法。其混合切片将大语言模型令牌消耗减少94.0%，在2,168个仓库上将分析成本从86.25美元降至5.19美元。在对包含超过730万个文件的120K个GitHub仓库的大规模研究中，MalTotal以总计338美元的成本发现了564个此前未知的跨语言恶意仓库。这些结果证明了MalTotal在缓解大规模代码投毒攻击方面的有效性、可扩展性和成本效益。

## Abstract
The widespread adoption of open source software (OSS) has introduced significant security risks, with malicious code poisoning attacks increasingly targeting public package registries and open-source platforms. Existing detection approaches, including heuristic-, learning-, and LLM-based methods, suffer from language-specific designs, limited generalization, and high analysis costs, making them unsuitable for large-scale multi-language analysis. To address these challenges, we propose MalTotal, a scalable and cost-effective framework for language-agnostic malicious code detection. MalTotal leverages LLM-assisted semantic reasoning to identify sensitive APIs, perform hybrid semantic slicing, and reconstruct malicious behavior contexts while reducing analysis overhead. Our evaluations show that MalTotal outperforms 8 state-of-the-art baselines, achieving an average F1-score of 93.1% across 5 mainstream languages. Its hybrid slicing reduces LLM token consumption by 94.0%, lowering the analysis cost from \$86.25 to \$5.19 on 2,168 repositories. In a large-scale study of 120K GitHub repositories containing over 7.3 million files, MalTotal discovered 564 previously unknown malicious repositories across multiple languages at a total cost of \$338. These results demonstrate the effectiveness, scalability, and cost-efficiency of MalTotal in mitigating large-scale code poisoning attacks.

- **现有方法的三大缺陷**：
  - **L1（范围受限与语言特定设计）**：大多数方法仅针对单一语言（如 Python 或 JavaScript），依赖生态特定行为模式和人工维护的敏感 API 规范，迁移到新语言需要大量重新工程。
  - **L2（恶意语义泛化能力差）**：现有工具将代码抽象为预定义行为模式或统计特征，依赖模式匹配已知恶意行为，难以应对 0-day 攻击，且学习方法的二元分类结果缺乏可解释性。
  - **L3（成本高、可扩展性差）**：LLM-based 方法受限于上下文窗口、严重幻觉问题和昂贵的 token 处理成本，难以扩展到数百万仓库。

## 2. 方法论

### 2.1 核心思想

MalTotal 的核心理念是**利用 LLM 作为语言无关的恶意代码语义分析的"银弹"**：LLM 预训练于多样化代码，具备恶意模式领域知识，经过对齐训练后能够区分恶意与良性模式。关键挑战在于如何以最小化、精确的代码上下文提供给 LLM，以克服上下文窗口限制和 token 成本问题。

### 2.2 三大组件

**（1）敏感 API 提取器（Sensitive API Extractor）**

- **内置 API 收集（离线）**：整合 MalOSS（1,257 个 API）、MalTracker（293 个 JavaScript API）和官方语言文档（新增 597 个 API），构建包含 **2,147 个内置敏感 API** 的知识库，覆盖 5 大类别（payload 执行、网络访问、文件操作、敏感数据访问、密码学）。
- **第三方库 API 分析（在线）**：解析项目依赖配置文件，下载第三方库，定位具体 API 实现（限制在函数体本身），通过 LLM 进行语义推理，判断是否为敏感操作。结果以 (library, version, function) 为键缓存，避免重复分析。已在评估中分析并缓存 27,746 个第三方 API，识别出 694 个敏感 API。
- **基于解析的过滤**：使用 Semgrep 作为轻量级预处理器，高效匹配敏感 API 的直接调用和别名引用，快速过滤无敏感 API 的项目，缩小后续分析范围。

**（2）混合代码切片器（Hybrid Code Slicer）**

- 基于 Joern 生成代码属性图（CPG），融合 AST、CFG 和 PDG。
- 采用**汇点驱动的向后切片**策略：从敏感 API 调用点出发，递归遍历 CPG，提取所有可能影响其行为的前驱代码。
- 结合三种依赖关系：**调用链（Call Chain）、控制依赖（Control Dependency）、数据依赖（Data Dependency）**；默认最大调用深度 k=3，且保留被调用函数的完整函数体以维持语义完整性。
- 对直接调用从 API 调用节点向后切片；对别名引用先进行前向数据流分析定位真实调用点，再向后切片。
- **上下文精炼与聚合**：先进行最大子集过滤（丢弃完全被包含的切片），再通过行级 Jaccard 相似度（阈值 τ=0.3）进行迭代聚合，将语义相似切片合并为完整行为上下文。

**（3）LLM 语义分析器（LLM-based Semantic Analyzer）**

- 设计结构化提示模板，整合四种关键提示工程技术：角色分配（安全专家）、思维链引导（四步推理：识别敏感操作→追踪数据流→评估意图→综合判断）、上下文学习（少样本示例）、标准化 JSON 输出。

## 7. 优点

- **语言无关设计**：首次系统性地利用 LLM 实现跨 5 种主流语言的恶意代码检测，无需针对每种语言重新设计特征或规则。
- **成本效益显著**：94% 的 token 削减和千万级仓库的极低分析成本，使大规模安全检测在经济学上成为可能。
- **系统化消融验证**：对每个设计决策（调用深度、依赖类型、切片粒度）进行了细致的敏感性分析，提供了充分的实证依据。
- **真实世界验证**：120K 仓库部署并发现 564 个真实恶意仓库，展示了方法从学术研究到实际威胁发现的有效转化。
- **针对第三方库的检测能力**：解决了现有方法忽略第三方库中敏感 API 的盲区，扩大了恶意行为检测覆盖面。

## 8. 不足与局限

- **依赖底层静态分析工具成熟度**：切片阶段需要语言感知的静态分析支持，扩展到新语言需要集成相应 parser/slicer 后端（如 CodeQL、YASA）并重新构建内置敏感 API 知识库。
- **无法处理跨语言攻击**：无法追踪跨语言边界的数据流/控制流（如 Python 调用 C 库），对将恶意 payload 隐藏在原生扩展中的高级攻击存在盲区。
- **别名分析简化**：预过滤阶段刻意省略了复杂的程序内/程序间别名解析，对深度多跳别名链隐藏敏感操作的复杂攻击存在检测盲区。
- **LLM 引入新攻击面**：易受提示注入攻击；攻击者可在代码中嵌入误导性注释或字符串，操纵模型将恶意代码误判为良性。
- **仅限源码级分析**：无法检测依赖投毒攻击（良性源码依赖恶意包）和外部文件执行链（如调用 powershell.exe 执行 .ps1 载荷）。
- **误报率仍偏高**：大规模部署中 FDR 达 32.2%（1,553 个初筛中 502 个误报），尽管 FPR 极低（0.4%），但对安全团队的人工审核仍有较大负担。
- **幻觉风险**：LLM 可能在第三方 API 识别或恶意判断中出现误判，虽然 TPL 验证中误报率低，但 LLM-as-a-Judge 的固有不确定性仍未完全消除。
- **数据集偏差**：Java/PHP/Go 恶意样本规模有限（<150 个），可能不足以代表这些语言的真实威胁分布；对 GitHub 仓库的研究集中于 StarScout 的高风险子集而非完全随机抽样。
