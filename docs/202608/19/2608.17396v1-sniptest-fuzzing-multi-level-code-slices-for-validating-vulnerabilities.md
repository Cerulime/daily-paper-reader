## 摘要
现代软件系统日益复杂，静态分析工具通常用于通过发出警告来识别潜在易受攻击的代码。然而，这些警告通常需要人工检查以确认所报告的问题是否真实存在，这使得该过程耗时且容易出错。定向模糊测试已成为一种强大的自动化技术，用于验证这些警告。然而，针对每个警告将其应用于整个项目在计算上是不可行的，通常需要数天的执行才能仅在代码覆盖率上获得渐进的改进。我们提出SNIPTEST，一个基于执行的警告分诊框架，它生成并模糊测试以静态分析警告为中心的编译代码切片。SNIPTEST并非证明整个程序中的可利用性，而是提供有关警告在逐步扩展的切片执行上下文中的行为的证据。它采用逐层切片策略，围绕目标位置逐步扩展上下文，以越来越高的精度验证潜在漏洞。我们在三个真实世界项目的97个真实漏洞和97个误报的基准上评估SNIPTEST。SNIPTEST通过在所有三个分析的切片级别上一致触发相应的bug预言，为97个已确认漏洞中的53个（54.6%）产生可能的真阳性证据，而其余案例不可达。特别是，在这些案例中的40.2%中，它沿着观察到的执行路径利用漏洞，与顶部三个栈帧匹配。在97个已确认的误报中，SNIPTEST通过到达警告而不触发bug预言，为54个案例（55.6%）产生可能的假阳性证据，但错误分类了28个案例（28.8%），其余案例未到达。最后，我们通过识别CVE-2025-11964展示了SNIPTEST的实际相关性。

## Abstract
Modern software systems are increasingly complex, and static analysis tools are commonly used to identify potentially vulnerable code by issuing warnings. However, these warnings often require manual inspection to confirm whether the reported issues are real, making the process time-consuming and error-prone. Directed fuzzing has emerged as a powerful automated technique to validate the warnings. However, applying it to the entire project in response to each warning is computationally infeasible, often requiring days of execution to achieve only incremental improvements in code coverage.   We present SNIPTEST, an execution-based warning triage framework that generates and fuzzes compiled code slices centered around static-analysis warnings. Rather than proving exploitability in the full program, SNIPTEST provides evidence about how a warning behaves under progressively expanded sliced execution contexts. It employs a layer-by-layer slicing strategy, incrementally expanding context around the target location to validate potential vulnerabilities with increasing precision. We evaluate SNIPTEST on a benchmark of 97 true vulnerabilities and 97 false alarms across three real-world projects. SNIPTEST produces Possible True Positive evidence for 53 of 97 confirmed vulnerabilities (54.6%) by triggering the corresponding bug oracle consistently across all three analyzed slice levels, while the remaining cases are unreachable. Particularly, in 40.2% of these cases, it exploits the vulnerability along the observed execution path, matching the top three stack frames. On the 97 confirmed false alarms, SNIPTEST produces Possible False Positive evidence for 54 cases (55.6%) by reaching the warning without triggering the bug oracle, but misclassifies 28 cases (28.8%),and the remaining cases are unreached. Finally, we demonstrate the practical relevance of SNIPTEST by identifying CVE-2025-11964.

### 1. 核心问题与整体含义（研究动机与背景）

- **背景**：现代软件系统日益复杂，静态分析工具被广泛用于发现潜在漏洞代码，但会产生大量警告，其中许多是误报。开发者需要人工逐一审查这些警告，过程耗时且易出错。
- **核心问题**：如何高效、自动化地验证静态分析警告的真实性（是真漏洞还是误报）？现有方法面临两难：
  - 全项目定向模糊测试（如 AFLGo）计算开销大，针对每个警告往往需要数天时间，且代码覆盖率提升有限。
  - 已有的切片式模糊测试（如 FUZZ SLICE）使用预先固定、不可调整的代码切片，切片过小会丢失必要上下文，过大则引入过多复杂性；且只使用单一局部切片，忽略备选调用链，容易产生假阴性。
- **整体含义**：SNIPTEST 提出一种基于执行的告警分诊框架，围绕静态分析警告生成并模糊测试**多级、逐步扩展的编译代码切片**，通过观察警告在不同切片级别下是否持续触发，来提供“可能的真阳性/可能假阳性”证据，从而帮助开发者优先处理真正的高风险警告，同时过滤误报。

### 2. 方法论：核心思想、关键技术细节、算法流程

#### 2.1 核心思想

- **多级切片（Slice Levels）**：以包含警告的函数为起点，按调用图距离逐层扩展切片上下文。
  - **Level 0**：只包含“脆弱函数”本身（最小切片）。
  - **Level 1**：加入脆弱函数的直接调用者及其依赖。
  - **Level 2**：再加入 Level 1 函数的调用者，依此类推。
- **跨级诊断信号**：将不同级别上的模糊测试结果序列作为诊断依据——
  - 警告只在最受限的 Level 0 触发，而在扩展上下文后消失 → 可能是脆弱的、上下文敏感的告警（偏误报）。
  - 警告在逐步扩展上下文中持续触发 → 更可能是系统性真实漏洞，应优先处理。

#### 2.2 算法流程（四步）

1. **构建静态函数级调用图**：使用 Tree-sitter 解析 AST，提取函数定义和调用关系。
2. **识别包含警告的函数**：根据静态分析警告位置在 AST 中定位其所在函数。
3. **生成并编译递增上下文切片**：
   - 定义切片级别（Level 0/1/2...）。
   - 对每个级别确定入口函数（调用距离为 k 的祖先函数）。
   - 基于 FUZZ SLICE 的底层切片编译功能，将切片生成独立可编译可执行的二进制。
   - SNIPTEST 的贡献在于多级编排，而非底层切片算法。
4. **模糊测试二进制并分类**：
   - 使用 AFL++ 进行模糊测试，结合 LLVM coverage 收集覆盖信息，使用 ASAN/UBSAN/LeakSanitizer 等作为 bug oracle。
   - **每二进制分类**：`Triggered`（触发漏洞）、`Reached`（到达但未触发）、`Not Reachable`（未到达）。
   - **每级别聚合**：`Vulnerable (V)`（至少一个二进制触发）、`Benign (B)`（至少一个到达但无触发）、`Not Reachable (NR)`。
   - **跨级别最终分类**：`Possible True Positive (PTP)`（所有级别均为 V）、`Possible False Positive (PFP)`（低级别 B，更高级别 B 或 NR）、`Not Reachable (NR)`。

#### 2.3 关键优化（O1–O6）

- **切片创建优化**：
  - O1：缓存最小化切片，避免重复最小化和编译（尤其处理循环调用）。
  - O2：并行化切片创建。
- **切片模糊测试优化**：
  - O3：某级别任一二进制触发后，跳过该级别剩余切片的模糊测试。
  - O4：如果某一级别到达警告但未触发，跳过更高级别模糊测试（早期停止）。
  - O5：并行化独立切片的模糊测试。
  - O6：静态剪除不影响漏洞执行的无关代码（如控制流块之后的代码），提高到达率。

### 6. 主要结论与发现

- **RQ1（真漏洞）**：SNIPTEST 对 53/97（54.6%）真实漏洞在所有三个级别上稳定触发 bug oracle，没有误分类；其余 44 个因不可达而无法分类。
- **RQ2（误报）**：对 54/97（55.6%）误报给出 PFP 证据；错误分类 28 个（28.8%）为 PTP；其余不可达。
- **RQ3（栈轨迹保真度）**：Level 0 平均 88.6% 的切片入口函数与真实栈轨迹对齐，随级别增加下降（Level 1：56.7%，Level 2：40.2%）。
- **RQ4（效率）**：优化使切片创建时间减少 92.9%，模糊测试时间减少 96.5%，被模糊的切片数量减少 70.7%；O6 使漏洞到达率提升 35%。
- **RQ5（与 AFLGo 对比）**：无种子 SNIPTEST 达到 107 个位置，多于无种子 AFLGo（40），与有种子 AFLGo（112）接近；总耗时 2.09 天 vs 22.23 天（10.6× 加速）vs 11.68 天（5.5× 加速）。
- **RQ6（与 LLM4SA 对比）**：SNIPTEST 的 F1 为 0.791，远高于 LLM4SA 的 0.360；LLM4SA 偏向将 TP 判为 FP。
- **RQ7（与 FUZZ SLICE 对比）**：SNIPTEST 在 Level 0 到达并分类 169 个位置，FUZZ SLICE 为 137 个（多 23.3%）；F1 从 0.722 提升到 0.791。
- **实践发现**：在 Vim 和 libpcap 中发现 3 个新漏洞，包括 CVE-2025-11964（libpcap 堆缓冲区溢出），并获得开发者确认和修复。

### 7. 优点：方法与实验设计的亮点

- **多级上下文作为诊断信号**：不依赖单个切片，而是通过警告在递增上下文中的行为稳定性来区分真漏洞与误报，构思新颖。
- **首个动态调整切片的方法**：相比 FUZZ SLICE 等固定切片方法，SNIPTEST 根据 fuzzing 反馈决定是否扩展切片，属于“反应式切片”。
- **工程优化全面**：缓存、剪枝、并行化、早期停止等优化使多级切片分析在可接受计算成本内完成，具备实际可用性。
- **评估严谨**：同时分析 TP/FP 两个方向，报告 PTP、PFP、NR，并计算精度/召回/F1；对与 AFLGo、LLM4SA、FUZZ SLICE 的对比进行了详细讨论，包括重叠和独有案例。
- **实际漏洞发现**：在真实项目中发现并披露 CVE，验证了方法的现实价值。
- **可复现性**：提供了公开的复制包和数据集。

### 8. 不足与局限

- **上下文不完整**：切片只扩展到 Level 2，某些决定性 guard 条件位于更高级调用者中，导致误分类（28 个误报被误判为 PTP）。
- **fuzzing 时间预算有限**：5/7.5/10 分钟可能不足以探索复杂切片，产生不可达或假阴性；重复实验中观察到 2 个 libxml2 案例在多次运行间结果不稳定。
- **环境建模缺失**：函数指针被置为 NULL、不处理文件 I/O 和环境变量，可能造成误报/假阴性/不可达。
- **分类规则是启发式的**：跨级聚合规则缺乏形式化的完备性保证，只能作为优先级参考而非最终判定。
- **基准构建依赖 RevBugBench**：注入的 bug 与真实自然漏洞存在一定差异，可能影响结论的推广性。
- **对比的公平性受任务设置影响**：SNIPTEST 与 LLM4SA 的比较本质上属于执行验证与静态预测的差异，LLM4SA 无法获得运行时证据，优势并不意外；与 AFLGo 的对比中，SNIPTEST 利用切片减少输入维度，占据天然优势，且 SLIPTEST 在 zstd 上无种子 AFLGo 完全无法到达目标，这可能与 AFLGo 的算法参数有关。
- **计算成本仍然较高**：即便有优化，完整分析 194 个位置仍需约 2 天（20 核），对大型项目或大量警告的可扩展性仍有挑战。
