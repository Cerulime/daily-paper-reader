## 摘要
自动化安全补丁回溯移植对于缓解N-day漏洞至关重要。近期工具在其各自数据集上报告的成功率超过80%。然而，这些评估通常局限于同质环境，例如单一代码库或特定项目版本。因此，这些工具在其最初目标场景之外的泛化能力仍不明确。我们提出了Porting Benchmark，一个包含1,234个安全补丁回溯移植案例的精选数据集，涵盖跨版本、跨分支和跨仓库场景，并配备了一个通用评估框架。使用该基准，我们在对齐设置下评估了涵盖程序分析、LLM提示和LLM智能体的五种工具。结果表明，对齐评估改变了表面性能格局：在复制数据集上，PortGPT和TSBPort仍相对较强，而FixMorph和Mystique在通用协议下性能大幅下降。在结构复杂的补丁上，性能急剧下降：最佳提交级成功率从Type-I补丁的85.2%降至Type-IV的24.0%。我们识别了四类根本原因（目标API感知缺失、跨版本语义不匹配、非局部依赖传播失败以及补丁构造或定位失败），并为下一代工具设计得出了具体方向。在一个包含经验证测试用例和构造的POC的45例动态验证子集上，我们进一步观察到，基于参考的基准分数并未完全反映真实世界的修复效果：精确匹配严重低估了更困难的目标适配，而可执行验证揭示了静态参考一致性遗漏的目标中残留集成失败。可执行反馈细化在最困难的可执行案例上提供了有限但可衡量的改进。

## Abstract
Automated security patch backporting is critical for mitigating N-day vulnerabilities. Recent tools report success rates above 80% on their respective datasets. However, these evaluations are often confined to homogeneous environments, such as one repository or specific project versions. Consequently, it remains unclear how well these tools generalize beyond their originally targeted scenarios. We present Porting Benchmark, a curated dataset of 1,234 security patch backporting cases spanning cross-version, cross-branch, and cross-repository scenarios, paired with a common evaluation framework. Using this benchmark, we evaluate five tools spanning program analysis, LLM prompting, and LLM agents under aligned settings. Our results show that aligned evaluation changes the apparent performance landscape: PortGPT and TSBPort remain comparatively strong on the Replication Dataset, while FixMorph and Mystique degrade substantially under the common protocol. Performance degrades sharply on structurally complex patches: the best commit-level success rate falls from 85.2% on Type-I patches to 24.0% on Type-IV. We identify four root-cause categories (missing target API awareness, cross-version semantic mismatch, non-local dependency propagation failure, and patch construction or localization failure) and derive concrete directions for next-generation tool design. On a 45-case dynamically validated subset with verified test cases and constructed POCs, we further observe that reference-based benchmark scores do not fully capture real-world remediation: exact match sharply under-credits harder target adaptations, while executable validation reveals residual integration failures in the target that static reference agreement misses. Executable-feedback refinement provides limited but measurable recovery on the hardest executable cases.

### 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：构建一个统一、可复现、覆盖多场景的基准平台（**Porting Benchmark**），统一评估协议、统一度量、统一信息级别，使不同范式的工具可在同一坐标系下公平比较。
- **关键技术细节**：

  - **基准构建（两层级数据集）**
    - **Replication Dataset**（复制数据集）：融合 5 个已发布数据集，去除重复，按跨场景和发布时间分层抽样，得到 600 个 commit 级案例，用于 RQ1 的可复现性评估。
    - **Evaluation Dataset**（评估数据集）：仅收集 2024+ 的漏洞修复案例（减少 LLM 数据泄漏），覆盖跨版本（233）、跨分支（283）、跨仓库（118），共 634 个 commit / 1,299 个文件 / 2,515 个函数，用于 RQ2–RQ4 的泛化性评估。
    - **45 例可执行子集**：从评估数据集中筛选出具备可复现构建环境、可运行测试和可触发 POC 的 45 个案例，用于 RQ3/RQ5 的动态验证。

  - **分类维度**：
    - **跨场景**：跨版本、跨分支、跨仓库；
    - **移植类型**（复杂度）：Type-I（完全一致）、Type-II（仅位置变化）、Type-III（语法适配）、Type-IV（结构性变化）；
    - **路径变化**：目标文件路径是否不同于源路径；
    - **信息级别**：I0（仓库级）、I1（文件级）、I2（函数级）。

  - **统一评估框架（五级层次化补丁匹配）**：
    - **L1（精确匹配 EM）**：归一化后的工具输出代码与参考代码完全一致；
    - **L2（段落匹配）**：工具产生的增删块与参考补丁的块一一对应，且行号偏移容忍度 δ≤3、归一化相似度阈值 τ=0.8；
    - **L3（函数重叠）**：匹配块作用于相同目标函数；
    - **L4（精确性）**：工具修改位置必须与参考修改位置一致；
    - **L5（完整性）**：所有参考修改位置必须被工具覆盖。
    - **Semantic Success（S-Succ）**：非精确匹配时，需通过 L2–L5 + 人工验证（ManualVerify）方可判定成功。

  - **人工验证协议（ManualVerify）**：七项检查（MV1–MV7），包括语法有效性、安全性/清理、缺少/弱化修复、多余行为、目标适配、纯格式差异、证据不足，采用双人独立盲审 + 第三方裁决。

  - **可执行验证指标**：POC 通过率（PPR）、测试通过率（TPR）、完整验证率（Full）。

  - **根因分析框架**：四类失败根因——F1（目标 API 感知缺失）、F2（跨版本语义不匹配）、F3（非局部依赖传播失败）、F4（补丁构造或定位失败）。

  - **可执行反馈细化（RQ5）**：对未通过完整验证的 PortGPT 案例，使用执行结果作为反馈，通过至多 4 轮、每轮至多 3 个 SEARCH/REPLACE 候选进行修复，采用有序无回归替换规则。

### 6. 论文的主要结论与发现

- **RQ1（性能稳定性）**：统一协议下所有工具相对原始报告均有下降。PortGPT（80.5% S-Succ）和 TSBPort（75.8%）在提交级仍相对较强，Mystique 从 92.4% 暴跌至 14.7%，FixMorph 从 75.1% 降至 28.1%，PPatHF 从 42.3% 降至 30.0%。
- **RQ2（场景分析）**：
  - 移植复杂度是主导瓶颈：PortGPT 提交级 S-Succ 从 Type-I 的 85.2% 降至 Type-IV 的 24.0%，其他工具 Type-IV 均不高于 10.4%；
  - 跨场景泛化因工具而异：PortGPT 全面领先（跨分支 70.7%、跨版本 63.1%、跨仓库 62.7%）；
  - 额外定位信息并非普遍有益：Mystique 在 I2 改善，PPatHF 基本不变，PortGPT 在 I0–I2 稳定；
  - 补丁规模影响显著：超过 500 行变更时所有工具归零；多文件（>5）时三个传统工具归零。
- **RQ3（基准-现实差距）**：静态参考一致性不能完全预测可执行修复效果。PortGPT 在 45 例上 S-Succ 和 Full 均为 80.0%（36/45），但存在两个案例级错配（一个仅 S-Succ 通过、一个仅可执行验证通过），表明精确匹配会低估困难适配，静态参考一致性也会遗漏真实集成失败。
- **RQ4（根因分析）**：F4（补丁构造或定位失败，45.0%）和 F3（非局部依赖传播失败，39.2%）是最常见失败类别；F1（8.3%）和 F2（6.7%）占比较低。
- **RQ5（可执行反馈改进）**：可执行反馈细化将 PortGPT 的 Full 验证从 36/45 提升至 37/45（+2.2 个百分点），改进有限但可衡量。

### 7. 优点

- **统一评估框架的开创性**：首次将三种范式的五类工具在统一协议、统一度量和统一坐标系统下对齐比较，有效解决了文献中无法横向对比的问题。
- **数据集规模与覆盖度**：1,234 个案例覆盖跨版本/跨分支/跨仓库三种场景，且评估数据集仅收集 2024+ 案例，减缓了 LLM 数据泄漏风险。
- **分层验证体系**：L1–L5 匹配 + 人工验证 + 可执行验证（POC/测试）相结合，兼顾静态一致性和动态有效性。
- **信息级别控制**：通过 I0–I2 三档信息级别，将定位能力与变换能力分离，避免混淆。
- **根因分析**：对失败案例进行系统分类，为下一代工具提供可操作的设计方向。
- **可复现性**：提供元数据、脚本和稳定的分层抽样种子（seed 42），并报告了人工标注一致性。

### 8. 不足与局限

- **样本量局限**：45 例可执行子集规模较小，且经过严格筛选（634→179→45），不能代表完整评估集，分小组统计功效有限。
- **静态参考偏差**：EM/S-Succ 均以参考补丁为基准，可能低估了结构不同但功能正确的修复方案。
- **人工验证主观性**：人工验证一致性仅为 κ=0.5357（76.5% 一致），存在主观判断风险；根因分类的比例可能受类别边界影响。
- **跨场景不均衡**：评估集中跨版本/跨分支案例较多，跨仓库仅 118 例；数据来源以 C/C++ 安全补丁为主（>50 个项目），难以推广到其他语言或项目类型。
- **数据污染风险**：时间截断（2024+）只能缓解但不能完全排除 LLM 训练数据污染。
- **工具排除限制**：FixMorph 因构建环境限制被排除在 RQ2 之外；PatchWeave、SKYPORT、MigGPT、LLMPort 因客观条件未参与评估，削弱了工具覆盖面。
- **可执行反馈改进范围有限**：RQ5 仅针对 PortGPT 的少数困难案例，且改进幅度很小（+1 例，2.2 pp），不能推广到其他工具。
- **失败分母问题**：缺少输出、应用失败、提取失败均计入失败分母，可能导致对某些工具的评估偏悲观。
