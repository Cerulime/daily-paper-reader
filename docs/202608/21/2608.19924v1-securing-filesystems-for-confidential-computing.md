## 摘要
机密计算在可信执行环境（TEEs）内保护应用程序，但使存储易受攻击。即使采用磁盘加密，恶意的云提供商也可以回滚、重放、分叉或篡改磁盘状态，破坏有状态应用所需的完整性和新鲜性保证。现有解决方案要么假设存储可信，要么产生高开销，要么将完整性逻辑推入应用程序。我们提出了ShieldFS，一个符合POSIX的文件系统，在机密计算威胁模型下为持久存储提供端到端的完整性和新鲜性，且无需修改应用程序。ShieldFS使用简洁的密码学承诺来表示允许的文件系统状态，这些承诺在TEE内维护，并复制到一个轻量级可信注册表中。磁盘上的数据结构，包括预写日志和存储池，通过哈希链和嵌入式Merkle树进行认证。ShieldFS利用事务和写时复制来原子地更新持久文件系统状态和承诺。这些承诺在读取期间进行验证，确保即使在整个I/O栈不可信时也能检测到回滚、重放和模棱两可攻击。我们通过扩展ZFS实现了该设计，得到ShieldZFS。使用标准文件系统基准测试和真实工作负载的评估表明，ShieldZFS提供了强大的完整性和新鲜性保证，性能与最先进的文件系统相当。

## Abstract
Confidential computing protects applications inside Trusted Execution Environments (TEEs), but it leaves storage vulnerable. Even with disk encryption, a malicious cloud provider can roll back, replay, fork, or tamper with disk state, breaking the integrity and freshness guarantees required by stateful applications. Existing solutions either assume trusted storage, incur high overheads, or push integrity logic into applications. We present ShieldFS, a POSIX-compliant filesystem that provides end-to-end integrity and freshness for persistent storage in the confidential-computing threat model without requiring application changes. ShieldFS represents permissible filesystem states using succinct cryptographic commitments, maintained inside TEEs and replicated in a lightweight trusted registry. On-disk data structures, including a write-ahead log and a storage pool, are authenticated using hash chains and an embedded Merkle tree. ShieldFS utilizes transactions and copy-on-write to update persistent filesystem state and commitments atomically. The commitments are verified during reads, ensuring that rollback, replay, and equivocation attacks are detected even when the entire I/O stack is untrusted. We implement the design by extending ZFS, yielding ShieldZFS. Evaluation with standard filesystem benchmarks and real-world workloads shows that ShieldZFS provides strong integrity and freshness guarantees with performance comparable to state-of-the-art filesystems.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：机密计算（Confidential Computing）通过可信执行环境（TEE）保护应用在内存中的数据和计算过程，即使云管理员或服务提供商被攻破，也无法窥探或篡改运行中的代码和数据。然而，TEE 并不保护持久化存储（如虚拟磁盘、远程云存储）。
- **核心问题**：即使应用使用 TEE 保护的密钥对磁盘数据进行加密，恶意的云提供商仍可对存储执行**回滚（rollback）、重放（replay）、分叉（fork）和篡改（tampering）**攻击，破坏有状态应用所需的完整性（integrity）和新鲜性（freshness）保证。
- **现有方案的不足**：
  - 应用级方案（如 EnclaveDB、Treaty）需要开发者重新实现存储抽象，牺牲可编程性；
  - 块设备级方案（如 dm-integrity、Rollbaccine）资源开销高、依赖专门硬件或需重新设计云存储后端；
  - 已有的完整性文件系统（如 IPFS、Nexus）要么假设存储可信，要么无法防回滚，或开销过高；
  - 许多系统（如 SUNDR、Plutus）不覆盖回滚攻击。
- **论文目标**：构建一个**符合 POSIX 接口、无需应用修改**的文件系统，在机密计算威胁模型下为持久存储提供端到端的完整性和新鲜性，同时保持性能、可扩展性和易用性。

## 2. 论文提出的方法论：核心思想与关键技术细节

### 核心思想
- 将文件系统的持久状态组织为**认证数据结构（authenticated data structures）**，并在 TEE 受保护内存中增量维护其**密码学承诺（cryptographic commitments）**。
- 承诺是文件系统当前状态的简洁可验证表示，TEE 从不可信存储读取数据时通过承诺检测任何偏离。
- 利用文件系统已有的**事务（transactions）和写时复制（copy-on-write）**机制，保证持久状态与承诺的原子更新。
- 通过一个**轻量级可信注册表（CoRe）**持久化承诺，以支持崩溃恢复和跨会话的新鲜性。

### 关键技术细节
- **存储池（Storage Pool）认证**：
  - 将 ZFS 原有的块指针校验和替换为强密码学哈希（如 SHA-256），作为块内容的认证器；
  - 读取块时重新计算哈希并与指针中存储的认证器比对，不匹配则丢弃并返回“数据损坏”错误；
  - 使用抗碰撞哈希确保存储池构成有向无环图（DAG），且通过 uberblock 的认证器（`h_{i,v} = H(UB_{i,v})`）作为对整个存储池状态的承诺。
- **预写日志（WAL / ZIL）认证**：
  - 对 WAL 块构造**哈希链**（hash chain）：
    ```
    h_0 = H(0 || WB_0)
    h_k = H(h_{k-1} || WB_k)   for k > 0
    ```
  - `h_k` 是对 `WB_0` 到 `WB_k` 整个序列的承诺；
  - 维护 WAL 头部索引 `i`、尾部索引 `j`、头部认证器 `h_{i-1}` 和尾部认证器 `h_{j-1}`；
  - 尾部更新采用 **persist-then-register** 顺序，头部更新采用 **register-then-persist** 顺序，保证崩溃一致性。
- **承诺注册（CoRe）**：
  - 注册表维护每个文件系统 ID 对应的最近两个头部承诺（head）和最新尾部承诺（tail）；
  - 提供 session establishment、state recovery、state update 等同步接口；
  - 通过 TEE 远程证明和互认证通道保证只有授权 TEE 能访问/更新承诺；
  - 同一文件系统只允许一个活动会话，防止分叉攻击。
- **恢复流程**：
  - 从注册表获取已注册承诺；
  - 读取磁盘上的 uberblock，计算其哈希并与承诺中的认证器比对；
  - 通过哈希链验证并重放 WAL，最终恢复文件系统内存状态；
  - 若验证失败则报告“损坏”错误，阻止应用观察被篡改或过期的状态。
- **实现**：扩展 ZFS 2.3-release，增加约 2.5K 行代码，不改变 ZFS 持久化布局和核心 I/O 管线；CoRe 基于 CCF 框架实现，使用 QUIC 协议通信，并优化了复制协议以降低延迟（约 0.68 ms 平均注册延迟）。

## 6. 论文的主要结论与发现

- **安全结论**：
  - ShieldZFS 能检测所有 63 种攻击场景，而 ZFS 在攻击者同时修正校验和时无法检测重排序、删除、追加等 WAL 篡改；
  - 安全分析表明，ShieldZFS 将攻击者的数据伪造（Forge）事件转化为可检测的数据损坏（Corrupt）事件，从而满足完整性和新鲜性定义；
  - CoRe 的单一活动会话机制可防止分叉攻击。
- **性能结论**：
  - 与 ZFS 相比，ShieldZFS 在大多数真实工作负载下开销 <10%；
  - 在 fsync 密集型工作负载（varmail）中最大开销约 1.7×（主要来自 CoRe 注册延迟）；
  - 对同步写入，ShieldZFS 比 ext4+dm-integrity 快 1.14–1.65×，有时甚至快于普通 ext4；
  - 在 1MB 大块 I/O 下，所有文件系统性能收敛并饱和磁盘带宽，注册成本可忽略；
  - CoRe 支持约 5000 commitments/s 时 p90 延迟 ≤0.7ms，可支撑 25–500 个并发文件系统实例；
  - 混合设计（RocksDB DB 目录在 ext4 + 日志在 ShieldZFS）能同时获得高异步吞吐和强持久化保证。

## 7. 优点

- **设计优雅**：利用现有文件系统的 CoW、WAL、事务机制，将安全机制叠加在认证数据结构和承诺之上，不对应用透明性造成破坏。
- **通用性**：方法不仅适用于 ZFS，还可推广到 btrfs、ReFS 等同样采用日志和 CoW 的文件系统。
- **性能开销低**：相较块级认证方案（dm-integrity）或应用级方案，ShieldZFS 在保持强安全性的同时开销更小。
- **安全分析严谨**：给出了形式化的完整性/新鲜性定义（事件、会话、承诺序列），并进行了模块化的安全论证，还实现了攻击注入框架进行实证验证。
- **工程实现完整**：不仅实现文件系统安全扩展，还实现了可容错的承诺注册服务（CoRe），并考虑了崩溃恢复、一致性、授权策略等实际部署问题。
- **实验设计细致**：区分了“无 CoRe”和“完整版”以量化注册开销；区分 VM 和 CVM 以量化 TEE 硬件影响；提供了混合部署优化方案。

## 8. 不足与局限

- **实验覆盖不足**：
  - 未在真实的多租户云环境下进行大规模长期运行测试；
  - 未评估 CoRe 自身在节点故障、网络分区等故障注入下的行为；
  - 安全实验只针对 ZIL/WAL 块，未系统性测试对存储池内数据/元数据块的对抗性篡改（虽然论文声称哈希链可覆盖，但实证较少）。
- **性能局限**：
  - 同步写入和 fsync 密集型工作负载下开销较大（最高 1.7×），在 CVM 中因网络延迟更高而更明显；
  - 直接读性能比 ext4+dm-integrity 慢约 4.5 倍（可能源于 ZFS 本身复杂元数据结构，但论文未深入分析）。
- **依赖假设**：
  - 依赖 CoRe 的可用性，CoRe 不可用时会阻塞同步更新和故障恢复，影响活性（liveness）；
  - 安全论证依赖防碰撞/抗循环哈希的密码学假设，以及 ZFS 本身 WAL 重放逻辑的正确性；
  - 未覆盖侧信道攻击、DRAM 物理攻击（论文明确声明超出范围），因此行内人可能会质疑威胁模型的全面性。
- **实验公平性**：
  - 基线系统（特别是 dm-integrity）的配置可能未达到最优，论文没有提供参数调优细节；
  - 论文未报告误差线或重复实验次数，难以判断性能差异的统计显著性。
- **应用限制**：
  - 扩展其他文件系统（如 btrfs、ReFS）的概念可行，但未给出实现证据；
  - 对分布式文件系统（如 CephFS）的扩展仍需额外机制，论文未深入验证。
