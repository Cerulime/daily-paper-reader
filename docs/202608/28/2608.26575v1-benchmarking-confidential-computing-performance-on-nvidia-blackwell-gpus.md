## 摘要
本文测量了在NVIDIA B200 GPU上的可信执行环境（TEE）中运行大型语言模型推理和训练的性能影响，使用Intel Trust Domain Extensions（TDX）机密虚拟机与NVIDIA Blackwell GPU上的NVIDIA机密计算（CC）相结合。性能影响是通过在同一物理主机上对机密与非机密运行进行配对比较得出的，其中唯一变量是GPU CC位和虚拟机启动中的TDX客户机对象。主要结果是，当堆栈配置正确时，Blackwell上的机密推理实现了低个位数的吞吐量开销，约为1-3%。由于可避免的配置而非可达到的工作点，标准推理堆栈会遭受30%至40%的惩罚。成本并非由单一数字完全表示，因为它由两个独立的轴控制：一个固定的每主机操作成本，随批处理大小增长而摊销；以及一个每NVLink流量成本，追踪步骤中花在加密集合通信上的份额，两者中哪一个占主导地位由工作负载和软件决定。我们将每个成本定位到特定的加密边界，给出一个微基准测试，该测试可在提交计数内预测服务惩罚，并最终提供具体的部署指导。GPU计算、能耗和可用内存容量不受CC影响。

## Abstract
This paper measures the performance impact of running large language model inference and training inside a Trusted Execution Environment (TEE) on NVIDIA B200 GPUs, using Intel Trust Domain Extensions (TDX) confidential VMs together with NVIDIA Confidential Computing (CC) on Blackwell GPUs. The performance impact is derived from paired confidential versus non-confidential runs on a single physical host where the only variable is the GPU CC bit and the TDX guest object in the VM launch. The main result is that confidential inference on Blackwell achieves low single-digit throughput overhead when the stack is configured correctly, at about 1-3%. Stock inference stacks incur 30 to 40% penalties due to avoidable configurations rather than the achievable operating point. The cost is not fully represented by a single number because it is governed by two independent axes, a fixed per-host-operation cost that amortizes as batch size grows and a per-NVLink-traffic cost that tracks the share of the step spent in encrypted collectives, and which of the two dominates is set by the workload and the software. We localize each cost to a specific encrypted boundary, give a microbenchmark that predicts the serving penalty to within a submission count, and end with concrete deployment guidance. GPU compute, energy draw, and usable memory capacity are unaffected by CC.

### 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

**核心思想：**
- **受控配对对比**：每一组测量均为同一物理主机、同一磁盘、同一GPU上“CC开”与“CC关”的配对比较，唯一变量是GPU CC位及TDX客户机对象——“CC开”指同时设置GPU CC位（经BAR0寄存器）并使客户机以TDX机密虚拟机运行。
- **成本归因到具体边界**：将CC开销分解到四条加密边界——PCIe大块拷贝、命令通道、NVLink加密（NVLE）、能力缺失（NVSwitch多播）。
- **机制验证而非仅描述**：构建合成微基准`cc_probe`，从每操作成本出发预测真实服务惩罚，再用真实框架测量验证预测精度（精确到提交次数）。

**关键技术细节：**

1. **两条独立成本轴模型：**
   - **每主机操作成本（Per-host-operation cost）**：每次内核提交与主机-设备同步在CC下更昂贵（加密GSP-RPC命令通道 + 强制同步拷贝），为每解码步骤的固定成本，随批大小摊销，并可通过完整CUDA图与框架补丁消除。
   - **每NVLink流量成本（Per-NVLink-traffic cost）**：跨GPU集合通信经NVLE加密，以近似恒定的每字节速率计费。该成本随工作负载暴露的跨GPU通信在墙钟时间中的占比而变，较大批次不会提高每字节速率，不随批次摊销，构成硬件底线。

2. **微基准模型（核心公式）：**
   - 每内核提交的CC边际代价 ≈ **12 μs**（加密GSP-RPC命令路径），裸同步≈0；
   - 解码CC惩罚 = (每步主机提交次数) × ~12 μs；
   - 实证：真实vLLM运行测得CC开销2.28 ms/步，除以12 μs ≈ **185次提交/步**，与vLLM逐段CUDA图分割的提交数完全吻合——预测精确到提交计数。

3. **NVLE速率常数（§5.3）：**
   - Copy Engine带宽损失约11%（−12%）；SM-based带宽损失约18%；NCCL集合级约10%；小跨GPU写入延迟约4×。

4. **测量纪律：**
   - 每次测试间必须重启系统（CC GPU可能遗留陈旧状态，伪报100%利用率）；
   - CUDA事件计时在CC下被禁用（防计时侧信道），改用`%globaltimer`或墙钟吞吐；
   - GPU内核级性能分析（NVIDIA Nsight CUPTI跟踪）在CC下自禁用；仅主机侧系统调用跟踪可用；
   - 跟踪运行只用于归因，不用作吞吐锚点；吞吐数据来自独立的非跟踪运行。

### 6. 论文的主要结论与发现

1. **配置正确的机密推理开销为低个位数**：
   - MoE服务 TP4 约 **1.5%**、TP8 约 **3%**（钉住值2.8–3.6%，5次重复×2会话中位数）；单GPU完整CUDA图+框架补丁后不足1%；8-GPU bf16训练约10–13%。

2. **30–40%的“高额惩罚”源于可避免的软件/配置问题**，而非硬件瓶颈：
   - 未打补丁的eager框架或overlap-on调度在CC下丢失计算/拷贝重叠，才是高惩罚的根因。

3. **两轴成本模型**：
   - 每主机操作成本（~12 μs/次提交）→ 随批大小摊销、可被CUDA图+补丁消除；
   - 每NVLink流量成本（NVLE恒定速率）→ 随跨GPU通信暴露份额变化、构成硬件底线。

4. **NVLink加密是残余底线**：Copy Engine ~11%、SM-based ~18%、NCCL集合级 ~10%、小写延迟~4×；多GPU MoE在并发64–128时NVLE税约5%。

5. **并行策略是核心杠杆**：张量并行产生注意力all-reduce加密流量（随上下文增长），专家/数据并行几乎不产生（32k上下文下CC税≈2%乃至于噪声）；TP4比TP8税减半且保留94%吞吐。

6. **长输出/长上下文摊销prefill成本**：输出长度从256→2048时，CC税从14.4%降至1.1%；32k上下文下CC税≈0。

7. **GPU计算、能耗、可用显存容量不受CC影响**：能耗在CC变慢时反而略降（GPU空闲更多）；显存仅一次性预留700 MB。

8. **训练税10–13%**，完全来自加密集合通信，GEMM/HBM不受影响；FP8在CC下额外受损（1.24× vs 1.04×），建议bf16为机密训练默认。

---

### 7. 优点

1. **方法论严谨性**：所有结论基于同主机、同磁盘、同GPU的配对对比（唯一变量为CC状态），排除了配置混淆；对每类测量都有严格的重启/计时/分析纪律。
2. **成本归因到硬件边界**：将聚合减速分解到PCIe加密、命令通道、NVLink加密、能力缺失四个具体边界，并为每个成本建立独立测量证据。
3. **机制验证的闭环**：合成微基准（cc_probe）从每操作成本预测真实服务惩罚，预测精确到提交次数（2.28 ms/步 ÷ 12 μs ≈ 185次提交），实现了从第一性原理到生产框架的完整验证链。
4. **结果呈现为“表面”而非“单一数字”**：并发、序列长度、输出长度、并行策略、框架版本等多维度扫描，清晰展示两轴成本模型的动态行为，避免误导性平均值。
5. **工程可操作性**：给出具体部署建议（完整CUDA图、异步D2H worker、右尺寸TP、偏好EP/DP、解码为主的服务），且每一项都经端到端验证。
6. **诚实标注局限**：对未测量的部分（跨节点RDMA、prefill/decode分离、TDISP方向）明确声明为gap而非量化成本，不夸大适用范围。
7. **复现性关注**：详细披露了CC下的测量陷阱（陈旧状态、CUPTI禁用、负事件时间等），为后续研究者提供可操作的测量指南。

---

### 8. 不足与局限

1. **单一平台约束**：所有测量基于单一物理主机（Intel Xeon 6767P + 8×B200），结论的外推性受限于Blackwell/TDX组合，不覆盖Hopper、AMD、其他主机CPU或更大规模的集群。
2. **跨节点通信未量化**：RDMA被CC阻止、GPUDirect被封锁、跨节点KV传输的惩罚仅作机制描述，未做端到端测量——对prefill/decode分离架构的实际成本仍属未知。
3. **训练结果覆盖有限**：无长训练时长对比、无不同批大小/序列长度的训练扫描、无跨节点训练数据；FP8训练仅一种配置，结论的统计力度较弱。
4. **安全属性不在范围内**：论文明确不审计安全边界有效性，仅假定保证成立并测量其价格——不能据此断言实际攻击面已关闭。
5. **测量噪声与方向性问题**：多数组为单pass运行（±2个百分点噪声）；跨表/跨章节比较涉及不同框架版本与数周数据采集，仅具方向性意义。
6. **长期稳定性未评估**：长时间运行的性能漂移、内存碎片、CC状态切换后的累积效应均未测试（且要求每次测量前重启暗示了部署中可能出现的状态问题）。
7. **对短文本/高并发极端场景的适用性有限**：短输出（256 token）的prefill-heavy流量可达14%以上的惩罚；极低批大小（c1–c8）下部分测量为负值（噪声内）；该场景下的放大效应未单独深入研究。
8. **框架补丁的生态依赖**：核心修复（异步D2H worker）尚未进入上游主版本（截至论文写作时仍在开发中），实际用户需自行构建修改版框架；且补丁后仍有长输入/长输出形状下最高6.5%的残余。
