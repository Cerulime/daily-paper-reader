## 摘要
LLM服务框架在共享基础设施上处理大量用户数据，这些数据通常包含敏感信息。确保共享同一服务框架（在CPU上）的用户与LLM算子（在GPU上）之间的隔离对于隐私保护至关重要。本文提出了GIFT，一个GPU信息流跟踪系统，以极小的开销在LLM服务中强制执行用户数据隔离。此外，GIFT的设计是非侵入式的，允许CPU侧服务框架自由演进。它基于两个关键见解。第一，加密即隔离利用了这样一个观察：CPU组件只编排数据流，而不进行内容操作；因此，按用户加密可以在不修改服务逻辑的情况下提供隔离。第二，GPU内核表现出有限且可预测的信息流，使得静态流分析成为可能。GIFT为每个内核预计算信息流规则，并使用解耦流跟踪，避免了插桩或GPU停顿。此外，我们将GIFT扩展到GIFT-CC，它集成了机密计算，以防范不受信任的操作系统和虚拟机监控程序（LLM服务提供商）。在vLLM和DistServe上实现后，GIFT和GIFT-CC以4-10.7%的吞吐量开销强制用户数据隔离，同时保持相同的延迟水平。

## Abstract
LLM serving frameworks process large volumes of user data--often containing sensitive information--on shared infrastructure. Ensuring isolation between users who share the same serving framework (on CPUs) and LLM operators (on GPUs) is critical for privacy protection.   This paper presents GIFT, a GPU Information Flow Tracking system that enforces user data isolation in LLM serving with minimal overhead. Moreover, the design of GIFT is non-intrusive and allows CPU-side serving frameworks to evolve freely. It rests on two key insights. First, encryption-as-isolation leverages the observation that CPU components only orchestrate data flow, not content manipulation; thus, per-user encryption can provide isolation without modifying serving logic. Second, GPU kernels exhibit limited and predictable information flows, enabling static flow analysis. GIFT precomputes information flow rules for each kernel and uses decoupled flow tracking, avoiding instrumentation or GPU stalls.   Furthermore, we extend GIFT to GIFT-CC, which integrates confidential computing to protect against untrusted operating systems and hypervisors (LLM service providers). Implemented on vLLM and DistServe, GIFT and GIFT-CC enforce user data isolation with a 4-10.7% throughput overhead while maintaining the same latency level.

- **研究动机**：LLM 服务框架（如 vLLM、DistServe）在共享 GPU 基础设施上处理大量敏感用户数据（个人日程、医疗咨询、商业文档等），而现有系统在用户数据隔离方面存在严重安全隐患。历史事件（如 2023 年 OpenAI 因缓存系统 bug 导致用户聊天记录泄露、2025 年 ChatGPT 内容出现在 Google 搜索结果中）以及大量已公开的漏洞（如 CVE-2025-24357 可实现远程代码执行并窃取 KV 缓存中的用户数据）表明，这类风险不仅是理论上的，而是真实发生过的。

- **核心问题**：如何在复杂且快速演进的 LLM 服务系统中，可靠且高效地强制执行用户数据隔离？具体面临两大挑战：
  1. **系统复杂性**：现代 LLM 服务框架规模庞大（vLLM 代码量 146K 行、PyTorch 2.4M 行、TensorFlow 1.9M 行），跨多语言（Python/C++/Rust），且演进速度极快（vLLM 一年 7.5K 次提交），传统 IFT 难以适配。
  2. **GPU 开销**：传统 GPU 指令级插桩的 IFT 方法会造成 2.5–5.7 倍的性能下降，无法满足 LLM 服务高吞吐、低延迟的生产要求。

- **核心威胁模型**：
  - **GIFT**：假定操作系统和 hypervisor 可信，但 LLM 服务框架不可信（可能被攻陷或恶意行为）。
  - **GIFT-CC**：进一步假定 OS 和 hypervisor 也不可信（如云服务商管理员），依赖机密计算保护数据机密性。

## 2. 方法论：核心思想与关键技术

### 2.1 两个关键洞察

1. **加密即隔离（Encryption-as-Isolation）**：CPU 侧框架只负责编排数据流（调度、批处理、发内核），不直接操作数据内容（数据面在 GPU 上）。因此，对每个用户的数据用独立密钥加密后存储在 CPU 内存中，即使框架被攻陷，攻击者拿到的也只是密文。解密动作仅由可信的 GIFT monitor 在数据传给 GPU 前执行。

2. **GPU 内核信息流可静态分析**：LLM 服务的 GPU 内核是预定义的、确定性强的、分支有限，且通常有源码可分析。因此可以离线分析内核行为，预计算信息流规则（IFT rules），运行时直接在 CPU 上执行规则即可，无需对 GPU 内核插桩。

### 2.2 三大核心技术（降低 IFT 开销）

- **所有权分段（Ownership Segmentation）**：用户数据在同属一个所有者的 GPU 内存中通常形成连续的段（segment），因此可以在段级别而非字节/元素级别记录所有权，极大降低元数据量。例如，对一个 B×H 的矩阵，传统逐元素追踪需要 B×H 条记录，而 GIFT 只需 B 条。使用两级索引数据结构存储：一级映射基地址到张量记录，二级映射下标值到所有权记录。

- **静态流分析（Static Flow Analysis）**：离线为每个内核构建信息流图（IFG），用符号执行（KLEE）验证 IFG 正确性，再生成 IFT 规则。以图 3 中的 AddBiasAndActivation 内核为例，传统插桩需对 7 条指令做 IFT，而 GIFT 只需 3 步运行时的规则操作（检查 bias 是参数、读输入行的所有权、传播所有权到输出行），计算复杂度从 7×B×H 降低到 2×B+1。

- **解耦流跟踪（Decoupled Flow Tracking）**：利用静态分析结果，所有权传播不再与 GPU 内核执行交织，可在 CPU 上异步执行 IFT，与 GPU 计算重叠（overlap），从而隐藏 IFT 开销。同时通过在内存跟踪中记录最后写入者和最后读取者内核，强制执行读写/写写竞态的同步约束，防止多 GPU 流场景下出现数据竞争导致的信息泄露。

### 2.3 系统架构与工作流

- GIFT monitor（Rust 实现，约 5.6K 行代码）运行在受保护域（VM 或 TEE）中，独占 GPU。
- 工作流：用户端 tokenize 提示词 → 用每用户密钥加密 → 发送给服务框架 → 框架在密文上处理调度/批处理 → 请求 GPU 内核时向 monitor 提交元数据 → monitor 解密、验证所有权、启动内核 → 输出数据加密后返回框架。
- **关键安全属性**：即使框架提交伪造的所有权元数据，最多导致解密失败而非隐私泄露。

### 2.4 额外优化

- **Token 加密与混淆**：逐 token 使用块密码加密并添加随机 nonce，避免相同 token 产生相同密文暴露序列模式。
- **KV cache 安全交换空间**：在 monitor 受保护内存中分配交换空间，避免 KV cache 换出到 CPU 内存时的加密开销。
- **索引表缓存**：缓存 GPU 中的索引表（如 block table）到 monitor 内存，避免 IFT 时从 GPU 拷贝索引表造成阻塞。

1. **GIFT 以极小开销实现用户数据隔离**：

## 7. 方法亮点与优势

1. **两个核心洞察非常精妙**：
   - "加密即隔离"将安全从复杂框架中解耦，让框架可以自由演进而无需修改安全逻辑——这是非侵入式设计的关键。
   - 利用 GPU 内核的确定性/有限分支特性，将 IFT 从运行时插桩问题转化为离线分析+轻量运行时规则执行问题。

2. **真正意义上的近零开销**：相比传统 GPU taint tracking 的 2.5-5.7 倍开销，GIFT 的 4%-10.7% 吞吐开销是质的飞跃，使 IFT 在 LLM 服务从不可能变为可行。

3. **通用性**：GIFT 不绑定特定框架，在 vLLM 和 DistServe 两个主流系统上都有实现；IFT 规则库（29 个内核族）覆盖 Qwen、Llama、Gemma、OPT、GPT-2、Phi-3 等主流模型。

4. **TCB 控制良好**：monitor 仅 5.6K 行 Rust 代码，暴露 32 个接口，攻击面小；在 GIFT-CC 中相比 NVIDIA-CC 原生的安全模型仅增加约 5.6K 行代码。

5. **关注了实际部署问题**：多 GPU 流的竞态控制、KV cache 交换空间的加密开销规避、索引表缓存的性能优化，都是工程落地中不可回避的问题。

## 8. 不足与局限

### 8.1 方法层面的局限

1. **假设 CPU 不修改用户数据**：GIFT 的前提是 CPU 侧框架只编排数据流而不操作内容。若未来框架出现需要在 CPU 上直接处理数据内容的新功能（如 CPU offload 的部分算子），GIFT 需要将这类操作委托给 monitor，可能引入额外复杂性和性能瓶颈。

2. **IFT 规则生成是半自动化的**：目前依赖人工提取信息流图（IFG）并将 CUDA 转译为 C++（供 KLEE 验证），原因是缺少完整的 CUDA 符号执行引擎和 CUDA 到 C++ 转译器。虽然一次性成本且规则可复用，但仍是工程化的瓶颈。

3. **部分内核可能无法预先分析**：若因技术或法律限制无法获得内核源码，只能通过黑盒采样推导近似规则，可能牺牲健全性（soundness）。

### 8.2 实验层面的局限

1. **GIFT-CC 实验硬件受限**：仅 1 张 H100，无法反映多卡 TEE 部署的真实情况；A800 不支持 NVIDIA-CC，导致 Baseline-TEE 对比仅在 H100 上；OPT-66B 和 Qwen2.5-72B 未纳入 GIFT-CC 评估。

2. **推测解码实验**中 GIFT-CC 相对 Baseline 的开销（10.7%）主要来自 NVIDIA-CC 的 CPU-GPU 通信开销，但论文未能分离 GIFT 自身逻辑与 TEE 硬件的开销贡献。

3. **安全评估缺乏系统性的攻防对抗实验**：只演示了一个概念验证攻击（confused-deputy 攻击），未进行大规模 fuzzing 或渗透测试。

### 8.3 威胁模型与适用边界

1. **侧信道攻击不防护**：论文明确将侧信道攻击排除在范围外（但对追求强隔离的用户来说，这可能是一个不可忽略的缺口）。
2. **DoS 攻击不防护**：依赖其他专门系统处理。
3. **推理结果完整性**：GIFT 不防止模型输出被恶意篡改或降质，只保证数据不被泄露。
4. **信任假设**：GIFT（非 CC 版本）仍信任 OS/hypervisor；GIFT-CC 虽不信任它们，但 TCB 中仍包含 CUDA runtime/driver（1.4M LoC）和精简 Linux 内核（1M LoC），并非最小 TCB。

### 8.4 其他

- 文本中未讨论互联网场景中的端到端加密通道（用户到 monitor 的密钥协商和传输安全）细节，仅提及用户设备在本地 tokenize 和加密。
- Token 加密使用 64-bit token + 随机 nonce 扩展为 128-bit 块密码，但未讨论 nonce 冲突对该方案安全性的影响。
