## 摘要
限制应用程序可用的系统调用可以缩小内核的攻击面，并大大减轻程序被攻破后的影响。近期的方法展示了生成系统调用过滤器的技术，然而，所有现有解决方案都需要修改内核或应用程序才能在运行时激活它们。这具有侵入性、易出错，并且通常不切实际，尤其是当代码由外部方维护时。本文提出了SysComb，一种基于eBPF的新型解决方案，能够根据应用程序状态强制执行时间特化的系统调用过滤器，而无需修改应用程序或内核代码，从而解决了上述限制。此外，SysComb允许开发者选择两种不同的强制执行策略：类似seccomp的策略，确保状态转换后不会获得新的权限；以及最小权限策略，对每个状态应用最严格的过滤器。我们使用广泛使用的软件对SysComb进行了评估，展示了准确的状态感知系统调用过滤以及与内置内核解决方案相当的 overhead，证明了我们方法的实用性。

## Abstract
Restricting the system calls available to applications shrinks the kernel's attack surface and greatly mitigates the impact of compromised programs. Recent approaches showcase techniques to generate system call filters, however, all existing solutions require either kernel or application modifications to activate them at runtime. This is intrusive, error-prone, and often impractical, especially when the code is maintained by external parties. This paper presents SysComb, a novel eBPF-based solution to enforce temporally-specialized system call filters based on the application state, without requiring any modification to the application or the kernel code, and thus addressing the above limitations. Moreover, SysComb lets the developer choose between two distinct enforcement strategies: seccomp-like, ensuring no new privileges are gained after a state transition is performed, and least-privilege, which applies to each state the most restrictive filter. We evaluated SysComb using widely used software, showcasing accurate state-aware system call filtering and an overhead comparable to built-in kernel solutions, demonstrating the practicality of our approach.

## 1. 核心问题与整体含义（研究动机与背景）

- **问题**：系统调用过滤（如 seccomp）是缩小内核攻击面、降低应用被攻破后影响的关键防护机制。但现有方案在实践中有效性和可用性不足：
  - 大多数应用只在启动时设置一次宽松的过滤器，之后几乎不更新，导致过滤粒度极粗，内部各组件共享同一组系统调用权限。
  - 已有研究（TSP、SysPart 等）提出了"时间特化"概念——按应用执行状态（如初始化阶段 vs. 服务阶段）配置不同过滤器，但激活这些过滤器需要**修改应用代码**、**打内核补丁**或**依赖用户态监控组件**，均具有侵入性强、维护成本高或扩展攻击面等缺点。
- **核心目标**：设计一种无需修改应用或内核代码、不引入用户态监控委托、且支持按应用状态（甚至按线程）细粒度切换系统调用过滤器的方案。
- **整体意义**：将系统调用过滤从"静态、粗粒度、部署困难"推向"动态、细粒度、透明部署"，让安全防护机制能在第三方维护的二进制软件上直接应用，具有较高的实用价值。

## 2. 方法论

### 核心思想
SysComb 完全基于 eBPF 在**内核边界内**运行，通过 uprobe 检测应用状态转换，通过内核 tracepoint/kprobe 拦截系统调用事件，在系统调用执行前进行同步检查和强制拦截。

### 关键技术细节

1. **应用状态跟踪**：
   - 开发者指定"转换点"（transition points），可以是符号名、符号偏移或绝对地址，可位于应用二进制或其动态依赖中。
   - 通过 uprobe 附着到这些转换点，配合 attach cookie 区分不同转换点，实现线程级状态跟踪。
   - 使用 `tracee map` 记录每个被跟踪任务（tracee）的当前状态；使用 `application state map` 存储各状态对应的系统调用位图和合法转换关系。
   - 新进程通过 fork/exec 跟踪和 ELF entry uprobe 自动纳入管理。

2. **系统调用跟踪与过滤**：
   - 跟踪模式下，在 `sys_enter` raw tracepoint 挂载 eBPF 程序，记录每个状态实际调用的系统调用，用于构建过滤器。
   - 强制模式下，可选两种挂钩方式：
     - **Raw tracepoint**（sys_enter）：用于直接拦截。
     - **kprobes + 错误注入（ALLOW_ERROR_INJECTION）**：挂在每个系统调用入口函数上，通过注入错误码在系统调用代码真正执行前拒绝调用，可避免副作用。
   - 两种方式均可覆盖所有系统调用，过滤决策在系统调用执行前同步完成，不可绕过。

3. **两种强制策略**：
   - **seccomp-like**：状态转换后过滤器只会收紧或不变，不会获得新权限。通过"基于流的系统调用反向传播"算法（Algorithm 1）实现，对状态图做强连通分量分析、逆拓扑序合并和回传，确保权限单调递减。
   - **least-privilege**：每个状态绑定自己最小的系统调用集，过滤效果更严格，但状态转换可能导致获得更多权限（需配合状态图合法性校验）。

4. **流程完整性验证**：强制模式下，所有状态转换需与跟踪阶段构建的状态图一致，非法转换（如控制流被劫持后跳转到任意转换点）会被检测并触发强制动作（日志/返回错误/终止）。

5. **强制动作**：支持三种：记录日志、注入错误码返回给应用、终止线程。实现上终止动作也会先注入错误码，确保系统调用代码不执行。

### 算法流程（文字描述）
**flow-based backpropagation（seccomp-like 策略）**：
1. 用 Kosaraju-Sharir 算法找出状态图所有强连通分量（SCC）。
2. 按逆拓扑序遍历所有 SCC。
3. 对每个 SCC，将其内所有状态的系统调用集合合并。
4. 将合并后的集合赋给该 SCC 内所有状态，并反向传播到所有前驱状态。
5. 合并后，可剪枝拥有相同系统调用集的冗余状态。

## 6. 主要结论与发现

1. **透明且准确**：SysComb 能准确捕获应用系统调用，且从应用入口点开始跟踪（比 strace 更精细），生成的过滤器经 Minijail 验证可正常运行。
2. **状态感知过滤更严格**：
   - seccomp-like 策略：从 Listen 到 Cleanup 阶段平均减少 11.82% / 20.77% / 76.34% 的系统调用。
   - least-privilege 策略：相比无特化，Startup 少 35.22%、Listen 少 47.97%、Serve 少 22.05%、Cleanup 少 76.34%。
3. **有效缩小攻击面**：
   - 37.8% 的测试 CVE（17/45）可通过比单一过滤器更严格的专用策略被阻止。
   - 安全敏感系统调用阻止率从 55.9% 提升到 72.8%（+16.9%）。
   - 平均每个应用多阻止 98 个 shellcode（+27.8%）。
4. **性能可接受**：
   - 微基准：getpid 在强制模式下为 303 ns（raw tracepoint）和 487 ns（kprobes），与 seccomp（217 ns）同数量级，远优于 ptrace（~12 μs）。
   - 宏基准：在 9 个应用中最大 overhead 为 Bind 的 4.46%（tracing），强制模式相对 seccomp 的最大 overhead 仅 0.68%。

## 7. 优点

- **完全透明**：无需修改应用源码或二进制、无内核补丁，对第三方维护的软件可直接部署，解决了现有工具的核心痛点。
- **真正的线程级、状态级细粒度过滤**：支持任意数量的执行状态（不只是两阶段），并跟踪每个线程的状态。
- **同步且不可绕过**：过滤决策在系统调用执行前在内核态完成，不依赖用户态监控组件，符合安全强制要求。
- **两种策略灵活可选**：seccomp-like 保证权限单调递减；least-privilege 提供更严格的最小权限。
- **内建控制流完整性检查**：通过状态图校验非法转换，能检测控制流劫持攻击的早期迹象。
- **完整支持动态依赖**：过滤范围覆盖动态库和外部二进制，避免过度近似。
- **工程实现扎实**：利用 attach cookie、eBPF 错误注入机制、bpffs pinning 和 LSM 防护等特性，兼顾可扩展性和安全性。
- **评估较全面**：从准确性、有效性、安全增益和性能四个维度系统评估，并覆盖多种工作负载。

## 8. 不足与局限

- **Green Threads 不支持**：对运行时库内部实现的绿色线程（如 Go、Java 协程）不能直接跟踪，需要额外对运行时函数挂钩子点。
- **解释型语言不直接兼容**：Python、Java、JavaScript 等运行时需定制转换点，且需深入理解运行时内部逻辑，泛化能力有限。
- **需要特权**：加载 eBPF 程序需要超级用户权限（虽然运行后自动释放），这在某些多租户环境下部署受限。
- **对控制流劫持攻击只能缓解不能根治**：能阻止通过非法状态转换提升权限，但不能阻止攻击者在当前状态合法权限内的恶意操作。
- **跟踪阶段的完整性依赖测试覆盖率**：测试覆盖不完整的路径（如高可用故障恢复、冷备切换）会导致过滤器过于严格，误杀系统调用；后续需要人工审查策略。
- **状态识别准确度没有系统量化**：过渡点选择依赖开发者经验，不同选择对过滤效果的影响没有深入分析。
- **未在容器/云原生环境中做端到端部署实验**：虽然与容器方案进行对比，但 SysComb 在 Kubernetes 等实际编排环境中的表现未验证。
- **用户态系统调用指令绕过的问题未充分讨论**：例如应用通过 SUD 或内联汇编绕过库调用的场景在评估中未覆盖。
