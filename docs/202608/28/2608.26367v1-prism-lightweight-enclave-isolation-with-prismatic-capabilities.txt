# Abstract 

Trusted execution environments (TEEs) protect sensitive code and data from external interference, but lack inherent memory safety. CHERI can enforce spatial memory safety at the object level. Attempts to establish a TEE using CHERI primitives su ff er from (1) expensive capability revocation op-erations, (2) need to rely on the host operating system (OS) to support provenance tracking and physical memory protec-tion, (3) expensive domain transitions, and (4) lack of support for remote attestation. We introduce prismatic capabilities and present PRISM , a TEE architecture for CHERI leveraging prismatic capabili-ties to create userspace enclaves while addressing these chal-lenges. PRISM binds enclave ‘hues’ (identifiers) in prismatic capabilities to physical memory access controls, enables O(1) ownership establishment without memory sweeps, and sup-ports e ffi cient domain transitions that atomically activate and deactivate prismatic capabilities. Additionally, PRISM en-ables remote attestation of its enclaves. We demonstrate that execution of userspace enclaves in PRISM incurs only mod-erate overhead ( ≤ 15%), a significant improvement over the same workloads under Intel SGX. 

# 1 Introduction 

Hardware-isolated trusted execution environments (TEEs) 

have become a cornerstone of confidential computing, en-abling applications to protect sensitive code and data even when the host operating system (OS) is compromised or ma-licious. TEEs provide an isolated computing environment within which code and data are inaccessible to the host sys-tem, except when authorized and through well-defined in-terfaces. The use of TEEs in industry [1, 2, 3, 4] and academia [5, 6, 7] is ubiquitous across a broad range of sys-tems. TEEs protect their code and data from direct manipu-lation. However, the Achilles’ heel of TEEs is the threat sur-face exposed by the software within; security lapses in real-world TEEs are predominantly caused by vulnerabilities in the trusted software, such as memory-safety issues [8, 9, 10]. The memory safety of TEE code is typically not enforced by the architecture itself. It can be achieved though memory-safe languages, e.g., Rust, but TEE OSs or their trusted run-time typically rely on low-level C (or C ++ ) components re-purposed from mainstream toolchains. The threat surface is exacerbated by bloated trusted computing bases (TCBs);

# 2 Background 

## 2.1 CHERI 

CHERI is an ISA extension that adds a capability-based hardware-software co-design for memory protection, using hardware-supported capabilities to enforce spatial safety for pointers. The CHERI ISA specification [11] defines how ca-pabilities are represented in registers and memory and the in-structions that manipulate them safely. As shown in Fig. 1, a CHERI capability is twice the width of a native pointer type—128 bits on 64-bit platforms—plus a separate validity-tag bit ➀ held outside the addressable data to prevent tampering by non-capability-aware instruc-tions. Capability-aware instructions preserve this tag, but it is cleared by unauthorized manipulation or attempts to inject ar-bitrary capabilities. CHERI widens the general-purpose and address registers to hold full capabilities, each comprising: 

• Permissions ➁: a bitmask defining allowed operations. 

• Object type ( otype ) ➂: a signed integer enabling tempo-rary “sealing” and “unsealing” of capabilities for opaque pointers and fine-grained in-process isolation.   

> 1We distinguish between hues and colors as, as explained in §4, prismatic capabilities combine both to provide isolation and temporal safety.
> 2With the exception of source-code changes necessary to make the enclave-code conformant to CHERI C /C++ and the recompilation of enclave code (typically targeting 64-bit x86) to our PRISM -enabled CHERI-Toooba target.

• Bounds ➃: The valid memory range relative to the baseline architecture address ➄, using a compressed encoding [16] to reduce the space taken by a capability at the cost of stricter alignment for larger object allocations. Special-purpose registers, e.g. the program counter ( pc ) and stack pointer ( sp ), are replaced with equivalent capability-registers: program counter capability ( pcc ) and stack pointer capability ( csp ). CHERI enforces spatial safety by associat-ing each allocation with a capability describing its valid range and permissions. New capabilities are derived from existing ones, while maintaining monotonicity that ensures that new capabilities cannot exceed the permissions or bounds of their parent. The lineage is traceable to initial boot-time capabil-ities; the default code capability ( ddc ) and pcc . CHERI’s sealing enables compartmentalization, rendering sealed ca-pabilities inert until passed to a cinvoke instruction which jumps to an entry point within a compartment and simultane-ously unseals a data capability, granting access to compart-ment data. Exception handling uses the same mechanism for limited non-monotonicity. Extensions to CHERI have also explored sandboxing [17], initialization safety [18, 19, 20], safe speculation [21, 22], and side-channel resistance [23]. 

Capability relocation. Capabilities cannot be embedded statically in an executable: storing a pointer-sized value as ordinary data lacks a valid tag, and conventional relocation types cannot describe a capability’s base, bounds, and per-missions. The CHERI toolchain emits a capability reloca-tion table ( __cap_relocs ) with one entry per capability to be initialized at program launch, recording the slot to fix up together with the target object’s base, o ff set, and size. The run-time linker—or, for statically linked binaries, equivalent startup code embedded in the C runtime—walks this table and, for each entry, derives a corresponding capability from the appropriate root, sets its tag, and writes it into the corre-sponding pointer slot, so that globals, function pointers, and similar values hold valid capabilities before application code runs. Because every capability originates this way, the mono-tonicity guarantee extends from these roots to all capabilities in the process [24]. 

CHERI temporal-safety enforcement. By design, CHERI avoids indirection such as table-based lookups. Temporal safety therefore relies on a software mechanism that peri-odically sweeps memory and revokes capabilities [25, 26]. 

PICASSO [27] introduces colored capabilities to track alloca-tion provenance and shows that single-bit indirection accel-erates temporal safety in CHERI. Colored capabilities decou-ple the validity of a capability’s provenance (the allocation it represents) from the validity of the capability itself. Each colored capability carries a provenance identifier (provenance ID) encoded in the otype field (referred to as the capability’s 

"color" ). A corresponding provenance-validity bit (PVB) is stored separately in a hardware-managed provenance-validity table (PVT) in process memory, indexed by the provenance ID. Hardware checks the PVB on every load or store issued through a colored capability. Dereferencing colored capabili-ties without a valid PVB bit is prevented. This allows all ca-pabilities sharing provenance to be retracted at once by inval-idating their PVB, disabling dereferencing dangling colored capabilities without permanently revoking them. 22.2 Trusted Execution Environments 

TEEs are a class of hardware extensions that provide a pro-tected runtime isolated from a system’s host environment: code and data in a TEE can only be directly called, read and written to by code in the same TEE. This is enforced on an architectural level, so even privileged software on the system (e.g., host operating system) cannot directly access code /data belonging to a TEE. The nature of the trusted environment varies based on the particular TEE implementation. Many designs of TEEs are available in commercial central processing units (CPUs) [3, 1, 4, 2, 28]. For example, Intel’s SGX [3] enables TEEs in userspace (referred to as enclaves) in Intel processors. ARM TrustZone [1] partitions all system resources (e.g., timers, peripherals, interrupts) between the host and TEE (referred to as the normal and secure world , re-spectively) in ARM Cortex-M and -A processors. Addition-ally, ARM TrustZone enables a set of trusted applications to execute within the bounds of its TEE (atop a small trusted operating system in the Cortex-A variant). Recent commer-cial CPUs have also enabled virtual machines inside a TEE [4, 2, 28], protected from the host virtual machine manager. Academic proposals for TEE design have been prevalent in recent years [7, 29, 30, 31, 32, 5, 33, 34, 35] including those targeting the RISC-V ISA [7, 29, 30, 31, 32]. Among them is Keystone [6], which enables construction of SGX-like TEEs using RISC-V primitives, leveraging the physi-cal memory protection (PMP) mechanism to restrict access to TEE memory. It also establishes a secure monitor run-ning in machine mode to act as a reference monitor that con-trols the PMP configuration at run time. Regardless of their specifics, TEEs guarantee hardware-backed isolation from the host OS. Because of this, TEEs can enable remote attes-tation, a challenge-response protocol in which a prover ( Prv )aims to convince a verifier ( Vrf ) that their software /hardware configuration is valid. Remote attestation requires the prover to have a root of trust on their device that can measure and re-port on the software /hardware components of interest to Vrf .The latter is typically conducted by computing a message au-thentication code (MAC) or digital signature over the compo-nents of interest, thus requiring secure key storage and usage. Due to this requirement, the hardware-backed security prop-erties of TEEs naturally constitutes such a root of trust, and some even build attestation operations directly into the CPU fabric [3, 2, 4]. 

# 3 Problem Statement 

## 3.1 System and Adversary Model 

We consider a Prv system running a host OS to manage the execution of multiple userspace processes, provide inter-process isolation, and perform virtual-to-physical translation. We assume a CPU core with a memory management unit. We also consider a CPU equipped for CHERI, such that the en-tire runtime environment can operate in pure-capability mode 

(i.e., all pointers are turned to capabilities and non-capability memory accesses are prohibited). Prismatic capabilities aim to support establishment of enclaves, housing code and data that is isolated from the most privileged software on the sys-tem. We consider an adversary ( Adv ) in line with related works [6, 7], which we assume can exploit vulnerabilities in the OS to gain control and call an arbitrary sequence of op-erations at its disposal. With this control, Adv can modify memory not explicitly protected to either (1) leak secrets (2) tamper with an enclave’s code /data. We assume CHERI’s spatial-safety properties hold as in-tended. As such, we assume permissions and bounds can only be decreased through the creation of a new (equal- or less-privileged) capability (cf. CHERI monotonicity in §2.1). An enclave may divulge prismatic capabilities pointing to enclave memory to untrusted software. In § 4 we explain how CPU hardware ensures such capabilities remain opaque to untrusted software and other enclaves. However, we as-sume enclave software to be responsible for validating that any prismatic capabilities it receives from untrusted software are pointing to valid and correct objects within the enclave. This assumption is consistent with TEEs which must vali-date any untrusted input from outside their trust boundary before the input is used in sensitive operations. Hardware attacks that require physical access to circumvent hardware protections (e.g., hardware-protected code /data) are out-of-scope for this work, as they require a set of mitigations that are orthogonal to the focus of this work [36, 37, 38, 39]. Con-sistent with prior TEE work [3, 13, 12, 7], availability is out of scope: since Adv controls the OS, it can trivially deny service by refusing to schedule the host process. Regarding remote attestation, we also assume Adv may discard, inject, or modify network messages [40]. We exclude microarchi-tectural side-channels from our adversary model, but discuss this threat surface in-detail in Appendix 8. 

## 3.2 Design Goals and Challenges 

Prior work [13, 12, 27] has extended traditional usage of CHERI capabilities beyond spatial safety. However, the fol-lowing challenges must be addressed to enable an e ffi cient capability-based TEE design: 1. obtaining exclusive ownership of capabilities belonging to the TEE without performing expensive look-up operations (e.g., memory sweeps or tree-traversal); 2. enabling privilege separation for management of metadata used to track provenance of TEE; 3. enabling exclusive access with an untrusted host OS, as capabilities are specified on virtual addresses and enclave protection needs to apply to physical addresses; 4. enabling e ffi cient domain transitions, such that enter and exit from enclave does not require performing an expen-sive context-switch routine to disable an enclave’s capa-bilities; 5. enabling external verifiers to assess whether a particular enclave was created using the expected code /data and ex-ecutes on the anticipated system. To address these challenges, a capability-based TEE architec-ture must have the following properties: 

[P1] Exclusive Ownership Management : assigning and re-voking exclusive ownership of an enclave’s capabilities must not require expensive search operations, and meta-data for provenance tracking must be inaccessible to un-trusted software. [P1] ensures enclave isolation from its untrusted host userspace process. 3[P2] Physical Memory Exclusivity : enclave capabilities must be bound to physical access control measures, in addition to out-of-the-box spatial safety on virtual ad-dresses. [P2] ensures enclave isolation from the un-trusted host OS. 

[P3] Safe Domain Transitions : entering and exiting an en-clave (calls /returns or interrupts by the untrusted OS) must not enable tampering with enclave state. 

[P4] Spatial and Temporal Safety : full spatial and temporal safety across both enclave and non-enclave execution. 

[P5] Secure Measurement and Attestation : enclave code and data is cryptographically measured upon creation, with measurements stored in TCB memory; attestation reports bind the enclave to both the installed TCB and device. 

# 4 Prismatic Capabilities Design 

Prismatic capabilities extend CHERI capabilities with a hue-based 3isolation mechanism that enforces exclusive access to physical memory regions. The name draws on the analogy of an optical prism separating white light into distinct spectral components: a single address space is partitioned into iso-lated protection domains, each identified by a distinct hue and accessible only through capabilities bearing the same hue. Prismatic data capabilities additionally carry a color for tem-poral safety protection of dynamically allocated memory re-gions within a hue (enclave instance). Fig. 2 shows the com-ponents of a prismatic capability system and depicts the en-clave life cycle. A prismatic capability carries a hue attribute (encoded in the capability’s object type field) assigned by a machine-mode TCB at enclave creation time. Each prismatic capa-bility belonging to a particular enclave instance carries the same hue. At each memory access, CPU hardware compares the capability’s hue against entries in a hardware-managed 

Hue-Addressed Memory (HAM) table. The HAM associates contiguous physical memory regions with the enclave’s hue identifiers. The check applies to both instruction fetch and data load /store (keyed on the authorizing capability); addi-tionally, for data loads /stores, a check on the validity of the color’s provenance is performed. The memory access suc-ceeds if 1) the access’s physical address, after translation, resides within the enclave’s physical region, 2) the hue and color of the capability authorizing the access matches that registered for the target region, and 3) the access is other-wise valid according to the bounds, permissions, and other invariants enforced by CHERI. Crucially, prismatic capabili-ties are usable only from within the enclave with the same hue 

[P1] . Additionally, even if stale or forged (non-hue) capabili-ties reference the same physical addresses, they cannot access a hue-locked region [P2] . Together, [P1] and [P2] provide isolation without page-table isolation or software-mediated domain crossings. CHERI’s monotonicity property ensures any capability de-rived from a prismatic capability shares the original capabil-ity’s hue, but capabilities of an arbitrary hue cannot be forged.

## 4.1 System Components 

As shown in Fig. 2, the system is comprised of hardware com-ponents, software modules, and data structures. Among the software modules are the following: 

• OS: the system’s full feature-rich host OS. The OS is as-sumed to be compromised and acting maliciously. 

• App : a host application, which requests the creation of an enclave within its own address space. 

• Enclave : a subsection of the App’s address space used for operations isolated from the rest of the system. 

• Hue Management Monitor (HMM) : a security monitor that operates at machine mode level, and is responsible for crucial aspects of an enclave’s life cycle. We assume there are just two main hardware components: 

• PRISM CPU : the CPU core which is capable of enforcing standard CHERI spatial memory safety, augmented with support for prismatic capabilities. 

• HAM : PRISM ’s hardware mechanism for enforcing phys-ical memory isolation for enclaves (full details in Sec-tion 5.1). It is a sub-component of the PRISM CPU. Finally, the HMM maintains one critical data structure called the hue table , which maintains a mapping of enclave hues and the measurement of the code and data upon creation. 

## 4.2 Life-cycle 

We describe the enclave life cycle stages: creation, execution (invocation, return, preemption), attestation, and destruction: 

Enclave Creation. In 1 , the host application creates an enclave by calling the OS and passing the enclave binary (e.g., encl.so in Fig. 2). In 2 , the OS allocates a contiguous physical region and invokes the HMM (via a privileged call) in 3 . In 4 the HMM assigns a unique hue to the enclave in-stance (e.g., 1 in the example depicted in Fig. 2), measures the memory contents by computing a cryptographic hash over the enclave’s code and data, and records the hue-to-measurement binding in hue table in HMM-private storage. Fig. 2 shows a mapping between the hue 1 and h(encl.so) in the hue table. In 5 , HMM updates the HAM to associate the hue with the physical region (further details in Section 5.1). Then, it locks the memory against all memory accesses except for ac-cesses through prismatic capabilities with the associated hue. Finally, the HMM seals a code capability and a data capa-bility (e.g., EPCC and EDCC in Fig. 2) with the assigned hue, and returns them to the host application in 6 . After creation, the sealed capabilities are the only means to enter the en-clave. Hue accesses are confined: a capability carrying a TEE hue may only access memory explicitly assigned to that hue; the host OS cannot redirect the enclave to attacker-controlled memory by manipulating page tables. 

Enclave Execution. The enclave is invoked in 7 by the host application. It enters the enclave via a single unprivi-leged hardware instruction (described further in Section 5). Upon the execution of this instruction, the HAM validates that both code and data capabilities carry matching hue, acti-vates the corresponding hue entry, installs the code capability, and transfers control to the enclave entry point. A return sen-try is saved for later use by the enclave to return to the caller. As a result of this design, no trap to the HMM occurs; in-vocation is entirely a hardware operation. From this point, in-4Figure 2: Overview of prismatic capabilities : hardware /software components and the enclave life cycle. struction fetches and data accesses succeed because the code and data capabilities carry matching hue. Any code whose capabilities carry a di ff erent hue is denied by the HAM. Interrupts may fire during enclave execution. The HMM preempts the enclave by saving its register state into enclave memory (inaccessible to the OS), deactivates the HAM en-try to re-lock the enclave’s memory, scrubs the trap frame, and redirects execution to OS interrupt handler. The OS pro-cesses the interrupt, unaware that an enclave was executing. To resume, the host simply re-invokes the enclave; entry logic detects the saved state and the HMM restores execution from the interrupted point. Synchronous faults (such as CHERI exceptions) are handled similarly, except they terminate the enclave execution rather than saving resumable state. In 8 , the enclave exits via a single unprivileged instruction that atomically deactivates the hue (re-locking the enclave’s memory) and returns control to the caller. The HAM entry remains valid, so the enclave can be re-entered at a later time. 

Attestation . The host application responds to remote at-testation requests by calling the OS to transfer control to the HMM for report generation in 9 . The HMM constructs a re-port, containing measurements of the enclave code, the hue, an attestation challenge, and measurement of the HMM code. This report is then signed using the device signing key, bind-ing the measurements of the enclave and HMM at the time of the attestation request to the particular device. The remote attestation protocol is discussed in more details in §5.6. 

Destruction. In 10 , the host application can permanently destroy an enclave, by making such a request to the OS, which in return forwards the request to the HMM via a privileged call. The HMM invalidates the hue in the HAM, retires the hue, then clears and releases the physical memory in 11 . Pris-matic capabilities become unusable when the hue is retired: their hue no longer corresponds to a HAM entry, so subse-quent invocation attempts fault. Retired hues can later be re-claimed by the HMM by performing a system-wide sweep to revoke stale prismatic capabilities held by untrusted software. This hue-revocation is independent of the enclave life cycle. 

## 4.3 Enclave temporal safety 

While enclave spatial safety follows from the baseline CHERI design (§ 3.1), we adapt colored-capability-based temporal-safety enforcement ([P4] ) from PICASSO [27] (§ 2.1). Our adversary model precludes storing provenance-validity data in a host-controlled PVT . Instead, each enclave contains an enclave provenance-validity table (EPVT) . Pris-matic capabilities reserve a portion of CHERI’s otype as hues. The remaining otype s are treated as PICASSO colors. The EPVT contains 1-bit PVB entries indexed by the color (i.e., provenance ID). On allocation, a trusted memory al-locator within the enclave assigns a unique color to pris-matic capabilities and marks the corresponding PVB in the EPVT valid . On free, the allocator marks the correspond-ing PVB invalid . All loads or stores with a color are subject to an additional hardware check against the EPVT in paral-lel to hue checks. Once a color has been invalidated, the CPU ensures that all capabilities with that color cannot be dereferenced, preventing use-after-free (UAF) and use-after-reallocation (UAR) conditions within the enclave. The re-vocation sweep which invalidates stale heap capabilities and reclaims colors (performed by a separate kernel thread in PI-CASSO ) is performed by the trusted runtime inside the en-clave. Unlike CHERI revocation sweeps, enforcing temporal safety within enclave instances only requires sweeping the particular enclave memory. According to our system and ad-versary model (§3.1), enclave code is responsible for validat-ing any capability divulged to, and later received back from untrusted code. Since temporal-safety enforcement does not extend to capabilities that have left the enclave boundary (due to our adversary model § 3.1), enclave software must ensure potentially stale capabilities originating from outside the en-clave are not used. 

# 5 Implementation Details 

In this section, we present PRISM , our implementation of pris-matic capabilities for the CHERI-RISC-V architecture. We implemented two versions of PRISM : 1) a QEMU-system-CHERI128 full-system emulator, and 2) a softcore based on the CHERI-Toooba processor intellectual property (IP) (§ 5.1). ## 5.1 PRISM CHERI-RISC-V Implementation 

Hue-Addressed Memory. The HAM is the hardware mech-anism that enforces enclave physical memory isolation. It is a 64-entry fully-associative table positioned between the memory management unit (MMU) and the memory subsys-tem. On every memory access (instruction fetch or data load-

/store), after the MMU produces a physical address, the HAM checks whether the capability used for the access falls within a protected region and, if so, whether it carries the correct hue. Where the MMU enforces virtual-to-physical translation and page-level permissions, the HAM enforces domain sepa-ration: it determines whether the code currently executing has the right to access a particular physical address range, based on the hue carried by the capability being used for the access. HAM entries use naturally aligned power-of-two (NAPOT) encoding, storing a base page number and a size exponent rather than explicit base and top addresses. This replaces two magnitude comparators with a single masked equality check. Each entry totals 66 bits:

Because the check hap-pens after address translation, a malicious kernel cannot use the page tables to redirect an enclave’s fetches or data ac-cesses to physical memory of another hue ( [P2] , § 3.2). Each entry additionally holds the temporal-safety metadata needed to verify the color, as de-scribed in §5.5, the enclave-virtual base address of its EPVT bitmap and the number of validity slots it covers. The HAM is core-local (similar to RISC-V’s PMP). In a multi-core con-figuration the HMM must program the corresponding entry on every core. In this work, we limit PRISM to a single core.

Hue, color and otype encoding. The layout of a prismatic capability is shown in Fig. 3. Compared to the CHERI capa-bility layout in Fig. 1, a prismatic capability subdivides the 

otype into two sub-ranges reserved for enclave use. The re-served sub-range of the otype space is defined via TEE_-OTYPE_BASE . All otype s values defined below this are either colors or CHERI reserved types, whereas otype s at or above it encode enclave instance identity in 3b and its EPVT meta-data in 3a . Specifically, each prismatic capability otype is defined as otype = (hue ≪ pvt_shift ) | color , where: 

• hue is an id_width -bit enclave instance identifier that se-lects the HAM entry and hue table row; 

• color is the remaining low-bit index into its EPVT; 

• pvt_shift splits the 21 otype bits between hue and 

color bits (e.g., pvt_shift = 21 - id_width ). The value of pvt_shift is determined at run time from a machine-mode control and status register (CSR). Making this split software-configurable preserves backward compatibility across di ff erent enclave-ID allocations without modifying the hardware datapath. The default 6-bit id_width admits up to 63 concurrent enclaves (hue ∈ [1 , 63]) and a 15-bit color per enclave instance. This split can be retuned without data-path changes. The four reserved CHERI otype s fall outside 

TEE_OTYPE_BASE and are exempt from the HAM check; the HAM gates only capabilities whose otype lies in the enclave range. 

Machine-mode monopoly on hue assignment. The hue is an unforgeable, M-mode-rooted credential that untrusted code may hold and pass but never conceive. The PRISM hard-ware restricts creation of enclave-range otype s to M-mode: any attempt by S- or U-mode software to seal a capability with a hue it does not already hold is rejected. Untrusted soft-ware thus cannot forge an enclave’s hue or mint a new one to alias it. The only source of valid enclave-owned prismatic 6capabilities is the HMM’s creation routine. 

## 5.2 Hue Management Monitor 

The HMM is a minimal M-mode security monitor. It is the only software component that can program HAM entries, ac-cess enclave memory (via M-mode exemption), and manage hue and otype encoding. 

Boot . The boot process atop PRISM occurs in two stages. The HMM is the first code to execute at reset. It (1) configures the HAM so that supervisor-mode software cannot access the HMM’s text region, (2) reserves one hue for its own exclu-sive use, and (3) initializes the hue table and M-mode CSR defining pvt_shift . In the second stage, the HMM loads the CheriBSD kernel and transfers control to its entry point in supervisor mode. Because isolation between HMM and OS is configured in the first stage, the HAM blocks OS ac-cess to HMM memory. The OS therefore serves TEE-related requests from the application through /dev/tee device node (discussed further in §5.3). 

Creation. On an enclave creation request, the HMM: (1) as-signs a hue from a bitmap allocator, (2) measures the enclave code and static data pages in place by computing SHA-256 over their contents (using relative virtual addresses so o ffl ine verification is independent of load address), (3) programs the HAM entry (with valid=1, active=0 ), and (4) seals code and data capabilities with the assigned hue. The sealed capa-bilities are returned to the kernel via a shared bu ff er. The HMM also processes __cap_relocs on behalf of the en-clave, deriving a corresponding capability for each entry: 

• function entries receive enclave-wide bounds (so that pcc -relative addressing remains valid from any function) and execute permission, derived from M-mode pcc ;

• data entries receive per-object bounds derived from M-mode default data capability ( ddc ), with constant entries further restricted to read-only. Each resulting capability is associated with the enclave’s hue and written into enclave memory where indicated by the cor-responding __cap_relocs entry. This ensures indirect refer-ences in the enclave use a valid prismatic capability carrying the enclave’s hue. 

Trusted interrupt handler. Timer interrupts arrive asyn-chronously and, because the untrusted OS services them, pose a confidentiality hazard: a preempted enclave’s register file must never be visible to the kernel, yet the kernel must still schedule and enforce fairness. PRISM reconciles these re-quirements by interposing the HMM on the interrupt path. When a timer fires during enclave execution, the HMM (1) takes the trap in M-mode, (2) saves the enclave’s architectural state into a per-enclave state save area (SSA) in the enclave’s own hue-protected data region, (3) scrubs the general-purpose registers, and (4) converts the machine timer interrupt into a supervisor timer interrupt that the kernel handles through its ordinary path. Execution resumes transparently on the next enclave entry. The SSA is laid out as follows:             

> Off set Field Size
> 0x000 resume_ marker 8 bytes 0x010 saved_pcc 16 bytes (capability) 0x020 user_ret 16 bytes (capability) 0x030 regs[0..31] 32 ×16 bytes

Non-preemptible transition windows. Saving the enclave’s architectural state is only correct when the interrupted pro-gram counter lies in enclave instructions, where all state is live in registers and the SSA is not being modified. This in-variant breaks while the enclave is inside its own entry /exit trampoline: these sequences write the SSA themselves, so saving the state mid-sequence could corrupt it or overwrite re-sume context that an OCALL is still consuming. We therefore treat this short, statically known entry /exit sequence as non-preemptible . The HMM sets a conservative boundary above it and, on a timer trap, compares the faulting pcc against this boundary, declining to enter the respective trampoline again and returns via mret . Since the sequence is short and non-looping, the pending tick is delivered cleanly through the ker-nel’s normal path on the next cycle. 

Idempotent resume. On re-entry via EInvoke the tram-poline inspects SSA.resume_marker : if unset, the trampo-line takes the first-entry path that establishes the stack and calls directly into enclave; if set, SSA.resume_marker de-notes a pending interrupt resume which PRISM handles in M-mode. The trampoline executes a single reserved instruction that traps directly into the HMM. The HMM reloads general-purpose registers from the SSA, sets mepcc CSR to saved_-pcc , and returns with mret to the enclave. Since this resume instruction sits in the non-preemptible prefix, a timer arriving just before it retires is declined and simply re-executes on the next entry, so interrupt /resume do not expose partial state. 

Trusted fault handler. A synchronous fault inside an ac-tive enclave—a HAM /temporal-safety denial or any CHERI violation—raises the same hazard as an interrupt: it occurs with the hue live and enclave data in registers, yet must be reported to untrusted software. PRISM does not delegate the enclave-relevant fault causes (the CHERI exception and the HAM’s load /store access faults) to supervisor mode, so they trap to the HMM. If the faulting pcc carries a hue, the HMM invalidates the HAM entry, scrubs the registers, and redirects to the host’s return sentry with a distinguished status—as on the interrupt path, but without saving resumable state, since a fault is fatal. The host sees a defined exit, not a register leak or crash. Faults from non-enclave code carry a non-prismatic capability pcc and are passed unchanged to the kernel. 

Report Generation. The HMM constructs and signs a RE-PORT data structure when a host application issues the TEE_-IOCTL_GEN_ATT ioctl (which drives the SBI_ENCLAVE_-GEN_ATT call, Table 1). The REPORT data structure has the fields:       

> Field Size
> chal __HASH_SIZE__ hue 8 bytes
> encl_measurement __HASH_SIZE__ hmm_measurement __HASH_SIZE__ signature __SIG_SIZE__

The host application obtains chal , the remote attestation challenge, over the network and passes it to the HMM call along with hue , the hue of the enclave being reported on. The remaining fields come from HMM private memory: encl_-measurement is read from the hue table entry for that hue, 

hmm_measurement is a static measurement of the HMM’s own initial state, and signature is the digital signature com-puted over the other four fields. hue is 8 bytes; while the re-7maining fields are sized according to the hash function and digital signature algorithm installed in the HMM. Our proto-type uses SHA256 and ED25519, so __HASH_SIZE__ is 32 bytes while __SIG_SIZE__ is 64 bytes. The HMM uses hash and signature algorithms from the formally verified HACL ∗

library [41]. 

Destruction. On a destroy request for a given hue, the HMM decodes and validates the enclave id from its hue, then zeros the enclave’s physical pages (data region, EPVT, and stack), along with the SSA, so that no later occupant of the same pages or hue can observe stale data or resume context. Only after scrubbing does the HMM invalidates the HAM entry, restoring the supervisor mode access and letting the kernel reclaim the pages. Since the scrub runs under the HMM’s M-mode HAM exemption, the enclave pages are never exposed to supervisor mode in an unclean state. Finally, it retires the hue, preventing its reuse until a full-memory sweep by the HMM (§8) revokes any prismatic capabilities which have es-caped the enclave memory. 

## 5.3 CheriBSD Support 

We implement a /dev/tee device in CheriBSD whose 

ioctl s cover the enclave lifecycle: creation, destruction, and attestation-report generation (see Table 1). The kernel’s role is minimal: allocate memory, invoke the HMM, and relay prismatic capabilities between the HMM and userspace. The kernel is explicitly untrusted: it can neither access enclave memory nor forge prismatic capabilities. 

Memory allocation & code transfer. Because a single HAM entry covers one naturally-aligned power-of-two region (§ 5.1), the kernel backs each enclave with exactly such a re-gion. Enclave creation begins with a single TEE_IOCTL_-CREATE request, carrying a caller-supplied struct that con-tains: (1) the entry virtual address and size; (2) the reloca-tion metadata the HMM requires; (3) the EPVT size. After validating that the region size is page-aligned and within the maximum size limit (e.g., 64 MB in our prototype), the ker-nel allocates physically contiguous pages with power-of-two size and natural alignment. For an enclave requesting n pages it allocates 2 ⌈log 2 n⌉ pages (at most a 2 × overhead). Any extra pages are zeroed and protected by the same HAM entry. The kernel also stages the enclave image: it wires the en-clave’s source pages, copies their contents through the ker-nel’s direct-mapped window, and rewrites the page-table en-tries at the enclave’s existing virtual addresses with the wired mappings. This leaves the virtual address unchanged while its physical backing becomes the region the HMM will isolate. Because staging precedes isolation, the region remains ordi-nary userspace memory until the HMM activates the HAM entry during the creation call (§ 5.2), after which the HAM denies access lacking the correct hue. 

The cap_buff protocol. The kernel communicates with the HMM through a fixed-layout shared bu ff er ( cap_buffer ), passed in via an Supervisor Binary Interface (SBI) call. The kernel fills the bu ff er’s input region with each enclave page’s physical address and relocation metadata HMM needs to seal the capability table (the __cap_relocs off set and size, the ELF text virtual address, and the static section size). ## 5.4 Supporting Unmodified SGX Applications 

To support unmodified SGX applications, we provide an SGX-compatibility library that operates over the standard SGX application file structure, as is depicted in Figure 4. The resulting host /enclave interface is small (Table 1): the whole enclave life cycle is two /dev/tee ioctl s plus close , and enclave entry and exit are unprivileged hardware instructions that never trap to the HMM. Intel SGX applications contain two source directories: 

• App : contains the host-side application, which creates and invokes an enclave. 

• Enclave : contains the enclave code itself and an Enclave Definition Language (EDL) file declaring the functions comprising the host-enclave interface. The EDL file declares a set of ECALLs and OCALLs, each annotated with a parameter direction (e.g., [in] , [out] ,or [in-out] ) and parameter semantics (e.g., [string] for string variables or [count=N] for expected bu ff er sizes). We first parse the EDL to identify the ECALL and OCALL functions, signatures, and shared data structs, producing four output files: Enclave_u.h , Enclave_u.c/cpp , Enclave_-

8t.h , Enclave_t.c/cpp . These files implement the un-trusted (_u ) and trusted (_t ) marshaling layers . Each layer defines identical per-ECALL structs describing the packed ar-gument layout, ensuring the host and enclave agree on the data representation across the trust boundary. The untrusted layer implements ECALL wrapper functions and an OCALL dispatcher. The trusted layer implements OCALL stubs and an ECALL dispatcher that reads the ECALL ID, allocates input bu ff ers, and invokes the target function. On return, it copies results back before freeing the temporary bu ff ers. At build time, the marshaling layers are combined with our untrusted and trusted runtime systems (URTS and TRTS). The TRTS is linked directly into the enclave source code and supplies (1) an ECALL trampoline for handling ECALL en-try, OCALL exit, and interrupt resumption; (2) a freestanding bounded heap allocator–adapted from dlmalloc; (3) a linker script; and (4) a freestanding C /math /C++ runtime—objects extracted from CheriBSD kernel. The URTS is linked into the host application and implements enclave management (cre-ation /destruction), the ECALL /OCALL dispatch loop, and an assembly wrapper around EInvoke for entry /re-entry. The TRTS’s allocator additionally enforces temporal-safety, asso-ciating each allocation with a fresh color and triggering a re-vocation sweep on color exhaustion (§5.5). 

Outside calls (OCALLs). An OCALL reaches a host-side service (file I /O, network access, or memory allocation be-yond the enclave’s static heap) without involving the HMM: the enclave exits and re-enters through the normal invoca-tion path. The enclave writes the OCALL request to a shared host-side memory bu ff er. It then saves its callee-saved registers and return address into a dedicated OCALL slot within the SSA (§ 5.2, disjoint from the interrupt save area), writes an OCALL-resume marker value, and executes 

EExit . The URTS detects the OCALL via a distinguished return value, dispatches the requested function, writes the re-sult back into the shared bu ff er, and re-invokes the enclave via 

EInvoke . On re-entry the trampoline detects the OCALL-resume marker value, restores the saved registers, and returns control after the OCALL call site, as if the host function had returned normally. The SSA preserves continuity across this boundary, and the HAM keeps enclave memory locked while host code executes. The shared bu ff er is an untrusted commu-nication channel; the enclave must validate all data returned through it. 

## 5.5 Spatial and Temporal Safety inside TEE 

CHERI provides spatial safety via its default pure capability mode. Temporal safety uses the EPVT (§4): a one-PVB-per-slot bitmap at the top of the enclave’s hue-protected region, unreachable from outside. Each tracked allocation carries a 

color , and each HAM entry holds the metadata to locate the EPVT. At creation, the HMM reserves a fixed 4KB EPVT at the top of the enclave’s hue-protected region. 

Allocation and enforcement. The trusted allocator assigns a color for every allocation; free marks the slot invalid. Since slots are never reused while fresh colors remain, a dan-gling capability can never match a later allocation, and use-after-frees fault immediately. Since validity bits are cached, revoking a slot is followed by a fence for the hardware check to observe it.

Although enclave creation has a per-page operation cost (for hashing code and data to obtain the enclave’s attesta-tion measurement), its cost is dominated by the dlopen of the enclave shared object and the contiguous allocation operation whose cost depends on total DRAM size rather than alloca-tion size. Enclave destruction is dominated by the teardown of enclave page table entries, which scales with page count. 

## 6.3 Security Analysis 

To answer RQ4 , we revisit PRISM ’s desired security proper-ties of from Section 3.2, and argue our design and implemen-tation upholds them. 

[P1] Exclusive Ownership Management. Since Adv con-trols the OS and can invoke arbitrary S-/U-mode operations, hue ownership must be unforgeable from that privilege level. 

PRISM restricts creation of enclave-range otype values to M-mode: any S- or U-mode attempt to access a capability with a hue it does not already hold is rejected, so only the HMM’s creation routine can produce a valid enclave-owned prismatic capability. Combined with CHERI’s monotonicity guarantee: new capabilities can only be narrowed via derivation from a valid capability, Adv cannot synthesize, upgrade, or alias a capability carrying an existing enclave’s hue. Adv may hold and relay prismatic capabilities opaquely (e.g., as a part of SGX-compatibility marshaling), but cannot mint, retype, or widen them. Hue ownership therefore remains rooted exclu-sively in the M-mode HMM, regardless Adv ’s OS-level priv-ileges. 

[P2] Physical Memory Exclusivity . Adv may modify page tables and other OS-managed structures at will, so iso-lation cannot depend on honest virtual-to-physical transla-tion. PRISM ’s HAM checks ownership on the post-translation physical address, authorizing the access by the used capabil-ity’s hue and denying any access whose HAM entry is inac-tive or whose hue mismatches. Since this check occurs post-translation, Adv can neither redirect an enclave’s accesses to attacker-controlled memory through page-table manipula-tion nor remap pages into an active enclave’s protected range. Only M-mode is exempt; it is used solely by the HMM to manage enclave memory during its life cycle. Since Adv 

cannot execute in M-mode, this exemption grants no ability to bypass the checks. 

[P3] Safe Domain Transitions . Since Adv controls OS scheduling and interrupts, domain transitions must not leak enclave state or execute under the wrong hue. Entry and exit via EInvoke /EExit are unprivileged and trap-free, with HAM activation tied to the instruction commit; on out-of-order cores, PRISM suppresses speculative redirects so no in-struction runs under the enclave’s hue before it is active. On 11 exit, the TRTS scrubs general-purpose and capability regis-ters, so no enclave secret in them is exposed to untrusted code. On preemption, the HMM checkpoints the state into the HAM-protected SSA and scrubs those registers before forwarding to the OS. Since the SSA is only reachable via M-mode or a matching hue, Adv learns nothing beyond an ordi-nary timer interrupt. A non-preemptible trampoline boundary and idempotent M-mode resume prevent interrupt racing the enclave entry /exit from capturing inconsistent state. 

[P4] Spatial and Temporal Safety. Spatial safety follows from CHERI’s guarantee that every access is mediated by an unforgeable, narrowing capability, preventing accesses out-side an object’s embedded bounds. Temporal safety comes from the EPVT: each capability to the enclave’s heap car-ries a unique identifier, which are retracted in the EPVT upon 

free , resulting in e ffi cient detection of use-after-frees. Since the EPVT shares the enclave’s HAM entry, Adv cannot alter it. Retraction and full capability revocation runs within the TRTS, without involving untrusted code. 

In-enclave use-after-free detection. We validate temporal memory safety using the heap use-after-free (CWE-416) test cases from the NIST Juliet suite [49], executed unmodified inside a PRISM enclave. All CWE-416 test cases (both C and C++ variants) are compiled into a single enclave. The un-trusted host invokes each vulnerable ( bad ) and benign ( good )function through the standard SGX ECALL interface and records the outcome. PRISM detected all 392 vulnerable cases and produced no false positives across the 392 benign cases. We discover a spatial memory safety violation in the Cryp-toEnclave application, which is further discussed in §8. 

[P5] Secure Measurement and Attestation . We vali-date [P5] by formally modeling the protocol in Fig. 5 (§ 5.6) using Tamarin Prover [50], a symbolic protocol verification tool. Protocol steps and Adv abilities are modeled as a multiset of rules , each rule having its own set of precondi-tions and postconditions ( facts ). Security properties are spec-ified as lemmas . Given the set of rules and lemmas, the Tamarin Prover symbolically evaluates rules in arbitrary or-der, to determine whether all lemmas are upheld (further de-tails in [51]). We prove the following security sub-properties for PRISM ’s attestation protocol, which together support [P5] :1. Report Authenticity : all reports obtained by Vrf only pass verification if signed using Prv ’s secret key; 2. HMM Integrity : the HMM code reported by Prv matches the expected value by Vrf ;3. Enclave Integrity : the pages loaded into an enclave with a particular hue match the expected value by Vrf ;4. Key Secrecy : report data sent by Prv does not allow Adv 

to learn secret key used to sign it; 5. Freshness : Vrf only accepts reports produced with a chal 

sent as a part of their request. Each property maps to a lemma verified by Tamarin. Full specification of our rule-based model of PRISM -based pro-tocol and lemmas specifying these security properties are in Appendix B. All lemmas run in ≈0.45 seconds with ≈168 MiB peak memory usage. This uniformity reflects the shared underly-ing model (e.g., the protocol outlined in Fig. 5), and the di ff er-ence in the proof steps arises from how early pruning occurs. All lemmas except for Key Secrecy require complete explo-ration of the model trace. In contrast, Key Secrecy is com-pleted after two steps since it is resolved by direct absence of attacker knowledge derivations, which is determinable with-out complete protocol exploration. 

# 7 Related Work 

To our knowledge, PRISM is the first capability-based TEE to combine hardware-enforced enclave isolation, in-enclave spatial and temporal safety, and remote attestation under an untrusted paging OS, while running unmodified SGX appli-cations on a real RTL implementation. Prior work achieves only subsets of these: software techniques harden TEE code without architectural enforcement; CHERI extensions add memory safety but no enclave isolation; RISC-V TEEs iso-late enclaves but leave their code’s memory safety to soft-ware; and earlier capability-based TEEs forgo virtual mem-ory, attestation, or a hardware realization. 

Memory Safety for TEEs. Prior work has also targeted memory safety within enclaves. SGXBounds [52] extends LLVM to encode bounds into pointers and instrument ac-cesses with bounds check. MPTEE [53] uses Intel Mem-ory Protection Extension (MPX) with a cross-over memory layout to enable bounds checking across permission regions. RustTEE [54] and Rust-SGX [55] lean on Rust’s memory-safety guarantees. The former provides a Rust compiler for ARM TrustZone, the latter a Rust layer over the Intel SGX SDK, with the Rust-to-C foreign function interface (FFI) formally modeled for safety. Unlike these compiler- and language-based approaches, PRISM enforces both spatial and temporal safety architecturally. 

CHERI extensions . A growing body of work extends CHERI’s baseline capability model to address security chal-lenges beyond spatial safety. Cornucopia [25, 26] integrates a malloc revocation shim into CheriBSD for heap temporal safety, quarantining freed memory and sweeping only when the quarantined reaches a threshold size. PICASSO [27] adds colored capabilities for provenance tracking, enabling more e ffi cient use-after-free protection via bulk retraction. BLACKOUT [23] adds blinded capabilities for added side-channel protection via taint tracking. CapChecker [56] ex-tends the capability model to hardware accelerators, medi-ating their memory interface as if they issued native ca-pabilities. CHERI-SIMT [57] adapts capability protections to GPUs via a capability-metadata register file that exploits redundant metadata across hardware threads to cut storage overhead. CHERI-Crypt [58] adds an encryption engine to a CHERI-RISC-V32 processor for transparent memory en-cryption of sealed capabilities against physical attacks, intro-ducing instruction variants that carry an encryption-required bit. 

RISC-V TEEs. SANCTUM [7] proposes an SGX-like de-sign in which enclaves occupy fixed physical memory ranges, using a dual page-table lookup to keep enclave and OS page tables from referencing each other’s memory. Keystone [6] isolates enclaves using PMP, with an M-mode security mon-itor that creates isolated enclave regions. Timber-V [29] targets embedded systems, using two-bit tagged memory to separate normal and trusted domains with MPU assistance. # 8 Discussion and Future Work 

Hue revocation. Because a hue is encoded in a fixed-width subfield of the otype (§ 5.1), the hue namespace is finite: the default 6-bit id_width allows 63 concurrent enclave in-stances. Retiring a hue at destruction renders the correspond-ing prismatic capabilities unusable, but does not immediately make the hue re-assignable: stale capabilities bearing that hue may still be held by untrusted software, and re-issuing the hue to a new enclave would let those capabilities alias the new instance’s HAM entry. The HMM therefore quaran-tines retired hues and reclaims them in batches. Only once the number of available hues falls below a pre-defined thresh-old does the HMM perform a system-wide sweep, walking all tagged memory—and all register state that may hold capabil-ities—and clearing the tag of every capability whose otype 

encodes a quarantined hue; the reclaimed hues are then re-turned to the hue allocator. Because the sweep is gated on hue pressure rather than on individual enclave destructions, its cost is amortized across many enclave lifetimes and is fully decoupled from the enclave life cycle: destruction it-self remains constant-cost, and no enclave operation blocks on a memory scan. The sweep is also independent of the per-enclave EPVT revocation sweep of §5.5, which is confined to a single enclave’s memory and runs in its trusted runtime. A naïve single-pass sweep is not sound while untrusted software runs concurrently: the host application or OS holds stale prismatic capabilities it may freely copy, so it can read one from a not-yet-swept location and store it into a loca-tion the sweep has already passed, surviving the sweep and aliasing a future enclave that receives the recycled hue. Note this is purely a hue-reuse hazard—a retired hue has no active HAM entry, so the capability cannot be dereferenced. In our current PRISM prototype, the HMM shares a single hart (RISC-V hardware thread) with the host OS, and thus performs the sweep with S-/U-mode execution halted. This approach is trivially sound but requires a pause proportional to physical memory size. We deem this an acceptable limita-tion for the prototype, given that availability is already out of scope §3.1 and the sweep is rare by construction, but it makes worst-case latency visible to non-enclave workloads. We expect multi-core PRISM processors to reduce the latency of the system-wide revocation by parallelizing the sweep, similarly to how Cornucopia Reloaded’s [26] temporal-safety revocation sweep runs in a kernel thread to parallelize its execution relative to userspace code. In PRISM ,the HMM runs in parallel on a hart dedicated for the sweep, while the host OS is scheduled onto another. This configura-tion requires a solution for the above hue-reuse hazard, and we leave evaluating the tradeo ff s between the following ap-proaches to future work: 1. Prismatic capability store barrier. Add an glsm-mode-writable retired-hue mask (a 63-bit CSR, or a retiring bit per HAM entry). On every capability store from U-/S-mode, compare the stored capability’s hue against the mask and clear the tag on a match. This closes the hazard directly: a retired capability can never be written anywhere, so sweep order is irrelevant and no register filtering is needed. The check is a masked lookup on the hue field, parallel to the existing HAM hue check. 2. Prismatic capability load barrier. Apply the same mask check on capability loads , clearing the tag in the destination register. Since the only way to move a ca-pability between memory locations is to load it into a register and store it back, a load barrier likewise makes the sweep single-pass and order-independent, and addi-tionally prevents stale capabilities from re-entering the register file at all. It requires one extra step: capabilities already resident in registers when the sweep begins must be filtered, e.g. the HMM sends a inter-processor inter-rupt (IPI) to each hart and scrubs retired-hue capabilities from its register file, SSAs, and kernel trap frames be-13 fore the sweep starts. Comparing (1) and (2) is largely a question of which path can better absorb the check. 3. Sweep-frontier register. Maintain an machine mode (M-mode) physical-address frontier CSR marking the swept prefix. Stores from U-/S-mode below the fron-tier trap to the HMM, which filters the stored value and completes the store. Only one comparator is added, and the fast path is untouched for the (majority) unswept re-gion; the cost is trap-per-store in the swept region, which grows as the sweep progresses. A HAM-based vari-ant—temporarily assigning swept regions to the HMM’s own reserved hue reuses existing hardware but is limited by the 64-entry, NAPOT-encoded table. 4. Write-tracked iterative sweep. Use coarse write track-ing (a card table over physical pages, or page-table dirty bits) to re-sweep any page that received stores after be-ing swept, iterating to convergence. Avoids datapath changes but an adversarial OS can keep dirtying pages indefinitely, so it needs a bounded number of itera-tions plus a final stop-the-world pass—making it strictly worse than our current stop-the-world sweep unless the tracking granularity is fine enough to make the final pass cheap. 5. Hue epochs. Pair each hue with a generation counter, held in the HAM entry and either carried in spare otype 

bits or in an added capability field, so that a recycled hue does not match capabilities from a previous gener-ation. This does not by itself solve the copying hazard, but it enlarges the e ff ective hue namespace and pushes the threshold-triggered sweep further out; with a wide enough epoch, sweeps become rare enough to be com-fortably a ff ordable. The trade-o ff is otype pressure: bits taken for epochs come out of the 15-bit color space per enclave (§5.1). 

Non-contiguous and dynamically resized enclaves. A

PRISM enclave’s memory is committed once, at creation, and cannot subsequently change. Because a single HAM entry describes exactly one NAPOT region § 5.1, the kernel backs each enclave with one physically contiguous region whose size if fixed by the TEE_IOCTL_CREATE request; the TRTS’s allocator is correspondingly a freestanding allocator over a static arena. An enclave must therefore be provisioned for its worst-case footprint, and over-provisioning is paid for twice: NAPOT rounding contributes up to 2 × internal fragmenta-tion on top of the requested headroom, and the entire region is zeroed and physically pinned for the enclave’s lifetime. Growth beyond the static enclave boundaries is possible only by OCALL to into host-managed memory, which lies out-side the enclave’s hue-protected region and is thus untrusted. This limitation closely mirrors first-generation Intel SGX, in which every Enclave Page Cache (EPC) page had to be added with EADD before EINIT : the heap was sized at build time from enclave configuration’s declared maximum. Intel ad-dresses this in SGX2 with Enclave Dynamic Memory Man-agement (EDMM), which permits pages to be augmented into a running enclave ( EAUG ) subject to explicit in-enclave ac-ceptance ( EACCEPT ). PRISM currently provides no analogous facility. The single-region restriction is an artifact of the one en-try per hue convention ; the HAM’s hue field is per-entry, and nothing in the access check requires hues to be unique across entries. A natural extension for future work is to let hues be associated with a set of NAPOT regions, added in-crementally. We sketch here a candidate design to support non-contiguous and dynamically resized enclaves, but leave implementation and evaluation for future work. The HMM must be permitted to program additional en-tries carruing and existing hue. The hue-check logic is un-changed: all 64 entries are already evaluated in parallel, and access is granted if /emphany matching entry is active with the correct hue. EInvoke and EExit must then activate /de-active every entry bearing the target hue rather than a single entry; on a fully-associate table this is a hue-masked broad-cast set /clear of the active bit, so domain transitions remain trap-free ( [P3] ). Growth is a privileged operation, since only M-mode may program HAM entures (§ 5.1). The enclave requests addi-tional memory from its TRTS; on arena exhaustion it per-forms an OCALL asked the host OS to donate memory; the kernel allocates a NAPOT region and issues an SBI_EN-CLAVE_GROW call over the cap_buffer protocol. The HMM then: i) rejects any region overlapping a valid HAM entry, its own reserved region, or a retired hue’s region; ii) zeroes the region under its M-mode exception before assigning it to the enclave’s hue, so the host OS cannot chosen bytes into the en-clave’s heap; iii) program a new entry with the enclave’s hue and sets it valid; and iv) returns a prismatic capability bound to the new region. AS in SGX EDMM, the host OS must not be able to uni-laterally alter an enclave’s view of its own address space. The TRTS performs an explicit accept step before the region is joined to the enclave’s heap: it validates that the returned pris-matic capability contains the enclave’s hue, that its bounds fall in a virtual range the TRTS itself requested and that it’s disjoint from all existing enclave mappings, and only then links the region into the allocator’s free list. A region the en-clave has not accepted is never dereferences, so an unsolicited growth is inert. Following SGX2’s treatment of augmented pages, grown regions are zero-filled and do not contribute to the enclave measurement, so h_enclave and the verification procedure of § 5.6 are unchanged. The HMM can additionally record per-hue committed-size high-watermark in the hue table and include it in REPORT , letting a verifier bound the enclave’s resource footprint. The EPVT remains at the top of the pri-mary region and need not grow, since the color-space is fixed by pvt_shift (§ 5.1). Encalve temporal-savety revocation sweeps must now traverse all accepted regions. The inverse shrinking operation follows symmetrically and is worth supporting for long-lived enclaves. On an enclave-initiated release, the HMM zeroes the region, invalidates its entry, and lets the kernel reclaim the pages; the same scrub-before-release ordering as destruction (§ 5.2) is applied to a subset of the enclave’s regions. The HMM must prevent the enclave’s primary region from being reclaimed in this man-ner. Beyond removing the worst-case provisioning require-ments, the design should reduce enclave creation latency, the the initial contiguous allocation can start small and grown on 14 demain rather than being sized for the worst case. However, The HAM is a fixed 64-entry resource shared across up to 63 concurrent hues, so unrestricted growth is not viable. HAM utilization can be limited by three complementary measures: 

Geometric growth: each grow doubles the committed size. 

Buddy coalescing: when a new region is the aligned buddy of an existing one, the HMM merges them into a single entry, so the steady-state entry count per enclave stays small. 

Region table with HAM as a cache: for the general case, maintain a per-hue region table in HMM-private memory and treat the HAM as a fully-associative cache over it, filled on miss by a hardware walker or an M-mode fill trap. This is conceptually the same approach as in Confidential VM Ex-tension (CoVE) with its hardware-walked Memory Track-ing Table (MTT) [59] (see below), decoupling the maximum number of regions from the table size at the cost of handling misses. 

Susceptibility of SGX Enclave code to memory-safety is-sues. A key advantage of PRISM is that enclave memory safety is enforced by default for all code, including the o ff -the-shelf SGX applications. Running these atop PRISM sur-faces latent memory-safety bugs that SGX’s lack of hardware bounds enforcement allows to go silently unnoticed. For example, for the examples used in our performance evaluation (in § 6), CryptoEnclave passes miscounted bu ff er lengths into its cryptographic routines: NUL-inclusive lengths, an unstripped strlen+1 key, and its AES decryp-tion loop reads a full 4 KiB block from a ciphertext bu ff er sized to a smaller per-chunk allocation, overreading the heap. Similarly, SGX_SQLite ’s btree integrity checker uses an un-bounded write index into a fixed-size coverage bu ff er, causing 

btreeHeapInsert() to overflow whenever a page’s cell and freeblock count exceeded pageSize/4 . This underscores that the lack of inherent memory-safety measures in the TEE programming model manifests as silent bugs in real-world applications, whereas PRISM ’s capability foundation catches these violations. Our source code changes to address these and other com-patibility issues add or modify the following number of lines for each application: 16 for CryptoEnclave , 25 for sgx-kmeans , and 16 for SGX_SQLite . This excludes minor changes, such as removal of SGX EID’s from function sig-natures, adding extern “C” labels in function declarations for compiling with our runtimes, and renaming of functions to avoid conflicts with C libraries (e.g., printf ). 

Speculative-execution and side-channel threat surface. 

PRISM does not attempt to systematically mitigate microar-chitectural side-channels, and we treat transient-execution and timing leakage as orthogonal to the isolation guarantees established in § 4. This scoping decision warrants justifica-tion, particularly in comparison to SGX. A substantial share of the attacks that have eroded SGX’s security guarantees are not failures of its isolation logic but artifacts of the commodity x86_64 microarchitecture into which SGX is embedded. Transient-execution attacks such as Foreshadow [60], LVI [61], and the broader Spectre /Melt-down family [62, 63, 64, 65] exploit speculative and out-of-order machinery that is shared with the rest of the core; SGX enclaves inherit this attack surface rather than introduce it. SGX is thus perennially exposed to a class of vulnera-bilities that are entangled with decades of accreted x86 mi-croarchitectural complexity and are di ffi cult to retrofit against without invasive changes or steep performance penalties. 

PRISM , by contrast, is built on an open CHERI-RISC-V substrate whose speculative behavior is comparatively con-strained and, crucially, tractable to reason about: recent work on architectural contracts for safe speculation in CHERI [21, 22] show that principled, hardware-enforced mitigation of transient leakage can be integrated into this platform rather than bolted on. We emphasize that this is a di ff erence in the tractability and extent of the threat surface , not a claim of immunity; an out-of-order core such as CHERI-Toooba retains a transient-execution surface, but the absence of SGX’s legacy microar-chitecture means PRISM does not begin from the same dis-advantaged position, and the mitigations above can compose with PRISM .We argue that pushing complete side-channel resistance into the hardware architecture is neither practical nor, in gen-eral, desirable. Enclave workloads di ff er widely in their side-channel objectives: a workload processing only public inputs may reasonably tolerate data-dependent timing, whereas one manipulating long-term secrets demands constant-time exe-cution and data-oblivious memory access. A one-size-fits-all architectural guarantee would either under-serve the lat-ter or impose its cost on the former. This tension is sharpest for cryptographic code, where the appropriate defenses are algorithm- and even implementation-specific. For exam-ple, the side-channel-resistant realization of post-quantum schemes, in particular, remains an open research problem; the leakage surface of lattice-based and other post-quantum con-structions is still being mapped, and constant-time or masked implementations continue to be discovered vulnerable. Fixing a side-channel countermeasure in silicon under these conditions risks entrenching a defense that later proves incomplete. PRISM therefore deliberately factors side-channel resistance out of its isolation primitives and leaves it to enclave software and to composable mechanisms, e.g., data-oblivious computation over blinded capabilities as in BLACKOUT [23], that can be applied selectively according to each enclave’s threat model. This separation of concerns keeps PRISM ’s TCB minimal while leaving the door open to stronger, use-case-appropriate guarantees where they are war-ranted. 

PRISM and RISC-V CVMs. PRISM and RISC-V’s emerging confidential-computing stack occupy complementary points in the isolation design space: the RISC-V Confidential VM Extension (CoVE) [59] provides confidential comput-ing through a TEE Security Manager (TSM) operating in M-mode to mediate transitions between confidential and non-confidential contexts, with the TSM acting as a trusted in-termediary between the hypervisor and its TEE Virtual Ma-chines (TVMs). Memory ownership in CoVE is enforced by a hardware-walked Memory Tracking Table (MTT) with per-domain access permissions, so that once physical memory is converted to confidential it is reachable only by the confiden-tial supervisor domain. A TVM is a coarse-grained, whole-VM abstraction: the unit of protection is a guest OS and its address space, and the TCB inside the TVM is correspond-ingly large. 15 PRISM and CoVE di ff er in three aspects which makes them complementary. First, in granularity : a TVM isolates an en-tire virtual machine (VM) from the host, whereas a PRISM en-clave isolates a sub-region of a single user process (at object-level capability granularity), without a guest OS. Second, in 

isolation mechanism : CoVE partitions physical memory be-tween supervisor domains through the MTT, conceptually analogous to Intel Trust Domain Extension (TDX)’s Secure-EPT or Arm Confidential Computing Architecture (CCA)’s Granule Protection Table, and enforces protection at the gran-ularity of pages assigned to a domain; PRISM instead binds physical ownership to unforgeable, M-mode-rooted hues car-ried in the capabilities themselves, and additionally inherits CHERI’s intra-enclave spatial and temporal memory safety, a guarantee entirely absent from the whole-VM model, whose in-TVM memory-safety posture is no better than a conven-tional guest. Third, in threat surface : CoVE assumes a trusted OS and runtime inside the TVM, whereas PRISM ’s threat model treats even the host OS as adversarial and shrinks the trusted computing base to a minimal M-mode monitor and the enclave code itself. A compelling direction for future work is composing these two mechanism by nesting PRISM enclaves within a CoVE TVM. A nested arrangement would yield defense-in-depth and let a CVM defend against a malicious hypervisor and host, while PRISM enclaves inside it defend sensitive com-ponents against the TVM’s own (potentially compromised) guest OS and against memory-safety exploits. Realizing this composition raises open questions we leave to future work. Chiefly, reconciling the MTT’s and HAM’s views of physical memory ownership, extending PRISM ’s at-testation chain to the CoVE layered-attestation architecture so that a verifier can reason about the enclave, the enclosing TVM, and the platform in a single evidence chain, and defin-ing the interrupt- and world-switch interactions when both the TSM and the HMM contend for M-mode traps. 

# 9 Conclusion 

We introduced prismatic capabilities, a CHERI extension that binds an enclave’s capabilities to an unforgeable, M-mode-rooted hue enforcing exclusive access to physical memory, and PRISM , a TEE architecture realizing them on CHERI-RISC-V. By carrying ownership in the capability itself and check-ing it against a hardware hue-addressed table after transla-tion, PRISM resolves the design challenges that have con-strained prior capability-based TEEs: 1) e ffi cient establish-ment of exclusive-ownership of a set of capabilities without memory sweeps or revocation trees at enclave initialization time, 2) enforcement of physical-memory exclusivity even against a malicious OS that controls address translation, per-forms domain transitions through unprivileged, 3) trap-free enclave entry, 4) and supports remote attestation rooted in a minimal M-mode monitor. We implemented PRISM on both a CHERI-RISC-V QEMU emulator and a CHERI-Toooba FPGA softcore and equipped it with support in CheriBSD and an SGX-compatibility layer that runs unmodified enclaves, and evaluated it across three real-world SGX applications with modest hardware cost ( ≈

16% logic) and low run-time overhead ( ≈ 6 − 15%). A symbolic Tamarin analysis establishes the security of its attestation protocol. Together these results show that strong userspace enclaves can be built as a lightweight, capability-native extension.

# A Additional Performance Evaluation 

We extend the evaluation from Section 6 to also compare the additional end-to-end run-time cost of PRISM (enclave cre-ation, temporally safe execution, enclave destruction) to run-ning the same application atop PICASSO (which enables tem-porally safe execution). To obtain the non-enclave baseline application, we modify the source code to remove the en-clave creation and destruction operations, and adjust the C-file header inclusions so that all code paths remain reachable. Figure 8 compares run time of the example SGX applica-tions on PRISM vs. PICASSO . For PRISM ’s run time, we report two measurements: 

• end-to-end run time: enclave creation, temporally safe execution, and enclave destruction (denoted “ PRISM To-tal”); 

• execution time: the temporally safe and isolated execu-tion time alone (denoted “ PRISM Exec.”). For PICASSO , we report only execution time, since it does not support enclave-specific operations by default. For CryptoEnclave , shown in Figure 8a, the performance overhead varies greatly depending on the particular config-uration. When the cryptographic operation takes input text via command line (denoted with “T”), execution time itself is negligible. This demonstrates that for simpler executions, the majority of PRISM overhead stems from life-cycle operations (e.g., enclave creation and destruction). For the variants that take input files (denoted with “F”), the execution time is more significant, reflected in the smaller gap between PRISM ’s end-to-end time and execution time. For the file-taking opera-tions, PRISM introduces 0.95%–4.46% overhead onto the ex-ecution time, whereas enclave life-cycle operations raise end-to-end run-time overhead to 20.7%–71.7%. For SGX_SQLite test cases, shown in Figure 8c, PRISM 

adds 4.9%–5.7% execution overhead to select tests, while reducing execution overhead for ib tests by 5.6%–6.4%. In-cluding the additional costs for enclave creation and destruc-tion, the end-to-end overhead accounts for a 1.19%-13.3% increase. A similar pattern is observed in sgx-kmeans , shown in Figure 8b: for pure execution time, PRISM reduces overhead by 0.33%–0.70% for N = 100K, 700K, and 900K, while adding overhead of up to 11.7% for other input sizes. This minimal variation shows that for these test cases, execution overhead is essentially negligible. The end-to-end overhead of PRISM for sgx-kmeans test cases ranges from 0.01%– 11.7%, heavily influenced by the marshaling of extracted data points via ECALL from the host application into the enclave. 

# B Tamarin Model 

We model PRISM ’s measurement and remote attestation pro-cess in Tamarin. We model the mechanisms and proto-col steps from Section 5.6 as a multiset of rules, and each sub-security property of [P5] from Section 6.3 using lem-mas. We use the hashing , signing , and natural-numbers 

Tamarin built-ins, providing modeling of a collision-resistant hash function, digital signature functions, and natural-number arithmetic, respectively. The rule-based model is shown in Figure 9, and the lemmas are shown in Figure 10. 

## B.1 Rule-based Model. 

Each rule follows the following structure: (1) has a set of pre-condition facts that are required to be true before the rule can be evaluated, (2) a set of action facts in the middle which are recorded when the precondition facts exist, and (3) a set of postcondition facts that are produced to complete the evalua-tion of the rule. Rule 5 models the initial step for installing the HMM into the system. The precondition shows that two fresh values (de-noted with Fr ) must be generated: one for the Prv ’s secret key (sk_prv ) and another for the HMM software itself ( S_HMM ). When this precondition is met, two action facts are recorded. First, HMM_Install is recorded to show that the HMM itself was indeed installed with S_HMM and SecretKey to show that the HMM exists with sk_prv . Four facts comprise the post-condition of this rule, which can then be used as preconditions for other rules: 

• System_Init , used to signal that the system is initial-ized with S_HMM and sk_prv ;

• Pk , signaling that a public key symbol corresponding to 

sk_prv exists; 

• Out , a built-in fact supplied by Tamarin to represent when a symbol is output to the network. In this case, the public key of sk_prv is broadcast into the network; 

• HueTable to demonstrate that an empty but initialized hue table was generated. Rule 7 corresponds to Prv receiving an attestation request from Vrf . A precondition is that a hue and chal value must be received together over the network. When this occurs, the action fact ReceivedRequest is created to log them. A post-condition of this rule is the generation of the fact Get_Re-port , symbolizing that the host has requested a report upon receipt of the request. Rule 8 models the generation of the report by the HMM. The precondition of this rule is that (1) the PRISM system was initialized, (2) a request was received, and (3) an enclave with the requested hue was created. These three are repre-sented by the System_Init , Get_Report , and HueTable 

precondition facts, respectively. When these preconditions are met, a report can be generated by producing a signature over the contents: %hue, chal, h_hmm, h_encl . This is logged with the action fact Signed , which records the con-tents that the signature sig is computed over. The postcon-dition of this rule is that the packed report is sent Out into an untrusted channel. Finally, Rule 9 has two preconditions: it receives some packed input structure via In containing some arbitrary re-port_data and sig , and the public key of a prover exists (e.g., Pk fact from Rule 5). When this precondition is met, an action fact Verified is logged to acknowledge the verifi-cation attempt. This records the report_data that is being verified, the public key used for verification pk_prv , and the verification result, using the built-in function verify . This rule has no postcondition, as it models the protocol’s last step.

Figure 10 shows the Tamarin lemmas modeling the sub-security properties of [P5] . Lemma 0 is used to check report authenticity.
