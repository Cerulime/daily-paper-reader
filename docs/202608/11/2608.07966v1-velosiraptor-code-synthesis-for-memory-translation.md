## 摘要
安全是操作系统（OS）开发者最关心的问题之一。安全运行时环境依赖于操作系统正确配置其运行所在的内存硬件。这是至关重要的，因为它提供了必要的安全相关特性和抽象，确保并排运行的不受信任应用程序的完整性和隔离。配置平台的内存硬件并非一次性工作，因为设计者不断开发具有不同功能和配置方式的新翻译与保护机制。使操作系统代码适应新硬件不仅是手动、重复且耗时的任务，还可能引入微妙但安全关键的缺陷，破坏安全和隔离保障。我们提出了Velosiraptor，一个自动生成正确、底层操作系统代码来编程机器内存硬件的系统。Velosiraptor利用软件合成技术，并利用该问题的领域特异性来使合成过程高效。使用Velosiraptor，开发者只需编写内存硬件映射行为和操作系统环境的高级描述。Velosiraptor工具链将此规范转换为可直接与操作系统其余部分链接的已验证实现。将操作系统环境纳入此过程允许将操作系统移植到新硬件平台，而无需担心编写配置内存硬件的代码。我们还可以使用相同的规范来生成硬件组件。这使得研究新翻译机制成为可能，使操作系统开发者从手动编写操作系统代码中解脱出来。

## Abstract
Security is among the top concerns of operating system (OS) developers. A secure runtime environment relies on the OS to correctly configure the memory hardware on which it runs. This is mission-critical as it provides essential security-relevant features and abstractions that ensure the integrity and isolation of untrusted applications running alongside each other. Configuring a platform's memory hardware is not a one-off effort as designers constantly develop new mechanisms for translation and protection with different features and means of configuration. Adapting the OS code to the new hardware is not only a manual, repetitive and time consuming task, it may also introduce subtle, but security critical bugs that break security and isolation guarantees.   We present Velosiraptor, a system that automatically generates correct, low-level OS code that programs the memory hardware of a machine. Velosiraptor leverages software synthesis techniques and exploits the domain specificity of the problem to make the synthesis process efficient. With Velosiraptor, developers write only a high-level description of the memory hardware's mapping behavior and OS environment.   The Velosiraptor toolchain transforms this specification into a verified implementation that can be linked directly with the rest of the operating system. Incorporating the OS environment into this process allows porting an OS to new hardware platforms without worrying about writing code to configure the memory hardware. We can also use the same specification to generate hardware components. This enables research in new translation mechanisms, freeing up OS developers from manually writing OS code.

## 2. 方法论

### 2.1 核心思想

Velosiraptor 将内存硬件的映射行为抽象为数学模型，将"生成配置代码"转化为"搜索满足目标状态的状态机转换序列"问题，并使用 SMT 求解器（Z3）进行程序验证。

### 2.2 关键技术细节

- **行为模型**：将映射建模为偏函数 `map :: inaddr → mode → state ⇀ outaddr`，即给定输入地址、访问模式和硬件状态，输出目标地址或引发异常。
- **操作模型**：映射单元包含 数据平面（map() 函数）与 控制平面（控制接口状态机），状态由寄存器与内存位置组成，OS 通过接口交互触发状态转换。
- **构建块与组合规则**：
  - 基本块：`segment`——将连续输入地址范围映射到连续输出地址范围；
  - 组合规则1：`enumeration`——类似 C union，多个 segment 共享状态位但不同解释（如页大小位区分大页/页表）；
  - 组合规则2：`static map`——类似表格，将多个 segment/enumeration 按地址索引组合。
- **规格语言**：开发者编写两份规范——硬件映射行为描述 + OS 环境描述（如内存分配函数、能力调用等）。语言支持状态定义（位域切片）、接口定义（读/写动作）、谓词（#[pred]）、翻译函数、合成目标函数（addmap/setperms/delmap）。
- **合成流程**：
  1. 解析规格，构建操作模型；
  2. 将模型编码为 SMT-LIB2 位向量逻辑，进行可行性检查；
  3. 程序生成器按控制接口定义的语法生成候选程序（接口调用序列）；
  4. 验证器将候选程序编码为 SMT 查询，验证其满足后置条件；
  5. 找到满足程序的实现后生成 C/Rust 代码。
- **搜索空间缩减技术**：
  - **状态分解**：通过构建块拆分大单元为小问题；
  - **目标分治**：将目标谓词按合取子式拆分，独立求解后合并；
  - **接口缩减**：仅保留与当前子目标相关的接口部分；
  - **表达式缩减**：根据子目标特征（是否引用参数、常数比较等）限制候选表达式；
  - **树状分治**：用平衡二叉树逐步合并子程序，提前过滤错误候选（例：四合取子式从 665 个程序降至 263 个）。
- **缓存与屏障处理**：采用多阶段合成——第一阶段假设更新立即可见，第二阶段插入缓存维护操作与屏障。
- **硬件生成**：同一份规格可生成 Arm Fast Models 的 LISA+ 模块（模拟硬件组件），支持硬件-软件协同设计。

## 3. 实验设计

### 3.1 评估场景（表1中的12种硬件描述）

覆盖多种翻译硬件类型：

- 简单页表（Simple Page Table）；
- x86_32 / x86_64 多级页表；

- Xeon Phi SMPT；
- 多种段类型（Simple/Variable/Medium/Assoc Segment）；

### 3.2 Benchmark

- **合成时间与扩展性**：测量各描述的合成与代码生成中位/95分位运行时间（100次运行），对比 Ubuntu Linux 内核 v6.2.0 编译时间（约154秒）。
- **消融研究**：分析四种优化（接口缩减、状态缩减、表达式缩减、树状结构）对搜索空间大小（以 log10 计）的累积影响。
- **硬件-软件协同验证**：在 Arm Fast Models 上生成模拟翻译硬件组件并放置于系统总线与 DRAM 之间，运行固件进行内存访问测试。
- **真实 OS 集成**：将 x86_64 页表生成代码集成至 Barrelfish OS，覆盖三种环境：单体内核、微内核特权态、微内核用户态（通过系统调用/能力操作）。
- **性能对比**：在 Linux 用户态比较 Velosiraptor 生成代码与 Linux 6.8 / Barrelfish 手写页表代码的 addmap/setperms/delmap 延迟（200次迭代）。

- 与 Linux、Barrelfish 的手写代码进行性能对比；
- 消融实验对比不同优化级别下的搜索空间大小。

## 6. 主要结论与发现

- **高效性**：Velosiraptor 合成时间对内核编译时间影响可忽略（x86_64 约 1.1 秒 vs 内核编译 154 秒）。
- **优化有效性**：接口+状态缩减是最有效的优化技术，显著降低搜索空间（多个场景从 10³⁸ 降至 10¹³ 以下）；树状分治虽不减少最大候选数但能提前剪枝。
- **正确性**：合成代码通过 SMT 验证满足规格后置条件（映射范围、权限、非目标区域不变性）。
- **硬件-软件协同设计可行**：同一规格可生成模拟硬件组件与对应 OS 代码，且功能正确。
- **真实 OS 可用**：生成的代码能正确配置 x86_64 页表并成功启动 Barrelfish（三种环境均通过测试）。
- **性能无显著差异**：生成代码与 Linux/Barrelfish 手写代码在延迟上基本一致（差异在 1–2ns 内）。

## 7. 优点

- **领域专用合成**：利用内存映射的领域特性（构建块+组合规则），使合成高效可扩展；
- **自动化程度高**：开发者只需编写高层行为描述，无需接触低级位操作；

## 8. 不足与局限

- **不区分异常类型**：模型将翻译错误与权限错误统一视为异常，不区分细粒度故障类别（留作未来工作）；
- **不支持 OS 特定使用场景**：生成的 addmap/setperms/delmap 不暴露交换条目（swap entries）或 NUMA-balancing 等非标准页表用法，用户需通过 enum 构造自行扩展；
- **x86 分段合成耗时高**：远高于 x86_64 页表（12.4s vs 1.1s），因复杂地址表达式无法有效分治；
- **SMT 求解不确定性问题**：含嵌套 forall 量词查询耗时波动大（几毫秒到几秒），造成运行时间双峰分布，影响稳定性预期；
- **硬件生成受限**：目前仅支持 Arm Fast Models（功能仿真），不支持 Verilog/其他 HDL，且无周期精确建模；FPGA 应用需求需额外工作；
- **未处理并发与缓存一致性细节**：论文未讨论多核并发页表操作及 TLB 一致性维护（提到未来集成硬件并发验证，如 Brun 等人的 Verus 工作）；
- **OS 集成验证范围有限**：Barrelfish 集成是部分替换而非全新 OS 移植；未验证在 Linux/其他主流 OS 的完整内核环境；
- **性能对比覆盖不足**：仅对比 2 类页表结构，未测量与手写代码在多级全流程的真实内核环境下的完整性能。
