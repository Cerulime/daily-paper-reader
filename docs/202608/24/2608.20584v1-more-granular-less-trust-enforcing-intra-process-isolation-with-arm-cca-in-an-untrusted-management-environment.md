## 摘要
随着机密计算的日益普及，安全敏感应用通常部署在机密虚拟机（CVM）中，从而减少对第三方云提供商的依赖。然而，源自操作系统的特权攻击在这些环境中仍然是重大威胁。现有的细粒度隔离方案（如SHELTER）提供了进程级保护，但仍易受进程内攻击以及操作系统与进程内对手之间潜在勾结的影响。许多当前的进程内隔离技术仍然依赖操作系统来管理和实施隔离域，导致可信计算基（TCB）庞大。这一差距凸显了对更细粒度、更少依赖信任的机密计算解决方案的需求。在本文中，我们提出了CCAegis，一个扩展Arm机密计算架构（CCA）以实施敏感数据和操作的进程内隔离的系统，保护它们免受进程内对手和操作系统的侵害。我们采用静态分析来跟踪敏感数据的流动并识别处理此类数据的函数。权限切换指令被插入到函数调用和返回点，通过粒保护表（GPT）调整权限，确保只有指定函数才能访问隔离数据。值得注意的是，CCAegis仅信任安全监视器，该监视器配置GPT并管理域切换，从而最小化TCB。我们在官方模拟器和真实开发板上实现了CCAegis以评估其性能。我们的实验结果表明，CCAegis有效隔离了敏感数据和操作，在真实密码学工作负载下，与原始版本相比，性能开销在1.01倍到1.43倍之间。

## Abstract
With the increasing adoption of confidential computing, security-sensitive applications are often deployed in confidential virtual machines (CVMs), which reduce reliance on third-party cloud providers. However, privilege attacks originating from the OS remain a significant threat in these environments. Existing finer-grained isolation schemes, such as SHELTER, provide process-level protection but are still vulnerable to intraprocess attacks and potential collusion between the OS and intra-process adversaries. Many current intra-process isolation techniques continue to depend on the OS to manage and enforce isolation domains, leading to a large Trusted Computing Base (TCB). This gap highlights the need for more granular, less trust-dependent confidential computing solutions. In this paper, we present CCAegis, a system that extends the Arm Confidential Compute Architecture (CCA) to enforce intra-process isolation of sensitive data and operations, safeguarding them from both intraprocess adversaries and the OS. We employ static analysis to track the flow of sensitive data and identify functions that handle such data. Permission-switching instructions are inserted at the function call and return points, adjusting permissions via the Granule Protection Table (GPT) to ensure that only designated functions can access the isolated data. Notably, CCAegis places trust solely in the Secure Monitor, which configures the GPTs and manages domain switching, thereby minimizing the TCB. We implemented CCAegis on both an official emulator and a real development board to assess its performance. Our experimental results show that CCAegis effectively isolates sensitive data and operations, with performance overheads ranging from 1.01x to 1.43x compared to the original version across real-world cryptographic workloads.

- **研究背景**：机密计算（Confidential Computing）被广泛用于保护云环境中的敏感应用，通常以机密虚拟机（CVM）为隔离单元，如AMD SEV、Intel TDX和Arm CCA。然而，CVM内的操作系统（OS）仍可能遭受特权提升攻击，一旦OS被攻破，应用数据极易泄露。
- **现有方案的不足**：
  - 现有隔离粒度较粗（VM、容器、进程级），如SHELTER提供进程级保护，但无法防御**进程内攻击**（如缓冲区溢出、控制流劫持）。

  - 部分方案（如Intel SGX）虽能实现细粒度隔离，但依赖x86硬件，无法直接迁移到Arm。
- **核心问题**：是否能在不可信OS的管理环境下，利用Arm平台现有硬件特性，实现**更细粒度、更少信任**的进程内隔离，保护敏感数据（如密钥）免遭特权软件和进程内攻击者的窃取？
- **整体含义**：本文提出CCAegis，通过扩展Arm CCA的粒保护表（GPT）机制，将隔离粒度下沉到**函数级**，将信任边界收缩到**Secure Monitor（根世界）**，显著缩小TCB，同时保持部署友好性。

## 2. 方法论：核心思想与关键技术

### 2.1 核心思想

- 基于Arm CCA的GRanule Protection Table（GPT）硬件原语，将进程的物理地址空间划分为**敏感区域**和**非敏感区域**。
- 通过**编译期静态分析**自动识别处理敏感数据（如密钥）的函数，并在函数边界插入**权限切换指令**（调用门），使只有“加密函数”才能访问受保护的加密缓冲区。
- 运行期由根世界的Secure Monitor负责GPT配置与域切换，**OS完全不可信**，不参与任何安全决策。

### 2.2 编译期静态分析与插桩

- **用户注解**：开发者只需标记最小集：`#pragma taint_source`（密钥入口）和`#pragma taint_sink`（密文输出），其余自动完成。
- **Taint IR**：在LLVM IR之上构建中间表示，支持上下文敏感、索引感知的指针分析与污点传播。
  - 指令包括：`alloc`、`load`、`store`、`index`、`merge`、`call`、`return`，以及`taint`、`erase`。
  - 通过索引辅助的约束规则（图4）解决结构体/数组的字节级精确定位，减少误报。
- **污点分析算法**（Algorithm 1）：从入口函数线性扫描，结合调用上下文，跟踪敏感数据的传播路径，最终识别出所有“加密函数”。
- **程序插桩**：
  - 对每个加密函数，在入口插入`GPERM`（授予权限），在出口插入`RPERM`（撤销权限）。
  - 对于嵌套调用和外部非加密函数调用，插入`INRPERM`/`INGPERM`内部调用门，维持安全上下文。
  - 采用上下文敏感分析，生成函数多版本，避免非安全上下文误用调用门。
  - 调用门状态机（图7）确保`INGPERM`只能按合法控制流顺序执行，防止攻击者直接跳入调用门。
  - 替换密钥相关的系统调用（如`malloc`/`free`/`read`）为Monitor提供的安全版本。
  - 针对Iago攻击，增加运行时检查：验证mmap返回区域不与加密缓冲区重叠，校验长度类系统调用的返回值。

### 2.3 运行期隔离机制

- **内存隔离**：
  - 设计三种GPT：**Host GPT**（OS用）、**Crypto GPT**（加密函数用）、**Non-Crypto GPT**（非加密函数用），每个核心可独立配置GPT视图。
  - 通过多GPT维护与同步（spinlock）防止内存重叠和过时视图。
  - 使用**影子页表**机制桥接虚拟/物理地址语义鸿沟，Monitor在委托页表前先将其设为no-access，再逐一检查映射，防止TOCTTOU攻击。
- **安全上下文切换**：
  - 调用门使用`svc`立即数传递调用号，绕过OS向量表，直接陷入EL3到Monitor处理。
  - 异常拦截：任何离开CCApp的控制流都会先进入Monitor，切换GPT、清理敏感寄存器状态、处理页表更新。
  - 寄存器清洗：进入加密函数时设置PSTATE为不变量，退出时清零通用寄存器，防止密钥残留。
- **敏感I/O与密钥生成**：
  - 密钥生成由Monitor直接读取硬件RNG（RNDR寄存器），绕过OS。
  - 密钥导入/导出时，Monitor验证文件签名的同时，确保`copy_from_ns`只从Normal内存拷贝，防止解密预言机攻击。
- **多线程支持**：每个线程独立crypto stack，按线程ID保存/恢复敏感状态，核心级GPT切换为无锁热路径，减少跨核TLB shootdown。

## 8. 不足与局限

- **单一敏感域**：目前仅支持一个crypto domain，无法同时隔离多种不同类型密钥的独立域（文中提及可扩展，但未实现）。
- **性能瓶颈**：高并发场景（如Nginx 350客户端）和频繁调用加密函数时开销显著（最高可达75.8%），调用门导致的EL3陷阱和TLB刷新是主要成本。
- **防主动泄露能力有限**：若敏感函数自身恶意泄露密钥，或开发者未正确标注源/汇，静态分析存在误报/漏报风险，无法完全杜绝（论文承认在复杂程序上完全soundness不可判定）。
- **硬件依赖未成熟**：实际实现依赖模拟GPT（用EL3寄存器代替），真实CCA硬件尚未普及，性能结果可能需要重新验证。
- **实验公平性讨论**：与SHELTER的对比并非原生基准，且FVP无法进行周期精确的性能测量，可能影响比较结论的通用性。
- **威胁模型排除较多**：不抵抗硬件攻击（冷启动、总线嗅探）、侧信道（Spectre/Meltdown）和DoS攻击，适用范围集中在软件内存攻击场景。
- **系统调用覆盖有限**：目前仅替换了内存管理和密钥I/O相关系统调用，其他类型系统调用在加密函数内的安全性尚未完全验证。
