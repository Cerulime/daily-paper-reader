## 摘要
大型语言模型（LLM）正从代码补全向仓库级智能体发展，这些智能体能够检索上下文、编辑文件、执行工具并参与安全敏感的工作流程。然而，关于这些系统的证据仍分散在两类评估中：一类是以功能任务完成为中心的软件工程评估，另一类是以漏洞检测、安全生成或利用导向验证为中心的软件安全评估。这项以证据为中心的结构化综述综合了截至2026年5月31日具有代表性的工作，涵盖软件工程任务、软件安全任务、适配机制、工件粒度及评估设计。除任务分类体系外，我们引入了一个保障框架，将功能正确性、安全性、运行可靠性、证据来源与智能体权限区分开来。综述表明，执行反馈与仓库访问能够显著提升工程任务的完成度，但其本身并不能确立安全性；反之，静态分析标签或漏洞分类评分也极少能确立可部署的正确性。我们识别出反复出现的有效性威胁——薄弱的测试预言、重复且时间泄漏的数据、不断变化的智能体框架、仅基于代理的安全检查，以及未充分报告的资源消耗与人工干预——并据此制定了一套用于跨研究比较的最低报告协议。由此产生的研究议程优先关注安全与功能兼备的基准、仓库规模的威胁模型、校准的人工监督、纵向可维护性证据以及可复现的智能体评估。核心结论是，模型能力应被判定为一个由任务适配证据支撑的保障案例，而非仅凭单一基准分数。

## Abstract
Large Language Models (LLMs) are moving from code completion toward repository-scale agents that retrieve context, edit files, execute tools, and participate in security-sensitive workflows. The evidence for these systems, however, remains divided between software engineering evaluations centered on functional task completion and software security evaluations centered on vulnerability detection, secure generation, or exploit-oriented validation. This evidence-centered structured survey synthesizes representative work available through May 31, 2026 across software engineering tasks, software security tasks, adaptation mechanisms, artifact granularity, and evaluation design. In addition to a task taxonomy, we introduce an assurance framework that separates functional correctness, security, operational reliability, evidence provenance, and agent authority. The review shows that execution feedback and repository access can substantially improve engineering task completion, but do not by themselves establish security; conversely, static-analysis labels or vulnerability-classification scores rarely establish deployable correctness. We identify recurring validity threats--weak test oracles, duplicated and temporally leaked data, changing agent harnesses, proxy-only security checks, and under-reported budgets and human intervention--and derive a minimum reporting protocol for cross-study comparison. The resulting research agenda prioritizes jointly secure-and-functional benchmarks, repository-scale threat models, calibrated human oversight, longitudinal maintainability evidence, and reproducible agent evaluation. The central conclusion is that model capability should be judged as an assurance case supported by task-appropriate evidence, rather than by a single benchmark score.

**E = ⟨A, C, M, T, V, B, H⟩**

### 2.4 联合功能与安全成功指标（J@k）

论文定义了交叉领域的核心结果指标：

**J@k = (1/N) · Σᵢ I[∃y ∈ Yᵢ⁽ᵏ⁾ : Fᵢ(y) ∧ Sᵢ(y)]**

其中：
- Fᵢ(y)：输出 y 是否满足任务 i 的功能测试
- Sᵢ(y)：输出 y 是否满足威胁模型对齐的安全检查
- Yᵢ⁽ᵏ⁾：最多 k 个生成候选的集合

同时强调：必须**单独报告 F 和 S**，因为相同的联合分数可能来自截然不同的失败分布，而简单地平均功能与安全分数会掩盖任一维度的灾难性失败。

| 等级 | 证据场景 | 可辩护的主张 | 典型失败 |
|------|---------|-------------|---------|
| E1 | 演示或策划示例 | 示范案例上的可行性 | 挑选样例、无分母 |
| E2 | 受控任务基准 | 在所述基准下的比较性能 | 泄漏、弱测试、度量错配 |
| E3 | 仓库与可执行环境 | 采样项目上的系统有效性 | 隐藏框架效应、基础设施不可复现 |
| E4 | 运行或纵向场景 | 实际部署中的效用、风险与可持续性 | 选择偏差、组织混杂、罕见事件不确定性 |

### 2.6 权威分层（Authority Tiers）

论文将智能体权威分为四个实际层级：

- **G0**：只读解释或检索
- **G1**：无执行的补丁提案
- **G2**：沙箱中的编辑与工具执行
- **G3**：可影响共享仓库、依赖、凭证或部署的行动

随着权威层级提高，评估需要附加最小权限工具范围、网络与秘密隔离、操作日志、审批门控、回滚和事件处理等要求。

论文将研究结论的证据等级划分为 E1–E4 四个级别，要求研究者区分"在基准上表现良好"与"在实践中可靠或安全"这二者。

## 6. 主要结论与发现

1. **执行反馈 + 仓库访问可显著改善工程任务完成度，但不足以确立安全性**——工具使用提升了任务完成率，但引入了框架依赖、更大的攻击面、更高的成本和可复现性挑战。
2. **静态分析标签 / 漏洞分类分数极少能确立可部署的正确性**——检测精度不能替代可利用性、修复时间或分析者成本证据。
3. **证据必须匹配部署主张**——单元测试仅支持测试相对的功能声明；漏洞标签支持分类声明；仓库级或操作级声明需要版本化环境、真实上下文、回归检查、安全预言、预算和人工工作证据。
4. **安全不是附加的下游任务，而是贯穿生成、修复、测试、审查和智能体权限的约束**。联合结果（如 J@k）应与单独的功能/安全结果并存。
5. **模型能力应被视为保障案例而非单一分数**——需结合互补的 E1–E4 证据层次，而非用一个分数替代另一个。
6. **当前文献支持"谨慎乐观"而非"无条件自动化"**——长期可维护性、多语言迁移、对抗鲁棒性和监督的组织成本仍缺乏充分证据。
7. **最优先的研究方向不是另一个孤立的排行榜，而是一个累积的证据基础设施**：版本化基准、可执行环境、防污染分割、功能安全联合验证、透明的智能体权限、完整的轨迹与预算日志，以及纵向以人为中心的结果数据。

- **选择有效性**：这是结构化叙述性综述，非穷尽式搜索和双评审筛选，可能遗漏相关工作；高可见度的英文论文和预印本可能被过度呈现。
- **构念有效性**：术语（如正确性、智能体、自主性、漏洞检测、安全生成）的使用在不同研究间不一致。
- **结论有效性**：任务和配置异质，分数未做统计池化，跨研究推断受限。
- **外部有效性**：语言（以 Python/Java 为主）、开源仓库、精选数据集和短评估窗口的覆盖偏差。
- **时间有效性**：模型、API、框架和排行榜变化迅速，需注意截止日期和基准版本。

### 8.2 应用层面的局限

- **基准覆盖偏差**：多数基准集中于英语、Python/Java、开源代码，对多语言、闭源工业代码、特定领域语言（如 Verilog）的覆盖不足。
- **安全评估的不完整性**：现有基准仍以 C/C++/Python 漏洞数据集为主，对 Web 安全、云安全、供应链安全等新兴领域的覆盖有限。
- **缺乏纵向证据**：可维护性、后续缺陷密度、代码逆转率等生命周期证据不足；短期任务完成率不能直接等同于长期生产力。
- **对抗鲁棒性未被充分测试**：现有评估多针对自然代码演化，对语义保留混淆、提示注入、工具输出操纵等对抗场景的测试不足。
- **人工干预度量缺失**：多数研究未报告人工审查时间、干预次数、审批决策等关键治理数据，使自动化程度的判断缺乏依据。
- **成本报告缺失**：token 数、模型调用次数、墙钟时间等成本信息在许多研究中未披露，导致效率比较不可行。
