## 摘要
可信执行环境（TEE）采用基于硬件的隔离机制来保护敏感代码和数据的机密性与完整性。其中一种普遍实现是Arm TrustZone，它将系统划分为安全世界和普通（非安全）世界。然而，这种划分导致安全世界对普通世界的操作信息可见性非常有限，从而在两个世界之间产生了语义鸿沟。具体而言，当安全世界从普通世界接收数据请求时，缺乏有效的用户身份认证。因此，普通世界中的恶意客户端应用（CA）可以利用精心构造的请求参数来欺骗安全世界中的可信应用（TA），从而危害其他CA存储的敏感数据。我们系统地分类了这些语义鸿沟漏洞（SGV），并提出了一种称为MATEE的TEE伴侣系统来防御SGV。MATEE利用Arm指针认证（PA）将每个请求绑定到相应CA的身份，并在CA访问敏感数据时验证身份，从而防止恶意请求伪造。特别地，MATEE无需修改现有CA和TA即可隔离不同CA的敏感数据。我们的评估表明，MATEE能够有效防御SGV，且运行时开销极小（2.19%）。

## Abstract
Trusted Execution Environments (TEEs) employ hardware-based isolation mechanisms to safeguard the confidentiality and integrity of sensitive code and data. One such prevalent implementation is Arm TrustZone, which partitions the system into the secure and normal (non-secure) worlds. However, this partitioning results in the secure world having very limited visibility into the operating information of the normal world, creating a semantic gap between these two worlds. Specifically, the secure world lacks an effective user identity authentication when receiving data requests from the normal world. Consequently, malicious Client Applications (CAs) in the normal world can deceive Trusted Applications (TAs) in the secure world by utilizing elaborate request parameters, compromising the sensitive data stored by other CAs. We systematically classify these Semantic Gap Vulnerabilities (SGVs) and propose a mate system for the TEE called MATEE to defend against SGVs. MATEE utilizes Arm Pointer Authentication (PA) to bind each request to the corresponding CA's identity and then verifies the identity when the CA accesses sensitive data, thereby preventing malicious request forgery. In particular, MATEE isolates sensitive data of different CAs without modifying existing CAs and TAs. Our evaluation demonstrates that MATEE successfully defends against SGVs with a minimal runtime overhead (2.19%).

- **核心问题**：TrustZone 的隔离是**单向**的——安全世界虽能访问普通世界资源，却对普通世界的运行信息可见性极低，形成**语义鸿沟（Semantic Gap）**。具体表现为：安全世界在接收普通世界请求时，**缺乏对请求发起者（CA 进程/线程）身份的有效认证**，恶意 CA 可伪造请求参数，欺骗 TA 访问其他 CA 的敏感数据。
- **漏洞分类**：本文将语义鸿沟漏洞（SGVs）分为两类：
  - **Type-I SGV（基于指针）**：如指针越界、类型混淆，已有 OP-TEE 等方案通过 PTRSAN 和参数类型校验有效防御，本文直接复用现有防护。
  - **Type-II SGV（基于资源 ID）**：包括共享内存劫持、TA 会话劫持、全局变量劫持、TA 堆破坏、不透明句柄（Opaque Handle）利用、持久存储劫持等。这类漏洞缺乏系统化防御，是本文的主要研究对象。
- **整体含义**：本文提出 **MATEE**，首次尝试系统性地解决 Type-II SGVs，通过 Arm Pointer Authentication（PA）将 TEE 资源 ID 与 CA 身份绑定，在不修改现有 CA/TA 的前提下实现细粒度的资源隔离与合法共享。

## 2. 论文提出的方法论

### 核心思想
利用 Arm PA（Pointer Authentication）生成**基于 CA 身份的资源 ID 签名**（即 PAC），在资源分配时签名、在资源访问时验证，使伪造或重用的资源 ID 无法通过认证。PAC 存放在资源 ID 的高位比特中，随 ID 复制/移动自动传播，无需额外存储或追踪。

### 关键技术细节
1. **CA 身份管理（§4.1）**
   - 使用 32 位随机数 `random_id`（而非可预测的 PID）标识 CA 进程，生成于进程初始化阶段，生命周期与进程同步。
   - 通过 TEE 驱动将 `random_id` 放入 SMC 指令的 `x4` 寄存器传递给安全世界，并存入 TA 会话结构中。
2. **异常处理（§4.2）**
   - 安全世界的 PAC 验证失败会置位 `pac_fail` 标志，清除当前会话，返回自定义错误码 `TEE_ERROR_PAC_FAIL` 给 TEE 驱动，驱动据此**立即终止恶意 CA 进程**，从而抵御暴力破解。
3. **PAC 签名与认证（§4.3）**
   - 在 TEE OS 中封装两个系统调用：`syscall_pacia()`（签名）和 `syscall_autia()`（验证），使用 QARMA 算法生成/校验 PAC。
   - 支持两种上下文（PA Context）：
     - `SESSION_PUBLIC`：仅用 CA 进程 `random_id` 作上下文，实现**进程间隔离**。
     - `SESSION_PRIVATE`：用 `(session_id << 32) + random_id` 作上下文，实现**线程间隔离**（同一 CA 的每个线程对应唯一 TA 会话）。
   - 会话 ID 中附加时间戳，防止重放攻击。
4. **可信线程管理（§4.4）**
   - 修改 TEE OS 调度模块，为同一 CA 进程**固定分配同一可信线程**，避免因不同可信线程拥有不同 PAC 密钥而导致的签名/验证密钥不一致问题。
5. **针对 CWE-639（认证绕过）**：在 Rich OS 的 TEE 驱动中，对共享内存 ID 和会话 ID 进行 PAC 签名与验证。
6. **针对 CWE-862（缺失授权）**：
   - 全局变量保护：用 LLVM 静态分析阻止单实例 TA 使用自定义全局变量；跨会话共享改用 `SetInstanceData()/GetInstanceData()`，其内部增加 PAC 签名/验证。
   - TA 堆保护：新增两种参数类型 `INVARIANT_VALUE_INPUT` / `INVARIANT_VALUE_OUTPUT`，对堆地址进行 PAC 封装；TA 端仍执行类型校验，防止恶意 CA 通过类型混淆绕过。
7. **针对 CWE-732（错误权限分配）**：
   - 不透明句柄保护：修改 91 个涉及五类 Opaque Handle（`TASessionHandle`、`PropSetHandle`、`ObjectHandle`、`ObjectEnumHandle`、`OperationHandle`）的 TEE Internal API，将用法 API 分为直接 API、包装 API、混合 API 三类，避免重复验证并保持调用约定。
   - 持久存储保护：修改存储对象关闭流程，仅重置标志和引用计数而**保留存储对象**，使攻击者用相同存储 ID 重建对象时拿到的句柄签名仍是受害者 CA 的身份，无法通过验证。

### 关键公式/指令流程
- 签名：`PAC = truncate(QARMA(Key, resource_id || context))`，置于 64 位资源 ID 的高位。
- 验证：`autia(resource_id, context)` 恢复错误位，通过检查错误位判断是否认证成功。
- 安全世界的 PAC 在禁用 MTE 时最长可达 31 位（TEE OS 使用 32 位虚拟地址），普通世界 Linux（48 位虚拟地址）下 PAC 为 15 位。

- **MATEE 能够有效防御全部 6 种 Type-II SGVs**，包括 BOOMERANG 中的共享内存劫持、HPE 中的会话/全局变量/存储劫持，以及新发现的 TA 堆和 Opaque Handle 利用。

- **兼容性良好**：无需重写现有 CA/TA，所有官方 xtest 回归测试通过。
- **实现进程级与线程级资源隔离**：`SESSION_PUBLIC` 提供进程间隔离，`SESSION_PRIVATE` 提供线程间隔离，并支持同一 CA 内部线程的合法共享。

## 7. 优点

- **问题定位精准**：首次系统化分类 Type-II SGVs，并由已知漏洞扩展到新攻击面（TA 堆地址、Opaque Handle）。
- **方案设计优雅**：
  - 利用 PA 硬件指令，PAC 嵌入资源 ID 高位，零额外存储开销、零应用改动；
  - 用 `random_id` + 时间戳分别抵御重放和预测攻击；
  - 可信线程绑定解决跨世界 PAC 密钥一致性问题；
  - 通过保留存储对象来阻断以新句柄绕过验证的攻击路径，思路巧妙。
- **防御粒度细**：支持进程级和线程级双层隔离，兼顾安全性与共享需求。
- **实验扎实且开源**：构建了可复现的 PoC 测试套件并开源（GitHub），安全评测覆盖面超过以往研究；性能测试在模拟器和真实开发板上均有实施。
- **TCB 影响小**：984 行代码改动对可审计性友好。

## 8. 不足与局限

- **硬件依赖**：完整实现在依赖 Armv8.3-A 或更新版本 PA 指令，较老设备无法部署（论文讨论中承认，并提及可用软件方案扩展至其他平台）。
- **长期存储保护不足**：短期运行时空闲存储受保护，但 CA 退出后留下的持久文件在新进程中因 `random_id` 更新而不可达；若 TEE OS 重启，之前管理的存储元数据被清除，拥有存储 ID 的任何 CA 都能访问文件。论文仅提出应在用户身份认证层面解决后续问题。
- **可用性问题（DoS 隐患）**：异常处理模块在验证失败时直接终止 CA 进程，攻击者可能故意触发验证失败来对其他进程实施拒绝服务攻击；论文建议以限速/挂起替代直接终止，但未在原型中实现。
- **不覆盖其他攻击类别**：不含侧信道攻击（如 PACMAN）、物理攻击（冷启动、总线嗅探）和 DoS；也不处理 Type-I SGVs（完全依赖 OP-TEE 既有防护）。
- **性能评估的硬件偏差**：性能测试在 Rock Pi 4B 上以软件 XOR 模拟 PA，不能完全反映硬件 PA 的真实时序与安全性；且未与其他非 PAC 类防护方案做横向对比。
- **TCB 信任假设较强**：同时信任安全世界软件栈**和 Rich OS**（因为身份信息由 TEE 驱动提供），若 Rich OS 内核被完全攻破，则身份来源不可信。
- **无法防御同进程内的恶意线程共享场景**：在 `SESSION_PUBLIC` 模式下，同 CA 的合法线程均可访问共享资源，若线程被攻破，仍可能导致数据泄露（但这是设计上有意支持的共享语义）。
