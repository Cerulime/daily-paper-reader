## 摘要
机密虚拟机（CVM）已成为敏感云工作负载的主要载体，从金融服务到隐私保护的人工智能推理。保护这些CVM免受恶意云侵害的硬件隔离，同时也使其所有者对虚拟机内部运行的内容一无所知：通过网络或供应链攻击植入的内核根工具包可以隐藏进程、篡改内核数据，并在保护虚拟机的同一隔离掩护下窃取模型权重。因此，租户需要从外部检查正在运行的CVM，但传统的虚拟机内省（VMI）预设了受信任的虚拟机监控器（Hypervisor），而CVM将其排除在可信计算基（TCB）之外。最先进的CVM-VMI系统00SEVen，通过在特权层（VMPL0）的VM内代理恢复了对AMD SEV-SNP的内省，而这一机制在Arm CCA上不存在，导致Realm虚拟机没有任何内省解决方案。我们提出了RealmEye，这是首个面向Arm CCA Realm虚拟机的VMI系统。RealmEye将整个内省逻辑放置在R-EL2级别的Realm管理监视器（RMM）中，实现了监视器与被监视虚拟机之间的硬件强制隔离：Realm内部不运行任何代理，且Realm保持不变。RealmEye读取Realm的内存和寄存器，暂停虚拟机以获取一致的快照，并捕获页级访问，无需依赖任何VM内接口。周期性、自驱动的触发模式将扫描时间保持在RMM内部，防止Hypervisor与Realm内的根工具包串通。结果通过硬件认证的通道返回给远程所有者，并且CCA驱动程序后端使LibVMI和DRAKVUF等现有工具能够与RealmEye无缝互操作，无需修改。在Arm FVP上，RealmEye检测到了Diamorphine的进程隐藏和系统调用表挂钩，并且其RMM内成本可从原语调用次数线性预测。

## Abstract
Confidential VMs (CVMs) have become the dominant substrate for sensitive cloud workloads, from financial services to privacy-preserving AI inference. The hardware isolation that protects these CVMs from a malicious cloud also blinds their owners to what runs inside them: kernel rootkits planted via network or supply-chain attacks can hide processes, tamper with kernel data, and exfiltrate model weights under the cover of the same isolation that defends the VM. Tenants therefore need to inspect a running CVM from outside, yet classical VM introspection (VMI) presupposes a trusted Hypervisor, which CVMs exclude from the TCB. The state-of-the-art CVM-VMI system, 00SEVen, restores introspection on AMD SEV-SNP via an in-VM agent at a privileged tier (VMPL0), a mechanism that does not exist on Arm CCA, leaving Realm VMs without any introspection solution.   We present RealmEye, the first VMI system for Arm CCA Realm VMs. RealmEye places the entire introspection logic inside the Realm Management Monitor (RMM) at R-EL2, achieving hardware-enforced separation between the monitor and the monitored VM: no agent runs inside the Realm, and the Realm remains unmodified. RealmEye reads Realm memory and registers, suspends the VM for consistent snapshots, and traps page-level accesses, without relying on any in-VM interface. A periodic, self-driven trigger mode keeps scan timing internal to the RMM, preventing the Hypervisor from colluding with in-Realm rootkits. Results are returned to the remote owner over a hardware-attested channel, and a CCA driver backend lets existing tools such as LibVMI and DRAKVUF interoperate with RealmEye unchanged. On the Arm FVP, RealmEye detects process hiding and syscall-table hooking by Diamorphine, and its in-RMM cost is linearly predictable from primitive invocation counts.

## 1. 核心问题与整体含义

- **研究背景**：机密虚拟机（CVM）已成为金融、AI推理等敏感云工作负载的主流基础设施。Arm CCA 通过硬件强制内存加密和访问控制（GPT 表）将 Realm VM 与云平台（Hypervisor）隔离，但这一隔离也带来了"安全盲区"——租户无法从外部感知 VM 内部的运行时状态。
- **核心问题**：敌方一旦通过网络或供应链攻击获取 Realm VM 内核控制权并植入 rootkit，便可在硬件隔离的"掩护"下隐藏进程、篡改内核数据结构、窃取模型权重，而租户对此毫无察觉。传统 VMI（虚拟机内省）依赖受信任的 Hypervisor 读取 VM 内存和寄存器，但 CCA 明确将 Hypervisor 排除在 TCB 之外，硬件层（GPT）禁止其访问 Realm 内存，导致经典 VMI 在 CCA 上彻底失效。
- **现有方案不可移植**：最先进的 CVM-VMI 系统 00SEVen（面向 AMD SEV-SNP）依赖 VMPL0 层级的 VM 内代理，而 Arm CCA 不存在 VMPL 类型的 VM 内特权分层，且 RMM 规范未提供任何内存内省接口。这使得 Realm VM 长期处于"无内省方案可用"的真空状态。
- **整体意义**：RealmEye 填补了这一空白，是首个面向 Arm CCA Realm VM 的 VMI 系统，为机密 VM 带来了可行的外部可见性。

## 2. 方法论

### 2.1 核心设计思想

将全部 VMI 逻辑放置于 Realm Management Monitor（RMM）的 R-EL2 层级，在硬件强制隔离的独立执行域中运行，**不在 Realm 内部部署任何代理、不修改 Realm VM 本身**，实现"监视器—目标"的跨域硬件隔离。

### 2.2 关键实现机制

- **状态访问（F1）**：寄存器直接从 REC 结构读取（TTBR1 EL1、VBAR EL1、SP EL0 等，由 CPU 硬件维护，不可伪造）。内存读取在 RMM 内部构建完整两级读取路径：从 TTBR1 EL1 出发手动完成 ARM64 四级 Stage-1 页表遍历（兼容 2MB 大页块描述符）→ 通过 `realm_ipa_to_pa` 完成 Stage-2 翻译 → 通过 `buffer_granule_map` 瞬时映射物理页读取数据。
- **一致性快照（F2）**：VMI 扫描在 `RMI_REC_ENTER` 内部执行，Realm 恢复运行前扫描即完成，VM 天然冻结，状态天然一致，无需额外机制。
- **页级访问陷阱（F3）**：清除 Stage-2 页表项的写权限位，后续写入触发 Stage-2 缺页退出到 RMM。面临 CCA 特有的 Stage-2 TLB 一致性问题（Hypervisor 无权限广播失效），文中给出了具体设计。
- **触发机制**：不引入新的 SMC 调用（会与 REC 锁死锁），而是复用 `RMI_REC_ENTER` 调用的 `rec_run.enter` 参数——在 `enter.flags` 字段的第 63 位嵌入触发标志，KVM 在进入 Realm 前检查挂起请求并置位，RMM 入口检查该位并执行扫描。
- **两种触发模式**：
  - **按需模式**：VM 所有者通过 Hypervisor 转发请求，扫描时机暴露给 Hypervisor。
  - **周期模式**：触发决策完全由 RMM 内部自主决定，不依赖任何 Host 输入；Hypervisor 眼中所有 `RMI_REC_ENTER` 完全相同，无法区分哪个调用携带扫描，从而切断 Hypervisor 与 rootkit 共谋的信号通道。
- **结果加密回传**：RMM 内部用 AES-128（约 100 行纯 C，无外部依赖）加密结果后写入 `rec_run.exit`，Hypervisor 全程只见密文。扫描结果编码为 16 字节定长明文（进程数 8 字节 + 检测状态码 8 字节）。
- **自主符号解析（S5）**：不依赖外部符号表。从 `VBAR EL1`（CPU 维护、不可伪造）出发，利用 ARM64 Linux 编译期固定偏移 0x800 推导内核文本基址 `stext`，再在受限范围内逐 8 字节扫描连续的内核代码段函数指针阵列（长度数百项），以模式匹配方式定位 `sys_call_table`，实现 KASLR 下的自主解析。
- **检测策略**：
  - **进程列表遍历**：从 REC 中的 SP EL0 指向的 `task_struct` 出发（偏移量经 pahole 静态提取），沿双链表遍历读取 pid/comm 字段——绕过 syscall 层，rootkit 的 `getdents64` 挂钩无法影响结果。
  - **syscall 表完整性检查**：验证 `sys_call_table` 每个条目仍指向内核代码段，若指向模块加载区则判定被挂钩。
- **LibVMI 兼容（F4）**：新增 CCA 驱动后端，将 `vmi_read_pa`、`vmi_read_va`、`vmi_get_vcpureg`、`vmi_pause_vm` 等核心 API 映射到 ioctl → rec_run 通道 → RMM 处理器，使 DRAKVUF、Volatility 等现有工具无需修改即可使用。

## 3. 实验设计

### 3.1 实验平台

- **Arm FVP**（Fixed Virtual Platform）：FVP Base RevC-2xAEMvA，Fast Models 11.29.42，8 核（2 簇 × 4 核），4 GB DRAM，支持 Armv9.2-A RME 扩展。
- **软件栈**：cca-3world 参考实现——TF-RMM v0.1.0（扩展 VMI 功能）、TF-A（EL3 Monitor）、Linux 6.15.0-rc1（cca-host/v8 分支）同时充当 Host 和 Realm 内核，kvmtool 启动 Realm VM。
- **计时**：ARM64 CNTPCT EL0 计数器记录时钟周期。
- **重要限制**：FVP 配置 `cache_state_ modelled=0`，不建模缓存、TLB 和流水线，报告数值反映指令级相对成本而非真实硬件绝对延迟。

### 3.2 检测场景

- **目标**：Diamorphine，ARM64 上广泛使用的真实 LKM rootkit，覆盖进程隐藏与 syscall 表挂钩两类攻击。
- **进程隐藏检测**：Realm 内启动测试进程，加载 Diamorphine 隐藏之，`ps` 和 `/proc` 不再显示；RealmEye 从 RMM 遍历 `task_struct` 列表成功发现隐藏进程；干净内核上 RMM 输出与 VM 内 `ps` 完全一致（对照组）。
- **syscall 表挂钩检测**：加载 Diamorphine 篡改 `getdents64` 和 `kill` 两个条目后，RealmEye 正确判定两个条目指向模块加载区；定位出的 `sys_call_table` 基地址与 kallsyms 条目一致，无假阳性。

### 3.3 微基准测试

- 3 个 RMM 内部原语：`result_encryption`（AES-128 加密）、`vmi_va_to_pa`（四级页表遍历）、`vmi_read_pa`（瞬时页映射读 8 字节）。
- 每个原语执行 1010 次，丢弃 10 次预热，取 1000 个样本。
- 指标采用中位数（p50）和 IQR，同时展示 min–max 误差条（因 FVP 模拟下 CNTPCT 分辨率偶发产生 0–300 周期的异常低值）。

### 3.4 宏基准测试

- **进程列表遍历**：50 个用户态进程的 Realm，执行 55 次取 50 个样本。
- **syscall 表完整性检查**：KASLR 下布局确定性使扫描路径确定，单次测量即可。
- **端到端框架开销**：GET VCPUREG 命令（最轻量，无地址翻译和内存读取），`clock_gettime(CLOCK_MONOTONIC)` 包裹 ioctl，1000 次调用。

### 3.5 对比对象

- 定性对比例：SEV-SNP 上的 00SEVen（唯一同类系统），从部署位置、分离强度、触发通道、抗共谋、符号解析五个维度对比。
- 无定量对比：未与 00SEVen 或其他 VMI 系统在同一平台进行性能数字的直接比较（本质上因平台不同无法直接对比）。

## 5. 实验数量与充分性

- **总体规模**：两套检测策略（进程隐藏、syscall 表挂钩）、三组微基准原语、两组宏基准策略、一组框架开销测试。微基准每个原语 1000 个有效样本，进程遍历 50 个有效样本，GET VCPUREG 1000 次调用，统计基础良好。
- **充分性评估**：
  - 检测功能覆盖了 rootkit 的两大类经典手法（信息隐藏与代码流劫持），且包含干净内核对照实验，逻辑自洽。
  - 成本模型验证充分：微基准 → 宏基准的预测误差均在 3% 以内（进程遍历 2.6%，syscall 检查约 1%），有力地支撑了"线性可预测"的核心论点。
  - **不足之处**：①所有实验均在模拟器上完成，缺乏真实 CCA 硬件验证（作者明确承认并讨论了 OpenCCA 迁移计划）；②未定量评估 F3（页级陷阱）的 Stage-2 TLB 失效成本；③没有直接测量对抗真实内核版本差异的鲁棒性（如不同内核版本的字段偏移变化）；④安全分析为论证性分析，未进行形式化验证或更广泛的攻击场景测试。

## 6. 主要结论与发现

- RealmEye 是首个在 Arm CCA 上实现的 VMI 系统，将内省逻辑全部放入 RMM（R-EL2），实现硬件强制的监视器与目标分离，不修改 Realm、不设 VM 内代理。
- 在 Arm FVP 上成功检测出 Diamorphine 的进程隐藏行为（隐藏进程出现在 `task_struct` 遍历结果中）和 syscall 表挂钩行为（`getdents64`、`kill` 条目被判定为篡改），且无假阳性。
- 自主符号解析方案可靠：RMM 从 VBAR EL1 推导的 `sys_call_table` 基址与 kallsyms 一致；与 00SEVen 依赖外部 System.map 相比，对篡改的符号输入免疫。
- 周期触发模式可有效对抗"恶意 Hypervisor + VM 内 rootkit"的共谋攻击，这是 00SEVen 无法提供的安全保障。
- 开销模型清晰且可预测：`vmi_read_pa` 为 1061 cycles（最小内存访问单元），`vmi_va_to_pa` 为 4523 cycles（约 = 4 × 1061 + 280，验证了四级遍历结构），结果加密 1930 cycles；端到端延迟（GET VCPUREG 中位数 502 μs）主要被 SMC 世界切换和 KVM 路径主导，而非 RMM 内原语成本。
- 与 LibVMI 生态的集成验证成功：通过 CCA 驱动后端，GET VCPUREG 读取的 TTBR1 EL1 与 RMM 全量扫描结果一致，且原有检测路径无回归。

## 7. 优点

- **部署位置选择精准**：RMM 是唯一同时满足"有硬件权限访问 Realm 状态"和"在 VM 内攻击者触及范围之外"的可信组件，将 VMI 逻辑嵌入 RMM 不引入任何新信任假设。
- **硬件强制隔离**：监视器与目标跨执行域、不共享 VM 实例，相比 00SEVen 的 VMPL 软件分层隔离更强——满足 S4 目标。
- **反共谋设计独特**：周期性自驱动触发模式使 Hypervisor 无法区分普通 REC 进入与携带扫描的调用，有效切断共谋信号通道——这是 00SEVen 未覆盖的新威胁维度。
- **自主符号解析**：从 CPU 维护的 VBAR EL1 出发、按固定偏移推导 stext、再以模式扫描定位 sys_call_table，整个过程不接受任何外部输入，对符号注入攻击天然免疫。
- **无侵入复用现有通道**：复用 `RMI_REC_ENTER` 的 rec_run 参数嵌入触发标志，不新增 SMC 类型，不破坏 REC 锁并发模型，是构建在现有执行语义之上的优雅设计。
- **生态兼容性**：新增 LibVMI CCA 后端使 DRAKVUF、Volatility 等成熟工具无改动可用，落地价值高。
- **成本模型严谨可验证**：微基准三原语到宏基准两策略的预测误差均控制在 3% 以内，且对 `vmi_va_to_pa` 的成本构成给出了独立可验证的解释（≈4× 内存读取成本）。

## 8. 不足与局限

- **缺少真实硬件验证**：所有性能数据来自 FVP 模拟器，且 FVP 不建模缓存、TLB 和流水线。文中明确承认 `vmi_va_to_pa` 在真实硬件上的每次内存访问延迟会随 TLB/缓存行为大幅变化，502 μs 的端到端成本在真实 SMC 切换下也需重新测量。
- **硬编码密钥**：当前原型使用硬编码的预共享密钥，生产部署需通过 CCA 认证派生会话密钥（文中已作为后续工作讨论）。此外，端到端信任链依赖 RA-TLS 类协议，但未给出实现细节。
- **可用性威胁视为超范围**：恶意 Hypervisor 可通过拒绝调度 Realm 或清除触发标志来抑制扫描，作者将其归为可用性（availability）问题而不在威胁模型内——对某些用户而言这可能是重要的实际限制。

- **内核版本依赖**：`task_struct` 字段偏移依赖 pahole 静态提取、VBAR 到 stext 的 0x800 编译期固定偏移、以及 `sys_call_table` 模式扫描范围均针对特定内核版本编译布局。文中未对不同内核版本进行系统性测试，若目标 Realm 升级内核导致布局变化，上述常量需重新生成与验证，削弱了长期部署的鲁棒性。
- **安全论证以定性分析为主**：RealmEye 对“恶意 Hypervisor + rootkit”共谋、页表陷阱逃逸等威胁的主张主要依赖架构分析和攻击场景推演，未给出形式化安全模型或更广泛的对抗性测试；结果回传仅用 AES-128 加密而不含认证（如 GCM），对恶意 Hypervisor 的密文替换/回放风险未充分讨论。
- **页级陷阱的 TLB 失效成本未实测**：F3 方案需要处理 CCA 特有 Stage-2 TLB 一致性问题，文中给出了 RMM 侧的失效设计，却未在微基准中定量评估该路径的周期开销；攻击者也可能通过反复写目标页触发陷阱，造成可观测的性能干扰，该 DoS 维度未被深入分析。
- **评估环境与攻击面有限**：全部实验在 FVP 模拟器上完成，且仅测试 Diamorphine 这一种 LKM rootkit；对直接修改内核代码段、伪造 `task_struct` 链表节点等更隐蔽的对抗技术未做验证。真实硬件（如 Arm CCA 开发平台）上的部署可行性与性能仍需 OpenCCA 迁移计划来检验。

## 9. 总结与展望

RealmEye 的核心贡献在于**用最小信任假设重构了机密 VM 的外部可见性**：将 VMI 逻辑放入 RMM 的 R-EL2 层，不触碰 Realm 内部、不新增 SMC 接口，而是复用 `RMI_REC_ENTER` 参数实现触发，从而在 Arm CCA 的硬件隔离边界内建立了“监视器—目标”分离。其自主符号解析、周期自驱动触发、结果加密回传三大设计，分别回应了 CCA 场景下符号不可信、Hypervisor 不可信、通道不可信的根本挑战，构成了一个完整自洽的反 rootkit 检测原型。尽管真实硬件验证缺失、常量硬编码、可用性攻击超范围等局限明显，RealmEye 仍为 Arm CCA 机密计算生态提供了首个可落地的 VMI 路径，也为后续在 RMM 之上扩展更丰富的内省能力（如内核堆遍历、完整性度量、基于认证密钥的加密通道）奠定了架构基础。
