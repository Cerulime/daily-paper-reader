## 摘要
处理器规格支撑着反汇编器、反编译器和模拟器等关键安全与程序分析工具，然而其正确性很少被检验。规格中的错误会扭曲程序行为、掩盖漏洞，并为规避分析提供可乘之机。验证处理器规格是一项艰巨的任务。我们的研究是一项重大努力，旨在首次实现对主要被Ghidra使用的开源SLEIGH语言规格的系统性验证。我们设计并实现了一个基于自动化代理预言验证策略的测试框架。我们的方法利用规格本身编码的结构来枚举可解码的指令形式并生成有针对性的初始状态。然后，通过将执行处理器规格的模拟器与硬件参考进行比较，对这些指令的成功解码和模拟进行差异性测试。将InSPECtor应用于多样化的开源规格——x86-64、AArch64、ARM/Thumb、RISC-V、MSP430——这些规格在风格、作者偏好和指令集架构设计上各有不同，我们发现了超过38,920处差异，这些差异导致了125个独特错误，并提出了修复建议，识别出解码和语义缺陷以及跨供应商的不一致性。我们将发现提炼为8条具体建议，以推动未来的改进。我们的工作强调了规格正确性的重要性，并提供了一种实用工具，以大幅提高SLEIGH处理器规格的保真度，从而增强下游安全与分析工具的可靠性。

## Abstract
Processor specifications underpin critical security and program- analysis tools such as disassemblers, decompilers, and emulators, yet, their correctness is rarely examined. Errors in specifications distort program behaviour, obscure vulnerabilities, and enable analysis-evasion techniques. Validating processor specifications is a non-trivial task. Our study is a significant undertaking to enable, for the first time, the systematic validation of open-source SLEIGH language specifications, predominantly used by Ghidra. We design and implement a testing framework based on an automated oracle validation strategy by proxy. Our approach leverages the structure encoded in a specification itself to enumerate decodable instruction forms and generate targeted initial states. Then differentially test the successful decoding and emulation of those instructions by comparing emulators exercising the processor specification against hardware references.   Applying InSPECtor across diverse, open-source specifications---x86-64, AArch64, ARM/Thumb, RISC-V, MSP430---embedding differences in specification styles, author preferences, and instruction set architecture designs, we uncovered over 38,920 discrepancies that led to 125 unique bugs with proposed fixes, identifying decoding and semantic defects as well as cross-vendor inconsistencies. We distill our findings into 8 concrete recommendations to drive future improvements. Our work underscores the importance of specification correctness and provides a practical tool to substantially improve the fidelity of SLEIGH processor specifications, strengthening the reliability of downstream security and analysis tools.

## 1. 核心问题与整体含义

- **背景**：处理器规格（Processor Specifications）是反汇编器（如 Ghidra）、反编译器、模拟器（如 Icicle、MetaEmu）等安全与分析工具的基石。SLEIGH 是 Ghidra 使用的领域特定语言（DSL），用于描述处理器指令的解码与语义（转化为 Pcode IR）。
- **问题**：尽管 SLEIGH 支撑着超过 35 个处理器家族的描述，其正确性却从未被系统验证。规范中的错误会：
  - 扭曲程序行为分析结果；
  - 掩盖或引入漏洞；
  - 被恶意软件利用以检测虚拟化环境或逃避分析。
- **研究动机**：ISA 手册庞大（ARM 手册 12,000 页，Intel SDM 5000+ 页）且持续演进，人工编写/维护规范极易出错。而现有研究多关注 CPU 模拟器、二进制提升器（lifter）或硬件本身，极少关注规范层面的正确性。
- **整体含义**：本文首次尝试对 SLEIGH 处理器规范进行系统化验证，为依赖这些规范的下游工具链提供正确性保障。

## 2. 方法论：核心思想与关键技术

**核心思想**：利用规范本身编码的结构来驱动验证——通过符号式遍历 SLEIGH 的解码规则，枚举所有可解码的指令形式，生成针对性的初始状态，然后将 SLEIGH 仿真器（作为被测规范的代理）与真实硬件（作为预言）进行差分测试。

**InSPECtor 框架由两大组件构成**：

### （1）GenSYS——测试用例生成器
- **指令生成（Instruction Generation）**：将解码过程视为约束满足问题（CSP），从根表出发递归遍历构造器（constructor）树，为每个可能的解码路径生成一条具体指令编码。
- **关键技术细节**：
  - **简单约束**：直接转换为指令/上下文字节向量中的固定位（mask-and-compare）。
  - **复杂约束**（不等式、非平凡表达式）：作为延迟约束（deferred constraints），在遍历完成后交给 Z3 SMT 求解器统一求解。
  - **附件（attachment）约束**：处理寄存器映射中无效值（如索引 0）对应的隐式约束。
  - **重叠构造器**：为保证生成的编码匹配目标构造器，需加入“避免匹配更高优先级重叠构造器”的隐含约束（取反）；支持通过子表回退（backtracking）区分语义相同的重叠构造器。
  - **解码动作（decode actions）与前缀解析**：处理上下文位更新（如 phase 切换、前缀对上下文的影响），对前缀重复设置遍历深度限制以避免无限长指令。
  - **避免构造函数组合爆炸**：对递归子表（如 ARM 的寄存器列表 2^16 种组合）设置遍历限制（traversal limit）并进行剪枝。
- **状态生成（State Generation）**：从指令的 Pcode 语义中提取潜在边界情况（edge case），例如整数溢出、除零、符号扩展边界、比较相差 ±1、移位越界、NaN 等，用符号执行+SMT 求解生成能触发这些边界的初始输入状态。
- **求解编码**：对仍有自由位的编码，利用 Z3 的 min/max 支持生成最小/最大边界编码，并强制操作数混叠（aliasing）以生成定向测试用例。

### （2）JuxtaPlayer——差分测试执行器
- 在两类系统上执行生成的测试用例：
  - **SLEIGH 仿真器**：基于 Icicle 单步执行 Pcode。
  - **硬件参考**：
    - x86-64 / AArch64 / ARM-Thumb：使用 KVM 硬件辅助虚拟机；
    - MSP430：使用 MSP430FR5969 微控制器 + EEM 调试模块；
    - RISC-V：使用 BeagleV-Ahead (C910) + ptrace。
- **执行流程**：配置初始状态（寄存器、内存、指令指针）→ 单步执行 → 记录最终状态（含异常）→ 与硬件参考逐项对比。
- **异常处理**：使用异常处理器防止三重错误（triple fault）导致 VM 重置；对内存异常采用惰性映射+回放策略。

## 6. 主要结论与发现

- **Bug 分类与根因**（Table 4）：
  - 解码问题（16 个）、语义排序问题（9 个）、错误语义（87 个）、操作数混叠（9 个）及少量其他类别。
  - 典型例子：
    - x86-64 前缀处理（冗余/乱序 REX 前缀）、长模式上下文位处理错误、构造器过度/欠约束、构造器顺序导致 64 位指令不可达；
    - MSP430 寻址模式操作顺序错误（如 `MOV.W @R7+, 0x0(R7)` 源寄存器自增早于目的地址计算）；

    - RISC-V 零寄存器可被写入非零值（CSR 交换）、除零结果依赖环境、浮点 NaN-boxing 缺失；
    - 多个 ISA 的 SIMD/浮点指令部分未实现或存在混叠问题。
- **不可直接修复的问题**：SIMD/向量指令未实现（I-11）、浮点语义不精确（I-12）、不可预测行为（I-13）、内存对齐异常缺语义（I-14）、x86-64 辅助进位标志（AF）缺失（I-15）。
- **8 条 SLEIGH 改进建议**：
  1. 增加反编译器提示（decompiler hints）；
  2. 设计模板化构造器和数组；
  3. 设计更安全的访问器函数（accessor functions）管理 export 引用；
  4. 引入内联辅助函数以同时兼顾反编译与模拟；
  5. 为 SIMD 提供向量化 Pcode 或结构化循环；
  6. 提供浮点操作与舍入模式描述；
  7. 显式处理不可预测/未定义值的 Pcode 操作；
  8. 为内存操作引入对齐信息。
- **对比实验结论**：朴素随机方法在 8 小时内只能命中 62% 构造器（漏掉 1249 个），漏掉 47% 的 Bug（15/32），证明 GenSYS 的规范驱动生成显著优于随机生成。

## 7. 优点

- **首次系统验证 SLEIGH 规范**：开创性地将“规格结构本身”作为测试生成指南，验证对象从模拟器/硬件提升到规范层。
- **方法新颖且通用**：
  - 符号遍历解码规则并结合 Z3 求解，兼顾穷尽性与效率；
  - 状态生成利用 Pcode 边界案例，能发现仅特定输入值触发的错误（如 PACKUSWB 的 255→0 边界错误）。
- **工程实现完备**：GenSYS + JuxtaPlayer 开源，覆盖 5 种差异极大的 ISA，支持 KVM、调试器、ptrace 等多种硬件接入方式；负责任披露，Bug 修复已提交 Ghidra 维护者。
- **分析深度**：手工根因分析（每个 Bug 平均约 4 小时）并对不可修复/非规范错误（如硬件差异、不可预测行为）做了合理分类。
- **研究贡献明确**：不仅发现问题，还提炼语言级改进建议，对 SLEIGH DSL 后续演进具备直接的指导价值。

## 8. 不足与局限

- **不保证完整性（Completeness）**：规范中未包含的指令不会被测试。缺失指令在模拟器/反汇编器中可能表现为“非法指令”异常，但仍可能影响控制流恢复等分析。
- **单指令测试粒度**：无法捕捉跨指令依赖行为（如 ARM/Thumb 的 ITE 条件指令块），未来需扩展到指令序列。
- **硬件/规范不一致难以完全归因**：部分差异源于硬件参考自身行为与文档不符，或厂商不同（Intel vs AMD 在特定指令上的差异、处理器模式限制），需要大量人工过滤。
- **不可修复问题占比高**：SIMD/浮点/对齐/不可预测行为等类别缺失的语义，在现有 SLEIGH DSL 下无法解决，只能靠语言扩展，短期影响工具可用性。
- **人工分析成本高**：125 个 Bug 需要大量人工分类与修复，难以扩展至其他 30+ 个 ISA。差异数（38,920 组）与 Bug 数（125）之间差距极大，自动化精简与根因定位仍是挑战。
- **计算资源与效率未详细披露**：缺少遍历与状态生成的完整资源-时间权衡数据（各 ISA 生成时间差异大，但未深入分析瓶颈）。
- **浮点/硬件参考限制**：RISC-V 与 MSP430 不能使用 KVM，改用调试器/pracc 导致效率低（MSP430 为 0.164 exec/s）、功能受限（RISC-V 仅限非特权指令）。
