## 摘要
自动驾驶车辆依赖庞大的安全关键软件栈，其中攻击者输入可达的弱点可能影响转向、制动或其他控制决策。静态分析可以识别候选位置，但动态确认可利用性需要可执行测试构件，而这些构件难以手动构建。我们研究大型语言模型（LLM）能否为开源自动驾驶栈Autoware自动化这一过程。我们对185个包执行编译器精确的静态分析，识别出1,375条决策规则、2,274项验证检查和482条输入到安全输出的流，据此推导出弱点分类，并抽样740个可达位置。两个本地开源权重LLM、一个无静态上下文消融模型和一个朴素模板基线生成3,700个构件集，在消毒器下针对真实构建进行编译，通过编译器在环反馈进行修复，并在可执行时进行模糊测试。主要结果是一个构建集成失败分类，显示80%的首轮编译失败源于依赖布线而非程序逻辑。推理模型首次尝试编译了64%的测试框架，而代码专用模型仅为6%。仅通过大量桩（stub）修复，推理模型才实现完整的对象可编译性；其测试框架中不到一半到达模糊测试器，且所有37次观察到的崩溃均源自桩代码而非Autoware。在预算内未动态确认任何候选弱点。这些结果表明，构建集成（而非候选生成或模糊测试）是可靠地对完整自动驾驶软件栈进行LLM辅助动态分析的主要障碍。

## Abstract
Autonomous vehicles depend on large safety-critical software stacks, where weaknesses reachable from adversarial inputs may affect steering, braking, or other control decisions. Static analysis can identify candidate sites, but dynamically confirming exploitability requires executable test artifacts that are difficult to construct manually. We investigate whether large language models (LLMs) can automate this process for Autoware, an open-source autonomous-driving stack. We perform compiler-precise static analysis across 185 packages, identifying 1,375 decision rules, 2,274 validation checks, and 482 input-to-safety-output flows, from which we derive a weakness taxonomy and sample 740 reachable sites. Two local open-weight LLMs, a no-static-context ablation, and a naive-template baseline generate 3,700 artifact sets, which are compiled against the real build under sanitizers, repaired through compiler-in-the-loop feedback, and fuzzed when executable. The main result is a build-integration failure taxonomy showing that 80% of first-shot compilation failures arise from dependency wiring rather than program logic. The reasoning model compiled 64% of harnesses on the first attempt, compared with 6% for the code-specialized model. Repair achieved full object-compileability for the reasoning model only through extensive stubbing; fewer than half of its harnesses reached the fuzzer, and all 37 observed crashes originated in stubbed code rather than Autoware. No candidate weakness was dynamically confirmed within budget. These results show that build integration, not candidate generation or fuzzing, is the primary barrier to reliable LLM-assisted dynamic analysis of full autonomous-vehicle software stacks.

## 1. 论文的核心问题与整体含义

**研究动机与背景：**
- 自动驾驶车辆（AV）正从受控测试环境走向公共道路，其软件系统安全已成为交通安全的核心问题，而非单纯的软件工程问题。
- 现代自动驾驶软件栈是大型分布式实时系统，处理传感器与网络数据并输出转向、加速、制动等指令。外部输入可能经多个组件传播后影响执行机构，因此攻击者可达的软件缺陷可能成为安全事故隐患。
- 静态分析可以定位潜在弱点位置，但其结果只是“候选”而非“确认”——静态证据无法证明运行时可达性、路径可行性或安全影响。
- 动态确认需要构造可执行测试工件（harness），包括目标类型、初始化要求、消息格式、中间件依赖、包边界和构建配置。在ROS 2架构的AV栈中，这一步极其困难。
- **核心问题**：LLM能否自动化这一测试工件构建过程，从而在规模化层面实现对自动驾驶软件栈弱点的动态确认？

**整体研究结论（定性判断）：**
- 本研究给出了**“有条件的否定”**结论：在预算内，没有候选弱点被动态确认。
- 根本障碍不在于模糊测试或输入生成，而在于**“对真实构建的忠实集成”（build integration）**——LLM生成的工件无法在原生 Autoware 构建环境中正确编译和链接。

## 2. 论文提出的方法论

**总体流程（五阶段流水线）：**

**Phase 0：静态候选识别**
- 对 Autoware 的 185 个包执行编译器精确的（compiler-precise）静态分析。
- 使用 Clang AST 处理每个编译单元（在其真实构建配置下），恢复 `if`/`switch` 条件，构建简化调用图。
- 解析 launch/YAML 文件获取节点组合、消息重映射和运行时配置；使用 CodeQL 进行交叉验证。
- 产出：1,375 条决策规则、2,274 项验证检查、482 条输入到安全输出的启发式路径。
- 为每个条件位点计算**安全相关性评分（0–11分）**：执行词相关 +3、验证/边界相关 +2、外部 ROS 输入暴露 +2、位于输入→安全输出流上 +3、位于安全关键域 +1。
- ≥8 分为 P1，5–7 分为 P2，其余为 P3。保留全部 P1/P2 位点，共 **740 个目标**。

**Phase 1：工件生成**
- 对每个目标使用**固定提示模板**填充：目标元数据 + 静态上下文（源代码窗口、发现描述、输入话题、安全输出）。
- 每个目标生成四种工件：
  - 函数级 libFuzzer harness；
  - ROS 2 消息变异器；
  - 软件在环故障注入规范（有界丢包、延迟、陈旧重放、NaN/Inf扰动）；
  - ASan/UBSan 构建配置。
- 对比条件包括：2 个 LLM × {静态上下文，无静态上下文} + 朴素基线。

**Phase 2：构建集成与编译修复**
- 使用目标编译单元的 include 路径、预处理器定义和编译选项，将 harness 对真实 Autoware 构建进行编译（启用 AddressSanitizer + UndefinedBehaviorSanitizer）。
- 编译失败进入**编译器在环修复循环**：将失败源码与 Clang 诊断返回给模型，最多 3 轮。
- 区分“首次编译成功”与“修复后编译成功”。

**Phase 3：分诊（Triage）**
- 编译成功的 harness 链接为 libFuzzer 可执行文件，在固定预算下运行。
- 有效性判定：只有调用了预期的 Autoware 实现并将 fuzzer 控制的输入传达到目标分支的 harness 才算有效。
- 崩溃去重、人工评估可达性/可复现性/安全影响。
- 分类：确认为弱点、误报（stub代码崩溃）、预算内未确认、未执行。

**Phase 4：聚合**
- 跨条件对比模型行为、编译失败分类、整体损耗（attrition）分析。

## 6. 论文的主要结论与发现

**核心发现：**

1. **静态攻击面丰富**：Autoware 存在大量安全相关决策逻辑（1,375 条决策规则，集中在规划域 1,161 条和控制域 203 条），验证逻辑分布不均（2,274 项检查中 1,789 项是范围/阈值守卫，仅 6 项数字有效性检查），以及 482 条输入→安全输出启发式路径。

2. **未能确认任何弱点**：在预算内，没有候选弱点被动态确认——但作者强调这并非证明攻击面是良性的，而是因为大多数工件在进入有效执行之前就失败了。

3. **构建集成是主要瓶颈**（回答 RQ1/RQ2）：
   - 2,960 个 LLM 生成的 harness 中，2,259 个首次编译失败；
   - **80% 的首次编译失败源于依赖布线**：1,436 个缺少必需的 ROS/Autoware 头文件（64%），381 个包含目标 .cpp 的路径无效（17%）；
   - 其余为 API 不匹配（225）、签名不匹配（110）、语法错误（81）和其他（26）。

4. **模型选择显著影响结果**（回答 RQ3）：
   - 推理模型（gpt-oss）带静态上下文时首次编译率达 **63.9%**（473/740）vs 代码专用模型（codestral）仅 **6%**（46/740）；
   - 去除静态上下文导致推理模型首次编译率降至 **24.2%**——证明静态上下文实质性地改善工件质量；
   - 修复后推理模型对象编译率升至 100%，但<半数 harness 能链接并到达 fuzzer（289/740 带上下文；315/740 无上下文）——原因在于大量“stub 收敛”。

5. **Stub 收敛（stub convergence）是修复循环的关键失败模式**：
   - 面对未解析依赖时，模型倾向于移除真实依赖并引入本地桩实现，生成自包含但不再调用真实 Autoware 代码的工件；
   - 所有 37 个崩溃均发生在模型重实现的桩代码中，与 Autoware 无关；
   - 朴素基线 100% 编译，但平均 libFuzzer 特征覆盖仅 2（vs 推理模型链接 harness 约 190）——表明“能编译”不等于“有用”。

6. **修复把瓶颈从编译转移到链接**：对象编译率不能作为有效分析的代理指标；需要区分对象编译、链接、目标可达性和真实动态确认。

## 7. 优点

- **首创性（端到端可行性研究）**：首次将存储库级静态分析 + LLM生成 + 原生构建编译/修复 + 模糊测试 + 目标可达性验证整合在对完整自动驾驶栈的分析流水线中。
- **严格的对比设计**：统一模板、统一解码参数、统一构建环境，模型为唯一变量；静态上下文消融和有朴素基线提供了清晰的下界参照。
- **诚实的失败分析**：没有报喜不报忧，系统性地分类了编译失败（构建集成失败分类法）并暴露了 stub 收敛问题——这对后续研究具有很高的指导价值。
- **细粒度的阶段区分**：将失败准确定位在候选选择、生成、构建集成、执行等不同阶段，而非笼统报告结果。
- **重现性意识强**：公布提示词、生成工件、静态分析输出和执行日志。
- **静态分析本身有独立价值**：即便动态阶段失败，1,375 条决策规则/2,274 项验证检查的刻画也能用于人工安全评审的优先排序。

## 8. 不足与局限

- **实验覆盖的局限**：
  - 仅评估一个 AV 栈（Autoware）与两个开源权重模型，结果不可直接外推；
  - 实际模糊时间 60 秒/目标仅为配置预算的 1/10；
  - 只保留具备编译数据库的包，覆盖面不完整。

- **方法论薄弱点**：
  - 决策规则分类与包级流分析是启发式的，既非可靠的上近似也非下近似；
  - “可编译”定义仅为对象编译，大量编译通过的 harness 实际替换了真实接口（stub），导致编译率是乐观上界；
  - 修复循环以“满足编译器”为优化目标而非“保持与真实目标的连接”，导致系统性的 stub 收敛；
  - 修复轮次固定为 3 轮，使用同一模型生成与修复，链接感知的修复可能表现更好。

- **结论的适用性限制**：
  - 软件在环（SIL）实验，未做物理车辆验证，对实际可利用性不作断言；
  - Autoware 是公开代码，可能出现在模型预训练数据中，实际偏向于模型表现——即便如此成功率仍很低；
  - 作者承认对安全性/可利用性的判断是“弱否证”（weak disconfirmation）：多数幸存 harness 执行的是桩代码而非真实目标。

- **潜在的偏差风险**：模型输出质量、生成成本、修复代际的详细统计未完整报告；4 个案例研究有选择性说明的倾向，但整体结论方向明确。

**总体评价**：这是一项设计严谨、诚实透明、结论明确的可行性研究。其核心贡献不在于“LLM 成功自动化了弱点确认”，而在于**精确定位了制约因素**——构建集成而非输入生成是规模级动态分析的主要瓶颈。这对未来自动化安全分析工具的设计方向（构建感知工具、链接感知修复、目标保持约束）具有重要指导意义，同时也证明静态分析本身在安全评审中具有独立价值。
