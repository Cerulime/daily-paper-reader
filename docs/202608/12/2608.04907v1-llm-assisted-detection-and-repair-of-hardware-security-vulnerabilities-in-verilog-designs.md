## 摘要
硬件设计与软件一样，容易受到漏洞的影响，这些漏洞可能引入安全弱点并为恶意利用创造机会。然而，与软件漏洞不同，硬件缺陷在制造后会被永久嵌入硅片中，使其难以或无法修补。这些弱点中的许多被归入通用弱点枚举（CWE）框架，包括不当的访问控制、敏感信息暴露以及意外的权限提升。为了改进此类漏洞的检测，我们提出了一种利用大语言模型（LLM）直接从Verilog硬件设计中识别潜在硬件CWE的方法。该方法在单模块Verilog设计数据集上进行了迭代评估，以检验其在检测硬件安全弱点方面的有效性。我们的结果证明了LLM在硬件设计过程中通过提供自动化、可扩展的辅助来识别安全漏洞，从而增强传统硬件安全分析的潜力。

## Abstract
Hardware designs, like software, are susceptible to bugs that can introduce security vulnerabilities and create opportunities for malicious exploitation. Unlike software vulnerabilities, however, hardware flaws become permanently embedded in silicon after fabrication, making them difficult or impossible to patch. Many of these weaknesses are categorized under the Common Weakness Enumeration (CWE) framework and include improper access control, exposure of sensitive information, and unintended privilege escalation. To improve the detection of such vulnerabilities, we propose a methodology that leverages a Large Language Model (LLM) to identify potential hardware CWEs directly from hardware designs in Verilog. The proposed approach is evaluated iteratively on a dataset of single-module Verilog designs to assess its effectiveness in detecting hardware security weaknesses. Our results demonstrate the potential of LLMs to augment traditional hardware security analysis by providing automated, scalable assistance for identifying security vulnerabilities during the hardware design process.

## 2. 论文提出的方法论：核心思想、关键技术细节与流程

论文提出了一套**迭代式、分阶段引导（structured prompting）的 LLM 分析框架**，并非仅让 LLM 直接判断“有没有漏洞”，而是通过多个步骤逐步引导模型理解设计意图、缩小搜索范围、最终定位并修复漏洞。核心技术流程如下：

### （1）模块分类（Module Classification）
- 向 LLM 提供待测 RTL 模块和一个“模块类型—功能特征—对应 CWE”映射表（如 JTAG 接口对应 CWE-1191、寄存器文件对应 CWE-1262 等）。
- LLM 识别模块中存在的功能和特征，从而**缩小需要重点审查的候选 CWE 集合**，避免对所有 CWE 逐一遍历带来的信息过载与性能退化。

### （2）资产识别（Asset Identification）
- LLM 基于模块类型和特征，识别模块中的关键资产与行为，包括：密钥、特权域边界、时钟行为、复位方案、攻击者能力、安全规则、有限状态机（FSM）状态等。
- 目的：帮助 LLM 理解模块的安全语义所在，为后续审查提供针对性指引。

### （3）依赖图分析（Dependency Graph Analysis）
- 要求 LLM 生成模块的**程序依赖图（PDG）**，图中节点为信号、寄存器和门，边为数据流与控制依赖关系。
- 基于 PDG 执行三类分析：
  - **可达性分析（Reachability）**：判断某节点能否从另一节点通过路径到达；
  - **支配性分析（Dominance）**：判断某节点是否必经另一节点；
  - **污点传播分析（Taint Propagation）**：追踪未受信任来源的信息流向。
- 这些分析的结果用于辅助后续 CWE 审查，帮助识别结构性和行为性缺陷。

### （4）CWE 驱动的人工审查（CWE-Driven Review）
- 将 RTL 设计、已识别的关键资产、PDG 分析结果以及**相关的 CWE 指南（CWE guides）**一同提供给 LLM。
- CWE 指南由作者基于 MITRE 的 CWE 条目设计，包含漏洞描述、引导性思考问题、常见成因和检查清单。
- 只提供候选 CWE 对应的指南，避免信息过载。LLM 输出漏洞列表及其对应 CWE 编号和描述。

### （5）测试平台生成（Testbench Generation）
- 基于已发现的漏洞，LLM 生成对应的 Verilog testbench，用于**验证漏洞的存在与否**，以及验证后续修复是否有效。
- 同时提供一个 CWE 安全设计规则（CWE Design Rules）清单作为指导；这些规则来源于 CWE 缓解措施和常见错误分析。
- 作者强调需要对生成的测试平台进行人工审查，防止误判导致后续修复失真。

### （6）仿真模拟（Simulation）
- 运行生成的 testbench 对 RTL 设计进行仿真。全部测试通过则流程结束；否则进入代码修复步骤。

### （7）代码修复（Code Repair）
- 将以失败测试用例、原始 RTL 设计、CWE 设计规则作为输入，LLM 生成修复后的 RTL 代码。
- 若修复过程中接口发生变化（如新增输入），LLM 需同步更新 testbench。
- 修复最多迭代三轮，若仍失败则记为测试失败。

> **整体思想**：通过多阶段、递进式的引导，将 LLM 的模糊知识逐步聚焦到具体的 CWE 威胁模型上，同时利用测试平台的物理验证结果来抑制幻觉和欠约束修复问题。

## 3. 实验设计：数据集、基准与对比方法

- **数据集**：32 个 Verilog **单模块** RTL 设计（非完整 SoC）。
  - 其中 27 个模块**含有对应的 CWE 漏洞**，用于检验检测能力；
  - 另外 5 个模块**不包含任何已知漏洞**，用于检验误报率（false positive rate）和判断 LLM 区分安全/不安全设计的能力。
- **CWE 覆盖范围**：以 MITRE 2025 年度“最重要的硬件弱点”列表为准，**排除了 CWE-1421 和 CWE-1423**（二者源于微架构设计考量），实际覆盖 8 种硬件 CWE：
  - CWE-226（残留敏感信息未清除）、CWE-1189（SoC 共享资源隔离不当）、CWE-1191（调试接口访问控制不当）、CWE-1234（锁定被内部/调试模式覆盖）、CWE-1247（电压/时钟毛刺保护不当）、CWE-1256（软件接口限制不当）、CWE-1260（受保护内存重叠处理不当）、CWE-1262（寄存器接口访问控制不当）、CWE-1300（物理侧信道保护不当）。
- **模块来源**：一部分由作者根据对应 CWE 的典型成因自行设计，另一部分取自 Qi et al.（2026）前序研究的数据集。
- **LLM 模型**：使用 Microsoft Copilot；作者指出使用其他模型可能得到不同结果。
- **基准与对比方法**：论文**没有设置直接的基线对比实验**，未与 VerilogLAVD、VeriRAG 等前序方法在相同数据集上做定量横向比较。讨论仅以相关工作形式总结方法差异。

## 6. 论文的主要结论与发现

- **强项**：LLM 在**早期分析阶段**表现优秀——模块分类几乎全部正确（仅 1 例误分类），资产识别、模块行为理解、PDG 分析与安全推理能力较强；在 CWE 审查之前，模型甚至常能提前识别出真正的硬件漏洞。
- **弱项**：
  - **测试平台生成是最大短板**：生成的 testbench 经常无法有效验证预期的安全性质，例如错误使用被测设计（DUT）、测试用例不完整、缺少 DUT 复位导致状态串扰、不能区分真实漏洞与正常功能。
  - **代码修复会改变原始功能**：由于未提供模块的预期行为规范，LLM 倾向于“过度安全化”，主动添加特权输入、锁定位、访问控制逻辑等不在设计需求范围内的安全机制，虽然从安全角度合理，却破坏了原设计需求。
  - **非漏洞模块的误报率很高**：5 个无漏洞模块全部被报告存在至少一个“漏洞”，原因多为模型将“缺少不必要安全机制”视为缺陷，属于对安全的不当泛化。
- **总体结论**：论文验证了 LLM 用于 RTL 安全分析的**潜力**，但同时也说明在测试平台生成、RTL 修复可靠性方面，LLM 仍有明显不足，目前仍需人工介入审查，不能完全自动化。

## 7. 优点

- **结构化的多阶段引导设计**：将模糊的漏洞检测任务分解为“分类 → 资产识别 → 图分析 → CWE 审查 → 测试验证 → 修复”六个步骤，逐步缩小模型关注范围、降低信息过载，思路清晰且可复现。
- **CWE 指南与设计规则的自建知识库**：针对每种 CWE 编写了思考引导、常见成因、检测清单和安全设计规则，是论文的重要贡献，也被完整开源。
- **利用 testbench 仿真作为客观验证手段**：不依赖 LLM 的自我判断，而是通过实际仿真结果来驱动是否进入修复阶段，具有一定客观性。
- **测试了误报率**：特意保留 5 个无漏洞模块来测试模型的假阳性倾向，实验设计超越了“仅检测已知漏洞”的简单验证，更具说服力。
- **开源发布**：数据集、提示词和全部实验结果均公开在 GitHub（https://github.com/JazzCat4/LLM-CWE-Detection），有利于后续研究复现和扩展。
- **失败分析详实**：对每个失败案例都做了归因分析（分类错误、testbench 质量问题、未初始化输出、过度修复等），为后续改进提供了价值。

## 8. 不足与局限

- **实验覆盖不够广**：仅覆盖 MITRE 2025 硬件 CWE 列表中的 8 类；32 个模块的数据规模较小；部分 CWE 仅对应 1–2 个测试模块，统计效力有限。
- **无基线横向对比**：未在相同数据集上比较 VerilogLAVD（时序边增强的属性图法）或 VeriRAG（检索增强生成）等方法，无法证明本方法的相对优势。
- **单一模型、无重复性验证**：仅用 Microsoft Copilot 做单次分析，未比较多个 LLM（如 GPT-4、Gemini 等），也未报告多次运行结果的稳定性，结果的随机性未知，存在偶然性风险。
- **未做消融实验**：无法定量回答哪些步骤（如 PDG 分析、CWE 指南）对最终结果贡献多大、可否省略。
- **测试平台生成质量是根本瓶颈**：大量失败（包括误报、漏报和修复无法验证）都源于 testbench 不可靠，而论文没有提出有效的手段来约束或自动校验 testbench 的正确性，这限制了整套流程的自动化程度。
- **缺少模块预期行为规范**：代码修复阶段仅给模块而不给功能规范，导致 LLM 无法区分“必要安全机制”和“过度安全增强”，是功能被改写的直接原因。
- **硬件资源与成本信息缺失**：未报告 LLM 调用的成本、推理时间和算力消耗，对实际可落地性评估帮助有限。
- **隐含假设较强**：仅针对单模块设计进行验证，现实中硬件安全风险多出现在多模块交互与 SoC 集成层面（如总线级访问控制），该方法的可扩展性未被验证。
