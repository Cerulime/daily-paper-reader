## 摘要
基于边界的安全设备（如防火墙或入侵检测系统）对于使用枢轴技术的现代攻击无效，其中攻击者通过被攻陷的主机“枢轴”流量，以访问原本无法访问的其他目标。由于中继流量的合法外观，枢轴攻击极难被检测到。尽管这些攻击的后果众所周知是严重的，但现有防御措施存在高处理延迟、低准确性或依赖全网参与等缺点，使其不方便甚至无效。本工作提出了Stitch，一个基于主机的系统，利用可编程内核实时检测枢轴攻击。通过观察主机穿越流量，Stitch使用进程追踪有效结合系统和网络级信息，连接入站和出站通信，并识别它们之间的枢轴特征。在两次实际部署中，Stitch相比最先进的枢轴防御在准确性上提升了31%，最大误报率为0.006%。Stitch通过为网络中的脆弱主机提供准确、轻量级且独立的覆盖，弥补了当前枢轴检测解决方案的空白。

## Abstract
Perimeter-based security appliances, such as firewalls or Intrusion Detection Systems, are ineffective against modern attacks that use pivoting, wherein attackers "pivot" traffic through compromised hosts to gain access to additional targets that would otherwise be inaccessible. Due to the legitimate appearance of the relayed traffic, pivoting is extremely difficult to detect. Although the consequences of these attacks are known to be severe, existing defenses suffer from drawbacks such as high processing delays, low accuracy, or reliance on network-wide participation, making them inconvenient or even ineffective. This work presents Stitch, a host-based system that uses the programmable kernel to detect pivoting in real time. By observing host-traversing flows, Stitch uses process tracing to effectively combine system and network-level information, connecting incoming and outgoing communications and identifying pivoting characteristics between them. Showing 31% gains in accuracy over state-of-the-art pivoting defenses and a maximum false positive rate of 0.006% over two separate real-world deployments, Stitch covers the gap in current pivot detection solutions by providing accurate, lightweight, and independent coverage for vulnerable hosts in a network.

# 论文详细中文总结

## 1. 核心问题与整体含义

- **研究背景**：现代高级持续性威胁（APT）攻击常利用**横向移动**（lateral movement）在网络内部扩展控制面。传统安全设备（防火墙、IDS）主要防御垂直流量（内外部通信），对内部横向流量高度信任。
- **核心问题**：**枢轴攻击（Pivot Attack）** 利用被攻陷主机作为中继点，将攻击者流量“枢轴”到原本不可达的内部目标。因中继流量外观与合法流量无异，极难被检测；且攻击后果严重（数据泄露、勒索、服务中断）。
- **现有方案的缺陷**：
  - 基于中心服务器的离线检测：延迟高、存储需求大；
  - 基于分布式信息流控制（DIFC）的方案：依赖全网节点协作，在 BYOD、IaaS、PaaS 等动态拓扑中不可行；
  - 基于纯流量特征（大小、时间）的方案：缺乏上下文，误报率（FPR）极高。
- **论文意义**：提出 **Stitch**——第一个将进程追踪与网络流量分析结合的实时主机型枢轴检测系统，无需网络协作即可为主机提供准确、轻量、独立的检测能力，弥补现有防御空白。

## 2. 方法论

- **核心思想**：主机侧检测必须将网络流与承载进程关联，综合系统上下文与流量特征。利用 eBPF（可编程内核）在关键内核监控点采集系统与网络数据，在内核内完成检测流水线，实现实时响应。
- **总体流程（四级过滤）**：
  1. **进程追踪建立因果关系**：将入站流标签传播到接收进程，再传播到其所有子进程及出站连接；
  2. **流量特征比较**：判断入站流和出站流的大小差和时间差是否落在窗口内；
  3. **端点频率分析**：频繁访问的端点视为管理员管理的正常路径，过滤掉；
  4. **告警输出**：满足以上条件的因果流量对判定为枢轴攻击，发送用户空间告警。
- **三大关键技术细节**：
  1. **系统架构四组件**：Userspace Agent（加载 eBPF 代码、处理告警）、Network Ingress Monitor（XDP 钩子监控入站包）、Process Monitor（跟踪进程生命周期：execve/clone/fork/exit）、Network Egress Monitor（TC 钩子监控出站包，执行检测逻辑）。
  2. **标签传播机制**：以五元组 flow ID 为标签，通过 `socketIn`（套接字→入站流）、`tgids`（进程→入站流）、`socketOut`（出站套接字→进程标签）三个 eBPF hash map 实现信息跨域传递；进程标签使用 TGID（线程组 ID）而非 PID，将子线程活动归因于父进程，避免多线程数据路径下的标签爆炸问题。
  3. **存储管理**：采用 eBPF 原生 LRU hash map。利用枢轴流对在生命周期内保持对称性的事实，即使早期上下文被淘汰也可在后续数据包到达时重新建立，支持小容量高周转存储。
- **检测判定公式**：
  - 时间窗口条件：`abs(A_start - B_start) ≤ T_w`（默认 T_w = 1s）
  - 大小窗口条件：`abs(size(A) - size(B)) ≤ S_w`（默认 S_w = 6500B）
  - 端点阈值：默认一个端点连接 ≥ 10 次视为常见、非异常
  - 参数依据：四种工具（SoCat、Chisel、SSH、Nmap）的实测连接握手大小（<50B 至 5500B）和建立时间（100ms 至 600ms）。

## 3. 实验设计

- **测试床环境**：
  - 三台互连服务器：一台枢轴节点、一台目标节点、一台承载 24 节点虚拟网络（含攻击者和目标）；
  - 硬件：Intel Core i7-9700 / Xeon Silver 4210R，16GB/32GB RAM，40Gbps SmartNIC；
  - 系统：Ubuntu 24.04.4，内核 6.8。
- **流量数据集**：使用 Selenium 生成模拟用户行为的合成 Web 流量，建模基于 **CIC-IDS2017** 数据集中 Web 服务器视角的流量。
- **攻击工具**：SoCat（数据中继）、Chisel（隧道，近期真实攻击中出现）、SSH（隧道）、Nmap（侦察），覆盖 APT 三类典型活动：侦察、恶意软件传播、数据外泄。
- **对比方法**：**FCB（flow-characteristics based）方案**——纯流量时间/大小特征检测的主机式 eBPF 实现，是 Spotlight 和 APIVADS 的检测基础，用于隔离对比。
- **参数调优实验**：分别扫描不同大小窗口（固定 Tw=1s）、不同时间窗口（固定 Sw=6500B）、不同端点阈值。
- **可扩展性实验**：用 httperf 生成高并发流量，测试不同 flowStats 映射大小（256 与 10240 条目）下的检测率。
- **资源开销实验**：轻负载（6 请求/秒）和重负载（16384 请求/秒）下的 CPU 占用率，以及 32 位/64 位系统的最大内存占用。
- **真实部署**：
  - 部署一：大学共享多用途服务器（约 4000 用户，日均 1500 次认证），运行 52 天，执行 85 次 SSH 隧道攻击验证；
  - 部署二：公开 Web 服务器及其连接数据库服务器（日均约 83000 次访问、200 次 SSH 连接），运行 32 天，未发起攻击。
  - 系统跨度：内核 6.1 和 5.14 两个版本，验证可移植性。

## 6. 主要结论与发现

- **检测效果**：
  - 测试环境中，平均检测准确率较 FCB 方案提升 **31.49%**，FPR 从平均 42.38% 降至 0.18%；
  - 在合适的参数窗口内，四种攻击工具的检出率均可达 100%；FCB 方案最高仅达 76.19%，且易漏检 SSH 和 Chisel（因连接建立阶段大且缓慢）。
- **误报控制**：真实部署中最大 FPR 仅 **0.006%**（共享服务器 0.005%，Web 服务器 0.006%）。误报来源集中：数据库端口转发（日均 9 条）和自动认证请求，具有一致性和可快速验证性。
- **性能开销**：系统调用延迟增加 1.1%–12%（绝对量 0.6–6.1 微秒），CPU 额外负载 < 0.1%，内存 < 350MB——对现代主机影响可忽略。
- **可扩展性**：flowStats 映射为 10240 条目（仅 240kB）时，可在每秒 20480 条新流的速率下保持 100% 检测率。
- **参数敏感性**：FCB 的检测率在不同窗口参数下波动剧烈，Stitch 则因 IFC 预建立因果关系而稳定；端点阈值越高 FPR 越高（阈值 10→0.23%，阈值 100→3.26%）。

## 7. 优点

- **设计创新**：首次将进程级 IFC 与网络流特征分析统一在同一框架中，3个设计原则（误报减少、资源约束、数据路径复杂性）均有针对性解决方案，逻辑自洽。
- **轻量实时**：整个检测流水线在内核中完成（eBPF），避免用户/内核态切换；LRU 存储策略利用了枢轴流量时间对称性的动态特性，做到小存储、高精度。
- **独立部署**：不依赖任何网络设备协作，兼容动态拓扑，可与其他安全方案（防火墙、审计系统）互补形成纵深防御。
- **可移植性验证**：在 Linux 内核 6.8、6.1、5.14 三个版本上成功运行，支持跨版本部署。
- **真实场景验证**：在大型学术网络（24000+ 用户）中进行 80+ 天真实部署，数据具有较高的生态效度。
- **参数选择有据可依**：基于实际工具的握手大小/时间实测与已有工作（Hopper 的端点阈值范围）确定基线参数。

## 8. 不足与局限

- **主机沦陷风险**：若攻击者获得 root 权限，可禁用或篡改 Stitch（删除标签、修改流记录、抑制告警）。论文承认此问题，并指出增加攻击者操作复杂度、配合 eBPF 映射加固方案可缓解，但未实际实现。
- **可被规避**：攻击者可填充数据包（规避大小窗口）、插入人为延迟（规避时间窗口）、泛洪新连接（触发 LRU 淘汰）来绕过检测。论文仅以“增加攻击足迹”为由认为可接受，未给出具体应对机制。
- **进程级追踪的粒度限制**：将子线程归因于父进程虽避免了标签爆炸，但可能丢失部分细粒度上下文，对复杂多线程进程可能降低关联准确性。
- **配置文件阈值需人工设定**：大小窗口、时间窗口、端点阈值依赖管理员配置，初始基线来自有限数量的工具测量，遇到新型/定制化攻击工具时可能需要重新调优。
- **测试床流量为合成数据**：虽基于 CIC-IDS2017 模型，但与真实互联网流量仍有差距；真实部署中未进行攻击注入（Web 服务器），攻击检测能力主要依赖测试床验证。
- **64 位系统内存上限偏高**：最坏情况下 tgids 映射最高达 320MB，虽然论文论证了实际场景中远低于该值，但对资源极度受限的主机仍有一定压力。
- **与最新系统无直接端到端对比**：相比 Spotlight 和 APIVADS 采用的是间接基线（FCB），未在同一测试环境中完整部署这些系统进行公平对比；对比结论的直观说服力略有削弱。
