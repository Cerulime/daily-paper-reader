## 摘要
现有的PDF阅读器模糊测试工具依赖于仅涉及单个API调用的简单测试用例，导致覆盖范围有限，并可能遗漏需要多个API调用序列的漏洞。为解决这些局限性，我们提出了PDFuzzer，一种新颖的PDF引擎模糊测试工具，能够自动生成复杂且有意义的API调用序列。PDFuzzer首先使用大型语言模型（LLM）从JavaScript API手册和运行轨迹中提取的规范构建上下文无关文法，并推断各个API调用之间的关系。基于这些文法和关系，PDFuzzer采用约束求解器生成具体的API调用序列以进行模糊测试。我们的实验表明，在三个主流PDF阅读器（Adobe Acrobat Reader、Foxit PDF Reader和PDF-XChange Editor）上，PDFuzzer显著优于最先进的PDF模糊测试工具（TypeOracle、Favocado和Cooper）以及基于LLM的模糊测试工具（Fuzz4All、朴素LLM）。与现有工具相比，PDFuzzer的覆盖率最高提升48%，并识别出这些阅读器中的31个零日漏洞，涉及从信息泄露到任意代码执行的多种类型。我们的消融研究验证了每个组件的必要性，包括LLM在流水线各阶段均实现了高精度（93-98%）。我们通过协调漏洞披露流程向供应商披露了所有漏洞，并获得了漏洞赏金。

## Abstract
Existing fuzzers for PDF readers rely on simple test cases that involve only individual API calls, leading to limited coverage and potentially missing vulnerabilities that require sequences of API calls. To address these limitations, we propose PDFuzzer, a novel PDF engine fuzzer that automatically generates complex and meaningful API call sequences. PDFuzzer first uses a Large Language Model (LLM) to construct context-free grammars and infer the relationships between individual API calls from specifications extracted from JavaScript API manuals and execution traces. Based on the grammars and relationships, PDFuzzer employs a constraint solver to generate concrete API call sequences for fuzzing. Our experiments show that PDFuzzer significantly outperforms state-of-the-art PDF fuzzers (TypeOracle, Favocado, and Cooper) and LLM-based fuzzers (Fuzz4All, naive LLM) on three mainstream PDF readers: Adobe Acrobat Reader, Foxit PDF Reader, and PDF-XChange Editor. PDFuzzer achieves up to 48% higher coverage than existing tools and identifies 31 zero-day vulnerabilities in these readers, from information leakage to arbitrary code execution. Our ablation study validates the necessity of each component, including LLMs, which achieve high accuracy across all pipeline stages (93-98%). We disclosed all vulnerabilities to the vendors via a coordinated vulnerability disclosure process and received bug bounties.

## 1. 核心问题与整体含义（研究动机和背景）

- **背景**：PDF文档支持嵌入JavaScript代码，由PDF阅读器内置的JavaScript引擎解析执行，以实现表单提交、拼写检查等交互功能。由于该引擎执行用户提供的代码，恶意PDF可利用引擎漏洞实现信息泄露、拒绝服务甚至任意代码执行。
- **核心问题**：现有PDF阅读器模糊测试工具（如Favocado、Cooper、TypeOracle）存在三个关键局限：
  - **缺失未文档化API规范**：Favocado和Cooper仅依赖官方API手册，遗漏大量未公开API；TypeOracle虽能识别未文档化API，但无法提取其语义功能与行为约束。
  - **无法捕获复杂API间关系**：现有工具最多仅建模生产者-消费者关系（一个API返回值作为另一个API的参数），而实际漏洞常依赖**值约束关系**（两个API参数值需满足相等/不等约束）和**隐式关系**（通过共享系统状态交互，无直接数据流）——这些复杂关系现有方法均无法捕捉。
  - **缺乏自动化规范提取**：API手册动辄数百页自然语言描述，现有工具需大量人工分析，耗时且易遗漏。
- **整体含义**：该论文提出PDFuzzer，利用LLM自动从API文档和执行轨迹中提取规范、生成语法、推断API间复杂关系，并通过约束求解器生成高语义质量的API调用序列，显著提升PDF阅读器JavaScript引擎的模糊测试覆盖率与漏洞发现效率。

## 2. 方法论（核心思想、关键技术细节）

PDFuzzer由四个主要组件构成：

- **① API规范提取**（双路径：文档化+未文档化）
  - **文档化API**：使用正则表达式解析官方API手册（HTML格式），提取对象、函数名、类型、参数、描述、返回值等信息，生成结构化JSON规范。
  - **未文档化API**：结合TypeOracle的差分分析提取原始签名 `object.method(param: type)`，再用LLM基于父对象描述、同对象其他API、参数名语义等上下文，推断功能描述、参数约束、有效范围、返回语义和行为，生成与文档化API格式一致的完整规范。LLM在参数类型识别中还能纠正TypeOracle的错误分类。

- **② 语法生成（Grammar Generation）**：两阶段参数级CFG生成
  - **阶段1**：将每个API规范按参数分解为独立规范单元，避免复杂API（如Doc.submitForm有23个参数）信息过载导致LLM生成过度泛化语法。
  - **阶段2**：对每个参数单独使用LLM生成BNF风格CFG，保留枚举值集、数值范围、格式要求等细粒度约束。
  - 附带Python后处理归一化步骤，修复字符串引号、数字前导零、数组中嵌套对象等问题，确保生成参数符合JavaScript语法。

- **③ 关系推断（Relationship Inference）**：两阶段RAG驱动的关系提取
  - **候选关系（弱层）**：通过RAG向量检索快速筛选可能共现的API配对，将$O(n^2)$复杂度降为$O(n)+O(k^2)$（$n=666$个API，$k\ll n$）。
  - **强符号关系（强层）**：LLM对候选配对进行三种语义类型的深入分析：生产者-消费者、值约束与隐式关系，同时完成参数符号化（分配符号变量）、生成SMT-LIB2约束、确定执行顺序。例如 `Doc.addField` 与 `Doc.getField` 的 `cName` 参数需相等且 `addField` 先执行，约束表示为 `(= x y)`。

- **④ 测试用例生成**：四阶段管道
  - **阶段1**：使用各API的CFG生成语法有效的单个API调用。
  - **阶段2**：关系感知的序列构建——候选关系仅要求共现（各参数独立生成）；强符号关系用Z3 SMT求解器求解约束确定参数值（最大序列长度设为2000次调用）。
  - **阶段3**：集成Cooper的合作变异，将PDF原生对象（页面、表单字段、动作、注释）与JavaScript API关联，生成包含必要PDF结构的丰富文档。
  - **阶段4**：对约15%的测试用例做定向变异（注入非BMP Unicode、转义序列、边界数值等），探测引擎鲁棒性。

- **覆盖率优势**：PDFuzzer在三个目标上实现最高覆盖率，比TypeOracle高最多37%，比Cooper高最多48%，比最优朴素LLM（Claude-3.7-Sonnet）高16-49%。Fuzz4All生成的大量无效代码导致其在Foxit和PDF-XChange上覆盖率最低。

- **约束求解可行性**：91.5%的强符号关系可成功实例化（值约束95.1%、生产者-消费者81.5%、隐式64.0%），证明推断的关系切实可用于生成。

## 7. 优点（方法或实验设计的亮点）

- **突破生产者-消费者局限**：首次系统建模值约束和隐式关系两类API间依赖，并用SMT求解器强制执行，覆盖现有方法无法触及的漏洞模式（如 `popUpMenuEx` 与 `search.query` 间需字符串相等的UAF漏洞）。
- **高效的两阶段关系推断**：RAG候选筛选将$O(n^2)$分析降到近线性，使666个API的全面关系分析在可接受成本内完成；同时分层建模（候选 vs 强符号）保证了生成灵活性与约束严密性的平衡。
- **参数级语法生成**：分解参数逐一处理，避免LLM上下文信息过载，保留枚举值、范围约束等关键细节；后处理归一化提升生成代码的语法有效性。
- **LLM+传统方法互补**：LLM负责语义推断（规范、语法、关系），传统方法负责精确求解（TypeOracle差分分析提类型、Z3求解约束），各取所长。
- **消融设计严密**：每个组件都有对照与量化贡献（如未文档化规范推断提升最多28%覆盖率、参数级语法提升最多18%、强弱关系分层提升最多8%、值约束+隐式关系比PC-only提升最多15.5%），因果关系清晰。
- **成本效率优越**：相比直接让LLM生成测试用例（每例60-90秒），PDFuzzer使用LLM仅做一次性离线分析，在线生成通过CFG+SMT实现，吞吐量高2-3个数量级，实际使用门槛低。

## 8. 不足与局限

- **闭源目标无法直接插桩**：覆盖率依赖DynamoRIO动态插桩，该工具本身带来执行开销和不稳定性，可能导致误报或性能影响；无法使用更精细的覆盖率反馈（如边覆盖率）进行导向式模糊测试。
- **依赖TypeOracle**：未文档化API的类型提取沿用TypeOracle的差分分析方法，若该方法存在系统性偏差可能向上传播；LLM能纠正部分类型误判但无法全部解决（如dcSignup中“Perm”后缀导致的误分类）。
- **LLM推断的固有不确定性**：无API文档的Foxit和PDF-XChange以Adobe手册为参考，其API差异可能造成规范偏差；LLM随机性和API模型演进可能影响结果可复现性；精度抽查样本量（每步60个）有限。
- **上下文窗口限制与错误恢复机制简单**：RAG只能粗粒度检索API配对；JSON格式失败仅靠简单重试，缺乏更精细的反馈校正机制。
- **实验环境较单一**：漏洞验证在Windows 8.1 VM中进行，虽在10/11上验证了复现性，但未测试其他操作系统（macOS、Linux）或更多读者版本；2周窗口可能遗漏需要更长运行时间才触发的漏洞。
- **约束求解失败的剩余8.5%**：隐式关系实例化成功率仅64%，表明部分推断的关系在实际生成中无法落地，存在提升空间。
- **部分数据报告不完整**：漏洞表包含省略号（如ID 10-14等信息未显示），对完整评审有一定影响。
