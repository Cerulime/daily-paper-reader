## 摘要
基于LLM的分析器已经开始在成熟的开源项目中发现真实漏洞：AISLE的分析器已在78个项目中获得超过280个CVE，包括OpenSSL、curl和GnuTLS。我们引入了HoF-Bench（以AISLE的公开名人堂命名），这是一个由八个仓库中固定于易受攻击提交的95个公开AI发现CVE构建的基准。分析器接收源文件和目标文件范围，但不接收CVE标识符、描述、修复或预期机制；一个检测器盲化的前沿模型评判器仅认可那些识别出相同代码路径、根本原因、攻击条件和影响的结果。一个刻意简化的基于LLM的分析器在此严格协议下重新发现了95个CVE中的65个（68%）。本研究中没有任何地方使用前沿模型进行检测。十个检测器骨干包括五个开放权重模型（总计210亿至2840亿参数，3至130亿激活）和五个专有小规模或“flash”级模型。它们都在固定脚手架中运行，四次重复扫描，一个可选的生成上下文阶段，以及一个可重放的多轮分诊阶段（7600条模型-CVE扫描记录）。难度受语言结构强烈影响；所有模型都遗漏的CVE集中在C基础设施代码中。HoF-Bench为比较漏洞扫描器、其跨重复运行的可靠性以及它们产生的候选数量提供了一个紧凑的测试平台。数据集可在https://huggingface.co/datasets/aisleinc/HoF-Bench获取。

## Abstract
LLM-based analyzers have begun finding real vulnerabilities in mature open-source projects: AISLE's analyzer is credited with more than 280 CVEs across 78 projects, including OpenSSL, curl, and GnuTLS. We introduce HoF-Bench (named after AISLE's public Hall of Fame), a benchmark built from 95 of these public AI-discovered CVEs across eight repositories pinned at vulnerable commits. Analyzers receive source and target-file scope but not CVE identifiers, descriptions, fixes, or expected mechanisms; a detector-blinded frontier-model judge credits only findings that identify the same code path, root cause, attack condition, and impact. A deliberately minimal LLM-based analyzer rediscovers up to 65 of the 95 CVEs (68%) under this strict protocol. No frontier model performs detection anywhere in the study. The ten detector backbones are five open-weight models (21B--284B total parameters, 3--13B active) and five proprietary small or "flash"-tier models. All of them run in the fixed scaffold with four repeated passes, an optional generated-context stage, and a replayable multi-round triage stage (7,600 model--CVE pass records). Difficulty is strongly structured by language; the CVEs missed by every model concentrate in C infrastructure code. HoF-Bench provides a compact test bed for comparing vulnerability scanners, their reliability across repeated runs, and the candidate volume they create. The dataset is available at https://huggingface.co/datasets/aisleinc/HoF-Bench.

# HoF-Bench 论文详细中文总结

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：基于 LLM 的漏洞分析器已在真实开源项目中发现了大量漏洞（AISLE 分析器贡献了 280+ CVE），但存在一个根本性的评估问题——**如果一个 LLM 分析器曾经发现过某个漏洞，另一个分析器能否仅凭易受攻击的源代码再次发现它？**
- **现有基准的不足**：绝大多数安全基准侧重于片段分类（如 Devign、Big-Vul）、补丁生成、利用复现或人为构造的易受攻击应用，这些任务不能直接衡量"扫描器报告是否在真实复杂软件环境中识别出值得 CVE 的漏洞"。
- **整体含义**：漏洞发现是一个系统性问题而非单次模型调用问题。论文旨在构建一个紧凑、可控的测试平台，用于衡量非前沿模型在严格协议下重新发现真实 AI 发现漏洞的能力，从而推动 AI 漏洞发现的可信评估。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 核心思想
- 构建 **HoF-Bench v1** 基准，包含 95 个 AISLE 公开的、由 AI 发现的真实 CVE（来自 8 个仓库，每个仓库固定在一个易受攻击提交快照上），要求扫描器**仅凭源代码和目标文件范围**重新发现这些漏洞的精确身份。
- 使用**固定参考扫描流水线**：可选上下文构建 → 漏洞检测 → 怀疑式三阶段分诊 + 仲裁，以公平比较不同检测模型。

### 关键技术细节
- **信息边界设计**：
  - 扫描器可见字段：仓库 URL、固定提交、目标文件（1–7 个，中位 911 行源码）、任务 ID。
  - 评估器专用字段（不泄露给扫描器）：CVE ID、预期路径、行范围、漏洞描述、修复元数据、CWE/严重性。
  - 扫描器不接收 CVE 标识符、漏洞描述、修复提交或预期漏洞片段。
- **严格重发现协议**：评估器（GPT-5.6 terra，前沿模型）被盲目化处理（不知道检测器身份、上下文条件、扫描轮次），只有识别出**相同代码路径/组件、根本原因、攻击者可控条件/信任边界、安全影响**四个身份维度的发现才获得严格匹配。
- **评判结果分为四类**：match（严格匹配）、partial（部分匹配）、no match、insufficient evidence，主要指标为严格召回率。
- **生成的上下文阶段**：检测器先行编写安全简报（组件用途、外部可达入口、信任边界、安全相关数据/控制流），并可发起最多 3 次仓库搜索（仅字面搜索）。
- **分诊系统**：三顺序轮次 + 仲裁模型，仲裁者基于代码证据做出最终判定而非投票。所有逐轮判定被存储，可追溯重放模拟更浅的分诊策略。
- **成功率计算**：Success@k 为在 k 个重复扫描子集中至少被一个发现覆盖的期望 CVE 数，遍历所有子集避免扫描顺序偏差。

## 6. 论文的主要结论与发现

- **大多数真实 AI 发现漏洞可以被重新发现，但没有任何单次运行能做到**：最佳四轮严格召回为 **65/95（68%）**（GPT-5.6 luna，有无上下文均如此）。6 个模型族至少达到 50 个 CVE。
- **重复扫描带来最稳定的收益**：从 1 次到 4 次重复平均每个模型多发现约 12–20 个 CVE；平均单次扫描仅恢复四轮扫描最终成果的 68%；62% 的成功模型–CVE–条件单元仅在 4 次相同扫描的部分（而非全部）中被捕获。
- **模型多样性优于重复**：4 个领先模型各扫描 1 次的组合覆盖期望 68 个 CVE，超过最强模型 4 次重复覆盖的 65 个。40 个上下文运行的总并集达 84/95（两种条件合计 85）。
- **生成的上下文不是普遍增益**：上下文在 pass@4 下略增 +21/950 个模型–CVE 单元（54.1% vs 51.9%），但置信区间穿越零（[-6, 47]）；它将全模型遗漏数从 16 降到 11，但显著增加了发现量（去重后从 1,664 增至 2,088）和每个已重发现 CVE 的评审负担（3.4 → 4.1 个去重发现）。
- **分诊深度影响不大**：3 轮+仲裁 vs 1 轮的总体重发现结果仅从 974 变为 1,007 个模型–CVE 单元，模型相关性明显。
- **语言是比模型选择更强的难度决定因素**（上下文条件下）：JavaScript 各模型召回中位数 81%（71–100%），PHP 为 63%（50–73%），C 仅 31%（16–62%）；11 个全模型遗漏 CVE 中 9 个在 C 中。同类漏洞（如授权类）在 JavaScript 中平均被 8.1 个模型发现、PHP 5.8 个、C 仅 3.0 个。源文件大小同样预测难度（ρ = -0.47 总体，C 内 -0.53）。
- **统计模型**：Rasch Beta-Binomial 模型显著优于 Binomial（∆ELPD > 100），证明重复扫描结果比独立伯努利假设更相关；2PL 增加的判别参数不带来显著改善（∆ELPD = 5.6，dSE = 6.3）。

## 7. 优点：方法或实验设计上的亮点

- **真实性与严格身份匹配的结合**：基准全部来自真实的 AI 已发现公开 CVE（真实生产项目，非合成），而评分又坚持"同代码路径+根本原因+攻击条件+影响"四维严格匹配，避免仅凭文件接近度或漏洞类别打分的弱评价。
- **信息泄露控制严谨**：扫描器可见字段与评估器专用字段分离，附带泄漏测试；评判器对检测身份、上下文条件和扫描轮次三重盲目化。
- **可复现性设计好**：每个仓库仅需 1 个检出、8 个检出即可运行完整基准；数据集和原始运行工件全部公开（Hugging Face + GitHub）；逐轮分诊评审被存储以支持政策重放。
- **可靠性视角的引入**：通过 success@k 曲线和 4 次重复运行，将扫描随机性模型化为 Beta-Binomial，打破"单次扫描分数代表模型能力"的惯例。
- **成本–效益分析**：补充图 6 给出每个基准 CVE 的归因 API 成本 vs 重发现数的实际权衡，对实际部署选择有指导意义。
- **语言与机制交叉分析**：揭示"漏洞难度更由语言/代码规模而非漏洞类别决定"这一重要结构化发现。
- **坦诚的偏差披露**：作者明确声明基准来自 AISLE 自身 CVE 人口、所有检测器共享同一分析器架构、训练数据污染和评判器同族偏好无法排除——透明度高。

## 8. 不足与局限

- **基准来源单一性**：HoF-Bench 的全部 CVE 来自 AISLE 一家供应商的自有发现，构成"AISLE 条件化"的样本，不代表更广泛的 agentic CVE 人口；作者建议读者对照 Berkeley 的 Agentic Vulnerability Coverage Map 评估代表性，而非信任其选择。
- **局限于目标条件召回**：任务提供目标文件范围（源于 ground truth、含主要易受攻击文件），因此测量的是"定位后分析"而非端到端的全仓库定位能力；没有精度/误报率测量（未匹配发现被标记为"未验证"而非"误报"）。
- **评判与去重的自动化未人工审计**：LLM 评判器和语义去重缺乏人工独立验证；评判器与多个检测器属同一供应商（OpenAI），即便身份盲目化也无法排除风格亲和性造成的评分偏好。
- **训练数据污染不可排除**：所有 CVE 均为公开数据，无法保证模型未在预训练中见过相关漏洞和补丁。
- **正样本全阳性设计**：所有任务均为正例，报告的是回忆度量，无法扩展到真实扫描场景中的精确率/误报率结论。
- **模型面板宽度受限**：虽然参数规模跨度大，但所有检测器共享单一脚手架/提示族/分诊设计/评判器，不能解读为对 10 个独立产品的横评。
- **跨任务语义分配未实现**：当前实现不进行跨任务语义分配（作者列为已知限制）。
- **补充统计模型的同族研究基础**：可靠性模型的推导依赖同一团队此前的两篇工作（[4, 15]），尚未被外部独立验证。上下文与分诊消融的不确定性区间较宽，说明这些维度影响的结论仍需更多数据支持。
