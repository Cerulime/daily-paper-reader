## 摘要
现代软件系统通过频繁的提交（commits）来演进，这些提交实现了错误修复、功能增强和安全补丁。虽然代码审查和测试被广泛用于检查这些变更，但它们对内存安全问题的保障往往有限。代码审查者可能遗漏细微的边界、生命周期或初始化错误，而现有测试可能无法执行提交所影响的具体路径。模糊测试在暴露此类缺陷方面非常有效，但将其应用于每次提交仍然不切实际，因为全程序模糊测试成本高昂、需要合适的测试框架，并且可能仍然无法触及提交所修改的代码。在本文中，我们提出了COMMITGUARD，一种针对代码变更验证的提交感知差分切片模糊测试方法。COMMITGUARD背后的关键洞察是：修改函数的提交前版本可以作为解释提交后发现的缺陷的行为基线。对于每个目标提交，COMMITGUARD识别修改过的函数，从提交前和提交后版本中提取可编译的代码切片，并独立地对配对的切片进行模糊测试。然后，它比较两个版本之间的消毒器报告，并仅将在提交后版本中出现的缺陷报告为候选的提交引入缺陷。我们在来自openSSL、libpcap和leptonica的300个提交上评估了COMMITGUARD。切片模糊测试最初在这些提交中产生了518份消毒器报告。通过比较提交前和提交后切片，COMMITGUARD将这个大量输出缩减为7个需要人工分类的候选提交引入缺陷报告。人工验证确认其中5份报告为真实缺陷，这些缺陷在我们报告后已被所检查项目的开发者修复，而只有2份报告被归类为误报。COMMITGUARD平均在32.4分钟内分析一次提交，并对修改函数实现了75.36%的平均覆盖率。

## Abstract
Modern software systems evolve through frequent commits that implement bug fixes, features, and security patches. Although code review and testing are widely used to check these changes, they often provide limited assurance for memory-safety issues. Code reviewers may miss subtle boundary, lifetime, or initialization errors, while existing tests may not exercise the specific paths affected by a commit. Fuzzing is effective at exposing such bugs, but applying it to every commit remains impractical because whole-program fuzzing is expensive, requires suitable harnesses, and may still fail to reach the code changed by a commit.   In this paper, we introduce COMMITGUARD, a commit-aware differential slice-based fuzzing approach for verifying code changes. The key insight behind COMMITGUARD is that the pre-commit version of a modified function can serve as a behavioral baseline for interpreting bugs found after the commit. For each target commit, COMMITGUARD identifies modified functions, extracts compilable code slices from both the pre-commit and post-commit versions, and fuzzes the paired slices independently. It then compares sanitizer reports across the two versions and reports bugs that emerge only in the post-commit version as candidate commit-induced bugs. We evaluate COMMITGUARD on 300 commits from openSSL, libpcap and leptonica. Slice fuzzing initially produces 518 sanitizer reports across these commits. By comparing pre-commit and post-commit slices, COMMITGUARD narrows this large output to 7 candidate commit-induced bug reports that require manual triage. Manual validation confirms 5 of these reports as real bugs that were fixed by developers of the examined projects after we reported them, while only 2 reports were classified as false positives. COMMITGUARD analyzes a commit in 32.4 minutes on average and achieves 75.36% average coverage of modified functions.

### 一、核心问题与整体含义（研究动机和背景）

- **研究背景**：现代软件系统通过频繁的代码提交（commits）进行演进，这些提交可能引入内存安全缺陷（如缓冲区溢出、空指针解引用、内存泄漏等）。代码评审和现有测试难以充分覆盖提交所影响的具体路径，导致缺陷可能在集成后长期存在。
- **核心问题**：如何高效、精准地检测“提交引入的缺陷”（commit-induced bugs）？全程序模糊测试虽然擅长发现内存安全缺陷，但逐提交运行全程序模糊测试成本过高，且可能因覆盖平台无法到达提交修改的代码。
- **研究价值**：需要一种面向提交粒度的自动化验证技术，既能聚焦变更代码，又能区分“该缺陷是否由本次提交引入”，从而辅助代码审查、降低人工排查负担。

### 二、论文提出的方法论

#### 核心思想
- **关键洞察**：修改函数的**提交前版本**可以作为解释提交后发现的缺陷的行为基线。若某缺陷仅在提交后版本中出现，则更可能是由该提交引入的。

#### 总体流程（差分切片模糊测试）
1. **输入**：目标提交（post-commit）和基线提交（pre-commit，通常为直接前驱）。
2. **识别修改函数**：通过 diff 找出两版本间被修改的函数；排除新增函数（无法差分）和删除函数。
3. **构造配对切片**：对每个修改函数，分别从提交前和提交后版本提取可编译的代码切片（包含目标函数及其编译运行所需依赖），形成一一对应的切片对。
4. **模糊测试配对切片**：为每个切片生成模糊测试包装器（基于参数类型自动构造），链接成可执行二进制，使用 AFL++ 进行独立模糊测试，并启用消毒器（ASan、LSan、UBSan、MSan）。
5. **差分缺陷判定（核心机制）**：
   - 仅当缺陷报告满足以下条件时才视为候选提交引入缺陷：
     - 缺陷出现在提交后切片中；
     - 同一位置（映射后）在提交前切片中无同类缺陷报告；
     - 该映射位置在提交前切片中可达（排除覆盖率差异造成的假象）。
6. **输入重放**：为了减少随机模糊探索不均衡带来的干扰，将两边发现的测试用例互相重放到对方切片上，提升差分比较的可靠性。

#### 技术亮点
- 复用 FUZZSLICE 作为切片和编译后端，但核心新增了**提交级配对、差分执行与报告逻辑**。
- 包装器生成时利用 tree-sitter 分析切片实际使用的结构体字段，仅初始化相关字段，减少模糊输入维度。
- 在 Kubernetes 集群上并行处理多个提交和函数，提升吞吐量。

### 六、主要结论与发现

- **有效性**：C OMMITGUARD 在 300 个提交上，将 518 份原始消毒器报告缩减至 **7 份候选提交引入缺陷报告**，人工确认其中 **5 份为真实缺陷**（开发者已修复），2 份为误报。
- **效率**：平均每次提交分析耗时为 **32.4 分钟**，每个函数平均 24.1 分钟；修改函数平均覆盖率为 **75.36%**，说明能够在可接受时间内覆盖大部分变更代码。
- **检测缺陷类型**：包括缓冲区溢出、内存泄漏、缓冲区越界读取、空指针解引用、整数溢出等；且部分缺陷并非直接由修改点引发，而是由于提交改变控制流/分配行为/可达性而暴露的潜在缺陷。
- **误报原因**：主要由两种情形导致——①孤立切片丢失全程序前置条件（如调用方保证参数非 NULL）；②函数签名变更导致自动生成包装器编码不同，削弱输入重放效果。

### 七、优点

- **问题定位准确**：将提交前版本作为行为基线，从大量模糊测试噪声中精准筛选与提交相关的报告，极大降低人工分类负担（518→7）。
- **面向实际需求**：无需手动编写测试用例或全程序模糊测试，直接基于提交进行自动化验证，适合在代码审查期间提供反馈。
- **可解释性强**：差分机制逻辑清晰，每个报告附带缺陷类型、位置和栈轨迹，便于开发者复现和修复。
- **效率与覆盖率兼顾**：通过函数级切片和并行执行，在较短时间内达到较高修改函数覆盖率。
- **真实缺陷验证**：报告送交开发者后获得确认和修复，证明方法具有实际价值。

### 八、不足与局限

- **新增函数无法直接分析**：新添加的函数没有提交前对应版本，无法进行差分，可能遗漏完全位于新函数中的缺陷。
- **孤立切片可能违反全程序不变量**：切片缺少调用方约束，会产生某些“在切片中可实现但全程序中不可触发”的误报。
- **签名变更影响差分可靠性**：提交若改变函数签名或输入结构，自动生成的包装器可能不一致，导致输入重放失效，产生误报。
- **仅覆盖消毒器可检测的缺陷**：无法检测语义级错误（如错误返回值、逻辑错误）或未触发内存安全问题的行为回归。
- **实验覆盖有限**：仅三个 C 项目、短模糊预算、无对比基线，结果外推需谨慎；同时未报告漏报率（无法知道有多少真实缺陷未被发现）。
- **计算资源依存于 Kubernetes**：实际部署需要并行基础设施，对小型项目/开发者个人环境可能不够便捷。
