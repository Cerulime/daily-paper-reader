## 摘要
基于静态分析的漏洞检测传统上依赖于安全专家将不安全的编码模式编码为算法规则。然而，这种方法通常侧重于语法模式，而忽略了代码中更深层的语义信息，例如变量和函数名称的含义。随着软件系统变得越来越复杂，仅使用语法规则对漏洞进行建模变得越来越具有挑战性。在本文中，我们提出了一种语义感知的软件漏洞检测方法。我们提出了SETYPE，一种语义感知的类型系统，它可以仅根据自然语言中符号和表达式的含义直接从源代码派生。在SETYPE类型系统中，类型推断和检查都由大型语言模型（LLM）执行，类型检查失败表示存在潜在漏洞。我们制作了原型PYSETYPE来证明SETYPE在检测Python Web应用程序漏洞方面的可行性。我们在真实世界应用程序上的评估实现了87%的检测精确率和88%的检测准确率。使用PYSETYPE，我们识别了15个潜在的零日漏洞，其中9个已得到开发人员确认。

## Abstract
Vulnerability detection via static analysis traditionally relies on security experts encoding insecure coding patterns into algorithmic rules. However, this approach often focuses on syntactic patterns and overlooks deeper semantic information in the code, such as the meanings of variable and function names. As software systems grow more complex, modeling vulnerabilities using only syntactic rules becomes increasingly challenging.   In this paper, we propose a semantics-aware approach to detecting software vulnerabilities. We present SETYPE, a semantics-aware type system that can be derived directly from source code based solely on the meanings of symbols and expressions in natural language. In the SETYPE type system, both type inference and checking are performed by Large Language Models (LLMs), and a failed type check indicates a potential vulnerability.   We prototype PYSETYPE to demonstrate the feasibility of SETYPE for detecting vulnerabilities in Python web applications. Our evaluation on real-world applications achieves 87% detection precision and 88% detection accuracy. Using PYSETYPE, we identified 15 potential zero-day vulnerabilities, nine of which were confirmed by developers.

## 2. 论文提出的方法论

**核心思想：SETYPE 语义类型系统**

- **SETYPE 的定义**：将每个变量和表达式赋予一个"语义类型"（如 "user input"、"file path from user"），所有类型是自然语言描述而非传统编程类型（int、string）。
- **双向类型系统**：借鉴编程语言中的 bidirectional type system，每个操作同时执行类型推断和类型检查。类型检查成功 = 程序无该类型可检测的漏洞；类型检查失败 = 潜在漏洞。
- **形式化规则**：论文给出 SETYPE 的类型推导规则，包括变量初始化（根据非执行上下文如变量名、注释推断初始类型）、表达式类型合成、赋值类型统一等。其中 inf、op、unify 三个关键函数由 LLM 实现。

**实现框架：PYSETYPE**

PYSETYPE 是 pytype（Google 的 Python 静态类型分析器）的扩展，流程分为三步：

1. **程序准备（Program Preparation）**：
   - 运行 pytype 生成依赖库的接口存根（.pyi 文件）和逐文件对象映射；
   - 识别程序入口点：main 函数 + Flask/FastAPI 路由装饰器 + Django URL 配置和类视图；
   - 构建字节码级别的 CFG（IPCFG）。

2. **SETYPE 推理（SETYPE Reasoning）**：
   - 在 pytype 虚拟机中沿 CFG 按拓扑序遍历基本块，模拟程序执行；
   - 对每个关键操作（赋值、函数调用、分支、循环、合并），使用提示模板查询 LLM，获取更新后的 SETYPE；
   - 关键提示模板：赋值、函数调用、分支合并、循环归纳、条件分支，每个提示约 200 tokens，保证 LLM 聚焦单一任务；
   - 在循环处理中用基于第一轮迭代前后的类型归纳推理最终类型。

3. **漏洞发现（Vulnerability Finding）**：
   - 针对 12 种常见 Web 漏洞类型（CWE-22、CWE-78、CWE-79、CWE-89、CWE-601、CWE-918 等）设计漏洞规则；
   - 采用**基于检查清单的验证策略**：将漏洞判定拆解为多个独立问题（如路径遍历三条检查：是否访问路径、路径是否由外部用户数据构造、函数是否自动消毒路径），逐项询问 LLM 后聚合决定；
   - 通过污点分析减少 LLM 查询次数（已标记为受污染的数据跳过来源检查）；
   - 仅在外部函数调用（非目标项目内定义）时进行漏洞检查。

**设计选择与替代方案对比：**
- 方案一（直接喂整个代码库给 LLM）：上下文受限、注意力分散，不可行。
- 方案二（让 LLM 生成规则供静态分析器执行）：规则不完全、LLM 随机性导致 F1 太低。
- 方案三（本文）：确定性遍历 + LLM 局部类型推理，兼顾覆盖完整性和语义灵活性。

## 6. 论文的主要结论与发现

1. **PYSETYPE 在 SVEN 数据集上全面优于所有基线**：精确率 0.87（CodeQL 0.67、Bandit 0.75、Vulnhuntr 0.52），召回率 0.87（CodeQL 0.39、Bandit 0.84、Vulnhuntr 0.45），F1 0.87（CodeQL 0.49、Bandit 0.79、Vulnhuntr 0.48）；
2. **在近期 CVE 数据集上**，所有工具性能均下降，但 PYSETYPE 仍然最优（F1 0.78 vs 0.33-0.53），表明检测能力不是来自训练数据泄漏，而是对未见漏洞具有泛化能力；
3. **零日漏洞发现**：在 103 个流行开源项目中识别出 15 个安全关键漏洞（9 个路径遍历、5 个开放重定向、1 个 SQL 注入），其中 9 个已获开发者确认，涉及微软官方库、Python 软件基金会服务器基础设施、美国 IRS 维护的系统；
4. **框架特征洞见**：开放重定向在 Django 项目中更常见（与框架的 "next" 参数设计相关），路径遍历在 Flask 项目中更常见（框架自由度高，缺乏内置 ORM 和文件处理约束）；
5. **静态分析的限制**：PYSETYPE 无法分析静态不可达的代码（如 Django 多态调用的方法重写、配置文件驱动的动态导入）和 Python 动态特性；
6. **LLM 幻觉仍然存在**：部分误报来自 LLM 错误判断（如将普通变量误认为用户可控输入、虚构不存在的危险函数）。

## 7. 优点

1. **新颖的研究视角**：将漏洞类比为类型错误，利用双向类型系统框架精确地组织了 LLM 在代码分析中的角色，避免了"全权交给 LLM"和"完全规则化"两端的缺陷；
2. **可控的 LLM 使用方式**：将分析拆解为约 200 token 的小型查询，每个查询聚焦单一任务，显著降低幻觉概率；同时采用检查清单策略引导系统推理，提高判断的结构化程度；
3. **工程实现务实**：基于 pytype 扩展而非从零构建，复用其成熟的 CFG/VM 基础设施，代码量仅约 3000 行；
4. **评估严谨**：使用知识截止日期后的 CVE 控制记忆偏差，在多个数据集上验证；零日漏洞挖掘结果有明确的开发者确认记录，可信度较高；
5. **成本分析透明**：详细报告了时间和经济成本，证明该方法在可接受成本内具备实际部署价值；
6. **细致的案例分析**：同时展示优势案例和失败案例，且对失败原因进行了深入分析（静态不可达、多态、LLM 幻觉、不完整补丁），为后续研究提供了参考。

## 8. 不足与局限

**方法/实验层面的局限：**

1. **静态分析固有盲区**：
   - 无法处理动态导入、元类、复杂装饰器等动态特性；
   - 无法分析静态不可达代码（如通过继承/多态被框架调用的方法重写）；
   - pytype 的间接调用映射不完整时可能漏掉函数调用；
2. **跨语言交互未充分建模**：Python 与 HTML 模板间的 XSS 等问题仅靠启发式处理（字符串模式匹配、将模板渲染看作不透明调用），无法精确建模跨语言语义；
3. **LLM 幻觉和非确定性**：LLM 可能在相似代码上给出不一致判断；在复杂/大项目中误报率显著上升（33 个告警中 15 个真实，误报率升高）；
4. **实现范围有限**：仅支持 Python 3.10；仅支持 Flask/Django/FastAPI 三个框架；仅覆盖 12 个 CWE 类型；目标漏洞以 Web 应用为主，通用性受限；
5. **数据集偏差风险**：SVEN 数据集（2016-2018 年漏洞）可能不代表现代的漏洞特征；近期 CVE 数据集规模较小（仅 9 个 CVE）；流行项目数据集中人工筛选存在主观性；
6. **评估一致性**：对基线工具误报/漏报的人工核查存在主观判断空间，未报告多轮运行的方差数据；
7. **未解决的现实案例**：补丁有时未真正修复漏洞（如 CVE-2025-6776 只是添加了登录限制而非输入消毒），导致在"已补丁"版本上 PYSETYPE 持续告警——这对实际使用中的"准确率"定义提出了挑战。

**潜在改进方向：** 跨语言分析、支持更多 Python 版本和框架、自动化漏洞规则生成、动态分析辅助静态不可达代码、更强健的 LLM 查询策略（如多轮交叉验证）等。
